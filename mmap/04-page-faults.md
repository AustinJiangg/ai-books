# 第 4 篇｜缺页异常：操作系统的"按需供货"魔法

> **本篇目标**：理解访问一个"不存在"的页时发生了什么——**缺页异常（page fault）**的完整流程；分清小缺页、大缺页和段错误；用实验证明"申请了内存 ≠ 占用了内存"。这是理解 mmap 为什么能"瞬间映射 10GB 文件"的关键。

---

## 一、先讲一个外卖店的故事

你开了一家外卖店，菜单上有 200 道菜。你有两种经营方式：

**方式一：提前备齐。** 每天开门前，把 200 道菜全部做好摆在柜台上。顾客点什么都能立刻拿走。但大部分菜根本没人点，最后全浪费了，而且每天开门前要忙好几个小时。

**方式二：按单现做。** 菜单照样挂着 200 道菜，但厨房里什么都不提前做。顾客点了哪道，才去做哪道。第一次点某道菜需要等一会儿，但不浪费，开门也很快。

现代操作系统管理内存，用的就是**方式二**。

- "菜单上有 200 道菜" = 进程的地址空间里登记了一大片合法区域；
- "厨房里什么都没做" = 页表项全都是无效的，没有分配物理内存；
- "顾客点菜" = 程序第一次访问某个地址；
- "现做" = 内核临时分配物理页、填好数据、改好页表。

这种策略叫**按需分页（demand paging）**，而"顾客点菜"这一刻触发的事件，叫**缺页异常（page fault）**。

---

## 二、缺页异常是什么

回忆上一篇：每个页表项都有一个**有效位**。当程序访问一个虚拟地址时，MMU 去查页表，如果发现：

- 对应的页表项**无效**（或者中间某一级表根本不存在）；或者
- 页表项有效，但**权限不符**（比如往只读页里写）；

MMU 无法完成翻译，就会**中断当前指令**，产生一个异常，把控制权交给内核。这就是**缺页异常**。

"异常"这个词听起来像是出错了，但在这里它完全是**正常业务流程**的一部分。一个程序从启动到退出，通常会经历成千上万次缺页异常，绝大多数都是内核"故意安排"的。

---

## 三、ARM64 上的完整流程

我们以 ARM64 为例，慢镜头回放一次缺页异常。

```
 用户程序 (EL0)                硬件 (MMU/CPU)                     内核 (EL1)
 ─────────────                ──────────────                     ──────────
 执行 ldr x0, [x1]
 (读 x1 指向的地址)
        │
        └─────────────▶  查 TLB：未命中
                         查页表：L3 页表项无效！
                         │
                         ├─ 把出错的虚拟地址存入 FAR_EL1
                         ├─ 把出错原因存入 ESR_EL1
                         ├─ 把出错指令的地址存入 ELR_EL1
                         └─ 切换到 EL1，跳到异常向量表 ──────▶  ① 读 ESR：是"数据访问异常"
                                                               ② 读 FAR：出错地址是 X
                                                               ③ X 属于进程的合法区域吗？
                                                               ④ 合法：准备物理页，填数据
                                                               ⑤ 修改页表项，设为有效
                                                               ⑥ eret 返回
                         ◀────────────────────────────────────
                         回到 ELR_EL1 指向的那条指令
        ◀────────────────  重新执行 ldr x0, [x1]
 这次成功了！              （页表已有效，翻译成功）
 程序浑然不觉
```

几个关键点：

**1. 硬件留下"案发现场"。** ARM64 用三个寄存器记录现场：

| 寄存器 | 记录的内容 |
|---|---|
| `FAR_EL1`（Fault Address Register） | 访问出错的**虚拟地址** |
| `ESR_EL1`（Exception Syndrome Register） | 出错的**原因**：是读还是写？是哪一级页表缺失？还是权限错误？ |
| `ELR_EL1`（Exception Link Register） | 出错**指令**的地址，处理完后从这里继续 |

**2. 指令会被重新执行。** 这是缺页异常最妙的地方。处理完毕后，CPU 回到**出错的那条指令**重新执行，而不是跳过它。第二次执行时页表已经准备好了，指令顺利完成。程序完全感觉不到中间发生了什么，只是这条指令"执行得比平时慢了一点"。

**3. 内核的判断依据。** 第③步，内核怎么知道地址 X 是不是"合法区域"？内核为每个进程维护了一份"菜单"，记录哪些地址范围是合法的、权限是什么、背后关联着什么（文件？匿名内存？）。你在 `/proc/self/maps` 里看到的每一行，就是菜单上的一个条目。这个数据结构叫 **VMA**，第 11 篇会深入讲。

> 关键区分：**"菜单"（VMA）和"页表"是两回事。** 菜单记录"你被允许用哪些地址"；页表记录"哪些地址现在真的有物理页"。菜单上有、页表里没有，就是"可以点但还没做的菜"——访问时触发缺页，内核现做。

## 四、缺页的几种情况

内核在第③④步会根据具体情况做不同处理。

### 情况一：首次访问匿名内存 → 分配一个清零的页

程序 `malloc` 了一大块内存，第一次往里写数据。这块地址在菜单上（合法），但页表里还没有。

内核的处理：从空闲物理页里拿一个，**全部填 0**，填入页表，返回。

为什么要填 0？因为这个物理页上一次可能被别的进程用过，里面可能有别人的密码、私信。不清零就会泄露数据。

### 情况二：访问文件映射，数据已在内存 → 直接挂上

程序访问了一段 mmap 映射的文件区域，而这部分文件内容恰好已经在内存的缓存里（第 5 篇的 page cache）。

内核的处理：找到那个缓存页，直接让页表项指向它。不用读磁盘，很快。

### 情况三：访问文件映射，数据不在内存 → 从磁盘读

和情况二一样，但文件内容不在内存里。

内核的处理：分配物理页，向磁盘发出读请求，**让当前进程睡眠等待**，CPU 去运行别的进程。磁盘读完后，唤醒进程，填好页表，返回。这可能需要几十微秒到几十毫秒。

### 情况四：写一个只读页 → 写时复制或报错

页表项有效但标为只读，程序却要写。内核检查菜单：

- 如果菜单说这块区域**本来就可写**，只是页表故意设成只读，那这是**写时复制**（Copy-on-Write）的信号：复制一份私有副本给程序写（第 7 篇详讲）；
- 如果菜单说这块区域**本来就只读**，那就是程序的错。

### 情况五：地址根本不在菜单上 → 段错误

程序访问了一个菜单上不存在的地址，比如空指针、野指针、数组越界越到了空白区域。

内核的处理：向进程发送 **SIGSEGV 信号**，默认动作是杀死进程。你看到的就是著名的：

```
Segmentation fault (core dumped)
```

**段错误的本质，就是一次内核无法"兑现"的缺页异常。**

---

## 五、小缺页与大缺页

内核把成功处理的缺页分成两类：

| 类型 | 英文 | 特点 | 典型耗时 |
|---|---|---|---|
| **小缺页** | minor fault | 不需要读磁盘：分配清零页、挂上已缓存的页 | 约 0.1～几微秒 |
| **大缺页** | major fault | 需要从磁盘读数据 | SSD 约几十～几百微秒，机械硬盘几毫秒以上 |

两者的耗时可能相差上千倍。分析 mmap 性能时，第一件事就是看大缺页有多少。

## 六、实验：申请了内存 ≠ 占用了内存

### 6.1 实验程序

```c
// lazy.c —— 观察按需分页
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/resource.h>

// 从 /proc/self/status 读取 VmRSS（实际占用的物理内存）
static long rss_kb(void) {
    FILE *f = fopen("/proc/self/status", "r");
    char line[256];
    long kb = -1;
    while (fgets(line, sizeof line, f)) {
        if (strncmp(line, "VmRSS:", 6) == 0) {
            sscanf(line + 6, "%ld", &kb);
            break;
        }
    }
    fclose(f);
    return kb;
}

static long minor_faults(void) {
    struct rusage ru;
    getrusage(RUSAGE_SELF, &ru);
    return ru.ru_minflt;
}

int main(void) {
    const size_t size = 1UL << 30;            // 1GB
    const long page = sysconf(_SC_PAGESIZE);

    printf("开始：        RSS = %6ld KB, 小缺页 = %ld\n", rss_kb(), minor_faults());

    char *p = malloc(size);
    if (!p) { perror("malloc"); return 1; }
    printf("malloc 1GB 后：RSS = %6ld KB, 小缺页 = %ld\n", rss_kb(), minor_faults());

    // 只写前 100MB，每页写一个字节
    for (size_t i = 0; i < 100UL * 1024 * 1024; i += page)
        p[i] = 1;
    printf("写 100MB 后： RSS = %6ld KB, 小缺页 = %ld\n", rss_kb(), minor_faults());

    // 把剩下的也写了
    for (size_t i = 0; i < size; i += page)
        p[i] = 1;
    printf("写满 1GB 后： RSS = %6ld KB, 小缺页 = %ld\n", rss_kb(), minor_faults());

    free(p);
    return 0;
}
```

```bash
gcc -O1 lazy.c -o lazy && ./lazy
```

### 6.2 典型输出（4KB 页）

```
开始：        RSS =   1408 KB, 小缺页 = 89
malloc 1GB 后：RSS =   1408 KB, 小缺页 = 91
写 100MB 后： RSS = 103944 KB, 小缺页 = 25691
写满 1GB 后： RSS = 1050132 KB, 小缺页 = 262236
```

> 如果你的系统开启了透明大页（第 10 篇），缺页次数可能会少得多，因为一次缺页可能直接分配 2MB。可以用 `cat /sys/kernel/mm/transparent_hugepage/enabled` 查看。

### 6.3 解读

1. **`malloc(1GB)` 之后，RSS 几乎没变。** 申请 1GB 只是在"菜单"上登记了一段地址，没有分配任何物理内存。
2. **写了 100MB 之后，RSS 涨了约 100MB，缺页增加了约 25600 次。** 100MB ÷ 4KB = 25600，每页一次缺页，完美对应。
3. **写满 1GB 后，缺页总数约 26 万次**，对应 1GB ÷ 4KB = 262144 页。

这就是按需分页：**内存是在第一次被触碰时才真正分配的。**

### 6.4 用工具统计缺页

不改代码也可以统计任何程序的缺页次数：

```bash
/usr/bin/time -v ./lazy 2>&1 | grep -i fault
#   Major (requiring I/O) page faults: 0
#   Minor (reclaiming a frame) page faults: 262236

# 或者用 perf
perf stat -e page-faults,minor-faults,major-faults ./lazy
```

### 6.5 观察大缺页

大缺页需要从磁盘读数据。我们先清空系统的文件缓存（第 5 篇解释），然后运行一个"大"程序：

```bash
sync; echo 3 | sudo tee /proc/sys/vm/drop_caches
/usr/bin/time -v python3 -c "pass" 2>&1 | grep -i "page faults"
#   Major (requiring I/O) page faults: 87      ← 冷启动：要从磁盘读 Python 的代码
#   Minor (reclaiming a frame) page faults: 1012

/usr/bin/time -v python3 -c "pass" 2>&1 | grep -i "page faults"
#   Major (requiring I/O) page faults: 0       ← 再跑一次：都在内存里了
#   Minor (reclaiming a frame) page faults: 1018
```

第一次运行时，Python 解释器和它的库都不在内存里，访问代码时触发了大缺页；第二次运行，这些文件已被缓存，大缺页变成 0。（这个实验会清空整个系统的文件缓存，别在繁忙的生产服务器上做。）

## 七、实验：亲手制造一次段错误

```c
// segv.c
#include <stdio.h>

int main(void) {
    int *p = (int *)0x1234;   // 一个肯定不在"菜单"上的地址
    printf("准备访问 %p ...\n", (void *)p);
    *p = 42;                  // 触发缺页 → 内核查菜单 → 不合法 → SIGSEGV
    printf("这句永远不会打印\n");
    return 0;
}
```

```bash
gcc segv.c -o segv && ./segv
# 准备访问 0x1234 ...
# Segmentation fault (core dumped)

dmesg | tail -2      # 可能需要 sudo
# segv[6001]: unhandled level 0 translation fault (11) at 0x0000000000001234, esr 0x92000044
```

内核日志里的 `level 0 translation fault` 说明：MMU 在**第 0 级页表**就发现条目无效了（这一大片区域根本没有页表）。`esr 0x92000044` 就是 ESR_EL1 寄存器的值，内核正是解码它得知"这是一次写操作导致的第 0 级翻译错误"。

## 八、按需分页带来的好处与代价

### 好处

1. **启动快**：程序启动时不需要把整个程序读进内存，用到哪部分读哪部分。
2. **省内存**：申请了没用的内存不占物理空间。很多程序会预留大块内存但只用一小部分。
3. **可以"超额"**：所有进程申请的内存总和可以超过物理内存。Linux 默认允许这种**内存超售（overcommit）**。
4. **为 mmap 铺平道路**：mmap 一个 10GB 的文件可以瞬间完成，因为它只是在"菜单"上登记，什么都不读。

### 代价

1. **第一次访问变慢**：每个页第一次被访问都要付出一次缺页的开销。对于"马上要全部用到"的内存，可以用 `MAP_POPULATE` 或 `madvise` 提前填充（第 10 篇）。
2. **超售的风险**：如果大家同时兑现承诺，物理内存不够了怎么办？内核会先尝试回收缓存、把不常用的页换出到磁盘（swap），实在不行就启动 **OOM Killer**（内存耗尽杀手），挑一个进程杀掉。
3. **延迟不可预测**：一次普通的内存读取，可能因为大缺页而卡住几毫秒。对延迟敏感的程序（比如交易系统、实时音视频）这是个大问题，可以用 `mlock` 把页面锁在内存里。

## 九、和 mmap 的关系

把本篇和前几篇连起来，mmap 的原理已经呼之欲出了：

```
调用 mmap(文件, 10GB)
   │
   └─▶ 内核只在"菜单"上登记：
       "地址 0xffff00000000 ~ 0xffff80000000 对应 文件 的 0~10GB 处"
       页表：一个都不填。 物理内存：一个字节都不分配。
       立即返回。

程序第一次读 p[5000]
   │
   └─▶ 缺页异常！
       内核查菜单：这个地址对应文件第 1 页（5000 / 4096 = 1）
       ├─ 文件第 1 页已在内存缓存中？ → 小缺页：直接挂上
       └─ 不在？ → 大缺页：从磁盘读进来，再挂上
       修改页表，重新执行指令，程序读到了数据

程序再读 p[5001]
   │
   └─▶ 同一页，页表已有效，TLB 命中，和读普通内存一样快
```

**mmap 不读文件，缺页才读文件。** 这就是 mmap 能"瞬间映射任意大文件"、并且"只为真正访问的部分付出代价"的秘密。

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 按需分页 | 内存在第一次被访问时才真正分配 |
| 缺页异常 | 访问无效页或违反权限时，MMU 交给内核处理的异常 |
| FAR / ESR / ELR | ARM64 记录出错地址、出错原因、出错指令的寄存器 |
| 指令重新执行 | 缺页处理完后重新执行出错指令，程序无感知 |
| VMA（菜单） vs 页表 | 前者记录哪些地址合法，后者记录哪些地址已有物理页 |
| 小缺页 | 不需要读磁盘，微秒级 |
| 大缺页 | 需要读磁盘，可能慢上千倍 |
| 段错误 SIGSEGV | 访问不合法地址时，内核无法处理的缺页 |
| overcommit / OOM | 允许超额申请；真不够了就杀进程 |
