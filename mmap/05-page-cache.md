# 第 5 篇｜页缓存：文件在内存里的"分身"

> **本篇目标**：认识 Linux 内核里最重要的缓存——**页缓存（page cache）**。理解读写文件时数据在哪里停留、脏页是什么、什么时候写回磁盘，并看清 `read` 与 mmap 在数据通路上的本质区别。

---

## 一、为什么需要页缓存

第 2 篇我们知道，读内存比读 SSD 快上千倍，比读机械硬盘快十万倍。同时，程序访问文件有很强的**局部性**：

- 刚读过的文件，很可能马上又要读（比如你反复编译同一个项目，头文件被读了无数次）；
- 读了文件的第 1 页，很可能接着读第 2、3 页。

于是内核做了一件很自然的事：**把从磁盘读出来的文件内容留在内存里**，下次再有人读，直接从内存拿。

这块用来缓存文件内容的内存，就叫**页缓存（page cache）**。名字里有"页"，因为它也以页（通常 4KB）为单位管理。

打个比方：图书馆的书都在地下书库（磁盘），取书要等管理员下去找。聪明的图书馆会在阅览室门口设一个"热门书架"（page cache），最近被借过的书先放在这里，下一个人要借直接拿。

## 二、页缓存长什么样

### 2.1 以文件为单位组织

页缓存不是一锅大杂烩，而是**按文件组织**的。内核为每个被打开过的文件维护一个"缓存目录"，记录：

> 这个文件的第 0 页、第 1 页、第 7 页……分别缓存在哪个物理页上。

```
 文件 /data/a.txt（12KB = 3 页）的缓存目录
 ┌──────────┬────────────────────┐
 │ 文件页号   │  物理页             │
 ├──────────┼────────────────────┤
 │    0     │  物理页 #1024        │
 │    1     │  （不在缓存中）       │
 │    2     │  物理页 #5577        │
 └──────────┴────────────────────┘
```

在 Linux 内核里，这个目录叫 **`address_space`**（名字有点误导，它其实是"某个文件在内存里的缓存"），每个文件的 inode 都有一个。第 11 篇会再见到它。

### 2.2 全局唯一

一个文件的某一页，在整个系统里**只有一份缓存**。无论多少个进程打开了这个文件，无论是用 `read` 读还是用 mmap 访问，用的都是同一份。这一点对理解 mmap 至关重要。

---

## 三、read 的完整过程

现在我们可以把第 1 篇的 `read` 讲得更精确了。程序调用 `read(fd, buf, 4096)` 读取文件的第 N 页：

```
          read(fd, buf, 4096)
                  │
                  ▼
   ┌──────── 查页缓存：第 N 页在吗？ ────────┐
   │ 在（缓存命中）                         │ 不在（缓存未命中）
   │                                       ▼
   │                         分配一个物理页，加入缓存目录
   │                         向磁盘发出读请求（DMA）
   │                         进程睡眠等待……磁盘完成，唤醒
   │                                       │
   ▼                                       ▼
   ┌───────────────────────────────────────────┐
   │   CPU 把页缓存里的数据 **拷贝** 到用户的 buf   │
   └───────────────────────────────────────────┘
                  │
                  ▼
              read 返回
```

注意两点：

1. 即使缓存命中，**拷贝依然发生**：数据要从页缓存（内核地盘）复制到 `buf`（用户地盘）。
2. 此刻同一份数据在内存里存了**两份**：一份在页缓存，一份在你的 `buf`。

### 3.1 预读：猜你下一步要读什么

磁盘有个特点：一次读 128KB 和一次读 4KB，耗时差别不大（主要成本在"找到位置"）。所以内核在发现你**顺序读**文件时，会主动多读一些后面的内容放进页缓存，这叫**预读（readahead）**。

- 内核默认的预读窗口通常是 128KB，可以调整（`/sys/block/<设备>/queue/read_ahead_kb`）；
- 如果你持续顺序读，预读窗口会逐渐扩大；
- 如果你跳来跳去地读，内核发现预读没用，会减少或停止预读。

预读机制对 mmap 同样生效，第 10 篇会讲如何用 `madvise` 调整它。

## 四、write 的完整过程：脏页

写文件时，内核同样借助页缓存，而且更"偷懒"：

```
          write(fd, buf, 4096)
                  │
                  ▼
   确保文件第 N 页在页缓存中（必要时先从磁盘读进来）
                  │
                  ▼
   CPU 把 buf 里的数据 **拷贝** 到页缓存
                  │
                  ▼
   把这一页标记为 "脏"（dirty）
                  │
                  ▼
   write 立即返回！ ← 此时数据还没到磁盘
```

**`write` 返回成功，并不代表数据已经写到磁盘上。** 数据只是进了页缓存。这种策略叫**写回缓存（write-back cache）**。

被修改过、还没写回磁盘的页，叫**脏页（dirty page）**。干净页（clean page）表示内容和磁盘上一致。

### 4.1 为什么要这么偷懒？

- **快**：写内存是纳秒级，写磁盘是微秒到毫秒级。让程序等磁盘太浪费了。
- **合并**：如果程序对同一页连续写了 100 次，只需要最后写回磁盘一次。
- **排序**：内核可以把很多脏页攒起来，按磁盘上的位置排好顺序再写，效率更高。

### 4.2 脏页什么时候写回？

Linux 内核有专门的后台线程负责把脏页写回磁盘，触发时机主要有：

| 触发条件 | 相关参数（`/proc/sys/vm/`） | 默认值 |
|---|---|---|
| 脏页存在时间太久 | `dirty_expire_centisecs` | 3000（即 30 秒） |
| 后台线程定期醒来检查 | `dirty_writeback_centisecs` | 500（即 5 秒） |
| 脏页占可用内存比例过高，后台开始写 | `dirty_background_ratio` | 10% |
| 脏页比例太高，**写进程被强制等待** | `dirty_ratio` | 20% |
| 程序主动要求 | `fsync`、`fdatasync`、`sync` | — |
| 内存紧张需要回收这一页 | — | — |

### 4.3 断电了怎么办？

既然数据可能在页缓存里停留几十秒，那么断电或系统崩溃时，这些脏页就**丢了**。

所以，对数据可靠性有要求的程序（数据库、版本控制系统等）在关键时刻会调用：

```c
fsync(fd);       // 把这个文件的脏页（和元数据）全部写到磁盘，等写完才返回
fdatasync(fd);   // 类似，但尽量不写不必要的元数据（比如修改时间），更快
```

mmap 也有对应的 `msync`，第 9 篇详讲。

## 五、为什么 Linux 总是"吃光"内存？

### 5.1 常见的困惑

很多人第一次在 Linux 上运行 `free`，会被吓一跳：

```bash
free -h
```

```
               total        used        free      shared  buff/cache   available
Mem:            15Gi       3.1Gi       420Mi       210Mi        12Gi        12Gi
Swap:          2.0Gi          0B       2.0Gi
```

"16GB 内存只剩 420MB 空闲了！内存泄漏了吗？"

不是的。看 `buff/cache` 那一列：**12GB 被用来做了缓存**，其中绝大部分就是页缓存。

### 5.2 空闲内存就是浪费的内存

Linux 的哲学是：**空着的内存一点用都没有。** 既然现在没人要用这些内存，不如拿来缓存文件，说不定下次就能省一次磁盘读取。

而一旦有程序真的需要内存，内核会立刻**回收**页缓存：

- **干净的缓存页**：内容和磁盘一致，直接丢弃即可，瞬间完成；
- **脏页**：必须先写回磁盘，才能回收。

所以真正应该看的是 **`available`** 这一列：它估算了"如果有程序要内存，大约能拿出多少"，包括了可以回收的缓存。上面的例子里，available 有 12GB，系统非常健康。

### 5.3 回收哪些页？

内核用类似 **LRU（最近最少使用）** 的策略决定回收谁：最近很久没被访问的页优先被回收。具体做法是维护"活跃"和"不活跃"两个链表，并参考第 3 篇提到的页表**访问标志（AF）**来判断一个页最近是否被访问过。较新的内核还引入了更精细的多代 LRU（MGLRU）。

## 六、实验

### 实验 1：感受缓存的威力

```bash
# 生成一个 1GB 的文件
dd if=/dev/urandom of=big.bin bs=1M count=1024

# 清空页缓存（需要 root，生产环境慎用）
sync; echo 3 | sudo tee /proc/sys/vm/drop_caches

# 第一次读：从磁盘读
time cat big.bin > /dev/null

# 第二次读：从页缓存读
time cat big.bin > /dev/null
```

典型结果：第一次可能要几百毫秒到几秒（取决于磁盘），第二次只要一两百毫秒甚至更短。差距就是磁盘和内存的差距。

### 实验 2：看缓存涨落

```bash
sync; echo 3 | sudo tee /proc/sys/vm/drop_caches
free -m           # 记下 buff/cache
cat big.bin > /dev/null
free -m           # buff/cache 增加了约 1024MB
```

### 实验 3：查看某个文件有多少在缓存中

util-linux 自带一个小工具 `fincore`：

```bash
fincore big.bin
#   RES PAGES  SIZE FILE
#    1G 262144   1G big.bin        ← 整个文件都在缓存里

sync; echo 3 | sudo tee /proc/sys/vm/drop_caches
fincore big.bin
#   RES PAGES  SIZE FILE
#    0B     0   1G big.bin        ← 全被清掉了
```

（有趣的是，`fincore` 本身就是用 mmap + `mincore` 系统调用实现的：映射文件，再问内核"这些页哪些在内存里"。）

### 实验 4：观察脏页

```bash
grep -E "Dirty|Writeback" /proc/meminfo
# Dirty:               120 kB
# Writeback:             0 kB

dd if=/dev/zero of=dirty.bin bs=1M count=500     # 写 500MB，立即返回
grep -E "Dirty|Writeback" /proc/meminfo
# Dirty:            512104 kB                     ← 500MB 脏页，还没写到磁盘

sync                                               # 强制写回
grep -E "Dirty|Writeback" /proc/meminfo
# Dirty:               136 kB                     ← 写回完成
```

你会发现 `dd` 写 500MB 几乎瞬间完成，而后面的 `sync` 才是真正在等磁盘。（如果你的系统内存较小，`dd` 可能在写的过程中就因为 `dirty_ratio` 被迫等待了。）

## 七、绕过页缓存：直接 I/O

既然页缓存这么好，有没有人不想要它？

有。一些数据库（比如 MySQL 的 InnoDB、PostgreSQL 的部分配置）会用 **`O_DIRECT`** 标志打开文件，绕过页缓存，让数据在磁盘和用户缓冲区之间直接传输。原因是：

- 数据库自己有一套更懂业务的缓存（buffer pool），内核再缓存一份就是**双重缓存**，浪费内存；
- 数据库需要精确控制数据何时写入磁盘、以什么顺序写入。

记住这个思路，第 12 篇讲"为什么有的数据库不用 mmap"时还会遇到。

## 八、关键领悟：read 与 mmap 的本质区别

现在，所有的拼图都齐了。

### 8.1 read：从缓存复制一份给你

```
  ┌────────────── 内核地盘 ──────────────┐     ┌───── 用户地盘 ─────┐
  │                                      │     │                    │
  │   页缓存  [物理页 #1024: 文件第0页]   │ ─── 拷贝 ──▶ buf[4096]    │
  │                                      │     │  （物理页 #3000）   │
  └──────────────────────────────────────┘     └────────────────────┘

  同一份数据，内存里有 2 份
```

### 8.2 mmap：直接把缓存页挂进你的页表

```
  进程的页表                             页缓存
  ┌───────────────────────┐          ┌──────────────────────────┐
  │ 虚拟地址 0xffff12340000 │ ───────▶ │ 物理页 #1024：文件第 0 页   │
  └───────────────────────┘          └──────────────────────────┘

  程序访问 p[0]，MMU 直接翻译到物理页 #1024
  没有拷贝，内存里只有 1 份
```

这就是 mmap 的核心秘密：

> **mmap 不是把文件"复制"到你的内存里，而是把页缓存里的那些物理页，直接挂进你的页表。你看到的，就是页缓存本身。**

现在可以回答第 1 篇留下的问题了：

**问：程序在 EL0，内核的数据在内核地盘里，程序怎么能直接看到？**
答：页缓存页本身只是普通的物理页，所谓"内核地盘"是由页表权限决定的。内核在**你的进程页表**里添加一条映射，设置为 EL0 可访问，你就能看到它了。安全性没有破坏：内核只会映射你有权限访问的文件，并按你打开文件的方式设置读写权限。

**问：mmap 10GB 文件，要先读 10GB 吗？**
答：不用。mmap 只登记"菜单"；你访问哪一页，就在缺页时把哪一页挂上（必要时从磁盘读进页缓存）。

**问：我改了 `p[i]`，文件会变吗？**
答：如果是共享映射，你改的就是页缓存里的那一页，它变成了脏页，之后会被写回磁盘——就像 `write` 一样，只是省掉了拷贝。如果是私有映射，情况不同，第 7 篇详讲。

### 8.3 一个推论：一致性是天然的

因为一个文件页在系统里只有一份缓存，所以：

- 进程 A 用 mmap（共享映射）修改了文件，进程 B 用 `read` 立刻就能读到新内容；
- 进程 A 用 `write` 修改了文件，进程 B 的 mmap 映射里立刻就能看到新内容。

大家看的都是同一个物理页。（`O_DIRECT` 例外，因为它绕过了页缓存。）

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 页缓存 | 内核把文件内容以页为单位缓存在内存里，全系统每页只有一份 |
| address_space | 每个文件的"缓存目录"，记录文件页号对应哪个物理页 |
| 预读 | 发现顺序读时，提前把后面的内容读进缓存 |
| 写回缓存 | `write` 只写到页缓存就返回，稍后再写回磁盘 |
| 脏页 | 被修改但尚未写回磁盘的页 |
| fsync | 强制把脏页写到磁盘并等待完成 |
| buff/cache / available | 缓存占用的内存可随时回收，看 available 才准 |
| O_DIRECT | 绕过页缓存的直接 I/O |
| read vs mmap | read 从页缓存**拷贝**一份；mmap 把页缓存页**直接映射**进页表 |
