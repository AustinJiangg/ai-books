# 第 1 篇｜从读一个文件说起：程序和操作系统是怎么打交道的

> **本篇目标**：搞懂"程序读文件"这件日常小事背后到底发生了什么，理解**用户态/内核态**、**系统调用**、**文件描述符**这几个基础概念，并亲眼看到"数据被搬了好几次"这个事实——它正是 mmap 诞生的理由。
>
> **约定**：本系列代码使用 C 语言 + Linux；涉及硬件细节时以 **ARM64（aarch64）** 为例，必要时对比 x86。

---

## 一、一个看似简单的问题

假设你有一个文件 `hello.txt`，内容是一行字：

```
Hello, mmap!
```

在终端里敲：

```bash
cat hello.txt
```

屏幕上就出现了 `Hello, mmap!`。

太简单了，对吧？但请你认真想一想：**`cat` 这个程序，到底是怎么拿到硬盘上那几个字节的？**

硬盘（或 SSD）是一块硬件，文件内容以电荷或磁信号的形式存在里面的某个位置。`cat` 只是一个普通程序，它怎么知道 `hello.txt` 存在硬盘的哪个位置？它怎么跟硬盘控制器"说话"？它又怎么把文字送到屏幕上？

答案是：**`cat` 自己一样都不会做。它全靠"求"操作系统帮忙。**

这句话就是整个系列的起点。

---

## 二、程序不能直接碰硬件

### 2.1 如果每个程序都能直接操作硬盘，会怎样？

设想一个没有"管理者"的世界：每个程序都可以直接对硬盘下命令。

- **混乱**：你的浏览器正在往硬盘第 1000 号位置写缓存，同时你的音乐播放器也往第 1000 号位置写配置。结果两边的数据互相覆盖，全坏了。
- **不安全**：一个随便下载的小游戏可以直接读走你硬盘上的密码文件、聊天记录，甚至把整块硬盘清零。
- **太难写**：硬盘有几十种型号，SATA、NVMe、U 盘、网络存储……每个程序都要自己学会跟所有硬件打交道？那写一个"打印文件内容"的程序可能需要几万行代码。

所以，现代计算机的做法是：**在程序和硬件之间放一个"管理者"——操作系统内核（kernel）**。

### 2.2 银行柜台的比喻

把计算机想象成一家银行：

| 银行 | 计算机 |
|---|---|
| 金库 | 硬件（硬盘、内存、网卡……） |
| 柜员 | 操作系统内核 |
| 顾客 | 普通程序（cat、浏览器、游戏） |
| 柜台窗口 | 系统调用 |

顾客不能自己走进金库拿钱。你只能走到柜台前，填一张单子："我要从我的账户取 500 元"。柜员核对你的身份，确认你确实有这个账户、确实有 500 元，然后**柜员**进金库取钱，从窗口递给你。

程序读文件也是一样：

1. `cat` 走到"柜台"前说："请帮我打开 `hello.txt`。"
2. 内核检查：这个文件存在吗？你有权限读吗？
3. 检查通过，内核去和硬盘打交道，把数据取出来。
4. 内核把数据从"窗口"递给 `cat`。

这个"柜台窗口"，在计算机里就叫**系统调用（system call，简称 syscall）**。

---

## 三、用户态与内核态：CPU 的两种身份

你可能会问：凭什么程序就"不能"直接碰硬件？程序也是在 CPU 上跑的指令，CPU 怎么知道该不该执行？

答案是：**CPU 本身就有"身份等级"的概念。**

### 3.1 ARM64 的异常级别

以 ARM64 处理器为例，CPU 在任意时刻都处在某个**异常级别（Exception Level，EL）**：

```
  EL0   ← 普通应用程序（cat、浏览器）     权限最低
  EL1   ← 操作系统内核（Linux）
  EL2   ← 虚拟机管理器（Hypervisor）
  EL3   ← 安全监控固件（Secure Monitor）   权限最高
```

普通程序运行在 **EL0**，这就是所谓的**用户态（user mode）**；Linux 内核运行在 **EL1**，这就是**内核态（kernel mode）**。

> 补充：x86 处理器用的是另一套叫法，叫"特权环"（ring），应用跑在 ring 3，内核跑在 ring 0。名字不同，思路一样。

在 EL0 下，有一大批"危险操作"是 CPU 直接拒绝执行的：比如修改内存翻译规则（第 3 篇会讲的页表）、直接访问硬件设备、关闭中断等等。如果用户程序硬要执行这些指令，CPU 会立刻产生一个"异常"，把控制权交给内核，内核通常会直接把这个程序杀掉。

**门卫由硬件亲自把守：不是程序"自觉"不碰硬件，而是 CPU 在硬件层面就不允许它碰。**

### 3.2 那怎么从 EL0 走到 EL1？

既然用户程序被关在 EL0，它怎么"请求"内核帮忙呢？

CPU 提供了一条专门的指令作为合法的"敲门"方式。在 ARM64 上，这条指令叫 **`svc`**（Supervisor Call，"呼叫管理者"）。

程序执行 `svc` 时，CPU 会：

1. 自动把身份从 EL0 切换到 EL1；
2. 跳转到内核预先设定好的固定入口地址（程序不能自己选跳到哪里，这保证了安全）；
3. 内核接手，看看你要办什么业务，办完之后用 `eret` 指令切回 EL0，回到程序里继续执行。

这一来一回，就是一次**系统调用**。

## 四、系统调用：程序的"业务单"

### 4.1 业务编号与参数

内核提供的"业务"有好几百种：打开文件、读文件、写文件、创建进程、申请内存、发网络包……每种业务有一个编号，叫**系统调用号**。

在 ARM64 Linux 上，程序发起系统调用的规矩是：

- 把**系统调用号**放进寄存器 `x8`；
- 把**参数**依次放进寄存器 `x0`、`x1`、`x2`……（最多 6 个）；
- 执行 `svc #0`；
- 内核办完后，把**返回值**放在 `x0` 里。

几个和读写文件相关的调用号（ARM64）：

| 系统调用 | 编号 | 作用 |
|---|---|---|
| `openat` | 56 | 打开文件 |
| `close` | 57 | 关闭文件 |
| `read` | 63 | 读数据 |
| `write` | 64 | 写数据 |
| `mmap` | 222 | 内存映射（本系列主角） |

你可能注意到了：这里没有 `open`，只有 `openat`。这是因为 ARM64 是比较新的架构，Linux 在设计它的系统调用表时去掉了一批"老式"接口，统一用功能更全的新版本代替。你在 C 代码里写 `open()`，C 库会帮你转换成 `openat`。

### 4.2 亲手"敲一次门"

为了让你感受到系统调用不是什么魔法，下面这段程序**不用任何库函数**来输出，直接用 `svc` 指令让内核往屏幕上写一句话（需要在 ARM64 Linux 上编译运行）：

```c
// raw_write.c —— 不借助 printf，直接用 svc 发起 write 系统调用（仅限 ARM64）
int main(void) {
    const char msg[] = "Hello from svc!\n";

    register long x0 asm("x0") = 1;               // 参数1：文件描述符 1（标准输出）
    register long x1 asm("x1") = (long)msg;       // 参数2：数据的地址
    register long x2 asm("x2") = sizeof(msg) - 1; // 参数3：字节数
    register long x8 asm("x8") = 64;              // 系统调用号：write = 64

    asm volatile("svc #0"                         // 敲门！
                 : "+r"(x0)
                 : "r"(x1), "r"(x2), "r"(x8)
                 : "memory");

    return 0;
}
```

```bash
gcc raw_write.c -o raw_write && ./raw_write
# 输出：Hello from svc!
```

平时我们写的 `printf`、`fwrite`、`write`，最终都会落到类似这样的几条指令上。C 标准库（glibc）只是帮你把这些麻烦事包装好了。

### 4.3 文件描述符：柜台给你的"号码牌"

上面代码里有个神秘的数字 `1`，它是什么？

当你请内核打开一个文件时，内核不会把"文件本身"交给你（你也拿不住），而是给你一个**小整数**，叫**文件描述符（file descriptor，简称 fd）**。以后你想读这个文件，就拿着这个号码来："请帮我读 3 号文件。"

就像银行取号：你不需要知道金库里的保险柜在哪，只要拿着号码牌，柜员就知道你要办哪个业务。

每个程序一启动，就自带三个已经打开的 fd：

| fd | 名称 | 通常指向 |
|---|---|---|
| 0 | 标准输入 stdin | 键盘 |
| 1 | 标准输出 stdout | 屏幕（终端） |
| 2 | 标准错误 stderr | 屏幕（终端） |

所以，你自己打开的第一个文件，拿到的 fd 通常是 **3**。

## 五、动手写一个迷你版 cat

有了这些知识，我们就能写出 `cat` 的核心逻辑了：

```c
// mycat.c —— 一个最简版本的 cat
#include <fcntl.h>    // open
#include <unistd.h>   // read, write, close
#include <stdio.h>    // perror, fprintf

int main(int argc, char *argv[]) {
    if (argc != 2) {
        fprintf(stderr, "用法: %s 文件名\n", argv[0]);
        return 1;
    }

    // 第1步：请内核打开文件，拿到号码牌 fd
    int fd = open(argv[1], O_RDONLY);
    if (fd < 0) {
        perror("open");   // 打开失败（文件不存在、没权限……）
        return 1;
    }

    char buf[4096];       // 在自己的内存里准备一个"篮子"
    ssize_t n;

    // 第2步：反复请内核"往我的篮子里装数据"
    while ((n = read(fd, buf, sizeof(buf))) > 0) {
        // 第3步：请内核"把篮子里的东西送到屏幕"
        write(1, buf, n);
    }
    // read 返回 0 表示读到文件末尾；返回 -1 表示出错

    // 第4步：归还号码牌
    close(fd);
    return 0;
}
```

```bash
gcc mycat.c -o mycat
echo "Hello, mmap!" > hello.txt
./mycat hello.txt
```

请特别注意 `read(fd, buf, sizeof(buf))` 这一行的语义：

> **"内核，请从 fd 号文件里读最多 4096 个字节，放进我提供的 `buf` 里。"**

数据是被**放进你提供的篮子**里的。这个"放进"，就是一次**拷贝**。记住这个词，我们马上就要和它较真。

## 六、一次 read 背后，数据到底走了几步？

现在我们跟着那几个字节走一趟，看看从硬盘到屏幕，它们经历了什么。

### 6.1 读的过程

```
   ┌──────────┐
   │  硬盘     │  "Hello, mmap!" 存在某个扇区里
   └────┬─────┘
        │ ① 硬盘控制器通过 DMA 把数据搬进内存
        ▼
   ┌──────────────────────┐
   │ 内核的缓冲区           │  （这块区域叫 page cache，第 5 篇详讲）
   │ "Hello, mmap!"       │
   └────┬─────────────────┘
        │ ② CPU 把数据从内核缓冲区拷贝到用户的 buf
        ▼
   ┌──────────────────────┐
   │ 用户程序的 buf[4096]   │
   │ "Hello, mmap!"       │
   └──────────────────────┘
```

**第①步：硬盘 → 内核内存。**
内核查到 `hello.txt` 的内容存在硬盘哪个位置，然后给硬盘控制器下命令。这一步通常用 **DMA（Direct Memory Access，直接内存访问）** 完成：硬盘控制器自己把数据搬进内存，不需要 CPU 一个字节一个字节地搬，CPU 可以趁机去干别的事。

**第②步：内核内存 → 用户 buf。**
数据现在在内核的地盘里。但你的程序在 EL0，按规矩不能直接去内核的地盘翻东西。所以内核在 EL1 下，**由 CPU 亲自**把数据复制到你提供的 `buf` 中。

为什么内核不直接让程序去自己的地盘读？因为内核的地盘里堆着所有程序的数据和内核自己的机密。一旦开放，安全隔离就荡然无存。所以"拷贝一份给你"是最简单安全的做法。

### 6.2 写的过程

接着 `write(1, buf, n)` 又发生了一次反向的拷贝：

```
   用户的 buf  ──③ CPU 拷贝──▶  内核缓冲区  ──④──▶  终端/屏幕
```

### 6.3 数一数

对于 `cat` 这样一个"把文件内容原样输出"的程序：

- 数据**在内存里被 CPU 拷贝了 2 次**（②和③）；
- 程序和内核之间**来回切换**了好多次（每次 `read`、每次 `write` 都是一次 EL0 → EL1 → EL0）。

而 `cat` 本身对数据**什么都没做**，它只是个"二传手"。数据从内核绕到用户程序，再原封不动地绕回内核。

## 七、拷贝和切换的代价有多大？

文件只有 13 个字节时，这点开销当然无所谓。但如果是一个 10GB 的数据库文件、一个 4K 电影、一台每秒处理几万个请求的服务器呢？

开销主要来自两方面：

**1. 系统调用本身的开销**

每次 EL0 ↔ EL1 切换，CPU 都要保存和恢复一堆寄存器、做安全检查，为了防御某些 CPU 漏洞可能还要做额外的处理。单次可能只是几十到几百纳秒，但次数多了就很可观。

**2. 数据拷贝的开销**

CPU 拷贝数据要占用 CPU 时间，还要占用内存带宽。拷贝 1GB 数据，就意味着 CPU 要从内存读 1GB、再写 1GB。而且拷贝来的数据会挤进 CPU 缓存，把其他有用的数据挤出去。

### 小实验 1：感受系统调用次数的代价

`dd` 命令可以指定每次 `read`/`write` 的大小（`bs` 参数）。我们读同一个 10MB 文件，分别每次读 1 字节和每次读 1MB：

```bash
# 准备一个 10MB 的测试文件
dd if=/dev/zero of=test.bin bs=1M count=10

# 每次读 1 字节：需要大约 1000 万次 read + 1000 万次 write
time dd if=test.bin of=/dev/null bs=1

# 每次读 1MB：只需要 10 次 read + 10 次 write
time dd if=test.bin of=/dev/null bs=1M
```

你会看到两者耗时相差**成百上千倍**：前者要好几秒，后者只要几毫秒（具体数字因机器而异）。搬运的数据量完全一样，区别只在于"敲门"的次数。这说明系统调用不是免费的。

这个实验里，第二次运行时文件内容已经在内存的缓存里了，硬盘几乎没参与。所以剩下的时间几乎全是"系统调用 + 拷贝"的成本。

## 八、小实验 2：用 strace 偷看 cat 的一举一动

Linux 有一个神器叫 **`strace`**，它可以把一个程序发起的**所有系统调用**都打印出来，相当于在银行柜台旁边装了个摄像头。

```bash
# 如果没装：sudo apt install strace
strace cat hello.txt
```

你会看到一大堆输出。前面很多行是程序启动时加载各种库产生的，我们先只看和文件有关的：

```bash
strace -e trace=openat,read,write,close cat hello.txt
```

输出大致如下（不同系统会有些差异）：

```
openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3
close(3)                                = 0
openat(AT_FDCWD, "/lib/aarch64-linux-gnu/libc.so.6", O_RDONLY|O_CLOEXEC) = 3
read(3, "\177ELF\2\1\1\3\0\0\0\0\0\0\0\0\3\0\267\0\1\0\0\0"..., 832) = 832
close(3)                                = 0
openat(AT_FDCWD, "hello.txt", O_RDONLY) = 3
read(3, "Hello, mmap!\n", 131072)       = 13
write(1, "Hello, mmap!\n", 13Hello, mmap!
)          = 13
read(3, "", 131072)                     = 0
close(3)                                = 0
close(1)                                = 0
close(2)                                = 0
+++ exited with 0 +++
```

逐行解读最关键的几行：

| strace 输出 | 含义 |
|---|---|
| `openat(..., "hello.txt", O_RDONLY) = 3` | 以只读方式打开文件，拿到号码牌 **3** |
| `read(3, "Hello, mmap!\n", 131072) = 13` | 请求读最多 128KB，实际读到 13 字节 |
| `write(1, "Hello, mmap!\n", 13) = 13` | 把 13 字节写到 fd 1（屏幕） |
| `read(3, "", 131072) = 0` | 再读，返回 0，说明到文件末尾了 |
| `close(3) = 0` | 归还号码牌 |

和我们写的 `mycat` 一模一样！真正的 `cat` 只是缓冲区更大（128KB），并多做了些错误处理。

> **彩蛋**：上面那行 `aarch64-linux-gnu` 说明我们在 ARM64 机器上。如果你去掉 `-e` 过滤，完整输出里会看到好几行以 **`mmap(`** 开头的系统调用。没错，`cat` 在启动阶段就悄悄用了 mmap：它用 mmap 把 C 库装进内存。我们的主角其实一直都在，只是你以前没注意到它。第 12 篇会专门讲这件事。

## 九、引子：能不能让文件"直接出现在内存里"？

回顾一下我们发现的问题：

1. 用 `read` 读文件，数据要从内核**拷贝**一份到用户程序；
2. 每读一块都要发起一次**系统调用**；
3. 如果文件很大、又需要**随机访问**（比如数据库里跳着读第 100 万条、第 3 条、第 50 万条记录），你得反复调用 `lseek` 定位、再 `read`，非常繁琐，开销也大。

于是一个大胆的想法出现了：

> **能不能让内核做一次"安排"，之后文件的内容就像一个普通的大数组一样，直接出现在我程序的内存里？我想读第几个字节，就直接 `p[i]`；想改，就直接 `p[i] = 'X'`。不用再一次次敲门，也不用来回拷贝。**

先剧透一眼它长什么样：

```c
// 只是预览，第 6 篇会逐行详解
char *p = mmap(NULL, 文件大小, PROT_READ, MAP_PRIVATE, fd, 0);

putchar(p[0]);          // 直接读第 0 个字节，没有 read()
putchar(p[1000000]);    // 直接跳到第 100 万个字节，没有 lseek()
```

这就是 **mmap（memory map，内存映射）**。

但是，这怎么可能？

- 程序在 EL0，内核的数据在 EL1 的地盘里，不是说不能直接看吗？
- 一个 10GB 的文件，难道一调用 mmap 就把 10GB 全读进内存？要是内存只有 8GB 呢？
- 你改了 `p[i]`，硬盘上的文件会跟着变吗？什么时候变？

要回答这些问题，我们必须先弄明白一件更根本的事：**程序眼里的"内存"，到底是什么？** 指针里存的那个地址，真的是内存条上的某个位置吗？

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 内核 | 管理所有硬件的"银行柜员"，程序必须通过它才能使用硬件 |
| 用户态 / 内核态 | CPU 的两种身份。ARM64 上应用跑在 EL0，内核跑在 EL1，由硬件强制隔离 |
| 系统调用 | 程序请求内核办事的唯一正规渠道。ARM64 上用 `svc` 指令，调用号放在 `x8` |
| 文件描述符 | 内核发给你的"号码牌"，一个小整数；0/1/2 是标准输入/输出/错误 |
| `read` 的本质 | 内核把数据**拷贝**进你提供的缓冲区 |
| 开销来源 | 系统调用的切换开销 + 数据拷贝开销 |
| mmap 的初心 | 让文件像数组一样直接出现在程序内存里，省掉拷贝和反复敲门 |
