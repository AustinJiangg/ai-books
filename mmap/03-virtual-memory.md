# 第 3 篇｜虚拟内存：每个程序都活在自己的"楚门的世界"

> **本篇目标**：理解虚拟地址如何被翻译成物理地址——**页、页表、MMU、TLB** 这四个核心概念；以 ARM64 为例拆解四级页表；最后第一次读懂进程的内存地图 `/proc/self/maps`，并在里面找到 mmap。

---

## 一、楚门的世界

电影《楚门的世界》里，主角楚门从出生起就生活在一个巨大的摄影棚里。他看到的街道、大海、天空全是布景，但他以为这就是整个世界。

每个进程都是一个楚门：

- 它以为自己独占了一个**巨大、连续、干净**的内存空间，地址从 0 一直到几百 TB；
- 它看不到别的进程，也看不到内核的内部；
- 它访问的每一个地址，都会被悄悄"翻译"成某个真实的物理地址。

这套机制叫**虚拟内存（virtual memory）**。每个进程拥有的这片"假"地址范围，叫它的**虚拟地址空间（virtual address space）**。

```
  进程 A 的世界                     物理内存                     进程 B 的世界
 ┌──────────────┐                ┌──────────┐                ┌──────────────┐
 │ 0xaaaa...010 │ ──────┐        │ 格子 #7  │       ┌─────── │ 0xaaaa...010 │
 │              │       └──────▶ │  值=111  │       │        │              │
 │              │                ├──────────┤       │        │              │
 │              │                │ 格子 #42 │ ◀─────┘        │              │
 │              │                │  值=222  │                │              │
 └──────────────┘                └──────────┘                └──────────────┘
```

这就解释了上一篇的实验：两个进程的同一个虚拟地址，翻译到了不同的物理位置。

## 二、翻译的单位：页

### 2.1 为什么不能逐字节翻译？

最直接的想法是：给每个进程准备一张表，记录"虚拟地址 0 对应物理地址几、虚拟地址 1 对应物理地址几……"。

但这样一张表比内存本身还大——每个字节的映射都需要好几个字节来记录。行不通。

### 2.2 分页：以块为单位翻译

解决办法是**批发**：把虚拟地址空间和物理内存都切成**固定大小的块**，以块为单位做映射。

- 虚拟地址空间里的一块，叫**虚拟页（page）**，简称**页**；
- 物理内存里的一块，叫**物理页帧（page frame）**，简称**页帧**或**物理页**；
- 一页的大小，最常见的是 **4KB（4096 字节）**。

> **ARM64 的特别之处**：ARM64 硬件支持 **4KB、16KB、64KB** 三种页大小（ARM 称之为"翻译粒度 granule"），由内核编译时选定。大多数发行版用 4KB，但某些服务器发行版用过 64KB，Apple Silicon 上的 Linux 用 16KB。本系列默认 4KB，但**写代码时永远不要把 4096 写死**，要用 `sysconf(_SC_PAGESIZE)` 查询。

查看你的系统页大小：

```bash
getconf PAGESIZE
# 4096
```

### 2.3 地址的拆分

有了页，一个虚拟地址就可以拆成两部分：

```
     虚拟地址  =  [ 虚拟页号 ]  [ 页内偏移 ]
```

因为 4KB = 2¹²，页内偏移正好是地址的**低 12 位**。

举例：虚拟地址 `0x12345678`

```
0x12345678
  ├─────┤├─┤
  0x12345 0x678
  虚拟页号  页内偏移
```

翻译时只需要查出"虚拟页 0x12345 对应哪个物理页"，假设是物理页 `0x8a0f1`，那么物理地址就是：

```
物理页号 0x8a0f1 拼上偏移 0x678  →  物理地址 0x8a0f1678
```

**页内偏移原样保留，只翻译页号。** 映射表的条目一下子少了 4096 倍。

记录"虚拟页号 → 物理页号"的这张表，叫做**页表（page table）**。每个进程都有自己的一份页表，这就是每个进程拥有独立世界的原因。

## 三、多级页表：ARM64 的四级结构

### 3.1 一张大表还是太大

ARM64 Linux 下，用户程序通常可用 **48 位**虚拟地址，即 256TB 的空间。去掉 12 位页内偏移，还剩 36 位页号，也就是 2³⁶ ≈ 687 亿个虚拟页。

如果用一张平铺的页表，每个条目 8 字节，那么**每个进程的页表就要 512GB**。显然不可能。

可现实中一个进程通常只用了几十 MB 到几 GB，256TB 里绝大部分都是空的。为空白区域准备表项纯属浪费。

### 3.2 解决办法：像目录一样分级

想想图书馆怎么管理几百万本书：先分"楼层"，楼层里分"区"，区里分"书架"，书架上才是"书"。没人用的楼层，根本不用摆书架。

ARM64（4KB 页、48 位地址）把 36 位页号拆成 **4 段，每段 9 位**：

```
 63      48 47     39 38     30 29     21 20     12 11          0
┌─────────┬─────────┬─────────┬─────────┬─────────┬────────────┐
│ 全0或全1 │ L0 索引  │ L1 索引  │ L2 索引  │ L3 索引  │  页内偏移   │
│ (选择    │  9 位    │  9 位    │  9 位    │  9 位    │   12 位    │
│ TTBR0/1) │         │         │         │         │            │
└─────────┴─────────┴─────────┴─────────┴─────────┴────────────┘
```

为什么是 9 位？因为 2⁹ = 512，每张表 512 个条目 × 8 字节 = **4096 字节，正好一页**。每一级的表本身就是一个物理页，设计得非常整齐。

Linux 内核给这四级起了通用的名字：

| ARM64 叫法 | Linux 通用叫法 | 每个条目管辖范围 |
|---|---|---|
| L0 表 | PGD（页全局目录） | 512GB |
| L1 表 | PUD（页上级目录） | 1GB |
| L2 表 | PMD（页中间目录） | 2MB |
| L3 表 | PTE（页表项） | 4KB（一页） |

### 3.3 一次完整的翻译（页表遍历）

```
  TTBR0_EL1 寄存器（存着 L0 表的物理地址）
        │
        ▼
  ┌──────────┐  用 L0 索引查
  │  L0 表    │─────────────┐
  └──────────┘             ▼
                     ┌──────────┐  用 L1 索引查
                     │  L1 表    │─────────────┐
                     └──────────┘             ▼
                                        ┌──────────┐  用 L2 索引查
                                        │  L2 表    │─────────────┐
                                        └──────────┘             ▼
                                                           ┌──────────┐  用 L3 索引查
                                                           │  L3 表    │──────┐
                                                           └──────────┘      ▼
                                                                    物理页号 + 页内偏移
                                                                         = 物理地址
```

每一级条目里存的是**下一级表的物理地址**，最后一级（L3）的条目里存的是**目标物理页的地址**。

**稀疏的妙处**：如果某个 512GB 范围完全没用，那么它在 L0 表里的条目就标记为"无效"，下面的 L1、L2、L3 表根本不用创建。一个普通进程的页表通常只占几十 KB 到几 MB。

### 3.4 页表项里还有什么？

一个 8 字节的页表项，除了物理页地址，还有一堆**标志位**。ARM64 上重要的几个：

| 标志 | 含义 |
|---|---|
| **有效位**（bit 0） | 这个条目是否有效。为 0 时，访问会触发异常（下一篇的主角：缺页异常） |
| **AP（访问权限）** | 只读还是可写；用户态（EL0）能否访问 |
| **UXN / PXN** | 禁止用户态 / 内核态从这一页**执行**代码 |
| **AF（访问标志）** | 这一页是否被访问过（内核用它判断哪些页"热"、哪些页"冷"） |
| **脏标记**（DBM 相关） | 这一页是否被写过 |

这些标志让页表不只是"翻译字典"，还是"门禁系统"：

- 代码页设为"只读 + 可执行"，防止程序被篡改；
- 数据页设为"可写 + 不可执行"，防止把数据当代码执行（防御很多攻击）；
- 内核的页设为"EL0 不可访问"，用户程序就碰不到内核。

记住"有效位"和"只读"这两个标志，后面讲缺页、写时复制、mmap 时会反复用到。

### 3.5 大块映射：跳过最后几级

L1、L2 的条目除了指向下一级表，还可以**直接指向一大块物理内存**（ARM64 称为 block 描述符）：

- L2 条目直接映射一块 **2MB** 的物理内存；
- L1 条目直接映射一块 **1GB** 的物理内存。

这就是**大页（huge page）**的硬件基础。第 10 篇讲性能时会用到。

## 四、MMU：干翻译活的硬件

翻译工作如果由软件来做，每访问一次内存都要先跑几十条指令查表，程序会慢得无法忍受。所以 CPU 里专门有一个硬件部件负责翻译，叫 **MMU（Memory Management Unit，内存管理单元）**。

- 程序发出的**每一个**地址都是虚拟地址；
- MMU 自动查页表、算出物理地址，再去访问内存；
- 整个过程对程序完全透明，程序根本不知道翻译发生过。

### 4.1 ARM64 的两个页表基址寄存器

ARM64 有个很优雅的设计：用**两个**寄存器分别管理地址空间的两半。

```
虚拟地址
0xFFFF_FFFF_FFFF_FFFF ┌─────────────────────┐
                      │                     │
                      │   内核空间           │  ← 由 TTBR1_EL1 指向的页表翻译
                      │                     │    （所有进程共享同一份）
0xFFFF_0000_0000_0000 ├─────────────────────┤
                      │                     │
                      │   不可用的"空洞"      │  ← 访问即出错
                      │                     │
0x0000_FFFF_FFFF_FFFF ├─────────────────────┤
                      │                     │
                      │   用户空间（256TB）   │  ← 由 TTBR0_EL1 指向的页表翻译
                      │                     │    （每个进程各一份）
0x0000_0000_0000_0000 └─────────────────────┘
```

- 地址最高 16 位全是 0 → 用 **TTBR0_EL1**（用户页表）翻译；
- 地址最高 16 位全是 1 → 用 **TTBR1_EL1**（内核页表）翻译。

**进程切换**时，内核只需要把 TTBR0_EL1 换成新进程的页表地址，CPU 瞬间就"进入"了另一个进程的世界。而内核那一半不用动。

> 上一篇实验里栈变量的地址 `0xffffd2a3b6ac`，看上去以 `0xffff` 开头，但它只有 48 位：`0x0000_ffff_d2a3_b6ac`，最高 16 位是 0，所以它在用户空间的顶部附近，不是内核地址。

## 五、TLB：翻译结果的小本本

### 5.1 翻译太慢了

仔细算一下：按 3.3 节的流程，翻译一个地址需要依次读 L0、L1、L2、L3 四张表，也就是**额外的 4 次内存访问**。本来只想读 1 次内存，结果要读 5 次，程序岂不是慢了 5 倍？

### 5.2 TLB 来救场

MMU 里有一个小而快的缓存，叫 **TLB（Translation Lookaside Buffer，地址转换后备缓冲区）**，专门记录"最近翻译过的虚拟页 → 物理页"。

```
程序访问虚拟地址
       │
       ▼
   查 TLB ──── 命中（绝大多数情况）──▶ 直接得到物理地址，几乎零开销
       │
     未命中
       │
       ▼
  页表遍历（4 次内存访问）──▶ 结果存入 TLB ──▶ 得到物理地址
```

因为局部性原理，程序在一段时间内总是反复访问少数几个页，所以 TLB 命中率通常高达 99% 以上。

TLB 通常只有几十到几千个条目。假设有 1024 个条目，每条管 4KB，那 TLB 总共能"覆盖" 4MB 内存。如果程序在几 GB 的数据里随机跳着访问，TLB 就会频繁未命中——这正是大页能提升性能的原因（一条 2MB 大页条目顶 512 个普通条目）。

### 5.3 TLB 的一致性问题

TLB 是页表的缓存，那么当内核**修改**了页表（比如解除一个映射、修改权限）时，TLB 里的旧记录就过时了，必须作废。

- ARM64 用 **`TLBI`** 指令作废 TLB 条目；
- 在多核系统中，其他 CPU 核的 TLB 里可能也有旧记录，也要一起作废。ARM64 的 `TLBI ... IS`（Inner Shareable）变体可以由硬件**广播**给所有核。

这个操作叫 **TLB shootdown（TLB 击落）**，代价不小。第 10 篇会讲到：`munmap` 有时候比你想象的慢，原因就在这里。

### 5.4 ASID：切换进程不用清空 TLB

进程切换后，旧进程的 TLB 记录对新进程无效。难道每次切换都清空 TLB？那太浪费了。

ARM64 给每个 TLB 条目打上一个标签，叫 **ASID（Address Space ID，地址空间编号）**，表示"这条记录属于哪个进程"。切换进程时换一个 ASID 即可，旧进程的记录可以留着，等它切回来时还能用。

## 六、虚拟内存一次解决了所有问题

回顾上一篇列出的五个问题：

| 问题 | 虚拟内存的解法 |
|---|---|
| 互相踩踏 | 每个进程有独立页表，相同虚拟地址对应不同物理页 |
| 没有隔离 | 进程只能访问自己页表里有的页；内核页禁止 EL0 访问 |
| 内存碎片 | 虚拟上连续的页，物理上可以分散在任何地方 |
| 程序位置不固定 | 每个进程都可以使用相同的虚拟地址布局 |
| 内存不够用 | 页表项可以标记为"无效"，数据暂时放在磁盘上，用到时再调入（下一篇） |

而且，虚拟内存还带来了一项全新的能力：

> **共享**：两个进程的页表可以指向**同一个物理页**。比如 100 个进程都在用 C 库，内存里只需要放一份 C 库的代码，大家的页表都指向它。

这正是 mmap 的根基：**让进程页表里的某些条目，指向存放着文件内容的物理页。**

## 七、进程的内存地图

### 7.1 典型的地址空间布局

一个运行在 ARM64 Linux 上的普通程序，用户空间大致是这样布局的（地址从高到低）：

```
0x0000_ffff_ffff_ffff ┌─────────────────────┐
                      │       栈 stack       │ ↓ 向低地址增长（局部变量、函数调用）
                      ├─────────────────────┤
                      │                     │
                      │    mmap 区域         │ ↓ 共享库、文件映射、大块 malloc
                      │  (0xffff... 附近)     │
                      │                     │
                      │   ……巨大的空白……      │
                      │                     │
                      ├─────────────────────┤
                      │       堆 heap        │ ↑ 向高地址增长（小块 malloc）
                      ├─────────────────────┤
                      │  .bss 未初始化数据    │
                      │  .data 已初始化数据   │
                      │  .text 程序代码       │ ← 通常在 0xaaaa... 附近
0x0000_0000_0000_0000 └─────────────────────┘
```

中间那片巨大的空白，就是 mmap 施展身手的地方。

### 小实验：读懂 /proc/self/maps

Linux 用文件 `/proc/<进程号>/maps` 公开每个进程的内存地图。`/proc/self` 指"读这个文件的进程自己"。

```bash
cat /proc/self/maps
```

在 ARM64 上输出类似这样（这是 `cat` 进程自己的地图）：

```
aaaab3c10000-aaaab3c28000 r-xp 00000000 fe:01 1835     /usr/bin/cat
aaaab3c3f000-aaaab3c40000 r--p 0001f000 fe:01 1835     /usr/bin/cat
aaaab3c40000-aaaab3c41000 rw-p 00020000 fe:01 1835     /usr/bin/cat
aaaacd5e1000-aaaacd602000 rw-p 00000000 00:00 0        [heap]
ffff8a400000-ffff8a5a0000 r-xp 00000000 fe:01 2071     /usr/lib/aarch64-linux-gnu/libc.so.6
ffff8a5a0000-ffff8a5af000 ---p 001a0000 fe:01 2071     /usr/lib/aarch64-linux-gnu/libc.so.6
ffff8a5af000-ffff8a5b3000 r--p 0019f000 fe:01 2071     /usr/lib/aarch64-linux-gnu/libc.so.6
ffff8a5b3000-ffff8a5b5000 rw-p 001a3000 fe:01 2071     /usr/lib/aarch64-linux-gnu/libc.so.6
ffff8a5b5000-ffff8a5c1000 rw-p 00000000 00:00 0
ffff8a5d0000-ffff8a5fb000 r-xp 00000000 fe:01 2054     /usr/lib/aarch64-linux-gnu/ld-linux-aarch64.so.1
ffff8a603000-ffff8a605000 rw-p 00000000 00:00 0
ffff8a609000-ffff8a60b000 r--p 00000000 00:00 0        [vvar]
ffff8a60b000-ffff8a60c000 r-xp 00000000 00:00 0        [vdso]
ffff8a60c000-ffff8a60e000 r--p 0002c000 fe:01 2054     /usr/lib/aarch64-linux-gnu/ld-linux-aarch64.so.1
ffff8a60e000-ffff8a610000 rw-p 0002e000 fe:01 2054     /usr/lib/aarch64-linux-gnu/ld-linux-aarch64.so.1
ffffd8e3a000-ffffd8e5b000 rw-p 00000000 00:00 0        [stack]
```

每一行是一段**连续的虚拟地址区域**，六列的含义：

| 列 | 例子 | 含义 |
|---|---|---|
| 地址范围 | `aaaab3c10000-aaaab3c28000` | 起止虚拟地址（左闭右开），大小总是页的整数倍 |
| 权限 | `r-xp` | r 可读、w 可写、x 可执行、`-` 没有该权限；最后一位 **p = 私有，s = 共享** |
| 偏移 | `00000000` | 这段区域对应文件中的哪个位置 |
| 设备 | `fe:01` | 文件所在设备的编号 |
| inode | `1835` | 文件在文件系统里的编号；0 表示没有关联文件 |
| 路径 | `/usr/bin/cat` | 关联的文件，或 `[heap]`、`[stack]` 等特殊名字 |

请注意这些细节：

1. **程序本身** `/usr/bin/cat` 被分成了几段：代码段 `r-xp`（可读可执行不可写）、只读数据 `r--p`、可写数据 `rw-p`。这正是页表权限标志在起作用。
2. **C 库** `libc.so.6` 也出现在地图里，路径在 `0xffff...` 附近——就是 mmap 区域。**这些行就是 mmap 的产物**：动态链接器用 mmap 把库文件"映射"进了进程的地址空间。
3. 没有路径、inode 为 0 的 `rw-p` 区域，叫**匿名映射**（第 8 篇详讲）。
4. 权限最后一位的 `p` 和 `s`，对应 mmap 的 `MAP_PRIVATE` 和 `MAP_SHARED`（第 7 篇详讲）。
5. 地址范围之间有大片空隙，那些地址在页表里根本没有有效映射，访问它们会导致**段错误**。

## 八、一个悬而未决的问题

上面的地图显示 C 库映射了约 1.6MB 的代码。那么问题来了：

> 程序启动那一刻，内核真的把这 1.6MB 全部从磁盘读进内存、并逐页填好页表了吗？

如果是这样，启动一个程序就要读很多数据；一个映射 10GB 文件的 mmap 调用就要读 10GB 才能返回。

事实并非如此。页表项里那个"**有效位**"，是一个精妙设计的起点：内核完全可以先把页表项留空，等程序**真的访问**某一页时，再临时去准备数据。

这个"临时准备"的过程，就是下一篇的主角：**缺页异常**。

| 概念 | 一句话解释 |
|---|---|
| 虚拟内存 | 每个进程拥有独立的"假"地址空间，由硬件翻译成物理地址 |
| 页 / 页帧 | 翻译的基本单位，常见 4KB；ARM64 还支持 16KB、64KB |
| 页表 | 记录"虚拟页 → 物理页"的映射表，每个进程一份 |
| 四级页表 | ARM64 把 36 位页号拆成 4 段 × 9 位，空白区域不用建表 |
| 页表项标志 | 有效位、读写权限、可执行、访问标志、脏标记 |
| MMU | CPU 中自动完成地址翻译的硬件 |
| TTBR0 / TTBR1 | ARM64 分别指向用户页表和内核页表的寄存器 |
| TLB | 翻译结果的高速缓存；修改页表后要作废（TLB shootdown） |
| ASID | TLB 条目的进程标签，避免切换进程时清空 TLB |
| /proc/pid/maps | 进程的内存地图，每行一段区域，库文件就是 mmap 进来的 |
