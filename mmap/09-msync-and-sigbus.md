# 第 9 篇｜数据什么时候真正落盘：一致性、同步与崩溃

> **本篇目标**：弄清写进 mmap 区域的数据**此刻在哪里**、**何时到达磁盘**；掌握 `msync` 的正确用法；理解 `munmap` 和进程退出到底保证了什么；认识断电时的崩溃一致性问题；最后学会诊断和防范 mmap 特有的 **SIGBUS**。

## 一、你写下的数据，此刻在哪里？

假设你用 `MAP_SHARED` 映射了一个文件，然后执行：

```c
p[100] = 'X';
```

这条指令执行完的瞬间，`'X'` 在哪里？

答案（结合第 5、6 篇）：**在页缓存里的某个物理页上**。它**不在磁盘上**。

```
 你的写入 ──▶ 页缓存中的物理页（变成脏页） ──?──▶ 磁盘
                                          这一步什么时候发生？
```

后半段旅程，和 `write` 写入的数据完全一样：由内核的后台回写线程在合适的时机写回磁盘（30 秒超时、脏页比例过高、内存回收等，见第 5 篇）。

### 1.1 内核怎么知道你写了？

这里有个有趣的问题：用 `write` 写文件时，内核亲自把数据拷进页缓存，当然知道哪一页脏了。但 mmap 的写入是程序**直接**用 CPU 指令写内存，内核根本不参与，它怎么知道哪些页被改过、需要写回？

Linux 用的是一个和写时复制很像的技巧：

1. 对于共享的可写文件映射，页第一次被挂进页表时，内核**故意把页表项设为只读**；
2. 程序第一次写这一页 → 权限缺页异常；
3. 内核借此机会：通知文件系统"这一页要被写了"（文件系统可能需要在磁盘上预留空间），把页**标记为脏**，再把页表项改成**可写**；
4. 后台线程把这一页写回磁盘后，会**再次把页表项改回只读**；
5. 程序下次再写，又会触发一次缺页，页再次被标记为脏。

```
  干净 + 只读 ──写──▶ 缺页：标记脏 ──▶ 脏 + 可写 ──写回磁盘──▶ 干净 + 只读 ──写──▶ ...
```

这样，内核用很小的代价（每页每轮一次缺页）精确地追踪了所有 mmap 写入。这也意味着：**往一个刚被写回的页上写数据，会有一次额外的缺页开销。**

> 在 ARM64 上，较新的硬件（ARMv8.1 起）支持由硬件自动维护页表项中的"脏"状态（DBM 机制），内核可以利用它减少一部分这类缺页，但整体思路相同。

## 二、msync：把数据推到磁盘

### 2.1 函数原型

```c
#include <sys/mman.h>

int msync(void *addr, size_t length, int flags);
```

`msync` 要求内核把指定范围内的脏页写回文件。`addr` 必须页对齐。`flags` 必须包含下面二者之一：

| 标志 | 含义 |
|---|---|
| `MS_SYNC` | 发起写回，并**等待写入完成**后才返回 |
| `MS_ASYNC` | 安排写回，立即返回 |

可选附加：

| 标志 | 含义 |
|---|---|
| `MS_INVALIDATE` | 让同一文件的其他映射失效，以便看到新数据（Linux 上由于页缓存是统一的，这个标志基本没有实际作用） |

### 2.2 MS_SYNC 和 MS_ASYNC 的真相

- **`MS_SYNC`**：真正有用的那个。在 Linux 上，它的效果大致相当于对这个文件范围调用 `fdatasync`：把数据写到磁盘并等待完成。函数返回 0 后，你可以相信数据已经持久化（前提是磁盘本身不撒谎）。
- **`MS_ASYNC`**：在现代 Linux 上**基本什么都不做**。因为第 1.1 节的机制，内核早已知道哪些页是脏的，它们本来就会被后台线程写回。`MS_ASYNC` 不会让写回提前发生。

所以，**需要持久化保证时，用 `MS_SYNC`**。

### 2.3 用法示例

```c
// 修改文件第 1000 字节附近的一条记录，并确保它落盘
long page = sysconf(_SC_PAGESIZE);

memcpy(p + 1000, record, sizeof record);

// msync 的地址要页对齐：从记录所在页的起点开始
char  *start = (char *)((uintptr_t)(p + 1000) & ~(uintptr_t)(page - 1));
size_t len   = (p + 1000 + sizeof record) - start;

if (msync(start, len, MS_SYNC) < 0) {
    perror("msync");          // 磁盘出错时会在这里报告！
}
```

最简单粗暴的做法是对整个映射区域调用 `msync(p, size, MS_SYNC)`，内核只会写真正脏了的页。

### 2.4 fsync 也可以

因为 mmap 写入的数据就在页缓存里，对同一个文件的 fd 调用 `fsync(fd)` 或 `fdatasync(fd)` 也能把它们写到磁盘。区别是：

- `fsync` 作用于整个文件，还会写入元数据（文件大小、修改时间等）；
- `msync` 只针对指定的地址范围。

如果你同时改变了文件大小（比如先 `ftruncate` 扩大文件再映射写入），最好在最后调用一次 `fsync`，确保文件大小这个元数据也已落盘。

## 三、常见误解：munmap 和退出会保存数据吗？

### 3.1 munmap

`munmap` 只是**解除映射**：删除"菜单"条目、清除页表项。被修改过的页依然作为脏页留在页缓存中，之后照常由后台线程写回。

- **数据不会丢**（只要系统不崩溃）：其他进程 `read` 这个文件马上就能看到你的修改；
- **但也没有被保证落盘**：`munmap` 不等待磁盘写入。

### 3.2 进程退出

进程退出（正常退出、被杀死、崩溃）时，内核会自动解除它的所有映射。效果和 `munmap` 一样：

- `MAP_SHARED` 映射中的修改已经在页缓存里，**不会因为进程退出而丢失**，会被正常写回；
- `MAP_PRIVATE` 映射中的修改（私有复印件）随进程一起消失，本来就不会写回文件。

这一点其实是 mmap 的一个优点：**进程崩溃不会丢失已写入共享映射的数据**。相比之下，用 `fwrite` 写到 C 库缓冲区、还没 `fflush` 的数据，进程崩溃时就丢了。

### 3.3 唯一会丢数据的情况

**操作系统崩溃或断电**。这时页缓存里还没写回的脏页全部丢失。

| 发生了什么 | 已写入 MAP_SHARED 的数据 |
|---|---|
| 调用 `munmap` | 安全（在页缓存中，稍后写回） |
| 进程正常退出 | 安全 |
| 进程崩溃 / 被 kill -9 | 安全 |
| 内核崩溃 / 断电，且之前没有 `msync(MS_SYNC)` | **可能丢失** |
| 内核崩溃 / 断电，之前已经 `msync(MS_SYNC)` 成功 | 安全 |

## 四、崩溃一致性：比"丢数据"更麻烦的问题

### 4.1 你无法控制写回的时机和顺序

用 `write` 时，至少数据是在你调用 `write` 的那一刻才进入页缓存的。而用 mmap，**数据从你写下的那一瞬间就在页缓存里了**，内核随时可能把它写回磁盘——哪怕你只改了一半。

假设你要更新一个 8KB、横跨两页的数据结构：

```
  第 A 页: [旧数据前半部分]      第 B 页: [旧数据后半部分]
         ↓ 你开始修改
  第 A 页: [新数据前半部分]      第 B 页: [旧数据后半部分]   ← 此刻内核恰好写回了第 A 页
         ↓ 断电！
  磁盘上: 新的前半部分 + 旧的后半部分 = 一个损坏的数据结构
```

更糟的是，内核写回脏页的**顺序**也不受你控制。你先改了第 B 页再改第 A 页，磁盘上可能 A 先落地。

### 4.2 页本身也可能"撕裂"

即使是同一页，一个 4KB 的页写到磁盘时，底层设备也不一定保证原子性。断电时可能只写进去一部分（称为"撕裂写" torn write）。

### 4.3 应对思路

需要崩溃一致性的程序（数据库、文件系统、日志系统）通常采用以下方法之一：

- **预写日志（WAL，Write-Ahead Log）**：先把"我打算做什么修改"追加写到一个日志文件，并 `fsync`；然后再修改数据文件。崩溃后根据日志重放或回滚。
- **写时复制数据结构**：从不原地修改旧数据，而是把新版本写到新位置，最后用一次原子的"指针切换"（比如更新一个元数据页）让新版本生效。LMDB 就是这么做的（第 12 篇）。
- **校验和**：给每个数据块加上校验和，崩溃后能检测出哪些块损坏了。

所有这些方法都需要在关键步骤之间插入 `msync(MS_SYNC)` 或 `fsync`，作为"屏障"：确保前一步真正落盘之后，才开始下一步。

> 这是"数据库到底该不该用 mmap"之争的核心之一：mmap 让内核在任意时刻都可能写回任意脏页，程序很难控制写回顺序。第 12 篇会详细讨论。

## 五、错误去哪儿了？

用 `write` 时，如果出错（磁盘满了、I/O 错误），`write` 会返回 -1，你立刻就能知道。

用 mmap 写入数据，只是一条普通的内存写指令，**不可能返回错误码**。那么错误怎么报告呢？

1. **写回时发生的 I/O 错误**（比如磁盘坏道）：内核把错误记录在文件上，在你下一次调用 `msync(MS_SYNC)` 或 `fsync` 时返回 `EIO`。**如果你从来不调用 `msync`/`fsync`，你可能永远不知道数据没写进去。**
2. **缺页时无法完成的情况**：内核没法让一条内存访问指令"返回错误"，只能给进程发送一个信号——**SIGBUS**。

## 六、SIGBUS：mmap 的专属"地雷"

### 6.1 什么时候会收到 SIGBUS

| 原因 | 说明 |
|---|---|
| 访问超出文件末尾的整页 | 第 6 篇讲过：映射长度大于文件，访问完全在文件之外的页 |
| **映射后文件被截短** | 你映射了 1GB 文件，另一个进程把它截成了 1MB，你访问后面的部分 |
| 读取时发生 I/O 错误 | 缺页时需要从磁盘读，但磁盘返回错误 |
| 磁盘空间不足 | 你往一个"稀疏文件"的空洞里写数据，文件系统需要分配磁盘块，却发现磁盘满了 |
| 超出配额 | 类似磁盘满，用户的磁盘配额用完了 |

第二种最常见、也最危险：你的程序没有任何 bug，却因为**别人**修改了文件而崩溃。

### 6.2 实验：亲手制造 SIGBUS 并捕获它

```c
// sigbus_demo.c —— 映射后文件被截短，访问触发 SIGBUS
#include <stdio.h>
#include <signal.h>
#include <setjmp.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/mman.h>

static sigjmp_buf jump_back;

static void on_sigbus(int sig, siginfo_t *info, void *ctx) {
    (void)sig; (void)ctx;
    // 信号处理函数里只做最少的事；这里为了演示打印出错地址
    char msg[96];
    int n = snprintf(msg, sizeof msg, "  收到 SIGBUS！出错地址: %p\n", info->si_addr);
    write(2, msg, n);
    siglongjmp(jump_back, 1);           // 跳回安全点，避免重新执行出错指令
}

int main(void) {
    long page = sysconf(_SC_PAGESIZE);

    // 创建一个 2 页大的文件
    int fd = open("bus.bin", O_RDWR | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) { perror("open"); return 1; }
    if (ftruncate(fd, 2 * page) < 0) { perror("ftruncate"); return 1; }

    char *p = mmap(NULL, 2 * page, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }

    // 注册 SIGBUS 处理函数
    struct sigaction sa = {0};
    sa.sa_sigaction = on_sigbus;
    sa.sa_flags = SA_SIGINFO;
    sigaction(SIGBUS, &sa, NULL);

    p[page] = 'A';
    printf("截断前：写第 2 页成功，p[page] = %c\n", p[page]);

    // 模拟"另一个进程"把文件截成 1 页
    ftruncate(fd, page);
    printf("文件已被截短为 1 页\n");

    printf("访问第 1 页：p[0] = %d（正常）\n", p[0]);

    if (sigsetjmp(jump_back, 1) == 0) {
        printf("访问第 2 页...\n");
        char c = p[page];               // 这一页已在文件之外 → SIGBUS
        printf("读到 %c（不会执行到这里）\n", c);
    } else {
        printf("从 SIGBUS 中恢复，程序继续运行\n");
    }

    munmap(p, 2 * page);
    close(fd);
    return 0;
}
```

```bash
gcc sigbus_demo.c -o sigbus_demo && ./sigbus_demo
# 截断前：写第 2 页成功，p[page] = A
# 文件已被截短为 1 页
# 访问第 1 页：p[0] = 0（正常）
# 访问第 2 页...
#   收到 SIGBUS！出错地址: 0xffffa1b21000
# 从 SIGBUS 中恢复，程序继续运行
```

注意：截断文件时，内核会把已经映射进页表的、超出新文件末尾的页**从所有进程的页表中移除**。所以即使第 2 页之前已经被访问过，截断后再访问也会触发缺页，然后发现"文件里已经没有这一页了"，于是发送 SIGBUS。

### 6.3 用 sigsetjmp/siglongjmp 捕获是好主意吗？

上面的做法可以让程序在 SIGBUS 后继续运行，但在真实项目中要非常谨慎：

- 信号处理函数里能安全调用的函数非常有限；
- 跳回之前，程序可能正处在某个数据结构修改的中途，状态不一致；
- 多线程程序中处理更加复杂。

大多数程序的选择是：**预防 SIGBUS，而不是处理 SIGBUS。**

### 6.4 如何预防

| 风险 | 预防方法 |
|---|---|
| 访问超出文件末尾 | 映射前用 `fstat` 获取大小，绝不访问超出范围的部分 |
| 别人截断文件 | 只映射你能控制的文件；用文件锁（`flock`）协调；使用 `memfd_create` 的封印（`F_SEAL_SHRINK`）禁止截短 |
| 磁盘满导致写入失败 | 映射前用 `fallocate` / `posix_fallocate` **预先分配磁盘空间**，而不是只用 `ftruncate` 创建稀疏文件 |
| 读取 I/O 错误 | 硬件问题，通常只能接受进程崩溃，或用 SIGBUS 处理函数记录日志后退出 |

`ftruncate` 和 `fallocate` 的区别：

```c
ftruncate(fd, 1 << 30);          // 文件变成 1GB，但磁盘上没有分配空间（稀疏文件）
                                 // 读起来全是 0；写的时候才分配磁盘块，此时可能因磁盘满而 SIGBUS

posix_fallocate(fd, 0, 1 << 30); // 文件变成 1GB，并且磁盘块已经全部分配好
                                 // 如果空间不够，这个调用本身就会返回错误，而不是之后崩溃
```

## 七、混用 read/write 和 mmap

第 5 篇说过，Linux 上 `read`/`write` 和 mmap 共用同一个页缓存，所以它们之间是**天然一致**的：

- 进程 A 通过 `MAP_SHARED` 写入，进程 B 立刻可以 `read` 到；
- 进程 A 通过 `write` 写入，进程 B 的 `MAP_SHARED`（以及没写过对应页的 `MAP_PRIVATE`）映射立刻可以看到。

例外：

- **`O_DIRECT`**：它绕过页缓存直接读写磁盘，可能和 mmap 看到的内容不一致。内核会尽力处理（在直接 I/O 前后刷新或作废页缓存），但同时对同一区域既做直接 I/O 又做 mmap 是自找麻烦。
- **网络文件系统**（如 NFS）：多台机器之间的一致性由 NFS 协议决定，比本地文件系统弱得多。

## 八、改变文件大小

mmap 不能改变文件大小。如果文件需要增长（比如日志不断追加），常见的做法有：

### 做法一：先扩大文件，再重新映射

```c
// 文件从 old_size 增长到 new_size
posix_fallocate(fd, old_size, new_size - old_size);  // 或 ftruncate
munmap(p, old_size);
p = mmap(NULL, new_size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
```

问题：重新映射后地址可能变了，所有指向旧映射的指针都会失效。

### 做法二：mremap（Linux 专有）

```c
#define _GNU_SOURCE
#include <sys/mman.h>

ftruncate(fd, new_size);
p = mremap(p, old_size, new_size, MREMAP_MAYMOVE);
```

`mremap` 可以原地扩大映射；如果原地空间不够且指定了 `MREMAP_MAYMOVE`，内核会把映射搬到别处（只修改页表，不拷贝数据），但地址同样可能改变。

### 做法三：一次预留足够大的地址空间

```c
// 预留 64GB 地址空间（不占物理内存，也不要求文件这么大）
char *base = mmap(NULL, 64UL << 30, PROT_NONE, MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE, -1, 0);

// 文件增长后，用 MAP_FIXED 把文件映射到这块预留区域的开头
ftruncate(fd, cur_size);
mmap(base, cur_size, PROT_READ | PROT_WRITE, MAP_SHARED | MAP_FIXED, fd, 0);
```

地址永远不变，指针永远有效。这是 LMDB 等数据库常用的思路：一开始就映射一个"最大大小"，文件在其中慢慢增长。

> `MAP_FIXED` 在这里是安全的，因为我们覆盖的正是自己预留的区域。这也是 `MAP_FIXED` 少数正当的用法之一。

## 本篇小结

| 要点 | 说明 |
|---|---|
| 写入的数据在哪 | 在页缓存的脏页中，稍后由内核写回磁盘 |
| 内核如何追踪 mmap 写入 | 页表项先设为只读，首次写入触发缺页并标记脏页 |
| `msync(MS_SYNC)` | 把指定范围的脏页写到磁盘并等待完成，需要持久化时必须调用 |
| `MS_ASYNC` | 现代 Linux 上基本无实际作用 |
| munmap / 进程退出 | 共享映射的修改不会丢（仍在页缓存），但不保证已落盘 |
| 断电 | 未 msync 的脏页可能丢失 |
| 崩溃一致性 | 内核随时可能写回任意脏页，需要 WAL、写时复制等机制配合 msync |
| 错误报告 | 写回错误在 msync/fsync 时返回；缺页无法完成时发送 SIGBUS |
| SIGBUS 常见成因 | 文件被截短、访问超出文件末尾、磁盘满、I/O 错误 |
| 预防 SIGBUS | 检查大小、文件锁、memfd 封印、用 fallocate 预分配空间 |
| 文件增长 | 重新映射、mremap，或预留大块地址空间再 `MAP_FIXED` |
