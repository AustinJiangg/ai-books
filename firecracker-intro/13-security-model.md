## 引子：城堡的多道城墙

中世纪的城堡从不只依赖一道城墙：外面有护城河，然后是外城墙、内城墙，最里面还有主塔。攻击者每突破一道，都会面对下一道。设计者假设**每一道防线都有可能被攻破**，所以不把所有希望寄托在任何一层上。

这就是**纵深防御（Defense in Depth）**。Firecracker 的安全设计完全基于这个思想。

## 一、威胁模型

在讨论“安全”之前，必须先说清楚三件事：**防谁、他能做什么、我们要保护什么。** 这叫威胁模型。

### 1.1 攻击者：Guest 里的一切

Firecracker 官方设计文档的表述非常直接：**从 vCPU 线程开始运行的那一刻起，就认为它们在执行恶意代码。**

也就是说，Firecracker 假设：

- Guest 里的用户程序是攻击者写的；
- Guest 内核也已经被攻击者完全控制（或者干脆就是攻击者自己编译的内核）；
- 攻击者了解 Firecracker 的全部源码，可以构造任意的设备寄存器访问、任意的 virtqueue 数据、任意的网络包。

### 1.2 被信任的一方

与此相对，以下这些被视为**可信**的：

- 宿主机操作系统和管理员；
- 调用 Firecracker API 的程序（通常是编排系统）；
- 传给 jailer 的参数和放进 chroot 目录里的文件。

这意味着：如果你的编排系统本身被攻破、或者把用户可控的内容直接拼进了 API 请求，那已经超出了 Firecracker 的防护范围。

### 1.3 要保护什么

| 保护目标 | 具体含义 |
|---------|---------|
| 宿主机 | Guest 不能在宿主机上执行代码、读写文件、提升权限 |
| 其他 microVM | Guest 不能读取或干扰同一宿主机上的其他 microVM |
| 资源公平性 | Guest 不能耗尽宿主机的 CPU、内存、磁盘、网络，影响他人（拒绝服务） |

## 二、纵深防御的层次

把从 Guest 到宿主机的路径画出来，可以看到攻击者需要依次突破的屏障：

```
┌─────────────────────────────────────────────────────────────┐
│  ⓪ Guest：攻击者完全控制（不可信区域）                          │
└───────────────────────┬─────────────────────────────────────┘
                        │  屏障 1：硬件虚拟化 + KVM
                        │   Guest 只能通过 VM Exit 与外界交互
┌───────────────────────▼─────────────────────────────────────┐
│  ① Firecracker 设备模型（vCPU 线程、VMM 线程）                  │
│     屏障 2：极简设备 + Rust 内存安全 + 严格校验                   │
└───────────────────────┬─────────────────────────────────────┘
                        │  屏障 3：seccomp 系统调用过滤（每个线程不同）
┌───────────────────────▼─────────────────────────────────────┐
│  ② Firecracker 进程的权限范围                                  │
│     屏障 4：jailer —— chroot、命名空间、cgroups、非 root 用户     │
└───────────────────────┬─────────────────────────────────────┘
                        │  屏障 5：宿主机加固（防火墙、补丁、侧信道缓解）
┌───────────────────────▼─────────────────────────────────────┐
│  ③ 宿主机与其他 microVM（需要保护的区域）                         │
└─────────────────────────────────────────────────────────────┘
```

下面逐层分析。

### 2.1 屏障 1：硬件虚拟化与 KVM

Guest 的代码运行在 EL1/EL0，它和外界交互的唯一方式是触发 VM Exit（第 03 篇）。Stage-2 页表保证 Guest 只能访问分配给它的内存。

这一层的攻击面是 **KVM 本身**——它是宿主机内核的一部分，处理 Guest 的系统寄存器访问、vGIC 模拟、PSCI 调用等。KVM 的漏洞会直接危及宿主机内核。应对方式是：**及时更新宿主机内核**，并使用 Firecracker 官方支持和测试的内核版本。

### 2.2 屏障 2：极简的设备模型

突破 VM Exit 之后，攻击者面对的是 Firecracker 的设备模拟代码。这是 VMM 历史上漏洞最多的地方。Firecracker 的防御是：

- **设备少**：只有十来种设备，没有软驱、USB、显卡等复杂设备，攻击面比通用 VMM 小一到两个数量级；
- **Rust**：消除绝大部分内存安全漏洞（第 07 篇）；
- **严格校验**：所有来自 Guest 的地址、长度、索引都经过检查（第 10 篇第五节）；
- **单一职责**：API 线程不接触 Guest 数据，vCPU 线程只做轻量的 MMIO 处理；
- **持续测试**：模糊测试（fuzzing）对设备模型和 API 解析器持续“轰炸”随机输入；对部分关键代码用 Kani 工具做形式化验证，在数学上证明某些性质（比如“地址计算不会溢出”）总是成立。

### 2.3 屏障 3：seccomp

假设攻击者找到了一个 Firecracker 的漏洞，能在 Firecracker 进程里执行任意代码。接下来他会想调用系统调用：打开宿主机文件、创建网络连接、执行 shell……

**seccomp** 把这条路几乎堵死。下一节详细讲。

### 2.4 屏障 4：jailer

即使攻击者能用 seccomp 允许的系统调用做些事，jailer 已经把 Firecracker 进程关进了一个“牢房”：

- **chroot**：能看到的文件系统只有一个几乎空的目录；
- **命名空间**：独立的挂载、PID、网络视图；
- **cgroups**：CPU、内存等资源有硬上限；
- **非 root 用户**：没有特权，每台 microVM 可以用不同的用户 ID。

第 14 篇专门讲 jailer。

### 2.5 屏障 5：宿主机加固

最后是宿主机本身的配置：防火墙过滤 Guest 流量（第 11 篇）、关闭 swap 和 KSM（第 09 篇）、侧信道缓解（本篇第四节）等。

## 三、seccomp：只允许“白名单”上的系统调用

### 3.1 seccomp 是什么

**seccomp（Secure Computing Mode）** 是 Linux 内核提供的系统调用过滤机制。进程可以给自己（准确地说，给某个线程）安装一个过滤程序：

- 过滤程序用 **BPF**（一种内核内的小型虚拟机字节码）编写；
- 每次该线程执行系统调用，内核都会先运行这个过滤程序，根据**系统调用号和参数**决定：放行、返回错误、还是直接杀死进程；
- 过滤器**一旦安装就无法撤销或放宽**，只能叠加更严格的过滤器。

这意味着：即使攻击者完全控制了一个线程，也无法绕过它。

### 3.2 Firecracker 的过滤器

Firecracker 为三类线程分别准备了不同的白名单。以 ARM64 版本为例（v1.17 发布包中的 `seccomp-filter-v1.17.0-aarch64.json`），允许的系统调用种类大致如下：

| 线程 | 允许的系统调用种类数 | 典型内容 |
|------|----------------|---------|
| VMM 线程 | 约 55 种 | `read`、`write`、`readv`、`writev`、`epoll_pwait`、`ioctl`（限定参数）、`mmap`、`madvise`、`fsync`、io_uring 相关…… |
| API 线程 | 约 32 种 | `accept4`、`recvfrom`、`sendto`（处理 HTTP）、`epoll_pwait`、`write`…… |
| vCPU 线程 | 约 27 种 | `ioctl`（主要是 `KVM_RUN` 等少数命令）、`write`（串口输出）、`futex`…… |

作为对比，ARM64 Linux 内核提供了三百多个系统调用。Firecracker 的每个线程只能用其中不到五分之一，而且很多调用还**限制了参数**。比如 `ioctl` 是一个“万能”系统调用（通过不同的命令号做完全不同的事），Firecracker 的过滤器会精确指定允许哪些命令号：

```json
{
  "syscall": "ioctl",
  "args": [
    { "index": 1, "type": "dword", "op": "eq", "val": 1077980793, "comment": "KVM_IOEVENTFD" }
  ]
}
```

意思是：只有当 `ioctl` 的第 2 个参数（命令号）等于 `KVM_IOEVENTFD` 时才放行。

值得注意的是**没有出现在白名单里的**系统调用：

- `execve`：无法执行任何新程序（比如启动 shell）；
- `fork`、`vfork`：无法创建新进程（`clone` 只允许以“创建线程”的参数组合调用）；
- `unlink`、`rename`、`mkdir`、`mount`、`chmod`：无法修改文件系统结构；
- `bind`、`listen`：无法开启新的监听端口；`socket` 只允许创建 Unix socket（`AF_UNIX`），不能创建 TCP/UDP socket；
- `ptrace`、`process_vm_readv`：无法调试或读取其他进程。

也有一些“看起来危险”的调用仍然被允许，因为 Firecracker 正常工作需要它们。比如 `openat` 没有参数限制（打开内核、磁盘、日志文件都需要它），`connect` 也被允许（vsock 需要连接宿主机上的 Unix socket）。这正是 seccomp 需要和 jailer 配合的原因：seccomp 管“能调用什么”，jailer 的 chroot 和降权管“调用了能碰到什么”——在 chroot 里，`openat` 只能打开牢笼里那几个文件。

### 3.3 什么时候安装

每个线程的过滤器都是在**执行任何 Guest 代码之前**安装的。这很重要：如果先运行 Guest、再安装过滤器，中间就存在一个没有保护的窗口期。

### 3.4 违规时会发生什么

默认动作是 **trap**：内核向线程发送 `SIGSYS` 信号。Firecracker 的信号处理函数会记录日志、更新 `seccomp.num_faults` 指标，然后以退出码 **148** 终止整个进程。

也就是说：**一旦 Firecracker 试图调用白名单之外的系统调用，这台 microVM 会立即被终止。** 对于正常运行的 Firecracker，这永远不应该发生；如果发生了，要么是 Firecracker 的 bug（比如新版本内核引入了新的系统调用路径），要么就是正在遭受攻击。

### 3.5 过滤器的来源与定制

- 发布包中的 Firecracker 二进制**内置**了默认过滤器（在编译时由 JSON 生成 BPF 并嵌入）；
- 发布包里附带了 JSON 源文件，你可以阅读它；
- 可以用 `seccompiler-bin` 把自己修改过的 JSON 编译成 BPF，再通过 `--seccomp-filter` 参数加载；
- `--no-seccomp` 参数可以完全关闭过滤——**仅用于调试，生产环境绝不能使用**。

从 v1.11 起，Firecracker 的 seccomp 编译器改为基于成熟的 `libseccomp` 库，生成的 BPF 更小、更高效。

### 3.6 动手：观察 seccomp

```bash
# 1. 看看发布包里的过滤器规则
cd ~/fc-lab
python3 - <<'EOF'
import json, glob
f = glob.glob("release-*/seccomp-filter-*.json")[0]
d = json.load(open(f))
for thread, v in d.items():
    names = sorted({r["syscall"] for r in v["filter"]})
    print(f"{thread:6} 默认动作={v['default_action']:5} 允许 {len(names)} 种: {', '.join(names[:12])} ...")
EOF

# 2. 启动一台 microVM 后，确认每个线程都启用了 seccomp
FC_PID=$(pgrep -f 'firecracker --api-sock' | head -1)
for t in /proc/$FC_PID/task/*; do
  printf "%-12s %s\n" "$(cat $t/comm)" "$(grep -E '^Seccomp:' $t/status)"
done
```

`Seccomp: 2` 表示该线程处于“过滤模式”。每个线程都应该是 2。

```bash
# 3. 看看 seccomp 相关的指标（需配置 metrics）
sudo curl -X PUT --unix-socket /tmp/firecracker.socket \
    -d '{"action_type":"FlushMetrics"}' http://localhost/actions
tail -n 1 metrics.json | jq '.seccomp'
```

正常情况下 `num_faults` 为 0。

## 四、侧信道：最难防的攻击

### 4.1 什么是侧信道

前面的防线都在阻止攻击者“直接读取”不属于他的数据。**侧信道攻击**另辟蹊径：通过测量时间、缓存状态等“副作用”，间接推断其他程序的数据。

2018 年公开的 **Spectre** 和 **Meltdown** 是最著名的例子：利用 CPU 的推测执行和缓存，一个程序可以推断出本应无权访问的内存内容。此后又陆续出现了大量变种（MDS、L1TF、Retbleed 等），其中很多与超线程（SMT）、共享缓存有关。

对于多租户场景，侧信道意味着：**即使虚拟化隔离完美无缺，同一台物理机上的两个 Guest 仍可能通过共享的硬件资源互相窥探。**

### 4.2 缓解措施

Firecracker 本身能做的有限，主要依靠宿主机配置。官方生产指南（`docs/prod-host-setup.md`）推荐：

| 措施 | 作用 |
|------|------|
| **关闭 SMT（超线程）** | 很多侧信道攻击要求攻击者和受害者在同一个物理核的两个超线程上运行。（ARM64 服务器芯片如 Graviton 本身没有 SMT） |
| 启用宿主机内核的各项漏洞缓解 | 如 Spectre、SSBD（推测存储绕过）相关的缓解选项 |
| 及时更新 CPU 微码 | 部分漏洞需要微码修复 |
| **关闭 KSM** | 防止通过内存合并探测其他 Guest 的内存内容（第 09 篇） |
| 关闭 swap 或使用加密 swap | 防止 Guest 数据残留在磁盘 |
| 使用带 Rowhammer 缓解的内存 | 防止通过频繁访问内存引发相邻位翻转 |
| 绑核与 cgroups 隔离 | 减少不同租户在同一物理核上交替运行 |
| 使用 CPU 模板 | 控制暴露给 Guest 的 CPU 特性，统一不同宿主机的“CPU 指纹”（第 16 篇） |

在 ARM64 上，Firecracker 还会在宿主内核支持时，把 Guest 的物理计数器归零（v1.11 起），避免 Guest 读到宿主机的运行时长等信息。

检查宿主机的漏洞缓解状态：

```bash
grep . /sys/devices/system/cpu/vulnerabilities/*
cat /sys/devices/system/cpu/smt/control 2>/dev/null   # x86 上查看 SMT 状态
```

## 五、拒绝服务：别让一个人拖垮所有人

除了窃取数据，恶意 Guest 还可能试图耗尽宿主机资源。

| 攻击方式 | 防御 |
|---------|------|
| 疯狂占用 CPU | cgroups CPU 配额；vCPU 线程是普通线程，受调度器管理 |
| 写满全部内存，拒绝气球回收 | cgroups 内存上限（只会杀死这台 microVM 自己） |
| 疯狂读写磁盘 | 块设备限速器 + cgroups io 控制 |
| 网络洪泛 | 网卡限速器 + 宿主机防火墙限速 |
| 疯狂往串口写数据，撑爆日志 | 生产环境关闭串口；v1.16 起支持串口输出限速 |
| 制造大量错误日志 | v1.16 起 Firecracker 对日志按调用点限速（每 5 秒每处最多 10 条） |
| 构造畸形 virtqueue 让 VMM 线程空转 | 设备实现的各种边界检查与修复 |

## 六、生产环境安全检查清单

综合本篇和前后几篇的内容：

**Firecracker 配置**
- [ ] 使用官方发布的静态链接二进制，Firecracker 与 jailer 版本一致
- [ ] 不使用 `--no-seccomp`
- [ ] 关闭串口，或至少把输出重定向到受控位置并限速
- [ ] 日志和指标输出到受控文件或管道，注意不要被写满
- [ ] 不使用标记为“开发者预览”的功能（除非评估过风险）

**jailer 配置（第 14 篇）**
- [ ] 每台 microVM 使用独立的 uid/gid
- [ ] 每台 microVM 独立的 chroot 目录
- [ ] 配置 cgroups 限制 CPU 和内存
- [ ] 使用独立的网络命名空间和 PID 命名空间

**宿主机**
- [ ] 使用官方支持的宿主机内核版本，及时打补丁
- [ ] 关闭 SMT（如果硬件有），启用漏洞缓解，更新微码
- [ ] 关闭 KSM，关闭或加密 swap
- [ ] 为 TAP 设备配置严格的防火墙规则（防元数据服务访问、防伪造、防横向移动）
- [ ] 镜像文件只读共享，可写盘每台独立，销毁时清理

**运维**
- [ ] 监控 `seccomp.num_faults` 等安全相关指标，非零立即告警
- [ ] 关注 Firecracker 的安全公告（仓库中的 `SECURITY.md` 说明了漏洞报告流程）

## 小结

| 屏障 | 挡住什么 | 关键机制 |
|------|---------|---------|
| 硬件虚拟化 + KVM | Guest 直接访问宿主机资源 | EL2、Stage-2、VM Exit |
| 极简设备模型 | 利用设备模拟漏洞逃逸 | 少量设备、Rust、校验、fuzzing、形式化验证 |
| seccomp | 逃逸后滥用系统调用 | 每线程白名单、参数过滤、违规即终止（退出码 148） |
| jailer | 逃逸后访问文件、进程、资源 | chroot、命名空间、cgroups、降权 |
| 宿主机加固 | 侧信道、网络滥用、资源耗尽 | 关 SMT/KSM/swap、防火墙、限速 |

## 思考题

1. 为什么 Firecracker 把“调用 API 的程序”视为可信的？如果你在构建一个平台，让用户可以指定自己的内核启动参数，需要注意什么？
2. seccomp 过滤器为什么必须在 Guest 代码运行之前安装？
3. 为什么 vCPU 线程的 seccomp 白名单比 VMM 线程的更短？
4. 一个攻击者通过 Firecracker 的漏洞在 VMM 线程里执行了任意代码，但 seccomp 和 jailer 都正常工作。他还能做哪些事？不能做哪些事？
5. 关闭 SMT 会损失一部分 CPU 性能。在什么场景下你会选择不关闭？
