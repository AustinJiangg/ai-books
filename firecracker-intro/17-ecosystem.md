## 引子：发动机与整车

第 04 篇说过，Firecracker 是一个“零件”，不是一个“平台”。它只负责一件事：在一个进程里运行一台 microVM。下载镜像、分配网络、调度到哪台机器、监控、计费……这些都不归它管。

就像一台优秀的发动机，需要装进不同的整车才能上路。这一篇看看 Firecracker 被装进了哪些“整车”，以及如果你想自己造一辆车，需要准备哪些零件。

---

## 一、AWS 内部：Firecracker 的“娘家”

### 1.1 AWS Lambda

Lambda 是 Firecracker 诞生的原因（第 04 篇）。在公开的资料和论文中，AWS 介绍了大致的架构思路：

- 大量裸金属服务器作为“工作节点”，每台节点上运行成百上千个 Firecracker microVM；
- 每个 microVM 承载一个函数的执行环境，不同客户的函数通过 microVM 隔离，可以安全地混部在同一台物理机上；
- 上层的调度系统负责决定在哪台节点、哪个 microVM 里执行请求，并管理 microVM 的创建、复用与回收。

**Lambda SnapStart** 是 Firecracker 快照能力（第 15 篇）的典型应用：函数发布时，Lambda 先初始化好执行环境并创建快照；之后冷启动时直接从快照恢复，跳过运行时初始化过程。这对 Java 等初始化较慢的运行时效果尤其明显。正因为涉及“从同一快照恢复多次”，AWS 也在文档中提醒开发者注意唯一性问题（随机数、连接等），并提供了恢复前后的钩子——这和第 15 篇第五节讨论的内容完全一致。

### 1.2 AWS Fargate

Fargate 是 AWS 的无服务器容器服务：用户只提供容器镜像，不用管理服务器。Firecracker 的官方介绍中提到它也被用于 Fargate。与 Lambda 类似，用户的容器运行在独立的轻量虚拟机里，获得比普通容器更强的隔离。

## 二、把 microVM 包装成容器

很多团队已经在用 Docker、Kubernetes 管理应用，他们希望获得虚拟机级别的隔离，又不想改变使用容器的方式。于是出现了“**用 microVM 运行容器**”的项目。

### 2.1 Kata Containers

**Kata Containers** 是 OpenInfra 基金会下的开源项目，它实现了一个 OCI 兼容的容器运行时：在 Kubernetes 里，你可以通过 `RuntimeClass` 指定某些 Pod 使用 Kata 运行。对 Kubernetes 来说，它就是一个普通的容器运行时；实际上，每个 Pod 都运行在一台独立的轻量虚拟机里。

```
Kubernetes → containerd → Kata 运行时（shim）→ 启动一台 VM（Firecracker / QEMU / Cloud Hypervisor）
                                                   └── Guest 里的 kata-agent 负责启动 Pod 中的容器
```

Kata 支持多种 VMM，Firecracker 是其中之一。Kata 自己的文档把 Firecracker 描述为“极其精简”的选项：容器创建速度和内存密度非常出色，代价是**不支持所有类型的设备**。比如 Kata 常用的 virtio-fs（把宿主机目录共享给 Guest 的文件系统）Firecracker 并不提供，因此搭配 Firecracker 时，容器的根文件系统需要以块设备的形式交给 Guest（常见做法是借助 containerd 的 devmapper 快照器）。

这恰好体现了 Firecracker 的取舍：用功能换取简单、速度和安全。

### 2.2 firecracker-containerd

**firecracker-containerd** 是 Firecracker 团队维护的项目，它让 containerd 能够把容器运行在 Firecracker microVM 里。核心组件包括：

- 一个 containerd 的运行时插件，负责创建 microVM；
- Guest 里的一个代理程序，通过 **vsock**（第 11 篇）接收宿主机的指令，在 Guest 内部启动容器；
- 一个“快照器”，把容器镜像层转换成可以挂载到 microVM 的块设备。

它很好地展示了一个“容器 on microVM”系统需要解决的问题。不过它的活跃度不如 Firecracker 主项目，使用前建议查看仓库的最新状态。

### 2.3 其他项目

- **Flintlock**（Liquid Metal 项目的一部分）：一个管理 microVM 生命周期的服务，面向在裸金属上运行轻量 Kubernetes 集群等场景，支持 Firecracker 和 Cloud Hypervisor；
- **Weave Ignite**：早期一个“像用 Docker 一样用 Firecracker”的工具，已经停止维护，但它的设计思路（用 OCI 镜像作为 microVM 的 rootfs）影响了后来的很多项目。

## 三、云平台与开发者服务

### 3.1 Fly.io

Fly.io 是一个面向开发者的全球应用托管平台。用户提供容器镜像，Fly.io 把它转换成 rootfs，运行在全球各地的服务器上。根据 Fly.io 的架构文档，**用户的应用代码运行在 Firecracker microVM 中**，每个应用实例都有硬件虚拟化级别的隔离。Fly.io 的“Machines”产品把 microVM 的创建、启动、停止直接暴露成 API，启动速度快到可以“按请求启动”。

### 3.2 AI 代码沙箱

近年最热门的新场景，是**给 AI Agent 执行代码的沙箱**。大语言模型生成的代码可能有 bug，也可能被提示注入攻击诱导执行恶意操作——这正是“运行陌生人的代码”的典型情形。

以开源项目 **E2B** 为例，它为 AI Agent 提供云端沙箱：每个沙箱都是一台带独立 Linux 内核的 **Firecracker microVM**，项目以 Apache 2.0 许可证开源，也支持用 Terraform 自行部署基础设施。

这类平台通常会综合运用本系列讲过的几乎所有技术：

| 需求 | 用到的 Firecracker 特性 |
|------|----------------------|
| 沙箱要在亚秒级就绪 | 快照恢复（第 15 篇）、精简内核与 rootfs |
| 宿主机要能下发代码、取回结果、读写文件 | Guest 代理 + vsock 或网络（第 11 篇） |
| 同一台机器跑大量沙箱 | 内存按需分配、超卖、共享只读镜像（第 09、12 篇） |
| 沙箱不能攻击宿主机或其他沙箱 | jailer、seccomp、网络命名空间、出站过滤（第 13、14、11 篇） |
| 沙箱可以暂停、保存、稍后继续 | 暂停 + 快照 |
| 从同一模板快速克隆很多沙箱 | 快照 + 网络命名空间（相同内部 IP）+ 唯一性处理 |

## 四、自己搭一个 microVM 平台：需要哪些组件

如果你要在自己的服务器上构建一个类似的平台，至少需要考虑下面这些组件。这张图也是对整个系列的一次总结：

```
                          ┌─────────────────────┐
     用户 / 上层服务 ────▶  │  API 与调度层          │ 决定在哪台宿主机上创建、何时回收
                          └──────────┬──────────┘
                                     │
          ┌──────────────────────────┼─────────────────────────────┐
          │                 每台宿主机上的“节点代理”                    │
          │                                                         │
          │  ┌────────────┐ ┌────────────┐ ┌────────────┐ ┌───────┐ │
          │  │ 镜像管理     │ │ 网络管理     │ │ 存储管理     │ │ 快照库 │ │
          │  │ OCI→rootfs │ │ netns/TAP  │ │ CoW 可写盘   │ │       │ │
          │  │ 内核版本     │ │ IP 分配/NAT │ │ 清理/配额    │ │       │ │
          │  │            │ │ nftables   │ │            │ │       │ │
          │  └────────────┘ └────────────┘ └────────────┘ └───────┘ │
          │  ┌─────────────────────────────────────────────────────┐ │
          │  │ 生命周期管理：jailer 启动 → API 配置 → 监控 → 清理       │ │
          │  └─────────────────────────────────────────────────────┘ │
          │  ┌─────────────────────────────────────────────────────┐ │
          │  │ 可观测性：日志、指标、seccomp 告警                       │ │
          │  └─────────────────────────────────────────────────────┘ │
          │        │ jailer + Firecracker（每个 microVM 一个）           │
          │        ▼                                                 │
          │   ┌─────────┐ ┌─────────┐ ┌─────────┐                    │
          │   │ microVM │ │ microVM │ │ microVM │  Guest 里运行代理 ◀─vsock─┐
          │   └─────────┘ └─────────┘ └─────────┘                    │   │
          └─────────────────────────────────────────────────────────┘   │
                                                     节点代理 ──────────┘
```

### 4.1 各组件要解决的问题

| 组件 | 要解决的问题 | 相关篇章 |
|------|------------|---------|
| **镜像管理** | 把 OCI 镜像转换为 ext4（或其他格式）rootfs；缓存和复用基础镜像；管理 Guest 内核版本 | 05、12 |
| **网络管理** | 为每台 microVM 创建网络命名空间、TAP、veth；分配 IP；配置 NAT 和端口映射；**编写出站过滤规则**；避免与宿主机上其他系统（Docker、其他平台）的网段和设备名冲突 | 11 |
| **存储管理** | 为每台 microVM 快速创建可写层（reflink、LVM 精简卷、device-mapper 快照等）；配额；销毁时安全删除 | 12 |
| **生命周期管理** | 用 jailer 启动 Firecracker；通过 API 配置；监控进程存活；处理异常退出；**可靠地清理** chroot、cgroup、命名空间、TAP | 05、06、14 |
| **快照库** | 创建、存储、分发快照；保证快照与宿主机 CPU 型号、Firecracker 版本匹配；处理克隆唯一性 | 15、16 |
| **Guest 代理** | 运行在 Guest 内的小程序，通过 vsock 接收指令（执行命令、传文件、健康检查），在快照恢复后重新初始化随机状态和网络 | 11、15 |
| **元数据与凭证分发** | 通过 MMDS 下发配置和临时凭证，避免把密钥写进镜像或快照 | 11 |
| **资源控制** | cgroups 限制 CPU、内存、IO；限速器；超卖比例控制 | 09、12、14 |
| **可观测性** | 收集 Firecracker 日志和指标，以及 Guest 内的日志；对 `seccomp.num_faults` 等安全指标告警 | 06、16 |
| **宿主机加固** | 内核版本与补丁、关闭 SMT/KSM/swap、漏洞缓解、防火墙基线 | 13 |
| **升级策略** | Firecracker 版本升级可能导致旧快照不可用；宿主机内核升级需要验证 | 04、15 |

### 4.2 常见的工程难点

根据社区经验，以下几个问题往往比“启动一台 microVM”本身难得多：

1. **清理的可靠性**：进程崩溃、宿主机重启、编排系统自身故障时，都要保证资源（TAP、netns、cgroup、磁盘文件、iptables 规则）不泄漏。最好设计成“声明式”的：定期对比“应该存在的”和“实际存在的”，清理多余的；
2. **网络命名冲突**：同一台机器上如果同时运行多套使用 Firecracker 或容器的系统，各自创建的 veth 设备名、内部网段、iptables 链名可能冲突。在规划时为每套系统使用独立的前缀和网段；
3. **快照与版本的匹配**：快照必须和 Firecracker 版本、CPU 型号匹配，大规模集群中要跟踪每个快照的“出生环境”；
4. **冷启动的长尾**：快照恢复后的缺页延迟、镜像首次拉取、页缓存未命中，都可能让少数请求变得很慢；
5. **多租户安全的完整性**：任何一个环节（比如忘了过滤到云元数据服务的流量）都可能成为突破口。

## 五、相关的开源工具与 SDK

| 工具 | 用途 |
|------|------|
| `firecracker-go-sdk` | 官方 Go 语言 SDK，封装了 API 调用、jailer 启动、网络配置（支持 CNI 插件） |
| Firecracker 仓库中的 `tools/devtool` | 在容器化的开发环境中构建 Firecracker、运行测试 |
| `resources/rebuild.sh` 等脚本 | 官方构建 CI 用的 Guest 内核和 rootfs 的脚本，适合参考来定制自己的镜像 |
| `resources/guest_configs/` | 官方 Guest 内核配置（包括 ARM64 各版本） |
| CNI 插件（如 `tc-redirect-tap`） | 让 Firecracker 接入标准的容器网络接口生态 |

## 小结

| 类别 | 代表 | Firecracker 的角色 |
|------|------|------------------|
| 云厂商内部 | AWS Lambda、Fargate | 多租户隔离的基础；SnapStart 基于快照 |
| 容器运行时 | Kata Containers、firecracker-containerd | 以 microVM 承载容器/Pod |
| 开发者平台 | Fly.io | 用户应用运行在 microVM 中 |
| AI 沙箱 | E2B 等 | 安全执行 AI 生成的代码 |
| 自建平台 | 你的系统 | 需要补齐镜像、网络、存储、调度、代理、清理、可观测性等组件 |
