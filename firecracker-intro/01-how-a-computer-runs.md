## 引子：讲 Firecracker，为什么从这里开始？

Firecracker 是一个"虚拟机监视器"（VMM），它的工作是在一台真实的电脑里，用软件"变出"很多台小电脑。

要理解"变出一台电脑"，你得先知道一台真实的电脑由什么组成、是怎么运转的。否则后面讲到"Firecracker 给虚拟机模拟了一个串口""Guest 发生了 MMIO 退出""vCPU 线程陷入 KVM"时，这些词都会像天书。

所以第一篇我们不谈虚拟化，只把一台普通电脑从里到外看一遍。这篇里埋下的几个概念——**寄存器、内存地址、MMIO、中断、特权级、系统调用、虚拟内存**——后面每一篇都会用到。

## 一、电脑的四大件：用一间厨房来理解

把电脑想象成一间餐厅后厨：

| 硬件 | 厨房里的角色 | 特点 |
|------|-------------|------|
| **CPU（处理器）** | 厨师 | 真正干活的人，但一次只能盯着手头的东西 |
| **内存（RAM）** | 案板 | 厨师手边的工作台，拿取极快，但面积有限，下班（断电）就清空 |
| **存储（SSD/硬盘）** | 冷库 | 容量大，断电也不丢，但每次去取都要走一段路 |
| **外设（网卡、键盘、屏幕、串口……）** | 传菜口、点单窗口 | 和外界打交道的通道 |

做一道菜的过程是：从冷库把食材搬到案板上（从硬盘加载程序到内存），厨师在案板上切配烹饪（CPU 处理内存里的数据），最后通过传菜口送出去（通过外设输出结果）。

一个关键事实：**CPU 只能直接处理内存里的东西**。程序存在硬盘上时，它只是一堆"躺着"的数据；必须先被加载进内存，CPU 才能执行它。后面讲 Firecracker 启动虚拟机时，第一步就是把 Guest 的内核文件"搬"进虚拟机的内存——道理完全一样。

## 二、CPU：一个不停"取指令、做事"的机器

### 2.1 指令：CPU 唯一听得懂的语言

CPU 不认识 Python、Java，甚至不认识 C。它只认识**机器指令**——一条条非常简单的命令，比如"把两个数相加""把某个地址的数据读进来""跳到另一条指令去执行"。

每种 CPU 架构都有自己的指令集。你手上的机器是 **ARM64**（也叫 AArch64），常见的 PC 和服务器则多是 **x86-64**。它们的指令完全不同，所以为 x86 编译的程序不能直接在 ARM64 上跑。

下面是一段 ARM64 汇编（指令的"人类可读版"）：

```asm
mov  x0, #2        // 把数字 2 放进 x0
mov  x1, #3        // 把数字 3 放进 x1
add  x2, x0, x1    // x2 = x0 + x1，结果是 5
```

### 2.2 寄存器：CPU 手里的"小纸条"

上面的 `x0`、`x1`、`x2` 叫**寄存器**。它们是 CPU 内部极少量、极快的存储单元。用厨房类比，寄存器就是厨师手里正握着的那几样东西——比案板还近。

ARM64 有 31 个通用寄存器（`x0` 到 `x30`），每个 64 位。此外还有几个特殊寄存器，最重要的是：

- **PC（Program Counter，程序计数器）**：记录"下一条要执行的指令在内存的哪个位置"。
- **SP（Stack Pointer，栈指针）**：指向当前的栈顶，函数调用时用来保存临时数据。
- **PSTATE**：记录 CPU 当前的状态，包括"现在运行在什么权限级别"（第五节会讲）。

> 📌 **为后文埋伏笔：** 一个 CPU 在某一瞬间的"全部状态"，基本就是它所有寄存器的值。如果把这些值完整保存下来，过一会儿再原样恢复，CPU 就能从中断的地方继续跑。这是操作系统切换任务的基础，也是第 15 篇 **Firecracker 快照**能把整台虚拟机"冻住再复活"的基础。

### 2.3 CPU 的工作循环

CPU 的一生就在重复三件事：

1. **取指（Fetch）**：按 PC 指向的地址，从内存取出一条指令；
2. **译码（Decode）**：弄清这条指令要干什么；
3. **执行（Execute）**：执行它，然后更新 PC 指向下一条。

现代 CPU 每秒能做几十亿次这样的循环（这就是"主频 3 GHz"的含义），还会用流水线、乱序执行等技巧同时处理多条指令，但基本模型不变。

### 2.4 多核

现在的 CPU 通常有多个**核心（core）**，每个核心都是一个独立的"厨师"，有自己的一套寄存器，可以同时执行不同的程序。后面你会看到，Firecracker 给虚拟机分配的 **vCPU（虚拟 CPU）**，本质上就是让 Guest 以为自己有几个核心。

## 三、内存：一条很长很长的"格子街"

### 3.1 地址

内存可以想象成一条很长的街道，每个门牌对应一个**字节**（8 个二进制位），门牌号就叫**地址**。一台 8 GB 内存的机器，大约有 80 亿个门牌。

CPU 读写内存时，就是在说"给我门牌 `0x4000_1000` 那里的 8 个字节"或"把这个数写到门牌 `0x4000_2000`"。

### 3.2 存储层次：越近越快，越快越小

| 层次 | 典型延迟（数量级） | 容量（数量级） |
|------|------------------|---------------|
| 寄存器 | < 1 纳秒 | 几百字节 |
| CPU 缓存（L1/L2/L3） | 1～几十纳秒 | KB～几十 MB |
| 内存 | 约 100 纳秒 | GB |
| SSD | 几十～几百微秒 | TB |
| 机械硬盘 | 约 10 毫秒 | TB |

从内存到 SSD，速度差了上千倍。这就是为什么程序必须先加载到内存再运行，也是为什么第 15 篇里"快照恢复时内存怎么加载"会成为性能关键。

## 四、外设：CPU 怎么和外界打交道

CPU 需要和网卡、硬盘控制器、串口等设备交流。这里有两个机制，**请你一定记住**，它们是理解 Firecracker 设备模型的钥匙。

### 4.1 MMIO：把设备"伪装"成内存

在 ARM64 上，设备通常通过 **MMIO（Memory-Mapped I/O，内存映射 I/O）** 来访问：系统把一部分地址"划给"设备。CPU 往这些地址写数据时，数据并不会进入内存条，而是送到了设备那里。

举个例子：假设串口设备占用地址 `0x0900_0000`。CPU 执行"往 `0x0900_0000` 写入字母 `A`"，串口就会把 `A` 发送出去，你在终端上就能看到它。

对 CPU 来说，读写设备和读写内存用的是同一类指令，区别只在于地址落在哪里。

> 📌 **伏笔：** 在虚拟机里，这些"设备地址"背后其实没有真实设备。当 Guest 访问它们时，CPU 会停下来通知宿主：“它在碰设备了，你来处理。”这就是第 3 篇和第 10 篇要讲的 **MMIO 退出**。Firecracker 的设备默认通过 **virtio-mmio** 呈现给 Guest，名字里的 MMIO 就是这个意思。

### 4.2 中断：设备主动"喊一嗓子"

设备什么时候有新数据？比如网卡收到一个数据包。CPU 有两种方式知道：

- **轮询**：CPU 每隔一会儿去问一次“有数据吗？”——简单但浪费；
- **中断**：设备有事时主动发一个信号，CPU 暂停手头工作，跳去处理这件事，处理完再回来。

中断就像餐厅里的叫号铃：厨师不用一直盯着点单窗口，铃响了再过去。

ARM64 上负责管理和分发中断的硬件叫 **GIC（Generic Interrupt Controller）**。第 10 篇会讲 Firecracker 怎么借助 KVM 把"虚拟中断"送进 Guest。

## 五、操作系统内核：后厨的总管

### 5.1 如果没有操作系统

假设电脑上同时跑着浏览器、音乐播放器和下载工具，而它们都可以直接操作硬件：

- 浏览器和下载工具同时往网卡写数据，数据包混在一起；
- 某个程序写错了内存地址，把另一个程序的数据覆盖了；
- 一个程序写了死循环，独占 CPU，其他程序永远轮不到。

这就像后厨里每个厨师都随便抢灶台、随便拿别人的食材——一片混乱。

### 5.2 内核的职责

**操作系统内核**（Linux 就是一个内核）就是后厨总管，它负责：

1. **管理 CPU**：决定哪个程序在哪个核心上跑多久（调度）；
2. **管理内存**：给每个程序分配内存，并阻止它们互相越界；
3. **管理设备**：统一操作硬件，程序想用设备必须通过内核；
4. **管理文件**：把硬盘上的一块块数据组织成文件和目录；
5. **提供安全边界**：检查权限，阻止程序做它无权做的事。

但这里有个问题：如果普通程序**有能力**直接操作硬件，内核又怎么“阻止”它？靠程序自觉吗？当然不行。答案在 CPU 硬件本身。

## 六、特权级：CPU 内置的"员工证等级"

### 6.1 ARM64 的异常级别

ARM64 CPU 在任何时刻都运行在某个**异常级别（Exception Level，EL）**上，级别越高，权限越大：

| 级别 | 通常运行什么 | 能做什么 |
|------|------------|---------|
| **EL0** | 普通应用程序（用户态） | 只能做计算和访问自己的内存 |
| **EL1** | 操作系统内核（内核态） | 可以配置内存映射、操作设备、处理中断 |
| **EL2** | 虚拟机监视器（Hypervisor） | 可以管理多个"EL1 内核"——**这就是虚拟化的舞台** |
| **EL3** | 安全监控固件 | 最高权限，负责安全世界切换 |

在 x86 上对应的概念叫"Ring 0～3"，原理类似。

关键在于：**某些指令和某些寄存器，只有在足够高的级别才能使用**。EL0 的程序如果试图修改内存映射配置，CPU 会直接拒绝并触发一个"异常"，把控制权交给内核处理，通常的结果是内核杀掉这个程序。

所以权限控制不是靠程序自觉，而是由 **CPU 硬件强制执行**的。

> 📌 **伏笔：** 表格里的 EL2 请留意。第 3 篇会讲到，KVM 正是利用 EL2，让一个 Guest 内核“以为”自己运行在 EL1、掌控整台机器，实际上它的一举一动都在宿主的掌控之下。

### 6.2 用户态和内核态

日常说的**用户态**就是 EL0，**内核态**就是 EL1。你写的 Python 脚本、运行的浏览器都在用户态；Linux 内核在内核态。

## 七、系统调用：程序向内核"递申请单"

### 7.1 一条 `printf` 的旅程

既然用户态程序不能直接碰设备，那它怎么在屏幕上打印文字、怎么读文件、怎么发网络包？

答案是**系统调用（system call）**：程序准备好参数，然后执行一条特殊指令，主动"陷入"内核，请内核代为完成。在 ARM64 上，这条指令是 `svc`（Supervisor Call）。

约定很简单：

- 系统调用编号放在寄存器 `x8`；
- 参数依次放在 `x0`、`x1`、`x2`……；
- 执行 `svc #0`，CPU 从 EL0 切换到 EL1，跳进内核的处理代码；
- 内核做完事，把返回值放进 `x0`，再切回 EL0，程序继续往下跑。

### 7.2 动手：不借助任何库，直接请内核打印一句话

在你的 ARM64 机器上新建 `hello.s`：

```asm
    .global _start

    .section .rodata
msg:
    .ascii "hello, kernel\n"     // 共 14 个字节

    .text
_start:
    // write(1, msg, 14)：向标准输出写 14 个字节
    mov  x0, #1          // 参数1：文件描述符 1（标准输出）
    ldr  x1, =msg        // 参数2：字符串的地址
    mov  x2, #14         // 参数3：长度
    mov  x8, #64         // ARM64 上 write 的系统调用号是 64
    svc  #0              // 陷入内核！

    // exit(0)：退出程序
    mov  x0, #0          // 参数1：退出码 0
    mov  x8, #93         // ARM64 上 exit 的系统调用号是 93
    svc  #0
```

编译运行：

```bash
as hello.s -o hello.o
ld hello.o -o hello
./hello
# 输出：hello, kernel
```

这个程序没有链接 C 标准库，只靠两次 `svc` 就完成了打印和退出。你平时用的 `printf`、`print()`，绕了很多层之后，最终也是落到这样一次系统调用上。

### 7.3 动手：用 strace 偷看系统调用

`strace` 可以记录一个程序做的所有系统调用（没装的话先 `sudo apt install strace` 或 `sudo dnf install strace`）：

```bash
strace ./hello
```

你会看到类似：

```
execve("./hello", ["./hello"], ...) = 0
write(1, "hello, kernel\n", 14hello, kernel
)         = 14
exit(0)                                 = ?
```

再对比一下普通命令：

```bash
strace -c ls > /dev/null
```

`-c` 会统计 `ls` 调用了哪些系统调用、各多少次。一个简单的 `ls` 也要和内核打几十上百次交道。

> 📌 **伏笔：** 系统调用是用户程序和内核之间**唯一的正规通道**，所以它也是**攻击面**——如果内核处理某个系统调用时有漏洞，恶意程序就可能借此突破限制。第 13 篇会讲 Firecracker 怎么用 **seccomp** 把自己能用的系统调用砍到最少，原因正在于此。

## 八、进程与线程

### 8.1 进程：一个"正在运行的程序"

硬盘上的 `/usr/bin/ls` 只是一个文件。当你运行它，内核会创建一个**进程**，并为它准备：

- 一块属于它的内存空间（存放代码、数据、栈）；
- 打开的文件列表；
- 一个编号（PID）；
- 权限信息（以哪个用户身份运行）；
- 保存寄存器状态的位置（被切换出去时用）。

内核会让多个进程轮流使用 CPU，每次切换时保存旧进程的寄存器、恢复新进程的寄存器。这个过程每秒发生成百上千次，所以看起来所有程序在"同时运行"。

### 8.2 虚拟内存：每个进程都以为自己独占内存

这是操作系统最精妙的设计之一，也是理解虚拟化的重要前提。

每个进程看到的内存地址都是**虚拟地址**。进程 A 的地址 `0x40_0000` 和进程 B 的地址 `0x40_0000` 是两个完全不同的位置。

把虚拟地址翻译成真实物理地址的，是 CPU 里的 **MMU（内存管理单元）**。它查阅一张由内核维护的映射表，叫**页表**。内存按"页"（通常 4 KB）为单位进行映射：

```
进程 A 的虚拟地址 0x40_0000 ──页表A──▶ 物理地址 0x8_1234_0000
进程 B 的虚拟地址 0x40_0000 ──页表B──▶ 物理地址 0x8_5678_0000
```

如果进程 A 访问了一个页表里没有映射的地址，MMU 会报告异常，内核就会发出那个著名的错误：`Segmentation fault`（段错误）。

因为页表只有内核（EL1）能修改，进程根本没办法“看见”别人的内存。这就是进程之间最基本的隔离。

> 📌 **伏笔：** 虚拟机里情况更进一步：Guest 内核也有自己的页表，把 Guest 进程的虚拟地址翻译成它“以为”的物理地址；但这个“物理地址”本身又是假的，还要再经过 Hypervisor 设置的第二套页表，才变成真正的物理地址。ARM64 把这两步叫 **Stage-1** 和 **Stage-2** 翻译，第 3 篇和第 9 篇会细讲。

### 8.3 线程：同一个进程里的多个"执行者"

一个进程里可以有多个**线程**。它们共享同一块内存空间、同一组打开的文件，但每个线程有自己的寄存器状态和栈，可以分别在不同 CPU 核心上同时运行。

用厨房类比：进程是一个独立的小厨房，线程是这个厨房里的几位厨师，共用案板和食材。

> 📌 **伏笔：** 第 7 篇会看到，一台 Firecracker 虚拟机就是宿主机上的**一个进程**，虚拟机的每个 vCPU 就是这个进程里的**一个线程**。

### 8.4 动手：观察你机器上的进程

```bash
# 查看 CPU 架构和核心数
uname -m           # 应输出 aarch64
nproc
lscpu

# 查看内存
free -h

# 查看所有进程
ps aux | head -20

# 查看某个进程的线程（以 systemd 为例，PID 为 1）
ls /proc/1/task

# 查看当前 shell 进程的内存布局（虚拟地址空间）
cat /proc/self/maps

# 查看中断统计：每种中断在每个核心上发生了多少次
cat /proc/interrupts
```

`/proc/self/maps` 列出的每一行都是一段虚拟地址区间以及它映射到了什么（程序代码、动态库、堆、栈……）。`/proc/interrupts` 里应该能看到 `GIC` 字样，那就是第四节提到的 ARM 中断控制器。

## 九、隔离：当很多人共用一台机器

### 9.1 云计算的核心难题

现在想象你是一家云服务商。你有一台 64 核、512 GB 内存的服务器，想把它分给 100 个互不认识的客户同时使用。这些客户里，有的可能写了有 bug 的程序，有的甚至可能是攻击者。

你需要保证：

1. **资源隔离**：一个客户跑满 CPU，不能拖慢其他人；
2. **数据隔离**：一个客户绝对看不到另一个客户的数据；
3. **故障隔离**：一个客户的系统崩了，不影响其他人；
4. **安全隔离**：即使一个客户被攻破或本身就是攻击者，也无法危及其他人和宿主机。

### 9.2 只靠进程隔离，够不够？

从前面学到的知识看，Linux 已经提供了不少隔离：虚拟内存让进程互相看不见；调度器可以限制 CPU 用量；文件权限可以挡住访问。后来又有了**命名空间（namespace）**和 **cgroups**，这正是 Docker 等容器技术的基础（第 2 篇会细讲）。

但有一个根本问题：**所有进程、所有容器共享同一个内核**。

内核是一个数千万行代码的庞大系统，提供几百个系统调用。只要其中任何一个系统调用存在可被利用的漏洞，攻击者就可能从 EL0 提权到 EL1——而一旦拿下了内核，同一台机器上所有客户的数据都暴露无遗。

用厨房类比：你给每位厨师分了独立的工位，贴了“禁止越界”的标签，但大家仍然听命于同一个总管。只要有人骗过或收买了总管，整个后厨就失守了。

### 9.3 更强的隔离：给每个人一个"自己的内核"

一个自然的想法是：**让每个客户拥有独立的内核**。就算攻击者攻破了自己的内核，也只是攻破了一个“假的”电脑，还有一道由硬件（EL2）守护的墙挡在外面。

这就是**虚拟机**的思路。传统虚拟机隔离性很好，但它们笨重——启动要几十秒、每台占用大量内存，很难做到“每个请求一台”。

**Firecracker 要解决的问题就是：能不能让虚拟机像进程一样轻快，同时保持虚拟机级别的隔离？** AWS 用它来运行 Lambda 函数，单台服务器上可以同时运行成千上万个 microVM，每个都在一百多毫秒内启动。

这是怎么做到的？我们一篇一篇来拆解。
