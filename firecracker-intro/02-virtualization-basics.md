## 引子：楚门的世界

电影《楚门的世界》里，主角楚门从出生起就生活在一个巨大的摄影棚里。天空是布景，太阳是灯，邻居是演员。只要导演组把一切安排得足够逼真，楚门就会以为这就是真实世界，照常上班、生活。

虚拟机做的事情一模一样：

- **楚门**是 **Guest 操作系统**，它以为自己独占一台真实电脑；
- **摄影棚**是**虚拟机（VM）**；
- **导演组**是 **Hypervisor / VMM**，它负责搭布景，并在楚门“碰到墙”时及时圆场；
- **摄影棚所在的真实世界**是 **Host（宿主机）**。

本篇要回答的就是：导演组怎么才能把布景搭得足够逼真，又不让楚门发现、更不让楚门逃出去？

## 一、几个名词先对齐

| 术语 | 含义 |
|------|------|
| **Host（宿主机）** | 真实的物理机器，以及跑在上面的真实操作系统 |
| **Guest（客户机）** | 运行在虚拟机里的操作系统及其程序 |
| **虚拟机（VM）** | 提供给 Guest 的一整套“假硬件”环境 |
| **Hypervisor** | 负责创建和运行虚拟机的底层软件，掌握最高控制权 |
| **VMM（Virtual Machine Monitor）** | 常与 Hypervisor 混用；在 KVM 体系里，特指运行在用户态、负责模拟设备和管理虚拟机生命周期的那部分程序（比如 QEMU、Firecracker） |

最后一行请留意：在本系列里，**KVM 是 Hypervisor 的内核部分，Firecracker 是 VMM**。两者分工合作，后面会反复用到这个区分。

## 二、虚拟机要“虚拟”哪些东西？

回想第 01 篇讲的电脑四大件，虚拟机必须把它们都提供给 Guest：

1. **CPU**：Guest 要能执行指令，包括内核才能执行的特权指令；
2. **内存**：Guest 要看到一段从 0 开始（或从某个固定地址开始）的“物理内存”；
3. **设备**：Guest 要有硬盘、网卡、串口、时钟、中断控制器；
4. **启动环境**：Guest 要能被“开机”——真实电脑上这由 BIOS/UEFI 固件完成。

其中 **CPU 和内存**的虚拟化，追求的是“接近原生速度”；**设备**的虚拟化，追求的是“够用、高效、安全”。这两块用的是完全不同的技术，Firecracker 的设计哲学也主要体现在对设备的取舍上。

## 三、核心难题：Guest 内核也想当老大

### 3.1 问题在哪

第 01 篇说过，内核运行在高特权级（ARM64 的 EL1），它会做这些事：

- 修改页表，决定内存怎么映射；
- 屏蔽或开启中断；
- 读写设备地址；
- 配置 CPU 的各种系统寄存器。

现在问题来了：Guest 里也有一个完整的 Linux 内核，它也想做这些事。但真正的物理机只有一套页表机制、一个中断控制器、一组设备。如果 Guest 内核真的去改了物理机的页表，Host 和其他虚拟机就全乱套了。

所以必须有一种机制：**Guest 内核执行这些“敏感操作”时，不能真正生效，而要被拦下来，交给 Hypervisor 代为处理**，处理完再假装“操作成功了”还给 Guest。

这个思路叫 **陷入-模拟（Trap-and-Emulate）**：

```
Guest 内核执行敏感指令
        │
        ▼  （CPU 发现这是敏感操作，触发陷入）
Hypervisor 接管
        │  检查 Guest 想干什么
        │  在“假硬件”上模拟出效果
        ▼
返回 Guest，继续执行下一条指令
```

### 3.2 一个经典理论

1974 年，Popek 和 Goldberg 提出了一个判断条件，大意是：**如果一种 CPU 架构里所有“敏感指令”都是“特权指令”**（在低权限下执行就会触发陷入），那么就可以高效地用陷入-模拟实现虚拟化。

麻烦在于，早期的 x86 不满足这个条件：它有一些敏感指令在低权限下执行时**不会陷入**，而是悄悄地做了别的事情。Hypervisor 根本拦不住它们。这逼出了各种“绕路”的技术，也就是下面要讲的三条路线。

## 四、三条技术路线

### 4.1 路线一：纯软件模拟

最直接的办法：**不让 Guest 的指令直接在 CPU 上跑**，而是由一个程序逐条读出 Guest 的指令，用软件模拟它的效果。

一个极简的“CPU 模拟器”伪代码：

```python
regs = [0] * 31     # 模拟的 31 个通用寄存器
pc = 0x4008_0000    # 模拟的程序计数器
memory = bytearray(256 * 1024 * 1024)  # 模拟的 256MB 内存

while True:
    insn = read_u32(memory, pc)       # 取指
    op, args = decode(insn)           # 译码
    if op == "ADD":
        regs[args.d] = regs[args.n] + regs[args.m]
    elif op == "STR" and is_device_addr(args.addr):
        emulate_device_write(args.addr, regs[args.t])   # 模拟 MMIO
    # ……成百上千种指令
    pc += 4
```

因为每条指令都经过模拟器之手，Guest 想干什么都逃不过它的眼睛，敏感指令的问题自然消失了。

**优点：** 什么都能模拟，甚至可以在 ARM64 上跑 x86 的系统（QEMU 的 TCG 模式就是这么做的，它还会把 Guest 指令块翻译成宿主指令并缓存，叫**动态二进制翻译**）。

**缺点：** 慢。一条 Guest 指令要变成很多条宿主指令。

### 4.2 路线二：半虚拟化（Paravirtualization）

既然 Guest 的敏感指令难以拦截，那干脆**修改 Guest 内核**：让它别执行那些敏感指令，而是主动调用 Hypervisor 提供的接口。这种接口叫 **Hypercall**，就像第 01 篇里的系统调用，只不过是 Guest 内核向 Hypervisor 递申请单。

Xen 早期就采用这种方式，性能很好，但需要修改 Guest 内核——Windows 这种闭源系统就没法改。

半虚拟化的思想并没有消失。在**设备**层面，它以 **virtio** 的形式成为了今天的主流，Firecracker 的设备全部基于它（第五节会讲）。

### 4.3 路线三：硬件辅助虚拟化（今天的主流）

既然问题出在 CPU 本身，那就让 CPU 厂商在硬件上解决：

- Intel 在 2005 年前后推出 **VT-x**；
- AMD 随后推出 **AMD-V**；
- ARM 在 ARMv7 上推出虚拟化扩展，ARMv8（即 ARM64）在架构中定义了 **EL2**。

核心思想都一样：**给 CPU 增加一个专门给 Hypervisor 用的特权层，并让 Hypervisor 可以精确配置“Guest 做哪些事情时要陷入”**。

以 ARM64 为例：

```
EL0   Guest 应用程序                  Host 应用程序（含 Firecracker 进程）
EL1   Guest 内核                      ─
EL2   ──────────── Hypervisor（KVM）────────────
```

Guest 内核真的运行在 EL1，绝大多数指令直接在 CPU 上全速执行。但 Hypervisor 在 EL2 设置好了“陷阱”：Guest 访问某些系统寄存器、访问没有映射的内存地址（比如设备的 MMIO 地址）、执行某些特定指令时，CPU 会自动陷入 EL2，由 Hypervisor 处理。

内存方面，硬件还提供了**第二阶段地址翻译**（ARM64 叫 Stage-2，Intel 叫 EPT，AMD 叫 NPT）：Guest 自己维护的页表只能把地址翻译到“Guest 物理地址”，硬件会自动再查一张由 Hypervisor 管理的表，翻译成真实物理地址。Guest 随便改自己的页表，都逃不出 Hypervisor 划定的范围。

> 📌 第 3 篇会详细展开 EL2、VHE 和 Stage-2 翻译，现在只需要记住：**硬件辅助虚拟化让 Guest 的 CPU 指令和内存访问几乎以原生速度运行，只有少数敏感操作才需要 Hypervisor 介入。**

### 4.4 三条路线对比

| 路线 | Guest 是否需修改 | CPU 性能 | 代表 |
|------|----------------|---------|------|
| 纯软件模拟 | 否 | 慢（数倍到数十倍开销） | QEMU TCG、Bochs |
| 半虚拟化 | 是（内核需改） | 快 | 早期 Xen |
| 硬件辅助 | 否 | 接近原生 | KVM、Hyper-V、ESXi、现代 Xen |

Firecracker 依赖 KVM，因此走的是**硬件辅助**路线。它**不支持纯软件模拟**——宿主机上没有 `/dev/kvm`，Firecracker 就无法运行。

## 五、设备怎么虚拟化

CPU 和内存有硬件帮忙，设备就没那么幸运了。网卡、硬盘千差万别，硬件不可能替你模拟每一种设备，这部分工作主要由 VMM 完成。常见有三种方式。

### 5.1 完全模拟：照着真实硬件演

VMM 用软件完整模拟一款**真实存在**的硬件，比如 Intel 的 e1000 网卡。Guest 里使用现成的 e1000 驱动，完全不知道这是假的。

问题在于：真实硬件的寄存器接口是为物理电路设计的，驱动程序往往要读写很多次寄存器才能完成一次收发包。每次读写都是一次 MMIO 陷入，一次陷入就要在 Guest 和 Hypervisor 之间来回切换。**频繁陷入 = 性能差**。

而且，为了模拟真实硬件的所有细节，VMM 的代码会非常庞大。代码越多，漏洞越多。历史上 QEMU 的软驱控制器模拟代码就曾爆出过让 Guest 逃逸到宿主机的严重漏洞（2015 年的 VENOM 漏洞）——一个现代服务器根本用不着的软驱，却成了攻击入口。

### 5.2 virtio：为虚拟机量身定做的“假硬件”

既然 Guest 早晚要装驱动，何必非要模拟真实硬件？不如**专门为虚拟环境设计一套简洁高效的设备接口**，让 Guest 装上配套驱动。这就是 **virtio**，一种半虚拟化的设备标准。

virtio 的核心是**共享内存里的环形队列（virtqueue）**：

```
Guest 驱动                                      VMM（如 Firecracker）
   │  1. 把要发送的数据放进共享内存                  │
   │  2. 在队列里登记“第 N 个缓冲区准备好了”          │
   │  3. 写一次通知寄存器（一次陷入）  ──────────────▶ │
   │                                              │  4. 批量取出队列里的请求处理
   │  ◀────────────────── 6. 注入一个中断           │  5. 在队列里登记“处理完了”
   │  7. 读取结果                                    │
```

关键在于**批量**：Guest 可以一次在队列里放好几十个请求，只通知一次。陷入次数大大减少，性能接近原生；同时设备接口极其简单，VMM 的实现代码也少得多。

Linux 内核早已内置 virtio 驱动，所以 Guest 不需要额外安装任何东西。

### 5.3 设备直通：把真硬件交给 Guest

直接把一块物理网卡或 GPU 交给某个 Guest 独占（Linux 上通过 VFIO 实现，网卡还可以借助 SR-IOV 把一块卡切成多个“虚拟功能”分给多个 Guest）。性能最好，但设备不能共享，虚拟机也难以迁移和快照。

### 5.4 Firecracker 的选择

Firecracker 的设备几乎全是 **virtio**（块设备、网络、vsock、balloon、熵源等），默认通过 **virtio-mmio** 方式呈现给 Guest（v1.13 起也可以选择 PCI 方式，第 10 篇会对比）；除此之外只模拟了串口等极少数必需的简单设备。没有显卡、没有 USB、没有声卡、没有软驱。

**少即是多**：设备越少，代码越少，攻击面越小，启动越快。这是 Firecracker 设计哲学的核心，第 4 篇和第 10 篇会细讲。

## 六、Type 1 与 Type 2 Hypervisor

传统上，Hypervisor 被分为两类：

**Type 1（裸金属型）**：Hypervisor 直接运行在硬件上，本身就是一个精简的“操作系统”。
- 代表：VMware ESXi、Xen、Microsoft Hyper-V

**Type 2（宿主型）**：先装一个普通操作系统，Hypervisor 作为其上的一个程序运行。
- 代表：VirtualBox、VMware Workstation、Parallels Desktop

```
   Type 1                           Type 2
┌─────┬─────┐                  ┌─────┬─────┐
│ VM1 │ VM2 │                  │ VM1 │ VM2 │
├─────┴─────┤                  ├─────┴─────┤
│ Hypervisor│                  │ Hypervisor│ 普通应用
├───────────┤                  ├───────────┴──────┐
│   硬件     │                  │   宿主操作系统      │
└───────────┘                  ├──────────────────┤
                               │      硬件         │
                               └──────────────────┘
```

### KVM 属于哪一类？

**KVM（Kernel-based Virtual Machine）** 是 Linux 内核里的一个模块，2007 年随 Linux 2.6.20 合入主线，后来又支持了 ARM 和 ARM64。加载 KVM 之后，Linux 内核本身就具备了 Hypervisor 的能力，直接管理硬件虚拟化特性。

所以 KVM 一般被视为 **Type 1**——Linux 内核本身就是那个“裸金属上的 Hypervisor”。不过它看起来又像 Type 2，因为宿主机上照样运行着普通的 Linux 程序。这种分类在今天已经没那么泾渭分明了，理解它的实际结构更重要：

```
┌───────────────────────┐   ┌───────────────────────┐
│ Guest 应用 (EL0)       │   │ Guest 应用 (EL0)       │
│ Guest 内核 (EL1)       │   │ Guest 内核 (EL1)       │
├───────────────────────┤   ├───────────────────────┤
│ Firecracker 进程（VMM） │   │ Firecracker 进程（VMM） │   ← 宿主机用户态
└───────────┬───────────┘   └───────────┬───────────┘
            │  ioctl(/dev/kvm)          │
┌───────────┴───────────────────────────┴───────────┐
│        Linux 内核 + KVM 模块（Hypervisor）           │   ← 宿主机内核，EL2
├───────────────────────────────────────────────────┤
│                    ARM64 硬件                       │
└───────────────────────────────────────────────────┘
```

**KVM 负责：** CPU 虚拟化（让 vCPU 在硬件上运行、处理陷入）、内存虚拟化（Stage-2 页表）、中断控制器虚拟化。

**用户态 VMM 负责：** 决定虚拟机有多少内存和 vCPU、把内核加载进内存、模拟设备、处理网络和磁盘 I/O、提供管理接口。

KVM 只提供“发动机”，车身、座椅、方向盘由 VMM 来造。同一台 KVM 发动机，可以装进不同风格的车：

| VMM | 风格 |
|-----|------|
| **QEMU** | 功能大而全，能模拟海量设备和多种架构 |
| **Firecracker** | 极简、专注 serverless 和多租户隔离 |
| **Cloud Hypervisor** | 面向现代云工作负载，功能比 Firecracker 稍多 |
| **crosvm** | Google 为 ChromeOS 开发，Firecracker 早期即基于它的代码起步 |

## 七、容器：另一种隔离思路

### 7.1 容器不是虚拟机

容器（Docker、Podman、containerd 等）里没有 Guest 内核，**所有容器和宿主机共享同一个 Linux 内核**。

容器只是被内核“特殊对待”的普通进程。内核用两类机制给它们制造隔离的假象：

- **Namespace（命名空间）**：控制进程“能看到什么”。比如 PID 命名空间让容器里的进程以为自己是 1 号进程；网络命名空间让容器拥有独立的网卡和路由表；挂载命名空间让它看到独立的文件系统树。
- **cgroups（控制组）**：控制进程“能用多少”，比如最多用 2 个 CPU 核、512 MB 内存。

### 7.2 动手：不用 Docker，手工造一个“容器”

```bash
# 1. 创建新的 PID 和挂载命名空间，并在其中启动一个 shell
sudo unshare --pid --fork --mount-proc --uts bash

# 2. 在这个新 shell 里：
ps aux
# 你会发现只能看到寥寥几个进程，bash 自己是 1 号进程

hostname my-container
hostname
# 主机名改成了 my-container

# 3. 再看内核版本
uname -r
```

现在**另开一个终端**（不在 unshare 里）执行：

```bash
hostname     # 宿主机主机名没有变，说明 UTS 命名空间隔离生效
uname -r     # 和“容器”里输出的完全一样！
```

最后这一步揭示了容器的本质：**无论隔离得多好，大家用的都是同一个内核**。在“容器”里输入 `exit` 退出。

你也可以看看 cgroups 的样子：

```bash
cat /sys/fs/cgroup/cgroup.controllers
# 典型输出：cpuset cpu io memory hugetlb pids ……
```

### 7.3 容器隔离的软肋

第 01 篇说过，共享内核意味着：只要内核有一个可以被利用的漏洞，容器里的攻击者就可能突破隔离，接管整台宿主机。

Linux 内核提供几百个系统调用，代码规模数千万行，每年都会发现不少安全漏洞。对于“自己的团队部署自己的服务”，容器的隔离通常够用；但对于“运行互不相识的陌生人的代码”——比如 AWS Lambda、在线代码沙箱、AI Agent 执行环境——仅靠容器就让人睡不着觉了。

### 7.4 中间路线：gVisor

Google 的 gVisor 走了一条折中路线：在用户态实现一个“迷你内核”，拦截容器的系统调用，自己处理大部分，只把少量安全的调用转交宿主内核。这样减少了宿主内核暴露的攻击面，但系统调用兼容性和性能会有一定代价。

## 八、把所有路线放在一起看

| | 传统虚拟机（如 QEMU+KVM 全功能） | 容器 | microVM（Firecracker） |
|--|--|--|--|
| 隔离边界 | 硬件虚拟化（EL2） | 共享内核，靠 namespace/cgroups | 硬件虚拟化（EL2） |
| 是否有独立内核 | 是 | 否 | 是 |
| 启动时间 | 秒级到数十秒 | 毫秒级到亚秒级 | 约百毫秒级 |
| 每实例额外内存开销 | 较大（数百 MB 常见） | 很小 | 很小（VMM 自身仅数 MB） |
| 设备模型 | 丰富（显卡、USB 等） | 不需要 | 极简（virtio 为主） |
| 可运行任意操作系统 | 是 | 否，只能是 Linux 程序 | 主要是 Linux |
| 适合场景 | 通用服务器虚拟化、桌面虚拟化 | 微服务、CI、开发环境 | Serverless、多租户沙箱、代码执行 |

> 表中的时间和内存数字是典型数量级，实际值取决于配置，第 16 篇会教你自己测量。

你可以看到，microVM 试图拿到两边的优点：**虚拟机级别的隔离 + 接近容器的轻量和速度**。代价是放弃“通用性”——Firecracker 跑不了 Windows，不能接显卡，也不打算做这些。

## 九、动手：检查你的机器能不能跑 Firecracker

Firecracker 的前提是宿主机有可用的 KVM。在你的 ARM64 机器上执行：

```bash
# 1. 确认架构
uname -m
# aarch64

# 2. 检查 KVM 设备文件是否存在
ls -l /dev/kvm
# 正常时类似：crw-rw---- 1 root kvm 10, 232 ... /dev/kvm

# 3. 查看内核日志中 KVM 的初始化信息
sudo dmesg | grep -i kvm
# 正常时会看到类似 "kvm [1]: Hyp mode initialized successfully"
# 或者带 "VHE" 字样的初始化信息

# 4. 检查当前用户能否读写 /dev/kvm
[ -r /dev/kvm ] && [ -w /dev/kvm ] && echo "KVM 可用" || echo "无权限"
```

如果最后一步显示“无权限”，可以把当前用户加入 `kvm` 组（发行版不同，组名可能不同），然后重新登录：

```bash
sudo usermod -aG kvm $USER
```

如果 `/dev/kvm` 根本不存在：

- 物理机：检查固件是否从 EL2 启动内核（大多数 ARM64 服务器默认如此），以及内核是否编译了 KVM；
- 云主机：很多云厂商的普通虚拟机实例不提供嵌套虚拟化，需要使用裸金属（bare metal）实例。

第 05 篇我们会真正在这台机器上启动第一台 microVM，到时候这些检查都必须通过。

## 小结

| 概念 | 一句话解释 |
|------|-----------|
| Host / Guest | 真实机器 / 虚拟机里的系统 |
| Hypervisor / VMM | 掌控虚拟机的底层软件 / KVM 体系中负责设备和管理的用户态程序 |
| 陷入-模拟 | Guest 做敏感操作时被拦下，由 Hypervisor 代为模拟 |
| 硬件辅助虚拟化 | CPU 提供专用特权层（ARM64 的 EL2）和 Stage-2 翻译，让 Guest 接近原生运行 |
| virtio | 专为虚拟机设计的高效设备接口，靠共享环形队列批量传输 |
| KVM | Linux 内核中的 Hypervisor 模块，提供 CPU、内存、中断虚拟化 |
| 容器 | 共享宿主内核的隔离进程，靠 namespace 和 cgroups |
| microVM | 保留硬件虚拟化隔离，砍掉不必要设备的轻量虚拟机 |
