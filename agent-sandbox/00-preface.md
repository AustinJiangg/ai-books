# 前言

## 为什么写这本书

几年前，"沙箱"在大模型产品里还只是一个功能部件：用户上传一个文件，模型写一段代码，在一个用完即弃的容器里跑完，结果回到对话框。到 2026 年，这个词指的东西已经完全不同了。一家实验室训练编码 Agent，一个作业就可能请求上万个沙箱，每个都要在几秒内就位，存活几十分钟到几小时，还随时可能因为 GPU 作业被抢占而暂停。DeepSeek 在 DSec 论文中披露，它的单个规模单元跨越近 160 个 CPU 节点、3 万个核、约 250 TB DRAM，管理着 PB 量级的层与镜像；典型的一天里服务约 300 万个沙箱，峰值并发约 38 万（摘要称超过 380,000），创建速率超过每秒 5,000 个（DSec §2.4、摘要；论文自述）。Kimi K3 把"带持久化 rollout 状态与沙箱状态的百万 token Agent RL"写进了技术报告的摘要（Kimi K3 技术报告摘要；论文自述）。

这些数字让我确信：在 AI 实验室里，沙箱已不再是挂在推理服务旁边的小组件，而是要和 GPU 集群、分布式存储放在同一张规划表上的基础设施。它有自己的控制面、自己的存储系统、自己的密度与成本模型，也有自己的事故史。可是就我所见，直到 2026 年秋天，还没有一本书系统地讲它。相关知识散落在几类地方：系统论文讲机制，厂商文档讲接口和价格，实验室博客讲事故复盘，安全社区讲提示注入和逃逸，标准机构讲治理原则。每一类材料都只照亮一角，彼此之间的术语、口径和数字常常对不上。

过去没有人做这件事，部分原因是材料不够。2025 年之前，关于 Agent 训练沙箱的公开信息几乎只有几句话：某某报告说"支持超过一万个并发沙箱实例"，某某博客说"需要在云端运行数十万个并发的沙箱化编码环境"。这样的句子可以引用，却没法分析：它们不说明负载的样子、瓶颈的位置，也不说明失败时发生了什么。

2026 年情况变了。7 月，AgentENV 以 MIT 许可在 kvcache-ai 组织下开源，成为机制最透明的开源 Agent 沙箱之一；9 月，DSec 论文给出了一套生产系统从负载刻画、控制面、存储、密度、网络到 RL 框架集成的全部主要设计，还附有一份训练期"模型攻击沙箱"的现场记录。几乎同一时期，几家国内模型公司的技术报告开始写失败率、构建成功率与磁盘压力，海外实验室公开了多份产品沙箱设计与事故复盘，OSDI、SOSP、ICML 等会议也陆续出现了相关工作。有了这些一手披露，第一次有可能把"Agent 沙箱"当作一个完整的系统领域来整理：先刻画负载，再拆解架构，再分场景讨论取舍，最后指出哪些问题还没有答案。这本书就是这样一次整理的结果。

## 本书的立场

**工业实践为主，安全为辅线。** 本书首先是一本系统书。它关心的问题是：几十万个有状态沙箱怎样拉起、暂停、回收；镜像和快照放在哪里；rollout（一次策略与环境交互直至结束的完整采样过程，也称轨迹展开）进行到一半时，状态归谁；产品沙箱怎样计费和休眠。全书的骨架是"三场景 × 八层架构"：训练、评测、产品推理三种场景，在接入与 API、控制面、节点运行时、镜像与存储、状态管理、密度与资源、网络与出站、RL 集成与完整性八个层次上分别作何取舍。安全是贯穿其中的一条辅线，用"两类对手"来组织：被利用的代理人，以及作为对手的模型。我没有把安全写成独立的一部分，因为在 Agent 沙箱里，安全问题几乎总是落在某一层的工程决策上：凭据放在哪里，出站规则由谁改写，包代理能不能写，.git 历史有没有清理干净。

**只写有出处的事实。** 本书讨论的大部分系统是 2026 年才公开的，材料以预印本、厂商文档和事故复盘为主。在这样的领域里，最容易犯的错误是把一句营销话术、一条媒体转述或一个记错的数字当作事实写下，再被别人继续引用。所以本书定了一条硬规矩：每个关键数字首次出现时，都写明出处和来源类型——论文自述、一手文档、厂商自报、二手报道、二手引述，或者笔者推算。"论文自述"和"厂商自报"不等于事实，它们只说明这句话是谁说的。

**冲突并列，不替读者二选一。** 来源互相矛盾时，我把各方说法连同来源与日期一起并列，并在附录 B 的"冲突数字登记"里给出判断与建议措辞。例如 AgentENV 的内存超售比，K3 报告称最高 6.5 倍，项目 README 称生产中 9.6 倍，两者归因的机制也不同（附录 B C-01）。我可以告诉读者两个数字各自的口径，但不应假装知道哪一个"才是真的"。

**"未披露"是结论。** 本书有大量表格的格子写着"未披露（已查：……）"。这不是偷懒，也不是遗憾，而是本书最想交给读者的结论之一：在本书检索范围内，这件事没有公开来源。哪些实验室公开训练侧、哪些只公开产品侧，哪些关键参数论文没有给出，这些空白本身就是这个领域现状的一部分。我宁可留一个空格，也不用推测去填它。凡是我从已引事实推出、原文没有明说的结论，都标"（推断）"；凡是我提出的设计、测量方法和规格字段，都标"本书建议"，与"某系统已经这样做"严格区分。

## 本书的方法

**数字溯源。** 每一章末尾都有一张"本章数字溯源"表，列出数字、含义、来源及原文位置、来源类型，以及对应的附录 B 编号。附录 B 按章分区汇总全书的数字，是全书数字的最终依据；正文与附录 B 不一致时，以附录 B 为准。附录 B 还专门列出"不应引用的数字"：那些流传较广、但已被一手来源纠正的说法，比如把 K2.5 的"10 万个并发任务"误读成"10 万个并发沙箱"（X-09）。

**独立核对。** 全书每个数字都回到原文核对过，每一章都有一份独立的核对记录：逐条对照原文的节号、表号、措辞和限定词，"约""超过""峰值""up to"照原文保留，不省略，也不加强。核对中发现的跨章不一致，统一在附录 B 中更正后再回写正文。第 1 章 1.5.2 节列出了几条按附录 B 统一更正的常见说法，例如 DSec 论文署名作者 131 人（C-03a）、E2B 自 2026 年 7 月起支持 fork（B16-12）。

**披露矩阵。** 对于厂商与实验室，本书不写"某公司很强"或"某公司落后"，而是用披露矩阵逐格记录：负载、隔离档位、存储、出站、RL 集成等维度上，每一格要么写"事实 + 出处"，要么写"未披露（已查：……）"（见第 26、27 章）。这种写法让两件事可以比较：各家做了什么，各家说了什么。它也让结论可以检验：任何一格，读者都能顺着出处回到原文。

**统一的体例。** 术语、译名、数字格式、来源类型与交叉引用的约定写在《凡例》和附录 A 开头的"用词规范"里。例如"沙箱"与"环境"是两种计数单位，不互换；"运行时"必须写明是沙箱运行时还是沙箱内运行时。这些约定看似琐碎，但在口径混乱的领域里，它们决定了一个数字能否被正确读懂。

## 本书的时效

本书的材料截至 2026 年 10 月初。网页来源在括注中注明读取日期，仓库材料注明提交号与日期，附录 C 中的"文档未见（10-05）"指截至 2026-10-05 本书读过的一手材料中没有相关接口或说明。

这个领域变化很快。仅在 2026 年夏天，E2B 就在 7 月加入了 fork；SandboxEscapeBench 在 8 月发布的 v3 中改用每样本 1 亿 token 的预算重测，基准被 Claude Mythos Preview 饱和，原先"难度 4–5 为 0"的结论只适用于旧预算（B20-22）；中国已立项的强制性国标《智能体应用安全基本要求》草案仍未公开（B23-13）。可以预料，本书出版之后，产品接口、价格和规模数字会继续变化。全书最容易过期的是两个附录：附录 B 中的厂商规模与价格数字，以及附录 C 的 API 对照。附录 C 是 2026 年 10 月初的切片，引用时请以所注的提交号与读取日期为准，并回到当前文档核对。

相对不容易过期的，是本书的框架与方法：负载五特征（突发、稀疏、有状态、低扇出、可中断）、三场景的取舍、八层架构、两类对手，以及"沙箱内的状态可以回滚，沙箱外的副作用必须事务化或者禁止"这一判断。即使具体系统更替，我希望这些框架仍能帮助读者读懂新的论文和新的产品文档，并知道该向一份新的披露提出哪些问题。附录 D 的负载刻画模板就是为此准备的。

本书一定有错误和疏漏，欢迎在本仓库提交 issue 指正。
