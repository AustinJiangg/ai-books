# 第 3 篇｜存储基础（二）：块设备与 NBD

> **本篇目标**：上一篇说一个文件可以当成硬盘用。本篇再往前走一步：一块“硬盘”的内容，能不能干脆由一个程序**实时回答**？答案是能，这就是 NBD（Network Block Device）。读完本篇，你会知道块设备是什么、NBD 一次读写是怎么往返的、为什么 E2B 一定要用它，以及这套环境为什么要自己编译 nbd 内核模块、把上限设成 512。

---

## 一、块设备：内核眼中的“硬盘”

### 1.1 `/dev` 下面的那些名字

在 Linux 上执行 `lsblk`，会看到类似这样的输出：

```
$ lsblk
NAME        MAJ:MIN RM   SIZE RO TYPE MOUNTPOINT
nvme0n1     259:0    0   3.5T  0 disk
├─nvme0n1p1 259:1    0   600M  0 part /boot/efi
└─nvme0n1p2 259:2    0   3.5T  0 part /
nbd0         43:0    0     0B  0 disk
nbd1         43:32   0     0B  0 disk
...
```

每一行是一个**块设备**（block device）。它是内核提供的一种抽象：不管背后是 NVMe 固态盘、机械硬盘，还是别的什么，对上层来说都一样，就是一排可以按编号读写的块。

- `nvme0n1` 是一块真实的固态盘，`nvme0n1p1`、`nvme0n1p2` 是它上面的分区；
- `nbd0`、`nbd1` 是 NBD 设备，此刻大小为 0，表示还没“接上”任何东西。

### 1.2 块设备层

程序读写块设备时，请求经过内核里的**块设备层**：

```
  程序：read(/dev/xxx, 第 100 块)
         │
         ▼
  文件系统（如果设备被挂载了）
         │
         ▼
  块设备层：排队、合并相邻请求、调度
         │
         ▼
  驱动程序：NVMe 驱动 / SCSI 驱动 / NBD 驱动 / ……
         │
         ▼
  真正干活的东西：固态盘 / 硬盘 / 一个用户态程序
```

关键在最后一层：**驱动决定了“块”的数据从哪来**。NVMe 驱动去问固态盘；而 NBD 驱动去问一个程序。

## 二、用户态也能“造”一块盘

### 2.1 loop 设备：把文件当盘

最简单的办法是 **loop 设备**：

```
$ losetup /dev/loop0 rootfs.ext4
$ mount /dev/loop0 /mnt
```

内核把对 `/dev/loop0` 第 N 块的读写，翻译成对 `rootfs.ext4` 文件第 N×4096 字节处的读写。这就把上一篇说的“镜像文件”变成了一块真正的块设备。

loop 设备的局限是：数据**必须**在一个本地文件里，而且内核直接读写这个文件，中间没有插手的机会。

### 2.2 NBD：盘的内容由程序回答

**NBD**（Network Block Device，网络块设备）更灵活。名字里有“网络”，因为它最初是为了把远方机器上的盘挂到本机用。但它的本质是：

> 对 `/dev/nbdN` 的每一次读写，内核都把它变成一个**请求消息**，通过一个 socket 发给某个程序；程序回一个**应答消息**，内核再把结果交给读写的人。

用一个比喻：NBD 设备是一部“假硬盘”，背后坐着一位**接线员**。每当有人要读第 N 块，接线员就去查资料，把内容念回来；有人要写第 N 块，接线员就把内容记在自己的本子上，然后说“写好了”。至于接线员是去本地文件里查、去远方服务器上查，还是去好几本资料里拼起来，读写的人完全不知道，也不需要知道。

## 三、NBD 协议的骨架

### 3.1 请求和应答

NBD 的消息格式很简单。E2B 的代码里是这样定义的（简化）：

```go
// 请求：内核 → 程序
type Request struct {
    Magic  uint32  // 固定值 0x25609513，用来校验
    Type   uint32  // 0=读 1=写 2=断开 3=刷盘 4=丢弃
    Handle uint64  // 请求编号，应答时原样带回
    From   uint64  // 从第几个字节开始
    Length uint32  // 读写多少字节
}

// 应答：程序 → 内核
type Response struct {
    Magic  uint32  // 固定值 0x67446698
    Error  uint32  // 0 表示成功
    Handle uint64  // 对应哪个请求
}
```

写请求后面紧跟着要写的数据；读应答后面紧跟着读出的数据。

### 3.2 一次读的往返

```
 客户机里的程序要读第 100 块
           │
           ▼
 内核 NBD 驱动 ──── 请求{读, 编号=7, From=409600, Length=4096} ───▶ socket
                                                                     │
                                                                     ▼
                                                        用户态程序（接线员）
                                                        查资料，找到这 4 KiB
                                                                     │
 内核 NBD 驱动 ◀─── 应答{成功, 编号=7} + 4096 字节数据 ─────────────── socket
           │
           ▼
 把数据交给读的人
```

几个细节：

- **编号（Handle）**：内核可以同时发出很多请求，不必等前一个回来。程序可以乱序应答，靠编号对上号。
- **刷盘（Flush）**：要求程序保证“之前写的都真正存好了”。打快照前会用到（第 14 篇）。
- **断开（Disconnect）**：设备不用了，通知程序收工。

### 3.3 socket 不一定是网络

“网络块设备”里的 socket 可以是真正的 TCP 连接，也可以是同一台机器上两个端点直接相连的 **unix socket 对**（socketpair）。E2B 用的是后者：orchestrator 自己建一对 socket，一头交给内核的 NBD 驱动，另一头自己拿着读请求、写应答。数据完全不出本机，没有任何网络开销。

一台 NBD 设备还可以同时接**多条**这样的连接，内核把请求分散到各条连接上并行处理，提高吞吐。

### 3.4 怎么把 socket 交给内核

老办法是用 `ioctl` 系统调用一项项设置；新办法是通过 **netlink**（内核和用户态之间的一种通信通道）一次性告诉内核：“把这几条 socket 接到 nbd5 上，块大小 4096，总大小 5 GiB，超时多少秒。”E2B 用的是 netlink 方式。接好之后，`/dev/nbd5` 的大小就从 0 变成了 5 GiB。

## 四、为什么 E2B 一定要用 NBD

回到 E2B 的需求。一个沙箱的根盘，内容来自哪里？

- 大部分块来自**模板**，而模板可能由好几代 diff 拼成（第 7 篇），数据散在好几个文件里；
- 这些文件还不一定在本地，可能要按需从存储后端拉（第 11 篇）；
- 沙箱自己写过的块，要记到沙箱**自己的**写时复制文件里，不能动模板（第 12 篇）。

也就是说，“第 N 块的内容是什么”不是一个固定的文件能回答的，需要**在读的那一刻**去查：

```
读第 N 块：
  沙箱自己写过吗？ ── 是 ──▶ 从沙箱的写时复制文件读
        │否
        ▼
  查模板的映射表：第 N 块在哪一代 diff 的哪个位置？
        │
        ▼
  那一段数据拉到本地了吗？ ── 否 ──▶ 先从存储后端拉下来
        │是
        ▼
  从本地缓存读出来
```

写的时候则一律写进沙箱自己的文件。

loop 设备做不到这些，因为它只会照着一个文件读写。NBD 正好合适：E2B 让 orchestrator 当“接线员”，把上面这套逻辑写在程序里。第 12 篇会详细讲这个接线员。

> **为什么不直接把文件交给 Firecracker**？Firecracker 的根盘只认一个宿主上的路径，读写时直接操作这个路径。它不知道什么模板、什么 diff。把路径指向 `/dev/nbdN`，Firecracker 照常读写，背后的复杂逻辑全由 NBD 接走。

## 五、NBD 设备是有限的

### 5.1 `nbds_max`

NBD 设备不是想要多少就有多少。内核的 nbd 模块在加载时有一个参数 `nbds_max`，决定创建多少个 `/dev/nbdN`。发行版自带的模块默认只有 16 个。

在 E2B 里，**每个运行中的沙箱占一台 NBD 设备**。所以 `nbds_max` 直接决定了一台机器上**最多同时跑多少个沙箱**。

### 5.2 这套环境的做法

这套环境用的是**自己编译的 nbd 模块**，加载参数 `nbds_max=512`，并且一次性固化到系统里，开机自动加载：

```bash
# 开机加载 nbd 模块
echo nbd > /etc/modules-load.d/nbd.conf
# 加载时带上参数
echo "options nbd nbds_max=512" > /etc/modprobe.d/nbd.conf
```

部署脚本 `build.sh -s` **不会**替你加载这个模块，这是部署前的手工准备步骤。如果没做，orchestrator 启动时去读 `/sys/module/nbd/parameters/nbds_max`，读不到就报 `NBD module not loaded`，直接起不来。

有一个容易踩的坑：**升级内核**之后，新内核目录里放的是发行版原版的 `nbd.ko`。它照样开机加载，`nbds_max` 也照样是 512（参数文件还在），从设备数上看不出任何异常，但用的已经不是自己编译的那个模块了。所以升级内核后要重新放一次自编译模块。

### 5.3 怎么判断一台 NBD 设备有没有人用

内核在 `/sys/block/nbdN/` 下为每台设备暴露一些文件。E2B 判断“这台设备空闲”的依据是两条：

- `/sys/block/nbdN/pid` **不存在**：说明没有程序接着它；
- `/sys/block/nbdN/size` 是 **0**：说明它没有被设成任何大小。

两条都满足，才认为可以拿来用。第 12 篇会讲 orchestrator 怎么管理这 512 台设备组成的“设备池”。

## 六、udev 与 NBD：一个部署细节

Linux 上有一个叫 **udev** 的守护进程，负责在设备出现、变化时做些事情，比如创建 `/dev` 下的文件、通知桌面环境“插入了新磁盘”。

udev 默认会**监视**块设备：设备一被关闭，它就去重新读一遍设备内容，看看分区表变没变。对普通硬盘来说这没什么；但对 NBD 来说，每次“重新读一遍”都变成发给 orchestrator 的一串读请求，而且沙箱启停非常频繁，这是纯粹的浪费，还可能和 orchestrator 的操作撞车。

所以部署脚本写了一条 udev 规则，关掉对 NBD 设备的监视：

```
# /etc/udev/rules.d/97-nbd-device.rules
ACTION=="add|change", KERNEL=="nbd*", OPTIONS:="nowatch"
```

写完规则后要让 udev 对已有设备重新应用一次。脚本特意**只对 nbd 设备**触发：

```bash
udevadm trigger --action=change --subsystem-match=block --sysname-match='nbd*'
```

为什么不直接 `udevadm trigger`？因为不带参数会给全机**每一个**设备都发一次事件。在一台有几百个 CPU、上千个内存块、512 个 nbd 设备，再加上别人的容器网卡的大机器上，udev 和 systemd 会被这波事件占住好几分钟，部署看起来就像卡死了一样。

## 七、读懂几条命令

```
$ cat /sys/module/nbd/parameters/nbds_max
512                         ← 模块加载了，上限 512

$ ls /dev/nbd* | wc -l
512                         ← 设备文件都在

$ cat /sys/block/nbd3/size
10485760                    ← 单位是 512 字节扇区：10485760 × 512 = 5 GiB，正被某个沙箱用着

$ cat /sys/block/nbd3/pid
123456                      ← 接着它的进程号，就是 template-manager

$ cat /sys/block/nbd4/size
0                           ← 空闲
```

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 块设备 | 内核提供的“一排可按编号读写的块”，`/dev/nvme0n1`、`/dev/nbd0` 都是 |
| 块设备层 | 内核里排队、合并、调度块请求的一层，下面接各种驱动 |
| loop 设备 | 把一个本地文件变成块设备，内核直接读写文件 |
| NBD | 块设备的每次读写变成发给用户态程序的请求，由程序回答 |
| 请求与应答 | 读、写、刷盘、断开、丢弃；靠编号对应，可以并发、乱序 |
| socketpair | E2B 用本机的一对 unix socket 连接内核和 orchestrator，不走网络 |
| netlink 连接 | 一次性把 socket、块大小、总大小告诉内核 |
| `nbds_max` | NBD 设备数上限，本环境自编译模块设为 512，决定单机并发沙箱上限 |
| 空闲判断 | `/sys/block/nbdN/pid` 不存在且 `size` 为 0 |
| udev nowatch | 关掉 udev 对 NBD 的监视，避免多余读请求；只对 nbd 触发 |
