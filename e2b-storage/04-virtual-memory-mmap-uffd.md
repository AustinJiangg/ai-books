# 第 4 篇｜存储基础（三）：虚拟内存、mmap、缺页与 userfaultfd

> **本篇目标**：上一篇用 NBD 实现了“磁盘按需取”。内存怎么按需取？本篇从虚拟内存讲起，讲清楚缺页是什么、mmap 怎么把文件贴到内存上、大页池怎么预留，然后引出本书最关键的内存机制 userfaultfd：让一个程序替另一个进程处理缺页。最后介绍三样后面要用的工具：pagemap、`process_vm_readv`，以及记录“脏页”的三种办法。

---

## 一、虚拟内存：每个进程都以为自己独占内存

### 1.1 两种地址

你写的程序里，指针里存的地址，比如 `0x7f3a2c001000`，并不是内存条上的真实位置。它是**虚拟地址**。

每个进程都有自己的一大片虚拟地址空间，看起来从 0 到很大很大，完全归自己用。CPU 访问内存时，会把虚拟地址**翻译**成内存条上的**物理地址**。翻译的依据是一张表，叫**页表**。

用一个比喻：虚拟地址是你通讯录里的“张三”，物理地址是张三家的真实门牌。每个人的通讯录各写各的，“张三”在你的通讯录里可能指向 A 小区，在别人的通讯录里指向 B 小区。页表就是通讯录。

### 1.2 按页翻译

页表不是一个字节一个字节地记，而是**一页一页**地记：“虚拟地址第 X 页对应物理内存第 Y 页”。这就是第 2 篇说内存按页管理的原因。普通页 4 KiB，大页 2 MiB。

页表里每一项除了“对应哪一页”，还有几个标志位，比如：

- **存在位**：这一页现在有没有对应的物理内存；
- **可写位**：能不能写；
- **脏位**：被写过没有。

## 二、缺页：用到了才准备

### 2.1 什么是缺页

一个进程申请了 1 GB 内存，内核会立刻给它 1 GB 物理内存吗？不会。内核只是在页表里登记“这 1 GB 虚拟地址归你了”，但每一项的“存在位”都是 0，一页物理内存都没给。

等进程真的去读写某一页时，CPU 翻译地址，发现存在位是 0，就停下来，交给内核处理。这叫**缺页**（page fault）。内核此时才：

1. 找一页空闲的物理内存；
2. 填好内容（新申请的内存填零；文件映射则从文件里读）；
3. 在页表里登记，存在位置 1；
4. 让进程从刚才停下的地方继续执行。

进程完全感觉不到这件事，只是这一次内存访问慢了一点。

### 2.2 按需加载的基础

缺页机制是“按需加载”的基础：**没被访问的页，永远不用准备**。一个 1 GB 的进程，如果只用了 50 MB，就只占 50 MB 物理内存。

E2B 想对客户机内存做同样的事：客户机有 2 GB 内存，但刚恢复时可能只用到几十 MB，那就只准备这几十 MB。问题在于，普通的缺页由内核处理，内核只会“填零”或“从一个文件里读”。而 E2B 的内存数据散在好几代快照里（第 7 篇），内核不知道该去哪读。这就需要下面的 userfaultfd。

## 三、mmap：把文件贴到内存上

### 3.1 基本用法

`mmap` 是一个系统调用，可以把一个文件“贴”到进程的虚拟地址空间里：

```go
data, _ := syscall.Mmap(fd, 0, size, PROT_READ|PROT_WRITE, MAP_SHARED)
// 之后 data[100] 就是文件第 100 个字节
```

贴好之后，读 `data[100]` 就等于读文件第 100 字节，写 `data[100]` 就等于写文件。第一次访问某一页时触发缺页，内核从文件里把那一页读进来（经过页缓存，第 2 篇）。

### 3.2 共享与私有

mmap 有两种模式：

| 模式 | 写入后 | 用途 |
|---|---|---|
| `MAP_SHARED` | 改动写回文件，其他映射同一文件的进程也能看到 | 用内存的方式读写文件 |
| `MAP_PRIVATE` | 改动只在自己这份里，写的时候复制一份（写时复制） | 多个进程共享只读数据，各自改各自的 |

### 3.3 在 E2B 里

E2B 的本地缓存文件（第 11 篇）、沙箱的写时复制文件（第 12 篇）都是用 `MAP_SHARED` mmap 出来用的。这样 orchestrator 读写这些文件，就跟读写一个大字节数组一样方便。

## 四、大页与 hugetlbfs

### 4.1 为什么要预留

第 2 篇说过，大页一次管理 2 MiB 连续物理内存。问题是：**连续**的 2 MiB 物理内存不是随时都有。机器跑久了，内存被切得七零八碎，想找一整块 2 MiB 可能找不到。

所以 Linux 的标准大页（HugeTLB）需要**预先留出一个池子**：开机不久、内存还完整的时候，先划出若干个 2 MiB 页放着，专门给要用大页的程序。

### 4.2 两个参数

| 参数 | 含义 |
|---|---|
| `nr_hugepages` | 静态池：现在就划出这么多大页，一直占着，不还给系统 |
| `nr_overcommit_hugepages` | 超分配额度：池子不够时，还可以临时向系统再要这么多，用完还回去 |

`/proc/meminfo` 里能看到大页的使用情况：

```
HugePages_Total:   20000     ← 当前一共有多少大页（静态 + 已临时要来的）
HugePages_Free:    15000     ← 其中空闲的
HugePages_Rsvd:      100     ← 已经被预订、还没真正用上的
HugePages_Surp:        0     ← 超出静态池、临时要来的
Hugepagesize:       2048 kB  ← 一个大页多大
Hugetlb:        40960000 kB  ← 大页一共占了多少内存
```

### 4.3 hugetlbfs

程序怎么用这个池子？一种办法是挂载一个特殊的文件系统 **hugetlbfs**：

```bash
mount -t hugetlbfs none /mnt/hugepages
```

在这个目录下建文件、mmap 它，得到的内存就来自大页池。这套环境的部署脚本就挂了 `/mnt/hugepages`。第 13 篇会讲这套环境怎么计算静态池和超分配额度，以及停服后为什么大页不会自动还给系统。

## 五、userfaultfd：把缺页交给用户态程序

### 5.1 想法

现在问题清楚了：E2B 想让客户机内存“用到哪页才准备哪页”，而且要由 orchestrator 决定每一页的内容从哪来。

Linux 提供了正好这个能力：**userfaultfd**（user fault file descriptor，简称 UFFD）。它允许一个程序**登记**一段内存区域，以后这段区域发生缺页时，内核不自己处理，而是**通知这个程序**，等程序把内容准备好、填进去，再让出错的线程继续。

用一个比喻：仓库按订单现取货。货架上一开始是空的，有人来拿某个格子的货，发现是空的，就按铃；仓库管理员（orchestrator）听到铃声，去后面的库房（快照文件）里把那一箱货搬来放上，拿货的人再继续拿。

### 5.2 一次缺页的处理过程

```
 Firecracker 进程（客户机内存在它的地址空间里）
   │ 客户机访问第 X 页，这一页还没准备
   ▼
 CPU 缺页 → 内核发现这段区域登记在 UFFD 上
   │ 让出错线程等着
   │ 往 UFFD 里放一条消息：“地址 A 缺页，是读还是写”
   ▼
 orchestrator 的 UFFD 处理程序
   │ 读到消息，算出这是客户机第 X 页
   │ 查映射表，从对应的快照文件里取出这一页内容
   │ 调用 UFFDIO_COPY：“把这 4 KiB / 2 MiB 填到地址 A”
   ▼
 内核把内容填进去，登记页表，唤醒出错线程
   │
   ▼
 客户机继续运行，完全不知道刚才发生了什么
```

`UFFDIO_COPY` 是 userfaultfd 提供的一个操作：**原子地**把一段数据拷进目标页并让它生效。原子的意思是，出错线程要么看到完整的新内容，要么还在等，不会看到一半。

### 5.3 几种事件

UFFD 登记时可以选择要接收哪些事件：

| 事件 | 什么时候触发 | E2B 用不用 |
|---|---|---|
| MISSING | 访问一个还没有内容的页 | 用，这是按需供页的核心 |
| WP（写保护） | 写一个被加了写保护的页 | 不登记这个事件，但用到了写保护位（见下） |
| MINOR | 页在页缓存里但没映射 | 不用 |

### 5.4 写保护位：给页贴封条

UFFD 还有一个功能叫**写保护**（write protect）：可以给一页贴一张“封条”，页的内容在，可以读，但一旦有人写，封条就被撕掉。

`UFFDIO_COPY` 填页时有一个选项 `UFFDIO_COPY_MODE_WP`，意思是“填进去，但同时贴上封条”。这样：

- 如果这一页之后只被读，封条一直在；
- 如果被写了，封条没了。

到打快照时，看哪些页的封条没了，就知道哪些页被写过。这是 E2B 在 x86 上精确记录“脏页”的办法。第 15 篇会看到，这套环境的 ARM 补丁去掉了这个选项，带来了有趣的后果。

## 六、两个观察工具

### 6.1 pagemap：每一页的状态

Linux 为每个进程提供一个文件 `/proc/<pid>/pagemap`，里面每 8 个字节对应进程的一页虚拟内存，记录这一页的状态：

| 位 | 含义 |
|---|---|
| 存在位（present） | 这一页现在有物理内存 |
| 换出位（swapped） | 这一页被换到交换区了 |
| uffd-wp 位 | 这一页带着 UFFD 写保护封条 |
| …… | 其他标志 |

读 pagemap，就能知道一个进程的每一页“在不在、有没有封条”。E2B 定制的 Firecracker 就靠它判断哪些页脏了。

### 6.2 `process_vm_readv`：直接读别人的内存

正常情况下，一个进程不能读另一个进程的内存。但 Linux 提供了 `process_vm_readv` 系统调用：有足够权限的进程，可以**直接从另一个进程的虚拟地址空间里拷贝数据**，不经过文件，也不需要对方配合。

E2B 打快照时，就是 orchestrator 用 `process_vm_readv` 从 Firecracker 进程里把客户机内存的脏页直接拷出来（第 14 篇）。

## 七、记录“脏页”的三种办法

打增量快照的核心问题是：**这一轮里，哪些页被写过？**本书会遇到三种回答方式：

| 办法 | 原理 | 谁来记 | 本书哪里用 |
|---|---|---|---|
| UFFD 写保护位 | 填页时贴封条，写了封条就没了；读 pagemap 看封条 | 内核 + UFFD | 暂停快照（第 14、15 篇） |
| KVM 脏页日志（软件） | 虚拟化层把客户机内存设成只读，第一次写时陷入、记一笔再放开 | KVM 内核模块 | Firecracker 的写跟踪，回滚靠它（第 16 篇） |
| KVM 脏页日志（硬件辅助） | CPU 自己在页表项里记“脏”，KVM 定期收集，不用陷入 | ARM 硬件（HDBSS）+ KVM | 同上，有这项能力时写跟踪默认打开（第 16 篇） |

后两种对上层是同一个功能：Firecracker 的“写跟踪”（track dirty pages）。区别只在 KVM 背后用不用硬件帮忙。三种办法的区别在于精度和开销：

- UFFD 写保护依赖填页方式，填页时不贴封条就失效；
- 软件的 KVM 脏页日志精确，但每一页第一次被写都要陷入一次虚拟化层，对从不打检查点的沙箱是纯开销；
- 硬件辅助由 CPU 自动完成，开销接近于零，但需要支持 HDBSS 的 ARM 处理器和对应的内核。代码里通过 KVM 的能力号 502 来探测。

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 虚拟地址 | 进程看到的地址，经页表翻译成物理地址 |
| 页表 | 按页记录虚拟页到物理页的对应，带存在、可写、脏等标志 |
| 缺页 | 访问没准备好的页时 CPU 停下，交给内核补上，是按需加载的基础 |
| mmap | 把文件贴到内存上；`MAP_SHARED` 写回文件，`MAP_PRIVATE` 写时复制 |
| 大页池 | 预先留出的 2 MiB 连续内存；`nr_hugepages` 静态，`nr_overcommit_hugepages` 临时 |
| hugetlbfs | 用文件的方式使用大页池，本环境挂在 `/mnt/hugepages` |
| userfaultfd | 把一段内存的缺页交给用户态程序处理 |
| `UFFDIO_COPY` | 原子地把数据填进缺页的地址 |
| 写保护封条 | `UFFDIO_COPY_MODE_WP` 填页时贴上，写了就撕掉，用来识别脏页 |
| pagemap | `/proc/<pid>/pagemap`，每页的存在位、写保护位等 |
| `process_vm_readv` | 直接拷贝另一个进程的内存 |
| 脏页的三种记法 | UFFD 写保护；KVM 脏页日志，软件实现或 ARM 硬件（HDBSS）辅助 |
