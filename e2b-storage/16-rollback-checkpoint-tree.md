# 第 16 篇｜快照回滚（一）：检查点树与内存

> **本篇目标**：暂停和恢复都要换一个新的 Firecracker 进程。这套环境的 ARM 补丁加了一项新能力：在沙箱运行中打若干个**检查点**，随时把沙箱**原地**退回到其中某一个，不换进程、不换网络、不丢沙箱 ID。本篇讲这项能力的整体设计和内存部分：它和暂停有什么不同、请求从哪进来、检查点之间怎么组成一棵树、一个检查点存了哪些文件、脏页从哪来、回滚怎么做、文件放在哪、能活多久。磁盘部分、压实和配额留给下一篇。

---

## 一、为什么需要回滚

设想一个 AI 智能体在沙箱里干活：

```
 第 1 步：git clone 项目
 第 2 步：pip install -r requirements.txt
 第 3 步：改代码
 ……
 第 7 步：rm -rf 了一个不该删的目录
```

第 7 步把环境搞坏了。想回到第 6 步之后的状态，有哪些办法？

- **重建沙箱**，从第 1 步重跑：太慢；
- **每一步之后都暂停一次、再恢复**：每次暂停都要停掉 Firecracker、导出内存、上传，恢复又要新开 Firecracker、重新换入工作集（第 14、15 篇），一来一回秒级，还会在 `/tmp/templates` 里堆满 diff。

回滚想做到的是：**在第 6 步之后打一个检查点，花几十毫秒；第 7 步搞坏了，再花几十毫秒把内存和磁盘原地倒回去。**

---

## 二、和暂停的区别

| | 暂停 / 恢复 | 模板快照 | 检查点回滚 |
|---|---|---|---|
| 存在哪 | 存储后端（`/tmp/templates`） | 存储后端 | **本机** `/orchestrator/build/checkpoints/` |
| 产生 build 吗 | 产生，有 buildID | 产生 | **不产生** |
| 活多久 | 跨进程，直到被删 | 同左 | **随这个 Firecracker 进程**，进程没了就没了 |
| 恢复方式 | 新开 Firecracker | 新开 Firecracker | **原地**：同一个进程把内存和 vCPU 倒回去 |
| 网络、NBD | 换新的 | 换新的 | **不变** |
| 典型耗时 | 秒级 | 秒级 | 几十到几百毫秒 |

一句话：检查点是**轻量的、本机的、短命的**快照，只为“同一个沙箱在同一次运行中来回跳”服务。

## 三、请求从哪进来

### 3.1 端口 49984

回滚的接口挂在一个特别的地址上：沙箱的 **49984** 端口。

正常情况下，访问 `<端口>-<沙箱ID>.<域名>` 会被代理转进沙箱里对应的端口（见《E2B 沙箱网络从零讲透》第 18 篇）。但 49984 端口的请求**不会进沙箱**，而是在宿主上被 orchestrator 截下来，交给一个叫 checkpoint 的服务处理。原因很简单：打检查点要暂停虚拟机、调用 Firecracker 的接口，这些事沙箱里面的任何程序都做不到。

这个服务提供四个方法：

| 方法 | 作用 |
|---|---|
| `CreateCheckpoint` | 打一个检查点，可以起名字 |
| `RestoreCheckpoint` | 回滚到某个检查点 |
| `ListCheckpoints` | 列出这个沙箱的检查点 |
| `DeleteCheckpoint` | 删除一个检查点 |

访问控制沿用沙箱的流量令牌（`e2b-traffic-access-token` 请求头），由这个服务自己检查。

### 3.2 SDK

`build.sh -i` 在打 SDK 补丁时，额外装了 `dep/e2b-sdk-checkpoint/` 里的一套 SDK 扩展，让 Python SDK 能直接调用这四个方法。它必须在 `patch_e2b.py` 之前装，因为后者会把 SDK 里所有 https 改成 http，顺序反了会把刚装的这份又改回去。

### 3.3 一个沙箱同一时间只做一件事

同一个沙箱的打检查点、回滚、删除，要排队。排队最多等 `CHECKPOINT_LOCK_WAIT_TIMEOUT`（默认 60 秒），等不到就回答“忙，请稍后重试”（HTTP 503，带 `Retry-After: 1`）。这个默认值特意设得比 SDK 的请求超时略短，让调用方收到一个明确的“忙”，而不是一个莫名其妙的超时。

## 四、检查点树

### 4.1 为什么是树，不是链

回滚之后还可以继续打检查点。看这个例子：

```
 运行 ──▶ 打 c1 ──▶ 运行 ──▶ 打 c2 ──▶ 运行 ──▶ 打 c3
                                   │
                                   └── 回滚到 c2，再运行 ──▶ 打 c4
```

c4 的父亲是 c2，不是 c3。c3 依然可以回滚过去。于是检查点之间的关系是一棵**树**：

```
        c1
        │
        c2
       ╱  ╲
     c3    c4
```

- 每个沙箱一棵树；
- 回滚**不删除**任何检查点：比目标新的检查点作为“另一条分支”保留，照样可以回滚过去；
- 下一个检查点的父亲是**回滚的目标**。

### 4.2 删除：隐藏而不是删掉

如果删除的检查点还有孩子，比如删 c2，它的孩子 c3、c4 还要靠它（下一节讲为什么），不能真删。这时 c2 只是**被隐藏**：列表里看不到它，不能回滚到它，但它的文件还在，供后代使用。下一篇讲的“压实”会在合适的时候把它并进孩子里，真正释放空间。

## 五、一个检查点存了什么

### 5.1 文件

检查点的文件放在：

```
/orchestrator/build/checkpoints/<沙箱ID>/
├── <检查点ID>/
│   ├── snapfile        机器状态（Firecracker 写）
│   ├── mem_diff        内存：这一段时间写过的页（稀疏文件）
│   ├── mem_bitmap      哪些页在 mem_diff 里（FCDB 格式的位图）
│   ├── rootfs.header   这个检查点的磁盘视图（下一篇）
│   └── manifest.json   给人看的说明，程序不读
├── <另一个检查点ID>/
│   └── ……
└── layers/             封存的磁盘写层（下一篇）
```

### 5.2 内存只存“这一段”写过的页

打检查点时，orchestrator 调用 Firecracker 的快照接口，这次**传了** `mem_file_path`，类型是 **Diff**，还多传了一个位图路径：

```
PUT /snapshot/create
{ "snapshot_type": "Diff",
  "snapshot_path":     ".../<检查点ID>/snapfile",
  "mem_file_path":     ".../<检查点ID>/mem_diff",
  "dirty_bitmap_path": ".../<检查点ID>/mem_bitmap" }
```

Firecracker 用写跟踪（第 4、15 篇）知道“自上一个快照或回滚以来，客户机写过哪些页”，把这些页按原位置写进 `mem_diff`（其余位置都是洞），并把它们列在 `mem_bitmap` 里，然后**清空**自己的写跟踪位图，开始记下一段。

“这一段时间”叫一个 **epoch**（时期）。一个检查点就是一个 epoch 写过的页。所以：

- 打检查点的开销和“这段时间写了多少页”成正比，和客户机内存总大小无关；
- 一个 2 GiB 的沙箱，一段时间写了 40 MiB，检查点就是 40 MiB，几十毫秒。补丁注释里的对比是：不开写跟踪时每次要写满 2 GiB，耗时一秒半。

### 5.3 位图边车文件

`mem_bitmap` 的格式（叫 FCDB）在代码注释里写得很清楚：

```
 "FCDB"            4 字节魔数
 版本号            4 字节，目前是 1
 页大小            8 字节
 页数              8 字节
 位图              每 64 页一个 8 字节字，第 w 个字的第 i 位表示第 w×64+i 页
```

这个格式由 orchestrator 和定制版 Firecracker 共用。

### 5.4 根检查点：一份完整的内存

只有 diff 是不够的。回滚到 c3，需要的是“c3 那一刻的完整内存”，c3 只有它那一段写过的页，其余的页在哪？在它的祖先里：c2 那一段、c1 那一段……一直往上，总得有个尽头。

尽头有两种选择，由 `CHECKPOINT_FULL_ROOT` 决定：

| 设置 | 树根是什么 | 特点 |
|---|---|---|
| 不设，或 `true`（默认） | 沙箱的**第一个检查点存完整内存**，它就是根 | 回滚只读检查点自己的文件，不碰模板 |
| `false` | 第一个检查点也是 diff，树根落到**沙箱启动时的内存来源**，即模板的 memfile | 第一个检查点更小，但回滚时可能要读模板 |

另外有两种情况一定会做一次完整捕获，开一棵新的子树：

- 这台机器没开写跟踪（第 15 篇第六节），没法知道哪些页写过；
- 链断了，比如位图不可信。

这套环境没设 `CHECKPOINT_FULL_ROOT`，所以每个沙箱的第一个检查点是一份完整内存。一个 2 GiB 的沙箱，第一个检查点就要 2 GiB 左右的空间。这是第 17 篇算配额时的“地板”。

## 六、脏页从哪来：两个位图之间的缝

### 6.1 问题

Firecracker 的写跟踪位图有个特点：**每打一次检查点就清空一次**（每次回滚也会）。它回答的永远是“自上一个检查点以来写过哪些页”。

对检查点自己来说，这正好。但对**暂停**（第 14 篇）来说就不够了。暂停要导出的是“自这个沙箱从模板恢复以来写过的所有页”，因为新 build 的 header 是相对模板 memfile 合成的。如果沙箱打过检查点再暂停，只问 Firecracker 的位图，就只拿到“最后一个检查点之后”写过的页，之前的都丢了。代码注释说得很重：这会让恢复出来的客户机由**两个不同时刻**的内存拼成，而暂停本身不会报任何错。

### 6.2 补丁的做法：DirtySinceBoot

补丁在 orchestrator 里为每个沙箱维护一个集合 **DirtySinceBoot**（自启动以来的脏页）：

- 每次 Firecracker **即将清空**它的位图时（打检查点、回滚），把那张位图**并进**这个集合；
- 暂停时，把 Firecracker 当前的位图和这个集合**取并集**，得到完整的“自启动以来写过的页”。

第 15 篇日志里的 `source=tracked+accumulated` 就是这种情况。

代码注释里有一句话概括了取舍：**导出多了只是慢，导出少了就是静默的数据损坏。**所以任何一步出了问题（并集失败、某次累积没成功），这个集合会被标记为“不可信”，之后的暂停一律退回到“常驻页”判据：宁可多导出，绝不少导出。

### 6.3 第一个检查点的特殊处理

第一个检查点是完整捕获，Firecracker 写出的位图是“全部页”。把它并进 DirtySinceBoot 是不对的：那会让之后每一次暂停都导出整个客户机内存。

所以第一个检查点在打快照**之前**，先让 Firecracker 导出一次当前的写跟踪位图（不清空），这才是“自启动以来真正写过的页”，用它来累积。代价是一次位图导出：每 GiB 客户机内存 32 KiB。如果这一步做不了，退回到用“全部页”，多但不会少。

## 七、回滚怎么做

### 7.1 要还原哪些页

回滚到目标检查点 T。当前内存和 T 那一刻相比，哪些页可能不一样？

- 当前 epoch 写过的页（Firecracker 当前的位图）；
- 从 T 往后、到现在为止各个检查点里写过的页；
- 如果当前处在另一条分支上，还有从“分叉点”到当前这条分支上写过的页。

这些页的并集叫**还原集**（revert set）。还原集之外的页，当前内存和 T 一样，不用动。

### 7.2 还原成什么内容

还原集里每一页，要还原成“T 那一刻的内容”。这个内容去哪找？沿着 T 的**祖先链**往上找：

```
 第 X 页：T 的 mem_bitmap 里有吗？ ─有─▶ 用 T 的 mem_diff
               │没有
               ▼
          T 的父亲里有吗？ ─有─▶ 用父亲的
               │没有
               ▼
          …… 一直到根（完整内存，或模板 memfile）
```

orchestrator 把找到的内容拼成两个临时文件，放在目标检查点目录旁边：`revert_mem`（要写回的内容）和 `revert_bitmap`（哪些页）。

注意：**整个过程从不在磁盘上拼出一份完整的内存镜像**。只处理还原集，开销和还原集大小成正比。补丁注释特意说明，这让检查点在任何文件系统上都是“和脏页数成正比”，不依赖 reflink 之类的文件系统特性。

### 7.3 原地倒回

然后在一个短暂的暂停窗口里：

```
 1. 暂停虚拟机
 2. 导出当前的写跟踪位图（暂停后它不会再变），确定最终的还原集，生成 revert 文件
 3. 让定制版 Firecracker 原地回滚：
      把 revert_mem 里的页写回客户机内存
      把 vCPU 寄存器、设备状态恢复成 T 的 snapfile 里的样子
 4. 把磁盘视图换成 T 的那一摞层（下一篇）
 5. 恢复虚拟机运行
 6. 等客户机里的 envd 响应（最多 45 秒）
```

整个过程里，Firecracker 进程、KVM、tap 网卡、网络槽位、NBD 设备都不换。一次健康的回滚，envd 大约 2 毫秒就能响应。

### 7.4 失败的两种结局

回滚中途可能失败。代码以 Firecracker 开始改写内存的那一刻为**提交点**：

- **提交点之前**失败：什么都还没改，恢复虚拟机运行，沙箱停留在当前状态，回答一个错误；
- **提交点之后**失败：内存已经改了一部分，磁盘或 vCPU 没跟上，客户机处在“两个时刻之间”的撕裂状态，无法继续。这个沙箱只能销毁重建。

另外，orchestrator 和定制版 Firecracker **必须配套**。如果 Firecracker 是不认识回滚接口的官方版本，回滚直接失败，不会降级成别的做法。

## 八、活多久

检查点的文件在本机，账本在 orchestrator 进程的**内存**里。目录里的 `manifest.json`，以及打开 `CHECKPOINT_DEBUG_INDEX` 后每个沙箱目录下的 `index.json`，都只是给人事后查看用的，程序从不读回。所以：

- **orchestrator 重启**：账本没了。检查点目录所在的 `/orchestrator/build` 本来就会在启动时被清空（第 11 篇），检查点存储自己启动时也会清空它的根目录；
- **沙箱暂停再恢复**：同一个沙箱 ID 回来了，但它是一个新的 Firecracker 进程，内存和磁盘栈都是新的，旧的 diff 链没法倒回到它身上。代码用“代”（generation，即每个 Firecracker 进程的生命周期 ID）来区分：新的一代接管这个沙箱 ID 时，丢掉上一代留下的所有检查点。

所以检查点**不能替代暂停**。想跨重启、跨暂停保留状态，还得用暂停或模板快照。

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 检查点 | 本机、轻量、随 Firecracker 进程存活的快照，用于原地回滚 |
| 49984 端口 | 检查点接口，请求在宿主被截下，不进沙箱 |
| 检查点树 | 回滚后再打检查点形成分支；回滚不删检查点 |
| 隐藏 | 删除还有孩子的检查点时只隐藏，文件留给后代 |
| epoch | 两个检查点之间的一段时间，检查点只存这段写过的页 |
| `mem_diff` + `mem_bitmap` | 稀疏的内存 diff 加 FCDB 格式位图 |
| 根检查点 | 默认第一个检查点存完整内存；`CHECKPOINT_FULL_ROOT=false` 时根落到模板 |
| DirtySinceBoot | 每次 Firecracker 清空位图前把它并进来，供暂停导出完整的脏页 |
| 还原集 | 当前和目标之间可能不同的页，只处理它们 |
| 祖先链查找 | 每页沿目标的祖先往上找内容，不拼完整镜像 |
| 原地回滚 | 同一个进程写回内存、恢复 vCPU，网络和 NBD 不变 |
| 提交点 | 之前失败可继续运行；之后失败只能重建沙箱 |
| 生命周期 | 账本只在内存里；重启、暂停恢复后检查点作废 |
