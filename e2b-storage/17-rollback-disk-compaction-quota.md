# 第 17 篇｜快照回滚（二）：磁盘层、压实与配额

> **本篇目标**：上一篇讲了回滚的内存部分。本篇讲剩下的三件事。第一，磁盘怎么跟着回滚：打检查点时写层怎么“封存”，回滚时磁盘视图怎么换，多层磁盘怎么读得快。第二，检查点删了以后空间怎么回来：层的引用计数，以及把隐藏检查点并进孩子的“压实”。第三，怎么防止检查点把磁盘吃光：几道配额和它们的默认值。最后讲怎么查看一台机器的检查点能力，并把三种快照放在一起做个对照。

---

## 一、磁盘的回滚：封存写层

### 1.1 回顾：沙箱的磁盘

第 12 篇说，沙箱的根盘是两层：只读的模板，加上沙箱自己的 COW 文件（写层）。

要让磁盘能回滚到某个检查点，就要在打检查点那一刻，把“磁盘长什么样”定格下来。最直接的办法是把整个 COW 文件拷一份，但 COW 文件可能有好几 GB，太慢。

### 1.2 封存

补丁的做法叫**封存**（Seal）：

```
 打检查点前：  模板 ── 写层 W1（沙箱正在往里写）

 打检查点时：  1. 虚拟机已暂停
              2. 刷新屏障：把内核 NBD 设备里已经接收的写，全部推进 W1
              3. 把 W1 冻结成只读的“封存层” L1
              4. 装上一个全新的空写层 W2

 打检查点后：  模板 ── L1（只读）── W2（沙箱往这里写）
```

封存只是几个指针的切换，不拷贝任何数据，所以很快。代码注释提到一个取舍：封存后**故意不**对 L1 做同步刷盘（msync）。L1 的脏页还在宿主的页缓存里，但之后所有读它的人（运行中的沙箱、回滚时重新打开它）都经过同一份页缓存，所以内容一致。刷盘只能换来“宿主崩溃后还在”，而检查点的账本本来就随进程消失（第 16 篇），这个保证没有意义。实测刷盘每 MB 脏数据要 0.49 毫秒，而且这是封存耗时随写入量增长的唯一原因。

封存层文件先留在沙箱的缓存目录里，虚拟机恢复运行后再移到检查点存储的 `layers/` 目录下（第 16 篇第五节的目录图）。

### 1.3 每个检查点的“磁盘视图”

打了几个检查点之后，磁盘是一摞层：

```
 模板 ── L1 ── L2 ── L3 ── W4（当前写层）
          ↑     ↑     ↑
         c1    c2    c3   （各自封存的那一层）
```

每个检查点记下自己那一刻的**磁盘视图**：“模板 + 从下到上哪几层”。c2 的视图是“模板 + L1 + L2”。这个视图被写成一个 header（就是第 7 篇那种映射表），存在检查点目录下的 `rootfs.header` 里。

### 1.4 回滚时换视图

回滚到 c2，磁盘这边做的是**换视图**（ResetView）：

1. 在虚拟机暂停前，按 c2 的视图把“模板 + L1 + L2”重新组装成一个只读设备（AssembleView）；
2. 暂停窗口里，刷新屏障，然后把 NBD 背后的 overlay 下层换成这个设备，再装一个全新的空写层；
3. 恢复运行。

NBD 设备本身不变，Firecracker 也不知道磁盘被换了。从客户机看，磁盘内容一瞬间回到了 c2 那一刻。客户机的页缓存则随内存一起回滚了，两者保持一致。

### 1.5 层的索引：LayerStack

层摞多了，读一块数据要从上往下逐层找，会越来越慢（第 5 篇的链表式）。第 12 篇提到的 **LayerStack** 就是为此准备的：

```
 每一块一个 uint16，记“这一块的主人是第几层”（0 表示模板）

 块号：    0    1    2    3    4    5   ……
 主人：    0    2    0    1    3    0   ……
```

读第 4 块：查数组得 3，直接去 L3 读。不管摞了多少层，读一块只查一次数组。

代价是内存：每 GiB 根盘 26 万多个块，每块 2 字节，即 **每 GiB 512 KiB**，每个视图一份。

## 二、空间怎么回来：层的引用计数

### 2.1 问题

一个封存层可能被很多人用到：

- 当前运行中的磁盘栈在读它；
- 好几个检查点的视图都列着它（c2、c3 的视图都包含 L1）。

删掉一个检查点，它封存的那一层能不能删？不一定。补丁注释记录了一个教训：早先的版本里层永远不删，一个在配额限制下循环打检查点的沙箱，攒下了几万个层文件，绝大多数属于早已删除的检查点。

为什么不能按检查点树来判断？因为“层的摞法”和“检查点树”不是一回事。一个完整内存捕获的检查点是新子树的根（第 16 篇），但它的磁盘视图仍然摞在之前所有封存层之上。树上不相干的两个检查点，可能共用同一层。

### 2.2 引用计数

于是补丁对层做**引用计数**，按“谁的列表里有它”来数：

| 动作 | 计数变化 |
|---|---|
| 封存一层，加入当前磁盘栈 | 这一层 +1 |
| 一个检查点提交了视图 | 视图里每一层 +1 |
| 回滚到某检查点 | 新视图里每一层 +1，被换下的旧栈里每一层 −1 |
| 删除或隐藏一个检查点 | 它视图里每一层 −1 |

计数归零，就删掉层文件和它的边车文件。整个沙箱结束时，剩下的一起删掉。

### 2.3 中毒

还有一种防御：如果某一步合并映射时校验失败，或者某次封存的层没能记进账本，orchestrator 就无法证明“账本上的磁盘视图”和“实际在读的那一摞层”是一致的。这时账本被标记为**中毒**（poisoned）：

- 之后打检查点一律失败，并明确告诉调用方原因；
- 回滚到一个已有的检查点可以修复它：回滚会用那个检查点的视图整个替换当前磁盘栈，之后账本和实际又一致了。

宁可拒绝，也不记下一个错误的视图。

## 三、压实：别让隐藏检查点越攒越多

### 3.1 问题

第 16 篇说，删除还有孩子的检查点时只隐藏。考虑一个常见用法：**只保留最近 N 个检查点，每打一个新的就删最老的**。

```
 c1 ── c2 ── c3 ── c4 ── c5        保留最近 3 个
 删 c1：c1 有孩子 c2，隐藏
 删 c2：c2 有孩子 c3，隐藏
 ……
```

每次删的都是下一个的父亲，**永远不会**出现“没有孩子的叶子”，隐藏的检查点无限增长，磁盘也跟着涨。按数量的配额只数“看得见的”检查点，管不住它。回滚时沿祖先链找内容，链也越来越长。

### 3.2 并进孩子

**压实**（compaction，代码里叫 fold）的规则是：一个隐藏的、不是当前基础的、**只有一个孩子**的检查点 H，可以并进它的孩子 C。

内存这半：

- 合并后的 C，脏页位图 = H 的位图 ∪ C 的位图；
- 内容：C 有的页用 C 的，C 没有而 H 有的页，从 H 拷进 C 的文件同一位置；
- 合并后的 C 保留 C 的 ID、快照和视图，父亲改成 H 的父亲。

代码注释给了一段证明：任何回滚，凡是路径经过 H 的，一定紧挨着经过 C（因为 H 只有 C 一个孩子），所以把两者合成一个不改变任何回滚的结果。如果 H 是一个完整内存的根，合并后的 C 也成为完整的根。

磁盘这半：如果所有列着 H 的封存层的视图，都是紧接着列着 C 的那一层，就把这两层合并成一层，改写引用它们的 header；否则 H 那一层就留在 C 的视图里，和以前一样。

### 3.3 并完以后

做完压实后，一棵有 V 个可见检查点的树，最多只有 V+1 个隐藏的，总共不超过 2V+1 个。

压实在删除检查点时顺带进行：

| 变量 | 默认 | 含义 |
|---|---|---|
| `CHECKPOINT_COMPACT` | 开 | 设为 `false` 就不压实，隐藏的检查点一直保留 |
| `CHECKPOINT_COMPACT_MAX_PER_OP` | 8 | 一次删除最多顺带并几个 |

某个候选并失败了，会在之后的删除里重试，最多 3 次，之后就放着不管。放着不管不会更糟，只是和没有压实时一样。

压实全程不影响正在进行的回滚：所有文件工作都写到新名字下，最后才一次性切换。同一个沙箱的所有操作本来就要排队（第 16 篇第三节）。

## 四、配额：别让检查点吃光磁盘

检查点存在 `/orchestrator/build/checkpoints/` 下，和本地缓存（第 11 篇）在同一块磁盘上。补丁设了三道闸：

### 4.1 剩余空间：`CHECKPOINT_MIN_FREE_BYTES`

打检查点之前，检查存储所在的文件系统**还剩多少空间**。不够就拒绝。

默认阈值 = max(4 GiB, 2 × 这个沙箱的客户机内存)。设为 0 关闭检查。

为什么是两倍客户机内存？因为最坏情况下一个检查点要写一份完整内存（第一个检查点就是），还要留余量。

### 4.2 数量：`CHECKPOINT_MAX_PER_SANDBOX`

每个沙箱最多同时持有几个**可见的**检查点。默认 0，即不限。

### 4.3 字节：`CHECKPOINT_MAX_BYTES_PER_SANDBOX`

每个沙箱的检查点总共能占多少字节。默认 0，即不限。

它按磁盘实际分配的块来算（稀疏文件只算写了的部分），包括：每个检查点的 diff、位图、snapfile、rootfs header，以及每个封存层和它的边车文件。

超了怎么办？打新检查点时回答 **429**，原因 `checkpoint_bytes_limit`。沙箱照常运行，回滚也不受限制。要腾出空间，得删检查点，但要删对：

- 删当前基础（沙箱正在其上运行的那个）或一个有多个孩子的分叉点：只能隐藏，只省下 snapfile 和 header 几十 KB；
- 删更老的检查点：会被并进它唯一的孩子，省下的是“孩子覆盖掉的那些页”，可能几乎为零，也可能接近一整份客户机内存。

### 4.4 地板

不管怎么删，只要沙箱还在运行，至少要留下一个完整的根：约等于**一份客户机内存**，加上磁盘层和 header。补丁注释给出了两个阈值（M 是客户机内存，ε 是额外开销，实测约 61 MiB，取 256 MiB 留余量）：

- 字节上限 > M + ε：沙箱永远不会被卡死，一直删老的，最终剩一个完整的根；
- 字节上限 > 2M + ε：即使最坏情况（每个检查点都改写全部内存），也能保留一个更早的回滚点并继续打检查点。

所以一个 2 GiB 的沙箱，字节上限设到 2.3 GiB 以下没有意义，设到 4.3 GiB 以上才宽裕。

这套环境三个变量都没设：剩余空间按默认阈值检查，数量和字节不限。

## 五、看一台机器的检查点能力

### 5.1 能力文件

orchestrator 启动时，把“这台机器的检查点栈会怎么工作”写进日志，同时写一个文件：

```
/orchestrator/build/checkpoint-capabilities.json
```

放在检查点存储根目录**旁边**而不是里面，因为存储根目录每次启动都会被清空。之所以要写文件，是因为忙碌的节点上日志几分钟就被轮转掉了，而人往往是在出问题以后才来找它。

文件里有：

| 字段 | 含义 |
|---|---|
| `Store` | 检查点存储的路径 |
| `TrackDirtyPages` 和原因 | 写跟踪开没开、为什么（第 15 篇第六节） |
| `LockWaitTimeout` | 排队等待上限，来自环境变量还是默认值 |
| `FCCallTimeout` | 单次 Firecracker 调用的超时 |
| `MinFreeBytes` | 剩余空间阈值 |
| `MaxPerSandbox`、`MaxBytesPerSandbox` | 两个配额 |
| `DebugIndex` | 是否写 `index.json` |
| `Compact`、`CompactMaxPerOp` | 压实设置 |
| `FaultInject` | 故障注入列表，正常节点应为空 |

每个值都标明它是来自环境变量（`env`）还是默认值（`default`）。这是为了回答一个常见的疑问：“我设的变量到底生效没有？”

### 5.2 故障注入

`CHECKPOINT_FAULT_INJECT` 用来在测试时故意让某个步骤失败，验证失败路径。生产节点不应设置它。能力文件里 `FaultInject` 不为空，就说明这台机器在跑故障测试。

## 六、三种快照的对照

| | 模板快照（第 9 篇） | 暂停与恢复（第 14 篇） | 检查点回滚（第 16、17 篇） |
|---|---|---|---|
| 谁发起 | 模板构建流水线 | SDK `pause()` | SDK 调 49984 端口 |
| 存什么（内存） | 完整（去掉全零页）或这一层的改动 | 自恢复以来的脏页 | 这个 epoch 写过的页；第一个是完整的 |
| 存什么（磁盘） | 完整或这一层写过的块 | COW 文件里的块 | 封存层 |
| 存在哪 | `/tmp/templates`（存储后端） | `/tmp/templates` | `/orchestrator/build/checkpoints/` |
| 映射结构 | header（拍平） | header（拍平） | 检查点树 + 每个视图一个 header |
| 活多久 | 直到手工清理或宿主重启 | 同左 | 随 Firecracker 进程 |
| 恢复 | 新开 Firecracker | 新开 Firecracker | 原地 |
| 耗时 | 秒级以上 | 秒级 | 几十到几百毫秒 |
| ARM 下内存精度 | 第一层去全零；之后同暂停 | 看写跟踪开没开 | 依赖写跟踪；没开就每次完整捕获 |

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 封存 | 暂停窗口里把当前写层冻结成只读层、换新写层，不拷数据、不刷盘 |
| 磁盘视图 | 模板加从下到上哪几层，存成检查点的 `rootfs.header` |
| 换视图 | 回滚时在 NBD 下面换掉 overlay 的下层，NBD 和 Firecracker 不变 |
| LayerStack | 每块一个 `uint16` 记主人，读一块查一次；每 GiB 512 KiB |
| 层引用计数 | 按“谁的列表里有它”计数，归零即删 |
| 中毒 | 账本与实际磁盘栈无法证明一致时，拒绝新检查点；回滚可修复 |
| 压实 | 只有一个孩子的隐藏检查点并进孩子；默认开，每次最多 8 个 |
| 剩余空间 | 默认至少 max(4 GiB, 2×客户机内存) |
| 数量、字节上限 | 默认都不限；超字节上限回 429 |
| 地板 | 至少一份客户机内存；字节上限要大于 M+ε 才不会卡死 |
| 能力文件 | `/orchestrator/build/checkpoint-capabilities.json`，标明每个值的来源 |
