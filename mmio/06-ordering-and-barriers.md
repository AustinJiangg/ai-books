# 第 6 篇｜顺序与屏障：先写数据，再按门铃

> **本篇目标**：理解为什么即使有了 `volatile`、有了 Device 内存类型，MMIO 访问的顺序仍然可能出错。读完本篇，你会知道 CPU 乱序和“提前写确认”分别带来什么问题，ARM64 的 DMB、DSB、ISB 三种屏障各管什么，Linux 的 `writel` 和 `writel_relaxed` 有什么区别，以及在什么场景下该用什么屏障。

---

## 一、一个经典场景：顺序就是语义

### 1.1 先准备，后开始

回忆第 3 篇的结论：**对设备来说，顺序就是语义**。最典型的就是“先准备，后开始”的模式：

```c
writel(src_addr, dev + DMA_SRC);     // ① 告诉设备：数据从哪里来
writel(dst_addr, dev + DMA_DST);     // ② 告诉设备：数据搬到哪里去
writel(length,   dev + DMA_LEN);     // ③ 告诉设备：搬多少
writel(START,    dev + DMA_CTRL);    // ④ 按下“开始”按钮
```

设备在收到 ④ 的那一刻，会去读 ①②③ 三个寄存器里的值，然后开始干活。如果 ④ 比 ③ 先到达设备，设备就会用旧的长度去搬数据。

还有一种更常见、更隐蔽的模式——**先把数据写进内存，再通知设备**：

```c
desc->addr = buf_dma_addr;           // ① 普通内存：填写一个“任务描述”
desc->len  = len;                    // ② 普通内存：填写长度
writel(1, dev + DOORBELL);           // ③ MMIO：按门铃，通知设备来取任务
```

设备收到门铃后，会自己去内存里读 `desc`（这就是 DMA，第 8 篇详讲）。如果门铃比 `desc` 的内容先“生效”，设备读到的就是一个半成品甚至垃圾任务。

### 1.2 前面几篇已经做了什么

我们已经过了两道关：

- **第 4 篇**：用 `volatile` 或访问函数，保证**编译器**不会调换 MMIO 访问的顺序。
- **第 5 篇**：用 Device 内存类型，保证 MMIO 访问**不被缓存**；其中的 `nR`（不重排）保证**对同一个设备**的访问按程序顺序到达。

那么上面第一个例子（4 次写同一个设备）在 Device-nGnRE 下其实已经安全了。但第二个例子呢？①② 是写**普通内存**，③ 是写**设备**，它们是两种不同类型的内存，`nR` 管不到它们之间的顺序。

另外还有一个我们在第 5 篇埋下的伏笔：**提前写确认（E）**——CPU 以为写完成了，设备却可能还没收到。

这一篇就来解决这两个问题。

## 二、CPU 为什么要乱序

### 2.1 程序顺序 vs. 实际顺序

我们写程序时，默认指令是“一条接一条”执行的。但现代 CPU 为了提高速度，内部会**不按程序顺序**执行指令。比如：

- 一条读内存的指令要等 100 纳秒，CPU 不会傻等，而是先去执行后面不依赖这个结果的指令；
- 写内存时，CPU 把要写的数据放进一个叫**写缓冲区（store buffer）**的小队列里，然后立刻继续往下走，写缓冲区在后台慢慢把数据写出去；
- 多个 CPU 核各自有自己的缓存和写缓冲区，一个核写入的数据，另一个核可能过一会儿才看到。

对单个 CPU 核上运行的单线程程序来说，这些优化是“透明”的——CPU 会保证你**自己**看到的结果和按顺序执行一样。但对于**其他观察者**（另一个 CPU 核，或者一个设备），它们看到的写入顺序，可能和程序顺序不同。

如果你读过[《mmap 从零讲透》第 8 篇](../mmap/08-anonymous-mapping.md)，那里讲过 ARM64 的“弱内存序”给多进程共享内存带来的问题。设备，本质上就是另一个“观察者”。

### 2.2 强内存序与弱内存序

不同 CPU 架构允许的乱序程度不同：

- **x86 是强内存序**（专业名称叫 TSO，Total Store Order）。它只允许一种乱序：后面的读可以跑到前面的写之前。写和写之间、读和读之间的顺序都是保证的。
- **ARM64 是弱内存序**。在普通内存上，读写之间几乎可以任意重排：写和写可以调换，读和读可以调换，读和写也可以调换——只要不违反单线程程序自己能看到的结果。

这就是为什么**很多在 x86 上运行良好的驱动程序，移植到 ARM64 后会出现莫名其妙的问题**：x86 的硬件“免费”提供了很多顺序保证，程序员不知不觉地依赖了它们；到了 ARM64 上，这些保证没了，潜伏的 bug 就暴露出来了。

### 2.3 回到门铃的例子

```c
desc->addr = buf_dma_addr;   // ① 普通内存写
desc->len  = len;            // ② 普通内存写
writel_relaxed(1, dev + DOORBELL);   // ③ 设备写（假设不带屏障）
```

在 ARM64 上，①② 是 Normal 内存的写，可能还在写缓冲区里或者缓存里没被设备“看到”，而 ③ 是 Device 内存的写，可能先一步到达了设备。设备收到门铃，去内存读描述符，读到的是旧值。

```
程序顺序：    ① → ② → ③

设备看到的：  ③ → （去读内存里的描述符，此时①②还没生效）→ 读到旧数据！
```

要防止这种情况，需要在 ② 和 ③ 之间插入一个“栅栏”，告诉 CPU：**栅栏前面的所有写，必须在栅栏后面的写之前生效。**

这个栅栏就叫**内存屏障（memory barrier）**。

## 三、提前写确认：写完了不等于到了

### 3.1 什么是 posted write

第 5 篇介绍过 Device-nGnRE 里的 E：允许提前写确认。在 PCI/PCIe 的世界里，这种写有一个专门的名字：**posted write（投递式写）**。

用寄信来类比：

- **非投递式（non-posted）**：你亲自把信送到收件人手上，看着他签收，然后才回家。你回到家时，**确定**对方收到了。
- **投递式（posted）**：你把信投进邮筒就回家了。你回到家时，信可能还在邮筒里、在分拣中心、在快递员的车上，**对方不一定已经收到**。

CPU 发出一次 MMIO 写，路上要经过互连、桥、PCIe 控制器、PCIe 链路，最后才到设备。如果每次写都要等设备亲自回复“收到了”，CPU 要等很久。所以大部分 MMIO 写都是投递式的：只要路上某个环节接手了，就算“写完成”，CPU 可以继续执行下一条指令。

PCIe 规范本身就规定：**对设备的内存写（Memory Write）是投递式的**，不需要设备回复。

### 3.2 什么时候会出问题

大部分时候，投递式写没问题——反正写最终会到达，而且对同一设备的写按顺序到达。问题出在**你需要知道写已经真的生效了**的时候。

**例子一：关闭中断**

```c
writel(0, dev + INT_ENABLE);     // 关掉设备的中断
// 现在我认为设备不会再发中断了……
free_irq_handler_resources();    // 释放中断处理程序要用的资源
```

`writel` 返回时，“关中断”的命令可能还在路上。设备在收到这个命令之前，仍然可能发出一个中断。中断处理程序被调用时，发现资源已经被释放了——崩溃。

**例子二：延时等待**

```c
writel(RESET, dev + CTRL);       // 让设备复位
udelay(10);                      // 手册说复位需要 10 微秒
writel(CONFIG, dev + CTRL);      // 复位后配置设备
```

如果复位命令在路上走了 5 微秒才到，那 `udelay(10)` 实际上只给了设备 5 微秒的复位时间。

### 3.3 解决办法：读回来

解决 posted write 问题的经典技巧是：**写完之后，对同一个设备做一次读**。

```c
writel(0, dev + INT_ENABLE);     // 关中断（投递式写）
readl(dev + INT_ENABLE);         // 读回来（读必须等设备真正回复）
// 现在可以确定关中断命令已经到达设备了
```

原理是：

1. **读一定是非投递式的**——你要拿到数据，就必须等设备真的回复；
2. **对同一个设备，读不能超越之前的写**——这是 PCIe 规范和 ARM 的 `nR` 属性共同保证的。读请求在路上不会“超车”前面的写请求。

所以，当 `readl` 返回时，它前面的那次写一定已经到达了设备。这叫做**“刷新”投递式写（flushing posted writes）**。读的那个寄存器不重要（甚至读回的值都不用看），只要是**同一个设备**上的、**读没有副作用**的寄存器就行。

Linux 内核文档明确指出：**`writel` 不保证写操作在函数返回时已经完成**；如果需要确认完成，驱动程序必须自己读回。

## 四、ARM64 的三种屏障

### 4.1 屏障是什么

**内存屏障**是一类特殊的 CPU 指令，它本身不读写任何数据，作用只有一个：**限制屏障前后的内存访问之间的顺序**。

可以把它想象成高速公路上的一个**检查站**：

- 检查站前面的车（屏障之前的内存访问）；
- 检查站后面的车（屏障之后的内存访问）；
- 检查站规定：前面的车必须全部通过某个关口，后面的车才能放行。

不同的屏障，规定的“关口”不一样。ARM64 有三种屏障指令。

### 4.2 DMB：数据内存屏障

**DMB（Data Memory Barrier）**：保证屏障**之前**的内存访问，在屏障**之后**的内存访问**之前被观察到**。

“被观察到”是关键词。DMB 不要求前面的访问真的完成，只要求**顺序**：任何观察者（其他 CPU 核、设备）都不会先看到后面的访问、再看到前面的访问。

```
写 A
写 B
DMB         ← 检查站：A、B 必须排在 C、D 前面
写 C
写 D
```

DMB 是“最轻”的屏障，开销最小。在门铃的例子里，用 DMB 就足够了：保证描述符的写入在门铃之前被设备看到。

### 4.3 DSB：数据同步屏障

**DSB（Data Synchronization Barrier）**：比 DMB 更强。它要求屏障之前的所有内存访问**真正完成**，CPU 才会执行屏障之后的**任何指令**（不只是内存访问）。

```
写 A
写 B
DSB         ← 检查站：A、B 必须完全完成，CPU 才能继续执行任何指令
（任何指令）
```

DMB 只管“排队顺序”，DSB 管“必须完成”。DSB 会让 CPU 停下来等待，开销比 DMB 大得多。

什么时候需要 DSB？当后面的操作**不是内存访问**，但又依赖前面的访问已经完成时。比如：

- 修改了页表之后，要刷新 TLB（地址翻译缓存）；
- 在让 CPU 进入低功耗等待状态（`WFI` 指令）之前，确保所有写都已经出去了；
- 执行某些系统寄存器操作之前。

### 4.4 ISB：指令同步屏障

**ISB（Instruction Synchronization Barrier）**：清空 CPU 的指令流水线，让后面的指令重新从内存（或指令缓存）取指、译码。

它和内存访问的顺序关系不大，主要用于：修改了一些影响指令执行的系统寄存器（比如开启 MMU、修改异常向量表地址）之后，确保后续指令能“看到”新设置。

在普通驱动的 MMIO 访问中，ISB 很少直接用到。

### 4.5 屏障的范围和类型

DMB 和 DSB 还可以带参数，进一步精确控制：

**范围（shareability domain）**——这个屏障要对“谁”保证顺序：

| 参数 | 范围 | 用途 |
|---|---|---|
| `ish` | Inner Shareable，通常是所有 CPU 核 | CPU 核之间的同步 |
| `osh` | Outer Shareable，包括 CPU 核和设备 | CPU 与设备（DMA）之间的同步 |
| `sy` | Full System，整个系统 | 最保险，开销最大 |

**类型**——这个屏障管“哪些访问”：

| 后缀 | 含义 |
|---|---|
| （无） | 读和写都管 |
| `st` | 只管写和写之间（store） |
| `ld` | 管读和后面的读写之间（load） |

比如 `dmb oshst` 的意思是：“对 CPU 和设备都可见的范围内，保证屏障之前的写在屏障之后的写之前被观察到”——这正好是门铃场景的需求。

你不需要记住这些组合，Linux 内核已经把它们封装好了。但看到驱动代码或内核源码里出现 `dmb`、`dsb` 时，你应该能认出它们是什么。

### 4.6 x86 的情况

x86 也有屏障指令：`mfence`（全屏障）、`sfence`（写屏障）、`lfence`（读屏障）。但由于 x86 是强内存序，而且对 UC 内存的访问本身就是严格有序的，所以在 x86 上，很多屏障实际上只需要阻止**编译器**重排就够了，不需要真正的 CPU 指令。

唯一的例外是**写合并（WC）内存**：WC 的写可能在写合并缓冲区里被重排或延迟，需要 `sfence` 来冲刷。

这又一次说明了为什么 x86 上的驱动“容易写对”，而 ARM64 上“容易出错”。

## 五、Linux 的约定

### 5.1 不用自己写屏障指令

驱动程序员几乎从来不直接写 `dmb`、`dsb` 这样的指令——那样代码就没法在 x86、RISC-V 等其他架构上编译了。Linux 内核提供了一套**与架构无关**的屏障函数和带屏障的访问函数，在每个架构上展开成恰当的指令。

### 5.2 `writel` vs. `writel_relaxed`

这是 Linux MMIO 访问函数里最重要的一对区别：

**`writel`（带屏障）**：Linux 规定，`writel` 在执行写操作**之前**，保证所有**先前的普通内存写**都已经对设备可见。也就是说，它内部隐含了一个“写屏障”。

```c
desc->addr = buf_dma_addr;
desc->len  = len;
writel(1, dev + DOORBELL);    // 安全：writel 保证 desc 先被设备看到
```

**`writel_relaxed`（不带屏障）**：只保证对**同一个设备**的 `_relaxed` 访问之间按顺序到达，**不保证**和普通内存访问之间的顺序。

```c
desc->addr = buf_dma_addr;
desc->len  = len;
writel_relaxed(1, dev + DOORBELL);   // 危险！在 ARM64 上可能先于 desc 到达
```

读也一样：

**`readl`（带屏障）**：保证这次读完成之后，**后续的普通内存读**才会执行。典型场景：先读设备的状态寄存器确认“DMA 已完成”，然后再去读 DMA 写进内存的数据。

```c
if (readl(dev + STATUS) & DMA_DONE) {
    process(dma_buffer);    // 安全：readl 保证读 buffer 发生在读 STATUS 之后
}
```

**`readl_relaxed`（不带屏障）**：不保证这一点。如果用它，CPU 可能在读 STATUS 之前就已经（推测地）把 `dma_buffer` 读进来了，读到的是 DMA 完成之前的旧数据。

### 5.3 为什么要有 `_relaxed` 版本

既然 `writel` 更安全，为什么还要 `_relaxed`？因为**屏障有代价**。在 ARM64 上，每个 `writel` 前面都会插入一条屏障指令，每个 `readl` 后面也会有。

如果你要连续配置一个设备的 20 个寄存器，中间不涉及任何普通内存：

```c
writel_relaxed(a, dev + REG1);
writel_relaxed(b, dev + REG2);
...
writel_relaxed(t, dev + REG20);
```

用 `_relaxed` 版本完全安全（因为同一设备的访问之间本来就按顺序，这是 Device-nGnRE 的 `nR` 保证的），而且省掉了 20 条屏障指令。在高性能驱动（网卡、存储）的热点路径上，这种优化很有价值。

**原则：默认用 `readl`/`writel`；只有在确认不需要和普通内存保持顺序、并且性能确实重要时，才用 `_relaxed`。**

### 5.4 单独的屏障函数

有时候你需要在访问函数之外单独放一个屏障。Linux 提供了几个：

| 函数 | 作用 | 典型用途 |
|---|---|---|
| `mb()` | 全屏障：读写都不能越过 | 最保险，开销最大 |
| `wmb()` | 写屏障：前面的写在后面的写之前 | 普通内存和 MMIO 之间的写顺序 |
| `rmb()` | 读屏障：前面的读在后面的读之前 | 普通内存和 MMIO 之间的读顺序 |
| `dma_wmb()` | DMA 写屏障：只保证 CPU 和设备看到的普通内存写的顺序 | 填写 DMA 描述符的多个字段之间 |
| `dma_rmb()` | DMA 读屏障 | 读取设备写回的描述符的多个字段之间 |

`dma_wmb()` 和 `wmb()` 的区别很微妙：`dma_wmb()` 只管**一致性 DMA 内存**（第 8 篇）里的普通写之间的顺序，开销更小（在 ARM64 上通常是一条 DMB）；`wmb()` 还要管 MMIO 写，开销更大（在 ARM64 上通常是一条 DSB）。

一个常见的组合模式：

```c
desc->addr  = buf_dma_addr;
desc->len   = len;
dma_wmb();                      // 保证 addr、len 先于 status 被设备看到
desc->status = DESC_READY;      // 最后才把描述符标记为“就绪”
writel(1, dev + DOORBELL);      // writel 自带屏障，保证 status 先于门铃
```

为什么 `status` 之前还要一个 `dma_wmb()`？因为有的设备不需要门铃，它会自己**轮询**内存里的描述符，看到 `status == DESC_READY` 就开始处理。如果 `status` 比 `addr`、`len` 先被设备看到，设备就会处理一个不完整的描述符。

### 5.5 多核与锁

还有一个更隐蔽的场景：两个 CPU 核都要访问同一个设备，用一把自旋锁保护。

```
CPU 0:                          CPU 1:
spin_lock(&lock);
writel(a, dev + REG);
spin_unlock(&lock);
                                spin_lock(&lock);
                                writel(b, dev + REG);
                                spin_unlock(&lock);
```

锁保证了 CPU 1 一定在 CPU 0 释放锁之后才执行写。但 CPU 0 的写可能还在它自己的写缓冲区或路上，而 CPU 1 的写可能先到达设备。设备看到的顺序是 `b` 然后 `a`——和锁的顺序相反。

在早期的 Linux 里，驱动需要在释放锁之前手动调用一个叫 `mmiowb()` 的屏障来防止这种情况。从 Linux 5.2 开始，这个保证被移进了自旋锁的实现本身：**在持锁期间做的 MMIO 写，保证在锁被下一个 CPU 拿到之前到达设备**。驱动程序员不再需要操心这一点。

## 六、一个典型 bug 的复盘

下面是一个在网卡驱动中反复出现过的 bug 模式（简化版），很多驱动在从 x86 移植到 ARM64 时都踩过类似的坑。

### 6.1 代码

一块网卡用一个“发送描述符环”来接收发包任务。驱动发包的代码是：

```c
void xmit_packet(struct nic *nic, dma_addr_t buf, u32 len) {
    struct tx_desc *d = &nic->tx_ring[nic->tail];

    d->buf_addr = buf;
    d->length   = len;
    d->flags    = DESC_OWNED_BY_HW;   // 把描述符交给硬件

    nic->tail = (nic->tail + 1) % RING_SIZE;
    writel_relaxed(nic->tail, nic->regs + TX_TAIL);   // 按门铃
}
```

### 6.2 现象

在 x86 服务器上运行了好几年，从来没出过问题。移植到 ARM64 服务器后，在高负载下，偶尔会出现：

- 网卡发出的包内容是错的（是上一轮的旧数据）；
- 网卡报告“描述符格式错误”；
- 极少数情况下，网卡通过 DMA 访问了一个非法地址，触发 IOMMU 错误。

### 6.3 分析

问题有两处：

1. **门铃用了 `writel_relaxed`**。在 ARM64 上，对描述符（普通内存）的三次写，和对 `TX_TAIL`（设备）的写之间没有屏障。网卡可能先收到门铃，然后去内存里读描述符，此时描述符还没被完全写好。
2. **`flags` 和其他字段之间没有 `dma_wmb()`**。即使门铃顺序对了，这块网卡在某些模式下还会自己轮询描述符的 `flags`。如果 `flags` 先于 `buf_addr` 被网卡看到，网卡会用一个旧的地址去 DMA。

在 x86 上，由于强内存序，写和写之间的顺序是天然保证的，所以这两个问题都不会暴露。

### 6.4 修复

```c
    d->buf_addr = buf;
    d->length   = len;
    dma_wmb();                          // 修复 2：先写好内容，再标记所有权
    d->flags    = DESC_OWNED_BY_HW;

    nic->tail = (nic->tail + 1) % RING_SIZE;
    writel(nic->tail, nic->regs + TX_TAIL);   // 修复 1：门铃用带屏障的 writel
```

两处改动，加起来不到 10 个字符。但如果不理解背后的原理，这种 bug 可能要花几周才能定位：它只在 ARM64 上出现，只在高负载时出现，而且一加调试打印就消失（因为打印函数里的各种操作“意外地”起到了屏障的作用）。

## 七、决策表：什么时候需要什么

| 场景 | 需要什么 | Linux 写法 |
|---|---|---|
| 连续访问同一个设备的多个寄存器 | 不需要额外屏障（Device 内存 `nR` 保证） | `readl_relaxed` / `writel_relaxed` 即可 |
| 先写普通内存（如 DMA 缓冲区），再写设备寄存器（如门铃） | 写屏障 | 用 `writel`（自带）；或 `wmb()` + `writel_relaxed` |
| 先读设备寄存器（如状态），再读普通内存（如 DMA 结果） | 读屏障 | 用 `readl`（自带）；或 `readl_relaxed` + `rmb()` |
| DMA 描述符多个字段之间，有“所有权”标志 | DMA 写屏障 | 字段 → `dma_wmb()` → 所有权标志 |
| 读设备写回的描述符，先看标志再读其他字段 | DMA 读屏障 | 标志 → `dma_rmb()` → 其他字段 |
| 需要确认写操作真的到达设备（关中断、复位后延时） | 读回同一设备 | `writel(...)` 后紧跟 `readl(...)` |
| 多 CPU 持锁访问同一设备 | 自旋锁已处理（Linux 5.2 起） | 正常使用 `spin_lock`/`spin_unlock` |
| 写合并（WC）映射的数据要确保发出 | 写屏障 | `wmb()` |

如果你记不住这张表，记住一句话就够了：**默认使用 `readl`/`writel`，它们在绝大多数情况下都是对的。**

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 顺序问题的来源 | CPU 乱序执行、写缓冲区、多核缓存、投递式写 |
| 强/弱内存序 | x86 强，几乎只允许读越过写；ARM64 弱，读写之间几乎可以任意重排 |
| Device `nR` 的范围 | 只保证同一设备的访问按序，不管和普通内存之间的顺序 |
| 投递式写（posted write） | 写被路上某环节接手就算完成，设备可能还没收到 |
| 读回刷新 | 对同一设备读一次，可以确保之前的写已经到达 |
| DMB | 保证屏障前后访问的观察顺序，开销最小 |
| DSB | 保证屏障前的访问真正完成，才执行后面任何指令 |
| ISB | 清空指令流水线，用于系统寄存器修改后 |
| `ish` / `osh` / `sy` | 屏障对 CPU 核之间 / CPU 与设备之间 / 整个系统生效 |
| `writel` / `readl` | 带屏障，保证与普通内存访问之间的顺序 |
| `_relaxed` 版本 | 不带屏障，只保证同一设备内的顺序，更快 |
| `wmb` / `rmb` / `mb` | 通用读/写/全屏障 |
| `dma_wmb` / `dma_rmb` | 只管一致性 DMA 内存里的读写顺序，开销更小 |
| `mmiowb` | 历史上用于持锁 MMIO 写的屏障，5.2 起由自旋锁承担 |
