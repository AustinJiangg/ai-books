# 第 12 篇｜虚拟机里的 MMIO 与 virtio-mmio

> **本篇目标**：理解虚拟机里的“设备”是怎么回事。读完本篇，你会明白客户机里的驱动程序明明在读写“设备寄存器”，背后却根本没有硬件，这是如何做到的；一次 MMIO 访问在虚拟化环境下要走过怎样的旅程、代价有多大、有哪些优化手段；以及专门为虚拟机设计的 virtio-mmio 设备长什么样。
>
> 本仓库的[《彻底搞懂 Firecracker》](../firecracker-intro/README.md)对 KVM 和 virtio 有更详细的讲解，本篇只从 MMIO 的角度串讲一遍，细节会给出链接。

---

## 一、一个“骗局”

### 1.1 客户机眼中的世界

在一台虚拟机里运行 Linux（我们把虚拟机里的系统叫**客户机**，把运行虚拟机的真实机器叫**宿主机**）。客户机的内核启动后，读取设备树，发现：

```
pl011@9000000 {
    compatible = "arm,pl011", "arm,primecell";
    reg = <0x00 0x09000000 0x00 0x1000>;
    ...
};
```

“哦，`0x09000000` 有一个 PL011 串口。”于是客户机内核加载串口驱动，`ioremap` 这段地址，然后像第 9 篇那样，用 `writel` 往数据寄存器里写字符。

字符确实出现在了宿主机的终端里。一切看起来和真实硬件一模一样。

但事实上，宿主机上**根本没有**一个物理串口被分配给这台虚拟机。客户机看到的那个“PL011”，是宿主机上的一个程序（虚拟机监控程序，比如 QEMU 或 Firecracker）**用软件假装出来的**。

### 1.2 问题

那么问题来了：客户机里的驱动执行了一条普通的写内存指令（第 1 篇说过，MMIO 就是普通的读写内存指令），目标地址是 `0x09000000`——

- 这条指令是由 CPU **直接执行**的（硬件虚拟化的核心就是让客户机代码直接在 CPU 上跑，而不是一条条翻译）；
- 宿主机上的软件怎么知道“客户机刚刚往串口写了一个字符”？
- 又怎么让这个字符最终出现在宿主机的终端里？

答案的关键在于：**让这次访问“失败”。**

## 二、原理：故意不映射

### 2.1 两阶段地址翻译回顾

在硬件虚拟化里，客户机的地址要经过**两次**翻译（详见《彻底搞懂 Firecracker》[第 3 篇](../firecracker-intro/03-hardware-virtualization-and-kvm.md)和[第 9 篇](../firecracker-intro/09-memory.md)）：

```
客户机程序的虚拟地址
      │  第一阶段：客户机自己的页表（客户机内核管理）
      ▼
客户机“物理”地址（ARM 叫 IPA，中间物理地址）
      │  第二阶段：stage-2 页表（宿主机的 KVM 管理）
      ▼
宿主机真正的物理地址
```

客户机以为自己看到的是物理地址，其实那只是一个“中间地址”。第二阶段的页表由宿主机控制，客户机看不到也改不了。（x86 上的同一机制叫 **EPT**，扩展页表。）

### 2.2 内存映射了，设备没映射

对于客户机的**内存**，KVM 会在 stage-2 页表里建立映射：客户机的“物理”地址 `0x40000000` 开始的那一段，映射到宿主机上某个进程（比如 Firecracker）mmap 出来的一大块内存（这块内存本身就是用匿名 mmap 分配的，参见[《mmap 从零讲透》第 12 篇](../mmap/12-real-world.md)）。客户机访问内存时，两次翻译都由硬件完成，**不需要宿主机软件参与**，速度和物理机几乎一样。

但对于客户机的**设备**地址（比如 `0x09000000`），KVM **故意不在 stage-2 页表里建立映射**。

于是，当客户机执行“往 `0x09000000` 写”这条指令时：

1. 第一阶段翻译：客户机页表把虚拟地址翻译成 `0x09000000`，没问题；
2. 第二阶段翻译：stage-2 页表里**找不到** `0x09000000` 的映射——**翻译失败**；
3. CPU 产生一个异常（ARM64 上叫 **stage-2 数据中止**），这个异常不会交给客户机，而是直接送到更高一级的特权层（EL2），也就是 KVM 所在的地方。

这就是虚拟化里经典的**“陷入-模拟”（trap-and-emulate）**：让客户机的敏感操作“陷入”宿主机，由宿主机软件来“模拟”这个操作的效果。

> 用一个比喻：客户机在一栋“样板房”里生活。卧室、客厅都是真的（内存映射了），可以随便用。但墙上的“电闸”其实是假的，后面没有线路（设备没映射）。客户机一扳电闸，就会触发一个藏起来的警报，管家（KVM/VMM）听到警报赶过来，问清楚“你想扳哪个闸、扳到什么位置”，然后替它在真实世界里把事情办了，再回来告诉它“好了”。

## 三、一次 MMIO 写的完整旅程

### 3.1 步骤

以客户机串口驱动执行 `writel('A', base + UARTDR)` 为例，看看在 ARM64 + KVM + Firecracker 的环境下，会发生什么：

```
 ┌───────────── 客户机（EL1/EL0）─────────────┐
 │ ① 执行 str w1, [x0]                        │
 │    x0 = 串口数据寄存器的虚拟地址             │
 │    w1 = 'A'                                │
 └──────────────────┬─────────────────────────┘
                    │ ② stage-2 翻译失败 → 数据中止，陷入 EL2
                    ▼
 ┌───────────── KVM（宿主机内核）──────────────┐
 │ ③ 读取异常信息寄存器：                       │
 │    - 出错的地址：0x09000000                 │
 │    - 是读还是写：写                          │
 │    - 访问宽度：32 位                        │
 │    - 数据在哪个寄存器：w1 → 值是 'A'          │
 │ ④ 这个地址是内核里模拟的设备吗？              │
 │    （比如虚拟中断控制器）→ 不是               │
 │ ⑤ 填写“退出原因”：KVM_EXIT_MMIO             │
 │    地址=0x09000000，写，4 字节，数据='A'      │
 │    返回用户态                                │
 └──────────────────┬─────────────────────────┘
                    ▼
 ┌──────── Firecracker（宿主机用户态进程）───────┐
 │ ⑥ vCPU 线程从 ioctl(KVM_RUN) 返回            │
 │    看到退出原因是 MMIO                        │
 │ ⑦ 在自己的“MMIO 总线”上查：                   │
 │    0x09000000 属于哪个模拟设备？→ 串口         │
 │ ⑧ 调用串口模拟代码的 write(offset=0, 'A')     │
 │    → 把 'A' 写到宿主机的标准输出               │
 │ ⑨ 再次调用 ioctl(KVM_RUN)，让客户机继续        │
 └──────────────────┬─────────────────────────┘
                    ▼
 ┌───────────── KVM ──────────────────────────┐
 │ ⑩ 把客户机的程序计数器往后挪一条指令            │
 │    返回客户机                                │
 └──────────────────┬─────────────────────────┘
                    ▼
 ┌───────────── 客户机 ────────────────────────┐
 │ ⑪ 继续执行下一条指令，                        │
 │    完全不知道刚才发生了什么                    │
 └────────────────────────────────────────────┘
```

如果是一次 MMIO **读**，流程类似，只是在第 ⑧ 步，模拟设备返回一个值（比如串口的 `UARTFR` 当前状态），Firecracker 把它填进退出信息里；KVM 在第 ⑩ 步把这个值写进客户机的目标寄存器，再把程序计数器往后挪。

### 3.2 KVM 怎么知道这次访问的细节

第 ③ 步很关键：KVM 是怎么知道“这次访问是写、宽度 32 位、数据在 w1 寄存器”的？

在 ARM64 上，CPU 在产生数据中止异常时，会把这些信息记录在一个叫 **ESR**（异常综合寄存器）的系统寄存器里。对于“简单”的读写指令，ESR 里有一个 **ISV**（指令综合信息有效）位被置 1，同时记录了：

- **访问宽度**（1、2、4 还是 8 字节）；
- **读还是写**；
- **数据寄存器编号**（是 x0～x30 中的哪一个）。

出错的地址则记录在另外的寄存器里。KVM 读出这些信息，就能完整还原这次访问，**不需要去解析客户机的指令**。

但如果客户机用的是一条“复杂”的指令——比如一次读写两个寄存器的 `ldp`/`stp`，或者带有“访问后自动修改地址寄存器”的写回寻址方式——CPU 就**不提供**这些信息（ISV 为 0）。这时 KVM 就很难处理这次 MMIO 访问了，在 ARM64 上通常会报错。

这就是第 4 篇提到的那个细节：**Linux 内核在 ARM64 上用内联汇编实现 `readl`/`writel`，强制生成单条、简单寻址的读写指令**——其中一个重要原因，就是保证在虚拟机里运行时，每一次 MMIO 访问都能被 KVM 正确地解读。如果驱动绕过访问函数、直接用 `memcpy` 访问设备内存，编译器可能生成 `ldp`/`stp`，在物理机上没问题，一放进虚拟机就出错。

（在 x86 上，硬件不提供这么方便的信息，KVM 必须**自己去读客户机的指令并解码**，弄清楚这是一条什么指令、操作数是什么。KVM 的 x86 部分有一个专门的“指令模拟器”来做这件事，复杂得多。）

## 四、代价与优化

### 4.1 一次 MMIO 退出有多贵

回顾上面的流程，一次 MMIO 访问要经历：客户机 → KVM（一次特权级切换） → Firecracker（一次从内核返回用户态） → 设备模拟 → KVM（一次系统调用） → 客户机（又一次特权级切换）。

在物理机上，一次 MMIO 写只需要几十到几百纳秒。在虚拟机里，同样一次写，**往返一趟通常要几微秒**——慢了一到两个数量级。

这对虚拟设备的设计提出了一个重要原则：

> **在虚拟机里，MMIO 访问是非常昂贵的。虚拟设备应该被设计成尽量少碰寄存器。**

想象一下，如果客户机用第 3 篇那种方式，通过轮询 `UARTFR` + 写 `UARTDR` 来一个字一个字地输出，每个字符要两次 MMIO 退出。输出一屏日志，就是成千上万次退出。这就是为什么虚拟机里的串口输出通常很慢。

对于网卡、磁盘这些高流量设备，如果完全模拟真实硬件（比如模拟一块 Intel 网卡，它的驱动每发一个包要访问好多次寄存器），性能会惨不忍睹。这就催生了专门为虚拟机设计的设备——virtio（第五节）。

### 4.2 优化一：在内核里处理

上面流程中，最贵的部分是从 KVM “退出到用户态” 再回来。如果某个设备在 KVM（内核）里就能直接模拟，就能省掉这一步。

最典型的例子是**中断控制器**：ARM64 的 GIC（第 7 篇）访问非常频繁，所以 KVM 在内核里实现了一个虚拟 GIC（**vGIC**）。客户机访问 GIC 分发器的 MMIO 寄存器时，在第 ④ 步就被 KVM 直接处理掉了，不用退到用户态。现代 ARM64 CPU 还对 GIC 的 CPU 接口提供了硬件虚拟化支持，连陷入都省了。

### 4.3 优化二：ioeventfd——门铃只响一下

第 8 篇讲过，高性能设备的热点路径上，通常只有一种 MMIO 访问：**按门铃**。而按门铃有一个特点：它是一次**写**，写的值通常不重要（或者只是一个队列编号），设备不需要立即响应，**客户机也不需要等待结果**。

**ioeventfd** 就是针对这个特点的优化：

1. VMM 事先告诉 KVM：“地址 X 是一个门铃，如果客户机往这里写，你不用退出到我这里，只要**通知一下**某个 eventfd 就行。”
2. 客户机按门铃 → 陷入 KVM → KVM 发现这是一个注册过的门铃地址 → 触发对应的 eventfd → **立刻返回客户机**。
3. VMM 的另一个线程（不是 vCPU 线程）在等待这个 eventfd，被唤醒后去处理队列里的新请求。

```
没有 ioeventfd：  客户机 → KVM → VMM（vCPU 线程处理请求）→ KVM → 客户机
                                       ↑ 客户机在这里干等

有 ioeventfd：    客户机 → KVM → 客户机（立刻回去干别的）
                           │
                           └→ 触发 eventfd → VMM 的 I/O 线程异步处理
```

客户机的 vCPU 不再需要等待设备处理完请求，只需要付出一次“陷入 KVM 再回来”的代价。

对应地，**irqfd** 是反方向的优化：VMM 处理完请求后，写一个 eventfd，KVM 直接把中断注入客户机，不需要 VMM 再调用一次 ioctl。

这两个机制在《彻底搞懂 Firecracker》[第 10 篇](../firecracker-intro/10-virtio.md)里有更详细的讲解。

### 4.4 优化三：设备直通——干脆不模拟

最极端的优化是：**不模拟，直接把一个真实的物理设备交给虚拟机。**

这就是**设备直通（device passthrough）**，通常借助上一篇讲的 **VFIO** 来实现：

1. 宿主机把一块物理网卡（比如一个 PCIe 设备）绑定到 `vfio-pci` 驱动；
2. VMM 通过 VFIO **mmap 这块网卡的 BAR**（上一篇第五节的第 ⑤ 步），得到一个宿主机虚拟地址；
3. VMM 再通过 KVM，把这段宿主机虚拟地址**映射进客户机的 stage-2 页表**，对应客户机“物理”地址空间里的某个位置（同时设成 Device 属性）。

这样，客户机访问这块网卡的寄存器时，stage-2 翻译**成功**了，直接指向真实设备的 MMIO 地址。**没有陷入、没有退出、没有模拟**，客户机的驱动直接操作真实硬件，性能和物理机几乎一样。

那 DMA 呢？客户机驱动告诉网卡的 DMA 地址，是客户机的“物理”地址，不是宿主机的物理地址。这时 **IOMMU**（第 8 篇）就派上用场了：VMM 通过 VFIO 把整个客户机内存注册到 IOMMU，让 IOMMU 把客户机的“物理”地址翻译成宿主机的真实物理地址。同时，IOMMU 保证这块网卡**只能**访问这台虚拟机的内存，不能越界。

设备直通的代价是：这块物理设备被这台虚拟机**独占**了。为了让一块物理设备能同时服务多台虚拟机，PCIe 还有一个叫 **SR-IOV** 的扩展：一块物理网卡可以“分身”成几十个虚拟功能（VF），每个 VF 有自己独立的 BAR 和配置空间，可以分别直通给不同的虚拟机。

### 4.5 小结

| 方式 | MMIO 访问的处理位置 | 每次访问的代价 | 例子 |
|---|---|---|---|
| 用户态模拟 | VMM 进程 | 最高（微秒级） | Firecracker 的串口 |
| 内核模拟 | KVM | 中等 | vGIC |
| ioeventfd | KVM 只通知，不等待 | 较低 | virtio 的门铃 |
| 设备直通 | 不陷入，直达硬件 | 最低（和物理机一样） | VFIO 直通网卡、GPU |

## 五、virtio-mmio：为虚拟机设计的 MMIO 设备

### 5.1 为什么需要“半虚拟化”设备

如果虚拟机要模拟一块真实存在的网卡（比如某款 Intel 千兆网卡），有两个问题：

1. **太慢**：真实网卡的驱动是为物理硬件设计的，它访问寄存器毫不吝啬（反正在物理机上 MMIO 只要几百纳秒）。在虚拟机里，每次访问都是一次昂贵的退出。
2. **太复杂**：要模拟一块真实网卡的全部行为（包括各种奇怪的硬件 bug），代码量巨大，而且每一行模拟代码都是一个潜在的安全漏洞（恶意客户机可以构造奇怪的寄存器访问来攻击模拟代码）。

解决思路是：**不模拟任何真实的硬件，而是专门为虚拟机设计一种“虚构”的设备。** 客户机知道自己在虚拟机里，安装专门的驱动来配合。这种方式叫**半虚拟化（paravirtualization）**。

**virtio** 就是一套这样的标准：它定义了虚拟网卡、虚拟磁盘、虚拟控制台等一系列设备的接口。它的设计目标正是本书前几篇讲的那些原则：

- **MMIO 访问越少越好**：只在初始化时访问寄存器，数据路径上只有“按门铃”和“清中断”。
- **数据全部走共享内存**：用描述符环（第 8 篇）在客户机内存里交换数据。由于 VMM 本身就能直接访问客户机的全部内存（它就是那块 mmap 出来的内存的主人），所以“DMA”在这里就是 VMM 直接读写那块内存，不需要任何拷贝。

virtio 设备需要一种方式让客户机发现它、和它通信，这叫**传输层（transport）**。最常见的两种传输层是 **virtio-pci**（把 virtio 设备伪装成一个 PCI 设备）和 **virtio-mmio**（把 virtio 设备放在一段固定的 MMIO 地址上）。

### 5.2 virtio-mmio 的寄存器布局

virtio-mmio 设备在客户机的物理地址空间里占一个小窗口（Firecracker 中每个设备 4KB），里面的寄存器由 virtio 规范定义。主要的寄存器有：

| 偏移量 | 寄存器 | 方向 | 作用 |
|---|---|---|---|
| `0x000` | MagicValue | 读 | 固定值 `0x74726976`，按小端序就是 ASCII 字符串 “virt” |
| `0x004` | Version | 读 | 版本号，2 表示现代 virtio-mmio |
| `0x008` | DeviceID | 读 | 设备类型：1 = 网卡，2 = 块设备…… |
| `0x010` | DeviceFeatures | 读 | 设备支持的特性 |
| `0x020` | DriverFeatures | 写 | 驱动接受的特性 |
| `0x030` | QueueSel | 写 | 选择要配置的队列 |
| `0x038` | QueueNum | 写 | 队列长度 |
| `0x044` | QueueReady | 读写 | 队列就绪 |
| `0x050` | **QueueNotify** | 写 | **门铃**：写入队列编号，通知设备该队列有新请求 |
| `0x060` | InterruptStatus | 读 | 中断原因 |
| `0x064` | InterruptACK | 写 | 确认中断（清除） |
| `0x070` | Status | 读写 | 设备状态，初始化握手用 |
| `0x080`～`0x0A4` | Queue 地址 | 写 | 描述符表、可用环、已用环在客户机内存中的地址 |
| `0x100` 起 | Config | 读写 | 设备专属配置，比如网卡的 MAC 地址、磁盘容量 |

看到这张表，你应该能认出前面几篇讲过的几乎所有概念：

- **MagicValue、Version、DeviceID**：只读的身份寄存器，就像第 9 篇演示驱动里的 ID 寄存器、第 10 篇 PCI 配置空间里的 Vendor ID/Device ID。驱动先读它们，确认“这里真的有一个 virtio 设备”；
- **Status**：控制/状态寄存器（第 3 篇）；
- **Queue 地址寄存器**：告诉设备描述符环在内存哪里，和第 10 篇 NVMe 的 ASQ/ACQ 一样（第 8 篇）；
- **QueueNotify**：**门铃寄存器**（第 8 篇），也是 ioeventfd 优化的对象；
- **InterruptStatus + InterruptACK**：读中断原因，再写确认清除（第 7 篇）。

### 5.3 初始化握手

驱动通过一系列对 Status 寄存器的写入，和设备完成初始化：

```
驱动                                              设备
 │ 写 Status = 0                                → 复位
 │ 写 Status |= ACKNOWLEDGE (1)                 → “我发现你了”
 │ 写 Status |= DRIVER (2)                      → “我知道怎么驱动你”
 │ 读 DeviceFeatures                            ← 设备支持的特性
 │ 写 DriverFeatures                            → 驱动接受的特性子集
 │ 写 Status |= FEATURES_OK (8)                 → “特性协商完成”
 │ 读 Status，确认 FEATURES_OK 还在               ← 设备同意了
 │ 配置每个队列：QueueSel、QueueNum、三个地址、QueueReady
 │ 写 Status |= DRIVER_OK (4)                   → “一切就绪，开工”
```

这一段初始化要做几十次 MMIO 访问，每次都是一次退出。但它**只在启动时做一次**，所以无所谓。

### 5.4 数据路径：只有门铃和中断

初始化完成后，以客户机发送一个网络包为例：

```
① 客户机驱动把网络包放进内存，填写描述符，更新可用环    （普通内存写，不退出）
② 客户机写 QueueNotify = 发送队列编号                   （MMIO 写 → ioeventfd，很快返回）
③ VMM 的 I/O 线程被唤醒，从客户机内存里读描述符和数据      （VMM 直接读那块 mmap 的内存）
④ VMM 把包发到宿主机的网络（比如写一个 tap 设备）
⑤ VMM 更新客户机内存里的已用环                          （VMM 直接写内存）
⑥ VMM 通过 irqfd 给客户机注入中断
⑦ 客户机中断处理：读 InterruptStatus，写 InterruptACK    （两次 MMIO，两次退出）
   读已用环，回收缓冲区                                  （普通内存读，不退出）
```

和第 8 篇的网卡发包流程对比，几乎是一模一样的结构。区别只在于：“设备”是 VMM 里的一段软件，“DMA”是 VMM 直接读写客户机的内存。

整个数据路径上，MMIO 访问只有门铃一次、中断处理两次。而且 virtio 还有“通知抑制”等机制，在流量大时可以进一步减少门铃和中断的次数。

更多细节（virtqueue 的结构、批处理、事件抑制、Firecracker 如何防御恶意客户机）请参阅《彻底搞懂 Firecracker》[第 10 篇](../firecracker-intro/10-virtio.md)。

### 5.5 客户机怎么发现 virtio-mmio 设备

virtio-mmio 设备的地址是固定的，没有 PCI 那样的枚举机制（第 10 篇），所以需要用第 2 篇讲的方法告诉客户机：

- **设备树**（ARM64）：VMM 生成一个设备树，里面有类似这样的节点：

  ```
  virtio_mmio@a000000 {
      compatible = "virtio,mmio";
      reg = <0x0 0x0a000000 0x0 0x200>;
      interrupts = <0 16 1>;
  };
  ```

  客户机内核里的 `virtio_mmio` 驱动匹配到 `compatible = "virtio,mmio"`，就去读这个地址的 MagicValue 和 DeviceID，然后交给对应的驱动（比如 `virtio_net`）。

- **内核命令行参数**（常见于 x86 上的 Firecracker）：

  ```
  virtio_mmio.device=4K@0xd0000000:5
  ```

  意思是：在物理地址 `0xd0000000` 有一个大小 4KB 的 virtio-mmio 设备，使用 5 号中断。

还记得第 2 篇 QEMU `virt` 机器的地址地图吗？`0x0A00_0000` 开始的 32 个 virtio-mmio 槽位，就是为此预留的。

### 5.6 virtio-mmio vs. virtio-pci

| | virtio-mmio | virtio-pci |
|---|---|---|
| 设备发现 | 设备树 / 命令行，地址固定 | PCI 枚举，地址动态分配 |
| 实现复杂度 | 简单：只需模拟一小段寄存器 | 较复杂：要模拟 PCI 配置空间、BAR、能力链表 |
| 启动速度 | 快：不需要扫描 PCI 总线 | 较慢：要枚举 |
| 中断 | 通常每个设备一条中断线 | 支持 MSI-X，每个队列可以有独立中断 |
| 多队列性能 | 受限于单个中断 | 好：中断可以分散到多个 CPU 核 |
| 热插拔 | 不支持 | 支持（PCI 热插拔） |
| 适用场景 | 轻量级虚拟机、嵌入式 | 通用虚拟机 |

**Firecracker** 的设计目标是“极简、快速启动、安全”，所以它最初只支持 virtio-mmio：设备数量少、启动时不用枚举、要模拟的代码量最小（攻击面也最小）。较新的版本（v1.13 起）也加入了可选的 virtio-pci 支持，用来满足需要更多队列、更好的中断分发的场景（详见《彻底搞懂 Firecracker》[第 10 篇](../firecracker-intro/10-virtio.md)）。

## 六、把视角拉远

回顾这一篇，你会发现虚拟化并没有发明什么新的 MMIO 机制，它只是**巧妙地利用了**前面几篇讲过的东西：

| 虚拟化中的做法 | 依赖的基础知识 |
|---|---|
| 设备地址在 stage-2 页表里不映射 | 第 2 篇：虚拟地址经页表翻译成物理地址 |
| 陷入后 KVM 解读访问的地址、宽度、数据 | 第 4 篇：访问函数用简单指令，保证可解读 |
| 直通设备在 stage-2 里映射成 Device 属性 | 第 5 篇：内存属性写在页表里 |
| ioeventfd 只优化门铃写 | 第 8 篇：热点路径上只有门铃 |
| virtio 用描述符环在共享内存里传数据 | 第 8 篇：控制走 MMIO，数据走 DMA |
| 中断用 irqfd 注入 | 第 7 篇：中断机制 |
| 直通设备的 BAR 通过 VFIO mmap | 第 10、11 篇：BAR 与用户态 MMIO |
| 直通设备的 DMA 靠 IOMMU 隔离 | 第 8 篇：IOMMU |

**理解了物理机上的 MMIO，就理解了虚拟机里的 MMIO。** 虚拟化的全部魔法，就是在“这次访问要不要陷入”和“陷入后谁来处理”这两个问题上做文章。

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 客户机 / 宿主机 | 虚拟机里的系统 / 运行虚拟机的真实机器 |
| 两阶段翻译 | 客户机页表 + stage-2 页表（x86 叫 EPT） |
| 陷入-模拟 | 设备地址在 stage-2 里不映射，访问时陷入宿主机，由软件模拟 |
| ESR 与 ISV | ARM64 在异常时记录访问宽度、方向、寄存器；复杂指令不提供（ISV=0） |
| `KVM_EXIT_MMIO` | KVM 把 MMIO 访问交给用户态 VMM 处理的退出原因 |
| MMIO 退出代价 | 往返一次几微秒，比物理机慢一到两个数量级 |
| vGIC | KVM 在内核里模拟中断控制器，省掉退出到用户态 |
| ioeventfd / irqfd | 门铃写只通知不等待 / 直接注入中断 |
| 设备直通 | 把真实设备的 BAR 映射进 stage-2，不陷入；DMA 由 IOMMU 隔离 |
| SR-IOV | 一块物理设备分身成多个虚拟功能，分别直通 |
| 半虚拟化 / virtio | 专为虚拟机设计的设备，尽量少碰 MMIO，数据走共享内存 |
| virtio-mmio | virtio 的 MMIO 传输层：固定地址、MagicValue “virt”、QueueNotify 门铃 |
| virtio-pci | virtio 的 PCI 传输层：枚举、MSI-X、热插拔 |
