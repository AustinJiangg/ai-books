# 第 7 篇｜设备怎么“回话”：轮询与中断

> **本篇目标**：前面几篇讲的都是 CPU 主动去读写设备。本篇换个方向：设备有事要告诉 CPU 时怎么办？读完本篇，你会理解轮询和中断这两种方式各自的优缺点，知道 ARM64 的中断控制器 GIC 是怎么工作的、中断处理程序里要做哪些 MMIO 操作、为什么清除中断晚了会造成“中断风暴”，以及为什么说现代 PCIe 设备的中断“本质上就是一次 MMIO 写”。

---

## 一、设备有话要说

### 1.1 问题

到目前为止，MMIO 的通信方向都是 **CPU → 设备**：CPU 写控制寄存器下命令，CPU 读状态寄存器查状态。设备永远是被动的一方。

但很多时候，设备有事要**主动**告诉 CPU：

- 串口收到了一个字节，需要 CPU 来取走，否则接收 FIFO 满了就会丢数据；
- 网卡收到了一个网络包；
- 硬盘完成了一次读写操作；
- 定时器到点了；
- 设备出错了。

设备不能主动“调用”CPU 上的函数，那它怎么让 CPU 知道“我这边有情况”？

有两种基本办法，用一个生活中的例子来说明。

### 1.2 等快递的两种方式

假设你在等一个快递。

**方式一：每隔几分钟就跑到楼下看一眼。** 快递到了你马上就知道，但你什么别的事也干不了，大部分时间都在白跑。

**方式二：在家干自己的事，快递到了快递员按门铃。** 你不用白跑，听到门铃再去取。缺点是：你得停下手头的事去开门，而且如果快递员每隔一分钟就来送一个小包裹，你一整天都在开门。

方式一叫**轮询（polling）**，方式二叫**中断（interrupt）**。

---

## 二、轮询：一直问“好了没”

### 2.1 怎么做

轮询就是 CPU 反复读设备的状态寄存器，直到状态变成自己想要的值。第 3 篇的串口输出函数就是轮询：

```c
while (readl(uart + UARTFR) & FR_TXFF) {
    // 发送 FIFO 满了，继续问
}
writel(c, uart + UARTDR);
```

接收数据也可以用轮询：

```c
while (readl(uart + UARTFR) & FR_RXFE) {
    // 接收 FIFO 是空的，继续问
}
c = readl(uart + UARTDR);
```

### 2.2 缺点

轮询最大的问题是**浪费 CPU**。

- 每次轮询都是一次 MMIO 读，而 MMIO 读很慢（第 2 篇说过，可能要几百纳秒）。
- 如果设备很久才有响应（比如等用户在串口上敲键盘，可能要等几分钟），CPU 就在这几分钟里一直空转，什么别的事也干不了。
- 在有操作系统的情况下，一个进程占着 CPU 空转，其他进程就得等着。

### 2.3 什么时候轮询反而更好

不过，轮询并不总是坏的。在以下几种情况下，轮询反而是更好的选择：

1. **等待时间极短且可预期**。比如往发送 FIFO 写一个字节，FIFO 只是暂时满了，几微秒就会有空位。为这几微秒搞一套中断机制，开销反而更大。
2. **系统还没准备好中断**。比如操作系统启动的最早期，中断系统还没初始化，内核的早期调试输出（`earlycon`）就是用轮询方式往串口写字符。
3. **对延迟极其敏感、而且事件非常频繁**。这是现代高性能 I/O 的一个重要趋势，第五节会详细讲。

## 三、中断：设备按门铃

### 3.1 基本原理

中断的思路是：**设备有事时，通过一根专门的信号线（或者别的方式）通知 CPU。CPU 收到信号后，暂停当前正在执行的程序，跳到一段专门的代码（中断处理程序）去处理，处理完再回来继续执行原来的程序。**

```
CPU 正在执行：  指令1 → 指令2 → 指令3 ┐
                                      │  ← 设备发出中断信号
                                      ▼
                           保存当前状态
                           跳转到中断处理程序
                             ├─ 读设备状态：发生了什么？
                             ├─ 处理（比如取走收到的数据）
                             └─ 告诉设备：我处理完了
                           恢复之前的状态
                                      │
                                      ▼
CPU 继续执行：  指令4 → 指令5 → ...
```

被中断的程序完全感觉不到这个过程——对它来说，就好像指令 3 和指令 4 之间什么都没发生，只是时间过得稍微久了一点。

### 3.2 中断的好处

- **CPU 不用空等**。在设备没有事情的时候，CPU 可以去执行别的程序，或者进入低功耗状态省电。
- **响应及时**。设备一有事，CPU 马上就知道，而不是要等到下一次轮询。

### 3.3 中断的代价

- **每次中断都有固定开销**：保存和恢复 CPU 状态、跳转、清空流水线、可能的缓存污染……一次中断的总开销通常在**微秒量级**。
- **打断了正在做的事**，影响其他程序的执行效率。

如果设备每秒产生几百个中断，这点开销完全可以忽略。但如果是一块万兆网卡，每秒收到几百万个包，每个包都触发一次中断，CPU 就会把全部时间花在处理中断上，什么正事都干不了。这种情况叫**中断活锁（interrupt livelock）**。第五节会讲怎么应对。

## 四、中断控制器：门铃的“总机”

### 4.1 为什么需要中断控制器

一台电脑里有几十上百个设备，每个都可能发中断；同时又有好几个 CPU 核，每个都可以处理中断。如果每个设备都直接拉一根线连到每个 CPU 核上，线就太多了，而且没法灵活配置。

所以中间需要一个“总机”：所有设备的中断信号都先送到它这里，由它决定：

- 这个中断现在**要不要**送给 CPU（有没有被屏蔽）；
- 送给**哪个** CPU 核；
- 好几个中断同时到达时，**先送哪个**（优先级）。

这个总机就是**中断控制器**。x86 上叫 **APIC**（高级可编程中断控制器），ARM 上叫 **GIC**（Generic Interrupt Controller，通用中断控制器）。

### 4.2 GIC 的结构

以 ARM64 上最常见的 **GICv3** 为例，它由这几部分组成：

```
   设备 A   设备 B   设备 C  ...          （各种外设的中断信号线）
     │        │        │
     ▼        ▼        ▼
 ┌──────────────────────────────┐
 │    Distributor（分发器）       │   全局唯一。管理所有“共享外设中断”：
 │    GICD，MMIO 寄存器          │   开关、优先级、送给哪个 CPU
 └──────┬──────────────┬────────┘
        ▼              ▼
 ┌─────────────┐ ┌─────────────┐
 │Redistributor│ │Redistributor│      每个 CPU 核一个。管理该核私有的中断，
 │  GICR（核0） │ │  GICR（核1） │      MMIO 寄存器
 └──────┬──────┘ └──────┬──────┘
        ▼              ▼
 ┌─────────────┐ ┌─────────────┐
 │CPU Interface│ │CPU Interface│      每个 CPU 核一个。CPU 用它来“接电话”
 │ （系统寄存器）│ │ （系统寄存器）│      和“挂电话”
 └──────┬──────┘ └──────┬──────┘
        ▼              ▼
      CPU 核 0        CPU 核 1
```

这里有一个有意思的事实：**中断控制器本身，也是通过 MMIO 来配置的**。回顾第 2 篇 QEMU `virt` 的地址地图：

```
0x0800_0000   GIC 分发器（GICD）
0x080A_0000   GIC 重分发器（GICR）
```

操作系统启动时，要通过 MMIO 写 GICD 和 GICR 的寄存器，来打开或关闭各个中断、设置优先级、指定目标 CPU。

（GICv3 的 CPU Interface 部分改用了 CPU 的系统寄存器来访问，而不是 MMIO——因为每次中断都要访问它，用系统寄存器比 MMIO 快得多。在更老的 GICv2 里，CPU Interface 也是 MMIO 寄存器，叫 GICC，地址在 `0x0801_0000`。）

### 4.3 中断号

GIC 给每个中断源分配一个编号，叫**中断号（INTID）**。不同范围的编号代表不同类型的中断：

| 范围 | 类型 | 说明 |
|---|---|---|
| 0～15 | SGI（软件生成中断） | 一个 CPU 核用来“戳”另一个核，比如通知它调度 |
| 16～31 | PPI（私有外设中断） | 每个核私有，比如每个核自己的定时器 |
| 32～1019 | SPI（共享外设中断） | 外部设备的中断，比如串口、网卡 |
| 8192 及以上 | LPI（特定局部外设中断） | 基于消息的中断，用于 PCIe 的 MSI（见第七节） |

回顾第 2 篇设备树里串口的那一行：

```
interrupts = <0x00 0x01 0x04>;
```

三个数分别表示：`0` = 这是一个 SPI；`1` = SPI 编号 1（对应 INTID 32 + 1 = 33）；`4` = 高电平触发（第六节讲触发方式）。操作系统读到这一行，就知道串口的中断会以 33 号的身份送到 GIC。

## 五、一次中断的完整旅程

现在把所有部件串起来。以“串口收到一个字节”为例：

### 5.1 步骤

```
① 串口收到一个字节，放进接收 FIFO
② 串口检查自己的中断屏蔽寄存器 UARTIMSC：
   “接收中断”是允许的 → 把中断信号线拉高
③ GIC 分发器收到 33 号中断，检查：已启用、优先级够高、目标是 CPU 0
   → 转交给 CPU 0 的重分发器和 CPU Interface
④ CPU 0 收到 IRQ 信号，暂停当前程序，跳到内核的异常处理入口
⑤ 内核读 CPU Interface 的“确认”寄存器：得知是 33 号中断
   （这一步同时告诉 GIC：33 号我接了，正在处理）
⑥ 内核找到 33 号中断对应的处理函数：串口驱动的中断处理程序
⑦ 串口驱动：
   - MMIO 读 UARTMIS：看看是哪种事件（接收？发送？出错？）
   - MMIO 读 UARTDR：取走字节（可能有多个，循环读到 FIFO 空）
   - MMIO 写 UARTICR：清除串口的中断状态
   → 串口把中断信号线拉低
⑧ 内核写 CPU Interface 的“结束”寄存器：告诉 GIC 33 号处理完了
⑨ CPU 0 恢复之前的程序，继续执行
```

### 5.2 中断处理程序里的 MMIO

步骤 ⑦ 是驱动程序员要写的部分。用 Linux 风格的代码（简化版）表示：

```c
static irqreturn_t uart_irq_handler(int irq, void *dev_id) {
    struct my_uart *u = dev_id;
    u32 status = readl(u->base + UARTMIS);    // 发生了什么？

    if (status == 0)
        return IRQ_NONE;                       // 不是我的中断

    if (status & INT_RX) {
        while (!(readl(u->base + UARTFR) & FR_RXFE)) {
            u8 c = readl(u->base + UARTDR);    // 取走一个字节
            push_to_tty(u, c);
        }
    }

    writel(status, u->base + UARTICR);         // 清除已处理的中断
    return IRQ_HANDLED;
}
```

几个值得注意的地方：

- **先读状态**：一个设备可能有多种中断原因共用一根中断线，必须先读状态寄存器，搞清楚是哪一种。
- **`IRQ_NONE`**：多个设备可能共享同一个中断号（在老式 PCI 上很常见）。如果读出来发现自己的设备没有中断，就返回 `IRQ_NONE`，让内核去问下一个共享的设备。
- **清除中断**：处理完之后，必须告诉**设备**“这个中断我处理过了”，设备才会放下中断信号。这里用的是 PL011 的只写清除寄存器 `UARTICR`，写 1 清除对应位（第 3 篇讲过）。
- **只清你处理过的**：写入 `status` 而不是全 1，避免误清在处理期间新发生的其他中断。

### 5.3 两层“确认”

注意在这个流程里有**两层确认**：

1. **对设备确认**（步骤 ⑦ 的写 `UARTICR`）：告诉设备“你的事我知道了”，设备放下中断信号。
2. **对中断控制器确认**（步骤 ⑤ 和 ⑧）：告诉 GIC“这个中断我接了 / 处理完了”。

第一层由**设备驱动**负责，第二层由**内核的中断子系统**负责。驱动程序员只需要操心第一层。

## 六、触发方式与中断风暴

### 6.1 电平触发和边沿触发

设备通过中断信号线通知 GIC 的方式有两种：

**电平触发（level-triggered）**：只要设备有未处理的中断，信号线就**一直保持**在“有效”电平（比如高电平）。GIC 只要看到线是高的，就认为中断还在。

**边沿触发（edge-triggered）**：设备在发生事件时，信号线**跳变一下**（比如从低到高）。GIC 只在看到跳变的那一瞬间记录一次中断。

用门铃来比喻：

- **电平触发**：快递员**一直按着门铃不松手**，直到你开门签收为止。
- **边沿触发**：快递员**按一下就走了**。你要是没听见，这个快递就错过了。

| | 电平触发 | 边沿触发 |
|---|---|---|
| 优点 | 不会丢中断：只要没处理完，信号一直在 | 不需要及时清除，不会重复触发 |
| 缺点 | 必须在设备上清除，否则会一直触发 | 可能丢中断：跳变时如果没被记录就错过了 |
| 常见于 | 大部分外设（串口、老式 PCI） | 定时器、部分 GPIO |

### 6.2 中断风暴

电平触发有一个经典陷阱：**如果驱动程序没有正确清除设备上的中断，就会形成中断风暴（interrupt storm）**。

过程是这样的：

1. 设备拉高中断线；
2. CPU 进入中断处理程序；
3. 驱动程序**忘了**写清除寄存器（或者写错了位）；
4. 中断处理程序返回，告诉 GIC“处理完了”；
5. GIC 一看，中断线**还是高的**——又来一个中断！
6. CPU 立刻又进入中断处理程序……

CPU 陷入无穷无尽的中断循环，没有任何机会去执行别的代码，整个系统看起来就像卡死了一样。

Linux 内核有一个防护机制：如果某个中断号在短时间内触发了大量次数（比如十万次），而所有处理函数都返回 `IRQ_NONE`（“不是我的”），内核会判断这个中断出了问题，打印一条 `irq NN: nobody cared` 的警告，然后**禁用这个中断号**。这样系统能活下来，但这个设备就不能用了。

### 6.3 清晚了也会出问题

还有一种更微妙的情况：驱动程序**确实**清除了中断，但**清得太晚**——或者说，清除操作还在路上。

回顾第 6 篇讲的投递式写：`writel(status, u->base + UARTICR)` 返回时，清除命令可能还没到达设备。如果中断处理程序紧接着就返回了，内核告诉 GIC“处理完了”，而此时设备那边的中断线**还没来得及放下**，GIC 就会再次触发这个中断。

第二次进入中断处理程序时，清除命令可能已经到了，设备状态是干净的——读状态寄存器得到 0，返回 `IRQ_NONE`。这叫做**伪中断（spurious interrupt）**。偶尔一两次没关系，但如果每次都这样，中断处理的开销就翻了一倍，而且会累积“nobody cared”的计数。

解决办法就是第 6 篇讲过的**读回刷新**：

```c
writel(status, u->base + UARTICR);    // 清除中断
readl(u->base + UARTICR);             // 读回，确保清除命令已到达设备
return IRQ_HANDLED;
```

（对于只写寄存器，读回同一设备上任何一个读无副作用的寄存器都可以。）

### 6.4 中断屏蔽

除了清除中断，设备通常还有一个**中断屏蔽寄存器**（比如 PL011 的 `UARTIMSC`）。它控制哪些事件允许产生中断：

- 屏蔽位为 0：这种事件发生时，只会在状态寄存器里记一笔，**不会**拉中断线；
- 屏蔽位为 1：这种事件发生时，会拉中断线。

驱动程序可以灵活地打开或关闭某些中断。比如：只有在发送缓冲区里有数据要发时，才打开“发送 FIFO 有空位”中断；数据发完了就关掉它，否则 FIFO 一直是空的，中断就会一直触发。

## 七、MSI：中断就是一次 MMIO 写

### 7.1 中断线的局限

前面讲的中断都依赖一根物理的**中断信号线**。在 SoC 内部，这没什么问题。但对于 PCI/PCIe 设备，中断线就成了一个大麻烦：

- PCIe 是一条高速串行链路，**根本没有单独的中断线**。老式 PCI 只给每个插槽分配了 4 根中断线（INTA～INTD），几十个设备只能共享这几根线，处理起来又慢又麻烦（每次都要挨个问“是不是你”）。
- 一块现代网卡可能有几十上百个收发队列，每个队列都希望有自己独立的中断，好分给不同的 CPU 核处理。4 根线远远不够。

### 7.2 MSI 的思路

PCI 规范后来引入了一种巧妙的方案：**MSI（Message Signaled Interrupts，消息信号中断）**。

它的思路是：**设备不再拉中断线，而是往一个特定的内存地址写一个特定的值。** 这个地址不是普通内存，而是中断控制器的一个 MMIO 寄存器。中断控制器收到这次写，就知道“某个设备发了一个中断”，再根据写入的值判断是哪个中断。

```
         传统中断：                           MSI：

  设备 ──── 中断线 ────→ 中断控制器       设备 ── PCIe 写操作 ──→ 中断控制器的
                                                 地址 = X               MMIO 寄存器
                                                 数据 = 中断号 N
```

换句话说：**以前是 CPU 用 MMIO 写设备；现在是设备用一次写操作（DMA 写）去写中断控制器的 MMIO 寄存器。** 方向反过来了，但机制是一样的——都是“往某个地址写一个值”。

在 x86 上，这个特殊地址位于 `0xFEE0_0000` 附近，正好对着 CPU 的本地 APIC（第 2 篇 x86 的 `/proc/iomem` 里能看到它）。在 ARM64 上，MSI 通常写到 GICv3 的一个叫 **ITS**（Interrupt Translation Service，中断翻译服务）的部件的 `GITS_TRANSLATER` 寄存器，由 ITS 翻译成一个 LPI 中断（就是第四节表格里 8192 号以后的那些）。

### 7.3 MSI 的好处

- **不需要中断线**：PCIe 链路本来就能传输写操作，不用额外的线。
- **数量多**：MSI 支持每个设备最多 32 个中断；升级版 **MSI-X** 支持每个设备最多 **2048** 个中断，每个都可以独立配置目标地址和数据，送给不同的 CPU 核。
- **不共享**：每个中断都是设备独占的，不用“挨个问”。
- **天然有序**：这是一个精妙的副作用。因为 MSI 本身就是一次 DMA 写，它在 PCIe 链路上和设备之前的 DMA 写（比如把收到的网络包写进内存）**按顺序传输**。所以当 CPU 收到 MSI 中断时，设备之前写进内存的数据**一定已经到了**。而传统的中断线和数据走的是两条不同的路，中断可能比数据先到，驱动程序需要额外做一次读回来确认。

### 7.4 MSI-X 的配置也是 MMIO

MSI-X 还有一个和本书主题相关的细节：每个中断的“目标地址”和“写入的值”存放在一张叫 **MSI-X 表**的结构里，**这张表就位于设备的某个 MMIO 区域（BAR，第 10 篇讲）中**。操作系统要配置一个中断送给哪个 CPU，就是用 MMIO 往这张表里写地址和数据。

所以在 MSI-X 的世界里，你会看到 MMIO 出现在两个方向上：

1. CPU 用 MMIO 写设备的 MSI-X 表，配置“中断该往哪里写”；
2. 设备发中断时，往中断控制器的 MMIO 地址写一个值。

## 八、轮询的回归：高性能 I/O 的选择

### 8.1 中断太贵了

第三节说过，每次中断都有微秒级的固定开销。对于一块每秒收发几千万个包的 100G 网卡，或者一块每秒能完成上百万次读写的 NVMe 固态硬盘，中断开销已经成了瓶颈。

于是，在高性能领域，**轮询又回来了**，只不过换了一种更聪明的方式。

### 8.2 几种折中方案

**中断合并（interrupt coalescing）**：设备不是每来一个包就发一次中断，而是攒够一定数量（比如 32 个包），或者等够一定时间（比如 50 微秒），再发一次中断。CPU 一次处理一批。代价是单个包的延迟增加了。网卡驱动里常用 `ethtool -C` 命令来调整这个参数。

**NAPI（Linux 网络栈的混合模式）**：

1. 平时开着中断，等第一个包到来；
2. 第一个包触发中断后，驱动**关掉**这个队列的中断，转入轮询模式，一口气处理掉所有积压的包；
3. 轮询发现没有新包了，再**重新打开**中断，回到等待状态。

这样，在流量小的时候享受中断的低 CPU 占用，在流量大的时候享受轮询的高吞吐。

**纯轮询**：有些场景干脆完全放弃中断。

- **NVMe 的轮询模式**：Linux 允许给 NVMe 硬盘配置专门的“轮询队列”，应用程序提交 I/O 后，CPU 不等中断，而是直接在原地反复检查完成队列。对延迟极其敏感的数据库可以用它把单次 I/O 延迟再降低几微秒。
- **DPDK、SPDK**：用户态的高性能网络和存储框架（第 11 篇会提到）。它们让一个或几个 CPU 核**专门**负责 100% 地轮询网卡或硬盘，完全不用中断。代价是这几个核永远是满负荷运转的，但换来了极致的吞吐和延迟。

值得一提的是，这些高性能轮询通常轮询的是**内存**（设备通过 DMA 写回内存的完成队列），而不是设备的 MMIO 状态寄存器——因为轮询内存（走缓存）比轮询 MMIO（每次都要穿越总线）快得多。这是第 8 篇的话题。

### 8.3 选择指南

| 场景 | 推荐方式 |
|---|---|
| 事件稀少（键盘、串口、传感器） | 中断 |
| 等待时间极短（几微秒） | 轮询 |
| 中断系统还不可用（启动早期） | 轮询 |
| 高吞吐、事件密集（网卡、NVMe） | 中断 + 合并，或 NAPI 式混合 |
| 极致延迟、愿意牺牲 CPU 核 | 纯轮询（DPDK、SPDK、NVMe 轮询队列） |

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 轮询 | CPU 反复读状态寄存器；简单但浪费 CPU |
| 中断 | 设备主动通知 CPU，CPU 暂停当前工作去处理 |
| 中断控制器 | 汇集所有中断、决定送给哪个 CPU 的“总机”；x86 叫 APIC，ARM 叫 GIC |
| GIC 分发器/重分发器 | 本身也通过 MMIO 配置 |
| INTID | GIC 的中断号；SGI、PPI、SPI、LPI 四类 |
| 中断处理里的 MMIO | 读状态 → 处理 → 写清除（只清处理过的） |
| 两层确认 | 驱动对设备清除中断，内核对中断控制器确认结束 |
| 电平触发/边沿触发 | 一直按着门铃 / 按一下就走 |
| 中断风暴 | 电平触发中断没有在设备上清除，CPU 被无限中断 |
| 伪中断 | 清除命令还在路上就返回，导致多触发一次；用读回解决 |
| MSI/MSI-X | 设备往中断控制器的特定 MMIO 地址写一个值来发中断 |
| MSI-X 表 | 位于设备 MMIO 区域里，配置每个中断的目标地址和数据 |
| 中断合并、NAPI | 减少中断次数的折中方案 |
| 纯轮询 | DPDK、SPDK、NVMe 轮询队列，用 CPU 换延迟 |
