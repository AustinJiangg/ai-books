# 第 8 篇｜MMIO 与 DMA：控制走 MMIO，数据走 DMA

> **本篇目标**：理解为什么大量数据不能靠 MMIO 来搬，以及 MMIO 和 DMA 是如何分工合作的。读完本篇，你会明白描述符环和门铃寄存器的工作原理，能完整描述一次网卡发包的全过程，了解 DMA 带来的缓存一致性问题，以及 IOMMU 为什么被称为“设备的页表”。

---

## 一、为什么不能全靠 MMIO 搬数据

### 1.1 一个算术题

假设网卡收到了一个 1500 字节的网络包，存在网卡内部的缓冲区里。如果用 MMIO 的方式把它读到内存，CPU 需要：

```c
for (int i = 0; i < 1500 / 4; i++) {
    buf[i] = readl(nic + RX_DATA);   // 每次读 4 字节
}
```

一共 375 次 MMIO 读。第 2 篇说过，一次 MMIO 读要穿越整个总线，可能要几百纳秒到一微秒（对 PCIe 设备来说尤其慢，因为读必须等设备回复）。按每次 500 纳秒算，读完一个包要将近 **200 微秒**。

一块 10G 网卡在满负荷时，每秒能收到大约 **80 万**个这样的包。如果每个包都要 200 微秒，CPU 需要每秒工作 160 秒——这显然不可能。

而且，在这 200 微秒里，CPU 什么都干不了，只是在当一个“搬运工”。这种 CPU 亲自一个字一个字搬数据的方式叫 **PIO（Programmed I/O，程序控制 I/O）**——注意它和第 1 篇的“端口 I/O”缩写相同，但意思不一样，这里强调的是“由 CPU 程序亲自搬”。

### 1.2 MMIO 擅长什么、不擅长什么

MMIO 读写的特点是：

- **每次访问都很慢**（相对于内存）；
- **每次访问的数据量很小**（通常 4 或 8 字节）；
- **CPU 必须亲自参与每一次访问**。

这使得 MMIO 非常适合**控制**——下一个命令、查一个状态、配一个参数，这些操作数据量小、频率低，慢一点无所谓；但非常不适合**数据**——搬运成千上万字节的网络包、磁盘块、视频帧。

### 1.3 解决方案：让设备自己搬

既然 CPU 当搬运工太浪费，那就让设备自己来搬。设备本身就挂在总线上，它也可以发起读写内存的操作。只要告诉它“数据要搬到内存的哪个位置”，它就能自己把数据写进去，不需要 CPU 参与。

这就是 **DMA（Direct Memory Access，直接内存访问）**：**设备直接读写内存，不经过 CPU。**

```
          PIO（CPU 亲自搬）                   DMA（设备自己搬）

   ┌─────┐   MMIO 读 ×375   ┌─────┐     ┌─────┐  MMIO 写：地址+长度  ┌─────┐
   │ CPU │ ←─────────────── │ 网卡 │     │ CPU │ ──────────────────→ │ 网卡 │
   └──┬──┘                  └─────┘     └─────┘   （几次，很快）     └──┬──┘
      │ 写内存 ×375                                                    │
      ▼                                                               │ DMA 写
   ┌──────┐                                    ┌──────┐               │ （设备自己搬）
   │ 内存 │                                    │ 内存 │ ←─────────────┘
   └──────┘                                    └──────┘
                                           CPU 在此期间可以干别的
```

第 1 篇我们说过：**MMIO 是 CPU 访问设备，DMA 是设备访问内存**。现在我们看到了两者如何配合：

> **控制走 MMIO，数据走 DMA。**
>
> CPU 用 MMIO 告诉设备“数据在内存哪里、有多长、开始吧”；设备用 DMA 自己去内存里搬数据；搬完了用中断通知 CPU。

## 二、DMA 的基本流程

### 2.1 最简单的 DMA

最简单的 DMA 设备只能一次处理一个任务。它的寄存器可能长这样：

```
偏移量    寄存器        作用
0x00      DMA_ADDR      内存地址：数据在内存的哪里
0x08      DMA_LEN       长度：搬多少字节
0x10      DMA_CTRL      控制：写 1 开始，方向位（读内存还是写内存）
0x14      DMA_STATUS    状态：忙、完成、出错
```

发送一块数据的流程：

```c
// 1. 准备好内存里的数据（普通内存操作）
memcpy(dma_buf, data, len);

// 2. 用 MMIO 告诉设备：数据在哪、有多长
writeq(dma_buf_addr, dev + DMA_ADDR);
writel(len,          dev + DMA_LEN);

// 3. 用 MMIO 按下“开始”按钮
writel(DMA_START | DMA_DIR_TO_DEVICE, dev + DMA_CTRL);

// 4. 设备自己去内存读数据……CPU 去干别的
// 5. 设备完成后发中断，中断处理程序读 DMA_STATUS 确认
```

注意第 1 步和第 3 步之间的顺序：必须确保 `dma_buf` 里的数据已经写好（并且对设备可见），才能按“开始”。这正是第 6 篇讲的屏障问题——`writel` 自带的屏障在这里起了关键作用。

### 2.2 一个关键细节：设备用的是什么地址

上面代码里有一个容易忽略的细节：写进 `DMA_ADDR` 的是 `dma_buf_addr`，而不是 `dma_buf` 这个指针本身。

为什么？因为 CPU 上的程序（包括内核）用的是**虚拟地址**，而设备不经过 CPU 的 MMU，它看不懂虚拟地址。设备需要的是一个它能直接在总线上使用的地址，叫做 **DMA 地址**（也叫总线地址或 IO 虚拟地址）。

在最简单的系统里，DMA 地址就等于物理地址。但在有 IOMMU 的系统里（第六节），DMA 地址是另一套独立的地址。所以 Linux 内核要求驱动程序**永远不要自己计算 DMA 地址**，而是通过 DMA API 来获取（第五节）。

## 三、描述符环：给设备排一个任务队列

### 3.1 一次只能干一件事太慢了

上面那种“一次一个任务”的 DMA 有个问题：CPU 每提交一个任务，都要等设备完成、发中断、处理中断，然后才能提交下一个。设备在两个任务之间是空闲的，CPU 也要频繁地被打断。

对于网卡这种每秒要处理几百万个包的设备，这完全不够用。需要一种方式，让 CPU **一次性提交很多任务**，设备**连续不断地处理**，两边都不用互相等待。

### 3.2 描述符

解决方案的第一步是：把“任务”从设备寄存器里搬到**内存**里。

每个任务用一个小结构体来描述，叫**描述符（descriptor）**：

```c
struct tx_desc {
    u64 buf_addr;    // 数据缓冲区的 DMA 地址
    u32 length;      // 数据长度
    u32 flags;       // 标志：谁拥有这个描述符、是否是最后一段、要不要发中断……
};
```

描述符本身放在内存里，CPU 用普通的内存写来填写它（快！），设备用 DMA 来读取它。

### 3.3 环形队列

然后，把很多个描述符排成一个**环形数组**，叫**描述符环（descriptor ring）**：

```
                 描述符环（在内存里，比如 256 个描述符）

      ┌────┬────┬────┬────┬────┬────┬────┬────┬────┬────┐
      │ 0  │ 1  │ 2  │ 3  │ 4  │ 5  │ 6  │ 7  │ ...│255 │
      └────┴────┴────┴────┴────┴────┴────┴────┴────┴────┘
                  ▲                   ▲
                  │                   │
                head                tail
           （设备处理到这里）    （CPU 填写到这里）

      [head, tail) 之间：CPU 已填好、等设备处理的任务
      tail 之后到 head 之前：空闲位置，CPU 可以继续填
```

这是一个经典的**生产者-消费者**模型：

- **CPU 是生产者**：在 `tail` 位置填写新的描述符，然后 `tail` 往前移。
- **设备是消费者**：从 `head` 位置开始取描述符、处理，然后 `head` 往前移。
- 走到数组末尾后，绕回到开头继续——这就是“环形”。

只要环没满，CPU 可以一口气填很多个描述符；只要环不空，设备可以一个接一个连续处理。两边各干各的，互不等待。

### 3.4 门铃：告诉设备“有新活儿了”

现在还剩一个问题：CPU 填好了新的描述符，**设备怎么知道？**

一种办法是让设备不停地用 DMA 去读内存里的描述符，看有没有新的——这叫设备端轮询，很浪费总线带宽。

更常用的办法是：CPU 填好描述符后，**用一次 MMIO 写，把新的 `tail` 值告诉设备**。设备收到后，就知道 `head` 到 `tail` 之间有新任务了。

这个专门用来通知设备的寄存器，就是第 3 篇提到的**门铃寄存器（doorbell register）**：

```c
// 填好 n 个描述符后……
writel(new_tail, nic->regs + TX_TAIL);   // 按门铃！
```

门铃这个名字非常形象：你在设备的“门口”（内存里的描述符环）放好了包裹，然后按一下门铃告诉它“东西放好了，来拿吧”。

### 3.5 门铃的精妙之处

门铃机制有几个精妙之处：

1. **批量化**：CPU 可以填好 32 个描述符，然后只按**一次**门铃。一次 MMIO 写，提交了 32 个任务。MMIO 的高延迟被分摊了。
2. **只写不读**：按门铃是一次 MMIO **写**，而第 6 篇说过，MMIO 写通常是“投递式”的，CPU 不用等待设备回复，写完立刻继续。相比之下，MMIO 读必须等设备回复，非常慢。好的设备设计会尽量让热点路径上**只有 MMIO 写，没有 MMIO 读**。
3. **大量数据走内存**：描述符的内容、数据缓冲区的内容，全都是 CPU 用普通内存访问写的，速度快、可以缓存。只有“门铃”这一个小小的数值走 MMIO。

### 3.6 完成通知：设备怎么告诉 CPU“做完了”

设备处理完一些描述符后，CPU 需要知道哪些任务完成了，好回收对应的缓冲区。常见的做法有：

- **设备写回描述符**：设备处理完一个描述符后，用 DMA 修改内存里这个描述符的 `flags` 字段（比如设置“已完成”位）。CPU 检查内存里的 `flags` 就知道了——这是读**内存**，不是读 MMIO，很快。
- **设备写回 head 指针**：设备用 DMA 把最新的 `head` 值写到内存里的一个约定位置，CPU 读这个内存位置。
- **完成队列**：设备在另一个专门的环里写入“完成记录”（NVMe 就是这种设计：提交队列 + 完成队列）。

无论哪种方式，核心思路都一样：**设备把结果写回内存，CPU 读内存而不是读设备寄存器**。再配合中断（第 7 篇）告诉 CPU“有新的完成记录了，快来看”。

这也解释了第 7 篇最后提到的：高性能轮询轮询的是内存，而不是 MMIO。

## 四、一次网卡发包的完整旅程

现在把所有知识串起来，看一次网卡发包的完整过程。

```
                  CPU（驱动程序）                         网卡
                        │                                  │
 ① 准备数据            │ 把网络包放进内存缓冲区              │
                        │ （普通内存写）                     │
                        │                                  │
 ② 获取 DMA 地址        │ dma_map_single(buf) → dma_addr    │
                        │                                  │
 ③ 填写描述符           │ desc[tail].buf_addr = dma_addr     │
                        │ desc[tail].length   = len          │
                        │ （普通内存写）                     │
                        │                                  │
 ④ 屏障                 │ dma_wmb()                          │
                        │                                  │
 ⑤ 交出所有权           │ desc[tail].flags = OWNED_BY_HW     │
                        │ tail++                             │
                        │                                  │
 ⑥ 按门铃（MMIO 写）    │ writel(tail, regs + TX_TAIL) ─────→│
                        │                                  │
                        │  CPU 去干别的事                    │ ⑦ DMA 读描述符
                        │                                  │ ⑧ DMA 读数据缓冲区
                        │                                  │ ⑨ 把数据发到网线上
                        │                                  │ ⑩ DMA 写回描述符：
                        │                                  │    flags |= DONE
                        │                                  │
                        │←─────────────────────── 中断（MSI）│ ⑪ 发中断
 ⑫ 中断处理            │                                  │
   检查描述符           │ 读 desc[i].flags（普通内存读）      │
   dma_rmb()            │                                  │
   回收缓冲区           │ dma_unmap_single(...)，释放 buf     │
                        │                                  │
```

在这 12 步里：

- **MMIO 只出现了一次**：第 ⑥ 步按门铃（加上中断处理里可能的一两次读写，用来清中断）。
- **DMA 出现了三次**：第 ⑦⑧ 步设备读内存，第 ⑩ 步设备写内存（第 ⑪ 步的 MSI 中断，按第 7 篇的说法，本质上也是一次设备发起的写）。
- **屏障出现在两个关键位置**：第 ④ 步保证描述符内容先于所有权标志被设备看到；第 ⑥ 步的 `writel` 自带屏障，保证描述符先于门铃被设备看到；第 ⑫ 步的 `dma_rmb()` 保证先确认 `DONE` 标志再读其他字段。

这就是第 6 篇那个“典型 bug”背后的完整场景。

真实的网卡驱动比这复杂得多（多个队列、分散-聚集、校验和卸载、TSO 等等），但骨架就是这样：**内存里排队，MMIO 按门铃，DMA 搬数据，中断报完成。** NVMe 硬盘、GPU、各种加速卡，用的都是同一个骨架。第 12 篇会看到，连虚拟机里的 virtio 设备也是这样。

## 五、DMA 与缓存一致性

### 5.1 问题

DMA 引入了一个新的麻烦：**缓存**。

第 5 篇说过，CPU 访问普通内存时会走缓存。而 DMA 是设备直接访问内存条，**它可能不经过 CPU 的缓存**。这就可能出现两种不一致：

**情况一：CPU 写，设备读（发送方向）**

```
CPU 把数据写进 dma_buf → 数据还在 CPU 缓存里（写回策略），没写到内存条
设备 DMA 读 dma_buf    → 从内存条读到的是旧数据！
```

**情况二：设备写，CPU 读（接收方向）**

```
设备 DMA 写 dma_buf    → 新数据写到了内存条
CPU 读 dma_buf         → 缓存里有这个地址的旧副本，缓存命中，读到旧数据！
```

### 5.2 两种硬件

这个问题是否存在，取决于硬件：

**缓存一致的 DMA（cache-coherent DMA）**：硬件保证设备的 DMA 访问会和 CPU 缓存“协商”。设备读内存时，如果 CPU 缓存里有更新的数据，硬件会从缓存里取；设备写内存时，硬件会自动让 CPU 缓存里的旧副本失效。x86 平台和大部分 ARM64 服务器上的 PCIe 设备都是这样的。对软件来说，缓存问题不存在。

**非一致的 DMA（non-coherent DMA）**：硬件不管。设备只看内存条，CPU 只看缓存，两者各说各话。很多 ARM64 嵌入式芯片、手机芯片上的部分设备是这样的。这时**软件必须手动维护缓存**：

- 发送前（情况一）：**清理（clean）**缓存，把缓存里的脏数据写回内存条；
- 接收后（情况二）：**作废（invalidate）**缓存，丢掉缓存里的旧副本，下次读时从内存条重新读。

ARM64 提供了专门的缓存维护指令来做这些事（`DC CVAC` 清理、`DC IVAC` 作废等）。

### 5.3 Linux DMA API

好消息是：驱动程序员**不需要关心**自己的设备是一致的还是非一致的，也不需要自己写缓存维护指令。Linux 提供了一套 **DMA API**，在不同的硬件上自动做正确的事。

它主要有两类用法：

**一致性映射（coherent / consistent mapping）**：

```c
void *cpu_addr;
dma_addr_t dma_addr;
cpu_addr = dma_alloc_coherent(dev, size, &dma_addr, GFP_KERNEL);
```

分配一块 CPU 和设备都能“同时、随时”访问的内存，内核保证两边看到的永远一致。在非一致硬件上，内核会把这块内存映射成**不可缓存**的（第 5 篇的 Normal Non-cacheable），从根本上避免缓存问题。

适合**长期存在、双方频繁访问**的数据结构，比如**描述符环**。

**流式映射（streaming mapping）**：

```c
dma_addr_t dma_addr = dma_map_single(dev, buf, len, DMA_TO_DEVICE);
// …… 设备做 DMA ……
dma_unmap_single(dev, dma_addr, len, DMA_TO_DEVICE);
```

把一块**已有的普通内存**临时交给设备使用。在 `dma_map_single` 时，内核根据方向做必要的缓存维护（发送方向：清理缓存）；在 `dma_unmap_single` 时，再做另一边的维护（接收方向：作废缓存）。

在映射期间，**这块内存的“所有权”属于设备**，CPU 不应该碰它。如果确实需要在映射期间访问，要用 `dma_sync_single_for_cpu` / `dma_sync_single_for_device` 来来回交接所有权。

适合**一次性**的数据缓冲区，比如每个网络包的数据。

| | 一致性映射 | 流式映射 |
|---|---|---|
| 函数 | `dma_alloc_coherent` | `dma_map_single` / `dma_unmap_single` |
| 内存来源 | 内核专门分配 | 已有的普通内存 |
| 缓存处理 | 必要时映射成不可缓存 | 映射/解除映射时做缓存维护 |
| 访问性能 | 在非一致硬件上 CPU 访问较慢 | CPU 访问走缓存，快 |
| 典型用途 | 描述符环、控制结构 | 网络包、磁盘块等数据缓冲区 |

两者都会返回一个 `dma_addr_t`——这就是要写进描述符、告诉设备的 DMA 地址。

## 六、IOMMU：给设备也装上“页表”

### 6.1 DMA 的安全问题

DMA 赋予了设备一个强大的能力：**直接读写内存**。但这也带来了风险：

- 如果驱动程序有 bug，把一个错误的地址告诉了设备，设备就会往一个错误的地方写数据——可能是内核代码、可能是别的进程的数据。这种破坏非常难排查，因为“凶手”不是 CPU 上的任何代码。
- 如果设备本身是恶意的（比如一个被篡改过的 USB-C/雷电接口外设），它可以通过 DMA 读取整个内存的内容——包括密码、密钥——或者往内核里注入恶意代码。这叫 **DMA 攻击**。
- 在虚拟化场景下（第 12 篇），如果把一个物理设备直接交给虚拟机使用，虚拟机里的驱动可以让设备 DMA 到宿主机的任意内存，完全突破虚拟机的隔离。

问题的根源是：CPU 访问内存要经过 MMU 和页表的检查，**但设备的 DMA 访问没有任何检查**。

### 6.2 IOMMU 的思路

解决办法很自然：**给设备也加一个 MMU**。

这就是 **IOMMU**（I/O Memory Management Unit）。在 ARM 平台上它叫 **SMMU**（System MMU），在 Intel 平台上叫 **VT-d**，在 AMD 平台上叫 **AMD-Vi**。

```
           没有 IOMMU                            有 IOMMU

   ┌────┐                               ┌────┐
   │设备│── DMA 地址 = 物理地址 ──→ 内存  │设备│── DMA 地址（IO 虚拟地址）
   └────┘   （想写哪就写哪）              └────┘          │
                                                         ▼
                                                  ┌───────────┐
                                                  │  IOMMU    │ 查设备的页表：
                                                  │（设备的MMU）│ 这个地址允许吗？
                                                  └─────┬─────┘ 对应哪个物理地址？
                                                        │
                                                        ▼ 物理地址
                                                       内存
```

IOMMU 位于设备和内存之间，它为每个设备（或每组设备）维护一套**页表**：

- 设备发出的 DMA 地址（叫 **IOVA**，IO 虚拟地址）要经过 IOMMU 翻译，才变成真正的物理地址；
- 如果设备访问的地址不在它的页表里，IOMMU 会**拦截**这次访问，并报告错误。

这和 CPU 的 MMU 几乎一模一样，只是服务对象从“进程”变成了“设备”。

### 6.3 IOMMU 带来的好处

1. **安全隔离**：每个设备只能访问内核明确允许的那几块内存。驱动 bug 或恶意设备都无法越界。
2. **虚拟化直通**：可以把一个物理设备安全地交给虚拟机，IOMMU 保证设备只能访问属于这台虚拟机的内存（第 12 篇）。
3. **地址重映射**：有些老设备只能访问 32 位地址（4GB 以下），但内存可能在 4GB 以上。IOMMU 可以把一个低地址的 IOVA 映射到高地址的物理内存，让老设备也能用。
4. **分散变连续**：一块逻辑上连续的缓冲区，在物理内存里可能是分散的很多页。IOMMU 可以把它们映射成一段连续的 IOVA，设备看到的是一块完整的缓冲区。

### 6.4 IOMMU 本身也是 MMIO 设备

有趣的是，IOMMU 本身也是通过 MMIO 来配置的。回顾第 2 篇 QEMU `virt` 的地址地图，`0x0905_0000` 处就有一个 SMMUv3（在启用时）。内核通过 MMIO 写 SMMU 的寄存器，告诉它每个设备的页表在内存的什么位置。

对驱动程序员来说，IOMMU 是透明的——你调用 `dma_map_single`，Linux DMA API 会自动在 IOMMU 里建立映射，返回的 `dma_addr_t` 就是 IOVA。这也是为什么前面强调：**永远通过 DMA API 获取 DMA 地址，不要自己计算**。

第 11 篇会看到，用户态驱动框架 VFIO 正是依靠 IOMMU 来保证安全性的。

## 七、三者的分工

到这里，我们已经认识了 CPU 与设备之间通信的三种基本机制。用一张图总结它们的分工：

```
                ┌─────────────────────────────────────────────────┐
                │                      CPU                        │
                └──┬──────────────────────▲─────────────────┬─────┘
                   │                      │                 │
          ① MMIO   │             ④ 中断    │                 │ 普通内存读写
          写配置    │             "我做完了" │                 │ （填描述符、
          按门铃    │                      │                 │   读完成记录）
          读状态    │                      │                 │
                   ▼                      │                 ▼
                ┌──────────────────────────┴───┐      ┌──────────────┐
                │            设备              │      │     内存      │
                │                             │ ②③   │  描述符环      │
                │                             │ DMA  │  数据缓冲区    │
                │                             │◄────►│  完成队列      │
                └─────────────────────────────┘      └──────────────┘
                                                (经过 IOMMU 检查)
```

| 机制 | 方向 | 发起者 | 数据量 | 用途 |
|---|---|---|---|---|
| **MMIO** | CPU → 设备 | CPU | 小（几字节） | 配置、命令、门铃、查状态 |
| **DMA** | 设备 ↔ 内存 | 设备 | 大（KB～MB） | 搬运数据、读写描述符 |
| **中断** | 设备 → CPU | 设备 | 无（只是一个信号） | 通知事件发生 |

一句话：**MMIO 下命令，DMA 搬数据，中断报完成。**

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| PIO（程序控制 I/O） | CPU 亲自用 MMIO 一个字一个字搬数据，慢且占 CPU |
| DMA | 设备直接读写内存，不经过 CPU |
| 控制走 MMIO，数据走 DMA | 两者的分工原则 |
| DMA 地址 | 设备在总线上使用的地址，不是 CPU 虚拟地址；由 DMA API 提供 |
| 描述符 | 内存里描述一个 DMA 任务的小结构体 |
| 描述符环 | 环形数组，CPU 生产、设备消费 |
| 门铃寄存器 | CPU 填好描述符后写一次 MMIO 通知设备；可批量、只写不读 |
| 完成通知 | 设备把结果 DMA 写回内存，再发中断 |
| 缓存一致的 DMA | 硬件自动维护缓存，软件不用管 |
| 非一致的 DMA | 软件必须清理/作废缓存 |
| 一致性映射 | `dma_alloc_coherent`，适合描述符环 |
| 流式映射 | `dma_map_single`，适合一次性数据缓冲区 |
| IOMMU / SMMU | 设备的 MMU，把 IOVA 翻译成物理地址并检查权限 |
| DMA 攻击 | 恶意设备通过 DMA 读写任意内存；IOMMU 可防御 |
