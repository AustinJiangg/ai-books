# 第 4 篇｜volatile 与编译器：为什么寄存器读写会“消失”

> **本篇目标**：理解编译器为什么会“篡改”你的内存访问，以及这对 MMIO 意味着什么。读完本篇，你会知道 `volatile` 关键字到底保证了什么、不保证什么，为什么访问宽度很重要，以及 Linux 内核为什么不让驱动程序直接用 `volatile` 指针。

---

## 一、一个“灵异事件”

### 1.1 调试版好好的，发布版卡死了

假设你写了上一篇那个串口输出函数，但手一滑，忘了写 `volatile`：

```c
#define UARTFR   ((uint32_t *)0x09000018)   // 注意：没有 volatile
#define UARTDR   ((uint32_t *)0x09000000)
#define FR_TXFF  (1u << 5)

void uart_putc(char c) {
    while (*UARTFR & FR_TXFF) {
        // 等发送 FIFO 有空位
    }
    *UARTDR = c;
}
```

你用 `-O0`（不优化）编译，一切正常，字符一个个打印出来。然后你改用 `-O2`（常规优化）编译发布版本——**程序在打印第一个长字符串时卡死了**，或者打印出来的字符少了一大截。

代码一个字都没改，只是换了个编译选项，行为就完全变了。这是嵌入式和驱动开发中最经典的“灵异事件”之一。

罪魁祸首是**编译器**。要理解它为什么这么干，我们得先站在编译器的角度想问题。

### 1.2 编译器眼中的世界

编译器的工作是把你的 C 代码翻译成机器指令，并且**尽量让程序跑得快**。为此它会做大量优化。但它不能随便改，它遵守一条根本原则，叫 **“as-if”规则（仿佛规则）**：

> 只要程序**看起来**和按源代码一句一句执行的结果一样，编译器可以随意改变实际的执行方式。

关键在于“看起来一样”是怎么判断的。在 C 语言标准里，一个普通程序“可被观察到的行为”只包括很少几样东西：对 `volatile` 对象的访问、文件输入输出、程序退出时的状态等。**对普通内存的读写本身，不算“可观察的行为”**——只要最终用到的值是对的，中间读了几次、写了几次、按什么顺序，编译器都可以自由安排。

在编译器的世界观里，内存是一个“安静”的地方：

- 你不往一个地址写东西，它的值就不会变；
- 读它不会有任何副作用；
- 写进去的值如果后面没人读，那这次写就是浪费。

这正是上一篇那张“内存常识”表里的左列。**编译器默认所有指针指向的都是普通内存。** 它不知道 `0x09000018` 背后是一个串口。

## 二、编译器会对你的读写做什么

下面列出编译器常做的几种优化。对普通内存，它们都是正确且有益的；对设备寄存器，每一种都可能带来灾难。

### 2.1 优化一：把重复的读“提”出循环

回到开头的例子：

```c
while (*UARTFR & FR_TXFF) { }
```

编译器分析这个循环：循环体是空的，循环里没有任何代码会修改 `*UARTFR`。根据“内存不会自己变”的假设，**每次读 `*UARTFR` 得到的值必然一样**。那何必每次都读呢？于是它把代码优化成相当于：

```c
uint32_t tmp = *UARTFR;        // 只读一次
while (tmp & FR_TXFF) { }      // 用这个值永远判断下去
```

如果第一次读的时候 FIFO 恰好是满的，`tmp` 的 `TXFF` 位就是 1，这个循环就**永远不会退出**——尽管串口在另一边早就把 FIFO 腾空了。

这就是开头程序卡死的原因。在编译器看来，它做了一个完全合理的优化；它只是不知道，这个“内存”的值会被设备在背后改变。

### 2.2 优化二：删掉“没用”的写

```c
*UARTDR = 'H';
*UARTDR = 'i';
```

编译器看到对同一个地址连续写了两次，第一次写的 `'H'` 还没人读就被 `'i'` 覆盖了。根据“写进去的值没人读就是浪费”的假设，第一次写是“死存储（dead store）”，可以删掉。于是只剩下：

```c
*UARTDR = 'i';
```

串口只发出了一个 `i`，`H` 消失了。这就是开头“打印出来的字符少了一大截”的原因。

同样的道理，如果你写了一个寄存器，但后面的代码再也没读过它（比如写一个“开始”命令寄存器），编译器在某些情况下甚至可能把整个写都删掉——因为在它看来，“写了没人读”就等于没写。

### 2.3 优化三：合并多次读写

```c
uint8_t a = *(uint8_t *)(base + 0);
uint8_t b = *(uint8_t *)(base + 1);
uint8_t c = *(uint8_t *)(base + 2);
uint8_t d = *(uint8_t *)(base + 3);
```

四次 1 字节的读，地址又是连续的。编译器可能会把它们合并成**一次 4 字节的读**，然后在 CPU 寄存器里拆开。对内存来说这快了好几倍；对设备来说，你本来是想分别读 4 个 8 位寄存器（每次读可能都有副作用），结果变成了一次 32 位读，设备看到的访问模式完全不同。

反过来，编译器也可能把一次大的访问**拆成多次小的访问**，下面第五节会讲。

### 2.4 优化四：调换读写的顺序

```c
*DMA_SRC  = src;      // ① 源地址
*DMA_LEN  = len;      // ② 长度
*DMA_CTRL = START;    // ③ 开始
```

这三个写操作针对三个不同的地址，彼此之间没有数据依赖。编译器可能为了更好地利用 CPU 流水线，调换它们的顺序，比如先写 ③ 再写 ①②。对内存来说结果一样；对设备来说，它在收到“开始”命令时，源地址和长度还是旧值。

### 2.5 优化五：把值“藏”在 CPU 寄存器里

```c
*CTRL = 1;
do_something();
if (*CTRL == 1) { ... }
```

如果编译器能确定 `do_something()` 不会修改 `*CTRL`（比如这个函数被内联了、而且里面没有碰这个地址），它可能会直接用刚才写进去的 `1` 作为判断条件，根本不去读 `*CTRL`。但设备可能在这期间已经修改了这个寄存器（比如操作完成后自动清零了“开始”位）。

### 2.6 汇总

| 优化 | 编译器的假设 | 对 MMIO 的后果 |
|---|---|---|
| 重复读只读一次 | 值不会自己变 | 轮询死循环 |
| 删除被覆盖的写 | 没人读的写是浪费 | 发送的数据丢失、命令丢失 |
| 合并多次访问 | 访问方式不影响结果 | 访问宽度和次数变了 |
| 调换访问顺序 | 无依赖的访问顺序无关 | 设备收到半成品配置 |
| 缓存在 CPU 寄存器 | 值只有我自己会改 | 读到过时的值 |

所有问题的根源都是同一个：**编译器把设备寄存器当成了普通内存**。我们需要一种办法告诉编译器：“这个地址不一样，别碰。”

## 三、volatile：告诉编译器“别自作聪明”

### 3.1 用法

C 语言提供了 `volatile` 类型修饰符，专门解决这个问题。把指针声明为“指向 `volatile` 对象的指针”：

```c
#define UARTFR   ((volatile uint32_t *)0x09000018)
#define UARTDR   ((volatile uint32_t *)0x09000000)
```

`volatile` 的字面意思是“易变的”。它告诉编译器：**这个对象的值可能在程序不知情的情况下被改变，对它的每一次访问都可能有副作用。**

### 3.2 volatile 保证了什么

C 标准规定，对 volatile 对象的访问属于“可观察的行为”，所以编译器必须：

1. **每一次访问都真实发生**。源代码里读 3 次，就生成 3 次读；写 2 次，就生成 2 次写。不能删、不能合并、不能提出循环。
2. **volatile 访问之间保持程序顺序**。两次 volatile 访问在源代码里谁先谁后，生成的指令里也是谁先谁后。
3. **不能把值缓存在 CPU 寄存器里**。每次读都要真的去那个地址读。

加上 `volatile` 后，第二节的五种优化全都被禁止了：

- 轮询循环每次都会重新读 `UARTFR`，不会死循环；
- 两次写 `UARTDR` 都会保留，`H` 和 `i` 都能发出去；
- 三次 DMA 配置写会按源代码顺序生成。

这就是为什么从第 1 篇开始，我们所有的 MMIO 示例代码里都带着 `volatile`。在裸机和单片机开发中，**MMIO 指针必须加 `volatile`**，这是铁律。

### 3.3 一个类比

可以把 `volatile` 理解成贴在地址上的一张标签：

> “**此处为设备，非普通内存。每次访问请亲自前往，不得凭记忆作答，不得擅自合并或省略，不得插队。**”

编译器看到这张标签，就会老老实实地按你写的每一次访问去生成指令。

## 四、volatile 不保证什么

`volatile` 解决了编译器的问题，于是很多人以为它“解决了 MMIO 的所有问题”。这是一个非常普遍的误解。实际上，`volatile` 管的范围很窄，**它只约束编译器，管不到编译器之外的事情**。

### 4.1 不保证 CPU 层面的顺序

`volatile` 保证编译器**生成的指令**是按顺序的。但指令生成之后，CPU 在执行时还可能调换顺序（乱序执行），写操作还可能在 CPU 的写缓冲区或总线上被延迟。

```
源代码顺序：    写 A → 写 B
      │ volatile 保证
      ▼
指令顺序：      写 A → 写 B          ← 编译器这一层守住了
      │ volatile 管不到
      ▼
实际到达设备：  写 B → 写 A ？        ← CPU 和总线可能调换
```

在 ARM64 这样的“弱内存序”架构上，这种调换是真实存在的。要在 CPU 层面保证顺序，需要用到**内存屏障指令**，这是第 6 篇的主题。

（实际上，ARM64 对“Device 类型”的内存有一些额外的顺序保证，能缓解一部分问题，但并不是全部。具体在第 5、6 篇讲。）

### 4.2 不保证和普通内存访问之间的顺序

`volatile` 只保证 **volatile 访问之间** 的顺序。对于一次 volatile 访问和一次**普通**内存访问，编译器仍然可以调换它们的顺序。

这在 DMA 场景下很要命：

```c
buffer[0] = data;          // 普通内存写：把要发送的数据放进内存缓冲区
*DOORBELL = 1;             // volatile 写：按门铃，通知设备来取数据
```

`buffer` 是普通内存，`DOORBELL` 是 volatile 设备寄存器。编译器**可以**把按门铃挪到写缓冲区之前——设备被叫醒后去内存里取数据，取到的是旧数据。要防止这种情况，同样需要屏障（第 6、8 篇）。

### 4.3 不保证原子性

`volatile` 不会让读-改-写变成原子操作：

```c
*CTRL |= ENABLE;   // 读、改、写三步，中间可能被打断
```

即使 `CTRL` 是 volatile，这仍然是三个独立的步骤。如果在读和写之间发生了中断，或者另一个 CPU 核也在改这个寄存器，就会出现覆盖问题。保护它需要用锁或者关中断。

`volatile` 也**不是**多线程同步的工具。在普通的多线程程序里用 `volatile` 变量做线程间通信，是一个流传甚广但错误的做法——应该用 C11 的原子类型（`_Atomic`）或者锁。`volatile` 是为“与硬件交互”设计的，不是为“与其他线程交互”设计的。

### 4.4 不保证访问宽度（严格来说）

你声明了 `volatile uint32_t *`，一般情况下编译器会生成一条 32 位的读写指令。但 C 标准并没有**严格保证**这一点——编译器理论上可以用两次 16 位访问来实现一次 32 位的 volatile 访问。

在主流编译器和主流架构上，对于自然对齐、宽度不超过 CPU 字长的 volatile 访问，编译器实际上都会生成单条对应宽度的指令。但在一些边界情况下（比如 64 位访问在 32 位 CPU 上、未对齐的地址、C 语言位域），就不一定了。

这引出了下一节的话题。

### 4.5 小结

| `volatile` 保证 | `volatile` 不保证 |
|---|---|
| 每次访问都真实发生 | CPU 执行时不乱序 |
| volatile 访问之间按程序顺序生成指令 | 和普通内存访问之间的顺序 |
| 不把值缓存在 CPU 寄存器里 | 读-改-写的原子性 |
| | 多线程之间的同步 |
| | 严格的访问宽度 |

一句话总结：**`volatile` 是必要条件，不是充分条件。** 它只解决了第 3 篇末尾那张图中第①层（编译器）的问题，而第②③④层（缓存、CPU 乱序、总线）它都管不着。

## 五、访问宽度与对齐

### 5.1 为什么宽度很重要

内存不在乎你是用 1 字节、2 字节还是 4 字节去访问它——无论怎么访问，数据都是一样的。但很多设备**只接受特定宽度的访问**：

- 有的设备规定所有寄存器**必须用 32 位访问**。如果你用 8 位读，可能读到 0、读到错误的值，甚至引发总线错误。
- 有的设备的某些寄存器是 8 位的，用 32 位去写，会同时写到相邻的另外 3 个寄存器。
- 对有副作用的寄存器，一次 32 位访问和四次 8 位访问是完全不同的行为：前者从 FIFO 取一次，后者取四次。

**芯片手册里通常会明确写出每个寄存器允许的访问宽度。** 驱动程序必须严格遵守。

在 C 语言里，访问宽度由指针的类型决定：

| 指针类型 | 访问宽度 |
|---|---|
| `volatile uint8_t *` | 8 位（1 字节） |
| `volatile uint16_t *` | 16 位（2 字节） |
| `volatile uint32_t *` | 32 位（4 字节） |
| `volatile uint64_t *` | 64 位（8 字节） |

所以，定义寄存器指针时，**类型必须和手册规定的宽度一致**。

### 5.2 对齐

**对齐**是指访问的地址必须是访问宽度的整数倍：32 位访问的地址必须是 4 的倍数，64 位访问的地址必须是 8 的倍数。

普通内存在现代 CPU 上通常允许未对齐访问（只是慢一点）。但在设备内存上，未对齐访问往往是**不允许的**——在 ARM64 上，对 Device 类型内存做未对齐访问，会直接触发对齐错误异常（第 5 篇会讲为什么）。

设备的寄存器本身总是对齐排列的，所以只要你用“基址 + 手册上的偏移量”来计算地址，一般不会出问题。容易出事的是下面这种情况。

### 5.3 `memcpy` 和结构体拷贝的坑

假设一个设备有一块 64 字节的“配置区”，你想一次性把它读出来：

```c
uint8_t buf[64];
memcpy(buf, (void *)DEV_CONFIG, 64);   // 危险！
```

问题在于，`memcpy` 是为普通内存高度优化的。不同的 C 库实现会用各种花招来加速：

- 用 CPU 支持的最宽指令（比如一次 16 字节甚至更宽的 SIMD 指令）；
- 先处理开头不对齐的几个字节，再大块拷贝，最后处理尾巴；
- 甚至可能**读超出范围一点点**（只要不跨页，对普通内存是安全的）；
- 在 ARM64 上，可能用 `DC ZVA` 之类的特殊指令。

这些花招在设备内存上全都可能出问题：访问宽度不对、对齐不对、多读了不该读的寄存器、用了设备内存不支持的指令。而且由于 `memcpy` 的参数是 `void *`，**你传进去的 volatile 修饰会被丢掉**，编译器还可能对它做进一步优化。

结构体拷贝也有同样的问题：

```c
struct dev_regs snapshot = *regs;   // 编译器可能用 memcpy 实现
```

正确的做法是**自己写一个循环，用规定的宽度一个一个读**：

```c
volatile uint32_t *src = (volatile uint32_t *)DEV_CONFIG;
uint32_t buf[16];
for (int i = 0; i < 16; i++) {
    buf[i] = src[i];    // 每次一个 32 位 volatile 读
}
```

Linux 内核为此专门提供了 `memcpy_fromio`、`memcpy_toio`、`memset_io` 这几个函数，它们知道如何正确地操作设备内存。

### 5.4 64 位寄存器的问题

有些设备有 64 位的寄存器（比如 64 位的地址寄存器、计数器）。在 64 位 CPU 上，一次 64 位访问没问题。但在 32 位 CPU 上，或者设备本身只支持 32 位访问时，就必须拆成两次 32 位访问。

拆分带来一个新问题：**两次读之间，值可能变了**。比如读一个 64 位计数器，先读低 32 位得到 `0xFFFFFFFF`，然后计数器加 1（变成高位 +1、低位 0），再读高 32 位，得到的是新的高位——拼起来的值比真实值大了约 40 亿。

常见的解决办法是“高-低-高”读法：先读高位，再读低位，再读一次高位；如果两次高位不一样，说明中间发生了进位，重新读一遍。Linux 内核里有 `lo_hi_readq`、`hi_lo_readq` 等辅助函数处理这类拆分。

## 六、Linux 为什么不直接用 volatile 指针

### 6.1 内核的态度

读到这里，你可能觉得：那以后访问 MMIO 都用 `volatile` 指针就好了。

在裸机程序里确实如此。但在 Linux 内核里，**直接用 `volatile` 指针访问 MMIO 是被明确反对的**。Linux 内核文档里甚至有一篇专门的文章，标题就叫《为什么不应该使用 volatile 类型》（*Why the "volatile" type class should not be used*）。

内核的做法是：设备寄存器的指针**不带** `volatile`，而是标记为一个特殊的 `__iomem` 类型；所有的访问都必须通过专门的**访问函数**来完成：

```c
void __iomem *base = ioremap(0x09000000, 0x1000);

u32 fr = readl(base + 0x018);    // 读一个 32 位寄存器
writel('A', base + 0x000);       // 写一个 32 位寄存器
```

`readl` 中的 `l` 表示 “long”，即 32 位；`b`、`w`、`q` 分别对应 8、16、64 位。第 9 篇会完整介绍这个家族。

### 6.2 访问函数做了什么

为什么要多一层函数？因为如上一节所说，`volatile` 只解决了编译器的问题。一次正确的 MMIO 访问，还需要：

1. **保证访问宽度**：访问函数内部用固定宽度的指令完成访问，不给编译器任何拆分或合并的余地。在 ARM64 上，内核直接用一小段内联汇编，强制生成**一条**指定宽度的读写指令。
2. **保证 CPU 层面的顺序**：`readl`/`writel` 内部带有适当的内存屏障，保证 MMIO 访问和前后的普通内存访问按正确顺序到达。这是 `volatile` 做不到的（第 6 篇详讲）。
3. **处理字节序**：PCI 设备的寄存器规定是小端序。如果 CPU 是大端序的，访问函数会自动转换字节顺序。
4. **方便调试和追踪**：所有 MMIO 访问都经过统一入口，可以方便地插入追踪代码（比如 x86 上的 `mmiotrace` 工具就是靠这个机制记录所有 MMIO 访问的）。
5. **支持虚拟化**：在虚拟机里，客户机的 MMIO 访问会被宿主机拦截，宿主机需要从硬件提供的信息中“读懂”这次访问的地址、宽度和数据。如果访问是由一条简单的标准读写指令完成的，硬件能直接提供这些信息；如果编译器生成了奇怪的复合指令，宿主机就很难处理。这也是 ARM64 内核坚持用内联汇编生成简单指令的原因之一（第 12 篇会再提到）。

同时，`__iomem` 标记配合内核的静态检查工具 **sparse**，可以在编译时发现“直接解引用设备指针”的错误代码——就像给这些指针加了一把锁，只有访问函数有钥匙。

### 6.3 一个对比

| | 裸机/单片机 | Linux 内核 |
|---|---|---|
| 指针类型 | `volatile uint32_t *` | `void __iomem *` |
| 访问方式 | 直接解引用 `*p = v` | `writel(v, p)` |
| 编译器问题 | 靠 `volatile` 解决 | 访问函数内部解决 |
| CPU 顺序问题 | 需要手动加屏障 | 访问函数默认带屏障 |
| 访问宽度 | 靠指针类型（通常可靠） | 访问函数强制保证 |

无论哪种风格，背后的道理是一样的：**告诉编译器（以及 CPU）“这里是设备，不是内存”**。只是 Linux 把这件事做得更彻底、更不容易出错。

## 七、写在最后

这一篇解决了 MMIO 之路上的第一道关卡：编译器。核心思想很简单——编译器默认所有地址都是“安静”的内存，我们必须用 `volatile`（或者更完善的访问函数）告诉它，有些地址背后是“活的”设备。

但我们也看到了，`volatile` 只能管住编译器。指令一旦生成，交给 CPU 去执行，又会遇到新的“自作聪明”：CPU 的缓存会想把设备寄存器的值存起来，CPU 的乱序执行会想调换读写的顺序。下面两篇，我们就继续沿着这条路往下走。

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| as-if 规则 | 只要可观察的结果一样，编译器可以任意改变执行方式 |
| 编译器对内存的假设 | 值不会自己变、读无副作用、没人读的写是浪费、无依赖的访问顺序无关 |
| 五种危险优化 | 提出循环、删除死存储、合并访问、调换顺序、缓存在 CPU 寄存器 |
| `volatile` 保证 | 每次访问都真实发生、volatile 访问间保持顺序、不缓存值 |
| `volatile` 不保证 | CPU 层面的顺序、与普通内存访问的顺序、原子性、线程同步、严格的宽度 |
| 访问宽度 | 设备往往只接受手册规定的宽度，由指针类型决定 |
| 对齐 | 设备内存上的未对齐访问通常不被允许 |
| `memcpy` 的坑 | 为内存优化的花招在设备上会出错，应改用 `memcpy_fromio`/`memcpy_toio` |
| 64 位寄存器拆分 | 两次 32 位读之间值可能变化，用“高-低-高”读法 |
| `__iomem` + 访问函数 | Linux 的做法：不用 `volatile` 指针，用 `readl`/`writel` 统一保证宽度、顺序和可追踪性 |
