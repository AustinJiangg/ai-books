# 第 1 篇｜从点亮一盏灯说起：程序怎么控制硬件

> **本篇目标**：搞清楚一个看似简单、其实很少有人认真想过的问题：**CPU 只会读写内存、做加减法，它是怎么“指挥”网卡、硬盘、串口这些外部设备的？** 读完本篇，你会知道历史上出现过的两种答案（端口 I/O 和内存映射 I/O），并对 MMIO 有一个准确的一句话理解。

---

## 一、一个被忽略的问题

### 1.1 字是怎么“跑”到屏幕上的

你写过无数次这样的程序：

```c
#include <stdio.h>

int main(void) {
    printf("Hello\n");
    return 0;
}
```

运行之后，终端上出现了 `Hello`。如果再往下追问一句：**这 5 个字母最后是怎么出现在显示器上的？**

学过一点操作系统的人会说：`printf` 调用了 `write` 系统调用，进入内核，内核交给终端驱动，终端驱动再交给显卡驱动……

继续追问：**显卡驱动又是怎么让显卡“动起来”的？** 驱动程序也是一段普通的代码，编译出来也只是一条条 CPU 指令。而 CPU 指令能做的事情，说穿了只有这么几类：

| 指令类别 | 例子 | 干什么 |
|---|---|---|
| 算术逻辑 | 加、减、与、或、移位 | 在 CPU 内部的寄存器之间算数 |
| 访存 | 读内存（load）、写内存（store） | 在 CPU 和内存之间搬数据 |
| 跳转 | 条件跳转、函数调用、返回 | 改变下一条执行哪条指令 |
| 特殊 | 系统调用、开关中断、屏障 | 和操作系统、CPU 自身打交道 |

你会发现，这张表里**没有一条指令叫“让网卡发一个包”或者“让显卡画一个字”**。CPU 的设计者不可能为世界上每一种设备都发明一条专门的指令——设备千千万万，而且每年都有新的。

那问题就来了：**CPU 和外设之间，到底是用什么“语言”沟通的？**

这就是本书要回答的问题。答案的名字叫 **MMIO（Memory-Mapped I/O，内存映射 I/O）**。不过别急，我们先从一个更简单的设备说起。

### 1.2 最简单的设备：一盏 LED 灯

想象一块开发板（比如树莓派）上有一盏 LED 灯，你想写程序让它亮起来。

从电路的角度看，这件事一点都不神秘：LED 接在芯片的一个引脚（叫 **GPIO**，通用输入输出引脚）上，只要让这个引脚输出高电平（比如 3.3 伏），电流流过 LED，它就亮了；输出低电平（0 伏），它就灭了。

所以问题变成了：**程序怎么控制一个引脚的电平？**

芯片里负责管理这些引脚的电路叫 **GPIO 控制器**。它内部有一些小小的存储单元，每一个比特对应一个引脚：

```
GPIO 控制器内部（示意）

  “输出设置”单元：  位 31 ... 位 18  位 17  位 16 ... 位 0
                     0   ...   0      1      0   ...   0
                                      ↑
                                 第 17 号引脚
                                  → 输出高电平 → LED 亮
```

只要往这个单元里写进一个“第 17 位是 1”的数，第 17 号引脚就会变成高电平。电路设计者把这个存储单元的每一位直接连到了引脚的驱动电路上——**写进去的不是“数据”，而是“命令”**。

这种设备内部、专门用来接收命令或反映状态的存储单元，就叫**设备寄存器（device register）**。

> 注意：这里的“寄存器”和 CPU 里的通用寄存器（ARM64 的 `x0`～`x30`）不是一回事。CPU 寄存器在 CPU 内部，用来暂存计算的中间结果；设备寄存器在设备内部，用来接收命令、汇报状态。本书后面说“寄存器”，如果没有特别说明，指的都是**设备寄存器**。

现在问题进一步缩小了：**CPU 怎么把一个数写进 GPIO 控制器的寄存器里？**

## 二、设备的“控制面板”

### 2.1 一个类比：遥控器和仪表盘

在继续之前，我们先建立一个贯穿全书的直觉。

把每个设备想象成一台机器，机器表面有一块**控制面板**：

```
           ┌──────────── 某设备的控制面板 ────────────┐
           │                                         │
           │  [开关] 启用    [开关] 中断    [按钮] 开始 │  ← 控制寄存器：你来拨
           │                                         │
           │  (灯) 忙碌      (灯) 出错      (灯) 完成  │  ← 状态寄存器：你来看
           │                                         │
           │  [投币口] 数据进   [取物口] 数据出        │  ← 数据寄存器：你来存取
           │                                         │
           └─────────────────────────────────────────┘
```

- **开关和按钮**：你拨动它们，机器就照着做。对应**控制寄存器**。
- **指示灯**：机器用它们告诉你现在的状态。对应**状态寄存器**。
- **投币口和取物口**：你从这里塞进数据、取出结果。对应**数据寄存器**。

几乎所有的硬件设备，不管是简单的 LED 控制器，还是复杂的万兆网卡，**从软件的角度看都只是一块控制面板**。驱动程序要做的事情，归根到底就是：在正确的时机，按正确的顺序，拨动正确的开关，查看正确的指示灯。

一块简单的串口芯片可能只有十几个寄存器；一块现代显卡或网卡可能有成千上万个。但原理完全一样。

### 2.2 问题的本质

现在问题已经被我们剥得很干净了：

> CPU 有办法读写内存，但没有专门“拨开关、看指示灯”的指令。**怎样让 CPU 能够读写设备的寄存器？**

历史上，计算机设计者给出了两种答案。

---

## 三、答案一：专门开一扇门（端口 I/O）

### 3.1 思路

第一种思路很直接：**既然现有指令不够用，那就加几条专门访问设备的指令。**

设计者在 CPU 和设备之间开辟一个**独立的“I/O 地址空间”**，和内存地址空间完全分开。每个设备寄存器在这个空间里有一个编号，叫做**端口号（port）**。然后增加两条特殊指令：

- `in`：从某个端口读一个数到 CPU 寄存器；
- `out`：把 CPU 寄存器里的数写到某个端口。

这种方式叫**端口 I/O（Port-Mapped I/O，PMIO）**，也常简称 **PIO**。

### 3.2 x86 的端口空间

最著名的例子就是 Intel x86。从 1978 年的 8086 开始，x86 就有一个独立的 **64K 端口空间**（端口号 0～65535），配套 `in`/`out` 两条指令。直到今天，你的 x86 电脑里仍然保留着这套机制。

一些“老牌”设备的端口号几十年都没变过：

| 端口号（十六进制） | 设备 |
|---|---|
| `0x60`、`0x64` | PS/2 键盘控制器 |
| `0x3F8`～`0x3FF` | 第一个串口（COM1） |
| `0x1F0`～`0x1F7` | 老式 IDE 硬盘控制器 |
| `0x70`、`0x71` | CMOS 实时时钟 |

用 C 语言（借助编译器提供的内联函数）往 COM1 串口发送一个字符，大致长这样：

```c
// x86 专用：往 0x3F8 端口写一个字节
outb('A', 0x3F8);
```

这里的 `outb` 最终会变成一条 `out` 指令。注意 `0x3F8` **不是内存地址**——它是端口空间里的编号。你用普通的指针去访问 `0x3F8` 这个内存地址，碰到的是内存（或者什么都碰不到），而不是串口。

在 x86 Linux 上，可以用这个命令看到端口空间的分配情况（需要 root 才能看到具体数字）：

```
$ sudo cat /proc/ioports
0000-0cf7 : PCI Bus 0000:00
  0000-001f : dma1
  0020-0021 : pic1
  0040-0043 : timer0
  0060-0060 : keyboard
  0064-0064 : keyboard
  0070-0071 : rtc0
  ...
  03f8-03ff : serial
...
```

### 3.3 优点和缺点

端口 I/O 的好处是**泾渭分明**：内存是内存，设备是设备，两者在地址上互不干扰。CPU 一看到 `in`/`out` 指令，就知道这是在跟设备打交道，可以采取特殊的处理方式（比如不经过缓存、严格按顺序执行）。

但它的缺点也很明显：

1. **指令太少、太死板**。只有 `in` 和 `out` 两条，只能在端口和 CPU 寄存器之间搬数据。你没法直接对一个端口做加法、做位运算，也没法用编程语言里熟悉的指针去访问它。
2. **空间太小**。64K 个端口，对于 1980 年代的设备足够了；对于一块需要几百 MB 寄存器和显存空间的现代显卡来说，简直是杯水车薪。
3. **需要专门的硬件支持**。CPU 要多出一套 I/O 总线信号，指令集要多出专门的指令，编译器要提供专门的内联函数。

这就引出了第二种答案。

## 四、答案二：把设备“摆”进内存地址里（MMIO）

### 4.1 思路

第二种思路更巧妙：**不加新指令，而是复用读写内存的指令。**

具体做法是：在内存地址空间里**划出一段地址，不接内存条，而是接到设备的寄存器上**。比如规定地址 `0xFE200000` 开始的一小段，对应 GPIO 控制器的寄存器。那么：

- CPU 执行一条普通的“写内存”指令，目标地址是 `0xFE20001C`；
- 这个写操作被送到总线上，总线发现这个地址属于 GPIO 控制器，于是把数据交给 GPIO 控制器；
- GPIO 控制器把数据写进对应的寄存器，LED 亮了。

从 CPU 的视角看，**它只是做了一次普通的写内存操作**。它根本不知道（也不需要知道）这个地址背后是内存条还是一盏灯。

这就是 **MMIO（Memory-Mapped I/O，内存映射 I/O）**：

> **MMIO 就是把设备的寄存器放进物理地址空间里，让 CPU 用普通的读写内存指令来访问它们。**

### 4.2 一张图看懂两种方式

```
        端口 I/O（PMIO）                         内存映射 I/O（MMIO）

   ┌─────┐                                   ┌─────┐
   │ CPU │                                   │ CPU │
   └──┬──┘                                   └──┬──┘
      │ load/store         in/out               │ load/store（只有这一套）
      ▼                    ▼                    ▼
 ┌──────────┐       ┌──────────────┐     ┌──────────────────────────┐
 │ 内存地址 │       │  I/O 端口空间 │     │       物理地址空间        │
 │  空间    │       │  0 ~ 0xFFFF  │     │ ┌──────┐ ┌──────┐ ┌────┐ │
 │ (内存条) │       │   (各种设备)  │     │ │内存条│ │ 串口 │ │GPIO│ │
 └──────────┘       └──────────────┘     │ └──────┘ └──────┘ └────┘ │
                                         └──────────────────────────┘
   两个独立空间，两套指令                    一个统一空间，一套指令
```

### 4.3 用 C 语言写起来什么样

MMIO 最大的魅力在于：**你可以像访问普通变量一样访问设备**。以树莓派 4 为例，它的 GPIO 控制器寄存器从物理地址 `0xFE200000` 开始，其中偏移 `0x1C` 处的寄存器叫 `GPSET0`，往它的某一位写 1，就能让对应引脚输出高电平。

在没有操作系统的环境里（比如直接在开发板上跑的“裸机”程序），点亮第 17 号引脚上的 LED 可以写成：

```c
#define GPIO_BASE  0xFE200000UL
#define GPSET0     (GPIO_BASE + 0x1C)

// 把地址当成一个“指向 32 位无符号整数的指针”，然后写进去
*(volatile unsigned int *)GPSET0 = 1u << 17;   // LED 亮了
```

（为了简洁，这里省略了“先把 17 号引脚设置为输出模式”这一步。另外，在 Linux 这样的操作系统里，程序不能直接这样访问物理地址，原因和办法我们在第 9 篇和第 11 篇讲。）

这一行代码里有三个值得注意的地方：

1. **地址是一个“写死”的数**。`0xFE20001C` 不是 `malloc` 来的，也不是编译器分配的，而是芯片手册里规定好的。
2. **用的是普通的指针解引用**。编译出来就是一条普通的“写内存”指令（ARM64 上叫 `str`），没有任何特殊指令。
3. **有一个 `volatile` 关键字**。它告诉编译器“这个地址很特殊，别自作聪明地优化”。为什么需要它，它又为什么不够用，是第 4 篇的主题。

对比一下端口 I/O：你必须调用专门的 `outb` 函数，没法用指针；而 MMIO 下，**设备寄存器就是一块“特殊的内存”**，所有能对内存做的操作——用指针、用结构体、做位运算——在语法上都可以对它做。

当然，“语法上可以”不等于“实际上都对”。设备寄存器毕竟不是真的内存，后面大半本书都在讲这两者的区别会带来哪些坑。

### 4.4 MMIO 的优缺点

**优点**：

- **不需要新指令**，CPU 设计更简单；所有访存指令（包括带各种寻址方式的）都能用。
- **地址空间大**。32 位系统有 4GB 地址空间，64 位系统更是大到用不完，可以轻松给设备分配几百 MB 甚至几 GB 的地址范围（比如显卡显存）。
- **编程方便**。用 C 指针就能访问，驱动代码更自然。
- **可以复用内存管理机制**。操作系统可以用页表来控制“哪个程序能访问哪个设备”，就像控制内存访问一样（第 11 篇会讲用户态程序怎么借助 mmap 直接访问设备）。

**缺点**：

- **占用了物理地址空间**。在 32 位时代这是个真问题：4GB 地址里如果给设备划走 1GB，那内存条最多只能用 3GB——这就是当年 32 位 Windows“装了 4GB 内存只认出 3.25GB”的根源之一。64 位时代这个问题基本消失了。
- **“看起来像内存”是一把双刃剑**。编译器和 CPU 都对内存做了大量优化（缓存、合并、重排、预取……），这些优化放在设备寄存器上就会出事。CPU 必须有办法区分“这段地址是内存”和“这段地址是设备”，并对后者区别对待。这是第 4～6 篇的核心话题。

## 五、历史小故事：谁赢了？

### 5.1 PDP-11：把 I/O 放进内存的先驱

MMIO 并不是新发明。1970 年，DEC 公司推出的小型机 **PDP-11** 就采用了这种设计。PDP-11 有一条叫 **Unibus** 的总线，内存和所有外设都挂在这条总线上，共享同一个地址空间。设计者把地址空间**最顶端的 8KB** 划出来，叫做“I/O 页（I/O page）”，所有设备的寄存器都放在这里。

PDP-11 对后世影响极大——C 语言和 Unix 最早就是在 PDP-11 上发展起来的。C 语言里“用指针访问任意地址”的能力，和 PDP-11 这种“一切皆地址”的硬件设计非常契合。

### 5.2 x86：两种都要

Intel 的 8080、8086 选择了端口 I/O，这是 x86 端口空间的由来。但随着设备越来越复杂，端口空间越来越不够用。IBM PC 的显卡从一开始就把**显存**用 MMIO 映射到了内存地址里——著名的文本模式显存就在物理地址 `0xB8000` 处，往那里写字符，屏幕上就会立刻出现对应的文字。

到了 PCI 时代（1990 年代），新设备几乎都改用 MMIO，端口 I/O 只为了兼容老设备而保留。今天的 x86 电脑是一个“混合体”：**两种机制都有，但绝大部分实际的数据交互走的是 MMIO**。一块现代 NVMe 固态硬盘或万兆网卡，基本只用 MMIO。

### 5.3 ARM、RISC-V：只有 MMIO

ARM（包括手机里、Mac 里、服务器里的 ARM64 芯片）从一开始就**没有端口 I/O**——指令集里根本没有 `in`/`out` 这样的指令。所有设备访问一律走 MMIO。RISC-V 也一样。

这其实反映了一种设计哲学：精简指令集（RISC）追求指令少而规整，能用已有指令解决的问题就不加新指令。既然 MMIO 能解决设备访问，端口 I/O 就是多余的。

那 x86 上那些用端口访问的 PCI 设备，接到 ARM 机器上怎么办？答案是：ARM 平台的 PCIe 控制器会把一段 MMIO 地址“翻译”成端口访问——在 CPU 看来还是 MMIO，只是由硬件在背后转换。Linux 内核对此做了封装，驱动程序基本不用操心。

### 5.4 结论

| | 端口 I/O | MMIO |
|---|---|---|
| 访问方式 | 专门的 `in`/`out` 指令 | 普通的读写内存指令 |
| 地址空间 | 独立的 I/O 空间（x86 上 64K） | 与内存共用物理地址空间 |
| 能用指针吗 | 不能 | 能 |
| 现状 | 仅 x86 保留，用于老设备 | 所有架构的主流方式 |

**MMIO 赢了。** 这也是为什么这本书专门讲它——你今天能接触到的几乎所有硬件，从手机的触摸屏到数据中心的网卡，从树莓派的 GPIO 到云服务器里的虚拟设备，都是通过 MMIO 来控制的。

在本书剩下的部分，我们以 **ARM64** 为主要例子（它只有 MMIO，概念最干净），在 x86 有明显差异时再做对比。

## 六、MMIO 和那些容易混淆的词

“MMIO”这个名字里有“内存（Memory）”和“映射（Mapped）”两个词，很容易和其他概念搞混。这里先把它们分清楚。

### 6.1 MMIO 和“内存”

**MMIO 访问的不是内存。** 虽然用的是读写内存的指令，地址也在“内存地址空间”里，但数据既不来自内存条，也不会存进内存条——它直接送到了设备。

打个比方：一条街上的门牌号从 1 号排到 100 号，大部分是住户（内存），但其中第 50 号是邮局（设备）。邮递员（CPU）按门牌号送信，送到 50 号时，信件交给了邮局，邮局会根据信的内容去干别的事。邮局门牌号和住户门牌号在同一套编号里，但邮局不是住户。

所以更准确的说法是：MMIO 访问的是**物理地址空间**，而物理地址空间里**既有内存，也有设备**。这一点是下一篇的主题。

### 6.2 MMIO 和 mmap

如果你读过本仓库的[《mmap 从零讲透》](../mmap/README.md)，可能会问：MMIO 和 mmap 有什么关系？

| | mmap | MMIO |
|---|---|---|
| 是什么 | 一个**系统调用** | 一种**硬件设计方式** |
| 谁提供的 | 操作系统 | 芯片和主板 |
| 干什么 | 把文件或设备映射进进程的**虚拟地址空间** | 把设备寄存器放进**物理地址空间** |
| 层次 | 软件层面（虚拟地址） | 硬件层面（物理地址） |

两者是不同层次的东西，但会在一个地方相遇：**用户态程序想直接访问设备寄存器时，可以用 mmap 把设备的 MMIO 地址映射到自己的虚拟地址空间里**。这是第 11 篇要讲的内容。

### 6.3 MMIO 和 DMA

还有一个经常和 MMIO 一起出现的词：**DMA（Direct Memory Access，直接内存访问）**。

- **MMIO** 是 **CPU 访问设备**：CPU 主动去读写设备的寄存器。
- **DMA** 是 **设备访问内存**：设备主动去读写内存条，不需要 CPU 一个字节一个字节地搬。

它们是合作关系：通常 CPU 用 MMIO 告诉设备“数据在内存哪里、有多长、开始吧”，然后设备用 DMA 自己去搬数据。第 8 篇会专门讲两者如何配合。

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 设备寄存器 | 设备内部用来接收命令、汇报状态、交换数据的存储单元，是设备的“控制面板” |
| 端口 I/O（PMIO） | 设备寄存器放在独立的端口空间里，用专门的 `in`/`out` 指令访问，x86 特有 |
| MMIO | 把设备寄存器放进物理地址空间，用普通的读写内存指令访问 |
| PDP-11 Unibus | 1970 年代采用 MMIO 的经典设计，地址空间顶端 8KB 是 I/O 页 |
| 现状 | ARM、RISC-V 只有 MMIO；x86 两者都有，但主流是 MMIO |
| MMIO vs mmap | MMIO 是硬件把设备放进物理地址；mmap 是软件把东西映射进虚拟地址 |
| MMIO vs DMA | MMIO 是 CPU 访问设备；DMA 是设备访问内存 |
