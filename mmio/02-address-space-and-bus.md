# 第 2 篇｜地址空间与总线：一个地址到底送到了哪里

> **本篇目标**：建立“物理地址空间是一张地图”的直觉。读完本篇，你会明白：CPU 发出的一个地址，是如何被硬件“分拣”到内存条或某个设备的；一台真实机器的地址地图长什么样；操作系统又是怎么知道每个设备住在哪里的。

---

## 一、物理地址空间：一张城市地图

### 1.1 地址不等于内存

上一篇我们说，MMIO 就是把设备寄存器“摆”进地址空间里。这句话隐含了一个很多新手没意识到的事实：

> **地址空间和内存不是一回事。地址空间是一套“编号系统”，内存只是占用了其中一部分编号。**

ARM64 处理器通常支持 48 位甚至 52 位的物理地址，也就是说，它能发出的物理地址范围从 `0` 一直到 `0xFFFF_FFFF_FFFF`（256TB）。但你的机器不可能装 256TB 内存。那这么多地址都干什么用了？

答案是：**大部分地址什么都没有接，是空着的；一部分接了内存条；还有一部分接了各种设备。**

### 1.2 城市地图的类比

把物理地址空间想象成一座城市的门牌号系统：

```
                    物理地址空间 = 一座城市
 ┌──────────────────────────────────────────────────────────────┐
 │  1 号～ 99 号街：    ROM 区       （开机用的固件，只能读）      │
 │  100 号～199 号街：  设备区       （串口、中断控制器、时钟……）  │
 │  200 号～999 号街：  PCIe 区      （网卡、显卡、硬盘……）        │
 │  1000 号街以后：     住宅区       （内存条）                    │
 │  ……更远的地方：      荒地         （什么都没有）                │
 └──────────────────────────────────────────────────────────────┘
```

- 每条街是一段连续的地址范围；
- 有的街住的是居民（内存），往里面存什么、取出来就是什么；
- 有的街是工厂和机关（设备），你送进去一张单子，它们会根据单子内容去做事；
- 有的街是荒地（空洞），什么都没有，往那里送信会被退回来，甚至引发事故。

这张“城市规划图”是谁画的？**是芯片设计者和主板设计者。** 芯片在设计时就决定了：哪段地址接内存控制器，哪段地址接串口，哪段地址留给 PCIe。这张规划图通常写在芯片的技术参考手册里，叫做**内存映射（memory map）** 或**地址映射（address map）**。

> 注意“内存映射”这个词：在硬件手册里，memory map 指的是**这张地址规划图**；在操作系统里，memory mapping 常常指 mmap 那种把文件映射进虚拟地址空间的操作。两者不是一回事，看上下文区分。

## 二、地址译码：快递分拣中心

### 2.1 CPU 不知道地址背后是谁

当 CPU 执行一条“往地址 `0x09000000` 写入 `0x41`”的指令时，它其实**并不知道**这个地址背后是内存还是设备。它只是把“地址 + 数据 + 这是一次写操作”这三样东西打包，发到芯片内部的“道路网”上。

真正决定这个包裹送到哪里的，是一个专门的部件：**地址译码器（address decoder）**。

### 2.2 分拣的过程

把它想象成一个快递分拣中心：

```
                         CPU 发出：写 0x09000000，数据 0x41
                                        │
                                        ▼
                         ┌──────────────────────────────┐
                         │   互连 / 总线（分拣中心）       │
                         │                              │
                         │   查规划表：                   │
                         │   0x00000000~0x07FFFFFF → ROM │
                         │   0x08000000~0x0800FFFF → GIC │
                         │   0x09000000~0x09000FFF → 串口 │ ← 命中！
                         │   0x40000000~...        → 内存 │
                         └──────────┬───────────────────┘
                 ┌──────────┬───────┼────────┬──────────┐
                 ▼          ▼       ▼        ▼          ▼
               ROM        GIC     串口      PCIe       内存控制器
                                    │
                                    ▼
                           串口内部再看低位：
                           偏移 0x000 → 数据寄存器
                           → 把 0x41（字母 'A'）发出去
```

这个过程分两层：

1. **第一层：找到设备。** 分拣中心看地址的**高位**，判断它落在哪个设备的范围里。`0x09000000` 落在串口的范围 `0x09000000`～`0x09000FFF` 里，于是交给串口。
2. **第二层：找到寄存器。** 串口收到后，看地址的**低位**（相对于自己起始地址的偏移量）。偏移量是 `0x000`，对应的是数据寄存器，于是把 `0x41` 当作要发送的字符。

这就引出了 MMIO 里最常用的两个概念：

- **基址（base address）**：设备在地址空间里的起始地址。比如串口的基址是 `0x09000000`。
- **偏移量（offset）**：某个寄存器相对于基址的距离。比如数据寄存器的偏移量是 `0x000`，标志寄存器的偏移量是 `0x018`。

> **寄存器的物理地址 = 设备基址 + 寄存器偏移量**

设备的手册里只写偏移量（因为同一款设备可以被放在不同芯片的不同位置），芯片的手册里再告诉你基址。两者一加，就是你要访问的地址。

### 2.3 总线和互连

在早期的计算机里，CPU、内存、设备真的是挂在**同一组导线**上的，这组导线叫**总线（bus）**。所有人都能“听见”总线上传输的地址，每个设备自己判断“这个地址是不是我的”，是就响应，不是就忽略。

现代芯片（尤其是手机、服务器里的 **SoC**，System on Chip，片上系统——把 CPU、内存控制器、各种设备控制器都集成在一块芯片上）内部要复杂得多。它们用的是**片上互连（interconnect）**，更像一张有很多路口和立交桥的道路网，而不是一根总线。

在 ARM 的世界里，你会经常看到两个名字：

- **AXI**：高性能的互连协议，用来连接 CPU、内存控制器、高速设备。好比城市里的高速公路。
- **APB**：简单、低速的外设总线，用来连接串口、定时器、GPIO 这类慢速设备。好比小区里的支路。

一次对串口的访问，可能要先走 AXI 高速公路，再经过一个“桥”下到 APB 小路，最后到达串口。这些细节对软件来说基本是透明的，你只需要知道两件事：

1. 访问设备的路比访问内存的路**长得多、慢得多**。读一个设备寄存器可能要几百纳秒，而读一个已在缓存里的内存变量只要一纳秒左右。
2. 路上有很多“中转站”，数据可能在某个中转站**暂存一会儿**。这会带来顺序问题，第 6 篇详细讲。

尽管现代硬件里已经不是一根真正的“总线”了，人们仍然习惯把这一整套机制叫做“总线”。本书也沿用这个说法。

## 三、读一张真实的地址地图

### 3.1 QEMU `virt` 机器

讲了这么多抽象概念，我们来看一张真实的地图。这里选用 **QEMU 的 `virt` 机器**——QEMU 是一个常用的开源虚拟机/模拟器，`virt` 是它专门为 ARM64 设计的一款“虚拟主板”，没有任何历史包袱，地址布局非常清晰。很多 ARM64 Linux 的开发和测试都在它上面进行。

它的地址地图（只列出主要部分）如下：

```
物理地址范围                      大小      住着谁
───────────────────────────────────────────────────────────────
0x0000_0000 ~ 0x07FF_FFFF        128MB    Flash（存放固件，开机从这里开始执行）
0x0800_0000 ~ 0x0800_FFFF         64KB    GIC 分发器（中断控制器的一部分）
0x0801_0000 ~ 0x0801_FFFF         64KB    GIC CPU 接口
0x080A_0000 ~ ...                         GIC 重分发器（GICv3 时）
0x0900_0000 ~ 0x0900_0FFF          4KB    UART 串口（PL011）
0x0901_0000 ~ 0x0901_0FFF          4KB    RTC 实时时钟（PL031）
0x0902_0000 ~ ...                         fw_cfg（QEMU 向固件传配置用）
0x0903_0000 ~ 0x0903_0FFF          4KB    GPIO 控制器（PL061）
0x0A00_0000 ~ 0x0A00_3FFF         16KB    32 个 virtio-mmio 设备槽，每个 512 字节
0x1000_0000 ~ 0x3EFE_FFFF       ~750MB    PCIe MMIO 窗口（给 PCIe 设备分配地址用）
0x3EFF_0000 ~ 0x3EFF_FFFF         64KB    PCIe I/O 窗口（模拟端口 I/O 用）
0x3F00_0000 ~ 0x3FFF_FFFF         16MB    PCIe 配置空间（ECAM）
0x4000_0000 ~ ...                         内存（RAM），你给虚拟机配多少就有多大
```

这张图值得仔细看一会儿，它能告诉你很多事情：

1. **内存从 1GB（`0x4000_0000`）处才开始**。地址 0～1GB 全部留给了固件和设备。这在 ARM 平台上很常见——内存往往不从 0 开始。
2. **小设备每个占 4KB**。串口其实只有十几个寄存器，用不了 4KB，但为了方便操作系统用页表管理（一页正好 4KB），通常给每个设备分配至少一页。
3. **有很多空洞**。比如 `0x0904_0000` 到 `0x09FF_FFFF` 之间大部分地方什么都没有。
4. **PCIe 有一大块“窗口”**。PCIe 设备的地址不是写死的，而是开机时动态分配的，这块窗口就是给它们准备的“预留地”。第 10 篇会细讲。
5. **连“中断控制器”自己也是一个 MMIO 设备**。第 7 篇会讲到它。

### 3.2 真实芯片的地图

真实的 ARM64 芯片（比如树莓派 4 的 BCM2711、手机里的骁龙、服务器里的鲲鹏）的地图要复杂得多，可能有几百个设备区域，但结构是一样的：**一部分给内存，一部分给各种设备，剩下的是空洞。**

举个例子，树莓派 4（在默认的“低外设”模式下）把大部分外设放在 `0xFC00_0000`～`0xFF7F_FFFF` 这一段，上一篇提到的 GPIO 控制器就在 `0xFE20_0000`。

## 四、在 Linux 上看地图：`/proc/iomem`

### 4.1 怎么看

Linux 内核在启动时会弄清楚整张地址地图，并把它通过 `/proc/iomem` 这个文件展示出来。在一台 ARM64 Linux 机器（比如跑在 QEMU `virt` 上的 Linux）上用 root 权限查看，大致是这样：

```
$ sudo cat /proc/iomem
04000000-07ffffff : 0.flash flash@0
09000000-09000fff : pl011@9000000
  09000000-09000fff : 9000000.pl011 pl011@9000000
09010000-09010fff : pl031@9010000
  09010000-09010fff : rtc-pl031
09030000-09030fff : pl061@9030000
  09030000-09030fff : pl061@9030000
0a003e00-0a003fff : a003e00.virtio_mmio virtio_mmio@a003e00
10000000-3efeffff : pcie@10000000
  10000000-100fffff : 0000:00:01.0
    10000000-10003fff : 0000:00:01.0
      10000000-10003fff : nvme
3f000000-3fffffff : PCI ECAM
40000000-bfffffff : System RAM
  40210000-415dffff : Kernel code
  41630000-41b8ffff : Kernel data
```

（具体内容会因为 QEMU 配置和内核版本不同而有差异，这里只是示意。）

### 4.2 怎么读

每一行的格式是 `起始地址-结束地址 : 名字`。缩进表示**包含关系**：缩进的那一行是它上面那一行的一部分。

逐行解读几处：

- `09000000-09000fff : pl011@9000000`：这 4KB 是 PL011 串口的地盘。下一行缩进的 `9000000.pl011` 表示串口驱动已经“认领”了这段地址——第 9 篇会讲驱动如何认领。
- `0a003e00-0a003fff : ... virtio_mmio`：一个 virtio-mmio 设备，只占 512 字节（`0x200`）。注意它是 32 个槽位里的最后一个——QEMU 从高地址往低地址分配 virtio-mmio 槽位。
- `10000000-3efeffff : pcie@10000000`：PCIe 窗口。下面缩进的几行说明：PCI 地址为 `0000:00:01.0` 的设备（这里是一块 NVMe 硬盘）分到了 `0x10000000` 开始的一段，并且被 `nvme` 驱动认领了。
- `40000000-bfffffff : System RAM`：这才是真正的内存，2GB。下面缩进的“Kernel code”“Kernel data”是内核自己的代码和数据所在位置。

对比上一节的 QEMU 地图，你会发现两者完全吻合。`/proc/iomem` 就是内核眼中的“城市地图”。

> 小提示：普通用户查看 `/proc/iomem` 时，所有地址都会显示成 0，这是出于安全考虑（隐藏内核在物理内存中的位置）。要看真实地址必须用 root。

### 4.3 x86 上的样子

在 x86 电脑上，`/proc/iomem` 的样子不一样，但道理相同。你会看到一些“历史遗迹”，比如：

```
000a0000-000bffff : PCI Bus 0000:00        ← 老式 VGA 显存，包括文本模式的 0xB8000
000c0000-000c7fff : Video ROM
000f0000-000fffff : System ROM
00100000-xxxxxxxx : System RAM
...
fec00000-fec003ff : IOAPIC 0               ← 中断控制器
fed00000-fed003ff : HPET 0                 ← 高精度定时器
fee00000-fee00fff : Local APIC             ← 每个 CPU 核自己的中断控制器
```

x86 的内存从 0 开始，但在 640KB～1MB 之间“挖”了一个洞给老式设备，在 4GB 以下又“挖”了一大块给 PCI 设备（这就是上一篇说的“32 位系统装 4GB 内存只认 3GB 多”的原因）。

## 五、系统怎么知道设备住在哪？

地图是芯片设计者画的，但操作系统内核并不是芯片设计者。内核启动时，它怎么知道串口在 `0x09000000` 而不是别的地方？这个问题有几种答案。

### 5.1 方法一：写死在代码里

最原始的办法：为每一款芯片专门写一份代码，把地址直接写进去。

```c
#define UART_BASE 0x09000000   // 只适用于 QEMU virt
```

在没有操作系统的小型嵌入式程序里，这很常见。但对 Linux 这样要支持成千上万种芯片的系统来说，这样做是灾难——早年 ARM Linux 确实是这么干的，每款芯片都要一堆专门的代码，结果内核里的 ARM 代码臃肿不堪，连 Linus Torvalds 都公开抱怨过。

### 5.2 方法二：设备树（Device Tree）

ARM Linux 后来的解决方案是**设备树**：把“这台机器上有哪些设备、住在哪里”写成一份独立的描述文件，由固件或引导程序交给内核。内核读这份文件，就知道该加载哪些驱动、每个设备的地址是多少。

设备树的源文件（`.dts`）长这样（节选，描述 QEMU `virt` 的串口）：

```
pl011@9000000 {
    compatible = "arm,pl011", "arm,primecell";
    reg = <0x00 0x09000000 0x00 0x1000>;
    interrupts = <0x00 0x01 0x04>;
    clock-names = "uartclk", "apb_pclk";
};
```

几个关键字段：

- `compatible`：这是什么型号的设备。内核据此找到能驱动它的驱动程序（这里是 ARM 的 PL011 串口驱动）。
- `reg`：**这个设备的 MMIO 地址范围**。`<0x00 0x09000000 0x00 0x1000>` 的意思是：起始地址是 `0x0_09000000`（用两个 32 位数拼成 64 位），长度是 `0x0_00001000`（4KB）。
- `interrupts`：这个设备用哪个中断号（第 7 篇讲）。

有了设备树，**同一份内核可以在不同的 ARM 板子上启动**，只要换一份设备树就行。这是 ARM Linux 历史上非常重要的一次改进。

在一台运行中的 Linux 机器上，内核解析后的设备树可以在 `/proc/device-tree/`（或 `/sys/firmware/devicetree/base/`）下看到，每个节点是一个目录，每个属性是一个文件。

### 5.3 方法三：ACPI

x86 电脑（以及一部分 ARM64 服务器）用的是另一套机制：**ACPI**（高级配置与电源接口）。它的思路和设备树类似——固件提供一组描述表，告诉操作系统有哪些设备、在哪里——只是格式更复杂，还能包含一些可执行的“小程序”（AML 字节码），用来处理电源管理等复杂操作。

ARM64 的服务器平台通常两种都支持，或者用 ACPI；嵌入式和手机平台基本只用设备树。

### 5.4 方法四：让设备自己报上来（PCI 枚举）

前三种方法都是“由别人告诉内核设备在哪里”。PCI/PCIe 则不同：**设备自己有一份“身份证”，内核可以主动去问。**

PCIe 设备插上之后，内核（或固件）会逐个扫描总线上的槽位，问每个设备：“你是谁？你需要多大的地址空间？”然后从 PCIe 窗口里划出一块分配给它。这就是上一节地图里那一大块 PCIe 窗口的用途。

这个过程叫**枚举（enumeration）**，是第 10 篇的主题。

### 5.5 小结

| 方法 | 谁提供信息 | 适用场景 |
|---|---|---|
| 写死在代码里 | 程序员 | 裸机程序、小型嵌入式系统 |
| 设备树 | 固件/引导程序传给内核的描述文件 | ARM、RISC-V 嵌入式和手机 |
| ACPI | 固件提供的描述表 | x86 电脑、部分 ARM64 服务器 |
| PCI 枚举 | 设备自己报告需求，系统动态分配 | 所有平台上的 PCI/PCIe 设备 |

## 六、访问一个“空洞”会怎样

地图上有大量空洞，如果程序不小心访问了一个空洞地址，会发生什么？

这取决于硬件的设计，大致有几种结果：

1. **总线报错，CPU 收到异常**。在 ARM64 上，这叫**外部中止（External Abort）**，是一种“同步”或“异步”的错误异常（SError）。CPU 会跳进内核的异常处理程序，内核通常会打印一堆错误信息，然后杀掉进程，甚至整个系统崩溃（kernel panic）。
2. **读回全 F**。很多总线在没有设备响应时，会返回全 1 的数据（`0xFFFFFFFF`）。PCI 总线尤其如此：读一个不存在的 PCI 设备，得到的就是全 F。驱动程序里常见这样的检查：“如果读回来是 `0xFFFFFFFF`，说明设备可能已经被拔掉了或者挂了。”
3. **悄无声息地什么都不发生**。有的总线对空洞地址的写操作直接丢弃，读操作返回 0。这是最危险的，因为程序不会发现自己出错了。

还有一种更隐蔽的情况：地址是对的，但设备**还没上电**或者**时钟没打开**。在手机芯片上，为了省电，很多设备平时是断电的。这时候去访问它的寄存器，可能会卡死整个总线，导致系统直接冻住。这也是嵌入式驱动开发中一类经典的“灵异 bug”。

> 结论：**MMIO 的地址必须准确，访问前设备必须准备好。** 普通内存访问出错，最多是程序崩溃；MMIO 访问出错，可能让整台机器挂掉。

## 七、物理地址和虚拟地址

到这里为止，我们讨论的都是**物理地址**——总线上真正跑的那个地址。但是如果你读过[《mmap 从零讲透》第 3 篇](../mmap/03-virtual-memory.md)，就知道：**CPU 上运行的程序看到的其实是虚拟地址**，要经过 MMU（内存管理单元）根据页表翻译之后，才变成物理地址。

所以完整的路径是：

```
程序里的指针（虚拟地址）
      │
      │  MMU 查页表翻译
      ▼
物理地址
      │
      │  互连/总线 按地址译码
      ▼
内存条 或 某个设备的寄存器
```

这意味着：

1. **要访问一个设备，必须先有一条页表映射**，把某个虚拟地址翻译到设备的物理地址上。在没有开启 MMU 的裸机程序里，虚拟地址就等于物理地址，所以上一篇点 LED 的代码可以直接用 `0xFE20001C`。但在 Linux 里，内核和用户程序都运行在开启了 MMU 的环境中，必须先建好映射。
2. **页表不仅负责地址翻译，还负责标注“这块地址是什么性质”**。同样是一页物理地址，是普通内存还是设备，是否允许缓存，这些属性都写在页表项里。这对 MMIO 至关重要，第 5 篇详细讲。
3. Linux 内核提供了 `ioremap` 函数来建立这种映射（第 9 篇），用户程序则可以借助 `mmap` 来做（第 11 篇）。

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 物理地址空间 | 一套地址编号系统，其中一部分接内存，一部分接设备，其余是空洞 |
| 内存映射（memory map） | 芯片手册里的地址规划图，规定每段地址接的是什么 |
| 地址译码 | 总线/互连根据地址高位找到设备，设备再根据低位找到寄存器 |
| 基址 + 偏移量 | 寄存器物理地址 = 设备在地图上的起点 + 寄存器在设备内的位置 |
| SoC 与片上互连 | 现代芯片内部用 AXI、APB 等协议组成的“道路网”代替单根总线 |
| `/proc/iomem` | Linux 展示物理地址地图的文件，需要 root 才能看到真实地址 |
| 设备树 / ACPI | 固件告诉内核“有哪些设备、在哪里”的两种方式 |
| PCI 枚举 | 设备自报需求，系统动态分配地址 |
| 空洞访问 | 可能报错（外部中止）、读回全 F，或被静默忽略 |
| 虚拟地址 → 物理地址 | 访问设备前必须先有页表映射，页表还负责标记设备属性 |
