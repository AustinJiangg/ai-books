# 第 11 篇｜在用户态访问 MMIO：/dev/mem、UIO 与 VFIO

> **本篇目标**：理解普通用户程序如何借助 mmap 直接访问设备寄存器。读完本篇，你会认识从最原始到最安全的三种方式——`/dev/mem`、UIO、VFIO，知道 sysfs 的 `resource` 文件怎么用，明白 DPDK、SPDK 为什么要把驱动搬到用户态，以及这样做有哪些风险。

---

## 一、用户程序能直接摸硬件吗

### 1.1 通常的路径

在 Linux 里，用户程序访问硬件的“正规”路径是：**通过系统调用，请内核驱动代劳**。

```
用户程序
   │ read() / write() / ioctl()          ← 系统调用
   ▼
内核：文件系统 / 网络协议栈 / 块设备层……
   │
   ▼
内核驱动：readl() / writel()            ← 真正的 MMIO 访问在这里
   │
   ▼
设备
```

这条路很安全：内核检查权限，驱动负责正确地操作硬件，用户程序就算写错了也不会把机器搞坏。但它也有代价：

- 每次系统调用都要从用户态切换到内核态，再切换回来（这个开销在[《mmap 从零讲透》第 1 篇](../mmap/01-reading-a-file.md)里讲过）；
- 数据要经过内核的好几层处理，可能还要在内核和用户空间之间拷贝；
- 想支持一种新设备，必须写内核驱动，而内核开发的门槛和风险都比较高。

### 1.2 能不能绕过内核

那么，能不能让用户程序**直接**读写设备寄存器，完全绕过内核？

答案是：**可以，而且办法就是 mmap。**

回顾一下前面的知识：

- 第 2 篇：设备寄存器有一个**物理地址**；
- 第 9 篇：内核访问它之前，要用 `ioremap` 在**内核页表**里建立一个映射；
- [《mmap 从零讲透》](../mmap/README.md)：mmap 的本质，就是在**进程页表**里建立映射。

把这几点串起来：如果能在**用户进程的页表**里建立一个映射，让某段用户虚拟地址指向设备的物理地址，并且设好 Device 内存属性，那么用户程序就可以像访问普通数组一样访问设备寄存器了。

```
  用户进程虚拟地址空间                           物理地址空间
  ┌──────────────────┐                       ┌──────────────────┐
  │                  │                       │                  │
  │ regs ──────────────── 进程页表映射 ───────→│ 设备寄存器        │
  │ (mmap 返回的指针) │   属性 = Device        │                  │
  │                  │   权限 = 用户可读写     │                  │
  └──────────────────┘                       └──────────────────┘

  之后：regs[0x14/4] = 1;   ← 一条普通的 str 指令，直达设备，不经过内核
```

这一切都在一次 mmap 调用中建立。之后用户程序访问设备寄存器，**没有系统调用、没有上下文切换、没有数据拷贝**——速度和内核驱动访问寄存器完全一样。

问题在于：**谁来提供这个 mmap 的“文件”？** 用户程序总得打开一个文件，才能对它调用 mmap。Linux 提供了好几种这样的文件，从最原始到最安全，我们一个个看。

## 二、`/dev/mem`：最原始的方式

### 2.1 是什么

`/dev/mem` 是一个特殊的字符设备文件，它代表**整个物理地址空间**。文件里的偏移量就等于物理地址：

- 读 `/dev/mem` 的偏移 `0x09000000`，就是读物理地址 `0x09000000`；
- 对 `/dev/mem` 做 mmap，偏移量填 `0x09000000`，就把物理地址 `0x09000000` 映射进了进程。

### 2.2 示例

用 `/dev/mem` 读一个设备寄存器：

```c
#include <fcntl.h>
#include <stdint.h>
#include <stdio.h>
#include <sys/mman.h>
#include <unistd.h>

int main(void) {
    int fd = open("/dev/mem", O_RDWR | O_SYNC);
    if (fd < 0) { perror("open"); return 1; }

    // 把物理地址 0x09000000 开始的 4KB 映射进来
    volatile uint32_t *regs = mmap(NULL, 4096,
                                   PROT_READ | PROT_WRITE, MAP_SHARED,
                                   fd, 0x09000000);
    if (regs == MAP_FAILED) { perror("mmap"); return 1; }

    // 读 PL011 的标志寄存器（偏移 0x018 = 第 6 个 32 位字）
    uint32_t fr = regs[0x018 / 4];
    printf("UARTFR = 0x%08x\n", fr);

    munmap((void *)regs, 4096);
    close(fd);
    return 0;
}
```

几个要点：

- **需要 root 权限**（准确地说是 `CAP_SYS_RAWIO` 能力）。
- **偏移量必须按页对齐**（通常是 4KB 的整数倍）。如果寄存器不在页边界上，就映射它所在的整页，再加上页内偏移。
- **`O_SYNC` 标志**：在一些架构上，它提示内核把这段映射设成不可缓存。在 ARM64 上，内核会根据物理地址是否属于普通内存来自动选择属性：不是内存的地址（也就是设备）会被映射成 Device 类型。
- **指针要加 `volatile`**：用户态程序没有 `readl`/`writel` 这些内核函数，只能自己用 `volatile` 指针。第 4 篇讲的那些坑（编译器优化、访问宽度）在这里全都适用。第 6 篇讲的屏障问题，在需要时也得自己处理（比如用编译器提供的内置屏障函数）。

第 9 篇提到的 `devmem` 工具，原理就是这段代码。

### 2.3 安全限制

`/dev/mem` 能访问整个物理地址空间，包括**所有内存**——内核代码、内核数据、其他进程的数据、密码、密钥……一个有 root 权限的程序可以通过它读取或篡改任何东西。这对安全来说是个巨大的漏洞。

所以现代 Linux 对 `/dev/mem` 加了好几层限制：

| 内核配置 | 作用 |
|---|---|
| `CONFIG_STRICT_DEVMEM` | 禁止通过 `/dev/mem` 访问**普通内存**（RAM），只允许访问设备区域等少数地址。几乎所有发行版都开启了 |
| `CONFIG_IO_STRICT_DEVMEM` | 更进一步：禁止访问**已经被内核驱动认领的**设备区域（就是 `/proc/iomem` 里被驱动登记过的那些） |
| 内核锁定（lockdown）模式 | 开启安全启动（Secure Boot）时，内核可能完全禁止 `/dev/mem` |

第二条限制很有意义：如果一个设备已经有内核驱动在管理，用户程序再通过 `/dev/mem` 去戳它的寄存器，两边就会互相干扰（第 9 篇讲 `request_mem_region` 时说过这个问题）。

所以 `/dev/mem` 主要用于**调试**和**嵌入式开发**：在没有驱动的情况下，快速验证一下硬件的行为。正式的产品代码很少依赖它。

## 三、sysfs 的 `resource` 文件：直接映射 PCI BAR

### 3.1 是什么

对于 PCI 设备，有一个比 `/dev/mem` 更方便、更有针对性的方法。上一篇提到，Linux 在每个 PCI 设备的 sysfs 目录下提供了 `resource0`、`resource1`…… 这样的文件：

```
$ ls /sys/bus/pci/devices/0000:03:00.0/
...  resource  resource0  ...
```

**每个 `resourceN` 文件对应设备的第 N 个 BAR**。对它做 mmap，偏移量从 0 开始，就直接映射到这个 BAR 的 MMIO 区域。

```c
int fd = open("/sys/bus/pci/devices/0000:03:00.0/resource0", O_RDWR | O_SYNC);
volatile uint32_t *bar0 = mmap(NULL, 16384, PROT_READ | PROT_WRITE,
                               MAP_SHARED, fd, 0);

uint32_t version = bar0[0x08 / 4];   // 读 NVMe 的 VS 寄存器
```

和 `/dev/mem` 相比：

- **不用知道物理地址**：BAR 的地址是动态分配的（上一篇），每次开机可能不一样，但 `resource0` 永远指向 BAR 0。
- **范围受限**：只能访问这一个 BAR，不能越界去访问别的东西。
- **仍然需要 root 权限**。

### 3.2 写合并版本

如果一个 BAR 是**可预取**的（上一篇），sysfs 还会提供一个 `resourceN_wc` 文件。对它做 mmap，得到的是**写合并**属性的映射（第 5 篇）。用户态的图形程序可以用它来高效地写显存。

### 3.3 内核那边是怎么做的

不管是 `/dev/mem` 还是 `resourceN`，内核在处理 mmap 请求时做的事情都差不多：

1. 检查权限和地址范围；
2. 计算出要映射的物理页号；
3. **设置内存属性**：用 `pgprot_noncached()`（不可缓存/Device）或 `pgprot_writecombine()`（写合并）修改页表属性；
4. 调用 `remap_pfn_range()`（或 `io_remap_pfn_range()`），把物理页直接填进用户进程的页表。

和普通文件的 mmap 不同，这里**没有页缓存、没有缺页时才读盘**（《mmap 从零讲透》第 6 篇讲的那些），页表项在 mmap 调用时就一次性建好了，直接指向设备的物理地址。如果你自己写一个内核驱动，想让用户程序能 mmap 你的设备寄存器，也是在驱动的 `mmap` 回调里做这几步。

## 四、UIO：最小的用户态驱动框架

### 4.1 只有 MMIO 还不够

有了 `resource0`，用户程序可以读写设备寄存器了。但一个完整的驱动还需要处理**中断**（第 7 篇）。中断是由 CPU 硬件直接送到内核的，用户程序没法直接接收。

**UIO**（Userspace I/O，用户空间 I/O）是 Linux 提供的一个小框架，专门解决这个问题。它的设计哲学是：**内核里只放一个极小的“桩”驱动，负责最基本的事情；真正的驱动逻辑全部在用户态实现。**

### 4.2 UIO 怎么用

当一个设备绑定到 UIO 驱动后，系统里会出现一个设备文件 `/dev/uioN`。用户程序通过它做两件事：

**一、映射 MMIO 区域**

UIO 设备的可映射区域列在 `/sys/class/uio/uioN/maps/` 下面。用户程序对 `/dev/uioN` 做 mmap，用偏移量来选择映射哪一块（第 0 块用偏移 0，第 1 块用偏移 1 页，以此类推）：

```c
int fd = open("/dev/uio0", O_RDWR);
volatile uint32_t *regs = mmap(NULL, size, PROT_READ | PROT_WRITE,
                               MAP_SHARED, fd, 0 * getpagesize());
```

**二、等待中断**

对 `/dev/uioN` 调用 `read()`，会**阻塞**，直到设备发生一次中断。`read` 返回一个 32 位整数，表示到目前为止总共发生了多少次中断：

```c
uint32_t count;
while (1) {
    read(fd, &count, sizeof(count));   // 阻塞，直到中断发生
    // 中断来了！通过 regs 读设备状态、处理数据、清中断……
    handle_device(regs);
    // 对于某些 UIO 驱动，需要写 1 来重新启用中断
    uint32_t one = 1;
    write(fd, &one, sizeof(one));
}
```

内核里那个小小的“桩”驱动，在中断到来时只做最少的事：关掉这个中断（防止第 7 篇讲的中断风暴），然后唤醒正在 `read` 的用户程序。用户程序处理完、清除了设备上的中断之后，再通过 `write` 重新打开中断。

### 4.3 UIO 的局限

UIO 简单易用，但有几个明显的缺陷：

1. **没有 DMA 保护**。用户程序可以让设备往任意物理地址做 DMA（第 8 篇），完全绕过了内存保护。一个有 bug 的用户态驱动可以破坏整个系统的内存。
2. **用户程序很难拿到 DMA 地址**。要让设备 DMA，用户程序得知道自己的缓冲区对应的物理地址，而用户态程序本来是看不到物理地址的。实际使用时需要各种不太优雅的手段（比如通过 `/proc/self/pagemap` 查，或者用大页并锁住内存）。
3. **中断支持有限**。比如通用的 `uio_pci_generic` 驱动只支持传统的中断线，不支持 MSI-X（第 7 篇）。

所以 UIO 主要适合**简单的、不需要 DMA 的设备**，或者在**可信环境**下的嵌入式应用。对于需要高性能 DMA 的场景，需要更好的方案。

## 五、VFIO：安全的用户态设备访问

### 5.1 核心思想：用 IOMMU 兜底

**VFIO**（Virtual Function I/O）是 Linux 提供的一个更完善、更安全的用户态设备访问框架。它最初是为**虚拟机设备直通**设计的（把一块物理网卡直接交给虚拟机使用，第 12 篇），后来也被广泛用于用户态驱动。

VFIO 和 UIO 最大的区别是：**它强制要求使用 IOMMU**（第 8 篇）。

回顾一下：IOMMU 是“设备的 MMU”，它规定了一个设备能通过 DMA 访问哪些内存。VFIO 利用这一点：

- 用户程序只能让设备 DMA 到**它自己明确注册过的内存**；
- 设备发出的 DMA 地址要经过 IOMMU 翻译和检查，越界的访问会被拦截。

这样，即使用户态驱动有 bug，甚至是恶意的，**它最多只能破坏自己的内存，碰不到内核或其他进程**。这让“把设备交给一个非特权程序或虚拟机”变得真正安全。

### 5.2 三层结构

传统的 VFIO 接口有三个层次的概念：

```
  ┌────────────────────────────────────────────────┐
  │ 容器（container）  /dev/vfio/vfio               │
  │   代表一套 IOMMU 地址空间（一张“设备页表”）       │
  │                                                │
  │   ┌──────────────────────────────────────┐     │
  │   │ 组（group）  /dev/vfio/12            │     │
  │   │   IOMMU 能隔离的最小单位               │     │
  │   │   （有时几个设备必须一起分配）          │     │
  │   │                                      │     │
  │   │   ┌──────────────┐ ┌──────────────┐  │     │
  │   │   │ 设备 03:00.0 │ │ 设备 03:00.1 │  │     │
  │   │   └──────────────┘ └──────────────┘  │     │
  │   └──────────────────────────────────────┘     │
  └────────────────────────────────────────────────┘
```

- **组（group）**：由于硬件拓扑的原因，有些设备之间可以绕过 IOMMU 互相访问（比如同一块卡上的多个功能），IOMMU 无法把它们隔离开。这样的一组设备必须**作为一个整体**分配给同一个用户。
- **容器（container）**：代表一个 IOMMU 地址空间。可以把多个组放进同一个容器，让它们共享同一套 DMA 映射。
- **设备（device）**：最终要操作的那个设备。

（较新的内核还引入了一套叫 **iommufd** 的新接口，可以直接通过 `/dev/vfio/devices/vfioN` 这样的字符设备打开单个设备，简化了组和容器的概念。但核心思路不变。）

### 5.3 使用流程

使用 VFIO 的大致步骤（省略了错误处理和很多细节）：

```
① 把设备从原来的内核驱动上解绑，绑定到 vfio-pci 驱动
   （通常用一个脚本，或者 driverctl 之类的工具）

② 打开容器和组，把组放进容器，设置 IOMMU 类型

③ 从组里拿到设备的文件描述符 device_fd

④ 查询设备的 MMIO 区域：
   ioctl(device_fd, VFIO_DEVICE_GET_REGION_INFO, &info)
   → 得到 BAR 0 在 device_fd 里的偏移量、大小、是否可 mmap

⑤ 映射 MMIO：
   regs = mmap(NULL, info.size, PROT_READ | PROT_WRITE, MAP_SHARED,
               device_fd, info.offset);
   → 现在可以直接读写设备寄存器了

⑥ 注册 DMA 内存：
   分配一块内存 buf，然后
   ioctl(container_fd, VFIO_IOMMU_MAP_DMA, {vaddr=buf, iova=0x10000, size=...})
   → 告诉 IOMMU：设备访问 IOVA 0x10000 时，翻译到 buf 所在的物理页
   → 以后填描述符时，DMA 地址就写 0x10000

⑦ 设置中断：
   创建一个 eventfd，通过 VFIO_DEVICE_SET_IRQS 把它和设备的某个
   MSI-X 中断关联起来
   → 中断发生时，eventfd 变为可读，用户程序用 read/poll/epoll 等待即可
```

对比 UIO：

| | UIO | VFIO |
|---|---|---|
| MMIO 访问 | mmap `/dev/uioN` | mmap 设备 fd |
| DMA | 无保护，自己想办法拿物理地址 | 通过 IOMMU 注册，用自己指定的 IOVA |
| DMA 安全 | 不安全 | IOMMU 保证隔离 |
| 中断 | `read()` 阻塞等待 | eventfd，支持 MSI/MSI-X |
| 需要 IOMMU | 否 | 是（有一个不安全的 no-IOMMU 模式，仅供测试） |
| 典型用户 | 简单嵌入式设备 | 虚拟机直通、DPDK、SPDK |

第 ⑤ 步值得强调：**VFIO 的 MMIO 访问，本质上和 `/dev/mem`、`resource0` 一样，都是 mmap 把设备的物理地址映射进用户页表**。VFIO 的价值不在于 MMIO 本身，而在于它把 DMA 和中断也安全地交给了用户态。

## 六、为什么要把驱动搬到用户态：DPDK 与 SPDK

### 6.1 内核的开销

第 7 篇提到过，对于一块 100G 网卡，每秒要处理上亿个包，平均每个包只有**几纳秒到几十纳秒**的处理时间预算。而走内核网络协议栈处理一个包，光是系统调用、中断、内存分配、协议处理、数据拷贝这些开销加起来，就可能达到**微秒**级别。差了两个数量级。

存储也一样：一块高端 NVMe 硬盘能做到每秒上百万次 I/O，单次延迟只有十微秒左右，内核块设备层的开销已经占了很可观的比例。

### 6.2 用户态驱动的思路

**DPDK**（Data Plane Development Kit，数据平面开发套件）和 **SPDK**（Storage Performance Development Kit，存储性能开发套件）是两个开源项目，分别针对网络和存储。它们的思路是：**彻底绕过内核，在用户态直接驱动硬件。**

具体做法正是本篇讲的这些：

1. **用 VFIO（或 UIO）把网卡/NVMe 设备交给用户程序**；
2. **mmap 设备的 BAR**，用户程序直接读写门铃寄存器（第 8 篇）；
3. **用大页内存作为 DMA 缓冲区**，通过 VFIO 注册给 IOMMU；
4. **不用中断，纯轮询**（第 7 篇）：一个 CPU 核 100% 负责不停地检查完成队列；
5. **应用程序直接在用户态处理数据**，不经过内核协议栈，没有系统调用，没有数据拷贝。

```
       传统路径                                DPDK / SPDK

  应用程序                                应用程序 + 用户态驱动
     │ send()/write()                        │
     ▼ 系统调用                               │ 直接写描述符（普通内存）
  内核协议栈 / 块设备层                        │ 直接写门铃（MMIO，经 mmap）
     │                                       │ 轮询完成队列（普通内存）
     ▼                                       │
  内核驱动                                    │
     │ writel(门铃)                           │
     ▼                                       ▼
   设备                                     设备
```

用这种方式，单个 CPU 核每秒可以处理几千万个网络包，或者上百万次 NVMe I/O。

### 6.3 代价

天下没有免费的午餐：

- **占用整个 CPU 核**：轮询的核永远是 100% 占用，哪怕没有任何流量。
- **失去内核的功能**：没有 TCP/IP 协议栈（要自己实现或用专门的用户态协议栈），没有文件系统，没有 `ifconfig`、`ping`、`iostat` 这些熟悉的工具。
- **设备被独占**：设备交给了一个用户程序，系统里的其他程序就用不了了。
- **开发和运维复杂**：需要专门的配置（大页、绑定驱动、CPU 隔离），出了问题调试也更困难。

所以 DPDK 和 SPDK 主要用在对性能有极致要求的场景：电信设备、软件路由器和防火墙、云平台的虚拟交换机、分布式存储系统等。

## 七、风险清单

用户态直接访问 MMIO 给了程序巨大的能力，也带来了相应的风险。总结一下：

| 风险 | 说明 | 缓解办法 |
|---|---|---|
| **写错地址导致死机** | 往错误的寄存器写入错误的值，可能让设备进入异常状态、挂死总线，甚至整个系统冻住（第 2 篇） | 仔细核对手册；先在测试机上试 |
| **读有副作用的寄存器** | 调试时随手读一下数据或状态寄存器，可能吃掉一个字节、清掉一个中断（第 3 篇） | 了解每个寄存器的读写属性 |
| **和内核驱动抢设备** | 内核驱动和用户程序同时操作一个设备，状态互相覆盖 | 先解绑内核驱动；`IO_STRICT_DEVMEM` |
| **DMA 破坏内存** | 让设备往错误的地址 DMA，破坏内核或其他进程的数据 | 使用 VFIO + IOMMU，不用 UIO 做 DMA |
| **安全漏洞** | 能访问 `/dev/mem` 的程序几乎等于拥有整台机器 | `STRICT_DEVMEM`、最小权限、内核锁定模式 |
| **编译器和顺序问题** | 用户态没有 `readl`/`writel`，第 4、6 篇的坑要自己处理 | 用 `volatile`；必要时加屏障；使用 DPDK/SPDK 提供的封装 |
| **可移植性** | 直接依赖寄存器布局，换一款设备就要重写 | 只在必要时使用，做好抽象 |

**原则：能用内核驱动就用内核驱动；需要调试时用 `/dev/mem` 或 `resource0`；需要高性能的生产环境用 VFIO。**

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 用户态 MMIO 的原理 | 用 mmap 把设备物理地址映射进进程页表，设好 Device 属性 |
| `/dev/mem` | 代表整个物理地址空间，偏移即物理地址；需要 root，受多层限制 |
| `STRICT_DEVMEM` | 禁止通过 `/dev/mem` 访问普通内存 |
| `IO_STRICT_DEVMEM` | 禁止访问已被内核驱动认领的设备区域 |
| `resourceN` | sysfs 中对应 PCI BAR N 的文件，可直接 mmap |
| `resourceN_wc` | 可预取 BAR 的写合并映射 |
| `remap_pfn_range` | 内核把物理页直接填进用户页表的函数 |
| UIO | 小型用户态驱动框架：mmap 寄存器 + `read()` 等中断；无 DMA 保护 |
| VFIO | 依赖 IOMMU 的安全框架：mmap 寄存器 + 注册 DMA 内存 + eventfd 中断 |
| 组 / 容器 | IOMMU 隔离的最小单位 / 一个 IOMMU 地址空间 |
| iommufd | 较新的 VFIO 接口，简化了组和容器 |
| DPDK / SPDK | 用户态网络/存储框架：VFIO + 直接写门铃 + 轮询 |
