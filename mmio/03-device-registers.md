# 第 3 篇｜设备寄存器：设备的“控制面板”

> **本篇目标**：走进设备内部，看清它的“控制面板”上都有些什么。读完本篇，你会认识寄存器的几种类型，学会用位运算操作寄存器里的一个个开关，照着手册看懂一个真实的串口设备，并彻底明白一句话：**寄存器不是内存**——这是 MMIO 一切坑的总根源。

---

## 一、寄存器的基本样子

### 1.1 一排小格子

上一篇说，设备占据物理地址空间里的一段范围，比如串口占 `0x09000000`～`0x09000FFF` 这 4KB。在这 4KB 里，散落着设备的各个寄存器。

大多数设备的寄存器是 **32 位（4 字节）** 宽的，按 4 字节对齐排列。一个典型设备的寄存器布局可能是这样：

```
偏移量    寄存器名        宽度    作用
────────────────────────────────────────────
0x000     DATA           32 位   数据寄存器：写入要发送的数据 / 读出收到的数据
0x004     STATUS         32 位   状态寄存器：设备当前状态（忙不忙、有没有出错）
0x008     CTRL           32 位   控制寄存器：启用/禁用设备，设置工作模式
0x00C     INT_STATUS     32 位   中断状态：哪些事件发生了
0x010     INT_MASK       32 位   中断屏蔽：哪些事件允许触发中断
0x014     （保留）
...
```

芯片手册里通常会有一张“寄存器总表”（register map / register summary），列出每个寄存器的偏移量、名字、宽度、读写属性和复位值。**看懂这张表，是写驱动的第一步。**

### 1.2 寄存器的四种角色

上一篇用“控制面板”做了类比。现在把它对应到具体的寄存器类型上：

| 类型 | 类比 | 方向 | 例子 |
|---|---|---|---|
| **控制寄存器** | 开关、旋钮 | 软件写，设备读 | 启用设备、设置波特率、选择工作模式 |
| **状态寄存器** | 指示灯 | 设备写，软件读 | 设备忙、发送缓冲区满、接收到数据 |
| **数据寄存器** | 投币口/取物口 | 双向 | 要发送的字节、收到的字节 |
| **中断相关寄存器** | 门铃和静音键 | 双向 | 哪些事件发生了、允许哪些事件打扰 CPU |

有些设备还有一种特殊的寄存器叫**门铃（doorbell）**：软件往里写一个值，就相当于“按了一下门铃”，通知设备“有新活儿了，快去看”。门铃在高性能设备（网卡、NVMe 硬盘）中特别重要，第 8 篇会详细讲。

### 1.3 复位值

每个寄存器在设备上电或复位之后都有一个初始值，叫**复位值（reset value）**。比如控制寄存器的复位值通常是 0，表示“设备默认是关闭的”。驱动程序初始化设备时，一般会先把关键寄存器设成自己想要的值，而不是假设它们是某个值——因为固件可能已经动过它们了。

## 二、位域：一个寄存器里藏着很多开关

### 2.1 为什么要“塞”在一起

一个 32 位寄存器有 32 个比特。设备的很多设置只需要 1 个比特（开/关），有的需要几个比特（比如“工作模式”有 4 种，需要 2 个比特）。如果每个设置都单独占一个寄存器，太浪费地址空间，访问次数也太多。

所以设计者通常把**多个设置塞进同一个寄存器**，每个设置占其中几个比特，这叫**位域（bit field）**。

以一个假想的控制寄存器为例：

```
CTRL 寄存器（偏移 0x008）

 位：  31 ............ 10   9    8    7 .. 4    3 .. 2    1    0
     ┌─────────────────┬────┬────┬─────────┬─────────┬────┬────┐
     │     保留         │ RXE│ TXE│  保留    │  MODE   │LOOP│ EN │
     └─────────────────┴────┴────┴─────────┴─────────┴────┴────┘

 EN   (位 0)    ：1 = 启用设备
 LOOP (位 1)    ：1 = 回环测试模式
 MODE (位 3:2)  ：工作模式，00/01/10/11 四种
 TXE  (位 8)    ：1 = 允许发送
 RXE  (位 9)    ：1 = 允许接收
```

手册里常用 `[3:2]` 这样的写法表示“从第 3 位到第 2 位”这个位域。

### 2.2 三个基本操作：读、设置、清除

要操作位域，就要用到 C 语言的**位运算**。如果你对位运算不熟，这是最需要掌握的部分，只有三招：

**第一招：判断某一位是不是 1（读）**

```c
uint32_t ctrl = read_reg(CTRL);
if (ctrl & (1u << 8)) {
    // 第 8 位（TXE）是 1，发送已允许
}
```

`1u << 8` 就是“只有第 8 位是 1，其他都是 0”的数，也就是 `0x100`。和寄存器值做“与”运算，结果非零就说明第 8 位是 1。这种只有特定位是 1 的数叫**掩码（mask）**。

**第二招：把某一位设为 1（设置）**

```c
ctrl = ctrl | (1u << 8);     // 第 8 位设为 1，其他位不变
```

**第三招：把某一位设为 0（清除）**

```c
ctrl = ctrl & ~(1u << 8);    // 第 8 位设为 0，其他位不变
```

`~` 是按位取反，`~(1u << 8)` 就是“只有第 8 位是 0，其他都是 1”。

**修改一个多比特的位域（比如 MODE）**，就是先清后设：

```c
#define MODE_SHIFT  2
#define MODE_MASK   (0x3u << MODE_SHIFT)   // 0b1100，覆盖第 3、2 位

ctrl = (ctrl & ~MODE_MASK) | (2u << MODE_SHIFT);   // 把 MODE 设为 10
```

为了代码可读，驱动程序总是给每个位、每个位域定义好名字，而不是到处写魔法数字 `0x100`。Linux 内核还提供了 `BIT(n)`、`GENMASK(h, l)`、`FIELD_PREP`、`FIELD_GET` 这些宏来简化位运算。

### 2.3 读-改-写

注意上面的模式：**先读出整个寄存器，改其中几位，再写回整个寄存器**。这叫**读-改-写（read-modify-write）**：

```c
uint32_t v = read_reg(CTRL);   // 读
v |= (1u << 0);                // 改：只动第 0 位
write_reg(CTRL, v);            // 写
```

为什么不能直接写？因为 MMIO 访问通常以整个寄存器为单位。如果你只想打开 `EN` 而直接写 `1`，那么 `TXE`、`RXE`、`MODE` 这些位会被一起写成 0——你把发送和接收都关掉了。

读-改-写看起来天经地义，但它有两个隐藏的问题：

1. **它不是原子的**。如果在“读”和“写”之间，另一个 CPU 核或中断处理程序也修改了这个寄存器，它的修改会被你覆盖掉。驱动程序通常要用锁来保护这类操作。
2. **有些寄存器读出来的值和写进去的含义不一样**，这时读-改-写会出大错。这就是下一节要讲的。

## 三、寄存器和内存的本质区别

这是全篇，甚至全书最重要的一节。

对于普通内存，有一些我们习以为常、从来不用想的“常识”：

1. 写进去什么，读出来就是什么；
2. 读多少次都一样，读本身不会改变任何东西；
3. 连续写两次同一个地址，只有最后一次有意义；
4. 读写的先后顺序，只要最终结果对，无所谓。

**对设备寄存器来说，这四条常识全都可能不成立。** 原因只有一个：**读写设备寄存器会产生副作用（side effect）**。下面一条条看。

### 3.1 读一次，值就变了

**FIFO 数据寄存器**：串口收到的字节会排成一个队列，放在设备内部的一个小缓冲区（FIFO，先进先出队列）里。数据寄存器就是这个队列的“出口”。你每读一次，就从队列里**取走**一个字节，下次再读，得到的就是下一个字节。

```
接收 FIFO：  [ 'H' | 'e' | 'l' | 'l' | 'o' ]
                ↑ 出口

第 1 次读 DATA → 'H'，FIFO 变成 [ 'e' | 'l' | 'l' | 'o' ]
第 2 次读 DATA → 'e'，FIFO 变成 [ 'l' | 'l' | 'o' ]
```

这和内存完全不同：读内存不会把内存里的数据“读没了”。

**读清零（Read-to-Clear，RC）寄存器**：有些状态寄存器在被读取之后，会自动把所有的位清零。比如一个“错误计数”寄存器，读一次得到“自上次读以来发生了几次错误”，同时计数归零。

这带来一个很阴险的问题：**如果有人在你之前“偷偷”读了这个寄存器，你就丢失了信息**。比如你在调试器里查看这段地址，调试器读了一次，状态就被清掉了，你的程序再读时什么都看不到。这类 bug 极难排查，因为“一调试就消失”。

### 3.2 写进去的值，读出来不一样

**写 1 清零（Write-1-to-Clear，W1C）寄存器**：这是中断状态寄存器最常见的设计。

- 当某个事件发生时，设备把对应的位设为 1；
- 软件读这个寄存器，知道哪些事件发生了；
- 软件处理完某个事件后，**往那一位写 1**，那一位就被清成 0；
- 往某一位写 0，那一位**不受影响**。

```
INT_STATUS 当前值：0b0110（事件 1 和事件 2 发生了）

软件处理完事件 1，写入 0b0010
INT_STATUS 变为：  0b0100（事件 1 清掉了，事件 2 还在）
```

为什么要这么反直觉的设计？因为它避免了读-改-写带来的竞争。软件只需要写“我处理过的那几位”，不用担心把别的位（可能是刚刚新发生的事件）误清掉。

**但如果你对 W1C 寄存器用了读-改-写**，灾难就来了。假设你只想清掉事件 1，却习惯性地这样写：

```c
uint32_t v = read_reg(INT_STATUS);   // 读到 0b0110
v |= (1u << 1);                      // 想清事件 1
write_reg(INT_STATUS, v);            // 写回 0b0110 —— 事件 1 和事件 2 一起被清掉了！
```

事件 2 还没处理就被清除了，它就这么“丢”了。对 W1C 寄存器，正确的写法是**只写你要清的那一位**：

```c
write_reg(INT_STATUS, 1u << 1);      // 只清事件 1
```

**只读（RO）和只写（WO）寄存器**：有的寄存器只能读，往里写没有任何效果（比如设备 ID 寄存器）；有的只能写，读出来是 0 或者垃圾值（比如某些命令寄存器）。对只写寄存器做读-改-写，读到的是垃圾，改完写回去，就把垃圾也写进去了。驱动程序通常会在内存里保存一份只写寄存器的“影子副本”，修改时改副本，再把副本写进寄存器。

**一个地址，读写是两个寄存器**：有些设备为了省地址，让同一个偏移量“读的时候是一个寄存器，写的时候是另一个寄存器”。最典型的就是串口的数据寄存器：写它，是往**发送** FIFO 塞字节；读它，是从**接收** FIFO 取字节。两个 FIFO 毫无关系。

### 3.3 写一次就会触发动作

有的寄存器，写入的值并不被“保存”下来，而是**触发一个动作**：

- 往数据寄存器写一个字节，串口就开始发送它；
- 往门铃寄存器写一个值，设备就开始处理新任务；
- 往复位寄存器写一个特定值，整个设备就复位了。

这意味着：**连续写两次和写一次是不一样的**。对内存来说，`x = 1; x = 1;` 和 `x = 1;` 没有区别；对串口数据寄存器来说，前者发送了两个字节，后者只发送了一个。

### 3.4 顺序很重要

设备通常要求按特定的顺序配置寄存器。比如一个 DMA 控制器：

1. 先写源地址寄存器；
2. 再写目的地址寄存器；
3. 再写长度寄存器；
4. 最后写控制寄存器的“开始”位。

如果第 4 步跑到了第 3 步前面，设备就会用一个错误的（旧的）长度去搬数据。对内存来说，这四次写的顺序无所谓，最后都会写进去；对设备来说，**顺序就是语义**。

### 3.5 汇总

| 内存的“常识” | 设备寄存器可能的情况 | 例子 |
|---|---|---|
| 写什么，读出什么 | 读写不对应 | W1C、只写寄存器、读写分离的数据寄存器 |
| 读不改变任何东西 | 读有副作用 | FIFO 数据寄存器、读清零寄存器 |
| 重复写等于写一次 | 每次写都触发动作 | 数据寄存器、门铃、命令寄存器 |
| 顺序无所谓 | 顺序决定语义 | 先配参数再按“开始” |
| 值不会自己变 | 值随时被设备改变 | 状态寄存器、计数器 |

最后一行值得单独强调：**内存里的值，只要你不写，它就不会变；状态寄存器的值，你没碰它，它也会变**——因为设备在另一边不停地更新它。这一点是下一篇讲编译器问题时的关键。

> **全书的核心论断：寄存器不是内存。** 编译器、CPU 缓存、CPU 乱序执行，这些机制都是为“内存”设计的，它们默认上面那张表左列的常识成立。一旦它们作用在设备寄存器上，就会出问题。第 4～6 篇，就是逐个讲清楚这三种机制分别会坏什么事，以及如何防住它们。

## 四、照着手册认识一个真实设备：PL011 串口

光说不练假把式。我们来看一个真实的设备：ARM 公司设计的 **PL011 UART**。UART 就是串口，它把字节一位一位地通过一根线发出去，是嵌入式系统里最常用的调试输出手段。前两篇提到的 QEMU `virt` 机器上 `0x09000000` 处的串口就是 PL011，很多真实芯片（包括树莓派）上也有它。

### 4.1 寄存器总表（节选）

PL011 的技术参考手册里列出了二十几个寄存器，最常用的是下面这些：

| 偏移量 | 名字 | 读写 | 作用 |
|---|---|---|---|
| `0x000` | `UARTDR` | 读写 | 数据寄存器：写=发送一个字节，读=取出一个收到的字节 |
| `0x018` | `UARTFR` | 只读 | 标志寄存器：各种状态标志 |
| `0x024` | `UARTIBRD` | 读写 | 波特率除数的整数部分 |
| `0x028` | `UARTFBRD` | 读写 | 波特率除数的小数部分 |
| `0x02C` | `UARTLCR_H` | 读写 | 线路控制：数据位数、校验、是否启用 FIFO |
| `0x030` | `UARTCR` | 读写 | 控制寄存器：总开关、发送开关、接收开关 |
| `0x038` | `UARTIMSC` | 读写 | 中断屏蔽：哪些事件允许产生中断 |
| `0x03C` | `UARTRIS` | 只读 | 原始中断状态：哪些事件发生了（不管是否屏蔽） |
| `0x040` | `UARTMIS` | 只读 | 屏蔽后的中断状态：哪些事件发生了且允许中断 |
| `0x044` | `UARTICR` | 只写 | 中断清除：写 1 清除对应的中断 |

### 4.2 几个关键寄存器的位

**标志寄存器 `UARTFR`（偏移 `0x018`）**，部分位：

```
 位    名字    含义
 7     TXFE    发送 FIFO 空（Transmit FIFO Empty）
 6     RXFF    接收 FIFO 满（Receive FIFO Full）
 5     TXFF    发送 FIFO 满（Transmit FIFO Full）
 4     RXFE    接收 FIFO 空（Receive FIFO Empty）
 3     BUSY    串口正在发送数据
```

**控制寄存器 `UARTCR`（偏移 `0x030`）**，部分位：

```
 位    名字    含义
 9     RXE     允许接收
 8     TXE     允许发送
 0     UARTEN  串口总开关
```

### 4.3 从手册读出“使用说明”

把这几张表放在一起，就能读出这个设备的工作方式：

1. **发送一个字节**：先看 `UARTFR` 的 `TXFF` 位。如果是 1，说明发送 FIFO 已满，要等一等；如果是 0，就把字节写进 `UARTDR`。
2. **接收一个字节**：先看 `UARTFR` 的 `RXFE` 位。如果是 1，说明接收 FIFO 是空的，没东西可读；如果是 0，就从 `UARTDR` 读一个字节。
3. **中断**：可以通过 `UARTIMSC` 让“收到数据”等事件触发中断，处理完后往 `UARTICR` 写 1 来清除（这里用的是一个专门的“只写清除寄存器”，而不是在状态寄存器本身上做 W1C，这是另一种常见设计）。

这里能看到上一节讲的几乎所有特点：`UARTDR` 读写分离且有副作用；`UARTFR` 的值由设备随时改变；`UARTICR` 是只写的；初始化时要按顺序配置波特率、线路控制，最后才打开 `UARTCR` 的开关（手册明确要求修改配置时先关掉 `UARTEN`）。

### 4.4 一段示例代码

下面是一个最简单的“通过串口输出字符”的函数。假设我们在一个没有操作系统、MMU 也没开的环境里（所以物理地址可以直接当指针用），并且固件已经把串口初始化好了：

```c
#include <stdint.h>

#define UART_BASE   0x09000000UL          // QEMU virt 上 PL011 的基址
#define UARTDR      (UART_BASE + 0x000)   // 数据寄存器
#define UARTFR      (UART_BASE + 0x018)   // 标志寄存器
#define FR_TXFF     (1u << 5)             // 发送 FIFO 满

// 把一个地址当作“32 位设备寄存器”来读写
static inline uint32_t reg_read(uintptr_t addr) {
    return *(volatile uint32_t *)addr;
}
static inline void reg_write(uintptr_t addr, uint32_t val) {
    *(volatile uint32_t *)addr = val;
}

void uart_putc(char c) {
    // 1. 发送 FIFO 满了就等着
    while (reg_read(UARTFR) & FR_TXFF) {
        // 什么都不做，继续查
    }
    // 2. 把字符写进数据寄存器，串口就会把它发出去
    reg_write(UARTDR, (uint32_t)c);
}

void uart_puts(const char *s) {
    while (*s) {
        uart_putc(*s++);
    }
}
```

逐段解释：

- **`#define` 那几行**：把基址、偏移量、位掩码都定义成有意义的名字。这是驱动代码的惯例。
- **`reg_read` / `reg_write`**：把一个整数地址强制转换成 `volatile uint32_t *` 指针，再解引用。这就是 MMIO 访问的本质——一次普通的 32 位读或写。`volatile` 的作用下一篇讲；现在你只需要知道，**去掉它，这段代码在开优化后很可能会出问题**。
- **`while` 循环**：反复读 `UARTFR`，直到 `TXFF` 位变成 0。注意循环体是空的——我们没有在循环里写任何东西，`UARTFR` 的值却会自己变化，因为串口在另一边不断把 FIFO 里的字节发送出去。这正是“值会被设备改变”的体现。这种不停查状态的做法叫**轮询（polling）**，第 7 篇会和中断做对比。
- **写 `UARTDR`**：一次写入就是一次“发送命令”。调用两次 `uart_putc('A')` 就会发送两个 `A`。

在 Linux 内核里，类似的代码会长得不太一样（用 `readl`/`writel` 而不是直接解引用指针，地址也要先经过 `ioremap` 映射），但核心逻辑完全相同。第 9 篇会看到。

## 五、用 C 语言描述寄存器的几种写法

上面的例子用“基址 + 偏移量宏”来描述寄存器。实际项目里还有几种常见写法，各有优劣。

### 5.1 写法一：偏移量宏 + 访问函数

```c
#define UARTDR  0x000
#define UARTFR  0x018

uint32_t fr = readl(base + UARTFR);
```

这是 **Linux 内核驱动最常用的写法**。基址 `base` 是一个运行时得到的指针（来自 `ioremap`），偏移量是编译时常量。好处是简单、清晰，所有访问都经过统一的访问函数，便于加屏障、加调试。

### 5.2 写法二：结构体映射

把寄存器布局写成一个结构体，然后把结构体指针指向设备的基址：

```c
struct pl011_regs {
    volatile uint32_t dr;         // 0x000
    volatile uint32_t rsr_ecr;    // 0x004
    uint32_t reserved[4];         // 0x008 ~ 0x014，占位
    volatile uint32_t fr;         // 0x018
    // ...
};

struct pl011_regs *uart = (struct pl011_regs *)0x09000000;

while (uart->fr & FR_TXFF) { }
uart->dr = 'A';
```

这种写法在**单片机和裸机开发**里非常流行（比如 ARM 官方的 CMSIS 规范就用这种风格），因为它可读性好、IDE 能自动补全寄存器名。

但它有几个风险：

- **必须保证结构体的内存布局和寄存器布局完全一致**。编译器可能在成员之间插入填充字节（padding），要小心计算保留字段的大小。
- **结构体整体拷贝会出事**。比如 `struct pl011_regs copy = *uart;`，编译器会用 `memcpy` 风格的方式一口气读出所有寄存器——包括那个“读一次就取走一个字节”的数据寄存器。
- Linux 内核**不推荐**这种写法，因为它绕过了访问函数，没法自动加屏障。

### 5.3 不推荐的写法：C 语言的位域语法

C 语言本身有一种“位域”语法，可以在结构体里声明“这个成员只占 3 个比特”：

```c
struct ctrl_reg {
    uint32_t en   : 1;
    uint32_t loop : 1;
    uint32_t mode : 2;
    uint32_t      : 4;
    uint32_t txe  : 1;
    uint32_t rxe  : 1;
    uint32_t      : 22;
};
```

看起来和手册里的图一模一样，非常直观。但**几乎所有严肃的驱动代码都避免用它来描述硬件寄存器**，原因是：

1. **位的排列顺序由编译器决定**。C 标准没有规定第一个成员是放在最低位还是最高位，不同编译器、不同架构可能不一样。
2. **访问宽度不确定**。写 `reg->en = 1` 时，编译器可能生成 8 位、16 位或 32 位的读写指令。如果设备要求必须 32 位访问，用 8 位访问可能读到错误的值，甚至引发总线错误。
3. **每次赋值都隐含一次读-改-写**，而且你在代码里看不出来。对 W1C 或只写寄存器来说，这是灾难。

所以，老老实实地用**掩码和移位**吧。它啰嗦一点，但每一次读、每一次写都清清楚楚地写在代码里。对 MMIO 来说，“清楚地知道每一次访问”比“代码好看”重要得多。

## 六、再看一眼：为什么后面会有那么多坑

到这里，我们已经知道 MMIO 访问长什么样了：**把设备地址当成指针，读写它**。看起来和访问一个普通变量没什么两样。

但是第三节那张表已经告诉我们，设备寄存器在本质上和内存完全不同。而在 CPU 访问内存的整条路上，有好几个“自作聪明”的环节，它们全都是为普通内存优化的：

```
你的 C 代码
   │
   ▼
① 编译器：可能删掉“多余”的读写、合并、重排、把值缓存在 CPU 寄存器里
   │
   ▼
CPU 指令
   │
   ▼
② CPU 缓存：可能把读到的值存起来，下次直接用；可能提前读、晚点写
   │
   ▼
③ CPU 乱序执行与写缓冲：可能调换读写的先后顺序
   │
   ▼
④ 总线/互连：可能让写操作在中途“暂存”一会儿
   │
   ▼
设备寄存器
```

对内存来说，这些优化让程序快了几十上百倍，而且结果不会出错。对设备寄存器来说，每一个环节都可能把你的意图搞乱。

接下来的三篇，我们就沿着这条路往下走：

- **第 4 篇**：第①层，编译器。
- **第 5 篇**：第②层，缓存。
- **第 6 篇**：第③④层，CPU 乱序与总线。

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 寄存器总表 | 手册里列出每个寄存器偏移量、名字、宽度、读写属性和复位值的表 |
| 控制/状态/数据/中断寄存器 | 开关、指示灯、投币口、门铃——设备控制面板上的四类部件 |
| 门铃寄存器 | 写入即通知设备“有新任务” |
| 位域 | 一个寄存器里不同的比特段代表不同设置 |
| 掩码与移位 | 用 `&`、`|`、`~`、`<<` 读取、设置、清除某几位 |
| 读-改-写 | 读出整个寄存器，改几位，再写回；非原子，对特殊寄存器有害 |
| 读有副作用 | FIFO 数据寄存器读一次少一个，读清零寄存器读一次清零 |
| W1C | 写 1 清零、写 0 无影响，常用于中断状态；不能对它做读-改-写 |
| 只读/只写 | 写只读寄存器无效，读只写寄存器得到垃圾 |
| PL011 | ARM 的串口设备，`UARTDR` 收发数据，`UARTFR` 看 FIFO 状态 |
| 结构体映射 | 裸机开发常用，Linux 不推荐 |
| C 位域语法 | 位序和访问宽度不确定，描述硬件寄存器时应避免 |
| 核心论断 | **寄存器不是内存**：读写有副作用、值会自己变、顺序有语义 |
