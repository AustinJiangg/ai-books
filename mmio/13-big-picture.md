## 一、一次按键的完整旅程

假设你在一台 ARM64 Linux 机器的串口终端上敲了一个字母 `a`，屏幕上回显出 `a`。我们把这个过程拆开来看，标出每一步用到了本书的哪一篇。

### 1.1 输入：从按键到程序

```
① 字母 'a' 的电信号沿着串口线到达 PL011 串口芯片
   串口把它放进接收 FIFO                                           [第 3 篇：FIFO]

② 串口检查中断屏蔽寄存器 UARTIMSC：接收中断已打开
   于是拉高中断信号线                                               [第 7 篇：中断屏蔽]

③ GIC 分发器收到 33 号中断，按配置把它送给 CPU 0                   [第 7 篇：GIC]
   （GIC 的这些配置，是内核启动时通过 MMIO 写进 GICD 的）          [第 2 篇：GIC 也在地址地图上]

④ CPU 0 暂停当前程序，跳进内核的中断入口，
   从 GIC CPU 接口读出中断号 33，找到串口驱动的中断处理函数          [第 7 篇：中断旅程]

⑤ 串口驱动的中断处理函数：
   readl(base + UARTMIS)  → 发现是“接收”事件                      [第 9 篇：readl]
   readl(base + UARTFR)   → RXFE=0，FIFO 里有数据                  [第 3 篇：状态位]
   readl(base + UARTDR)   → 取出 'a'（读有副作用：FIFO 少一个）     [第 3 篇：读有副作用]
   writel(INT_RX, base + UARTICR) → 清除中断（写 1 清除）           [第 3 篇：W1C 类]
   readl(...)             → 读回，确保清除命令已到达设备            [第 6 篇：posted write]

   这些访问之所以能正确执行：
   - base 是 ioremap 得到的，页表里标记为 Device-nGnRE              [第 5 篇：内存属性]
   - 地址来自设备树里的 reg = <0x0 0x09000000 ...>                  [第 2 篇：设备树]
   - readl/writel 保证了访问宽度、不被编译器优化、带屏障             [第 4、6 篇]

⑥ 驱动把 'a' 交给 TTY 子系统，内核唤醒正在 read() 等待的 shell 程序

⑦ 中断返回，CPU 0 继续之前被打断的程序
```

### 1.2 输出：从程序到屏幕

```
⑧ shell 收到 'a'，决定回显：调用 write(1, "a", 1)
   → 系统调用进入内核 → TTY 子系统 → 串口驱动

⑨ 串口驱动：
   readl(base + UARTFR)   → TXFF=0，发送 FIFO 有空位                [第 3 篇：轮询状态]
   writel('a', base + UARTDR) → 把 'a' 写进发送 FIFO                [第 3 篇：写触发动作]
   （这次写是投递式的，writel 返回时字符可能还在路上，但这没关系）   [第 6 篇]

⑩ 串口把 'a' 一位一位地发到串口线上，你的终端显示出 'a'
```

### 1.3 如果这是一台虚拟机

如果这台“ARM64 Linux 机器”其实是一台 Firecracker 虚拟机，那么上面的每一次 `readl`/`writel`：

```
客户机执行 ldr/str → stage-2 翻译失败 → 陷入 KVM               [第 12 篇]
→ KVM 解读 ESR：地址、宽度、方向、寄存器                         [第 12 篇，呼应第 4 篇]
→ KVM_EXIT_MMIO 退到 Firecracker
→ Firecracker 的串口模拟代码处理这次访问
→ 回到客户机
```

而“按键”则是 Firecracker 从宿主机标准输入读到 `a`，放进模拟串口的接收 FIFO，再通过 KVM 给客户机注入中断。客户机里的驱动代码**一行都不用改**。

### 1.4 如果这是一个网络包

如果换成网卡收到一个网络包，结构几乎一样，只是数据不再通过 `readl(UARTDR)` 一个字节一个字节地读，而是：

```
网卡通过 DMA 把包写进内存里预先准备好的缓冲区                    [第 8 篇：DMA]
（DMA 地址经过 IOMMU 翻译和检查）                                [第 8 篇：IOMMU]
网卡在完成队列里写一条记录，然后发 MSI-X 中断                     [第 7 篇：MSI = 一次写]
驱动读内存里的完成队列（不是 MMIO）                               [第 8 篇]
驱动补充新的空缓冲区，写门铃寄存器                                [第 8 篇：门铃]
网卡的地址来自 PCI 枚举时分配的 BAR                               [第 10 篇]
```

如果是 DPDK 程序，以上这些全部在用户态完成，门铃寄存器通过 VFIO mmap 访问，不用中断而是轮询（第 11 篇）。

### 1.5 一张总图

```
                          应用程序
                             │ 系统调用            （或 DPDK/SPDK：mmap 直接访问，第 11 篇）
                             ▼
       ┌──────────────── Linux 内核 ─────────────────────┐
       │                                                 │
       │  驱动：readl / writel / readl_poll_timeout       │ 第 9 篇

       │        devm_request_irq                          │ 第 7 篇
       │                                                 │
       │  ioremap：建立页表映射，设 Device 属性             │ 第 5、9 篇
       │  地址来源：设备树 / ACPI / PCI 枚举（BAR）         │ 第 2、10 篇
       └───────────────────────┬─────────────────────────┘
                               │
            编译器（volatile / 访问函数）                     第 4 篇
```

## 二、常见坑汇总

下面是 MMIO 编程中最常见的错误，按“哪一层出的问题”分类。每一条都在前面某一篇里详细讲过。

### 2.1 地址与映射

| 坑 | 症状 | 原因 / 对策 | 见 |
|---|---|---|---|
| 地址写错 | 读回全 F 或 0；外部中止；系统卡死 | 核对芯片手册的基址和设备手册的偏移量；对照 `/proc/iomem` | 2 |
| 设备没上电 / 时钟没开 | 系统卡死、总线挂起 | 访问前先打开电源和时钟 | 2 |
| 直接把物理地址当指针 | 内核缺页，“Unable to handle kernel paging request” | 先 `ioremap` | 9 |
| `iounmap` 后继续访问 | 同上 | 用 devm 系列管理生命周期 | 9 |
| 两个驱动抢同一段地址 | probe 失败 `-EBUSY`，或设备状态被搞乱 | `request_mem_region`；查 `/proc/iomem` | 9 |
| PCI 设备没打开 Mem / BusMaster | 读全 F；DMA 不工作 | `pci_enable_device`、`pci_set_master` | 10 |

### 2.2 编译器

| 坑 | 症状 | 原因 / 对策 | 见 |
|---|---|---|---|
| 忘了 `volatile`（裸机/用户态） | 轮询死循环；写入丢失；`-O0` 好 `-O2` 坏 | 编译器把寄存器当普通内存优化 | 4 |
| 用 `memcpy` / 结构体拷贝访问设备 | 访问宽度错误、多读了寄存器、对齐异常；虚拟机里 MMIO 无法解码 | 用 `memcpy_fromio`/`memcpy_toio` 或逐个访问 | 4、12 |
| 访问宽度不对 | 读到错误的值；改动了相邻寄存器 | 指针类型或访问函数宽度与手册一致 | 4 |
| 用 C 位域描述寄存器 | 位序、宽度不确定；隐式读-改-写 | 用掩码和移位 | 3 |

### 2.3 寄存器语义

| 坑 | 症状 | 原因 / 对策 | 见 |
|---|---|---|---|
| 对 W1C 寄存器做读-改-写 | 中断“丢失”，没处理的事件被清掉 | W1C 只写要清的那一位 | 3 |
| 对只写寄存器做读-改-写 | 写入垃圾值 | 在内存里维护影子副本 | 3 |
| 调试器 / `devmem` 读了读清零或 FIFO 寄存器 | “一调试 bug 就消失”或数据丢失 | 了解每个寄存器的读副作用 | 3 |
| 读-改-写没加锁 | 偶发的配置被覆盖 | 用锁，或 `regmap_update_bits` | 3、9 |
| 配置顺序不对 | 设备拿到半成品参数 | 按手册顺序；必要时加屏障 | 3、6 |
| 64 位寄存器拆成两次 32 位读 | 偶发的值错得离谱 | “高-低-高”读法 | 4 |

### 2.4 缓存与内存属性

| 坑 | 症状 | 原因 / 对策 | 见 |
|---|---|---|---|
| 设备被映射成可缓存 | 读到过期值；写不到达；凭空的副作用 | 用 `ioremap`（Device 属性） | 5 |
| 控制寄存器用了写合并 | 命令乱序、延迟 | 写合并只用于显存类可预取区域 | 5 |
| 同一物理地址用两种属性映射 | 数据时好时坏，不可预测 | 一块物理地址只用一种属性 | 5 |
| 非一致 DMA 没做缓存维护 | 设备读到旧数据 / CPU 读到旧数据 | 使用 Linux DMA API | 8 |

### 2.5 顺序与屏障

| 坑 | 症状 | 原因 / 对策 | 见 |
|---|---|---|---|
| 写描述符后用 `writel_relaxed` 按门铃 | ARM64 上偶发设备读到旧描述符；x86 上正常 | 用 `writel`，或 `wmb()` + `_relaxed` | 6 |
| 描述符的所有权标志先于内容可见 | 设备处理不完整的描述符 | 内容 → `dma_wmb()` → 标志 | 6 |
| 读状态后用 `readl_relaxed`，再读 DMA 数据 | 读到 DMA 完成前的旧数据 | 用 `readl`，或 `_relaxed` + `rmb()` | 6 |
| 以为 `writel` 返回时写已到达 | 关中断后仍有中断；复位延时不够 | 读回同一设备刷新 | 6 |

### 2.6 中断

| 坑 | 症状 | 原因 / 对策 | 见 |
|---|---|---|---|
| 没清除电平中断 | 中断风暴，系统卡死；“nobody cared” | 处理完在设备上清除 | 7 |
| 清除命令还在路上就返回 | 伪中断，每次中断处理两遍 | 清除后读回 | 7 |
| 清除了没处理的中断 | 事件丢失 | 只清自己处理过的位 | 7 |
| 共享中断时不检查自己的状态 | 别的设备的中断被误处理 | 读状态，不是自己的返回 `IRQ_NONE` | 7 |

### 2.7 一个有用的心法

如果遇到一个 MMIO 相关的怪 bug，可以按第 3 篇末尾那张图，**从上往下逐层排查**：

```
① 地址对吗？设备活着吗？         → /proc/iomem、读 ID 寄存器、查电源和时钟
② 编译器有没有动手脚？           → 有没有 volatile / 访问函数？反汇编看看
③ 缓存有没有挡路？               → 映射属性对不对？
④ 顺序有没有乱？                 → 普通内存和 MMIO 之间有没有屏障？
⑤ 写真的到了吗？                 → 需要确认时有没有读回？
⑥ 寄存器语义理解对了吗？         → 重读手册：W1C？读清零？只写？
```

很多“灵异”bug 的共同特征是：**在 x86 上没问题，在 ARM64 上出问题；不加打印出问题，加了打印就好了；单核没问题，多核出问题；低负载没问题，高负载出问题**。看到这些特征，首先怀疑第 ④⑤ 层。

## 四、和 MMIO 相关的安全话题

MMIO 的本质是“读写某个地址就能控制硬件”。这种强大的能力，自然也是攻击者觊觎的目标。

### 4.1 `/dev/mem` 与物理内存访问

第 11 篇讲过，`/dev/mem` 能访问整个物理地址空间，一个能读写它的程序几乎等于控制了整台机器。现代 Linux 通过 `STRICT_DEVMEM`、`IO_STRICT_DEVMEM`、内核锁定模式等手段层层设限。在安全要求高的环境里，应该确认这些选项是开启的。

### 4.2 DMA 攻击

第 8 篇讲过，设备可以通过 DMA 直接读写内存。如果一个外接设备是恶意的——比如一个伪装成普通 U 盘或扩展坞的雷电（Thunderbolt）设备——它可以在几秒钟内通过 DMA 读出整个内存（包括磁盘加密密钥、登录凭据），或者往内核里写入恶意代码。这类攻击有过很多公开演示。

**防御手段是 IOMMU**：开启 IOMMU 后，每个设备只能访问内核明确分配给它的内存。现代操作系统对外接的雷电/USB4 设备默认启用 IOMMU 保护，有的还在系统启动的早期就打开 IOMMU（防止在操作系统接管之前被攻击）。

### 4.3 虚拟设备模拟代码的漏洞

第 12 篇讲过，虚拟机里的 MMIO 访问会被交给宿主机上的模拟代码处理。如果模拟代码有 bug——比如没有检查客户机写入的队列长度，导致越界读写——恶意客户机就可以通过精心构造的 MMIO 访问，攻击宿主机上的 VMM 进程，甚至**逃逸出虚拟机**。

历史上，QEMU 的软盘控制器、网卡、USB 等设备模拟代码中都出现过这类漏洞（比如 2015 年著名的 “VENOM” 漏洞，就出在 QEMU 早已很少使用的虚拟软盘控制器里）。

这也是 Firecracker 这类 microVM 选择**只模拟极少数设备**、用内存安全的 Rust 语言编写、并对 virtio 握手做严格检查的原因：**模拟的设备越少、代码越简单，攻击面就越小。**

### 4.4 MMIO 相关的 CPU 漏洞

2018 年以来，一系列 CPU 推测执行漏洞（Spectre、Meltdown 及其后续变种）震动了业界。其中有一类和 MMIO 直接相关：2022 年，Intel 披露了一组叫 **“MMIO Stale Data”**（MMIO 陈旧数据）的漏洞。

简单地说：在某些 Intel CPU 上，CPU 内部有一些用于在核心和其他部件之间传递数据的缓冲区。当程序执行 MMIO 读写时，这些缓冲区里可能**残留着之前其他程序的数据**，在特定条件下，攻击者可以通过 MMIO 操作配合推测执行，推断出这些残留数据。这在虚拟机直通设备的场景下尤其值得关注（客户机可以直接对设备做 MMIO，可能窥探到宿主机或其他虚拟机的数据）。

修复手段包括 CPU 微码更新，以及操作系统在特定时机（比如切换虚拟机时）清空这些缓冲区。Linux 在 `/sys/devices/system/cpu/vulnerabilities/mmio_stale_data` 文件里报告当前 CPU 是否受影响、缓解措施是否生效。

这个例子说明：**MMIO 不仅是一个“正确性”问题，也是一个“安全”问题。** CPU 在处理 Device 内存时的各种内部机制，也可能成为信息泄露的通道。

## 五、其他架构速览

本书以 ARM64 为主、x86 为辅。这里简单看一下 MMIO 在其他架构上的情况。

### 5.1 RISC-V

RISC-V 和 ARM 一样，**只有 MMIO，没有端口 I/O**。

- **内存属性**：RISC-V 早期规范里，一段地址是内存还是 I/O 由硬件平台固定决定（通过一种叫 PMA，物理内存属性的机制），不能通过页表修改。后来的 **Svpbmt** 扩展才在页表项里加入了属性位，可以把一页标记为“不可缓存”或“I/O”，和 ARM64 的 MAIR、x86 的 PAT 起类似的作用。
- **顺序**：RISC-V 是弱内存序（叫 RVWMO），和 ARM64 类似。它的屏障指令叫 `fence`，可以通过参数精确指定“哪些类型的访问（读/写/设备读/设备写）之间需要排序”。比如 `fence w,o` 表示“前面的内存写在后面的设备写之前完成”——这恰好就是门铃场景需要的。
- **中断控制器**：传统上用 **PLIC**（平台级中断控制器）管理外部中断，用 **CLINT** 管理定时器和核间中断，它们都是 MMIO 设备。新一代的 **AIA**（高级中断架构）引入了支持 MSI 的中断控制器，思路和 ARM 的 GICv3 ITS 类似。
- QEMU 的 RISC-V `virt` 机器上，串口（一个兼容 16550 的 UART）在 `0x1000_0000`，virtio-mmio 设备从 `0x1000_1000` 开始。

Linux 的 `readl`/`writel` 在 RISC-V 上同样可用，驱动代码基本不用改。

### 5.2 x86 的现状

x86 至今仍然**两种都有**：端口 I/O 用于少数历史遗留设备（PS/2 键盘控制器、传统串口、CMOS 时钟、PCI 配置空间的老式访问方法等），绝大部分现代设备（PCIe 网卡、NVMe、GPU、USB 控制器）都只用 MMIO。

x86 的强内存序让很多顺序问题“自动消失”了，这对驱动开发者是一种便利，但也让很多驱动在不知不觉中依赖了这种便利——这些驱动在移植到 ARM64、RISC-V 等弱内存序架构时，就会暴露出问题（第 6 篇）。如果你要写跨平台的驱动，**请按照最弱的内存模型来写**，老老实实用 Linux 提供的屏障和访问函数。

### 5.3 一个共同点

不管是 ARM64、x86 还是 RISC-V，MMIO 的核心问题都是一样的：

1. 设备住在物理地址空间的什么地方？
2. 怎么告诉编译器“这里不是内存”？
3. 怎么告诉 CPU 缓存“这里不要缓存”？
4. 怎么保证访问的顺序和完成？

各个架构的答案在细节上不同（MAIR vs. PAT vs. Svpbmt，DMB vs. mfence vs. fence），但问题本身是通用的。这也是为什么 Linux 能用一套统一的 `ioremap` + `readl`/`writel` + 屏障函数，在所有架构上工作。

## 结语

回到第 1 篇开头的那个问题：**CPU 只会读写内存、做加减法，它是怎么指挥形形色色的外部设备的？**

现在你知道了答案：**把设备的“控制面板”摆进地址空间里，让 CPU 用读写内存的方式去拨开关、看指示灯。** 这就是 MMIO。

这个想法本身简单得近乎朴素，但为了让它在现代计算机里**正确**、**高效**、**安全**地工作，硬件和软件的设计者们搭起了一整套精巧的机制：地址地图与设备树、volatile 与访问函数、Device 内存类型、内存屏障、中断与 MSI、DMA 与 IOMMU、BAR 与枚举、VFIO、stage-2 与 virtio……每一样，都是在回答同一个问题：**怎样让“寄存器不是内存”这个事实，不至于把一切搞砸。**

希望这本书帮你看清了这条从 CPU 到设备的路。下次再看到 `writel`、`ioremap`、`lspci` 输出里的 Region，或者虚拟机日志里的 MMIO exit，你会知道它们背后发生了什么。
