# 第 5 篇｜内存属性与缓存：设备内存为什么不能被缓存

> **本篇目标**：理解 CPU 缓存和预取对设备寄存器意味着什么，以及 CPU 是如何区分“这段地址是内存”和“这段地址是设备”的。读完本篇，你会明白 ARM64 的 Normal 与 Device 两大类内存、`nGnRnE` 这串“密码”的含义、x86 上 UC/WC/WB 等类型的作用，以及为什么显存要用“写合并”。

---

## 一、先回顾：CPU 缓存是什么

### 1.1 速度鸿沟

CPU 的速度和内存的速度之间有一道巨大的鸿沟。一个现代 CPU 核每秒能执行几十亿条指令，执行一条简单指令不到 1 纳秒；而从内存条读一个数据，要花 50～100 纳秒。如果每次访问内存都要等这么久，CPU 大部分时间都在发呆。

解决办法是**缓存（cache）**：在 CPU 内部放几块又小又快的存储器，把最近用过的内存数据存一份副本。下次再访问同样的地址，直接从缓存里拿，只要 1～几纳秒。

```
     CPU 核
       │
   ┌───┴───┐
   │ L1 缓存│  ~1 纳秒，几十 KB
   └───┬───┘
   ┌───┴───┐
   │ L2 缓存│  ~几纳秒，几百 KB 到几 MB
   └───┬───┘
   ┌───┴───┐
   │ L3 缓存│  ~十几纳秒，几 MB 到几十 MB（多核共享）
   └───┬───┘
       │
    内存条     ~50～100 纳秒，几 GB 到几 TB
```

### 1.2 缓存的几个关键行为

缓存不是简单地“存一份副本”这么简单。为了效率，它有几个重要的行为特点（如果你读过[《mmap 从零讲透》第 2 篇](../mmap/02-memory-and-addresses.md)，对此应该不陌生）：

1. **以缓存行为单位搬运**。缓存不是一个字节一个字节地从内存读，而是一次读一整块，通常是 **64 字节**，叫一个**缓存行（cache line）**。你读一个 4 字节的整数，缓存会把它周围的 64 字节都读进来——因为程序很可能马上会用到旁边的数据。
2. **写回（write-back）**。你写一个变量，CPU 通常只改缓存里的副本，并把这一行标记为“脏的”。等到这一行要被挤出缓存时，才一次性写回内存。这样，对同一个变量的多次写入，只需要一次内存写。
3. **预取（prefetch）**。CPU 会观察你的访问模式，如果发现你在顺序读一个数组，它会**提前**把后面的数据读进缓存，等你真正要用时就已经在那里了。
4. **推测执行（speculative execution）**。CPU 遇到一个条件分支时，会猜一个方向先执行下去，包括执行其中的读内存操作。如果猜错了，结果作废，但那些读操作**已经发生了**。

对普通内存，这四个行为都是纯粹的好事：数据还是那些数据，只是来得更快了。

但是，请拿着上面这四条，再回头看看第 3 篇那张“寄存器不是内存”的表。

## 二、缓存遇上设备寄存器：一场灾难

### 2.1 读：拿到的是“过期报纸”

假设串口的标志寄存器 `UARTFR` 被当作普通内存缓存起来了。

1. 程序第一次读 `UARTFR`，缓存未命中，从设备读到 `TXFF = 1`（发送 FIFO 满），把它存进缓存。
2. 过了一会儿，串口把 FIFO 里的字节发出去了，`UARTFR` 在设备那边已经变成了 `TXFF = 0`。
3. 程序再读 `UARTFR`——缓存命中！直接返回缓存里的 `TXFF = 1`。
4. 程序永远在等待，就像第 4 篇里那个被编译器坑了的死循环。只不过这次，**连 `volatile` 也救不了你**——编译器确实老老实实地生成了每一次读指令，但每一次读都被缓存拦截了。

这就像你订了一份报纸，但门卫每次都把第一天那份递给你，说“这个我这儿有，不用跑一趟了”。

### 2.2 写：命令“卡”在半路

写的情况更糟。由于缓存是写回的：

1. 程序往 `UARTDR` 写入字符 `'A'`。
2. CPU 只是改了缓存里的副本，把这一行标为“脏”，**根本没有发给串口**。
3. 程序接着写 `'B'`，覆盖了缓存里的 `'A'`。
4. 很久以后，这一行被挤出缓存，`'B'` 才被写到串口。`'A'` 永远丢了。

更可怕的是，写回是以**整个缓存行**为单位的。串口的 64 字节范围内有好几个寄存器，写回时，这 64 字节会被一次性写到设备上——包括那些你根本没碰过的寄存器，它们被写入了缓存里的旧值（甚至是垃圾）。

### 2.3 预取和推测：无中生有的读

最隐蔽的是预取和推测执行。

比如你的程序读了 `UARTFR`（偏移 `0x018`），缓存为了“效率”，把同一个缓存行里的 `UARTDR`（偏移 `0x000`）也一起读了。而 `UARTDR` 是一个**读有副作用**的寄存器：每读一次，就从接收 FIFO 里取走一个字节。你一个字节都没打算接收，却已经丢了一个。

推测执行也一样：

```c
if (has_data) {
    c = read_reg(UARTDR);    // 只有在 has_data 为真时才读
}
```

如果 CPU 推测 `has_data` 为真，提前执行了 `read_reg(UARTDR)`，结果发现猜错了——在普通内存上，作废结果即可；在设备上，那个字节已经从 FIFO 里被取走了，**覆水难收**。

### 2.4 结论

| 缓存行为 | 对内存 | 对设备寄存器 |
|---|---|---|
| 缓存命中返回副本 | 更快 | 读到过期的状态 |
| 以 64 字节为单位读 | 顺便读了邻居，可能有用 | 读了不该读的寄存器，触发副作用 |
| 写回 | 合并多次写，更快 | 写不及时到达，多次写被合并，邻居被乱写 |
| 预取 | 提前准备数据 | 凭空产生读操作 |
| 推测执行 | 猜错了就作废 | 读的副作用无法作废 |

所以必须有一种机制，让 CPU 知道：**这段地址是设备，不要缓存、不要预取、不要推测、不要合并。**

这个机制就是**内存属性（memory attributes）**，也叫**内存类型（memory type）**。

## 三、内存属性由谁决定：页表

### 3.1 页表不只是翻译地址

在第 2 篇的最后我们提到，程序访问的是虚拟地址，要经过页表翻译成物理地址。页表里的每一项（页表项）除了记录“这一页虚拟地址对应哪一页物理地址”之外，还记录了一些**属性位**，比如：

- 这一页能不能读、能不能写、能不能执行；
- 用户程序能不能访问，还是只有内核能访问；
- **这一页是什么内存类型：能不能缓存，怎么缓存。**

最后一项就是我们关心的。CPU 每次访问内存时，在翻译地址的同时就拿到了这一页的内存类型，然后根据类型决定这次访问要不要走缓存、能不能被预取、能不能和别的访问合并。

> **内存属性是“按页”设置的，写在页表里。** 这就是为什么第 2 篇说“设备通常至少占一页（4KB）”——同一页里不能一半是内存一半是设备，因为它们需要不同的属性。

这也意味着：**同一个物理地址，用不同的属性去映射，CPU 访问它的方式就完全不同**。操作系统在为设备建立映射时（比如 Linux 的 `ioremap`，第 9 篇），最重要的一件事就是**设对内存属性**。

### 3.2 MMU 还没开的时候呢？

你可能会问：第 1 篇和第 3 篇的裸机例子里，MMU 根本没开，没有页表，那访问串口的时候 CPU 用的是什么属性？

ARM64 规定：**MMU 关闭时，所有数据访问都被当作最严格的 Device 类型**（Device-nGnRnE，下面马上会讲）。所以裸机程序在不开 MMU 的情况下访问设备是安全的——代价是访问内存也变得很慢，因为所有东西都不走缓存。真正的裸机程序和操作系统都会尽快开启 MMU，把内存设成可缓存，把设备设成 Device。

## 四、ARM64 的内存类型

### 4.1 两大类：Normal 和 Device

ARM64 把所有内存分成两大类：

**Normal（普通内存）**：给真正的内存（RAM、ROM）用的。CPU 可以对它做几乎任何优化：缓存、预取、推测读、合并、重排、未对齐访问……Normal 内存还可以进一步细分缓存策略：

- **Write-Back（写回）可缓存**：最常用，性能最好，普通程序的内存都是这种；
- **Write-Through（写透）可缓存**：写的时候同时写缓存和内存；
- **Non-cacheable（不可缓存）**：不走缓存，但其他优化（合并、重排、推测读）仍然允许。

**Device（设备内存）**：给设备寄存器用的。它的核心特征是：

1. **永远不会被缓存**。每次读写都直接到达设备。
2. **不允许推测访问**。CPU 不会因为预取或推测执行而凭空产生对 Device 内存的读写，只有程序真正执行到的访问才会发出去。
3. **不允许未对齐访问**。对 Device 内存做未对齐访问会触发对齐错误异常（这就是第 4 篇提到的原因）。
4. **一些特殊指令不能用**。比如用于快速清零一整块内存的 `DC ZVA` 指令，在 Device 内存上会报错；用于实现原子操作的独占访问指令，在 Device 内存上的行为也没有保证。这正是 `memcpy`、`memset` 不能直接用在设备上的硬件层面的原因。

### 4.2 Device 的四种细分：解读 `nGnRnE`

Device 内存又细分成四种，名字看起来像密码：

```
Device-nGnRnE
Device-nGnRE
Device-nGRE
Device-GRE
```

其实每个名字都是由三个字母组成的，每个字母代表一种“允许或禁止的优化”，前面加 `n` 表示“不允许”（not）：

| 字母 | 全称 | 含义 |
|---|---|---|
| **G** | Gathering（聚合） | 允许把多次访问**合并**成一次。比如两次相邻的 4 字节写合并成一次 8 字节写 |
| **R** | Reordering（重排） | 允许对同一设备的多次访问**调换到达顺序** |
| **E** | Early write acknowledgement（提前写确认） | 允许写操作在**还没到达设备时**，就由路上的某个中转站提前回复“写好了” |

于是：

| 类型 | 聚合 | 重排 | 提前确认 | 严格程度 | 典型用途 |
|---|---|---|---|---|---|
| **Device-nGnRnE** | ✗ | ✗ | ✗ | 最严格 | 对写完成时机要求极严的寄存器 |
| **Device-nGnRE** | ✗ | ✗ | ✓ | 次严格 | **绝大多数设备寄存器**（Linux 默认） |
| **Device-nGRE** | ✗ | ✓ | ✓ | 较宽松 | 少见 |
| **Device-GRE** | ✓ | ✓ | ✓ | 最宽松 | 对访问方式不敏感的设备缓冲区 |

### 4.3 三个字母分别意味着什么

**G（聚合）**：用“快递打包”类比。你连续寄了两个小包裹给同一个地址，快递站把它们装进一个大箱子一起送。对内存来说没问题；但对设备来说，它期待的是“两次独立的 4 字节写”，结果收到了“一次 8 字节写”，可能完全不认。禁止聚合（nG）就是说：**你发几次，设备就收几次，一次不多一次不少，宽度也不变**。

**R（重排）**：你先寄了包裹 A，再寄包裹 B，但 B 先到了。nR 保证**对同一个设备的访问按程序顺序到达**。注意它只保证“同一个设备”内部的顺序（更准确地说，是同一块由硬件实现决定大小的地址范围内）；对**不同**设备、或者设备与普通内存之间的顺序，它不管——那是第 6 篇屏障要解决的问题。

**E（提前写确认）**：这是最微妙的一个。CPU 发出一次写，需要等收到“写好了”的回复，才认为这次写**完成**了。如果允许提前确认（E），那么路上某个中转站（比如互连上的一个缓冲区）收到这次写，就可以先回复“好了”，然后再慢慢转交给设备。这样 CPU 可以更快地继续往下走。

但提前确认意味着：**CPU 以为写完成了，其实设备可能还没收到。** 对绝大多数情况，这没关系；但如果你写了一个“关闭中断”的寄存器，紧接着就认为“现在中断肯定不会来了”，那可能会出问题——设备还没收到关闭命令，中断照样会来。nE 禁止提前确认，保证 CPU 认为写完成时，设备真的已经收到了，但代价是每次写都要等待更久。第 6 篇会详细讲提前写确认（posted write）带来的问题和解决办法。

### 4.4 Linux 用的是哪种

在 ARM64 Linux 上，驱动最常用的 `ioremap` 函数会把设备映射为 **Device-nGnRE**——禁止聚合和重排，允许提前写确认。这是性能和安全之间的一个平衡：大部分设备都能接受提前写确认，而需要确认写真正完成的场景，驱动可以通过“读回”等手段单独处理（第 6 篇）。

Linux 还提供了几个变体：

| 函数 | ARM64 上的内存类型 | 用途 |
|---|---|---|
| `ioremap` | Device-nGnRE | 普通设备寄存器（默认） |
| `ioremap_np` | Device-nGnRnE | 要求禁止提前写确认的平台（如苹果 M 系列芯片的部分设备） |
| `ioremap_wc` | Normal Non-cacheable | 写合并，用于显存等大块缓冲区（见第六节） |
| `ioremap_cache` | Normal 可缓存 | 实际上是内存、只是不在常规内存范围内的区域 |

### 4.5 MAIR：一张属性“菜单”

最后简单说一下 ARM64 在硬件上是怎么实现这一切的。

页表项的空间很宝贵，不可能把“Device-nGnRE”或“Normal 写回可缓存”这么详细的信息都塞进每一个页表项。ARM64 的办法是：

1. CPU 里有一个专门的系统寄存器叫 **MAIR**（Memory Attribute Indirection Register，内存属性间接寄存器）。它像一张有 **8 道菜的菜单**，每一项（8 个比特）描述一种完整的内存类型。操作系统启动时把这张菜单填好，比如第 0 项是“Normal 写回可缓存”，第 3 项是“Device-nGnRnE”，第 4 项是“Device-nGnRE”，等等。
2. 每个页表项里只需要 **3 个比特**（叫 **AttrIndx**，属性索引），写上“我用菜单上的第几项”。

```
          MAIR 寄存器（操作系统启动时填好）
   ┌────┬───────────────────────────────┐
   │ 0  │ Normal，写回可缓存             │
   │ 1  │ Normal，写回可缓存（带标签）    │
   │ 2  │ Normal，不可缓存               │
   │ 3  │ Device-nGnRnE                 │
   │ 4  │ Device-nGnRE                  │
   │ …  │ …                             │
   └────┴───────────────────────────────┘
               ▲
               │ AttrIndx = 4
   ┌───────────┴───────────────────────────┐
   │ 页表项：物理页号 | 权限位 | AttrIndx=4 │  → 这一页是 Device-nGnRE
   └───────────────────────────────────────┘
```

（上面这张菜单的具体编号以 Linux 内核源码为准，不同版本可能略有不同。）

所以，当 Linux 用 `ioremap` 映射一个设备时，它做的事情就是：建立一个页表项，物理页号填设备的地址，AttrIndx 填“Device-nGnRE”在菜单上的编号。

## 五、x86 的内存类型

x86 的思路相同，具体机制不同。它有两套配置内存类型的手段：

### 5.1 MTRR：按物理地址范围设置

**MTRR**（Memory Type Range Registers，内存类型范围寄存器）是一组 CPU 寄存器，可以设置“物理地址从 X 到 Y 这一段是什么类型”。它通常由 BIOS/固件在开机时设置好，比如“0～2GB 是可缓存的内存，3GB～4GB 是不可缓存的 PCI 设备区”。

MTRR 的特点是**按物理地址设置**，不依赖页表，而且数量有限（通常只有十几个范围）。

### 5.2 PAT：按页设置

**PAT**（Page Attribute Table，页属性表）则和 ARM64 的 MAIR 很像：CPU 里有一张 8 项的属性表，页表项里用 3 个比特（PAT、PCD、PWT）来选择其中一项。

最终一个页面的类型，由 MTRR 和 PAT **共同决定**（按一套规则组合，大致是“取更严格的那个”）。

### 5.3 x86 的几种内存类型

| 类型 | 全称 | 含义 | 典型用途 |
|---|---|---|---|
| **UC** | Uncacheable | 不可缓存，严格按顺序，不推测 | 设备寄存器 |
| **UC-** | Uncacheable minus | 和 UC 一样，但允许被 MTRR 的 WC 设置覆盖 | Linux `ioremap` 的默认值 |
| **WC** | Write-Combining | 不缓存读，但写可以在专门的缓冲区里合并后一起发出 | 显存、帧缓冲 |
| **WT** | Write-Through | 读可缓存，写同时写缓存和内存 | 少见 |
| **WP** | Write-Protected | 读可缓存，写直接发到总线并使缓存失效 | 少见 |
| **WB** | Write-Back | 完全可缓存，写回 | 普通内存 |

对应关系大致是：x86 的 UC ≈ ARM64 的 Device（尤其是 nGnRnE/nGnRE），x86 的 WC ≈ ARM64 的 Normal Non-cacheable，x86 的 WB ≈ ARM64 的 Normal 写回可缓存。

一个有趣的区别：x86 的内存模型本身比 ARM64 严格得多（“强内存序”），所以在 x86 上很多顺序问题天然不存在。这也是为什么很多在 x86 上跑得好好的驱动，移植到 ARM64 上就出现奇怪的 bug——第 6 篇会讲到。

## 六、写合并：为什么显存要“开个口子”

### 6.1 问题：显存太大，写得太多

上面讲的规则是“设备内存一律不缓存、不合并”。但有一类设备是例外：**显卡的帧缓冲（framebuffer）**。

帧缓冲就是显存里存放屏幕画面的那块区域。一块 1920×1080 的屏幕，每个像素 4 字节，一帧画面就是约 8MB。刷新一次画面，CPU 要往帧缓冲里写 200 多万次（每次 4 字节）。

如果把帧缓冲当作严格的设备内存（UC 或 Device-nGnRE），每一次 4 字节的写都要作为一次独立的总线事务发出去，一个一个排队，效率极低。

### 6.2 写合并的思路

但帧缓冲有一个特点：**它其实更像内存，而不像寄存器**。往帧缓冲写像素没有副作用，写两次和写一次的最终结果一样（屏幕上显示的是最后写的颜色），写的顺序也无所谓（反正最后整个画面都会被刷新）。唯一的要求是：**不要缓存读**（因为显卡也可能在修改它），**写要尽快送到**。

于是 CPU 设计者提供了一种折中的类型——**写合并（Write-Combining，WC）**：

- CPU 内部有几个专门的“写合并缓冲区”，每个通常是一个缓存行大小（64 字节）；
- 对 WC 内存的写，先放进这个缓冲区；
- 如果后续的写落在同一个 64 字节范围内，就合并到同一个缓冲区里；
- 缓冲区满了（或者遇到屏障指令等情况），就把整个 64 字节**一次性**发给设备。

```
CPU 依次写像素：  [0] [1] [2] ... [15]        （16 次 4 字节写）
                         │
                         ▼
              ┌────────────────────────┐
              │  写合并缓冲区（64 字节） │
              │ [0][1][2]...[15]        │
              └───────────┬────────────┘
                          │ 满了，一次性发出
                          ▼
                     显卡帧缓冲              （1 次 64 字节突发写）
```

16 次小写变成了 1 次大写，总线效率提高了一个数量级。

### 6.3 写合并的代价

写合并的代价是：**写入的顺序和时机都不再严格**。数据可能在缓冲区里停留一段时间才发出去，不同缓冲区的数据发出的顺序也可能与写入顺序不同。

所以写合并**只能**用于那些“对顺序和时机不敏感”的设备区域，比如显存、某些网卡的大块数据缓冲区。**绝对不能**用于控制寄存器——想象一下，你写了“设置参数”和“开始”两个命令，结果它们在写合并缓冲区里被调换了顺序，或者“开始”命令在缓冲区里待了好几毫秒才发出去。

如果确实需要确保写合并缓冲区里的数据已经发出去（比如写完一帧画面后要通知显卡“可以显示了”），需要执行一条屏障指令来“冲刷”缓冲区。这又是第 6 篇的话题。

在 PCI 设备上，一块区域能不能用写合并，通常由设备的 BAR 是否标记为“**可预取（prefetchable）**”来提示（第 10 篇）。在 Linux 里，驱动用 `ioremap_wc` 来建立写合并映射。

## 七、属性设错了会怎样

### 7.1 把设备映射成可缓存

这是第二节描述的灾难：读到过期的值，写不能及时到达，预取和推测触发不该有的副作用。这类 bug 的症状往往很诡异——“有时候好，有时候坏”“加一行打印就好了”（因为打印改变了缓存的状态）。

### 7.2 把内存映射成设备

反过来，如果把普通内存映射成 Device 类型，功能上通常不会出错，但会**极其缓慢**——每次访问都绕过缓存，直接访问内存条。另外，那些在 Device 内存上不允许的操作（未对齐访问、`DC ZVA`、原子操作）也会出错。

### 7.3 同一块物理地址用两种属性映射

最危险的是**属性冲突（mismatched attributes）**：同一块物理地址，在一个地方被映射成可缓存，在另一个地方被映射成不可缓存。

比如内核把一块内存映射成 Normal 可缓存，同时某个驱动又用 `ioremap` 把同一块内存映射成 Device。通过前一个映射写入的数据可能还在缓存里，通过后一个映射读到的却是内存条上的旧数据；更糟的是，缓存里的脏数据可能在任意时刻被写回，覆盖掉通过后一个映射写进去的新数据。

ARM 架构手册明确规定，这种情况会导致“失去一致性”，结果不可预测。所以 Linux 内核会尽量阻止这种情况——比如 ARM64 上的 `ioremap` 会拒绝映射已经被当作普通内存管理的物理地址。

> **原则：一块物理地址，应该只用一种内存属性来映射。**

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 缓存行 | 缓存搬运数据的单位，通常 64 字节 |
| 写回 | 写只改缓存副本，被挤出缓存时才写回内存 |
| 预取/推测执行 | CPU 提前读可能用到的数据，对设备会凭空触发副作用 |
| 内存属性 | 写在页表项里，告诉 CPU 这一页能不能缓存、能不能合并重排 |
| MMU 关闭时 | ARM64 把所有数据访问都当作 Device-nGnRnE |
| Normal 内存 | 允许缓存、预取、推测、合并、重排、未对齐访问 |
| Device 内存 | 不缓存、不推测、不允许未对齐访问、部分指令不可用 |
| G / R / E | 聚合（合并访问）、重排（调换顺序）、提前写确认；前面加 n 表示禁止 |
| Device-nGnRE | Linux ARM64 上 `ioremap` 的默认类型 |
| MAIR + AttrIndx | 8 项属性菜单 + 页表项里的 3 位索引 |
| x86 MTRR / PAT | 按物理范围 / 按页设置内存类型 |
| UC / WC / WB | x86 的不可缓存、写合并、写回三种主要类型 |
| 写合并 | 不缓存读，但合并多次写一起发出；用于显存，绝不能用于控制寄存器 |
| 属性冲突 | 同一物理地址用不同属性映射，会导致数据不一致 |
