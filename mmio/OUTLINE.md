# 大纲

**读者**：会一点编程（能看懂简单的 C 代码）、但没学过操作系统和硬件的新手。
**目的**：花几个小时读完，对 MMIO 有相当程度的了解。只读不练，不安排动手实验。
**写法**：从现实问题出发，先讲“为什么需要”，再讲“是什么”，最后讲“怎么用、坑在哪”。多用生活类比和文字图，每篇末尾有“本篇小结”表格。
**代码**：只放简短的 C 示例片段帮助理解，不放汇编，不追求完整可编译。
**约定**：涉及硬件细节时以 ARM64（aarch64）为例，必要时对比 x86。深度对齐本仓库《mmap 从零讲透》。与《mmap 从零讲透》《彻底搞懂 Firecracker》重叠的内容（页表、缺页、KVM）只简要回顾并给出链接。
**规模**：13 篇，每篇约 3500～5500 字，合计约 6 万字。

## 第一部分　打地基：CPU 怎么和外设说话

### 第 1 篇　从点亮一盏灯说起：程序怎么控制硬件

- 一个问题：`printf` 的字最后是怎么跑到屏幕或串口上的？CPU 只会读写内存和做运算，它怎么“指挥”一块网卡？
- 外设内部有一块“控制面板”：用遥控器按钮和仪表盘类比寄存器
- 两种思路：一种是专用 I/O 指令（端口 I/O，x86 的 `in`/`out`），另一种是内存映射 I/O，即把设备寄存器“摆”到地址里，用普通的读写内存操作访问
- 历史小故事：PDP-11 的 Unibus；x86 为什么有 64K 端口空间；ARM 和 RISC-V 为什么只有 MMIO
- MMIO 的一句话定义；它和“内存”“mmap”这两个容易混的词是什么关系
- 引子：地址明明是给内存用的，设备是怎么“住”进去的？

### 第 2 篇　地址空间与总线：一个地址到底送到了哪里

- 物理地址空间是一张“城市地图”，不是每个地址都通向内存条
- 地址译码：总线和片上互连如何按地址把一次读写送到内存、ROM 或某个设备（用快递分拣中心类比）
- 看一张真实的地址分布图：以 QEMU `virt` 机器为例，看 Flash、中断控制器、串口、时钟、virtio 设备、PCIe 和内存各占哪一段
- 系统怎么知道设备在哪：写死在代码里、设备树的 `reg` 属性、ACPI、PCI 枚举（第 10 篇详讲）
- 访问一个“空洞”地址会怎样：总线错误、外部中止、读回全 F
- `/proc/iomem` 怎么读（直接给出示例输出并逐行解释）
- 和虚拟地址的关系：CPU 发出的是虚拟地址，经 MMU 翻译后才变成物理地址（回顾，链接《mmap 从零讲透》第 3 篇）

### 第 3 篇　设备寄存器：设备的“控制面板”

- 寄存器的分类：控制、状态、数据、中断相关；基址加偏移量
- 位域：一个 32 位寄存器里塞了多个开关；掩码、移位、读-改-写
- 寄存器和内存的本质区别是读写有“副作用”：
  - 读一次值就变：FIFO 数据寄存器、读清零
  - 写 1 清零（W1C）、只读、只写、写进去的值读不回来
  - 写入会触发动作：启动传输、按门铃
- 照着手册认识一个真实设备：ARM PL011 串口的几个关键寄存器（数据、标志、波特率、控制）
- 一段简短的 C 示例：等串口发送缓冲区不满，再写一个字符，逐行解释它在干什么
- 用 C 描述寄存器的常见写法：偏移量宏、结构体映射；为什么不推荐用 C 的位域语法
- 小结：后面那么多“坑”，几乎都来自“寄存器不是内存”这一点

## 第二部分　正确地访问 MMIO：坑在哪里

### 第 4 篇　volatile 与编译器：为什么寄存器读写会“消失”

- 编译器眼中的内存：它可以合并、删除、缓存到 CPU 寄存器里、重排、拆分你的读写
- 典型事故：轮询状态寄存器的循环，开了优化后变成死循环（用“编译器以为值不会变”来解释，不看汇编）
- `volatile` 保证了什么：每次访问都真实发生、volatile 访问之间不被编译器重排
- `volatile` 不保证什么：不保证 CPU 层面的顺序、不保证原子性、不保证访问宽度
- 访问宽度与对齐：8/16/32/64 位寄存器必须用对应宽度访问；结构体拷贝和 `memcpy` 的坑
- Linux 为什么不直接用 `volatile` 指针，而用 `readl`/`writel` 这类访问函数（第 9 篇详讲）
- 小结表：编译器优化与 MMIO 冲突的几种形态

### 第 5 篇　内存属性与缓存：设备内存为什么不能被缓存

- 回顾缓存与缓存行；假如串口的数据寄存器被缓存了，会发生什么
- 推测读与预取：CPU 可能“提前”读一个地址，对内存无害，对 FIFO 却是灾难
- ARM64 的两大类内存：Normal 与 Device；Device 的 nGnRnE / nGnRE / nGRE / GRE 分别是什么意思（聚合、重排、提前写响应）
- 一页内存是什么属性由页表决定：MAIR 寄存器与页表项的配合（概念讲解）
- x86 对照：MTRR、PAT，以及 UC、WC、WT、WB 几种类型
- 写合并：为什么显存帧缓冲用写合并，控制寄存器却必须用不可缓存
- Device 内存上的限制：不能未对齐访问、有些指令不能用；Linux 为什么要用 `memcpy_toio` 代替 `memcpy`

### 第 6 篇　顺序与屏障：先写数据，再按门铃

- 经典场景：先往设备写好参数，最后写“开始”寄存器；如果顺序错了，设备就拿到半成品
- CPU 层面的乱序：写缓冲、乱序执行、多核；ARM64 是弱内存序（回顾《mmap 从零讲透》第 8 篇）
- 提前写响应（posted write）：写指令完成不等于设备已经收到；常见做法是读回同一设备来“冲刷”
- ARM64 的三种屏障 DMB、DSB、ISB 各管什么（概念讲解，不讲指令写法）
- 普通内存与 MMIO 之间的顺序：为什么写完 DMA 缓冲区再按门铃需要屏障
- Linux 的约定：`writel` 自带屏障，`writel_relaxed` 不带；`wmb`、`dma_wmb`、`mb` 的区别
- 一个典型 bug 的复盘：网卡驱动的门铃顺序问题
- 小结：一张“什么时候需要哪种屏障”的决策表

### 第 7 篇　设备怎么“回话”：轮询与中断

- 轮询：一直读状态寄存器；优缺点，以及什么时候反而更好（高性能网络、NVMe 轮询模式）
- 中断：设备“拉一下铃”，CPU 暂停手头工作去处理
- ARM64 的中断控制器 GIC：它自己也是通过 MMIO（或系统寄存器）来配置的
- 中断处理里的 MMIO：读中断状态、写清除；清晚了为什么会造成“中断风暴”
- 电平触发与边沿触发；中断屏蔽
- MSI/MSI-X：中断本身就是一次往特定地址的 MMIO 写

### 第 8 篇　MMIO 与 DMA：控制走 MMIO，数据走 DMA

- 为什么不能全靠 MMIO 搬数据：让 CPU 一个字一个字地搬太慢
- DMA 的思路：CPU 用 MMIO 告诉设备“数据在内存哪里、有多长”，设备自己去读写内存
- 描述符环：生产者/消费者索引；门铃寄存器的作用
- 一次网卡发包的完整流程：填描述符 → 屏障 → 写门铃 → 设备 DMA → 中断 → 回收
- DMA 与缓存一致性：一致性 DMA 与流式 DMA；ARM64 上为什么有时要手动维护缓存
- IOMMU/SMMU：给设备也装上“页表”，防止它乱写内存
- 小结：一张 MMIO、DMA、中断三者的分工图

## 第三部分　操作系统里的 MMIO

### 第 9 篇　Linux 内核驱动里的 MMIO

- 内核也用虚拟地址：`ioremap` 把设备物理地址映射进内核地址空间，同时设好 Device 属性
- `__iomem` 标记是做什么的；为什么不能直接解引用
- 访问函数家族：`readb/w/l/q`、`writeb/w/l/q`、`_relaxed` 版本、`ioread32`、`memcpy_fromio`
- 资源管理：`request_mem_region`，`/proc/iomem` 里的占用记录，`devm_*` 自动释放
- 从设备树到驱动：`platform_device`、`devm_platform_ioremap_resource`
- 一个最小驱动的代码骨架（几十行示例，讲清楚每一步在干什么）
- regmap：寄存器访问的抽象层（简介）

### 第 10 篇　PCI 与 PCIe：设备地址是“谈”出来的

- 为什么 PCI 设备的地址不能写死：插槽、热插拔、设备数量都不确定
- 配置空间：每个设备都有的“身份证 + 申请表”（厂商 ID、设备 ID、类别、BAR）
- BAR：设备声明“我需要多大一块 MMIO 空间”，系统给它分配基址；“写全 1 再读回”探测大小的技巧
- 32/64 位 BAR、可预取（prefetchable）、I/O BAR
- ECAM：配置空间本身也是通过 MMIO 访问的
- 枚举过程：固件和内核如何扫描总线、分配地址、配置桥的窗口
- 怎么读 `lspci -vv` 里的 Region 行（给出示例输出并解释）
- 驱动这边怎么用：`pci_iomap`、`pci_resource_start`

### 第 11 篇　在用户态访问 MMIO：/dev/mem、UIO 与 VFIO

- 用户程序能不能直接摸硬件？能，但要靠 `mmap` 把设备的物理地址映射进来（呼应《mmap 从零讲透》第 12 篇）
- `/dev/mem`：最原始的方式；`CONFIG_STRICT_DEVMEM` 等安全限制
- sysfs 的 `resource0`：直接 `mmap` 一个 PCI BAR
- 用户态映射设备内存时页属性怎么设：不可缓存与写合并
- UIO：最小的用户态驱动框架，中断怎么通知到用户程序
- VFIO：配合 IOMMU 的安全方案；DPDK、SPDK 为什么要在用户态写驱动
- 风险清单：写错地址导致死机、权限问题、和内核驱动抢设备

## 第四部分　虚拟化与全景

### 第 12 篇　虚拟机里的 MMIO 与 virtio-mmio

- 客户机里的驱动以为自己在写真设备，背后其实没有硬件，这是怎么做到的
- 原理：MMIO 区域在第二阶段页表里故意“不映射”，客户机一访问就陷入宿主机（两阶段翻译回顾，链接《彻底搞懂 Firecracker》）
- 一次 MMIO 写的旅程：客户机写寄存器 → 陷入 → KVM 解析出地址、宽度、数据 → 交给 VMM（如 Firecracker）模拟 → 回到客户机
- 代价与优化：每次退出要几微秒；ioeventfd、内核内模拟、设备直通
- virtio-mmio：为虚拟机设计的 MMIO 设备；寄存器布局（MagicValue `0x74726976` 即 “virt”）、初始化握手、QueueNotify 门铃（呼应第 8 篇）
- virtio-mmio 与 virtio-pci 的对比；Firecracker 为什么选 virtio-mmio
- 更多细节见《彻底搞懂 Firecracker》的相关篇目

### 第 13 篇　全景、常见坑与安全

- 一次按键从设备到程序的全链路复盘，把前 12 篇串起来
- 常见坑汇总表：忘了 volatile、访问宽度不对、缓存属性错误、缺屏障、W1C 误清、读清零寄存器被调试器“偷读”
- 排查时常用的工具和信息来源：`/proc/iomem`、`lspci`、`devmem2`、`mmiotrace`（只介绍是什么）
- 安全话题：DMA 攻击与 IOMMU、`/dev/mem` 的风险、MMIO 相关的 CPU 漏洞（如 MMIO Stale Data）简介
- 其他架构速览：RISC-V、x86 的 MMIO 现状
- 术语表（中英对照）与延伸阅读
