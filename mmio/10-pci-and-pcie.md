# 第 10 篇｜PCI 与 PCIe：设备地址是“谈”出来的

> **本篇目标**：理解 PCI/PCIe 设备的 MMIO 地址是怎么来的。读完本篇，你会知道什么是配置空间、什么是 BAR、系统如何通过“写全 1 再读回”探测设备需要多大的地址空间、开机时的枚举过程是怎样的，并能读懂 `lspci -vv` 输出里的 Region 行。

---

## 一、为什么 PCI 设备的地址不能写死

### 1.1 SoC 设备 vs. PCI 设备

上一篇讲的 platform 设备，地址是芯片设计时就定死的，写在设备树里。串口永远在 `0x09000000`，不会变。

但你电脑里的显卡、网卡、NVMe 固态硬盘，情况完全不同：

- **插在哪个槽位不确定**：同一块网卡，今天插在第一个槽，明天可能插在第三个槽。
- **插了几块不确定**：一台服务器可能插 2 块网卡，也可能插 8 块 GPU。
- **每块设备需要的地址空间大小不一样**：一块简单的网卡可能只需要 128KB 的寄存器空间，一块高端 GPU 可能需要 16GB 甚至更多（把整个显存都映射出来）。
- **可能热插拔**：服务器上的 NVMe 硬盘可以在运行时插拔。
- **主板厂商不知道你会插什么**：主板设计时根本不可能预知用户会插什么设备。

所以，PCI 设备的 MMIO 地址**不可能事先写死**。必须有一种机制，让系统在开机时（或设备插入时）动态地：

1. 发现有哪些设备；
2. 问清楚每个设备需要多大的地址空间；
3. 给每个设备分配一段不冲突的地址；
4. 告诉设备“你的地址是这里”。

这就像一个新小区开盘：开发商（芯片设计者）只划定了一大片“商业区”（第 2 篇地址地图里的 PCIe 窗口），但具体哪家店铺用哪间门面，要等商户入驻时再分配。每个商户先报上自己需要多大面积，物业再给它们分配门牌号。

### 1.2 一点历史

**PCI**（Peripheral Component Interconnect）是 Intel 在 1992 年推出的总线标准，用来取代更老的 ISA 总线。ISA 时代的设备地址和中断号都要靠用户手动拨跳线来设置，冲突了就无法工作，非常痛苦。PCI 的一大革命就是引入了**自动配置**——也就是本篇要讲的机制。

**PCIe**（PCI Express）是 2003 年左右推出的后继者。它的物理层完全不同（从并行总线改成了高速串行点对点链路），但**在软件看来，PCIe 和 PCI 几乎完全兼容**：同样的配置空间、同样的 BAR、同样的枚举过程。所以本篇里说的“PCI”，绝大部分也适用于 PCIe。

## 二、PCI 设备的“门牌号”：BDF

在讨论地址分配之前，先要解决一个问题：系统怎么**称呼**一个 PCI 设备？

PCI 设备用一个三元组来唯一标识，叫 **BDF**：

- **Bus（总线号）**：设备在哪条 PCI 总线上，8 位，0～255；
- **Device（设备号）**：在这条总线上的第几个设备，5 位，0～31；
- **Function（功能号）**：一个物理设备可以有多个“功能”（比如一块网卡上有 4 个网口，就有 4 个功能），3 位，0～7。

在 Linux 里，BDF 通常写成 `总线:设备.功能` 的形式，比如 `00:01.0`、`3b:00.1`。前面还可以加一个**域号**（domain，也叫 segment），用于有多个独立 PCI 层次结构的大型服务器，比如 `0000:3b:00.1`。

第 2 篇 `/proc/iomem` 里的这一行：

```
  10000000-100fffff : 0000:00:01.0
```

意思就是：域 0、总线 0、设备 1、功能 0 的这个 PCI 设备，被分配到了 `0x10000000` 开始的 1MB 地址。

## 三、配置空间：每个设备的“身份证 + 申请表”

### 3.1 什么是配置空间

每个 PCI 设备（准确地说，每个功能）都有一小块特殊的寄存器区域，叫**配置空间（configuration space）**。

- 传统 PCI：每个功能 **256 字节**；
- PCIe：扩展到每个功能 **4KB**（前 256 字节和 PCI 兼容）。

配置空间的特殊之处在于：**它不依赖于 MMIO 地址分配**。即使设备还没有被分配任何 MMIO 地址，系统也能通过 BDF 去访问它的配置空间。这是“鸡生蛋蛋生鸡”问题的解法：要先能和设备说上话，才能给它分配地址。

### 3.2 配置空间里有什么

配置空间的前 64 字节是标准化的“头部”，所有 PCI 设备格式都一样。其中最重要的几个字段：

```
偏移量   大小   字段                  含义
──────────────────────────────────────────────────────────────────
0x00     2      Vendor ID            厂商 ID：0x8086=Intel，0x10DE=NVIDIA，
                                     0x1AF4=Red Hat（virtio）……
                                     0xFFFF 表示这里没有设备
0x02     2      Device ID            设备型号 ID，由厂商自己定义
0x04     2      Command              命令寄存器：
                                       位 0：允许响应 I/O 访问
                                       位 1：允许响应 MMIO 访问
                                       位 2：允许发起 DMA（Bus Master）
0x06     2      Status               状态寄存器
0x08     1      Revision ID          版本号
0x09     3      Class Code           设备类别：网卡、存储控制器、显卡……
0x0E     1      Header Type          0=普通设备，1=PCI 桥
0x10     4      BAR 0                ┐
0x14     4      BAR 1                │
0x18     4      BAR 2                │  六个基址寄存器
0x1C     4      BAR 3                │  （Base Address Register）
0x20     4      BAR 4                │
0x24     4      BAR 5                ┘
0x2C     2      Subsystem Vendor ID  子系统厂商（比如显卡的品牌商）
0x34     1      Capabilities Pointer 能力链表的起点（MSI、MSI-X、电源管理……）
0x3C     1      Interrupt Line       传统中断线号
```

可以把它看成设备的**身份证 + 申请表**：

- **身份证**部分：Vendor ID、Device ID、Class Code——“我是谁”。操作系统根据它们找到合适的驱动。
- **申请表**部分：BAR——“我需要多大的地址空间”。
- **开关**部分：Command 寄存器——“允许我工作吗”。

### 3.3 能力链表

配置空间从偏移 `0x34` 指向的位置开始，还有一个**能力链表（capability list）**：一串可选的功能描述块，每个块里有一个“下一个块在哪”的指针。常见的能力有：

- **MSI / MSI-X**：第 7 篇讲的消息信号中断。MSI-X 能力块里会说明“MSI-X 表在第几个 BAR 的什么偏移处”。
- **电源管理**：设备支持哪些省电状态。
- **PCIe 能力**：链路速度、宽度等 PCIe 特有的信息。

PCIe 的 256～4095 字节还有一个**扩展能力链表**，存放 AER（高级错误报告）、SR-IOV（单根 I/O 虚拟化）等高级功能的描述。

## 四、怎么访问配置空间

配置空间这么重要，那 CPU 怎么去读写它呢？有两种方式。

### 4.1 老方法：x86 的 `0xCF8`/`0xCFC` 端口

在 x86 上，最初的 PCI 规范定义了一种用**端口 I/O**（第 1 篇）访问配置空间的方法：

1. 把“我要访问哪个 BDF 的哪个偏移”编码成一个 32 位数，写到端口 `0xCF8`；
2. 然后读写端口 `0xCFC`，就是在读写那个配置寄存器。

这种方法只能访问前 256 字节，而且两步操作之间不能被打断（需要加锁），效率很低。

### 4.2 新方法：ECAM，配置空间也是 MMIO

PCIe 引入了一种更直接的方法：**ECAM（Enhanced Configuration Access Mechanism，增强配置访问机制）**。

思路很简单：**把所有设备的配置空间，按 BDF 顺序排列，整体映射到一段 MMIO 地址上。**

每个功能 4KB，每个设备 8 个功能，每条总线 32 个设备，最多 256 条总线：

```
4KB × 8 × 32 × 256 = 256MB
```

于是，任何一个配置寄存器的地址都可以直接算出来：

```
地址 = ECAM 基址 + (总线号 << 20) + (设备号 << 15) + (功能号 << 12) + 寄存器偏移
```

回顾第 2 篇 QEMU `virt` 的地址地图：

```
0x3F00_0000 ~ 0x3FFF_FFFF    16MB    PCIe 配置空间（ECAM）
```

16MB = 16 条总线 × 1MB/总线。所以在 QEMU `virt` 上，要读 `00:01.0` 的 Vendor ID，只需要读物理地址：

```
0x3F000000 + (0 << 20) + (1 << 15) + (0 << 12) + 0x00 = 0x3F008000
```

**配置空间本身也是 MMIO。** 这样一来，访问配置空间和访问普通设备寄存器没有任何区别，用的都是 `readl`/`writel`。ARM64 平台没有端口 I/O，ECAM 是唯一的选择。

在 Linux 里，驱动不需要自己计算这个地址，而是用 `pci_read_config_dword`、`pci_write_config_word` 这类函数，内核会根据平台选择合适的访问方式。

## 五、BAR：设备的“面积申请”

### 5.1 BAR 是什么

**BAR（Base Address Register，基址寄存器）** 是配置空间里最关键的字段。每个设备最多有 6 个 BAR，每个 BAR 描述设备的**一块** MMIO（或端口 I/O）区域。

比如一块网卡可能有：

- BAR 0：控制寄存器区，128KB；
- BAR 2：MSI-X 表所在的区域，16KB；
- BAR 4：闪存（存放固件）的访问窗口，1MB。

每个 BAR 承担两个职责：

1. **开机时**：告诉系统“我需要一块多大的、什么类型的地址空间”；
2. **分配之后**：记录系统分配给它的**基址**。从此以后，设备只响应落在这段地址范围内的 MMIO 访问。

### 5.2 BAR 的格式

一个 32 位 BAR 的低几位是只读的“类型标志”，高位是可写的基址：

```
内存 BAR（位 0 = 0）：

  31                                    4   3    2  1    0
 ┌──────────────────────────────────────┬────┬──────┬────┐
 │              基址                     │预取│ 类型 │ 0  │
 └──────────────────────────────────────┴────┴──────┴────┘
                                           │    │
                                           │    └─ 00 = 32 位地址
                                           │       10 = 64 位地址（占用两个 BAR）
                                           └─ 1 = 可预取（prefetchable）

I/O BAR（位 0 = 1）：

  31                                         2   1    0
 ┌───────────────────────────────────────────┬────┬────┐
 │              基址                          │保留│ 1  │
 └───────────────────────────────────────────┴────┴────┘
```

几个要点：

- **位 0** 区分是内存 BAR（MMIO）还是 I/O BAR（端口 I/O）。现代设备几乎都用内存 BAR。
- **64 位 BAR**：如果设备需要的空间很大，或者希望被放在 4GB 以上的地址，可以用 64 位 BAR。它会**占用两个连续的 BAR 位置**，第一个存低 32 位，第二个存高 32 位。所以一个设备最多可以有 3 个 64 位 BAR。
- **可预取（prefetchable）**：表示这块区域“读没有副作用”，可以被预取，也可以使用写合并。第 5 篇说过，显存这种更像内存的区域通常标记为可预取，而控制寄存器区域绝对不能标记为可预取。系统据此决定能不能用 `ioremap_wc` 来映射它。

### 5.3 “写全 1 再读回”：探测 BAR 大小

BAR 里只有基址的位置，并没有一个字段直接写着“我需要多大”。那系统怎么知道设备需要多大的空间？

答案是一个非常巧妙的技巧：**往 BAR 里写全 1，再读回来。**

原理是这样的：

- PCI 规范要求，设备需要的地址空间大小必须是 **2 的幂**（4KB、64KB、1MB……），而且基址必须**按大小对齐**。
- 所以，如果一块区域大小是 64KB（`0x10000`），那么基址的低 16 位一定全是 0。设备就把 BAR 中这些位做成**只读的 0**——无论你写什么，读回来都是 0。
- 只有高于“大小”的那些位是可写的。

探测过程：

```
步骤 1：往 BAR 写入 0xFFFFFFFF

步骤 2：读回 BAR
        得到 0xFFFF0000
        （低 16 位写不进去，仍然是 0；高 16 位被写成了 1）
        
步骤 3：清掉低 4 位的类型标志
        0xFFFF0000 & 0xFFFFFFF0 = 0xFFFF0000

步骤 4：取反再加 1
        ~0xFFFF0000 + 1 = 0x0000FFFF + 1 = 0x00010000 = 64KB

结论：这个 BAR 需要 64KB 的地址空间
```

用一个比喻：BAR 就像一张表格，前面的格子可以填，后面的格子被预先涂黑了。你拿笔把所有格子都涂上，再看看——哪些格子涂不上颜色，就知道表格有多“短”，也就知道对方要多大的面积了。

**注意一个细节**：在探测过程中，BAR 的值被临时写成了全 1，这时设备会去响应一个奇怪的地址范围。所以在探测之前，系统要先把 Command 寄存器的“允许响应 MMIO 访问”位关掉，探测完、写好正式的基址之后再打开。

### 5.4 分配地址

知道了每个 BAR 需要多大，系统就从 PCIe 窗口（第 2 篇地图里的那一大块）里给它划出一段对齐的地址，写进 BAR。最后打开 Command 寄存器的 MMIO 位。

从这一刻起，CPU 访问这段地址，就会通过 PCIe 链路送到这个设备上——设备的 MMIO 地址就这样“谈”出来了。

## 六、枚举：开机时的大普查

### 6.1 拓扑结构

真实的 PCIe 系统是一棵树：

```
                      CPU
                       │
               ┌───────┴────────┐
               │   根复合体      │   Root Complex：CPU 和 PCIe 世界的接口
               │   （主桥）      │   管理 PCIe 窗口和 ECAM
               └───┬───────┬────┘
           总线 0  │       │
            ┌──────┘       └───────┐
            ▼                      ▼
       ┌─────────┐            ┌─────────┐
       │ 根端口  │ (00:01.0)  │ 根端口   │ (00:02.0)     ← 根端口本身是一个“PCI 桥”
       └────┬────┘            └────┬────┘
     总线 1 │                总线 2 │
            ▼                      ▼
       ┌─────────┐            ┌──────────┐
       │  网卡   │ (01:00.0)  │ PCIe 交换机│               ← 交换机内部也是桥
       └─────────┘            └──┬────┬──┘
                          总线 3 │    │ 总线 4
                                 ▼    ▼
                              NVMe   GPU
                            (03:00.0)(04:00.0)
```

树的每个分叉点是一个**PCI 桥**（bridge），桥的上游是一条总线，下游是另一条总线。

### 6.2 枚举过程

开机时，系统（固件或操作系统）要对这棵树做一次完整的“普查”，大致步骤：

1. **从总线 0 开始，逐个检查每个设备号、功能号**：读它的 Vendor ID。如果读到 `0xFFFF`，说明这里没有设备（第 2 篇说过，访问不存在的 PCI 设备通常读回全 F）。
2. **发现一个设备**：读它的 Header Type。
   - 如果是**普通设备**：探测它所有 BAR 的大小，记下来。
   - 如果是**桥**：给桥下游分配一个新的总线号，然后**递归**地去扫描下游总线。
3. **整棵树扫完之后**：知道了每个设备需要多大空间，开始**分配地址**。
   - 从叶子往根汇总：每个桥下面所有设备需要的空间加起来，就是这个桥需要的“窗口”大小；
   - 从根往叶子分配：先给每个桥划一个窗口，再在窗口里给每个设备分配 BAR 地址。
4. **配置桥的窗口**：桥的配置空间里有“内存基址/上限”寄存器，告诉它“落在这个范围内的 MMIO 访问，请转发到下游”。这就像在路由器上配置路由表。
5. **打开设备**：设置每个设备的 Command 寄存器，允许它响应 MMIO 访问、允许它发起 DMA。

桥的窗口也分成两类：**可预取窗口**和**不可预取窗口**，分别容纳下游设备的可预取 BAR 和不可预取 BAR。

### 6.3 谁来做枚举

- **x86 电脑**：通常由 BIOS/UEFI 固件在开机时完成枚举和地址分配，操作系统启动后直接沿用固件分配的地址（必要时也可以重新分配）。
- **ARM64**：情况不一。服务器平台通常由 UEFI 固件完成；嵌入式平台和 QEMU `virt` 上，常常是 Linux 内核自己来做。

无论谁来做，Linux 启动后都会读取配置空间，建立起完整的设备树（这里是“设备的树状结构”，不是第 2 篇的“设备树”文件），在 `/sys/bus/pci/devices/` 下为每个设备创建一个目录，然后根据 Vendor ID、Device ID、Class Code 为每个设备寻找驱动。

## 七、读懂 `lspci -vv`

### 7.1 示例输出

`lspci` 是查看 PCI 设备的标准工具。加上 `-vv` 参数（详细模式），可以看到每个设备的 BAR 信息。下面是一块 NVMe 硬盘的示例输出（节选，具体数值因机器而异）：

```
$ sudo lspci -vv -s 03:00.0
03:00.0 Non-Volatile memory controller: Samsung Electronics Co Ltd NVMe SSD Controller
        Subsystem: Samsung Electronics Co Ltd Device a801
        Control: I/O- Mem+ BusMaster+ SpecCycle- MemWINV- ...
        Status: Cap+ 66MHz- UDF- FastB2B- ...
        Latency: 0, Cache Line Size: 64 bytes
        Interrupt: pin A routed to IRQ 16
        Region 0: Memory at fe600000 (64-bit, non-prefetchable) [size=16K]
        Capabilities: [40] Power Management version 3
        Capabilities: [50] MSI: Enable- Count=1/32 Maskable- 64bit+
        Capabilities: [70] Express (v2) Endpoint, MSI 00
        Capabilities: [b0] MSI-X: Enable+ Count=33 Masked-
                Vector table: BAR=0 offset=00003000
                PBA: BAR=0 offset=00002000
        Kernel driver in use: nvme
```

### 7.2 逐行解读

- **`03:00.0`**：BDF，总线 3、设备 0、功能 0。
- **`Control: I/O- Mem+ BusMaster+`**：这是 Command 寄存器的内容。`I/O-` 表示不响应端口 I/O；`Mem+` 表示**允许响应 MMIO 访问**；`BusMaster+` 表示**允许发起 DMA**。一个正常工作的设备，后两项都应该是 `+`。
- **`Region 0: Memory at fe600000 (64-bit, non-prefetchable) [size=16K]`**：这是本篇的重点。逐段看：
  - `Region 0`：BAR 0；
  - `Memory`：这是一个内存 BAR（MMIO），而不是 I/O BAR；
  - `at fe600000`：系统分配给它的基址是 `0xFE600000`；
  - `64-bit`：这是一个 64 位 BAR（占用了 BAR 0 和 BAR 1 两个位置，所以下一个就不会出现 Region 1）；
  - `non-prefetchable`：不可预取，说明这里是控制寄存器，不能用写合并；
  - `[size=16K]`：大小 16KB，这是通过“写全 1 再读回”探测出来的。
- **`MSI-X: ... Vector table: BAR=0 offset=00003000`**：MSI-X 表位于 BAR 0 的偏移 `0x3000` 处，也就是物理地址 `0xFE603000`。第 7 篇说过，配置中断就是往这里做 MMIO 写。
- **`Kernel driver in use: nvme`**：这个设备被 `nvme` 驱动认领了。

对照 `/proc/iomem`，你会看到同一段地址：

```
fe600000-fe603fff : 0000:03:00.0
  fe600000-fe603fff : nvme
```

### 7.3 NVMe 的 BAR 0 里有什么

顺便看一眼这 16KB 的 MMIO 空间里装着什么，这能把前面几篇的知识串起来。根据 NVMe 规范，BAR 0 的布局大致是：

```
偏移量     寄存器          作用
0x0000     CAP             控制器能力（只读）：支持多少队列、门铃间距……
0x0008     VS              规范版本号
0x0014     CC              控制器配置：启用位、队列条目大小……
0x001C     CSTS            控制器状态：就绪位、致命错误位……
0x0024     AQA             管理队列大小
0x0028     ASQ             管理提交队列的 DMA 地址（64 位）
0x0030     ACQ             管理完成队列的 DMA 地址（64 位）
...
0x1000     门铃寄存器区     每个队列一对门铃：提交队列尾、完成队列头
...
0x2000     MSI-X PBA       （本例中）
0x3000     MSI-X 表        （本例中）
```

这里你能看到：

- **控制寄存器**（CC）和**状态寄存器**（CSTS）——第 3 篇；
- **队列的 DMA 地址寄存器**（ASQ、ACQ）——第 8 篇，告诉设备描述符环在内存哪里；
- **门铃寄存器区**——第 8 篇，提交命令后写门铃；
- **MSI-X 表**——第 7 篇，配置中断。

一块 NVMe 硬盘的全部 MMIO 交互，就发生在这 16KB 里。

## 八、驱动这边怎么用

### 8.1 sysfs 里的 resource 文件

Linux 在 `/sys/bus/pci/devices/<BDF>/` 下为每个 PCI 设备提供了一些文件：

```
$ cat /sys/bus/pci/devices/0000:03:00.0/resource
0x00000000fe600000 0x00000000fe603fff 0x0000000000140204
0x0000000000000000 0x0000000000000000 0x0000000000000000
...
```

每一行对应一个 BAR：起始地址、结束地址、标志。同一个目录下还有 `resource0`、`resource1`…… 这样的文件，它们可以被**直接 mmap** 到用户空间——这是第 11 篇的话题。

### 8.2 PCI 驱动的典型初始化

一个 PCI 驱动在 `probe` 函数里，和 MMIO 相关的部分通常是这样的：

```c
static int my_pci_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
    void __iomem *regs;
    int ret;

    // 1. 启用设备：设置 Command 寄存器的 Mem 位等
    ret = pcim_enable_device(pdev);
    if (ret)
        return ret;

    // 2. 认领 BAR 0 的地址并映射（pcim_：托管版本，自动释放）
    regs = pcim_iomap_region(pdev, 0, "my-driver");
    if (IS_ERR(regs))
        return PTR_ERR(regs);

    // 3. 允许设备发起 DMA：设置 Command 寄存器的 BusMaster 位
    pci_set_master(pdev);

    // 4. 开始访问寄存器
    u32 version = readl(regs + 0x08);
    ...
}
```

（不同内核版本中，托管版 PCI 映射函数的名字有过几次调整，比如较早的代码里常见 `pcim_iomap_regions` + `pcim_iomap_table` 的组合，或者非托管的 `pci_request_regions` + `pci_iomap`。思路都是一样的。）

如果需要知道 BAR 的物理地址和大小（比如要打印出来，或者要交给用户态 mmap），可以用：

```c
resource_size_t start = pci_resource_start(pdev, 0);
resource_size_t len   = pci_resource_len(pdev, 0);
```

和上一篇的 platform 驱动对比一下：

| | platform 设备 | PCI 设备 |
|---|---|---|
| 地址来源 | 设备树/ACPI 里写死的 | 枚举时动态分配，记录在 BAR 里 |
| 匹配依据 | `compatible` 字符串 | Vendor ID + Device ID（或 Class Code） |
| 获取映射 | `devm_platform_ioremap_resource` | `pcim_iomap_region` / `pci_iomap` |
| 额外步骤 | 无 | 启用设备、打开 Bus Master |
| 访问寄存器 | `readl` / `writel` | `readl` / `writel`（或 `ioread32`） |

**一旦映射完成，两者访问寄存器的方式完全一样。** 不同的只是“地址从哪来”。

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 动态分配的必要性 | 设备种类、数量、位置、大小都不确定，必须开机时“谈” |
| BDF | 总线:设备.功能，PCI 设备的唯一标识 |
| 配置空间 | 每个功能 256 字节（PCI）或 4KB（PCIe）的“身份证 + 申请表” |
| Vendor ID / Device ID | 设备的厂商和型号，`0xFFFF` 表示没有设备 |
| Command 寄存器 | Mem 位允许 MMIO，BusMaster 位允许 DMA |
| 能力链表 | MSI、MSI-X、电源管理等可选功能的描述 |
| `0xCF8`/`0xCFC` | x86 用端口 I/O 访问配置空间的老方法 |
| ECAM | 把所有配置空间映射到一段 MMIO 地址，配置空间也是 MMIO |
| BAR | 基址寄存器，声明需要的地址空间大小、记录分配到的基址 |
| 64 位 BAR | 占用两个 BAR 位置 |
| 可预取 | 读无副作用，可用写合并 |
| 写全 1 再读回 | 探测 BAR 大小的技巧：取反加 1 |
| 枚举 | 递归扫描总线、探测 BAR、分配地址、配置桥窗口、打开设备 |
| `lspci -vv` 的 Region 行 | BAR 编号、基址、位宽、是否可预取、大小 |
| `pci_iomap` 等 | PCI 驱动映射 BAR 的函数 |
