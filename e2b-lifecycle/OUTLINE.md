# 大纲

**书名**：《E2B 模板构建、沙箱启动与暂停恢复从零讲透》

**读者**：会一点编程、用过命令行的新手。不要求懂虚拟机、KVM、Firecracker、页表、块设备、网络命名空间，用到时从头讲。

**目的**：花几个小时读完，能把 E2B 原有的三个操作从头到尾讲清楚，也能说清我们为 ARM 和快照回滚对它们做了哪些修改、为什么这样改：

- **构建模板**：一个 Dockerfile 怎样变成一份“随时能拉起来”的虚拟机快照；
- **启动沙箱**：为什么 E2B 的“启动”其实是“恢复快照”，一次启动在宿主上依次发生了什么，时间花在哪；
- **暂停与恢复**（pause / resume）：沙箱怎样“存盘离场”，又怎样在别处“读盘重建”，增量是怎么算出来的；
- **我们的修改**：把这三条路搬到 ARM（鲲鹏）上要改什么；为了更快、更稳又做了哪些优化；加入快照回滚以后，哪些地方被撞坏了、后来怎么修好的。

概念讲透，只读不练，不安排动手实验。

**写法**：从现实问题出发，先讲“为什么需要”，再讲“是什么”，最后讲“这套实现怎么做、坑在哪”。多用生活类比（模具与铸件、存档与读档、仓库与提货单）和图。每篇末尾有“本篇小结”表格。凡讲到我们的修改，都按同一个格式交代：**原来怎样 → 在 ARM 上 / 在并发下 / 和回滚叠加时出了什么问题 → 改成了什么 → 改完的证据**。

**代码**：以讲清原理为主，不逐函数讲解源码，不给读代码的路线。正文只在必要时放几行示例：

- SDK 调用：`Template.build`、`Sandbox.create`、`sandbox.pause()`、`Sandbox.connect()`；
- 启动脚本、Firecracker 的几个 HTTP 接口长什么样；
- 日志里能直接看到的计时行（如 `[ResumeSandbox] configured fc cost`）和几个关键开关（如 `E2B_FC_NETNS_EXEC_HELPER`）。

**依据**：以 [AustinJiangg/e2b-infra](https://github.com/AustinJiangg/e2b-infra) 仓库的现状和提交历史为准。

- **代码**：仓库根目录的 `0001-adapted-for-arm-architecture.patch`（ARM 适配、启动优化、快照相关修改都在这一份补丁里）和 `e2b-deploy/` 部署脚本。用来核对事实，正文不展开讲代码。
- **测量与分析**：`benchmark/` 下的启动耗时分析、高并发瓶颈定位、netns-exec 优化、空闲沙箱内存实测；`deploy-docs/` 下的增量快照 ARM 实测、模板存储位置；`rollback/docs/` 里讲原生快照、精确增量、两种快照配合的几章。正文按新手的顺序重新组织，不照搬。
- **只讲技术**：作者、团队、客户、内部仓库和分支名、服务器地址这些与实现无关的信息，书里一概不写。

**和其他几本书的分工**：

- 快照回滚（checkpoint / restore）本身**不展开**，只在讲“它和暂停恢复怎么互相影响”时用到几个结论，详见《E2B 沙箱快照回滚从零讲透》；
- 部署、网络、存储只讲到本书用得到的程度，详见同仓库的《E2B 部署从零讲透》《E2B 沙箱网络从零讲透》《E2B 沙箱存储从零讲透》；
- 想逐个包、逐个函数地读上游源码，看《E2B Infra 源码导读》。本书不按代码组织，按“一个操作从头到尾”组织。

**规模**：23 篇，每篇约 1700～3500 个汉字，合计约 5.3 万汉字，79 张图。

**名词**：正文统一用这几个说法，第 1 篇给出对照表。

| 本书说法 | 英文 / 接口名 | 一句话 |
|---|---|---|
| 模板 | template / build | 一份“开机到一半就冻住”的虚拟机快照，所有沙箱都从它拉起 |
| 构建 | template build | 从 Dockerfile 做出模板的整个过程 |
| 启动沙箱 | `Sandbox.create` → `Create` RPC → `ResumeSandbox` | 从模板快照恢复出一台新沙箱 |
| 暂停 | `sandbox.pause()` → `Pause` RPC | 存盘并**停掉**沙箱，产物进存储 |
| 恢复 | `Sandbox.connect()` → `ResumeSandbox` | 从暂停留下的快照**重建**一台沙箱 |
| 快照三件套 | snapfile / memfile / rootfs | CPU 与设备状态、内存、磁盘 |
| 映射表 | header | 记录“这一块数据在哪一代的哪个文件里” |
| 一代 | build ID | 每次构建一层、每次暂停，都产生新的一代 |
| 懒加载 | userfaultfd（uffd） | 内存不一次读回，用到哪页再取哪页 |
| 快照回滚 | checkpoint / restore | 我们新增的“活沙箱原地存档读档”，本书不展开 |

**全书的主线**：三个操作其实共享同一套部件，全书反复回到这三句话。

| 一句话 | 解释 | 主要在哪几篇 |
|---|---|---|
| **一切皆快照** | 构建的终点是打一张快照；启动是从快照恢复；暂停是再打一张快照，恢复又是从它恢复。三个操作是同一个循环的不同位置 | 第 1、4、8、10、16 篇 |
| **只为用到的付费** | 启动不读整份内存，用到哪页取哪页；暂停只存改过的页和块；模板按层缓存，没改的层不重做 | 第 4、7、12、17、20 篇 |
| **固定开销藏在“建”和“拆”里** | 启动慢在拉起 Firecracker 进程，暂停慢在拆掉虚机；搬数据反而不是大头 | 第 14、15、17、18 篇 |

**贯穿全书的几个事实**，正文会反复回到这里：

- E2B 从不“冷启动”用户的沙箱。模板构建时已经把系统开到 envd 就绪那一刻并拍下快照，`Sandbox.create` 只是从这张快照恢复，envd 进程在快照里本来就在跑
- 启动一台沙箱，宿主上要准备五样东西：Firecracker 进程、网络槽位、根磁盘（NBD + 写时复制）、内存懒加载（uffd）、guest 里的 envd。前三样在恢复时并行准备
- 100 路并发下，`ResumeSandbox` 平均 294.7 ms，其中 82%（241.6 ms）卡在“拉起 Firecracker 并等它的 API 就绪”；加载快照本身只要 29 ms
- 暂停一定会停掉沙箱。导出磁盘差分这个动作的参数之一就是“关掉沙箱”；恢复一定是新进程，沙箱 ID 不变，底下的 Firecracker 已经换了一个
- 鲲鹏 950 上，暂停一个什么都没改的沙箱也要约 250 ms，其中真正存内存状态的只有前约 10 ms；恢复在各档改动量下都约 100～120 ms
- ARM 适配基线上，内存增量的判据塌缩成“读过就算脏”：改 12 MiB，导出 148 MiB。修成精确增量要同时改三层（判、存、填），只换判据会被 2 MiB 大页卡住
- 快照回滚和暂停恢复是两套独立的机制，但共用 Firecracker、写层、脏页位图。回滚加进来以后，暂停曾经静默丢过数据，后来修好了
- 每个空闲沙箱在宿主上约占 350 MiB（大页 157 MiB + 普通内存 194 MiB），`memory_mb` 是上限而不是占用

## 第一部分　先打底：沙箱是什么，快照是什么

### 第 1 篇｜一个沙箱的一生：构建、启动、暂停、恢复

**要回答的问题**：E2B 是干什么的？这本书讲的三个操作分别是什么，它们在一个沙箱的一生里处在什么位置？

- 从 AI Agent 要“一台随时可用、用完即扔的小电脑”讲起：为什么用虚拟机而不是容器，为什么要求“一百多毫秒内可用”
- 用几行 SDK 走一遍一生：`Template.build` → `Sandbox.create` → 跑命令 → `pause()` → `connect()` → `kill()`
- 三个操作一句话：构建 = 做模具，启动 = 用模具铸一个，暂停 / 恢复 = 存盘离场、改天读盘重建
- 核心洞见先摆出来：**一切皆快照**。三个操作首尾相接，形成一个循环
- 和快照回滚划清界限：暂停恢复是“沙箱离场”，回滚是“活沙箱原地读档”，本书只讲前者
- 我们做了什么：搬到 ARM、提速、和回滚共存，三类修改的地图
- 名词对照表、全书地图、阅读建议

### 第 2 篇｜一台沙箱由什么组成：从 SDK 到 Firecracker

**要回答的问题**：用户手里的 `Sandbox` 对象背后，宿主上有哪些进程、哪些文件？请求怎么一路走到虚拟机里？

- 虚拟机的最小知识：CPU 虚拟化、KVM、为什么 Firecracker 叫“微虚拟机”（只有几样设备，启动快、占用小）
- guest 里有什么：Linux 内核、根文件系统、systemd、envd（沙箱里唯一的“管家”，负责跑命令、读写文件）
- 宿主侧四个服务：api（接请求、记账）、orchestrator（真正管沙箱的人）、template-manager（构建模板）、client-proxy / edge（转发流量）；单节点部署里 orchestrator 和 template-manager 是同一个进程
- 两条路：**控制面**（创建、暂停走 api → orchestrator 的 gRPC）和**数据面**（跑命令走 proxy → envd）
- 一台沙箱在宿主上的“家当”：Firecracker 进程、网络命名空间与 tap、NBD 设备、uffd 处理器、cgroup
- 硬件：x86 与鲲鹏 920B / 950 两类 ARM 机器，后文所有实测数字都注明是哪台

**配图**
- 2-1 一台沙箱的组成：guest 内的内核 / rootfs / envd，宿主上的 Firecracker 与四样家当
- 2-2 宿主侧服务全景：api、orchestrator、template-manager、proxy 与存储
- 2-3 控制面与数据面：一次 `create` 和一次 `run` 各自走哪条路

### 第 3 篇｜必备底子：内存页、缺页、块设备与命名空间

**要回答的问题**：后面反复出现的“页”“大页”“缺页”“写时复制”“命名空间”是什么意思？

- 内存按页管：4 KiB 小页、2 MiB 大页；页表是“门牌号到房间”的对照表；大页为什么能让 TLB 更省
- 缺页：访问一个还没准备好的页时，CPU 停下来请操作系统去补
- userfaultfd：把“补页”这件事交给一个用户态程序来做。E2B 的内存懒加载全靠它
- 块设备与 NBD：把一个“远方的文件”伪装成本地磁盘；写时复制（COW）：底下只读、改动另存一层
- 命名空间：给进程一套独立的“网络视图”“挂载视图”；为什么每台沙箱都要一个网络命名空间
- 稀疏文件、mmap 这两个在构建和暂停里都会用到的小工具

**配图**
- 3-1 页、大页与页表：同样 2 MiB，小页要 512 个表项，大页只要 1 个
- 3-2 缺页与 userfaultfd：guest 访问 → 缺页 → 用户态处理器补页的往返
- 3-3 写时复制的磁盘：只读底层 + 写层，读先查写层，查不到再往下
- 3-4 命名空间：同一台宿主上，每台沙箱看到自己的一套网卡和挂载

### 第 4 篇｜快照是什么：三件套与映射表

**要回答的问题**：一张虚拟机快照里到底存了什么？“一代一代”的增量快照怎么拼起来？

- 快照三件套：snapfile（vCPU 寄存器、中断控制器、设备状态，几十 KB）、memfile（内存）、rootfs（磁盘）
- 为什么 E2B 的内存和磁盘不交给 Firecracker 存，而是自己管：要能增量、能按需取、能上传对象存储
- 映射表（header）：把“设备上的第几块”翻译成“哪一代、哪个文件、哪个偏移”；增量只存改过的块，没改的指向上一代
- 一代就是一个 build ID：模板的每一层、每次暂停，都长出新的一代；查一个块就是沿链条往上找
- 存在哪：本地缓存、本地存储或对象存储（MinIO），以及“模板放在 tmpfs 上，宿主重启即丢”这个部署细节
- 预告：构建是“长出第一批代”，启动是“沿链条读”，暂停是“再长一代”

**配图**
- 4-1 快照三件套：snapfile、memfile、rootfs 各存什么、多大
- 4-2 映射表：一块数据沿 header 找到它所在的那一代
- 4-3 代际链：模板各层 → 第一次暂停 → 第二次暂停，每一代只存自己改的部分
- 4-4 产物落在哪：节点本地缓存、本地存储、对象存储三层目录

## 第二部分　构建模板：从 Dockerfile 到可恢复的快照

### 第 5 篇｜构建总览：为什么镜像不够，要的是一张快照

**要回答的问题**：有了 Docker 镜像为什么还要“构建模板”？构建的输入、输出和主流程是什么？

- 镜像只是一堆文件；要做到一百多毫秒拉起，必须连“开机”这一步也提前做掉，存成一张快照
- 输入：Dockerfile（或基础模板）、CPU 和内存规格、启动命令与就绪检查；输出：一个 build ID 及其快照三件套
- 流水线五段：base（镜像变磁盘、装系统）→ 默认用户 → steps（每条指令一层）→ finalize（跑启动命令、等就绪、拍最终快照）→ optimize（记录预取表）
- 每一段都是“起一台沙箱 → 在里面干活 → 暂停成一层”：**构建本身就是在反复启动和暂停**
- 构建在哪跑、谁在等：api 下发，template-manager 执行，SDK 轮询状态与日志

**配图**
- 5-1 镜像与模板的区别：一堆文件 vs 一台开到一半就冻住的机器
- 5-2 构建流水线：base → user → steps → finalize → optimize，每段产出什么
- 5-3 构建就是反复“启动—干活—暂停”：每一层都是一次小的暂停

### 第 6 篇｜base 阶段：把镜像变成一块能开机的磁盘

**要回答的问题**：一个容器镜像怎样变成虚拟机能用的 ext4 磁盘？为什么第一次开机要用 busybox？

- 拉镜像、校验平台、把各层解包成一个 ext4 文件；磁盘大小与预留空间
- 往磁盘里注入什么：envd、systemd 单元、provision 脚本、busybox
- 第一台构建沙箱：基础镜像里通常没有 systemd，所以用 busybox 当临时的 1 号进程，只跑 `provision.sh` 装上 systemd、ssh、chrony 等
- 第二台构建沙箱：换 systemd 冷启动，等 envd 就绪，暂停成第一层
- 这一段是唯一需要联网（装包）的，也是最容易出错的：内核日志直接流给用户

**配图**
- 6-1 镜像解包成 ext4：各层叠起来压成一个磁盘文件
- 6-2 base 阶段的两台沙箱：busybox 跑 provision，systemd 冷启动后暂停
- 6-3 注入清单：磁盘里被放进了哪些 E2B 自己的文件

### 第 7 篇｜指令、层与缓存：一条 RUN 是怎么执行的

**要回答的问题**：Dockerfile 里的 `RUN`、`COPY`、`ENV` 在 E2B 里怎么落地？为什么改了最后一行，前面的不用重做？

- 每条指令：从上一层恢复一台沙箱 → 通过 envd 执行 → 暂停成新一层
- 一条 RUN 的完整路径：命令经 envd 的进程服务执行、输出流回构建日志
- 层缓存：本层 hash = 上一层 hash + 本条指令；命中就直接跳过，不起沙箱
- 默认用户：在最后一步才创建、为什么要加进 sudo 组
- 和 Docker 层缓存的异同：E2B 的“层”是一整张虚拟机快照，不只是文件差分

**配图**
- 7-1 一条指令一层：恢复 → 执行 → 暂停，层层相叠
- 7-2 层 hash 链：改了第 3 条，第 1、2 条命中缓存
- 7-3 一条 RUN 的路径：template-manager → envd → shell → 日志回流

### 第 8 篇｜finalize 与 optimize：拍下最终那张快照

**要回答的问题**：模板的最后一张快照是在什么时刻拍的？为什么要“重启一次、等就绪、再暂停”？预取表是什么？

- finalize：重启沙箱、跑 `configure.sh`、执行用户的启动命令、轮询就绪命令；就绪那一刻同步磁盘、暂停
- 为什么拍在“就绪那一刻”：之后每台沙箱一恢复就是就绪状态，这是“一百多毫秒可用”的根本来源
- optimize：再恢复两次，记下“一恢复就会访问哪些页、按什么顺序”，存成预取表，供启动时提前搬
- 上传与登记：等产物上传完成、写入层缓存索引，模板才算可用
- 模板产物最终长什么样：一条代际链 + 元数据 + 预取表

**配图**
- 8-1 finalize 的时序：重启 → 配置 → 启动命令 → 就绪 → 拍快照
- 8-2 快照拍在就绪那一刻：之后每次启动都“从就绪开始”
- 8-3 预取表：恢复后访问页的顺序被记下来，下次提前搬

### 第 9 篇｜把构建搬到 ARM 上：我们改了什么

**要回答的问题**：上游 E2B 只在 x86 上跑。要在鲲鹏和 openEuler 上把模板构建跑通，踩过哪些坑？

- 架构写死的地方：镜像平台从 `amd64` 改 `arm64`；内嵌的 busybox 按架构选 x86 / arm64 两份二进制
- 发行版的差异：provision 脚本从只认 apt 改为识别 apt / dnf；建用户 `adduser` 与 `useradd`；sudo 组与 wheel 组；去掉 openEuler 上装不上的包
- 系统环境的差异：envd 的 systemd 单元去掉 cgroup 相关指令；宿主是 cgroup v1 时不报错而是跳过；ARM 上读不到 CPU 型号时给出兜底值
- Firecracker 版本：ARM 上用自己编译的 Firecracker，版本目录标签和实际版本不一致引出的一次构建失败

- 模板构建的虚机不走启动优化（第 15 篇的 netns-exec），以及为什么

## 第三部分　启动沙箱：从模板快照恢复出一台新机器

### 第 10 篇｜启动就是恢复：一次 `Sandbox.create` 的全景

**要回答的问题**：`Sandbox.create` 之后，请求经过了哪些环节？orchestrator 里的 `ResumeSandbox` 分几段？

- 请求链：SDK → api（认证、选节点、挑模板版本）→ orchestrator 的 `Create` RPC

- 和“冷启动”的对比：省掉的是内核启动、systemd、envd 初始化这几秒

### 第 11 篇｜拉起 Firecracker：启动脚本与加载快照

**要回答的问题**：orchestrator 怎样把一个 Firecracker 进程放进正确的网络和文件视图里？快照里写死的文件路径怎么办？

- 问题：快照里录死了固定路径（如 `/fc-vm/rootfs.ext4`），但每台沙箱的磁盘、内核在宿主上是不同的文件

- 等 API socket 出现（10 ms 轮询），然后通过 HTTP 接口加载 snapfile、指定内存由 uffd 提供
- 恢复 vCPU、写 MMDS（把沙箱身份交给 guest）

### 第 12 篇｜内存怎么回来：懒加载、预取与大页

**要回答的问题**：恢复时为什么不把整份内存读回来？一页内存从磁盘文件到 guest 手里经过了什么？

- 懒加载：Firecracker 把 guest 内存交给 uffd，guest 访问哪页，orchestrator 就补哪页
- 补一页的路径：缺页 → 查映射表找到所在代 → 从本地缓存（或对象存储）读 → `UFFDIO_COPY` 填进去
- 大页：guest 内存由 2 MiB 大页背衬，一次缺页填 2 MiB；静态大页池在部署时预留
- 预取：按模板记下的顺序，后台提前把页搬进来，缓解恢复后头几秒的缺页风暴
- 成本被推迟了：恢复本身很快，但恢复后第一次读大块内存比快照前慢
- 一台空闲沙箱占多少内存：实测约 350 MiB（大页 157 + 普通内存 194），`memory_mb = 2048` 只是上限；并发容量先受 orchestrator 的 cgroup 上限约束，而不是大页池

- 12-2 预取与按需：后台按顺序搬，前台缺哪页补哪页
- 12-3 一台空闲沙箱的内存账：大页、page cache、匿名内存各多少

### 第 13 篇｜磁盘、网络与 envd：其余几样怎么就位

**要回答的问题**：沙箱的根盘、网卡、身份是怎么在恢复时接上的？

- 根盘：模板的 rootfs 经 NBD 变成块设备，上面叠一个写层（COW）；读按映射表取，写只进写层
- NBD 设备数量：上游默认的设备数不够高并发，我们换成 `nbds_max=512` 的内核模块并持久化，以及内核升级会悄悄换回原模块的坑
- 网络槽位：每台沙箱一个网络命名空间、一对 veth、一组 iptables 规则；槽位池预先建好，启动时直接领
- 槽位池的回收：orchestrator 被强杀时整池泄漏；为什么从外面分不清“池里闲着的”和“泄漏的”，只能停服务再清
- envd 的 `/init`：把访问令牌、环境变量交给 guest；MMDS 取身份；恢复后时钟漂移要重新对时

### 第 14 篇｜启动有多慢、慢在哪：埋点与测量

**要回答的问题**：一次启动的时间到底花在哪？客户端感觉到的 600 ms 和服务端日志里的 294 ms 差在哪？

- 三个口径别混：客户端墙钟、准入排队、`ResumeSandbox` 总耗时
- 埋点怎么打：在关键阶段打 `[ResumeSandbox] <阶段> cost` 日志，同一 traceID 归并；报告分组 ≠ 代码结构，并行段要还原
- 100 路并发的结果：总 294.7 ms，拉起 Firecracker 241.6 ms（82%），加载快照 29.1 ms，建进程 15.5 ms，其余合计不到 9 ms
- 关键路径：并行段只算最长那一路，等 uffd 和准备根盘被盖住了

- 一次埋点的坑：普通创建和从暂停恢复走两条不同的排队路径，只给一条打了点，排队时间曾恒为 0
- 可视化：每台沙箱一条甘特，阶段按真实时刻摆放，并行段分泳道

### 第 15 篇｜启动优化：把“拉起 Firecracker”压下来

**要回答的问题**：拉起一个 Firecracker 为什么在高并发下要 240 ms？我们改了什么，哪些试过又放弃了？

- 病因：`ip netns exec` 远不止“进网络命名空间”，它还会再开一个挂载命名空间、遍历整棵挂载树、重挂 `/sys`；这些动作都抢同一把内核全局锁，100 路并发时互相排队
- 解法：一个约 70 行的静态小程序 `fc-netns-exec`，只做 `setns` + `execve` 两件事；在脚本模板里生成而不是字符串替换；模板构建的虚机不走这条路
- 默认开启的代价：小程序不在时 Firecracker 根本起不来，所以要有快速、准确的报错
- 顺带修掉的 bug：等 socket 时用了与调用方无关的上下文，Firecracker 早已死掉还要空等 300 秒，报错还指向“超时”
- 试过又放弃的两档：把整条启动管线重写成 Go / C，子进程侧从 138 ms 压到 29 ms，但父进程侧复制挂载命名空间反被拖到 143 ms，合计倒赔约 31 ms
- 并发参数：同时启动上限 3 → 可配置（30 / 500）、排队超时 15 s → 300 s、网络槽位池 32 / 100 → 300 / 1000、预取并发翻倍、envd `/init` 超时放宽、uffd 等待 10 s → 120 s；怎样用“上限扫描”判断瓶颈是排队还是 CPU
- guest 侧的一处小改：envd 取身份时复用连接，不再每次新建
- 宿主侧：大页池的申请与释放、NUMA 节点编号不连续导致调度器崩溃、沙箱绑核与 NUMA 亲和

**配图**
- 15-1 `ip netns exec` 实际做的六件事，只有一件是需要的
- 15-2 全局锁上的排队：100 个沙箱同时进入挂载命名空间操作

## 第四部分　暂停与恢复：存盘离场，读盘重建

### 第 16 篇｜暂停走一遍：存盘，然后离场

**要回答的问题**：`sandbox.pause()` 之后宿主上依次发生了什么？为什么暂停一定会停掉沙箱？

- 两个 RPC：`Pause`（存盘 + 停沙箱）与 `Checkpoint`（存盘 + 停沙箱 + 从新快照再拉起一个，SDK 里叫 `create_snapshot`）
- 三个 ID：沙箱 ID 不变，执行 ID 不变，Firecracker 进程实例 ID 换新，以及为什么必须换
- 六步：停健康检查 → 暂停 vCPU → 写 snapfile → 取脏页集合 → 导出内存增量 → 导出磁盘增量（这一步关掉沙箱）
- 为什么必须停：摘出写层后不能再有写入，遍历写层时不能有并发写，NBD 设备要释放写层文件才能关
- 等上传完成才返回：元数据不能早于数据标记为就绪
- 暂停在构建里也用：第 7 篇的每一层其实就是一次暂停

- 16-1 Pause 与 Checkpoint：同一段存盘，后面是否再拉起一台
- 16-2 暂停的六步时序：哪一步之后沙箱就回不来了

### 第 17 篇｜增量怎么算出来：脏页、导出与映射表

**要回答的问题**：暂停时怎么知道哪些页、哪些块改过？数据怎么搬出来？暂停为什么改动量为 0 也要约 250 ms？

- 内存的判据（x86 上游）：靠 uffd 写保护位。读缺页填进来的页保持写保护，写过的页保护位被清掉；“驻留且未写保护”就是脏
- 搬运：orchestrator 用 `process_vm_readv` 直接从 Firecracker 进程地址空间读出脏页，写成紧凑差分文件
- 新一代的映射表：写过的块指向本次差分，没写过的指向上一代
- 磁盘：摘出写层，逐块导出；全零块只记一位不写数据；产物紧凑，“存储偏移 ≠ 设备偏移”
- 成本模型：950 上 0 MiB 档 252 ms、256 MiB 档 430 ms，约 246 ms 固定开销 + 每 MiB 约 0.52 ms
- 那 246 ms 去哪了：真正存内存状态只用前约 10 ms，其余是销毁虚机——进程退出、释放挂载命名空间、销毁 KVM 虚机、断开 NBD；还有约 114 ms 未归因，是下一步该查的地方

**配图**
- 17-1 脏页判据：读进来的页保持写保护，写过的页保护被清
- 17-2 内存导出：从 Firecracker 进程地址空间拷出脏页，拼成紧凑文件
- 17-3 磁盘导出：写层里的块 → 紧凑差分 + 映射表
- 17-4 一次 0 MiB 暂停的时间账：10 ms 存状态，其余在拆机

### 第 18 篇｜恢复：在新进程里读盘重建

**要回答的问题**：`Sandbox.connect()` 恢复一台暂停的沙箱，和第三部分的“启动”有什么不同？成本落在哪？

- 恢复就是启动：同一个 `ResumeSandbox`，只是快照换成了暂停时那一代，映射链更长
- 宿主资源全部重建：进程、KVM、设备、网络、NBD、uffd
- 实测：950 上各档都在 100～120 ms，不随改动量变化；时间分布（建进程约 28 ms、加载快照约 21 ms、等 envd 约 35 ms）
- 成本被推迟：恢复后第一次读 192 MiB 负载比快照前多花约 112 ms，由 guest 里第一个访问这些页的程序承担
- 原生快照擅长什么：跨节点迁移、长期保存、进程崩溃后恢复、低频使用；不擅长的是高频回退，那正是快照回滚要解决的
- 恢复后的一个 SDK 修复：`connect()` 没带上沙箱路由头，导致恢复出来的沙箱上无法使用经 proxy 按头路由的服务

**配图**
- 18-1 恢复的结构：和启动同一条路，只是映射链更长
- 18-2 恢复的时间账：建进程、加载快照、等 envd
- 18-3 成本被推迟：恢复很快，第一次访问工作集才慢
- 18-4 原生快照的适用场景：迁移、持久化、崩溃恢复 vs 高频回退

### 第 19 篇｜ARM 上的退化：读过就算脏

**要回答的问题**：为什么 ARM 上什么都没改，一次暂停也要导出一百多 MiB？

- ARM 适配时的一处改动：arm64 的 6.6 内核没有 uffd 写保护，填页时带写保护的那几行被注释掉
- 后果链：写保护位恒为 0 → 判据塌缩成“驻留即脏” → 读进来的页全算脏
- 叠加的放大：每一代都是新进程，guest 一跑就要把工作集重新缺页换入 → 每代增量的下限约等于工作集
- 实测：连拍三次，中间什么都不做也是 112 MiB；950 上改 12 MiB 导出 148 MiB，只读 192 MiB 导出 324 MiB；预取会被直接算进增量
- 为什么不影响正确性：驻留是写过的超集，只会多导，不会少导；磁盘侧走写层，仍然精确
- 正确的位图其实就在旁边：Firecracker 的写跟踪位图同期只有 4.6 / 15 / 19.7 MiB

**配图**
- 19-1 判据塌缩：写保护位恒为 0，驻留即脏
- 19-2 两个放大叠加：新进程换入工作集 × 换入即脏
- 19-3 三列对比：原判据、写跟踪位图、实际导出

### 第 20 篇｜精确增量：判、存、填三层一起改

**要回答的问题**：把判据换成写跟踪位图就够了吗？为什么还要动存储和缺页？怎样做到导出精确而恢复不变慢？

- 内存增量的三层：**判**（哪些页要导出）、**存**（映射表的块大小）、**填**（缺页一次填多大）；三层的粒度被 2 MiB 大页锁在一起
- 只换判据的地板：4 MiB 的散写落在 67 个不同的 2 MiB 块里，归并后仍是 134 MiB
- 先立规矩：**宁可多导，不可少导**。少导一页，pause 报成功，resume 后 guest 内核崩溃
- 两条路线：关大页（缺页次数 ×512，所有沙箱失去大页）vs 保留大页、4 KiB 存、2 MiB 拼。选后者
- 三层的改法：判——换成写跟踪位图；存——映射表块大小降到 4 KiB，父代映射原样保留；填——一次 2 MiB 缺页，三级取源（整块同代零拷贝、跨代才拼、拼用缓冲池）
- 恢复开销的来回：第一版每次缺页分配 2 MiB，恢复后首次触碰慢了约 120 ms；零拷贝快路径和缓冲池把它收回到修复前水平
- 退路：跟踪没开、位图不可信、Firecracker 没有导出接口时，回到“驻留即脏”；每次暂停在日志里说清导了多少、凭什么导
- 修复后（920B）：只读 192 MiB 的导出从 358 MiB 降到 12.7 MiB，只改 12 MiB 从 176 MiB 降到 20.3 MiB，导出量等于写跟踪位图，逐行相等

**配图**

- 20-2 只换判据的地板：散写落进几十个大块
- 20-3 两条路线对比：关大页 vs 4 KiB 存、2 MiB 拼
- 20-4 三级取源：同块、同代零拷贝、跨代拼接

## 第五部分　和快照回滚共存：哪些地方被撞到，怎么修好

### 第 21 篇｜快照回滚动了哪些共用部件

**要回答的问题**：我们新增的快照回滚和暂停恢复是两套机制，为什么还会互相影响？加了回滚之后，普通的启动和暂停多付了什么？

- 两种快照的分工一句话：回滚是活沙箱里的高频原地读档，暂停恢复是沙箱离场与重建；谁也替代不了谁（只讲结论，机制见回滚那本书）
- 共用的部件：Firecracker（带回滚扩展）、虚机启动时的配置、写层、脏页位图、proxy、网络槽位
- 启动时多了什么：加载快照时就打开脏页跟踪；关闭 SMT；每个网络槽位多开一个 conntrack 句柄；proxy 拦截一个专用端口
- 脏页跟踪的运行期代价：没有硬件跟踪的机器上，每个干净页第一次被写都要陷出一次；所以默认值跟着硬件走（950 有 HDBSS 就开，920B 默认关）
- 磁盘写层从“一层”变成“一叠”：读要穿过多层，所以回滚那边要折叠层、限制层数，普通读路径才不会越来越慢

### 第 22 篇｜三处被撞坏的地方和修法

**要回答的问题**：回滚加进来以后，暂停恢复具体出过哪些问题？为什么这些问题都是“静默”的？最后怎么修、怎么证明修好了？

- **磁盘：做过 checkpoint 的沙箱一暂停，封存层就丢了**
  - 原因：checkpoint 把写层封存、另开新写层；原生暂停只导出当前写层，更早的写全回到模板，做过 restore 的几乎什么都不剩
  - 为什么静默：映射表从导出内容推出来，自己跟自己对得上；已有测试不做暂停；第一版验证写小文件被 guest 页缓存盖住，假通过
  - 修法：暂停时把整叠层按读的顺序压平再导出；从没 checkpoint 过的沙箱走原来的单层导出，逐字节不变
  - 证据：在 checkpoint 前后各写一大份随机数据，暂停恢复后用 `O_DIRECT` 绕开页缓存读回比哈希；修复前 3/3 损坏，修复后全过
- **内存：脏页位图被回滚清零，暂停少导了页**
  - 原因：精确增量依赖“位图 = 这一代启动以来写过的页”；可 checkpoint 和 restore 都会清零位图，restore 写回内存还不进任何日志
  - 后果：pause 报成功，resume 后 guest 内核几十毫秒内崩溃
  - 修法：在每次清零之前，把即将被忘掉的位图并进一个每台虚机的“自启动以来脏页集”；暂停时并回再导出；全量 checkpoint 的“全 1”侧车不能并，改为拍之前先导一次活跃位图；对不上就标“不可信”、退回驻留判据
  - 从不 checkpoint 的沙箱完全不受影响
- **SDK：恢复出来的沙箱用不了回滚**
  - `connect()` 只带访问令牌，没带沙箱路由头，proxy 无法按头路由；envd 不受影响（它的地址里带沙箱 ID），所以没人发现
- 共同的教训：两个各自正确的机制叠加时，要重新检查每一个前提；测试要专门走“组合”，读回要绕开缓存
