# 第 14 篇｜沙箱里的 DNS

> **本篇目标**：讲清楚沙箱这一侧的 DNS。读完本篇，你会知道：沙箱的 `/etc/resolv.conf` 是怎么来的、为什么写的是 `8.8.8.8`；一次 DNS 查询从沙箱出发要走哪条路；宿主机上明明有 dnsmasq，沙箱为什么用不了；宿主机出不了外网时沙箱的 DNS 会怎样、该改哪里；以及 DNS 和“按域名过滤”之间的微妙关系。

---

## 一、沙箱的 resolv.conf 从哪来

### 1.1 模板构建时写进去的

第 5 篇讲过，Linux 程序查 DNS 时读 `/etc/resolv.conf`。沙箱里的这个文件，是**构建模板时**由 orchestrator 写进根文件系统的。它用一个很短的模板文件生成：

```
nameserver {{ .Nameserver }}
```

而 `Nameserver` 取的是代码里的一个常量：

```go
const DefaultNameserver = "8.8.8.8"
```

所以每个沙箱里的 `/etc/resolv.conf` 都是：

```
nameserver 8.8.8.8
```

同一批写入的还有 `/etc/hosts`，内容是常规的几行：`127.0.0.1 localhost`、IPv6 的几个本地名字，以及 `127.0.1.1 <主机名>`。

### 1.2 构建时临时“锁住”它

构建模板时，要在根文件系统里安装各种软件包。有些软件包（比如 systemd-resolved、resolvconf）一装上就会改写 `/etc/resolv.conf`，把它指向自己。

为了防止这种情况，模板构建的初始化脚本 `provision.sh` 在开头执行：

```bash
chattr +i /etc/resolv.conf     # 设为不可修改（immutable）
```

`chattr +i` 给文件加上“不可变”属性：即使是 root 也无法修改、删除或重命名它。等所有软件装完，脚本结尾再执行 `chattr -i` 解除锁定。

所以，构建过程中 `resolv.conf` 始终保持 `nameserver 8.8.8.8`。不过解锁之后，如果模板里有服务在**运行时**又改写了它，沙箱的 DNS 也会跟着变。遇到“沙箱 DNS 不对”的问题，第一步就是进沙箱看看这个文件现在的内容。

### 1.3 不是从内核参数来的

第 9 篇提过，内核启动参数 `ip=` 的第 8 段本来是 DNS 服务器的位置，但代码里填的是 `tap0`，不是有效地址。沙箱实际使用的 DNS 完全由 `/etc/resolv.conf` 决定。

## 二、一次 DNS 查询的路径

沙箱里执行 `pip install pandas`，第一步是解析 `pypi.org`。路径就是第 13 篇的“旅程一”：

```
沙箱里的 pip
   │ 读 /etc/resolv.conf → 问 8.8.8.8
   ▼
UDP 包：169.254.0.21:随机端口 → 8.8.8.8:53
   │
   ▼ tap0 进入命名空间
nftables：
   规则 3：8.8.8.8 不在预置拦截集合里     → 不匹配
   规则 4/5：只看用户集合（默认空）         → 不匹配
   默认：放行
   │
   ▼ 命名空间 SNAT：169.254.0.21 → 10.13.0.5
   ▼ veth → 宿主机
宿主机：UDP 不匹配任何 REDIRECT → FORWARD 放行 → MASQUERADE → 物理网卡
   │
   ▼
8.8.8.8 回答 pypi.org 的 IP → 原路返回
```

要点：

- DNS 查询是 **UDP**，不经过 TCP 防火墙代理，只受命名空间里 nftables 的检查。
- 它最终是**从宿主机的物理网卡、用宿主机的地址**发出去的。所以沙箱的 DNS 能不能用，取决于**宿主机能不能直接访问到 `8.8.8.8:53`**。

## 三、沙箱为什么用不了宿主机的 dnsmasq

宿主机上有一个 dnsmasq（第 17 篇），能解析一切。为什么不让沙箱也用它？我们试着让沙箱去找它，看看每条路为什么都走不通：

| 尝试 | 结果 | 原因 |
|---|---|---|
| `nameserver 127.0.0.1` | 不通 | 沙箱里的 `127.0.0.1` 是沙箱自己（第 2 篇），沙箱里没有 DNS 服务 |
| `nameserver 10.14.0.10`（宿主机侧 veth 地址） | 被拦 | 在 `10.0.0.0/8` 里，命名空间防火墙直接丢弃 |
| `nameserver 192.168.10.23`（宿主机物理网卡地址） | 被拦 | 在 `192.168.0.0/16` 里，同样被丢弃 |
| `nameserver 192.0.2.1`（“orchestrator 地址”） | 不通 | 防火墙放行它，但宿主机只为它的 TCP 80/111/2049 端口准备了改道（第 19 篇），没有 DNS |

而且，即使能连上，宿主机的 dnsmasq 也不适合给沙箱用：它会把 `*.e2b.app` 解析成 `127.0.0.1`、把 `*.consul` 转给内部的 Consul，这些都是给宿主机自己用的“内部答案”，不应该暴露给不可信的沙箱。

所以，沙箱和宿主机的 DNS 被刻意设计成**两套互不相干的系统**：宿主机用自己的 dnsmasq，沙箱直接用公网 DNS。

## 四、宿主机出不了外网时会怎样

### 4.1 一个现实的场景

很多私有化部署的服务器并不能直接访问互联网：

- 可能只能通过一个 HTTP 代理上网（配了 `http_proxy`）。
- 可能有内网 DNS，但访问不到 `8.8.8.8`。

这套环境的部署脚本里就有这样的注释：“有的机器上 `/etc/resolv.conf` 根本不存在……上外网走 `http_proxy`”。

在这种机器上，沙箱的 DNS 查询从宿主机物理网卡发往 `8.8.8.8:53`，石沉大海。沙箱里的程序要等 DNS 超时（每次默认 5 秒，还会重试），最后报“解析不了域名”。`pip install`、`curl` 统统失败。

### 4.2 能不能改成内网 DNS

自然的想法是把沙箱的 nameserver 改成内网的 DNS 服务器，比如 `10.0.0.53`。可惜**不行**：

- 内网 DNS 的地址几乎一定是私有地址。
- 命名空间防火墙的规则 3 会无条件丢弃发往私有地址的包，而且它排在用户放行规则（规则 4）**之前**。也就是说，**用户配置的 `allowOut` 也救不了它**（第 15 篇详讲这个顺序）。

沙箱能用的 DNS 服务器，必须是一个**公网地址**，并且宿主机能直接访问到它。

### 4.3 如果要改，改哪里

如果确实需要换一个 DNS 服务器（公网地址），有两条路：

1. **改代码里的默认值**（`DefaultNameserver`），重新编译、重新打 RPM，并**重新构建所有模板**。因为 resolv.conf 是在构建模板时写进去的，已经构建好的模板不会变。
2. **在模板的启动命令或 Dockerfile 里自己写入 `/etc/resolv.conf`**。这样只影响这一个模板。

还要注意一个连带影响，见下一节：用户配置了“按域名放行”时，API 会自动放行 `8.8.8.8`，但不会放行你换上去的那个地址。

## 五、DNS 与“按域名过滤”

### 5.1 API 自动放行 8.8.8.8

用户可以配置“只允许访问某些域名”（第 15、16 篇），比如：

```json
{
  "allowOut": ["pypi.org", "files.pythonhosted.org"],
  "denyOut": ["0.0.0.0/0"]
}
```

意思是“拒绝一切，只放行这两个域名”。可是，`denyOut: 0.0.0.0/0` 会把发往 `8.8.8.8` 的 DNS 查询也拦掉。DNS 都查不了，沙箱根本不知道 `pypi.org` 的 IP，连发起连接的机会都没有。

所以 api 服务在把配置传给 orchestrator 之前，做了一件贴心的事：**只要 `allowOut` 里有域名，就自动把 `8.8.8.8` 加进放行的地址列表**。代码注释写得很直白：

```go
// If allowed domain is provided, add the default nameserver to the allowed addresses
// This is to ensure that the sandbox can resolve the domain name to the IP address
if len(allowedDomains) > 0 {
    allowedAddresses = append(allowedAddresses, sandbox_network.DefaultNameserver)
}
```

这也是为什么第 4.3 节说：如果你把沙箱的 DNS 换成了别的地址，在“按域名放行”的场景下，要自己把那个地址也加进 `allowOut`。

### 5.2 沙箱可以对 DNS 撒谎，但没用

沙箱是不可信的。它完全可以：

- 修改自己的 `/etc/hosts`，写一行 `10.0.0.5 pypi.org`。
- 换一个 DNS 服务器，让它对 `pypi.org` 返回一个内网地址。

然后去连接“`pypi.org`”（实际上是内网地址），企图借着“`pypi.org` 在放行名单里”的名义访问内网。

E2B 对此早有防备，第 16 篇会详细讲。简单说两点：

1. 沙箱发往内网地址的包，在命名空间防火墙就被丢弃了，不管它打着什么域名的旗号。
2. TCP 防火墙代理按域名放行一个连接后，**不用沙箱解析出来的 IP**，而是在宿主机上**自己重新解析**这个域名，并检查解析结果是不是内网地址。

所以，沙箱的 DNS 只决定“沙箱自己以为对方是谁”，不决定“流量最终能去哪”。

### 5.3 UDP 是一个缺口

TCP 流量有代理把关，可以按域名过滤。但 DNS 查询本身是 UDP，只经过 nftables 按 IP 过滤。在默认配置下（没有 `denyOut`），沙箱可以向**任何公网地址**发送 UDP 包，包括任意的 DNS 服务器。

这意味着，在默认配置下，沙箱可以通过 DNS 查询或其他 UDP 协议，把数据带出去。如果你需要严格的出站控制，应该配置 `denyOut: ["0.0.0.0/0"]`，再按需放行（第 15 篇）。第 22 篇的安全回顾还会提到这一点。

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 沙箱 resolv.conf | 构建模板时写入，`nameserver 8.8.8.8`，来自代码常量 `DefaultNameserver` |
| `chattr +i` | 构建期间锁住 resolv.conf，防止安装软件时被改写，结束时解锁 |
| 不靠 `ip=` 参数 | 内核参数里的 DNS 位置填的是 `tap0`，无效；实际以 resolv.conf 为准 |
| 查询路径 | UDP 53 → nftables → 两次 NAT → 宿主机物理网卡 → 8.8.8.8 |
| 用不了宿主 dnsmasq | 127.0.0.1 是沙箱自己，宿主地址被防火墙拦，192.0.2.1 不提供 DNS |
| 宿主出不了外网 | 沙箱 DNS 超时，所有依赖域名的操作失败 |
| 不能用内网 DNS | 私有地址被防火墙规则 3 无条件丢弃，`allowOut` 也救不了 |
| 改 DNS | 改代码常量并重建模板，或在模板里自行写入；必须是公网地址 |
| 自动放行 8.8.8.8 | `allowOut` 含域名时，api 自动把 `8.8.8.8` 加入放行列表 |
| DNS 撒谎无效 | 命名空间防火墙拦内网地址，TCP 代理在宿主机重新解析域名 |
| UDP 缺口 | 默认配置下沙箱可向任意公网地址发 UDP，需要严格控制时用 `denyOut` |
