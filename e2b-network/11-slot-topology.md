# 第 11 篇｜一个槽位的拓扑：几块网卡、几个地址

> **本篇目标**：把一个网络槽位“拆开”来看。读完本篇，你会知道：一个槽位里有哪几块网卡、几个地址、几条路由；怎么从槽位编号一步步算出它的所有地址；单台机器最多能有多少个槽位；E2B 为什么用“路由 + 点对点”而不是网桥；以及这套环境为什么把地址池改成了 `10.13/10.14`、把网卡名改成了 `e2bv-`。

---

## 一、一个槽位里有什么

以编号为 5 的槽位为例。它由以下几样东西组成：

| 组件 | 名字 | 在哪 | 地址 |
|---|---|---|---|
| 网络命名空间 | `ns-5` | 挂在 `/var/run/netns/ns-5` | — |
| 客户机网卡 | `eth0`（客户机内部） | Firecracker 虚拟机里 | `169.254.0.21/30` |
| tap 设备 | `tap0` | `ns-5` 里 | `169.254.0.22/30` |
| veth 的命名空间一头（vpeer） | `eth0` | `ns-5` 里 | `10.14.0.11/31` |
| veth 的宿主机一头 | `e2bv-5` | 宿主机 | `10.14.0.10/31` |
| Host IP | — | 宿主机路由表里的一条 `/32` 路由 | `10.13.0.5` |

注意两个容易混淆的地方：

1. **有两个 `eth0`**：一个在客户机里面（virtio-net 网卡），一个在命名空间里（veth 的一头）。它们不是同一个东西，只是恰好重名。本书说“客户机的 `eth0`”和“vpeer”来区分。
2. **Host IP 不在任何一块网卡上**。它只是一个“门牌号”：宿主机的路由表知道“去这个门牌，从 `e2bv-5` 走”；命名空间的 NAT 规则知道“这个门牌的住户是 `169.254.0.21`”。

## 二、完整拓扑图

```
┌────────────────────────────── 宿主机（初始命名空间）──────────────────────────────┐
│                                                                                │
│   物理网卡 enp125s0f0（例如 192.168.10.23）◄── 默认路由 ──► 互联网                │
│                                                                                │
│   路由：10.13.0.5 via 10.14.0.11 dev e2bv-5      ← 去往 Host IP 走这里            │
│   路由：10.14.0.10/31 dev e2bv-5                  ← 直连                         │
│                                                                                │
│   e2bv-5  10.14.0.10/31                                                        │
│      ║                                                                         │
└──────╫─────────────────────────────────────────────────────────────────────────┘
       ║ veth 对（一根虚拟网线）
┌──────╫──────────────────── 网络命名空间 ns-5 ─────────────────────────────────────┐
│      ║                                                                         │
│   eth0 (vpeer)  10.14.0.11/31                                                  │
│                                                                                │
│   路由：default via 10.14.0.10 dev eth0          ← 出去的包交给宿主机             │
│   路由：10.14.0.10/31 dev eth0                    ← 直连                         │
│   路由：169.254.0.20/30 dev tap0                  ← 直连，客户机在这边             │
│                                                                                │
│   iptables nat：                                                                │
│     出：-o eth0 -s 169.254.0.21 → SNAT 成 10.13.0.5                             │
│     入：-i eth0 -d 10.13.0.5    → DNAT 成 169.254.0.21                          │
│   nftables：表 slot-firewall（出站过滤）                                         │
│                                                                                │
│   tap0  169.254.0.22/30                                                        │
│      ║  （Firecracker 进程打开它，也运行在 ns-5 里）                              │
│      ║                                                                         │
│   ┌──╨──────── Firecracker 虚拟机 ───────────┐                                   │
│   │  客户机 eth0  169.254.0.21/30            │                                   │
│   │  默认网关 169.254.0.22                   │                                   │
│   └──────────────────────────────────────────┘                                   │
└────────────────────────────────────────────────────────────────────────────────┘
```

这张图包含了一个槽位的全部“硬件”和“规则”。宿主机上还有几条和这个槽位相关的 iptables 规则（转发放行、MASQUERADE、几条 REDIRECT），第 12 篇按建网顺序逐条列出。

### 2.1 三段“网线”

从客户机到物理网卡，一共经过三段：

1. **客户机 `eth0` ↔ `tap0`**：`169.254.0.20/30` 网段。由 Firecracker 搬运数据。
2. **vpeer ↔ `e2bv-5`**：`10.14.0.10/31` 网段。veth 对直接相连。
3. **宿主机 ↔ 外网**：宿主机的物理网卡。

命名空间夹在第 1 段和第 2 段中间，充当一台小路由器：从 `tap0` 进来的包转到 `eth0` 出去，反之亦然（这就是第 3 篇说命名空间需要 `ip_forward=1` 的原因）。

### 2.2 两组路由，各管一个方向

- **命名空间里的默认路由**（`default via 10.14.0.10`）：客户机发往任何外部地址的包，命名空间都交给宿主机那头的 veth。
- **宿主机上的 `/32` 路由**（`10.13.0.5 via 10.14.0.11`）：宿主机上谁要访问这个沙箱的 Host IP，就把包交给命名空间那头的 veth。

有了这两条，宿主机和命名空间之间双向都通了。

## 三、从槽位编号算出所有地址

### 3.1 两个地址池

一个槽位用到的“可变地址”来自两个地址池：

| 地址池 | 上游默认 | 这套环境 | 用途 | 每个槽位占 |
|---|---|---|---|---|
| Host 池 | `10.11.0.0/16` | `10.13.0.0/16` | 每个沙箱的 Host IP | 1 个地址（`/32`） |
| VRT 池 | `10.12.0.0/16` | `10.14.0.0/16` | veth 对的两头 | 2 个地址（`/31`） |

两个地址池分别由环境变量 `SANDBOXES_HOST_NETWORK_CIDR` 和 `SANDBOXES_VRT_NETWORK_CIDR` 配置。

### 3.2 计算规则

orchestrator 的计算规则非常简单，就是第 2 篇练过的“取第 N 个地址”：

```go
// 简化示意：由槽位编号 idx 算出地址
vethIP  := 第N个地址(VRT池, idx*2)     // 宿主机那头
vpeerIP := 第N个地址(VRT池, idx*2 + 1) // 命名空间那头
hostIP  := 第N个地址(Host池, idx)      // Host IP
```

### 3.3 算一遍：编号 5

- `vethIP` = `10.14.0.0` + 5×2 = **`10.14.0.10`**
- `vpeerIP` = `10.14.0.0` + 5×2+1 = **`10.14.0.11`**
- 这两个地址组成 `/31` 网段 `10.14.0.10/31`
- `hostIP` = `10.13.0.0` + 5 = **`10.13.0.5`**

### 3.4 再算一遍：编号 300

- `vethIP` = `10.14.0.0` + 600。600 = 2×256 + 88，所以是 **`10.14.2.88`**
- `vpeerIP` = **`10.14.2.89`**
- `hostIP` = `10.13.0.0` + 300。300 = 1×256 + 44，所以是 **`10.13.1.44`**

### 3.5 地址可以反推编号

反过来，看到一个地址，也能推出它属于哪个槽位：

- Host IP `10.13.1.44` → 编号 300。
- `e2bv-300` → 编号 300。

这对排障很方便：在宿主机的 conntrack 表或日志里看到 `10.13.1.44`，就知道该去看 `ns-300`。这套环境的清理脚本也是靠这个规律识别“哪些 iptables 规则属于哪个槽位”的（第 21 篇）。

## 四、一台机器最多多少个槽位

### 4.1 由 VRT 池决定

每个槽位占 VRT 池里的 2 个地址。一个 `/16` 有 65536 个地址，所以最多 32768 块，代码再减去 2 留出余量，得到 **32766** 个槽位。orchestrator 启动时会在日志里打印这个数：

```
Using network slot size: 32766
```

Host 池每个槽位只占 1 个地址，同样是 `/16` 的话完全够用。

### 4.2 编号从 2 开始

这套环境的槽位编号是**从 2 开始**的。代码在分配编号时跳过了 1，注释说编号 1 留给“宿主机槽位”。所以你在宿主机上看到的命名空间是 `ns-2`、`ns-3`……没有 `ns-1`。

### 4.3 实际上限远小于这个数

32766 只是地址上的上限。实际能同时跑多少沙箱，受内存、CPU 等资源限制，远远到不了这个数。这套环境的网络池默认最多**预建** 300 个新槽位（第 20 篇），已经足够。

## 五、为什么是“路由 + 点对点”，而不是网桥

第 6 篇介绍过两种连接方式。E2B 选择了每个沙箱一对专属 veth、宿主机用路由表区分的方式，原因有三：

1. **网桥行不通。** 所有命名空间里的 vpeer 地址各不相同，接网桥本来可以。但命名空间里还藏着相同的 `169.254.0.21`；而且网桥意味着所有命名空间处在同一个二层网络里，可以互发 ARP、互相访问，还得另加隔离规则。
2. **点对点天然隔离。** 每个命名空间只和宿主机直连，彼此之间没有任何二层通路。命名空间 A 想访问命名空间 B，包只能先到宿主机，由宿主机决定转不转。而第 15 篇会讲到，命名空间里的防火墙从源头上就禁止了访问 `10.0.0.0/8`，包根本出不了 A。
3. **规则简单。** 每个槽位的规则都只涉及它自己的网卡名（`e2bv-5`）和地址（`10.13.0.5`），彼此独立，增删一个槽位不影响别人。

代价是宿主机上网卡和路由的**数量**多：每个槽位一块 veth、一条 `/32` 路由。几百个槽位就是几百块网卡。对 Linux 来说这不算什么，但运维时需要知道这一点（第 21 篇）。

## 六、这套环境的两处改动

### 6.1 地址池：从 10.11/10.12 改成 10.13/10.14

这套机器上还部署了另一个沙箱系统 **AgentENV**。巧的是，它的网络设计和 E2B 几乎一模一样，连默认地址池都是 `10.11.0.0/16` 和 `10.12.0.0/16`。两边同机运行时：

- 两边都会往宿主机路由表里加 `10.11.x.y/32` 这样的路由。内核不允许同一条路由出现两次，后建的一方直接报错 `File exists`。
- veth 地址也会重叠。

所以这套环境在 `.env` 里把 E2B 的地址池改到了 `10.13.0.0/16` 和 `10.14.0.0/16`，和 AgentENV 彻底分开。`.env` 里的注释写得很清楚：

```bash
# 沙箱网络地址池。上游默认 10.11.0.0/16（宿主机访问沙箱用）和 10.12.0.0/16（veth 对），
# 与同机部署的 AgentENV 默认值完全相同，同机会撞地址和路由，所以改用 10.13/10.14。
# 两段不能互相重叠，也不能与本机/内网在用的网段重叠；VRT 段的大小决定单机槽位上限
export SANDBOXES_HOST_NETWORK_CIDR=10.13.0.0/16
export SANDBOXES_VRT_NETWORK_CIDR=10.14.0.0/16
```

选地址池的三条规矩：

1. 两段不能互相重叠。
2. 不能和本机或内网正在用的网段重叠。否则宿主机去访问内网里真正的 `10.13.x.x` 时，会被路由到某个沙箱。
3. VRT 段的大小决定槽位上限。

### 6.2 网卡名：从 `veth-` 改成 `e2bv-`

同样因为 AgentENV：它的宿主机侧网卡也叫 `veth-<编号>`，编号也从小往大排，同名网卡直接冲突。更麻烦的是，AgentENV 会在宿主机上安装匹配 `veth-+`（即所有以 `veth-` 开头的网卡）的 iptables 规则，其中一条会**拒绝**来自这些网卡、发往宿主机的流量。E2B 沙箱的出站 TCP 要先交给宿主机上的防火墙代理（第 16 篇），正好被这条规则拒掉。

ARM 适配补丁因此把 E2B 的宿主机侧网卡名改成了 `e2bv-<编号>`：

```go
// VethName uses its own prefix rather than upstream's "veth-": other sandbox
// runtimes on the same host (AgentENV) name their host-side interfaces
// veth-<n> and install iptables rules matching "veth-+".
func (s *Slot) VethName() string {
    return fmt.Sprintf("e2bv-%d", s.Idx)
}
```

这一改，AgentENV 的 `veth-+` 规则就匹配不到 E2B 的网卡了。部署脚本的清理逻辑也相应地只认 `e2bv-` 开头的网卡（第 21 篇）。

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 槽位组成 | 命名空间、`tap0`、veth 对（vpeer + `e2bv-N`）、Host IP、路由和规则 |
| 两个 `eth0` | 客户机里的 virtio 网卡，和命名空间里的 vpeer，只是重名 |
| Host IP | 不在任何网卡上，只是路由和 NAT 规则里的“门牌号” |
| 三段网线 | 客户机↔tap0（`/30`），vpeer↔`e2bv-N`（`/31`），宿主机↔外网 |
| 命名空间的默认路由 | `default via` 宿主机那头的 veth |
| 宿主机的 `/32` 路由 | `Host IP via` 命名空间那头的 veth |
| 地址计算 | veth = VRT 池第 2N 个，vpeer = 第 2N+1 个，Host IP = Host 池第 N 个 |
| 槽位上限 | VRT 池 `/16` → 32766 个；编号从 2 开始 |
| 路由而非网桥 | 点对点天然隔离，规则只涉及自己，代价是网卡和路由数量多 |
| 这套环境的地址池 | `10.13.0.0/16`（Host）和 `10.14.0.0/16`（VRT），避开 AgentENV |
| 这套环境的网卡名 | `e2bv-<编号>`，避开 AgentENV 的 `veth-+` 规则 |
