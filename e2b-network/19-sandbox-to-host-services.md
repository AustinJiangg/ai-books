# 第 19 篇｜沙箱访问宿主服务：192.0.2.1 背后的 hyperloop、NFS 与 portmap

> **本篇目标**：讲最后一个方向：沙箱主动访问宿主机上的服务。宿主机的地址对沙箱是禁区，E2B 是怎么开出几个“小口子”的？读完本篇，你会知道：为什么选了一个“文档专用”的地址 `192.0.2.1`；沙箱是怎么知道这个地址的；三条 REDIRECT 规则分别通向哪个服务；宿主机上的服务怎么知道请求来自哪个沙箱；最后，我们把全书出现过的所有地址转换汇总成一张总表。

---

## 一、问题：要开口子，又不能开大门

沙箱有时确实需要和宿主机上的服务打交道：

- **查询自己的信息**：我是哪个沙箱？
- **上报日志和事件**：沙箱里发生了什么，要让宿主机知道。
- **挂载持久化存储卷**：用户希望某些数据在沙箱销毁后还保留，这些数据通过 NFS 由宿主机提供。

但第 15 篇的防火墙会丢弃发往一切私有地址的包：宿主机的物理网卡地址、veth 地址都在其中。这是保护宿主机的底线，不能为了这几个服务就放开。

怎么办？E2B 的做法是：

1. 约定一个**特殊地址**，作为沙箱眼中的“宿主机服务地址”。
2. 防火墙**只放行**这一个地址。
3. 发往这个地址的包，在宿主机门口按端口**改道**到对应的服务。

这样，沙箱能访问的只有那几个特定的端口，其他一切仍被挡在外面。

---

## 二、为什么是 192.0.2.1

### 2.1 一个“不存在”的地址

这个特殊地址默认是 **`192.0.2.1`**，由 orchestrator 的环境变量 `SANDBOX_ORCHESTRATOR_IP` 配置。代码里叫它“沙箱里的 orchestrator 地址”（OrchestratorInSandboxIPAddress）。

第 2 篇讲过，`192.0.2.0/24` 是 RFC 5737 规定的**文档专用地址**，保证不会分配给任何真实设备。选它有几个好处：

- **不会和真实网络冲突。** 如果选一个普通的公网或私有地址，万一某天沙箱真的需要访问那个地址上的真实服务，就会被错误地截走。
- **不在预置拦截列表里。** `192.0.2.1` 不属于 10/8、172.16/12、192.168/16 等任何一段，放行它不需要在拦截规则上开例外。
- **它只是一个“暗号”。** 宿主机上没有任何网卡配这个地址。它的全部意义，就是让宿主机上的 REDIRECT 规则能认出“这是沙箱在找宿主服务”。

### 2.2 防火墙放行它

第 15 篇的预置放行集合里只有一个元素：`192.0.2.1/32`。规则 2 放行所有发往它的包，并且排在“预置拦截”和所有用户规则之前。所以即使沙箱配置了“完全断网”（`allow_internet_access=false`），访问 `192.0.2.1` 依然畅通。

### 2.3 沙箱怎么知道这个地址

沙箱是从快照恢复的，它怎么知道 `192.0.2.1`？靠 orchestrator 在沙箱启动时告诉它。

第 1 篇提过，沙箱恢复后，orchestrator 会调用 envd 的 `/init` 接口，传入一些初始化信息。其中就有一个字段 `hyperloopIP`，值就是 `192.0.2.1`。envd 收到后做两件事：

1. 在客户机的 `/etc/hosts` 里写一行：`192.0.2.1 events.e2b.local`。
2. 设置环境变量 `E2B_EVENTS_ADDRESS=http://events.e2b.local`。

沙箱里的程序于是可以用 `events.e2b.local` 这个名字访问宿主机服务，不用记 IP。

## 三、三条 REDIRECT

第 12 篇建网的第 10 步，为每个槽位在宿主机上加了三条规则（以槽位 5 为例）：

```bash
iptables -t nat -A PREROUTING -i e2bv-5 -p tcp -d 192.0.2.1 --dport 80   -j REDIRECT --to-port 5010
iptables -t nat -A PREROUTING -i e2bv-5 -p tcp -d 192.0.2.1 --dport 111  -j REDIRECT --to-port 5012
iptables -t nat -A PREROUTING -i e2bv-5 -p tcp -d 192.0.2.1 --dport 2049 -j REDIRECT --to-port 5011
```

| 沙箱访问 | 改送本机端口 | 服务 | 端口的环境变量 |
|---|---|---|---|
| `192.0.2.1:80` | 5010 | hyperloop | `SANDBOX_HYPERLOOP_PROXY_PORT` |
| `192.0.2.1:111` | 5012 | portmap | `SANDBOX_PORTMAPPER_PORT` |
| `192.0.2.1:2049` | 5011 | NFS 代理 | `SANDBOX_NFS_PROXY_PORT` |

三个服务都运行在 orchestrator 进程里。

### 3.1 一个包的路线

以沙箱访问 `http://events.e2b.local/me` 为例：

```
客户机：events.e2b.local → /etc/hosts → 192.0.2.1
   │  TCP 169.254.0.21:随机端口 → 192.0.2.1:80
   ▼
tap0 → 命名空间
   │  nftables 规则 2：目的地在预置放行集合 → 放行
   │  SNAT：169.254.0.21 → 10.13.0.5
   ▼
e2bv-5 → 宿主机 PREROUTING
   │  命中：-i e2bv-5 -d 192.0.2.1 --dport 80 → REDIRECT 到 5010
   ▼
INPUT → orchestrator 里的 hyperloop 服务（:5010）
```

### 3.2 规则顺序：为什么不会被防火墙代理截走

细心的读者会发现：发往 `192.0.2.1:80` 的包，同样满足第 16 篇那条“所有 80 端口 TCP → 5016”的规则。它为什么去了 hyperloop，而不是 TCP 防火墙代理？

答案是**顺序**。建网时，三条“宿主服务”规则先加，三条“防火墙代理”规则后加。规则从上往下匹配、命中即停，`192.0.2.1:80` 先命中了 hyperloop 规则。

顺序在这里至关重要。第 17 篇讲过一个真实的事故：那条不带 `--dst-type LOCAL` 的全局“80 → 3002”规则在部署时就加上了，**排在所有槽位规则前面**，于是沙箱访问 hyperloop 的请求全被它截到了 client-proxy。

### 3.3 只有 TCP

三条规则都带 `-p tcp`。如果沙箱向 `192.0.2.1` 发 UDP 包，或者访问其他端口，防火墙虽然放行，但宿主机上没有对应的改道规则。包会按路由表去找 `192.0.2.1` 这个“不存在”的地址，最终无果。所以沙箱能用的宿主服务，**严格限于这三个 TCP 端口**。

## 四、三个服务各做什么

### 4.1 hyperloop：沙箱和宿主机之间的小信道

hyperloop 是一个很小的 HTTP 服务，提供两个接口：

- `GET /me`：回答“你是哪个沙箱”。
- `POST /logs`：接收沙箱上报的日志，转发给日志收集服务。

它怎么知道请求来自哪个沙箱？和 TCP 防火墙代理一样：**看连接的源地址**。请求经过命名空间的 SNAT，源地址是这个沙箱的 Host IP（如 `10.13.0.5`），hyperloop 拿着它在本机的沙箱列表里一查就知道了。

接收日志时，hyperloop 还会用查到的结果**覆盖**日志里的沙箱 ID 和团队 ID。代码注释说这是“为了防止伪造”：沙箱可以在日志里随便写“我是沙箱 X”，但它没法伪造自己的源地址。源地址是在命名空间里由 SNAT 改写的，沙箱碰不到。

这又是“出口换门牌”的一个用处：**Host IP 成了沙箱不可伪造的身份凭证**。

### 4.2 NFS 代理和 portmap：挂载持久卷

E2B 支持给沙箱挂载**持久卷**：一块独立于沙箱生命周期的存储，沙箱销毁后数据仍然保留。它通过 NFS（网络文件系统）协议提供给沙箱：

- 沙箱里执行类似 `mount 192.0.2.1:/<卷名> /挂载点` 的操作。挂载目标就是 orchestrator 在 `/init` 时告诉 envd 的 `192.0.2.1:/<卷名>`。
- NFS 客户端先访问 **portmap**（111 端口），这是 NFS 体系里的“服务目录”，问它“NFS 服务在哪个端口”。
- 然后访问 **NFS 服务**（2049 端口）读写数据。

宿主机上，orchestrator 运行着一个 portmap 服务和一个 NFS 代理，NFS 代理再把读写请求转到真正的存储后端。对沙箱来说，它只是在和 `192.0.2.1` 上的一台普通 NFS 服务器打交道。

没有使用持久卷的沙箱，不会去访问这两个端口。

## 五、全书地址转换总表

到这里，四类流量都讲完了。下面把全书出现过的所有 NAT 和改道规则汇总在一起。“槽位规则”指每个槽位各一份（以槽位 5 为例）。

### 5.1 命名空间里（每个槽位各一份）

| 规则 | 匹配 | 动作 | 作用 | 篇目 |
|---|---|---|---|---|
| nat POSTROUTING | `-o eth0 -s 169.254.0.21` | SNAT → `10.13.0.5` | 出口换门牌 | 12、13 |
| nat PREROUTING | `-i eth0 -d 10.13.0.5` | DNAT → `169.254.0.21` | 入口换回 | 12、13 |
| nftables | 从 `tap0` 进来的包 | 放行/丢弃 | 出站过滤 | 15 |

### 5.2 宿主机上（每个槽位各一份）

| 规则 | 匹配 | 动作 | 作用 | 篇目 |
|---|---|---|---|---|
| nat PREROUTING | `-i e2bv-5 -p tcp -d 192.0.2.1 --dport 80` | REDIRECT → 5010 | hyperloop | 19 |
| nat PREROUTING | `-i e2bv-5 -p tcp -d 192.0.2.1 --dport 111` | REDIRECT → 5012 | portmap | 19 |
| nat PREROUTING | `-i e2bv-5 -p tcp -d 192.0.2.1 --dport 2049` | REDIRECT → 5011 | NFS 代理 | 19 |
| nat PREROUTING | `-i e2bv-5 -p tcp --dport 80` | REDIRECT → 5016 | 防火墙代理（HTTP） | 16 |
| nat PREROUTING | `-i e2bv-5 -p tcp --dport 443` | REDIRECT → 5017 | 防火墙代理（TLS） | 16 |
| nat PREROUTING | `-i e2bv-5 -p tcp` | REDIRECT → 5018 | 防火墙代理（其他） | 16 |
| nat POSTROUTING | `-s 10.13.0.5/32 -o <默认出口网卡>` | MASQUERADE | 非 TCP 出站换成宿主地址 | 12、13 |

| 规则 | 匹配 | 动作 | 作用 | 篇目 |
|---|---|---|---|---|
| nat PREROUTING | `-p tcp --dport 80 --dst-type LOCAL` | REDIRECT → 3002 | 外部访问入口 | 17 |
| nat OUTPUT | `-p tcp -o lo --dport 80` | REDIRECT → 3002 | 本机访问入口 | 17 |

### 5.4 谁连谁

| 发起方 | 目标 | 经过 | 篇目 |
|---|---|---|---|
| 沙箱 | 互联网（TCP） | nftables → SNAT → REDIRECT → 防火墙代理 → 代理另开连接 | 13、16 |

| 沙箱 | 宿主服务 | nftables 放行 192.0.2.1 → SNAT → REDIRECT → 5010/5011/5012 | 19 |

| 组件 | 组件 | Consul DNS → 直连 | 17 |

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 特殊地址 | `192.0.2.1`（`SANDBOX_ORCHESTRATOR_IP`），文档专用段，不对应真实设备 |
| 防火墙放行 | 预置放行集合里只有它，排在所有拦截规则之前，断网时也能访问 |
| 沙箱如何得知 | `/init` 传入 `hyperloopIP`，envd 写 `/etc/hosts` 和 `E2B_EVENTS_ADDRESS` |
| 三条 REDIRECT | 80→5010 hyperloop，111→5012 portmap，2049→5011 NFS 代理 |
| 规则顺序 | 宿主服务规则排在防火墙代理规则前面，否则 80 端口会被截走 |
| 只有 TCP 的三个端口 | 其他协议和端口在宿主机上没有改道，访问无果 |
| hyperloop | `/me` 和 `/logs`，按源地址识别沙箱，并覆盖日志里的身份字段防伪造 |
| Host IP 是身份凭证 | 由命名空间 SNAT 写入，沙箱无法伪造 |
| NFS 与 portmap | 为持久卷服务，挂载目标是 `192.0.2.1:/<卷名>` |
