# 第 15 篇｜出站防火墙（一）：命名空间里的 nftables

> **本篇目标**：讲清楚沙箱出站流量要过的第一道关：每个命名空间里的 nftables 防火墙。读完本篇，你会知道：这张防火墙表放在哪、只管哪些包；预置拦截了哪些地址、为什么要拦；四个集合与五条规则各司何职、为什么这样排序；用户的 `allow_internet_access`、`allowOut`、`denyOut` 是怎么一路变成集合里的元素的；以及一个容易被误解的结论：**私有地址是永远放不出去的**。

---

## 一、防火墙放在哪、管什么

### 1.1 每个命名空间一张表

第 12 篇建网的第 7 步，orchestrator 在槽位的命名空间里建了一张 nftables 表：

- 表：`inet slot-firewall`
- 链：`PREROUTE_FILTER`，挂在 PREROUTING 钩子上，优先级 -150，默认策略 accept

每个槽位一张，互不相干。

### 1.2 只管“从客户机出来的包”

链里的每条规则都以 `iifname "tap0"` 开头，**只检查从 `tap0` 进入命名空间的包**，也就是客户机发出的包。从 `eth0`（vpeer）进来的包，比如外部的回包、宿主机发起的连接，都不受这些规则约束。

所以这是一个纯粹的**出站**防火墙：它决定沙箱能主动访问哪里。“谁能访问沙箱”是入口代理的事（第 18 篇）。

### 1.3 在地址转换之前检查

优先级 -150 早于 NAT 的 -100（第 8 篇）。防火墙看到的包，目的地址是沙箱**原本想访问的地址**，源地址还是 `169.254.0.21`。在这个位置判断“能不能去那里”，判断的对象是准确的。

## 二、四个集合

防火墙有四个 IP 地址集合，分成“预置”和“用户”两组：

| 集合名 | 类别 | 内容 | 何时改变 |
|---|---|---|---|
| `filtered_always_denylist` | 预置拦截 | 私有、环回、链路本地等地址段 | 固定不变 |
| `filtered_always_allowlist` | 预置放行 | `192.0.2.1/32` | 固定不变 |
| `filtered_denylist` | 用户拦截 | 用户的 `denyOut` | 每个沙箱拿到槽位时填入，归还时清空 |
| `filtered_allowlist` | 用户放行 | 用户 `allowOut` 中的 IP 和网段 | 同上 |

### 2.1 预置拦截：哪些地址永远不让去

预置拦截集合的内容来自代码里的一个列表：

| 地址段 | 是什么 | 为什么要拦 |
|---|---|---|
| `10.0.0.0/8` | 私有地址 | 机房内网；同机其他沙箱的 Host IP（`10.13.x.x`）和 veth 地址（`10.14.x.x`）也在这里 |
| `172.16.0.0/12` | 私有地址 | 内网；Docker 默认网段也在这里 |
| `192.168.0.0/16` | 私有地址 | 内网 |
| `127.0.0.0/8` | 环回 | 防止通过某些路径绕回宿主机自身 |
| `169.254.0.0/16` | 链路本地 | **云元数据服务** `169.254.169.254` |

代码里的这个列表还包括三段 IPv6 本地地址（`::1`、`fc00::/7`、`fe80::/10`），对应 IPv4 的环回、私有和链路本地。

这张表就是这套环境 README 里那句话的来源：“为隔离沙箱网络，沙箱发往 10.\*、169.254.\*、172.16.\*、127.\*、192.168.\* 网段的请求将被拒绝”。

**补充一点**：E2B 官方后来的版本在这个列表里加入了 `100.64.0.0/10`（运营商级 NAT 地址，部分云厂商用它放内部服务）。这套环境基于的 2026.09 版本还没有这一段。如果部署环境的内网用到了这段地址，需要留意。

### 2.2 预置拦截“拦了自己”？

细心的读者会问：客户机自己的地址 `169.254.0.21`、网关 `169.254.0.22` 都在 `169.254.0.0/16` 里，会不会把沙箱自己的正常通信也拦了？

不会，原因有三：

1. **客户机和 `tap0` 之间的通信**（比如 ARP）是二层的，不经过 IP 层的 PREROUTING 规则。
2. **访问 MMDS（`169.254.169.254`）的包在 Firecracker 里就被截下了**，根本不会出现在 `tap0` 上（第 9 篇）。
3. **沙箱回复宿主机连接的包**（目的地址 `10.14.0.10`）虽然在拦截范围内，但会先被规则 1 当作已建立连接放行（第 13 篇）。

### 2.3 预置放行：只有一个地址

预置放行集合里只有 `192.0.2.1/32`。这是沙箱眼中的“orchestrator 地址”（由环境变量 `SANDBOX_ORCHESTRATOR_IP` 配置，默认就是 `192.0.2.1`）。沙箱访问它的特定端口，会被宿主机改道到内部服务（第 19 篇）。

## 三、五条规则

```
iifname "tap0" ct state established,related accept                          # 规则 1
iifname "tap0" ip daddr @filtered_always_allowlist accept                    # 规则 2
iifname "tap0" ip daddr @filtered_always_denylist drop                       # 规则 3
iifname "tap0" meta l4proto != tcp ip daddr @filtered_allowlist accept       # 规则 4
iifname "tap0" meta l4proto != tcp ip daddr @filtered_denylist drop          # 规则 5
（链默认策略：accept）                                                         # “规则 6”
```

逐条看，每条回答一个问题。

**规则 1：已建立连接的包，放行。**
“这个包是不是一条已有连接的一部分？”是就放行。它保证客户机能回复别人主动发起的连接（比如宿主机连 envd），也保证一条已经放行的连接不会被后面的规则误伤。

**规则 2：去往 `192.0.2.1`，放行。**
“是不是去找 orchestrator 的？”是就放行，不管什么协议。它排在规则 3 前面，意味着即使用户拦截了一切（`0.0.0.0/0`），甚至预置拦截列表将来包含了这个地址，沙箱访问宿主内部服务的通道也不会被切断。

**规则 3：去往预置拦截的地址，丢弃。所有协议。**
“是不是想去内网、元数据服务、本机？”是就丢弃，**TCP、UDP、ICMP 一视同仁**。

**规则 4：非 TCP 流量，去往用户放行的地址，放行。**

**规则 5：非 TCP 流量，去往用户拦截的地址，丢弃。**

**默认：放行。**
上面都没命中的包一律放行。对 TCP 来说，“放行”只是放它过这一关，接下来它会在宿主机上被 REDIRECT 到 TCP 防火墙代理，在那里接受第二道检查（第 16 篇）。

### 3.1 为什么用户规则只管非 TCP

规则 4、5 都带着 `meta l4proto != tcp`：**用户配置的放行和拦截，在这一层只对非 TCP 流量生效**。

TCP 流量的用户规则交给 TCP 防火墙代理去判断。原因是：用户可以按**域名**配置放行（比如 `pypi.org`），而域名只能在 TCP 连接的内容里看到（HTTP 的 Host、TLS 的 SNI，第 4 篇）。nftables 只看得到 IP 地址，判断不了域名。所以干脆把 TCP 的用户规则全部交给代理，由它统一按“域名 + IP”判断。

### 3.2 为什么“私有地址永远放不出去”

注意规则 3 和规则 4 的顺序：**预置拦截（规则 3）排在用户放行（规则 4）之前**。

这意味着：即使用户在 `allowOut` 里写了 `10.0.0.5`，发往 `10.0.0.5` 的包也会先撞上规则 3，被丢弃，轮不到规则 4。TCP 也一样：规则 3 对所有协议生效，包在命名空间里就被丢了，到不了宿主机，更到不了代理。

这是一个**刻意的安全设计**：用户（也就是调用 API 的人）不能通过配置让沙箱访问内网。如果真有这种需求，只能改代码里的预置列表，那就是运维层面的决定了。

### 3.3 允许优先于拒绝

规则 4（用户放行）在规则 5（用户拦截）之前。所以当一个地址**同时**落在 `allowOut` 和 `denyOut` 里时，放行胜出。

最典型的用法就是“拒绝一切，再开几个口子”：

```json
{ "denyOut": ["0.0.0.0/0"], "allowOut": ["1.1.1.1"] }
```

`0.0.0.0/0` 进入用户拦截集合，`1.1.1.1` 进入用户放行集合。发往 `1.1.1.1` 的 UDP 包命中规则 4，放行；发往其他地址的 UDP 包命中规则 5，丢弃。TCP 代理也遵循同样的“允许优先”（第 16 篇）。

## 四、用户配置是怎么变成集合元素的

### 4.1 用户能配什么

创建沙箱时，和出站相关的参数有三个：

| 参数 | 含义 | 允许的值 |
|---|---|---|
| `allow_internet_access` | 是否允许上网 | `true` / `false` |
| `network.allowOut` | 放行列表 | IP、CIDR、域名（支持 `*.example.com`） |
| `network.denyOut` | 拦截列表 | 只能是 IP 或 CIDR，不支持域名 |

### 4.2 api 服务的处理

api 服务收到请求后，先做校验，再转换成发给 orchestrator 的格式：

1. **校验**：
   - `denyOut` 里每一项必须是 IP 或 CIDR，否则报错。
   - 如果 `allowOut` 里有域名，`denyOut` 里**必须包含 `0.0.0.0/0`**，否则报错。道理很简单：默认就是全放行的，不先“拒绝一切”，按域名放行就毫无意义。
2. **拆分**：把 `allowOut` 拆成两部分：IP/CIDR 和域名。
3. **补 DNS**：如果有域名，自动把 `8.8.8.8` 加进放行的 IP 列表（第 14 篇）。
4. **断网开关**：如果 `allow_internet_access` 是 `false`，把拦截列表**整个替换**成 `["0.0.0.0/0"]`，原来的 `denyOut` 被覆盖，`allowOut` 保留。

转换后发给 orchestrator 的是三个列表：

```
AllowedCidrs   = allowOut 里的 IP/CIDR（+ 8.8.8.8）
AllowedDomains = allowOut 里的域名
DeniedCidrs    = denyOut，或 ["0.0.0.0/0"]
```

### 4.3 orchestrator 的处理

orchestrator 这边还有一个节点级的开关 **`ALLOW_SANDBOX_INTERNET`**（这套环境的 `.env` 里是 `true`）。逻辑是：

- 如果请求里**明确**带了 `allow_internet_access`，以请求为准。
- 如果请求里**没有**这个字段，就用 `ALLOW_SANDBOX_INTERNET` 的值。
- 最终结果为“不允许上网”时，把 `DeniedCidrs` 设为 `["0.0.0.0/0"]`。

所以把 `.env` 里的 `ALLOW_SANDBOX_INTERNET` 改成 `false`，效果是：**没有明确要求上网的沙箱，默认都断网**。

### 4.4 装进集合

orchestrator 从池子里取出一个槽位后，调用 `ConfigureInternet`：

```go
// 简化示意
if 三个列表都为空 {
    return  // 默认全放行，什么都不用做
}
进入槽位的命名空间:
    for each cidr in AllowedCidrs { 加入用户放行集合 }
    for each cidr in DeniedCidrs  { 加入用户拦截集合 }
```

注意：

- `AllowedDomains` **不进 nftables**，因为 nftables 不认识域名。它们只保存在沙箱的配置里，留给 TCP 代理查（第 16 篇）。
- 三个列表都空时什么也不做，槽位保持“干净”状态，归还时也不用清理。
- `0.0.0.0/0` 需要特殊处理：Go 的地址库不把它当作合法的网段，代码直接往集合里写入“`0.0.0.0` 到 `255.255.255.255`”这个区间。

### 4.5 什么时候生效、能不能改

这套环境的版本里，网络规则**只在沙箱拿到槽位时设置一次**。创建沙箱、从暂停中恢复沙箱，都会走这一步。沙箱运行期间，没有接口可以修改出站规则。要换规则，只能暂停再恢复，或者重建沙箱。

## 五、归还时清空

沙箱结束、槽位要放回池子时，orchestrator 调用 `ResetInternet`：

- 如果这个槽位曾经设置过用户规则，就进入命名空间，把**用户放行和用户拦截两个集合清空**，把两个预置集合**重新填一遍**。
- 如果从没设置过（默认全放行），什么也不做。

这一步至关重要。第 10 篇说过，槽位会被下一个沙箱复用。如果不清空，上一个用户“只允许访问 PyPI”的规则就会留给下一个用户，或者反过来，上一个用户的放行规则被下一个用户“继承”了。

## 六、三个典型配置

**完全断网：**

```json
{ "allow_internet_access": false }
```

用户拦截集合 = `0.0.0.0/0`。所有非 TCP 流量被规则 5 丢弃；所有 TCP 连接在代理那里被拒绝。沙箱仍可访问 `192.0.2.1`（规则 2），宿主机仍可连进沙箱（规则 1 放行回包）。

**禁止访问某个公网网段：**

```json
{ "network": { "denyOut": ["203.0.113.0/24"] } }
```

发往这个网段的 UDP、ICMP 被规则 5 丢弃；TCP 在代理那里被拒绝。其他地址照常放行。

**只允许访问 PyPI：**

```json
{
  "network": {
    "allowOut": ["pypi.org", "files.pythonhosted.org"],
    "denyOut": ["0.0.0.0/0"]
  }
}
```

nftables 这一层：用户放行集合 = `8.8.8.8`（自动补上），用户拦截集合 = `0.0.0.0/0`。于是 DNS 查询能出去，其他 UDP 全部被丢。两个域名的 TCP 放行由代理根据 SNI 判断。

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 位置 | 每个命名空间一张 `inet slot-firewall` 表，PREROUTING，优先级 -150 |
| 只管出站 | 每条规则都匹配 `iifname "tap0"` |
| 预置拦截 | 10/8、172.16/12、192.168/16、127/8、169.254/16（另有三段 IPv6 本地地址） |
| 预置放行 | 只有 `192.0.2.1/32` |
| 规则 1 | 已建立连接放行，让沙箱能回复宿主机 |
| 规则 3 | 预置拦截对所有协议生效，且排在用户放行之前 |
| 私有地址放不出去 | `allowOut` 也救不了，刻意设计 |
| 规则 4/5 | 用户规则在这一层只管非 TCP；TCP 交给代理 |
| 允许优先 | 用户放行排在用户拦截之前 |
| api 的转换 | 拆分 IP 与域名；有域名就补 `8.8.8.8`；断网则拦截列表替换为 `0.0.0.0/0` |
| `ALLOW_SANDBOX_INTERNET` | 请求未指定时的默认值，改为 `false` 则默认断网 |
| 何时生效 | 取槽位时设置一次，运行中不能改 |
| 归还清空 | 用户集合清空、预置集合重填，防止规则遗留给下一个沙箱 |
