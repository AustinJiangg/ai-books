# 第 18 篇｜从 SDK 到 envd：一次沙箱请求的完整路径

> **本篇目标**：把 SDK 访问沙箱的整条路一次走完。读完本篇，你会知道：client-proxy 怎么从域名里认出“哪个沙箱、哪个端口”，又怎么知道沙箱在哪台机器上；orchestrator 的代理怎么把请求送到沙箱的 Host IP；为什么连接池要用“生命周期 ID”区分；访问令牌在哪里校验；只监听 localhost 的服务为什么也能被访问到；以及这套环境的补丁对代理做了哪些改进。

---

## 一、全路径一览

先看全貌。SDK 在宿主机上执行 `sbx.commands.run("whoami")`：

```
① SDK
   │  请求 http://49983-<沙箱ID>.e2b.app/...
   ▼
② dnsmasq：*.e2b.app → 127.0.0.1                         （第 17 篇）
   ▼
③ iptables OUTPUT：127.0.0.1:80 → 127.0.0.1:3002          （第 17 篇）
   ▼
④ client-proxy (:3002)
   │  从 Host 头解析出：端口 49983，沙箱 ID
   │  查沙箱目录：这个沙箱在哪个节点？→ 节点 IP（单机就是本机）
   ▼
⑤ orchestrator proxy（节点 IP:5007）
   │  再次解析端口和沙箱 ID
   │  在本机内存里找到沙箱 → 它的 Host IP，例如 10.13.0.5
   ▼
⑥ 宿主机路由：10.13.0.5 via 10.14.0.11 dev e2bv-5          （第 11 篇）
   ▼
⑦ 命名空间 ns-5：DNAT 10.13.0.5 → 169.254.0.21             （第 13 篇）
   ▼
⑧ tap0 → Firecracker → 客户机里的 envd (:49983)
```

响应沿原路返回。①～③ 上一篇讲过，⑥～⑧ 第 13 篇讲过，本篇重点讲中间的两层代理。

---

## 二、第一层：client-proxy

### 2.1 从域名里认出沙箱和端口

client-proxy 收到的 HTTP 请求里，`Host` 头是：

```
Host: 49983-i2k5fx3h0qa9z1m7.e2b.app
```

解析规则很简单：

1. 取第一个点之前的部分：`49983-i2k5fx3h0qa9z1m7`。
2. 按 `-` 切开：第一段 `49983` 是**端口**，第二段 `i2k5fx3h0qa9z1m7` 是**沙箱 ID**。

如果格式不对，比如没有点或没有 `-`，就返回“无效的 Host”错误。这也是第 17 篇说 client-proxy 不能转发控制请求的原因：`api.e2b.app` 切不出端口和沙箱 ID。

除了 Host 头，也可以用两个请求头指定目标：`E2b-Sandbox-Id` 和 `E2b-Sandbox-Port`。当客户端直接用 IP 或 `localhost` 访问、没法用域名时，就靠这种方式。

### 2.2 沙箱在哪台机器上

client-proxy 本身不知道沙箱跑在哪。它要查一份**沙箱目录**（catalog）。这套环境用 Redis 存这份目录（`.env` 里 `SANDBOX_STORAGE_BACKEND=redis`）：

- 沙箱创建时，api 往目录里写一条：“沙箱 X 在 orchestrator 节点 IP 为某某的机器上”。
- client-proxy 查目录得到节点 IP。为了少查 Redis，结果会在本地缓存半秒。

单机部署时，节点 IP 永远是本机。但这套机制是为多节点设计的，单机也照样走一遍。

如果目录里没有这个沙箱，可能是沙箱已经被暂停了。这时 client-proxy 可以请 api 把它恢复，前提是开启了“自动恢复”功能；否则返回“沙箱不存在”。

### 2.3 转给节点上的 orchestrator 代理

拿到节点 IP 后，client-proxy 把请求原样转发到：

```
http://<节点 IP>:5007
```

5007 是 orchestrator 内置代理的端口（`.env` 里 `ORCHESTRATOR_PROXY_PORT=5007`）。注意，转发时 `Host` 头保持不变，下一层代理还要用它。

## 三、第二层：orchestrator 代理

### 3.1 找到沙箱的 Host IP

orchestrator 代理收到请求，**再解析一次** Host 头，得到端口和沙箱 ID。然后在**本机内存**里查找这个沙箱（它就是管这个沙箱的那个进程，内存里有全部信息），拿到它所在槽位的 **Host IP**。

```go
// 简化示意
sbx := sandboxes.Get(sandboxID)
target := fmt.Sprintf("http://%s:%d", sbx.Slot.HostIP, port)   // 例如 http://10.13.0.5:49983
```

然后把请求转发过去。接下来就是第 13 篇的“旅程三”：宿主机路由到 `e2bv-5`，命名空间里 DNAT 成 `169.254.0.21`，进入客户机。

### 3.2 为什么要两层代理

既然 orchestrator 代理自己就能完成转发，为什么前面还要一层 client-proxy？

因为 E2B 是为**多节点集群**设计的：

- client-proxy 是**集群的统一入口**，只负责“找到沙箱在哪个节点”。
- orchestrator 代理是**每个节点上的本地入口**，负责“把请求送进本机的某个沙箱”。只有它知道本机沙箱的 Host IP。

单机部署时，两层都在同一台机器上，看起来有点多余，但结构和多节点完全一致。

### 3.3 失败时自动重试

orchestrator 代理在连接沙箱失败时会**重试**，最多 5 次。代码注释说明，这是为了应对“沙箱里 envd 的端口转发还没就绪”的情况（第五节）：用户刚启动一个服务，envd 还要过一会儿才把它暴露出来。

---

## 四、连接池：为什么按“生命周期 ID”区分

### 4.1 连接复用的风险

代理为了性能，通常会**复用**到后端的 TCP 连接：一个请求用完的连接不关，留给下一个发往同一地址的请求接着用。连接池一般按“目标地址”来分组，比如“所有发往 `10.13.0.5:49983` 的请求共用一组连接”。

但第 10 篇说过：**Host IP 会换主人**。槽位 5 今天给沙箱 A 用，明天给沙箱 B 用，Host IP 都是 `10.13.0.5`。如果连接池只按地址分组，可能出现：

1. 代理和沙箱 A 建了一条到 `10.13.0.5:49983` 的连接，放进连接池。
2. 沙箱 A 结束，槽位 5 分给了沙箱 B。
3. 发给沙箱 B 的请求，从连接池里拿到了那条“发往 `10.13.0.5:49983`”的旧连接。

这条连接两端的状态已经对不上了，请求失败；更糟的情况下，请求可能被错误的对象处理。

### 4.2 E2B 的做法

orchestrator 代理的连接池不按地址分组，而是按沙箱的**生命周期 ID**（LifecycleID）分组。每个沙箱实例有一个唯一的生命周期 ID，不同的沙箱、哪怕用同一个槽位，ID 也不同，它们的连接绝不会混用。

代码注释还专门解释了为什么不直接用沙箱 ID：沙箱暂停后再恢复，沙箱 ID 不变，但它已经是一个“新的实例”了，可能落在不同的槽位上。按沙箱 ID 分组，会在“暂停/恢复”的边界上出问题。

另外，orchestrator 代理到沙箱的连接**关闭了 keep-alive**，也就是不长期保持空闲连接。注释给出的理由是：沙箱里的服务可能不稳定（随时重启），而代理和沙箱在同一台机器上，新建连接的开销很小。

## 五、访问控制：谁能访问沙箱

沙箱的 URL 是可以被猜到的格式，必须有访问控制。这套环境里有两类令牌，分别保护两类端口。

### 5.1 envd 端口（49983）：envd 自己校验

访问 envd 的请求要带上访问令牌。envd 用 MMDS 里的 `accessTokenHash`（第 9 篇）校验调用者带来的令牌。这一步在沙箱**里面**完成，代理不管。

### 5.2 其他端口：流量访问令牌

用户在沙箱里起的服务（比如 8000 端口的网页），默认**任何人都能访问**，只要知道 URL。

创建沙箱时可以设置 `network.allowPublicTraffic: false`。这时 api 会为沙箱生成一个**流量访问令牌**。之后访问这个沙箱的**非 envd 端口**，请求头里必须带上：

```
e2b-traffic-access-token: <令牌>
```

orchestrator 代理负责检查：没带或者不对，直接拒绝，不会把请求送进沙箱。

### 5.3 改写 Host 头：maskRequestHost

还有一个和入站相关的配置 `network.maskRequestHost`。沙箱里的 Web 服务收到请求时，`Host` 头是 `8000-<沙箱ID>.e2b.app` 这种样子。有些 Web 框架会校验 Host，看到这种奇怪的值就拒绝服务。

设置 `maskRequestHost` 后，orchestrator 代理在转发给沙箱前，把 `Host` 头改成你指定的值（其中可以用一个占位符代表端口号）。这只对非 envd 端口生效。

## 六、访问只监听 localhost 的服务

### 6.1 问题

用户在沙箱里执行：

```bash
python -m http.server 8000 --bind 127.0.0.1
```

服务只监听客户机的 `127.0.0.1:8000`。但请求是经过 DNAT 后，以 `169.254.0.21:8000` 为目的地进来的（第 13 篇）。第 4 篇讲过：只监听 `127.0.0.1` 的服务，从 `169.254.0.21` 访问是连不上的。

### 6.2 envd 的端口转发

envd 解决了这个问题。它**定期扫描**客户机里正在监听的 TCP 端口，专门找“只监听在 `127.0.0.1`、`localhost` 或 `::1` 上”的那些。每发现一个，就启动一个 `socat` 进程：

```bash
socat TCP4-LISTEN:8000,bind=169.254.0.21,fork TCP4:localhost:8000
```

意思是：在 `169.254.0.21:8000` 上监听，每来一个连接，就转给 `localhost:8000`。这样，从外面进来的请求先到 socat，再被转给用户的服务。

```
代理 → 10.13.0.5:8000 → DNAT → 169.254.0.21:8000 (socat) → 127.0.0.1:8000 (用户服务)
```

服务停止后，envd 也会停掉对应的 socat。

因为扫描是定期的，用户刚启动服务的那一刻，socat 可能还没起来。第 3.3 节说的“orchestrator 代理重试 5 次”，正是为了兜住这个时间差。

## 七、这套环境对代理的改进

ARM 适配补丁对代理（client-proxy 和 orchestrator 代理共用同一个代理库）做了几处改动，和网络行为直接相关的有三处：

1. **请求体全双工。** 修复了一个隐蔽的 bug：Go 的 HTTP 服务器默认在开始写响应时就关掉请求体。而代理此时可能还在往后端转发请求体，于是转发失败，连接被关闭，导致**流式响应**（比如命令输出流）在已经收到前几条消息后突然中断。补丁开启了全双工模式，让请求体和响应可以同时进行。
2. **可选的请求追踪。** 通过环境变量打开，记录每个请求在代理里的各个阶段，用于排查中断类问题。默认关闭。
3. **快照回滚感知。** 这套环境支持把运行中的沙箱回滚到某个检查点（第 20 篇）。回滚期间，沙箱暂停、TCP 状态也在倒退：
   - 回滚进行中到达的请求，代理**立即**返回明确的错误，而不是让它挂到回滚结束再失败。
   - 一个请求如果在回滚前就已经发出、回滚后才失败，代理返回“沙箱已回滚”的明确说明，而不是笼统的“端口未开放”。后者会误导使用者去沙箱里找一个根本不存在的问题。

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 全路径 | SDK → dnsmasq → iptables 80→3002 → client-proxy → orchestrator 代理 :5007 → Host IP → DNAT → envd |
| 解析 Host | `<端口>-<沙箱ID>.<域名>`；也可用 `E2b-Sandbox-Id/Port` 请求头 |
| 沙箱目录 | Redis 里记录“沙箱在哪个节点”；client-proxy 查它得到节点 IP |
| 两层代理 | client-proxy 是集群入口，orchestrator 代理是节点入口，只有后者知道 Host IP |
| 重试 | orchestrator 代理最多重试 5 次，兜住端口转发的延迟 |
| 连接池按生命周期 ID | Host IP 会换主人，按 ID 分组防止连接串到别的沙箱 |
| envd 令牌 | envd 用 MMDS 里的哈希自己校验 |
| 流量访问令牌 | `allowPublicTraffic: false` 时，访问非 envd 端口要带 `e2b-traffic-access-token` |
| maskRequestHost | 转发前改写 Host 头，只对非 envd 端口生效 |
| envd 端口转发 | 扫描只监听 localhost 的端口，用 socat 在 `169.254.0.21` 上暴露 |
| 补丁改进 | 请求体全双工、可选追踪、回滚期间返回明确错误 |
