# 第 20 篇｜槽位池、复用与快照回滚下的 conntrack

> **本篇目标**：讲两件和“规模”有关的事。第一件是**网络槽位池**：为什么要预先建好几百个槽位，池子怎么取、怎么还，这套环境把池子调大到了多少，槽位编号存在哪、怎么避开别人的命名空间。第二件是这套环境新增的**快照回滚**能力，它带来一个隐蔽的网络问题：回滚之后，连接会莫名卡死。我们会看到问题出在内核的 conntrack 表上，以及补丁怎么解决它，甚至怎么解决“解决它”本身带来的性能问题。

---

## 一、为什么要预先建好槽位

第 12 篇的建网过程有十一步：建命名空间、建 veth、配地址、建 tap、加路由、写十几条 iptables 规则、建 nftables 表……每一步都是一次或几次系统调用，有些还要拿内核里的锁。在并发创建沙箱时，这些操作互相排队，一个槽位从无到有要花不少时间。

而沙箱从快照恢复只要几百毫秒。如果每次都现场建网，网络准备就成了最慢的一环。

所以 orchestrator 在启动时就开始**预先建好一批槽位**，放进池子。创建沙箱时，直接从池子里拿一个现成的，网络准备几乎不花时间。

---

## 二、池子的结构

### 2.1 两条队列

池子里有两条队列：

| 队列 | 里面是什么 | 上游容量 | 这套环境的容量 |
|---|---|---|---|
| 新建队列（new） | 刚建好、从没用过的槽位 | 32 | **300** |
| 复用队列（reused） | 用过、已经清理复位的槽位 | 100 | **1000** |

ARM 适配补丁把两个容量都调大了大约 10 倍，以应对高并发创建沙箱的场景。补丁还在每建好一个槽位时打一条日志，报告两条队列当前的长度，便于观察池子的状态。

### 2.2 后台一直在“补货”

orchestrator 启动后，有一个后台协程一直在循环：

```go
// 简化示意
for {
    slot := 建一个新槽位()        // 第 12 篇的十一步
    newSlots <- slot              // 放进新建队列；队列满了就在这里等着
}
```

新建队列满了，协程就阻塞在“放进去”这一步；有人取走一个，它就再建一个补上。所以正常情况下，新建队列总是接近满的。orchestrator 刚启动时，要花一段时间把这 300 个槽位建出来。

### 2.3 取：先拿旧的，再拿新的

创建沙箱时，从池子里取槽位：

```go
// 简化示意
select {
case slot = <-reusedSlots:     // 复用队列里有，优先拿
default:
    slot = <-newSlots          // 没有，就去新建队列拿（必要时等）
}
slot.ConfigureInternet(用户的网络配置)   // 装载用户的出站规则（第 15 篇）
```

优先用旧的，是因为旧槽位已经建好，用掉它不会触发新的建网操作；新建队列里的槽位留作储备。

### 2.4 还：清理复位，放回复用队列

沙箱结束时归还槽位：

1. **清理用户规则**：清空 nftables 的用户集合（第 15 篇）。如果清理失败，这个槽位就不能再用了，直接拆掉。
2. **放回复用队列**。
3. 如果复用队列**已经满了**（1000 个），这个槽位就没地方放，直接**拆掉**（第 12 篇的 RemoveNetwork），并释放它的编号。

### 2.5 复用时复位了什么、没复位什么

一个槽位被复用时：

| 东西 | 是否复位 | 说明 |
|---|---|---|
| 命名空间、网卡、地址、路由 | 不需要 | 本来就和沙箱无关，原样复用 |
| NAT 规则、REDIRECT 规则 | 不需要 | 只和槽位编号有关 |
| nftables 用户集合 | **清空** | 否则上一个用户的规则会留给下一个 |
| conntrack 记录 | 不主动清理 | 旧连接的记录按超时自然消失 |

最后一行值得一提。上一个沙箱留下的 conntrack 记录不会在归还时被清掉，而是等它们自己超时。下一个沙箱是从全新的快照恢复的，它发起的连接会用新的随机端口，一般不会和旧记录撞上。但这里确实存在一个“槽位换主人、内核记录还在”的窗口，这也是第 18 篇说连接池要按生命周期 ID 区分的原因之一。

### 2.6 orchestrator 退出时

orchestrator 正常退出时，会关闭池子，把新建队列和复用队列里所有空闲槽位逐个拆掉。如果它是被强杀的，这些槽位就成了残骸（第 12 篇、第 21 篇）。

## 三、槽位编号存在哪

### 3.1 两种存储方式

每个槽位要有一个**不重复的编号**。谁来保证不重复？E2B 有两种实现：

| 方式 | 依据 | 适用场景 |
|---|---|---|
| Consul KV | 把“哪些编号被谁占用”记在 Consul 的键值存储里 | 多节点生产集群 |
| 本地存储 | 直接看本机 `/var/run/netns/` 目录 | 开发环境、单机 |

选哪种由环境决定：`ENVIRONMENT` 是 `local` 或 `dev`，或者设置了 `USE_LOCAL_NAMESPACE_STORAGE`，就用本地存储。这套环境的 `.env` 里是 `ENVIRONMENT=local`，所以用的是**本地存储**。

### 3.2 本地存储的规则

本地存储的思路是：**`/var/run/netns/` 这个目录本身就是分配表**。`/var/run/netns/ns-7` 存在，就说明编号 7 被占用了。

具体来说：

1. **启动时**：扫描 `/var/run/netns/` 里已经存在的所有条目，记为“别人的”命名空间，以后永远跳过这些编号。
2. **分配时**：从编号 2 开始往上找（编号 1 留给宿主机），跳过“别人的”和“自己已经分出去的”，再检查 `/var/run/netns/ns-<编号>` 是否存在。不存在，就把这个编号分配出去。整个查找有 500 毫秒的超时。
3. **释放时**：从“自己已分出去”的记录里删掉这个编号。

### 3.3 一个运维陷阱

注意第 1 步：“别人的”命名空间是**启动时**的一次性快照，运行期间不更新。

假设上一次 orchestrator 被强杀，留下了 300 个残留的 `ns-2` 到 `ns-301`。这次启动时，它们全被记成“别人的”，编号 2～301 全部跳过，新槽位从 `ns-302` 开始建。残留的命名空间既占着系统资源，又白白浪费了编号。

更麻烦的是，即使你在 orchestrator **运行期间**手动删掉了这些残留命名空间，它也不知道，因为“别人的”名单不会更新，那些编号依然不会被使用。

所以清理残留必须在 orchestrator **启动之前**进行。这套环境的部署脚本 `build.sh -d` 和 `--recycle-netns` 都是先停 orchestrator、再清理、再启动（第 21 篇）。

## 四、快照回滚：一个隐蔽的网络问题

### 4.1 什么是快照回滚

这套环境在上游 E2B 之上增加了**检查点与回滚**能力：可以给一个**正在运行**的沙箱打一个检查点（保存它此刻的内存和状态），之后随时把沙箱**回滚**到这个检查点。

回滚的过程大致是：

1. 停掉沙箱当前的 Firecracker 进程。
2. 用同一个网络槽位，启动一个新的 Firecracker，从检查点的快照恢复。

沙箱“回到了过去”，网络槽位没变，Host IP 也没变。

### 4.2 回滚后，连接卡死了

问题来了。假设沙箱在检查点之后打开过一些 TCP 连接，或者检查点时就已经有连接在进行中。回滚后：

- **客户机**回到了过去：它的 TCP 状态（序列号等）回到了检查点那一刻。检查点之后建立的连接，它完全不记得。
- **内核的 conntrack 表**没有回到过去：命名空间里和宿主机上的两张表（第 7 篇），还记着回滚**之前**最新的连接状态，包括序列号推进到了哪里。

于是客户机发出的包，和 conntrack 的记录对不上：序列号“倒退”了，或者属于一条 conntrack 认为状态不一样的连接。内核把这些包判为 **INVALID**（第 7 篇），直接丢弃。

结果是：**连接不报错，只是卡住**。客户机不停重发，内核不停丢弃，直到超时。代码注释称之为“最难调试的一种失败方式”。

### 4.3 解决：回滚时清掉 conntrack

补丁新增了一个函数 `FlushConntrack`，在回滚过程中调用，时机是**旧 Firecracker 已停、新 Firecracker 还没恢复**的那一刻。这时虚拟机不在运行，没有任何流量，不会有新的记录在清理中途被创建出来。

它清理两张表：

| 表 | 清理方式 | 原因 |
|---|---|---|
| 命名空间里的 conntrack 表 | **整张清空** | 这张表里只有这一个沙箱的连接 |
| 宿主机的 conntrack 表 | 只删除**原始方向源地址或目的地址是这个沙箱 Host IP** 的记录 | 这张表是所有沙箱和宿主机共用的，不能误删 |

宿主机这边要删的记录有两类：

- 沙箱主动发起的：UDP 出站、被 REDIRECT 给代理的 TCP，原始源地址是 Host IP。
- 宿主机主动连进沙箱的：比如 orchestrator 连 envd，原始目的地址是 Host IP。

两张表的清理同时进行，互不依赖。

清理之后，客户机发出的包会被内核当作**新连接**处理。这正是客户机自己以为的情况：它根本不记得那些旧连接。

### 4.4 配合：代理层也要知道回滚

第 18 篇提过，orchestrator 代理也做了配合：

- 回滚进行中，到达的请求立即得到明确的错误。
- 跨越了回滚的请求失败后，返回“沙箱已回滚”的说明，而不是笼统的“端口未开放”。

## 五、一个更深的坑：关闭一个套接字要几百毫秒

### 5.1 现象

清理 conntrack 要通过一种叫 **netlink** 的内核接口：程序打开一个 netlink 套接字，通过它向内核发出“删除这些记录”的请求。

最初的实现是：每次清理时，进入命名空间，打开一个 netlink 套接字，发请求，关闭套接字。看起来很平常。

但在鲲鹏 920 服务器（内核 6.6）上实测发现，回滚变得很慢，而且很不稳定。追查下去，罪魁祸首竟然是**关闭套接字**这一步。

### 5.2 原因

代码注释记录了排查结果：关闭这类 netlink 套接字时，内核会通知 nf_tables（nftables 的内核模块），然后**等待 nf_tables 的内部工作队列清空**。而这个队列恰恰在 orchestrator 的槽位池建新槽位时最忙：每个新槽位都要往内核写一批 nftables 规则（第 12 篇第 7 步）。

实测数据：

- 关闭一次套接字，最快 127 毫秒，中位数 250 毫秒，最慢 447 毫秒。
- 耗时超过 150 毫秒的回滚里，87% 都能用“某一次关闭套接字”来解释，而这一步占了整个回滚耗时的 90%。

一次回滚本身才 100 毫秒左右，关一个套接字就要 250 毫秒。

### 5.3 解决：套接字只开一次、不关

补丁的办法是：**回滚路径上不打开、也不关闭任何 netlink 套接字**。

- **命名空间这边**：在建网的最后一步（第 12 篇第 11 步）就为这个槽位打开一个套接字，一直保存在槽位对象里，回滚时直接用。槽位拆除时才关闭它，而且交给后台协程去关，不阻塞拆网。
- **宿主机这边**：由一个常驻的“清扫器”统一持有一个套接字，批量处理所有沙箱的删除请求。

万一某个槽位的套接字坏了，就退回到“进入命名空间、临时开一个套接字”的老办法，并只打印一次告警。

这个案例说明了一个道理：在高并发、强调毫秒级延迟的系统里，看起来“理所当然很快”的操作也可能是瓶颈，必须靠实测来发现。

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 为什么预建 | 建一个槽位步骤多、要拿锁，现场建会拖慢毫秒级恢复 |
| 新建队列 | 从没用过的槽位，上游 32 个，这套环境 300 个 |
| 复用队列 | 清理复位后的旧槽位，上游 100 个，这套环境 1000 个 |
| 补货 | 后台协程持续建槽位，队列满了就等着 |
| 取 | 先拿复用的，再拿新建的，然后装载用户出站规则 |
| 还 | 清空用户集合，放回复用队列；队列满则拆掉 |
| 复用不复位的 | 网卡、地址、NAT 规则原样复用；conntrack 记录等它超时 |
| 编号存储 | `ENVIRONMENT=local` → 本地存储，以 `/var/run/netns/` 为分配表 |
| 编号从 2 开始 | 编号 1 留给宿主机 |
| 启动时快照 | 已存在的 `ns-*` 被记为“别人的”，运行期不更新；清理残留要在启动前 |
| 快照回滚 | 补丁新增：把运行中的沙箱回到检查点，复用同一槽位 |
| 回滚后连接卡死 | 客户机 TCP 状态倒退，conntrack 记录没倒退，包被判 INVALID 丢弃 |
| FlushConntrack | 虚拟机停机期间，清空命名空间的表，删除宿主表里与 Host IP 相关的记录 |
| 关闭套接字很慢 | 鲲鹏 + 内核 6.6 上要等 nf_tables 工作队列，中位 250 毫秒 |
| 套接字只开一次 | 每个槽位建网时打开、拆网时后台关闭；宿主侧由常驻清扫器持有 |
