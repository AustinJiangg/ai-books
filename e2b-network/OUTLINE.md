# 大纲

**读者**：会一点编程、用过命令行，但没系统学过计算机网络和 Linux 内核网络的新手。
**目的**：花几个小时读完，把一套实际在用的 E2B 环境的网络栈看明白：从客户机网卡到宿主机入口，每一层用了什么机制、为什么这样设计、配置项各管什么。概念讲透，但只读不练，不安排动手实验。
**写法**：从现实问题出发，先讲“为什么需要”，再讲“是什么”，最后讲“这套环境怎么做、坑在哪”。多用生活类比和文字图，每篇末尾有“本篇小结”表格。
**代码**：只放简短的示例片段，帮助理解，不追求完整可运行，也不需要读者自己核对。片段包括：
- 简化后的 Go 代码；
- `ip`、`iptables`、`nft` 命令和规则；
- 命令的示例输出。
**依据**：以作者实际部署的环境为准，不讲 E2B 官方最新版的新功能。
- 源码：上游 [e2b-dev/infra](https://github.com/e2b-dev/infra) tag `2026.09`，打上 ARM 适配补丁 `0001-adapted-for-arm-architecture.patch`。
- 部署方式：单机鲲鹏 ARM 服务器、openEuler。用 RPM 安装到 `/opt/e2b-infra`，再依次执行 `build.sh -d`（停止并清理）、`-i`（安装）、`-s`（启动部署）。

本书自成一体，不依赖本仓库其他书。
**规模**：22 篇，每篇约 2000～3400 个汉字，合计约 5.7 万汉字（连同代码、命令和英文约 13 万字符）。

## 第一部分　打地基：够用的网络知识

### 第 1 篇　从一行 `curl` 说起：E2B 沙箱网络要解决什么问题

- 两个场景：
  - 沙箱里的 AI 执行 `curl example.com`、`pip install`。
  - 宿主机上的 Python SDK 调用 `sandbox.commands.run(...)`。

  这两件事背后，包都走了哪条路？
- E2B 是什么：
  - 用 Firecracker microVM 跑不受信任的代码。
  - 一台服务器上同时跑成百上千个沙箱。
  - 沙箱从快照恢复，而不是冷启动。
- 本书讲的这套环境：单机部署，各组件和它们之间的关系。
  - nomad、consul 负责调度和服务发现。
  - api 负责控制面。
  - client-proxy 是流量入口。
  - orchestrator 管理沙箱。
  - 沙箱里跑着 envd。
  - 宿主机 DNS 用 dnsmasq。
- 沙箱网络的四类流量：
  - 出站：沙箱访问互联网。
  - 入站：SDK 或浏览器访问沙箱。
  - 控制：宿主调用沙箱里的 envd。
  - 内部服务：沙箱访问宿主上的 hyperloop、NFS。
- 设计目标：
  - 沙箱之间互相隔离。
  - 保护宿主和内网。
  - 出站流量可控。
  - 网络准备要快，不能拖慢沙箱启动。
- 一张贯穿全书的全景图。沙箱一侧依次是：客户机 eth0、tap0、网络命名空间、veth、宿主机路由与 NAT、物理网卡、外网。入口一侧依次是：dnsmasq、iptables 80→3002、client-proxy、orchestrator proxy、沙箱。
- 本书路线图：每一部分负责全景图上的哪一段。

### 第 2 篇　网络基础（一）：IP 地址、子网与几类特殊地址

- IP 地址是“门牌号”：32 位、点分十进制；网络号和主机号。
- 子网掩码与 CIDR 写法，用“一条街有几个门牌”来类比。本书会用到四种：
  - `/16`：一个地址池。
  - `/30`：tap 那一小段。
  - `/31`：veth 对，只有两个地址的点对点链路。
  - `/32`：单个地址。
- 怎么从一个 CIDR 算出第 N 个地址（为第 11 篇的槽位地址计算做准备）。
- 几类特殊地址，后面每一类都会用到：
  - 私有地址：10/8、172.16/12、192.168/16。
  - 环回地址：127/8。
  - 链路本地地址：169.254/16。沙箱客户机地址和元数据服务都在这一段。
  - 文档保留地址：192.0.2.0/24。沙箱眼中的“orchestrator 地址”`192.0.2.1` 就在这一段。
- IPv4 与 IPv6 一句话对比：本书只讲 IPv4，IPv6 在这套环境里只出现在拦截列表里。

### 第 3 篇　网络基础（二）：以太网、ARP、路由表与转发

- 两层地址：MAC 地址管“这一段线上交给谁”，IP 地址管“最终送到哪”（类比快递面单上的收件人和每一站的中转员）。
- 以太网帧的结构：帧头里的 MAC 地址、里面装着的 IP 包。
- ARP：知道 IP、问 MAC；为什么同一网段里两台机器 IP 相同会出乱子（第 10 篇伏笔）。
- 路由表：
  - 按“最长前缀匹配”选路。
  - 直连路由。
  - 默认路由与默认网关。
- 一台机器什么时候会“帮别人转包”：`net.ipv4.ip_forward` 的含义。
- 读懂 `ip addr`、`ip route`、`ip neigh` 的输出（直接给出示例输出并逐行解释）。

### 第 4 篇　网络基础（三）：TCP、UDP、端口与连接

- 端口是“房间号”：一台机器上很多程序共用一个 IP。
- UDP 和 TCP 的区别：寄明信片和打电话。
- 一次 TCP 连接的生命周期：
  - 三次握手。
  - 序列号与确认号。
  - 四次挥手。
  - 连接在两端各有一份状态。

  序列号会在第 20 篇“快照回滚后连接卡死”里用到。
- 五元组：协议、源 IP、源端口、目的 IP、目的端口；为什么它能唯一标识一条连接。
- 监听地址：`0.0.0.0`、`127.0.0.1` 和某个具体 IP 的区别（第 18 篇 envd 端口转发要用）。
- 应用层能在连接一开始看到的东西：
  - HTTP 请求的 `Host` 头。
  - TLS 握手里的 SNI。

  这两样都不用解密就能看到“想访问哪个域名”，是第 16 篇按域名过滤的基础。

### 第 5 篇　网络基础（四）：DNS 是怎么工作的

- 域名到 IP：根、顶级域、权威服务器、递归解析器，用查电话号码簿来类比。
- 一台 Linux 机器怎么查 DNS：
  - glibc 解析器读 `/etc/resolv.conf`。
  - 多个 nameserver 的顺序与超时。
- A 记录和 AAAA 记录；为什么客户端常常两种一起查，一个没回就要等超时。
- DNS 默认走 UDP 53 端口；这对第 15 篇的防火墙意味着什么。
- 本地 DNS 转发器（dnsmasq 这一类）是什么：本机的“DNS 总机”，按域名分流、给特定域名直接作答。
- 服务发现型 DNS（Consul）：服务的地址会变，用名字找到它“现在在哪”。
- 小结：这套环境里有两套完全独立的 DNS。一套是宿主机的 dnsmasq，见第 17 篇；另一套是沙箱里的 resolv.conf，见第 14 篇。

### 第 6 篇　Linux 虚拟网络的积木：网络命名空间、veth 与 tap

- 内核眼中的“网卡”：物理网卡、环回网卡、各种虚拟网卡都是一个接口。
- 网络命名空间（netns）：
  - 一台机器开出多套互相看不见的网络栈，各有网卡、路由表、iptables 规则和 conntrack 表。
  - 用公寓楼里的独立套间来类比。
  - 命名空间靠什么“活着”：进程，或者 `/var/run/netns/` 下的挂载点。
- veth 对：
  - 一根两头的虚拟网线，一头放进命名空间，一头留在宿主机。
  - 两头可以分别改名、配地址。
- tap 设备：
  - 一头是内核里的网卡，一头是用户态程序手里的文件描述符。
  - 程序读写这个文件描述符，就是在收发以太网帧。
- tun 与 tap 的区别；为什么虚拟机要用 tap。
- 把三块积木连起来有两种思路：网桥，以及路由加 NAT（第 11 篇解释 E2B 为什么选后者）。
- 读懂几条命令的输出：
  - `ip netns list`
  - `ip netns exec ns-1 ip addr`
  - `ip link show type veth`

### 第 7 篇　Netfilter（一）：iptables、NAT 与 conntrack

- 内核里的“安检口”：包经过的五个钩子点。
  - PREROUTING
  - INPUT
  - FORWARD
  - OUTPUT
  - POSTROUTING
- 一张图分清三种包各走哪几个钩子：进本机的、本机发出的、经本机转发的。
- 表与链：
  - filter 管放行或丢弃。
  - nat 管改地址。
  - mangle 管改包头里的其他字段。
  - 规则从上往下匹配，命中即停。
- iptables 命令怎么读：`-t`、`-A`、`-i`、`-o`、`-s`、`-d`、`-p`、`--dport`、`-j`。
- NAT 的四种形态，用快递来类比：
  - SNAT：改寄件人。
  - MASQUERADE：自动用出口网卡的地址做 SNAT。
  - DNAT：改收件人。
  - REDIRECT：转给本机前台的某个窗口。
- conntrack 连接跟踪：
  - 只有一条连接的第一个包查 NAT 规则，后续包和回包按记录改写。
  - `ESTABLISHED`、`RELATED` 是什么意思。
  - conntrack 表也是按命名空间分开的。
- `SO_ORIGINAL_DST`：被 REDIRECT 之后，程序怎么问内核“这个连接原本要去哪”（第 16 篇要用）。
- `-m addrtype --dst-type LOCAL` 是什么意思（第 17 篇要用）。

### 第 8 篇　Netfilter（二）：nftables 与集合

- nftables 是 iptables 的继任者：同一套 Netfilter，新的规则语言。
- 表、链、优先级；链可以挂到任意钩子上。
- 集合（set）：
  - 把成百上千个网段装进一个集合，一条规则查一次，不用写一百条规则。
  - 区间集合怎么表示 CIDR。
- 一次提交、原子生效：为什么改规则时不会出现“改了一半”的窗口。
- 读懂 `nft list ruleset` 的输出（给出示例）。
- 这套环境同时用了两者：
  - 命名空间里的出站过滤用 nftables。
  - NAT、转发、重定向用 iptables。
  - 两者并存时谁先谁后。

## 第二部分　一个沙箱的网络栈

### 第 9 篇　虚拟机的网卡：Firecracker、virtio-net 与 tap

- 客户机里的 `eth0` 是一块 virtio-net 网卡：前端驱动在客户机里，后端是 Firecracker 进程，Firecracker 再读写宿主上的 tap。
- 一个以太网帧从客户机到 tap 的旅程（概念讲解）。
- orchestrator 怎么配置这块网卡：
  - 通过 Firecracker API 指定 tap 名 `tap0` 和客户机 MAC。
  - 可选的限速器。
- 客户机的 IP 从哪来：不跑 DHCP，而是用内核启动参数 `ip=`。逐段解释这串参数：`169.254.0.21` 是本机地址，`169.254.0.22` 是网关，掩码 `255.255.255.252`，网卡 `eth0`。
- Firecracker 进程必须“住”在沙箱的命名空间里，才能打开那里的 `tap0`：
  - 上游的做法：`ip netns exec`。
  - 本环境补丁的做法：换成小工具 `fc-netns-exec`，直接 `setns` 后 `exec` Firecracker，省掉 `ip netns exec` 的额外开销；模板构建时仍走原路径。
- MMDS：
  - Firecracker 内置的元数据服务，客户机里访问 `169.254.169.254`。
  - envd 用它拿到沙箱身份信息。
  - 补丁把 envd 访问 MMDS 改成复用连接。

### 第 10 篇　快照带来的难题：为什么每个沙箱都是 169.254.0.21

- 沙箱从模板快照恢复：内存、设备状态，连同网卡配置一起“冻住”。
- 后果：每个沙箱的客户机网络配置完全相同。
  - IP 都是 `169.254.0.21`。
  - 网关都是 `169.254.0.22`。
  - MAC 一样。
  - 连 ARP 缓存都一样。
- 如果把它们直接接到同一个网段：地址冲突、ARP 混乱、回包不知道给谁。
- 能不能恢复后再改 IP？要进客户机改、要等，还会破坏“毫秒级恢复”。
- 解法：
  - 每个沙箱一个网络命名空间，命名空间里的地址都一样，互不可见。
  - 在命名空间出口用 NAT 把它们翻译成各不相同的地址。
- 槽位（slot）：一个编号，决定一个命名空间、一组网卡、一组地址。
- 小结：这套网络设计里几乎所有选择，都源自“快照里的地址改不了”这一点。

### 第 11 篇　一个槽位的拓扑：几块网卡、几个地址

- 一个槽位里有什么：
  - 命名空间 `ns-<编号>`。
  - 命名空间里的 `tap0`，地址 `169.254.0.22/30`。
  - 客户机地址 `169.254.0.21`。
  - veth 对：命名空间一侧叫 `eth0`（代码里叫 vpeer），宿主一侧叫 `e2bv-<编号>`。
  - 宿主可见的沙箱地址 Host IP。
- 两个地址池：
  - VRT 池给 veth 对用，每个槽位一个 `/31`。
  - Host 池给每个沙箱一个 `/32` 的 Host IP。

  上游默认是 `10.12.0.0/16` 和 `10.11.0.0/16`，本环境 `.env` 改成了 `10.14.0.0/16` 和 `10.13.0.0/16`，原因见第 21 篇。
- 地址计算举例：从槽位编号 5，一步步推出它的 vpeer、veth、Host IP。
- 容量上限：VRT 池 `/16` 能切出多少个 `/31`，即单机槽位上限。
- 为什么用“路由 + NAT”而不是网桥：
  - 每个沙箱一段独立的点对点链路，天然隔离。
  - 不用处理二层广播和 ARP 冲突。
- 宿主侧网卡改名：上游叫 `veth-<编号>`。本环境补丁改成 `e2bv-<编号>`，因为同机部署的 AgentENV 也用 `veth-` 前缀，并装了匹配 `veth-+` 的 iptables 规则。
- 一张完整的文字拓扑图，标出所有网卡、地址与路由。

### 第 12 篇　建网与拆网：CreateNetwork 一步一步

- 用简化的 Go 代码和等价的 `ip`/`iptables` 命令对照着讲，每一步回答“少了这一步会怎样”：
  1. 锁定线程、记住宿主命名空间：Go 里切换命名空间为什么要锁线程。
  2. 创建命名空间 `ns-N`。
  3. 建 veth 对，配 vpeer 地址，把宿主那头移回宿主并配地址。
  4. 进入命名空间，建 `tap0`、配地址，启用 `lo`。
  5. 命名空间里加默认路由，下一跳是宿主侧 veth。
  6. 命名空间里加两条 NAT 规则：出去时 SNAT 成 Host IP，进来时把 Host IP DNAT 回 `169.254.0.21`。
  7. 命名空间里初始化 nftables 防火墙（第 15 篇详讲）。
  8. 回到宿主，加一条路由：去往 Host IP 的包交给 vpeer。
  9. 宿主上加 FORWARD 放行规则（veth ↔ 默认出口网卡）和 MASQUERADE 规则。
  10. 宿主上加 REDIRECT 规则：通往宿主内部服务的三条（第 19 篇），出站 TCP 交给防火墙代理的三条（第 16 篇）。
  11. 本环境补丁新增：为这个命名空间预先打开一个 conntrack 句柄（第 20 篇）。
- “默认出口网卡”是怎么找到的：读路由表里的默认路由。
- 拆网 RemoveNetwork：
  - 按相反顺序删规则、路由、网卡、命名空间。
  - 拆不干净会留下什么：孤儿 veth，以及一直匹配不上的 iptables 规则。
  - 这类残留攒多了的后果（第 21 篇讲部署脚本怎么清）。

### 第 13 篇　包的旅程：出站、回程与宿主访问沙箱

- 出站：沙箱里 `curl` 发出的第一个 UDP 或 TCP 包，逐跳写出源和目的地址怎么变：
  1. 客户机 `eth0`。
  2. Firecracker。
  3. `tap0`。
  4. 命名空间里的 nftables。
  5. 命名空间路由。
  6. 命名空间内 SNAT：`169.254.0.21` 换成 Host IP。
  7. vpeer。
  8. `e2bv-N`。
  9. 宿主 PREROUTING：TCP 在这里被改道到防火墙代理，第 16 篇单独讲。
  10. 宿主路由与 FORWARD。
  11. MASQUERADE：Host IP 换成宿主网卡地址。
  12. 物理网卡。
- 回程：两层 conntrack 记录怎么把回包一路翻译回去，准确找到是哪个沙箱。
- 宿主访问沙箱：
  - 发往 Host IP:端口 的包走宿主路由到 vpeer，再由 DNAT 改成 `169.254.0.21`。
  - 这是第 18 篇入站和控制通道的基础。
- 一张“地址变化表”：每一跳的源地址和目的地址。
- 常见误区：
  - 为什么在宿主上直接 `ping 169.254.0.21` 不通，而访问 Host IP 能通。
  - 为什么两个沙箱互相访问不了。

### 第 14 篇　沙箱里的 DNS

- 沙箱的 `/etc/resolv.conf` 从哪来：
  - 模板构建时写进根文件系统，`nameserver 8.8.8.8`。
  - 构建脚本用 `chattr +i` 防止被改写。
- 一次 DNS 查询的路径：UDP 53 端口，经 nftables（不在拦截集合里就放行），再经两次 NAT 出到外网。
- 为什么沙箱用不了宿主机的 dnsmasq：
  - 宿主的 127.0.0.1 对沙箱来说是“它自己”。
  - 宿主的内网地址在拦截列表里。
- 在宿主出不了外网、或 8.8.8.8 不可达的环境里会发生什么，要改应该改哪里。
- DNS 与“按域名过滤”的关系：沙箱可以绕过 DNS 直接连 IP，所以域名过滤不能只靠 DNS（第 16 篇伏笔）。
- 和第 17 篇的宿主机 DNS 对照：两套 DNS 各服务谁、互不相干。

## 第三部分　管住出站流量

### 第 15 篇　出站防火墙（一）：命名空间里的 nftables

- 防火墙放在哪：每个命名空间一张 nftables 表，挂在 PREROUTING 上，只看从 `tap0` 进来的包。
- 预置拦截的地址段，以及各自为什么要拦：
  - 10/8、172.16/12、192.168/16：内网。
  - 127/8：环回。
  - 169.254/16：链路本地，包括云元数据服务。
  - IPv6 的本地地址段。

  同机其他沙箱的地址也在这些段里。
- 四个集合：
  - 预置放行。
  - 预置拦截。
  - 用户放行。
  - 用户拦截。
- 六条规则的顺序，每条用一句话解释它防什么：
  1. 已建立连接放行。
  2. 预置放行。
  3. 预置拦截。
  4. 非 TCP 的用户放行。
  5. 非 TCP 的用户拦截。
  6. 默认放行。
- 为什么用户规则只管 TCP 以外的流量：TCP 统一交给第 16 篇的代理处理，因为那里能看到域名。
- 用户能配什么，以及它们怎么变成集合里的元素，允许优先于拒绝：
  - 创建沙箱时的 `allow_internet_access=false`，等同于把 `0.0.0.0/0` 加入用户拦截集合。
  - `network.allowOut`
  - `network.denyOut`
- `0.0.0.0/0` 在集合里的特殊处理。
- 节点级开关 `ALLOW_SANDBOX_INTERNET`：本环境 `.env` 里是 `true`，改成 `false` 的效果。
- 槽位复用时防火墙怎么复位。

### 第 16 篇　出站防火墙（二）：TCP 防火墙代理

- 只看 IP 为什么不够：一个 IP 上住着很多网站，CDN 的 IP 还经常变。
- 宿主 PREROUTING 上的三条 REDIRECT，把沙箱发出的所有 TCP 按目的端口分三类，交给 orchestrator 里的 TCP 防火墙代理：
  - 80 → 5016：看 HTTP `Host` 头。
  - 443 → 5017：看 TLS SNI。
  - 其他端口 → 5018：只按 IP 判断。

  为什么要分开：SSH 这类“服务器先说话”的协议，如果代理先等客户端发数据，就会卡住。
- 代理收到一个连接后做什么：
  1. 按源地址（Host IP）找到这是哪个沙箱。
  2. 检查这个沙箱的连接数是否超限。
  3. 用 `SO_ORIGINAL_DST` 取出原本的目的地址。
  4. 窥探开头的字节，取出域名。
  5. 判定放行或拒绝。
  6. 放行就由代理自己连向目标，两边对接。
- 判定规则：
  - 域名匹配 `allowOut`（支持 `*.example.com`）。
  - 没有域名的连接退回到按 IP 判定。
  - 预置拦截段永远拦截。
- 防绕过：代理自己解析域名后，还要复查解析出的 IP 是否落在拦截段里，防止“域名指向内网”。
- 这条路径对性能和排障的影响：
  - 沙箱里看到的对端其实是谁。
  - 代理挂了会怎样。
- 小结：nftables 与 TCP 代理的分工对照表。

## 第四部分　入站与内部通道

### 第 17 篇　宿主机的入口：dnsmasq、Consul DNS 与 80→3002

- 问题：SDK 访问 `http://49983-<沙箱ID>.e2b.app`，这个域名在本机怎么落地？
- 宿主 DNS 的三层：
  - `/etc/resolv.conf` 第一行是 `127.0.0.1`。
  - dnsmasq 是本机 DNS 总机。
  - 不认识的域名转给默认上游。
- 两条关键的 dnsmasq 配置：
  - `address=/.e2b.app/127.0.0.1` 加 `local=/e2b.app/`：把所有 `*.e2b.app` 答成本机，AAAA 查询立即返回空，避免每个新连接多等 15 秒。
  - `server=/consul/127.0.0.1#8600`：`*.service.consul` 转给 Consul 的 DNS 接口。

  两者的区别：一个是自己作答，一个是转给别人答。
- 为什么 DNS 只能给地址、不能给端口：所以还需要 iptables 改端口。
- 两条 iptables 入口规则逐条解析：
  - PREROUTING 规则：只接管目的地址是本机（`--dst-type LOCAL`）的 80 端口流量，改送 3002。
  - OUTPUT 规则：本机经 `lo` 访问 80 端口的流量，改送 3002。

  老规则不带 `--dst-type LOCAL`，会截走经本机转发的所有 80 端口流量，包括沙箱和容器访问外网的 http。
- 内部服务互访：api、client-proxy 等组件之间靠 `*.service.consul` 直连，不经过 80/3002。
- SDK 一侧的配合：`patch_e2b.py` 把 SDK 的 https 全部改成 http，因为这套单机环境走明文。

### 第 18 篇　从 SDK 到 envd：一次沙箱请求的完整路径

- 沙箱 URL 的格式 `<端口>-<沙箱ID>.<域名>`，代理怎么从中解析出端口和沙箱 ID；也可以用请求头 `E2b-Sandbox-Id`、`E2b-Sandbox-Port` 指定。
- 全路径，一步一步：
  1. SDK。
  2. dnsmasq 把域名解析成 `127.0.0.1`。
  3. iptables 把 80 改到 3002。
  4. client-proxy 按沙箱 ID 查询，得知沙箱所在节点（单机时就是本机）。
  5. orchestrator proxy，端口 5007。
  6. 沙箱的 Host IP 加端口，通常是 envd 的 49983。
  7. 宿主路由送到命名空间，DNAT 改成 `169.254.0.21`。
  8. 客户机里的 envd。
- 连接池与“沙箱换人”：同一个 Host IP 下一次可能分给别的沙箱，所以连接不能乱复用。
- 访问控制：
  - envd 的访问令牌。
  - `allowPublicTraffic` 与流量令牌。
  - `maskRequestHost` 改写 Host 头。
- 访问沙箱里的其他服务，例如用户在 8000 端口起的网页：
  - 服务只监听 `127.0.0.1` 时，envd 自动用 socat 把 `169.254.0.21:端口` 转到客户机的环回地址。
  - 这就是为什么监听地址很重要（呼应第 4 篇）。
- 本环境补丁对代理的改动：
  - 请求体全双工，修复流式响应中途被掐断。
  - 可选的请求跟踪。
  - 回滚期间的请求直接返回明确的错误，而不是笼统的“端口未开放”（第 20 篇）。

### 第 19 篇　沙箱访问宿主服务：192.0.2.1 背后的 hyperloop、NFS 与 portmap

- 问题：沙箱有时需要访问宿主上的服务，比如查询自身信息、上报日志、挂载持久卷。但宿主地址对沙箱是拦截的，怎么办？
- 约定一个固定的“orchestrator 地址”`192.0.2.1`：为什么选文档保留地址段。
- 宿主 PREROUTING 上的三条 REDIRECT：
  - 80 → 5010：hyperloop。
  - 111 → 5012：portmap。
  - 2049 → 5011：NFS 代理。
- 这些包为什么能过 nftables：`192.0.2.1` 在预置放行集合里。
- 这三个服务各做什么（简介）。
- 一张“谁连谁、走哪个端口、由谁做转换”的总表，把第 16～19 篇的所有 REDIRECT、DNAT、SNAT 汇总在一起。

## 第五部分　规模、运维与这套环境的改动

### 第 20 篇　槽位池、复用与快照回滚下的 conntrack

- 为什么要预先建好网络：建一个槽位要做十几步系统调用，沙箱等不起。
- 槽位池的两条队列，以及本环境补丁的改动：
  - 新建队列：上游 32，补丁改成 300。
  - 复用队列：上游 100，补丁改成 1000。
  - 取用的优先级、归还的流程。
- 槽位编号存在哪：
  - 本环境 `ENVIRONMENT=local`，用 StorageLocal，以 `/var/run/netns` 目录本身作为分配表。
  - 与多节点时用 Consul KV 的对比（简介）。
- 复用一个槽位时要复位什么：用户防火墙规则；以及哪些东西不会被复位。
- 快照回滚，本环境新增的能力：
  - 回滚后，客户机“忘了”它的连接，而且 TCP 序列号倒退了。
  - 内核里两张 conntrack 表（命名空间里的和宿主的）还记着旧连接，于是把新包判为无效、直接丢弃，表现为连接卡死而不是报错。
  - 补丁的做法：在新 Firecracker 恢复之前，把命名空间和宿主两边属于这个沙箱的 conntrack 记录清掉；句柄在建网时预先打开（呼应第 12 篇）。
  - 代理层的配合：回滚窗口内的请求立刻返回明确错误；跨越回滚的旧连接要识别出来。

### 第 21 篇　部署脚本里的网络配置：build.sh 的 -d、-i、-s

- `-i`（安装）对网络做了什么：
  - 安装 dnsmasq。
  - 写入 `*.e2b.app` 的两条配置。
  - 给 SDK 打补丁。
- `-s`（启动部署）对网络做了什么，按执行顺序：
  1. `start-client.sh` 改 `/etc/resolv.conf`，加 Consul 转发，并调网络相关的 sysctl（`somaxconn`、`netdev_max_backlog`、`tcp_max_syn_backlog`）。
  2. `init-client.sh` 确保 `net.ipv4.ip_forward=1`。它必须在建槽位池之前生效，因为新命名空间的 `ip_forward` 是创建那一刻从宿主继承的；openEuler 自带的 `/etc/sysctl.conf` 会把它压回 0。
  3. 往 `/etc/hosts` 加 `harbor`。
  4. 用 nomad 启动 orchestrator 和 template-manager。
  5. 最后加 80→3002 的两条 iptables 规则。
- `-d`（停止）对网络做了什么：
  - 优雅停止，让 orchestrator 自己拆掉池里的网络。
  - 识别“在用”的槽位（命名空间里还有进程）并绕开。
  - 只清 `ns-<数字>` 和 `e2bv-<数字>`，不误删 docker、cni 等别人的网卡。
  - 用 `iptables-restore --noflush` 批量删除源地址在 Host 池里的残留规则，因为逐条删上万条要几个小时。
  - `--recycle-netns`：只回收沙箱网络，不重启其他组件。
- 配置项总表，每项说明默认值、本环境的值、作用、改了会影响全景图的哪一段：
  - `.env` 里的 `SANDBOXES_HOST_NETWORK_CIDR`、`SANDBOXES_VRT_NETWORK_CIDR`、`ALLOW_SANDBOX_INTERNET`、`ENVIRONMENT`。
  - `template-manager.hcl` 里的 `E2B_FC_NETNS_EXEC_HELPER`。
  - 各内部端口：5007、5010～5012、5016～5018、49983、3002。
  - `SANDBOX_ORCHESTRATOR_IP`
- 与 AgentENV 同机部署时的网络冲突，以及这套环境的对策：
  - 网段改成 10.13/10.14。
  - 网卡前缀改成 `e2bv-`。
  - 80 端口规则只截本机流量。
  - 两边共用的 resolv.conf 和 ip_forward。
- 改网段或前缀时要动哪几处、要注意什么：不能和内网重叠、两段不能互相重叠、已运行的沙箱怎么办。

### 第 22 篇　全景、排障与安全

- 一次完整往返的复盘，把前 21 篇串起来：
  1. SDK 创建沙箱。
  2. 在沙箱里 `pip install`。
  3. 在沙箱里起一个网页，宿主上用浏览器打开。
  4. 包怎么走、每一层谁在起作用。
- 排查思路：按“DNS → 入口 iptables → 代理 → 槽位 → 命名空间内”分层定位。
- 常用工具，只介绍看什么、怎么读输出：
  - `ip netns exec ns-N ...`
  - `nft list ruleset`
  - `iptables -t nat -S`
  - `conntrack -L`
  - `dig`
  - `tcpdump` 抓哪块网卡
- 常见问题速查表，每条给出现象、原因、看哪里：
  - 沙箱上不了网。
  - 沙箱解析不了域名。
  - 某个域名被拦。
  - SDK 第一条命令慢 15 秒。
  - 访问沙箱 URL 返回 502 或“端口未开放”。
  - 服务只监听 localhost。
  - 槽位耗尽。
  - iptables 规则越来越多、越来越慢。
  - 重启后入口规则丢失。
  - 回滚后连接卡死。
- 安全回顾：
  - 每一层分别挡住了什么：沙箱互访、访问宿主与内网、访问元数据服务、用域名绕过、连接数滥用。
  - 还剩哪些风险：DNS 直连外部、UDP 默认放行、单机明文 http。
