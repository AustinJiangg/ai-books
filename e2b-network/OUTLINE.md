# 大纲

**读者**：会一点编程、用过命令行，但没系统学过计算机网络和 Linux 内核网络的新手。
**目的**：花几个小时读完，把 E2B 沙箱从客户机网卡到公网入口的整套网络栈看明白：每一层为什么这样设计，配置项都管什么。只读不练，不安排动手实验。
**写法**：从现实问题出发，先讲“为什么需要”，再讲“是什么”，最后讲“E2B 怎么做、坑在哪”。多用生活类比和文字图，每篇末尾有“本篇小结”表格。
**代码**：只放简短的示例片段，包括简化后的 Go 代码、`ip`/`iptables`/`nft` 命令和规则片段，用来帮助理解，不追求完整可运行，也不需要读者自己核对。
**版本**：以 [e2b-dev/infra](https://github.com/e2b-dev/infra) tag `2026.30` 为准，默认讲当前默认的数据路径 `NETWORK_VERSION=1`；新的 nftables 数据路径 v2 单独放在第 13 篇。
**约定**：深度对齐本仓库《mmap 从零讲透》《MMIO 从零讲透》。与本仓库其他书重叠的内容只简要回顾，并给出链接：
- 《彻底搞懂 Firecracker》：virtio-net、tap、MMDS。
- 《e2b 服务端基础设施技术手册》：第 07、35、36、53～55 篇是代码级讲解。

本书把那些代码级内容讲成新手能读懂的版本，不逐行读源码。
**规模**：15 篇，每篇约 3500～5500 字，合计约 6.5 万字。

## 第一部分　打地基：够用的网络知识

### 第 1 篇　从一行 `curl` 说起：沙箱网络要解决什么问题

- 场景：AI 在沙箱里执行 `curl example.com`、`pip install`，开发者在浏览器里打开沙箱里跑着的网页，这些包都走了哪条路？
- E2B 是什么：用 Firecracker microVM 跑不受信任的代码，一台宿主机上同时跑成百上千个沙箱（链接《e2b 服务端基础设施技术手册》第 00 篇）。
- 沙箱网络的四个方向：
  - 出站：沙箱访问互联网。
  - 入站：用户访问沙箱里的端口。
  - 控制：orchestrator 调用沙箱里的 envd。
  - 内部服务：沙箱访问宿主上的 hyperloop、NFS。
- 设计目标与威胁模型：
  - 隔离：沙箱之间互不可见。
  - 保护宿主和云内网：沙箱不能访问元数据服务 `169.254.169.254` 和内网地址。
  - 可控出站：可以按网段、按域名放行或拦截。
  - 启动快：毫秒级拿到一套网络。
- 一张全景图：客户机 → tap → 网络命名空间 → veth → 宿主 → 网卡 → 互联网；以及反方向的 client-proxy → orchestrator proxy → 沙箱。
- 本书路线图：每一部分回答全景图上的哪一段。

### 第 2 篇　网络基础速成：IP、子网、路由、端口与 DNS

- IP 地址是“门牌号”，端口是“房间号”；TCP 和 UDP 的区别（打电话和寄明信片）。
- 子网与掩码：`/16`、`/30`、`/31`、`/32` 分别是多大一块；为什么 E2B 会同时用到这四种。
- 几类特殊地址：
  - 私有地址：10/8、172.16/12、192.168/16。
  - 环回地址：127/8。
  - 链路本地地址：169.254/16，包括云元数据服务的地址。
  - 运营商级 NAT 地址：100.64/10。
- 路由表：包按“最长前缀匹配”找下一跳；默认路由和默认网关。
- 一次 TCP 连接的生命周期：三次握手、数据、挥手；“连接”在两端各有一份状态。
- DNS：域名怎么变成 IP；为什么“按域名过滤”比“按 IP 过滤”难（第 10 篇伏笔）。
- HTTP 的 `Host` 头和 TLS 的 SNI：在加密之前，连接里还能看到“想访问哪个域名”。

### 第 3 篇　Linux 网络的积木：网卡、命名空间、veth 与 tap

- 内核眼中的“网卡”：物理网卡、环回网卡和各种虚拟网卡都是一个“接口”。
- 网络命名空间（netns）：一台机器上开出多套互相看不见的网络，各自有网卡、路由表和防火墙规则（类比公寓楼里的独立套间）。
- veth 对：一根两头的虚拟网线，一头放进命名空间，一头留在宿主。
- tap 设备：一头是网卡，一头是文件描述符；用户态程序（Firecracker）通过读写它来收发以太网帧。
- 路由、转发与 `ip_forward`：宿主什么时候会帮别人转包。
- 为什么 E2B 用“路由 + NAT”而不是“网桥”把沙箱接起来（回顾，链接《e2b 服务端基础设施技术手册》第 07 篇）。
- 读懂几条命令的输出：`ip addr`、`ip route`、`ip netns list`（直接给出示例输出并解释，不要求动手）。

### 第 4 篇　Netfilter 入门：iptables、nftables、NAT 与 conntrack

- 内核里的“安检口”：包经过的几个钩子点（PREROUTING、FORWARD、POSTROUTING 等）。
- 表与链：filter、nat、mangle 各管什么；规则从上往下匹配。
- NAT 的几种形态：
  - SNAT：换源地址。
  - MASQUERADE：自动用出口网卡的地址做 SNAT。
  - DNAT：换目的地址。
  - REDIRECT：改送到本机某个端口。

  这几种分别用快递改寄件人、改收件人、转给前台来类比。
- conntrack 连接跟踪：NAT 只对一条连接的第一个包查规则，后面的包按记录改写；`ESTABLISHED/RELATED` 是什么意思。
- iptables 与 nftables：新旧两套前端、同一个 Netfilter；集合（set）为什么让大规模规则更快。
- E2B 同时用到两者：命名空间里的过滤用 nftables，NAT 与重定向用 iptables（v2 的变化见第 13 篇）。

## 第二部分　一个沙箱的网络栈

### 第 5 篇　虚拟机怎么上网：Firecracker、virtio-net 与客户机网卡

- 客户机里的 `eth0` 是 virtio-net 网卡，背后是宿主上的 tap 设备，Firecracker 在中间搬运数据（回顾，链接《彻底搞懂 Firecracker》网络篇）。
- orchestrator 通过 Firecracker API 配置网卡：指定 tap 名、客户机 MAC；网卡限速器（rate limiter）。
- 客户机的 IP 从哪来：内核启动参数 `ip=`，不跑 DHCP；默认 DNS 服务器 `8.8.8.8`。
- MMDS：Firecracker 内置的元数据服务，在客户机里地址是 `169.254.169.254`；envd 为什么要给它“钉”一条规则。
- 客户机这一侧的视角：在沙箱里执行 `ip addr`、`ip route` 会看到什么。

### 第 6 篇　快照带来的难题：为什么每个沙箱都是 169.254.0.21

- E2B 的沙箱从不冷启动，而是从模板快照恢复（链接《e2b 服务端基础设施技术手册》第 27 篇）。
- 快照把客户机的网络配置也一起冻住：所有沙箱的 IP 都是 `169.254.0.21`，网关都是 `169.254.0.22`，MAC 也完全一样。
- 如果把它们直接接到同一个网络里会怎样：地址冲突、ARP 混乱。
- 解法：每个沙箱一个网络命名空间，命名空间里地址都一样，靠 NAT 在出口把它们“翻译”成各不相同的地址。
- 槽位（slot）的概念：一个编号，对应一个命名空间、一组网卡和一组地址。
- 小结：E2B 网络设计的几乎所有选择，都源自“快照里的地址改不了”这一点。

### 第 7 篇　一个槽位的完整拓扑：几个地址、几块网卡

- 一个槽位里有哪些东西：
  - 命名空间 `ns-<编号>`。
  - 命名空间里的 `tap0`，地址 `169.254.0.22/30`。
  - 客户机地址 `169.254.0.21`。
  - veth 对：宿主侧 veth、命名空间侧 vpeer，取自 `10.12.0.0/16` 中的一个 `/31`。
  - 宿主可见的沙箱地址 Host IP：取自 `10.11.0.0/16` 的一个 `/32`。
- 槽位编号怎么算出这些地址：一个例子从编号 5 推出全部地址。
- 建网的步骤，用简化的 Go 代码和等价的 `ip` 命令对照着讲：
  1. 建命名空间。
  2. 建 veth 对并把一头移进命名空间。
  3. 配地址。
  4. 建 tap。
  5. 加路由。
  6. 加 NAT 规则。
  7. 加宿主侧规则。
- 一张文字拓扑图，把地址、网卡、规则全部标上。
- 删除槽位时要拆掉哪些东西；拆不干净会留下什么问题。

### 第 8 篇　包的旅程：出站与回程一步步走

- 出站：沙箱里 `curl` 发出的第一个包，按下面的顺序走完全程，每一跳都写出包头里的源和目的地址怎么变：
  1. 客户机 `eth0`。
  2. Firecracker。
  3. `tap0`。
  4. 命名空间路由。
  5. 命名空间内的 SNAT，`169.254.0.21` 变成 Host IP。
  6. vpeer。
  7. veth。
  8. 宿主路由。
  9. FORWARD 放行。
  10. MASQUERADE，换成宿主网卡地址。
  11. 物理网卡。
  12. 互联网。
- 回程：回包怎么靠两层 conntrack 记录一路被“翻译”回去，找到正确的沙箱。
- 宿主访问沙箱：发往 Host IP 的包在命名空间入口被 DNAT 回 `169.254.0.21`；这是后面入站和控制通道的基础。
- 一张“地址变化表”：每一跳的源地址、目的地址。
- 常见误区：为什么在宿主上 `ping 169.254.0.21` 不通，而 `ping` Host IP 能通。

## 第三部分　管住出站流量

### 第 9 篇　出站防火墙（一）：按网段放行与拦截

- 默认拦截哪些地址：私有网段、环回、链路本地（含云元数据服务）、CGNAT、IPv6 本地地址；为什么要拦。
- 用户能配什么：
  - `allow_internet_access=false`：等同于把 `0.0.0.0/0` 加入拦截。
  - `allowOut`：放行列表。
  - `denyOut`：拦截列表。

  允许优先于拒绝。
- 命名空间里的 nftables 链，规则按以下顺序匹配，每条规则用一句话解释它防什么：
  1. 已建立连接放行。
  2. 预置放行。
  3. 预置拦截。
  4. 用户放行。
  5. 用户拦截。
  6. 默认放行。
- 为什么网段规则只管 TCP 以外的流量：TCP 另走代理（第 10 篇）。
- 运行中修改规则：更新网络配置的 API；规则集整体替换、一次原子提交的意义。
- 完全断网模式（DenyEgress）：连宿主的内部服务也不让访问，什么时候用。
- 非 DNS 的 UDP 流量：计数或丢弃两种模式简介。

### 第 10 篇　出站防火墙（二）：按域名过滤与 TCP 防火墙代理

- 只看 IP 为什么不够：一个 IP 上住着很多网站，CDN 的 IP 还经常变。
- 只看 DNS 为什么也不够：客户机可以绕过 DNS，直接连 IP。
- E2B 的做法：沙箱的出站 TCP 被 iptables REDIRECT 到宿主上的 TCP 防火墙代理，按端口分 HTTP、TLS、其他三类。
- 代理怎么知道目标域名：HTTP 看 `Host` 头，TLS 看 SNI；不解密也能拿到域名。
- 判定流程：
  - 域名匹配 `allowOut`：放行。
  - 没有域名的连接（如 `https://1.1.1.1`）退回到按 IP 判定。
  - 通配符 `*.example.com` 的匹配规则。
- 代理放行后要自己去连目标：重新解析域名、防止 DNS 重绑定到内网地址。
- 域名级请求改写（`rules` 的 header 注入）：为什么需要沙箱信任一份 CA 证书；风险提示。
- 自带 SOCKS5 出口代理（egressProxy，BYOP）：过滤之后再通过用户的代理出去，沙箱本身不感知。
- 小结：网段过滤和域名过滤分工的对照表。

## 第四部分　入站与内部通道

### 第 11 篇　从公网访问沙箱：URL、client-proxy 与 orchestrator proxy

- 一个沙箱 URL 长什么样：`<端口>-<沙箱ID>.<域名>`；也可以用 `E2b-Sandbox-Id`、`E2b-Sandbox-Port` 请求头指定。
- 请求的全路径：
  1. 负载均衡。
  2. client-proxy：按沙箱 ID 查目录，得知沙箱在哪个节点。
  3. 节点上的 orchestrator proxy，端口 5007。
  4. 沙箱的 Host IP 加端口。
  5. DNAT 到 `169.254.0.21`。
  6. 客户机里的服务。
- 连接复用与沙箱“换人”：为什么连接池要按沙箱的生命周期区分（链接《e2b 服务端基础设施技术手册》第 36 篇）。
- 访问控制：`allowPublicTraffic` 与访问令牌；`maskRequestHost` 改写 Host 头；`httpsPorts` 让代理用 HTTPS 连沙箱里的服务。
- 服务只监听 `localhost` 怎么办：envd 的端口转发，把 `169.254.0.21` 上的端口转到客户机的环回地址。
- 沙箱暂停时的请求：自动恢复（简介）。

### 第 12 篇　沙箱与宿主之间：envd、hyperloop、NFS 与 portmap

- 控制通道：orchestrator 通过 Host IP 连客户机里的 envd（端口 49983），调用 `/init`、执行命令、读写文件；访问令牌怎么交给沙箱（简介，链接《e2b 服务端基础设施技术手册》第 36 篇）。
- 反方向：沙箱访问宿主上的服务，统一访问一个固定的“orchestrator 地址”，在宿主侧被 REDIRECT 到不同端口：
  - 80 → hyperloop（沙箱查询自身信息、上报日志）。
  - 111 → portmap。
  - 2049 → NFS 代理（持久卷）。
- 为什么这些目的地要预置放行，以及断网模式下它们为什么也被切断。
- 健康检查走哪条路。
- 一张“谁连谁、走哪个端口、谁做转换”的对照表。

## 第五部分　规模、配置与全景

### 第 13 篇　槽位池与规模化：预建、复用、清理与网络 v2

- 为什么要预先建好网络：建一个槽位要几十毫秒，沙箱等不起。
- 槽位池：新建队列与复用队列；取用与归还；容量上限怎么由地址段推出来。
- 复用时要复位什么：防火墙规则、自定义规则、DSCP 标记；conntrack 残留为什么危险，以及归还时序。
- 槽位编号的分配与持久化：本地以 `/var/run/netns` 为准；启动时回收上一次进程遗留的网络。
- 出站流量打 DSCP 标记：给沙箱流量分优先级（简介）。
- 网络 v2：
  - 把宿主侧大量逐槽位的 iptables 规则换成 nftables 集合元素。
  - 命名空间内 NAT 也改用 nftables。
  - 可选的 eBPF 计数。
  - 为什么还是灰度开启；从 v1 切到 v2、再回滚的注意事项。

### 第 14 篇　网络配置一览：用户侧 API 与运维侧参数

- 用户侧，即创建或更新沙箱时可以填的网络配置，逐项说明作用、默认值和常见用法：
  - `allow_internet_access`
  - `network.allowOut`
  - `network.denyOut`
  - `network.rules`
  - `network.egressProxy`
  - `network.allowPublicTraffic`
  - `network.maskRequestHost`
  - `network.httpsPorts`
- 几个典型配置示例：
  - 完全断网。
  - 只允许访问 PyPI 和某个 API。
  - 禁止公网访问沙箱 URL。
  - 走企业代理出网。
- 运维侧，即部署 orchestrator 时可以调的参数：
  - 地址段：`SANDBOXES_HOST_NETWORK_CIDR`、`SANDBOXES_VRT_NETWORK_CIDR`。
  - 各内部服务端口：proxy、hyperloop、portmap、NFS 代理、TCP 防火墙三个端口。
  - `NETWORK_VERSION`、`SANDBOX_EGRESS_DSCP` 等。
- 改这些参数时要注意什么：与云内网地址冲突、多节点一致性、已运行的沙箱不受影响。
- 一张总表：配置项 → 影响全景图上的哪一段。

### 第 15 篇　全景、排障与安全

- 一次完整往返的复盘，把前 14 篇串起来：
  1. 用户浏览器访问沙箱里的网页。
  2. 网页的后端代码 `curl` 一个外部 API。
  3. 响应原路返回。
- 排查思路和常用工具（只介绍看什么、怎么读输出，不要求动手）：
  - `ip netns exec`
  - `nft list ruleset`
  - `iptables -t nat -L`
  - `conntrack -L`
  - `tcpdump` 抓哪块网卡
- 常见问题汇总表，每条给出现象、原因、看哪里：
  - 沙箱上不了网。
  - 某个域名被拦。
  - 访问沙箱 URL 返回 502。
  - 服务只监听 localhost。
  - 槽位耗尽。
  - 复用后串连接。
- 安全回顾：
  - 每一层分别挡住了什么攻击：访问元数据服务、横向访问其他沙箱、DNS 重绑定、带宽滥用。
  - 还剩哪些风险。
- 和其他方案的简单对比：Docker 默认网桥、gVisor 网络栈、Kubernetes CNI 各自的思路。
- 术语表（中英对照）与延伸阅读。
