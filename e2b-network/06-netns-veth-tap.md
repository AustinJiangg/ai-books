# 第 6 篇｜Linux 虚拟网络的积木：网络命名空间、veth 与 tap

> **本篇目标**：认识 Linux 内核提供的三块“虚拟网络积木”：**网络命名空间**（在一台机器里开出多套互相隔离的网络）、**veth 对**（一根两头的虚拟网线）、**tap 设备**（让用户态程序收发以太网帧的虚拟网卡）。E2B 每个沙箱的网络都是用这三块积木搭出来的。读完本篇，再看 `ip netns`、`ip link` 的输出就不会发怵了。

---

## 一、内核眼中的“网卡”

在 Linux 内核眼里，“网卡”不一定是一块插在主板上的硬件。凡是能收发数据包的东西，都可以是一个**网络接口**（interface）：

| 类型 | 例子 | 背后是什么 |
|---|---|---|
| 物理网卡 | `enp125s0f0`、`eth0` | 真实的网卡硬件 |
| 环回网卡 | `lo` | 内核自己，发给它的包立刻转回本机 |
| veth | `e2bv-5` | 一根虚拟网线的一头 |
| tap | `tap0` | 一个用户态程序 |
| 网桥 | `docker0`、`virbr0` | 内核里的一台虚拟交换机 |

不管背后是什么，它们对上层都一样：有名字、有 MAC 地址、能配 IP、能出现在路由表里、能被防火墙规则匹配。这种统一性，正是能用软件“搭”出任意网络拓扑的基础。

## 二、网络命名空间：一栋楼里的独立套间

### 2.1 问题

一台宿主机上跑着几百个沙箱。我们希望每个沙箱看到的网络环境是**独立**的：

- 有自己的网卡。
- 有自己的路由表。
- 有自己的防火墙规则。
- 看不见别的沙箱的网卡，更连不上。

如果所有沙箱的网卡都堆在宿主机的同一个网络环境里，规则会写得极其复杂，还容易出错。

### 2.2 网络命名空间

Linux 的答案是**网络命名空间**（network namespace，简称 netns）。一个网络命名空间就是**一整套独立的网络栈**，包括：

- 一组网卡，至少有一个自己的 `lo`。
- 一张路由表。
- 一套 iptables / nftables 规则。
- 一张连接跟踪表（第 7 篇）。
- 一套网络相关的内核参数，比如 `ip_forward`。
- 一组端口：在 A 命名空间监听 80 端口，不影响 B 命名空间也监听 80 端口。

可以把宿主机想象成一栋公寓楼，每个网络命名空间是一间**独立的套间**：各有各的门牌、水电、门锁，邻居之间互相看不见。宿主机本身的网络环境也是一个命名空间，叫**初始命名空间**（或“宿主机命名空间”）。

### 2.3 一块网卡只能在一个命名空间里

一个关键规则：**一块网卡同一时间只属于一个命名空间**。把一块网卡“移进”某个命名空间，它就从原来的地方消失了。

这意味着：命名空间之间默认**完全不通**。要让它们通信，得专门搭一根“线”，下一节的 veth 就是这根线。

### 2.4 命名空间靠什么“活着”

命名空间不是一个文件，也不是一个进程，它是内核里的一个对象。只要还有东西**引用**它，它就存在。引用它的可以是：

- 一个在这个命名空间里运行的**进程**。
- 一个打开着的**文件描述符**。
- 一个**挂载点**：`ip netns add ns-5` 会在 `/var/run/netns/ns-5` 创建一个文件，并把命名空间“挂”在上面。

E2B 的 orchestrator 建好命名空间后，会立刻关掉自己手里的文件描述符（第 12 篇）。之后一个空闲的命名空间只靠 `/var/run/netns/ns-<编号>` 这个挂载点活着，等沙箱用上它时，里面才会有 Firecracker 进程。

这个细节在运维时很有用。这套环境的清理脚本判断一个命名空间“是否在用”的方法，就是看它里面有没有进程（第 21 篇）。

### 2.5 常用命令

```bash
ip netns list                       # 列出所有命名空间（即 /var/run/netns 下的条目）
ip netns add ns-5                   # 新建一个命名空间
ip netns exec ns-5 ip addr          # 在 ns-5 里执行 ip addr
ip netns pids ns-5                  # 列出在 ns-5 里运行的进程
ip netns delete ns-5                # 删除（去掉挂载点）
```

`ip netns exec` 是最常用的：它让一条命令“进入”某个命名空间去执行，看到的就是那个命名空间里的网卡和路由。

## 三、veth 对：一根两头的虚拟网线

### 3.1 它是什么

**veth**（virtual ethernet）总是**成对**出现。一对 veth 就像一根网线的两头：从一头发进去的包，立刻从另一头出来。

```
   veth A  ════════════════════  veth B
（发进去的包）               （从这里出来）
```

它的妙处在于：**两头可以放在不同的命名空间里**。一头留在宿主机，一头放进沙箱的命名空间，两个原本隔绝的网络就有了一条通道。

### 3.2 创建和摆放

```bash
# 创建一对 veth：e2bv-5 和 eth0
ip link add e2bv-5 type veth peer name eth0

# 把 eth0 这头移进命名空间 ns-5
ip link set eth0 netns ns-5

# 两头分别配地址、启用
ip addr add 10.14.0.10/31 dev e2bv-5
ip link set e2bv-5 up
ip netns exec ns-5 ip addr add 10.14.0.11/31 dev eth0
ip netns exec ns-5 ip link set eth0 up
```

完成后：

```
┌──── 宿主机 ────┐                ┌──── ns-5 ────┐
│                │                │              │
│  e2bv-5        │════ veth ══════│  eth0        │
│  10.14.0.10/31 │                │ 10.14.0.11/31│
└────────────────┘                └──────────────┘
```

两头的地址在同一个 `/31` 里（第 2 篇），彼此是“直连”的邻居。

### 3.3 两头名字可以不同，同名也不冲突

注意命名空间里那一头叫 `eth0`。宿主机上可能也有一块叫 `eth0` 的物理网卡，但它们在**不同的命名空间**里，互不冲突，就像两个套间里都可以有一个叫“卧室”的房间。

E2B 的实际命名：

- 宿主机那一头：上游叫 `veth-<编号>`，这套环境的补丁改成了 `e2bv-<编号>`（原因见第 11 篇）。
- 命名空间那一头：一律叫 `eth0`，代码里称它为 **vpeer**。

## 四、tap 设备：一头是网卡，一头是程序

### 4.1 虚拟机的网卡要接到哪里

Firecracker 虚拟机里有一块网卡。虚拟机发出的数据，最终是由宿主机上的 Firecracker **进程**拿到的，这只是一个普通的用户态程序。它拿到数据后，要交给宿主机的内核网络栈，才能继续往外走。

那么问题是：一个普通程序，怎么把以太网帧“塞进”内核的网络栈，又怎么从内核那里接收发给虚拟机的帧？

### 4.2 tap 设备

**tap 设备**就是为此设计的。它有两面：

- **对内核来说**，它是一块普通网卡（比如叫 `tap0`），可以配 IP、出现在路由表里，和别的网卡没区别。
- **对用户态程序来说**，它是一个**文件描述符**。程序打开 `/dev/net/tun` 并绑定到 `tap0` 之后：
  - 往这个文件描述符里 `write` 一个以太网帧，内核就认为 `tap0` 这块网卡“收到”了一个帧。
  - 内核从 `tap0` 往外“发”的帧，程序 `read` 这个文件描述符就能读到。

```
                  write(帧)
 Firecracker ─────────────────►  tap0 （内核网卡）──► 内核网络栈
 （用户态进程）◄──────────────────  tap0            ◄── 内核网络栈
                  read(帧)
```

于是，Firecracker 只要在“虚拟机的网卡”和“tap 的文件描述符”之间来回搬帧，虚拟机就等于接上了宿主机的网络（第 9 篇详讲）。

### 4.3 tun 与 tap 的区别

和 tap 一起出现的还有 **tun** 设备，二者的区别只有一点：

| | tun | tap |
|---|---|---|
| 收发的单位 | IP 包（第三层） | 以太网帧（第二层，带 MAC） |
| 典型用途 | VPN | 虚拟机 |

虚拟机的网卡模拟的是真实的以太网卡，它要处理 MAC 地址、要做 ARP，所以必须用 **tap**。

### 4.4 tap 必须和 Firecracker 在同一个命名空间

程序打开 tap 设备时，是**按名字**找的，而且只能找到**自己所在命名空间**里的网卡。E2B 的每个命名空间里都有一块叫 `tap0` 的设备，所以：

- Firecracker 进程必须**运行在沙箱的命名空间里**，才能打开**那个**命名空间的 `tap0`。
- 每个命名空间的 tap 都可以叫 `tap0`，名字不冲突，所有沙箱的配置都一样，正好配合快照（第 10 篇）。

上游 E2B 用 `ip netns exec ns-5 firecracker ...` 把 Firecracker 放进命名空间。这套环境的补丁改用一个更轻的小工具 `fc-netns-exec`（第 9 篇）。

## 五、把积木连起来：两种思路

有了命名空间、veth、tap，怎么把几百个沙箱接到外网？主流有两种思路。

### 5.1 思路一：网桥（虚拟交换机）

建一个**网桥**，把所有沙箱的 veth 都插上去，就像把所有电脑接到同一台交换机上：

```
沙箱1 ─veth─┐
沙箱2 ─veth─┼── 网桥 docker0 ──（NAT）── 物理网卡
沙箱3 ─veth─┘
```

Docker 默认就是这么做的。好处是简单。缺点是：所有沙箱处在**同一个二层网络**里，能互相 ARP、互相访问，要隔离还得另加规则；而且每个沙箱都必须有**不同的** IP 和 MAC。

### 5.2 思路二：路由 + NAT（点对点）

不用网桥。每个沙箱用**自己专属的一对 veth** 接到宿主机，宿主机用**路由表**决定包往哪走，再用 **NAT** 做地址转换：

```
沙箱1 ═veth═ 宿主机 ═veth═ 沙箱2
                │
          路由 + NAT
                │
             物理网卡
```

每个沙箱都是一条独立的点对点链路，彼此天然不在同一个二层网络里，看不见对方的 ARP。

E2B 选的是思路二。第 11 篇会解释为什么：最根本的原因是 E2B 的沙箱**无法拥有不同的 IP 和 MAC**（第 10 篇）。

## 六、读懂几条命令的输出

### 6.1 列出命名空间

```
$ ip netns list
ns-302
ns-301
...
ns-3
ns-2
```

这套环境里，E2B 的命名空间都叫 `ns-<编号>`，编号从 2 开始（第 20 篇解释为什么）。

### 6.2 看一个命名空间里有什么

```
$ ip netns exec ns-5 ip addr
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 ...
    inet 127.0.0.1/8 scope host lo
2: eth0@if1234: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 ...
    link/ether 9e:21:4b:7f:10:02 brd ff:ff:ff:ff:ff:ff link-netnsid 0
    inet 10.14.0.11/31 scope global eth0
3: tap0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 ...
    link/ether 3a:7d:52:c1:09:e4 brd ff:ff:ff:ff:ff:ff
    inet 169.254.0.22/30 scope global tap0
```

- `lo`：命名空间自己的环回网卡。
- `eth0@if1234`：veth 的命名空间一头（vpeer），对端是宿主机上编号 1234 的网卡，也就是 `e2bv-5`。
- `tap0`：给 Firecracker 用的 tap 设备，地址 `169.254.0.22/30`，这是客户机眼中的网关。

这三块网卡，加上一张路由表和几条防火墙规则，就是一个沙箱网络的全部家当。第 11 篇会把它画成完整的拓扑图。

### 6.3 看宿主机上的 veth

```
$ ip -br link show type veth
e2bv-2@if2     UP   ...
e2bv-3@if2     UP   ...
e2bv-5@if2     UP   ...
```

`-br` 是简洁输出。每个 `e2bv-N` 对应一个沙箱网络槽位。`@if2` 表示对端在各自命名空间里的编号都是 2：每个命名空间里先有 `lo`（编号 1），再有 `eth0`（编号 2）。

## 本篇小结

| 概念 | 一句话解释 |
|---|---|
| 网络接口 | 内核里能收发包的“网卡”，可以是硬件，也可以是纯软件 |
| 网络命名空间 | 一整套独立的网络栈：网卡、路由、防火墙、连接跟踪、内核参数 |
| 初始命名空间 | 宿主机本身的网络环境 |
| 命名空间的生命 | 靠进程、文件描述符或 `/var/run/netns/` 下的挂载点维持 |
| `ip netns exec` | 在指定命名空间里执行命令 |
| veth 对 | 一根两头的虚拟网线，两头可放在不同命名空间 |
| vpeer | E2B 对命名空间里那一头 veth（`eth0`）的称呼 |
| tap 设备 | 对内核是网卡，对程序是文件描述符，收发以太网帧 |
| tun vs tap | tun 收发 IP 包，tap 收发以太网帧；虚拟机用 tap |
| tap 与命名空间 | 程序只能打开自己所在命名空间里的 tap，所以 Firecracker 要住进沙箱命名空间 |
| 网桥 vs 路由 | 网桥把大家放进同一个二层网络；路由 + NAT 给每人一条点对点链路，E2B 选后者 |
