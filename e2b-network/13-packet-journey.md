# 第 13 篇｜包的旅程：出站、回程与宿主访问沙箱

> **本篇目标**：放几个包进刚建好的槽位，跟着它们走完全程。读完本篇，你会清楚地知道：沙箱里的一个 UDP 包（比如 DNS 查询）怎么经过两次地址转换到达互联网、回包又怎么准确地找回来；沙箱里的一个 TCP 连接为什么“走另一条路”；宿主机上的 orchestrator 又是怎么连进沙箱的。每一跳的源地址、目的地址都会写清楚。

本篇沿用槽位 5 的地址：

| 名称 | 地址 |
|---|---|
| 客户机 | `169.254.0.21` |
| tap0 | `169.254.0.22` |
| vpeer（命名空间里的 `eth0`） | `10.14.0.11` |
| `e2bv-5`（宿主机侧 veth） | `10.14.0.10` |
| Host IP | `10.13.0.5` |
| 宿主机物理网卡 `enp125s0f0` | `192.168.10.23` |

---

## 一、旅程一：一个 UDP 包去往 8.8.8.8

先看最“标准”的一条路：沙箱里的程序向 `8.8.8.8` 发一个 DNS 查询（UDP 53 端口）。之所以先讲 UDP，是因为它会完整地走一遍两次 NAT，没有任何捷径。

### 1.1 去程

**第 1 跳：客户机内部。** 客户机查路由表，`8.8.8.8` 不在本网段，交给默认网关 `169.254.0.22`。客户机内核把包交给 virtio-net 驱动。

```
源 169.254.0.21:41234   →   目的 8.8.8.8:53
```

**第 2 跳：Firecracker → tap0。** Firecracker 从共享队列取出帧，写进 `tap0`。包进入 `ns-5` 的网络栈。

**第 3 跳：`ns-5` 的 PREROUTING。** 先过 nftables 防火墙（优先级 -150）：

- 规则 1：这是一个新连接，不是 ESTABLISHED，不匹配。
- 规则 2：`8.8.8.8` 不在预置放行集合（只有 `192.0.2.1`）里，不匹配。
- 规则 3：`8.8.8.8` 不在预置拦截集合（私有和本地地址）里，不匹配。
- 规则 4、5：用户集合默认为空，不匹配。
- 默认策略：放行。

然后是 iptables 的 nat PREROUTING。这里只有一条“目的是 `10.13.0.5` 就 DNAT”的规则，不匹配。

**第 4 跳：`ns-5` 路由与转发。** 目的地 `8.8.8.8`，命中默认路由 `default via 10.14.0.10 dev eth0`。这个包不是给命名空间自己的，需要转发，经过 FORWARD。

**第 5 跳：`ns-5` 的 POSTROUTING——第一次 NAT。** 命中 SNAT 规则（从 `eth0` 出去、源是 `169.254.0.21`）：

```
源 169.254.0.21:41234   →   源 10.13.0.5:41234
```

`ns-5` 的 conntrack 表记下这条转换。

**第 6 跳：vpeer → `e2bv-5`。** 包从命名空间的 `eth0` 发出，从宿主机的 `e2bv-5` 冒出来。

```
源 10.13.0.5:41234   →   目的 8.8.8.8:53
```

**第 7 跳：宿主机的 PREROUTING。** 宿主机的 nat PREROUTING 链里有 6 条 `-i e2bv-5` 的 REDIRECT，但它们全都要求 `-p tcp`。这是 UDP 包，不匹配。

**第 8 跳：宿主机路由与转发。** 目的地 `8.8.8.8` 命中宿主机的默认路由，从 `enp125s0f0` 出去。这是转发，经过 filter FORWARD，命中 `-i e2bv-5 -o enp125s0f0 -j ACCEPT`，放行。

**第 9 跳：宿主机的 POSTROUTING——第二次 NAT。** 命中 MASQUERADE 规则（源是 `10.13.0.5/32`、从 `enp125s0f0` 出去）：

```
源 10.13.0.5:41234   →   源 192.168.10.23:41234
```

宿主机的 conntrack 表也记下一条。（如果这个源端口已被别的连接占用，MASQUERADE 还会顺带换一个端口，这里不展开。）

**第 10 跳：物理网卡 → 互联网。** 包带着宿主机的地址出门。再往后，如果机房出口还有一层 NAT，那是机房网络的事了。

### 1.2 回程

`8.8.8.8` 回了一个包：

```
源 8.8.8.8:53   →   目的 192.168.10.23:41234
```

**宿主机收到。** conntrack 一查：这是那条 MASQUERADE 连接的回包，于是把目的地址改回：

```
目的 192.168.10.23:41234   →   目的 10.13.0.5:41234
```

查路由，`10.13.0.5` 命中 `10.13.0.5 via 10.14.0.11 dev e2bv-5`。经过 FORWARD，命中 `-i enp125s0f0 -o e2bv-5 -j ACCEPT`，从 `e2bv-5` 送进命名空间。

**`ns-5` 收到。** 包从 `eth0` 进来。conntrack 一查：这是那条 SNAT 连接的回包，把目的地址改回：

```
目的 10.13.0.5:41234   →   目的 169.254.0.21:41234
```

查路由，`169.254.0.21` 在 `tap0` 所在的 `/30` 网段里，直接从 `tap0` 发出。Firecracker 读到这个帧，交给客户机。客户机里的程序收到了 DNS 回答。

注意：nftables 的规则都以 `iifname "tap0"` 开头，只检查**从客户机出来**的包。这个回包是从 `eth0` 进来的，不受这些规则影响。

### 1.3 地址变化一览

| 位置 | 方向 | 源地址 | 目的地址 |
|---|---|---|---|
| 客户机 → tap0 | 去 | 169.254.0.21:41234 | 8.8.8.8:53 |
| `ns-5` SNAT 后 | 去 | **10.13.0.5**:41234 | 8.8.8.8:53 |
| 宿主机 MASQUERADE 后 | 去 | **192.168.10.23**:41234 | 8.8.8.8:53 |
| 互联网回来 | 回 | 8.8.8.8:53 | 192.168.10.23:41234 |
| 宿主机 conntrack 改回后 | 回 | 8.8.8.8:53 | **10.13.0.5**:41234 |
| `ns-5` conntrack 改回后 | 回 | 8.8.8.8:53 | **169.254.0.21**:41234 |

两次转换，两张 conntrack 表，各管一段。正因为第一次转换把相同的 `169.254.0.21` 变成了各不相同的 Host IP，宿主机的 conntrack 才能分清回包属于哪个沙箱。这就是第 10 篇“出口换门牌”的实际效果。

## 二、旅程二：一个 TCP 连接去往 pypi.org

现在换成沙箱里执行 `pip install`，它要和 `pypi.org`（比如 `151.101.0.223`）的 443 端口建立 TCP 连接。

### 2.1 前半段一样

客户机 → `tap0` → nftables 放行 → SNAT 成 `10.13.0.5` → 从 `e2bv-5` 冒出来。和 UDP 完全一样：

```
源 10.13.0.5:51000   →   目的 151.101.0.223:443   （TCP SYN）
```

### 2.2 在宿主机门口被“截下”

宿主机 nat PREROUTING 链里这条规则命中了：

```bash
-A PREROUTING -i e2bv-5 -p tcp --dport 443 -j REDIRECT --to-port 5017
```

目的地址被改成了**本机**（REDIRECT 会改成包进来的那块网卡 `e2bv-5` 的地址，即 `10.14.0.10`），端口改成 5017：

```
目的 151.101.0.223:443   →   目的 10.14.0.10:5017
```

因为改的是 PREROUTING，路由判断看到的是新地址，于是判定这是一个**给本机的包**，走 INPUT，不再走 FORWARD。宿主机的 conntrack 记下了原始目的地址。

### 2.3 防火墙代理接手

orchestrator 里的 TCP 防火墙代理在 `0.0.0.0:5017` 上监听，接到了这个连接。它看到：

- 对方地址：`10.13.0.5:51000`。按 Host IP 一查，知道这是哪个沙箱。
- 通过 `SO_ORIGINAL_DST` 向内核要来原始目的地址：`151.101.0.223:443`。
- 读出 TLS 握手里的 SNI：`pypi.org`。

检查通过后，代理**自己**向 `pypi.org:443` 发起一个**全新的** TCP 连接，然后把两个连接对接起来，双向搬运数据。（具体判定规则见第 16 篇。）

### 2.4 两条连接

所以，沙箱里看似“一条”连接，实际上是**两条**：

```
连接①：  沙箱 10.13.0.5:51000  ⇄  代理 10.14.0.10:5017
        （沙箱以为自己连的是 151.101.0.223:443）

连接②：  宿主机 192.168.10.23:随机端口  ⇄  pypi.org 151.101.0.223:443
        （这是宿主机自己发起的普通连接）
```

连接② 是宿主机本机程序发出的，走 OUTPUT → POSTROUTING，源地址直接就是物理网卡的地址，**用不到**第 9 步那条 MASQUERADE，也用不到 FORWARD 放行规则。

所以第 12 篇说：宿主机上的 FORWARD 放行和 MASQUERADE，实际承载的是 **UDP、ICMP 等非 TCP 流量**；TCP 全都走代理。

### 2.5 回程

`pypi.org` 的数据从连接② 回到代理，代理写进连接①。连接① 的回包从宿主机发往 `10.13.0.5`，沿着路由进入命名空间，被 conntrack 改回 `169.254.0.21`，送进客户机。客户机看到的回包源地址是 `151.101.0.223:443`（宿主机 conntrack 会把 REDIRECT 反向改回），它完全不知道中间换过人。

## 三、旅程三：宿主机访问沙箱里的 envd

最后看反方向：orchestrator 要调用沙箱里 envd 的接口，它连接 `10.13.0.5:49983`。

### 3.1 去程

**宿主机。** orchestrator 发起连接。宿主机查路由，`10.13.0.5` 命中 `/32` 路由，从 `e2bv-5` 发出，下一跳 `10.14.0.11`。源地址怎么选？内核会选**出口网卡上的地址**，也就是 `10.14.0.10`。

```
源 10.14.0.10:38000   →   目的 10.13.0.5:49983
```

这是本机发出的包，走 OUTPUT。宿主机 PREROUTING 上的那些 REDIRECT 规则只匹配从 `e2bv-5` **进来**的包，与它无关。

**`ns-5`。** 包从 `eth0` 进来。nat PREROUTING 的 DNAT 规则命中：

```
目的 10.13.0.5:49983   →   目的 169.254.0.21:49983
```

查路由，从 `tap0` 发出，经 Firecracker 交给客户机。envd 收到一个来自 `10.14.0.10` 的连接。

### 3.2 回程：防火墙第一条规则的意义

envd 回包，目的地址是 `10.14.0.10`。客户机把它交给网关，包从 `tap0` 进入 `ns-5`，**要过 nftables 防火墙**。

注意，`10.14.0.10` 属于 `10.0.0.0/8`，在**预置拦截集合**里！按规则 3，这个包本该被丢掉。

救它的是排在最前面的规则 1：

```
iifname "tap0" ct state established,related accept
```

这个回包属于一条已经建立的连接（宿主机先发起的），状态是 ESTABLISHED，直接放行，根本轮不到规则 3。

这正是第 8 篇说“防火墙第一条规则通常是放行已建立连接”的原因：**沙箱不能主动访问 `10.x`，但宿主机主动发起的连接，沙箱可以正常回复**。

之后，conntrack 把源地址 `169.254.0.21` 改回 `10.13.0.5`，包经 `eth0` → `e2bv-5` 回到宿主机，orchestrator 收到回答。

## 四、两个常见误区

### 4.1 为什么宿主机 `ping 169.254.0.21` 不通

在宿主机上执行 `ping 169.254.0.21`，ping 不通。原因：

- 宿主机的路由表里没有任何一条路由指向 `169.254.0.21`。这个地址只存在于各个命名空间里，而且每个命名空间里都有一个。宿主机该找哪一个？
- 宿主机能访问的，是各个沙箱的 **Host IP**。`ping 10.13.0.5` 会经过 DNAT 到达槽位 5 的客户机。

如果确实想在“沙箱视角”下操作，可以进入命名空间：

```bash
ip netns exec ns-5 ping 169.254.0.21
```

在 `ns-5` 里，`169.254.0.21` 是唯一的、直连的。

### 4.2 为什么两个沙箱互相访问不了

沙箱 A 想访问沙箱 B 的 Host IP `10.13.0.6`。包从 A 的 `tap0` 进入 A 的命名空间，nftables 一看：`10.13.0.6` 在 `10.0.0.0/8` 里，属于预置拦截集合，**直接丢弃**。

而且不管 UDP 还是 TCP，这条规则都生效。规则 3 对所有协议一视同仁（第 15 篇）。所以 TCP 连接连 REDIRECT 到代理的机会都没有，在命名空间里就被拦下了。

沙箱之间的隔离，就这样在源头被保证了。

## 本篇小结

| 路径 | 关键步骤 |
|---|---|
| UDP 出站 | tap0 → nftables 放行 → 命名空间 SNAT（`169.254.0.21`→Host IP）→ veth → 宿主 FORWARD → MASQUERADE（Host IP→物理网卡地址）→ 互联网 |
| UDP 回程 | 宿主 conntrack 改回 Host IP → `/32` 路由进命名空间 → 命名空间 conntrack 改回 `169.254.0.21` → tap0 |
| TCP 出站 | 前半段同 UDP；在宿主 PREROUTING 被 REDIRECT 到防火墙代理；代理另开连接访问目标 |
| TCP 的两条连接 | 沙箱 ⇄ 代理；宿主机 ⇄ 目标 |
| FORWARD 与 MASQUERADE | 只承载非 TCP 流量 |
| 宿主访问沙箱 | 宿主路由到 `e2bv-N`，源地址是 veth 地址 → 命名空间 DNAT → 客户机 |
| 防火墙规则 1 的作用 | 让客户机能回复宿主机发起的连接，尽管 `10.x` 在拦截集合里 |
| 宿主 ping 169.254.0.21 | 不通：宿主没有到它的路由，要用 Host IP 或进命名空间 |
| 沙箱互访 | 不通：目的地址在 `10.0.0.0/8`，命名空间防火墙直接丢弃 |
