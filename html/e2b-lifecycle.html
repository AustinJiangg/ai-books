E2B 模板构建、沙箱启动与暂停恢复从零讲透

一本写给计算机新手的书，讲 E2B 原有的三个操作：构建模板（把一个 Dockerfile 做成一张随时能拉起来的虚拟机快照）、启动沙箱（从这张快照恢复出一台新机器）、暂停与恢复（存盘离场，改天读盘重建）。也讲我们对它们做的修改：搬到 ARM、提速、和新增的快照回滚共存。

  • 代码：AustinJiangg/e2b-infra 仓库里的 0001-adapted-for-arm-architecture.patch（ARM 适配、启动优化、快照相关修改都在这一份补丁里）和 e2b-deploy/ 部署脚本。
  • 机器：鲲鹏 920B 与鲲鹏 950 两类 ARM 服务器，openEuler 系统，单节点部署。
  • 范围：三个操作各自怎么做、时间花在哪、我们改了什么、为什么改、改对了的证据。快照回滚本身不展开。

全书围绕一句话展开：一切皆快照。构建的终点是拍一张快照；启动从这张快照恢复；暂停在当前状态上再拍一张；恢复又从那一张恢复。构建本身也在这个圈里反复转：每条指令都是“恢复—执行—暂停”。另外两条主线：只为用到的付费（内存懒加载、只存改过的部分、层缓存），固定开销藏在建和拆里（启动慢在拉起 Firecracker，暂停慢在拆掉它）。

前 4 篇打底：沙箱由什么组成，内存页、缺页、块设备、命名空间这些基础，快照三件套与映射表。之后分四部分：

  1. 构建模板：流水线五个阶段，base 阶段的两次开机，指令、层与缓存，就绪那一刻拍下的最终快照，以及搬到 ARM 改了什么。
  2. 启动沙箱：启动就是恢复，拉起 Firecracker，内存懒加载与预取，磁盘、网络与 envd，时间花在哪，怎样把它压下来。
  3. 暂停与恢复：暂停六步与为什么一定要停沙箱，增量怎么算、250 ms 花在哪，恢复与推迟的成本，ARM 上“读过就算脏”，精确增量。

一个沙箱的一生：构建、启动、暂停、恢复

本篇目标：先不碰任何术语，用几行 SDK 代码把一个沙箱从出生到消失走一遍，看清本书要讲的三个操作（构建模板、启动沙箱、暂停与恢复）分别处在哪个位置。然后给出全书最重要的一句话“一切皆快照”，说明这三个操作为什么其实是同一个循环。最后交代我们对它们做了哪三类修改，以及全书的地图和名词对照。

一、E2B 要解决什么问题

设想一个 AI 助手要帮你分析一份表格。它会写一段 Python，然后需要一个地方去运行这段代码。直接在你的电脑上跑？太危险，谁也不知道模型写出来的代码会不会删文件。在服务器上开一台完整的虚拟机？又太慢，开机一次要几十秒，用户等不起。

E2B 提供的就是这样一种东西：一台随时可用、用完即扔的小电脑，叫“沙箱”（sandbox）。它有三个要求：

要求 含义 为什么
隔离 沙箱里的程序碰不到宿主机和别人的沙箱 模型生成的代码不可信
快 从“我要一台”到“可以跑命令”，一百多毫秒 Agent 一次对话可能要开好几台
便宜 一台物理服务器上同时跑几百上千台 大部分沙箱只活几分钟，很多时候在空闲

隔离这一条决定了 E2B 用虚拟机而不是容器。容器和宿主共用一个操作系统内核，内核一旦有漏洞，容器里的程序就可能逃出来；虚拟机有自己独立的内核，中间隔着一层硬件虚拟化，边界硬得多。

可虚拟机传统上又慢又重。E2B 用两样东西把它变得又快又轻：

  • Firecracker：一种专为这种场景设计的“微虚拟机”，只模拟最少的几样设备，进程本身很小；
  • 快照：不是每次都从开机开始，而是提前把一台“已经开好机”的虚拟机存下来，要用时直接恢复。

第二样是本书的主角。

二、用几行代码走一遍一生

下面是用 E2B 的 Python SDK 写的一段示意代码，覆盖了一个沙箱从生到死的全部环节：

from e2b import Template, Sandbox

# 1. 构建模板：把一个运行环境做成“模具”（只需做一次）
Template.build(template, alias="my-python")

# 2. 启动沙箱：用模具“铸”出一台新沙箱
sbx = Sandbox.create("my-python")

# 3. 运行：在沙箱里跑命令、读写文件
sbx.commands.run("python3 analyze.py")

# 4. 暂停：把沙箱存盘，然后让它离场
sbx.pause()

# 5. 恢复：过一会儿（可能是几天后），把它读盘拉回来
sbx = Sandbox.connect(sbx.sandbox_id)

# 6. 销毁：用完扔掉
sbx.kill()

六步里，本书详细讲第 1、2、4、5 步，也就是三个操作：

操作 对应 SDK 一句话 类比
构建模板 Template.build 把一个运行环境（操作系统、软件、配置）做成一张可以反复使用的快照 做一个模具
启动沙箱 Sandbox.create 从模板快照恢复出一台新的沙箱 用模具铸一个零件
暂停与恢复 pause() / connect() 把正在运行的沙箱存成快照并停掉；以后再从这份快照重建出来 存盘离场，改天读盘

第 3 步“运行”和第 6 步“销毁”只在需要时提到。

三、核心洞见：一切皆快照

把上面的三个操作再往下看一层，会发现一件有意思的事：它们处理的是同一种东西，就是虚拟机快照。

  • 构建模板的终点是打一张快照。 构建时，E2B 真的会开一台虚拟机，在里面装软件、跑你的启动命令，等一切就绪，然后在那一刻把整台机器冻住、存下来。这张快照就是模板。
  • 启动沙箱是从这张快照恢复。 Sandbox.create 不会重新开机。它把模板快照加载进一个新的 Firecracker 进程，虚拟机从“就绪那一刻”接着往下跑。这就是 E2B 能在一百多毫秒内给你一台可用沙箱的根本原因：开机、启动系统服务、初始化那几秒，在构建时就已经做完了。
  • 暂停又是打一张快照。 它记下沙箱此刻的内存和磁盘，但只存相对于上一张快照改过的部分。
  • 恢复又是从快照恢复。 走的是和启动完全相同的那条路，只是用的是暂停时留下的那张快照。

更进一步，构建本身就是在这个循环里反复转圈。Dockerfile 里的每一条指令，都是“从上一张快照恢复一台虚拟机 → 在里面执行这条指令 → 再暂停成一张新快照”。所以构建模板、启动沙箱、暂停恢复，用的其实是同一套部件：同一个 Firecracker、同一套内存懒加载、同一套磁盘分层、同一种快照格式。

这就是为什么本书把三个操作放在一起讲。理解了其中一个，另外两个只是在同一张图上换了个位置。

四、和快照回滚划清界限

我们的仓库里还有一个新增的功能叫快照回滚（checkpoint / restore），另一本书《E2B 沙箱快照回滚从零讲透》专门讲它。它和本书的“暂停与恢复”名字相近，做的事却完全不同：

暂停与恢复（本书） 快照回滚（另一本书）
来历 E2B 原有的功能 我们新增的功能
存盘之后 沙箱停掉，离场 沙箱接着跑，什么都没发生
读盘 新起一个 Firecracker 进程重建沙箱 在同一个活着的进程里原地写回
擅长 长期保存、换机器恢复、进程崩了也能恢复 一秒内反复存档读档
典型耗时 暂停约 250 ms 起，恢复约 100 ms 存档、读档各约 20 ms 起

两者是独立的两套机制，本书不展开讲快照回滚。但它们共用了不少部件（Firecracker、磁盘写层、脏页记录），回滚加进来以后，暂停恢复真的被撞坏过几处，后来又修好了。这段经过在第五部分讲。

五、我们做了哪三类修改

E2B 的开源版本只在 x86 服务器上跑。我们的仓库在它的基础上做了不少修改，全部打在一个补丁文件里。按目的可以分成三类：

类别 为什么要改 例子 主要在哪几篇
搬到 ARM 要在鲲鹏服务器、openEuler 系统上跑起来 镜像架构从 amd64 换成 arm64；发行版脚本识别 dnf；内核没有某个功能时退而求其次 第 9、13、19 篇
更快、更稳 高并发下启动太慢、参数太保守、出错时报得不对 换掉启动管线里最贵的一环；放宽并发上限；修掉一个让失败等 300 秒的 bug 第 14、15、20 篇
和快照回滚共存 回滚加进来后，暂停恢复的几个前提不再成立 暂停时把多层磁盘压平再导出；补回被清零的脏页记录 第 21、22 篇

一、虚拟机的最小知识

一台电脑能运行程序，靠的是 CPU、内存、磁盘、网卡这几样硬件。虚拟机就是用软件“假装”出一套这样的硬件，让一个完整的操作系统在上面跑，而这个操作系统以为自己独占了一台真机器。

“假装”最难的部分是 CPU。现代 CPU（不管 x86 还是 ARM）都内置了硬件虚拟化支持：虚拟机里的指令大部分直接在真 CPU 上执行，只有少数敏感操作（比如访问设备）会“陷出来”交给宿主处理。Linux 内核里负责这件事的模块叫 KVM。有了 KVM，虚拟机里的程序跑起来几乎和在真机上一样快。

KVM 只管 CPU 和内存，设备要另外有人模拟：磁盘读写、网卡收发、串口输出。负责模拟设备、管理一台虚拟机生命周期的那个宿主进程，叫虚拟机监控器（VMM）。传统的 VMM（比如 QEMU）能模拟几百种设备，功能全但体积大、启动慢。

Firecracker 是一种极简的 VMM，原本为“函数计算”这类场景设计。它只模拟最少的几样设备：

设备 用途
virtio 块设备 虚拟机的磁盘
virtio 网卡 虚拟机的网络
串口 内核日志输出
vsock、balloon 等少数几个 宿主与虚拟机通信、内存回收

没有显卡、没有 USB、没有 BIOS 那一大套。代价是只能跑特定配置的 Linux，好处是每个 Firecracker 进程很小，启动只要一百多毫秒，一台物理机上能同时跑几千个。

Firecracker 对外暴露一个 HTTP 接口，走的是一个本地的 Unix 套接字（一种只在本机可见的“文件形式的网络端口”）。宿主上的程序通过它告诉 Firecracker：用哪个内核、哪块磁盘、多少内存，开机、暂停、恢复、打快照。后面会反复看到这个接口。

二、虚拟机里面有什么

一台 E2B 沙箱的虚拟机里，和一台普通 Linux 服务器差不多：

  • Linux 内核：E2B 自己编译的一个精简内核，宿主上按版本号存放；
  • 根文件系统（rootfs）：一个 ext4 格式的磁盘镜像，里面是 Ubuntu、Debian 或 openEuler 这样的发行版，加上用户装的软件；
  • systemd：1 号进程，负责拉起各种系统服务；
  • envd：E2B 自己写的一个小服务，监听虚拟机里的 49983 端口。SDK 里的“跑命令”“读写文件”“看进程”最后都是 envd 在执行。

envd 是沙箱里唯一的“管家”。它不是在你每次 Sandbox.create 时才启动的。在构建模板时它就已经启动好，和整个系统一起被冻进了快照。每台沙箱从快照恢复时，envd 进程本来就在内存里跑着，只需要“醒过来”接收新的身份信息。第 8、13 篇会细讲这件事。

三、宿主机上为它准备了什么

一台沙箱在宿主机上不只是一个 Firecracker 进程。为了让它能跑起来，宿主还要为它准备好四样“家当”：

家当 是什么 为什么需要 详见
网络槽位 一个独立的网络命名空间，里面有一块 tap 网卡，外面通过一对 veth 接到宿主 每台沙箱要有自己的网络，彼此看不见 第 13 篇
根盘 一个 NBD 块设备，背后是“模板只读层 + 本沙箱写层” 几百台沙箱共用同一份模板磁盘，各自的改动互不干扰 第 13 篇
内存处理器 一个 userfaultfd（uffd）处理程序 虚拟机内存不一次读回，用到哪页再补哪页 第 12 篇
cgroup 一个资源控制组 统计和限制这台沙箱用了多少 CPU、内存 第 15 篇

加上 Firecracker 进程本身，一台沙箱在宿主上一共是五样东西。记住这个数字：启动一台沙箱，本质上就是把这五样东西准备好，再加载快照。 暂停则是反过来，把它们拆掉。

四、宿主侧的服务

沙箱之外，还有几个常驻服务在管理它们。

服务 管什么 一句话
api 对外的入口 认证、记账、决定把沙箱放到哪个节点、记下每个模板有哪些版本
orchestrator 一个节点上的所有沙箱 真正动手的人：拉起 Firecracker、准备四样家当、暂停、恢复

在官方的大规模部署里，这些服务分散在不同的机器池里。我们仓库的部署是单节点的：所有服务都在一台机器上，而且 orchestrator 和 template-manager 是同一个进程（同一个二进制，通过环境变量同时打开两种角色）。所以在我们的环境里，“构建模板”和“启动沙箱”其实是同一个进程在干，共用同一套 Firecracker、同一个网络槽位池、同一个内存上限。这一点在第 9 篇讲构建时的内存故障、第 12 篇讲空闲沙箱的内存账时都会用到。

还有一个容易被忽略的角色：存储。模板快照、暂停产生的快照，都要放在一个地方，下次启动或恢复时再取出来。官方用云厂商的对象存储；我们的部署支持本地目录和 MinIO（一种可以自己部署的对象存储）。第 4 篇会讲快照在存储里长什么样。

五、两条路：控制面和数据面

请求从 SDK 出发，有两条完全不同的路。

控制面：创建、暂停、恢复、销毁这类“管理”操作。

SDK ──HTTPS──▶ api ──gRPC──▶ orchestrator ──HTTP（Unix 套接字）──▶ Firecracker

api 收到 Sandbox.create 后，查数据库确定模板的最新版本，挑一个节点，用 gRPC 调用该节点 orchestrator 的 Create 接口。orchestrator 准备好家当，再通过 Firecracker 的 HTTP 接口加载快照。

数据面：沙箱活着时，跑命令、读写文件、访问沙箱里开的网页服务。

SDK ──HTTPS──▶ client-proxy ──▶ orchestrator 的代理 ──▶ 沙箱网络 ──▶ envd（49983）

请求的地址里带着沙箱 ID（形如 49983-<沙箱ID>.<域名>），client-proxy 按它查路由表，找到沙箱所在节点，交给那个节点上 orchestrator 内置的代理，代理再把它送进沙箱的网络，最后到达 envd。

两条路分开，是因为它们的性质不同：控制面请求少、每个都很重要，要认证、要记账；数据面请求多、要求延迟低，只做转发。

本书讲的三个操作都走控制面。但有两处会碰到数据面：一是启动的最后要确认 envd 能应答，二是第 18 篇讲的一个修复，恢复后的沙箱因为少带了两个请求头，数据面上有一类请求路由不过去。

一、内存按页管理

1. 页

操作系统不会一个字节一个字节地管理内存，那样账本会比内存本身还大。它把内存切成固定大小的块，叫页（page），以页为单位分配、回收、记录状态。

在 x86 和本书用到的 ARM 机器上，最常见的页大小是 4 KiB。一台 2 GiB 内存的虚拟机，就是 524288 个 4 KiB 的页。

2. 页表

程序看到的内存地址（虚拟地址）和内存条上的真实位置（物理地址）不是一回事。两者之间靠一张页表来翻译：每一项记着“这一页虚拟地址对应哪一页物理内存”。这像一栋楼的门牌对照表，程序只知道门牌号，CPU 查表才知道是哪个房间。

查表要时间，所以 CPU 里有一个小缓存，叫 TLB，记着最近查过的几百到几千项。命中就快，不命中就要去内存里一级一级地查。

3. 大页

如果一个程序要用很大一块内存，4 KiB 一页就太碎了：2 MiB 的数据需要 512 个页表项，TLB 很快就装不下。大页（huge page）把一页做成 2 MiB，同样 2 MiB 的数据只要 1 个表项，TLB 覆盖范围扩大 512 倍。

大页的代价是：一旦要处理“一页”，就是整整 2 MiB。读一页、补一页、存一页，都是 2 MiB 起步。

Linux 上用大页最直接的方式是 hugetlbfs：系统启动后预留一个“大页池”，程序从里面按 2 MiB 领取。池子是提前划走的，没人用也占着。

和本书的关系：E2B 沙箱的内存默认由 2 MiB 大页背衬，好处是虚拟机里的程序跑得快。但“一次至少 2 MiB”这个特点，在第 12 篇的内存懒加载和第 20 篇的精确增量里都是关键约束。部署时要在宿主上预留大页池，第 15 篇会讲它的申请和释放。

二、缺页

程序访问一个虚拟地址，CPU 查页表发现“这一页现在没有对应的物理内存”（比如还没分配，或者被换到了磁盘上），就会暂停这个程序，向操作系统报告一次缺页（page fault）。操作系统把这一页准备好（分配物理内存、从磁盘读回内容），填进页表，再让程序从刚才那条指令继续执行。程序完全感觉不到中间发生过什么，只是这一次访问慢了一点。

缺页是正常机制，不是错误。Linux 正是靠它实现“按需分配”：你申请 1 GiB 内存，系统只是答应了，真正用到哪一页才分配哪一页。

和本书的关系：沙箱从快照恢复时，内存一开始是“空”的，guest 每访问一页都会触发一次缺页。怎么处理这次缺页，就是下一节的 userfaultfd。

三、userfaultfd：让一个普通程序来补页

正常的缺页由内核处理，内核知道去哪里取内容（物理内存、交换分区、文件）。可如果内容在一个内核不知道的地方呢？比如在一份快照文件的某个偏移，甚至在远端的对象存储里？

Linux 提供了一个机制叫 userfaultfd（简称 uffd）：一个程序可以登记“这一段内存的缺页由我来处理”。之后这段内存每发生一次缺页：

  1. 访问它的线程被挂起；
  2. 内核通过一个文件描述符通知登记的程序：“地址 X 缺页了”；
  3. 程序自己去找内容（读文件、查表、从网络下载），然后用一个系统调用 UFFDIO_COPY 把内容填进那一页；
  4. 内核唤醒刚才挂起的线程，它从头重做那次访问，这次就成功了。

uffd 还有一个可选功能叫写保护（write-protect）：填页时可以要求“这一页先保持只读”，之后有人第一次写它，会再通知一次处理程序。利用这一点，处理程序就能分辨“这一页只是被读过”还是“被写过”。

和本书的关系：E2B 的内存懒加载全靠 uffd，处理程序在 orchestrator 里（第 12 篇）。写保护功能则是暂停时判断“哪些页改过”的依据。第 19 篇要讲的 ARM 问题，根源正是 ARM 内核上没有这个写保护功能。

四、块设备、NBD 与写时复制

1. 块设备

磁盘在操作系统眼里是一个块设备：一长串固定大小的块，可以按编号读写任意一块。文件系统（比如 ext4）建在块设备之上，把“文件”“目录”翻译成“哪些块”。

2. NBD

NBD（Network Block Device，网络块设备）是 Linux 内核的一个模块，它创建形如 /dev/nbd0 的块设备，但这块“磁盘”的读写请求不交给硬件，而是通过一个套接字转发给某个用户态程序处理。程序想从哪里读、往哪里写都行，本地文件、内存、网络都可以。

这和 uffd 的思路如出一辙：把本来由内核处理的事，交给一个普通程序来决定。

3. 写时复制

几百台沙箱都从同一个模板启动，磁盘内容一开始完全一样。如果每台都复制一份几 GiB 的磁盘，又慢又占地方。

写时复制（copy-on-write，COW）的做法是：

  • 底下放一份只读的公共磁盘（模板）；
  • 每台沙箱上面叠一个自己的写层，一开始是空的；
  • 写：只写进自己的写层；
  • 读：先看写层里有没有这一块，有就用写层的，没有就从底下的模板读。

于是启动一台沙箱不用复制任何磁盘数据，写层只随改动增长。

和本书的关系：E2B 的根盘就是“NBD + 写时复制”：orchestrator 当 NBD 背后的那个程序，按上面的规则在模板和写层之间分派读写（第 13 篇）。暂停时导出的磁盘增量就是写层里那些块（第 17 篇）。我们的快照回滚又把一个写层变成了一叠写层，这给暂停带来了问题（第 22 篇）。

五、命名空间

Linux 的命名空间（namespace）让一组进程拥有一份独立的“视图”。常用的有几种：

命名空间 隔离什么 本书用到的地方
网络命名空间 网卡、IP、路由表、防火墙规则 每台沙箱一个，里面放它的 tap 网卡
挂载命名空间 能看到哪些挂载点、文件路径指向哪里 启动 Firecracker 时，让同一个路径在不同沙箱里指向不同文件

一个进程进了某个网络命名空间，就只能看见那里面的网卡。这样宿主上同时跑一千台沙箱，每台都可以有一块叫 eth0 的网卡、一个相同的内部 IP，互不冲突。

创建和切换命名空间都要动内核里的全局数据结构。平时很快，但几百个进程同时做，就会在内核的锁上排队。第 15 篇的启动优化正是从这里下手的。

六、两个小工具：稀疏文件与 mmap

稀疏文件：一个文件可以声明自己有 2 GiB 大，但只有写过的地方真正占磁盘，没写过的地方是“空洞”，读出来是全零。适合存“大部分是空的”数据。

mmap：把一个文件直接映射进进程的内存地址空间，读写这段内存就等于读写文件，由内核负责在两者之间搬数据。E2B 读快照文件、维护磁盘写层都大量使用 mmap。

写时复制 只读底层 + 各自写层 几百台沙箱共用一份模板磁盘
命名空间 进程的独立视图 每台沙箱一个网络命名空间

快照是什么：三件套与映射表

本篇目标：上一篇的底子到这里派上用场。本篇回答三个问题：一张虚拟机快照里到底存了什么；为什么 E2B 不让 Firecracker 自己存内存和磁盘，而是自己管；一代一代的增量快照怎样靠一张“映射表”拼成一个完整的样子。最后看快照在宿主上和存储里放在哪。读完这一篇，后面构建、启动、暂停三部分都只是在“读快照”和“长出新一代”。

一、存一台机器，要存哪三样

把一台正在运行的电脑“冻住”再“解冻”，要保证解冻后它能从冻住那一刻接着往下跑，好像什么都没发生。需要记下的东西分三类：

类别 内容 大小 E2B 的文件名
CPU 与设备状态 每个 vCPU 的寄存器（正执行到哪条指令、各寄存器的值）、中断控制器、虚拟设备的内部状态（网卡队列到哪了、磁盘请求处理到哪了） 几十 KB 到几 MB snapfile
内存 虚拟机的全部内存内容：内核、所有进程的代码和数据、文件缓存 等于虚拟机内存大小（如 2 GiB），但只存用到的部分 memfile
磁盘 根文件系统 磁盘大小（几 GiB），只存改过的部分 rootfs.ext4

这就是快照三件套。三样必须是同一个时刻的：如果内存里的文件系统缓存说“某个文件写了 100 行”，磁盘上却只有 50 行，恢复后系统就会错乱。所以打快照前一定要先暂停 vCPU，让虚拟机停止产生新状态，再分别把三样存下来。

除了三件套，每一代快照还有一个 metadata.json，记着模板的版本、用哪个内核和 Firecracker、启动命令是什么、预取表（第 8 篇）等等。

二、为什么内存和磁盘不交给 Firecracker 存

Firecracker 自己会打快照：调它的 PUT /snapshot/create 接口，它就把 vCPU 状态写进 snapfile，再把整份内存写进一个内存文件。它也支持“差分快照”：只写上一次快照以来改过的页。

可 E2B 只让 Firecracker 写 snapfile，内存和磁盘都自己管。原因有三：

  1. 要能按需取。从快照恢复时，E2B 不想先把 2 GiB 内存全读回来再开跑，而是用 uffd 懒加载，用到哪页取哪页（第 12 篇）。这要求内存文件能按偏移随机读，而且读的人是 orchestrator，不是 Firecracker。
  2. 要能增量、能拼链。一个沙箱可能被暂停很多次，每次只该存改过的部分。几十代快照叠在一起，恢复时要知道每一页最新的内容在哪一代。Firecracker 的差分快照只描述“相对上一次”，不负责记这条链。
  3. 要能上传、能搬走。快照要存进对象存储，以后可能在另一个节点上恢复。产物必须是自足的、紧凑的文件，而不是依赖某个进程的状态。

磁盘更是如此：Firecracker 的快照根本不含磁盘，它假定磁盘由外部保证一致。E2B 的磁盘本来就是 orchestrator 用 NBD 提供的（第 3 篇），自然由 orchestrator 来存。

所以分工是：Firecracker 只存 CPU 和设备状态；内存由 orchestrator 从 Firecracker 进程里直接读出来存；磁盘由 orchestrator 从写层导出。 第 17 篇会细讲这两种“导出”。

三、增量：只存改过的块

模板构建完是第一代。之后每暂停一次，沙箱的内存和磁盘都只有一小部分变了。如果每次都存一整份，一个暂停过十次的 2 GiB 沙箱就要 20 GiB，显然不行。

E2B 的做法是每一代只存自己改过的块，并且把这些块紧凑地首尾相接写进文件。比如这一代只改了内存里第 3、7、8 块（每块 2 MiB），这一代的 memfile 就只有 6 MiB，里面依次放着第 3、7、8 块的内容。

“块”的大小是这样定的：

文件 块大小 原因
memfile 2 MiB 和 guest 的大页一样大，一次缺页正好填一块（第 20 篇会改这一点）
rootfs.ext4 4 KiB 和 ext4 文件系统的块一样大

问题来了：文件里只是紧挨着的几块数据，怎么知道哪一块原来在哪个位置？没存的块又去哪里找？

四、映射表

每一代除了数据文件，还有一个映射表（header）文件：memfile.header 和 rootfs.ext4.header。它是一张按地址排序的表，每一行说：

“设备上从偏移 A 开始、长度为 L 的这一段，在第几代的数据文件里，从偏移 B 开始。”

举个例子。设备（内存或磁盘）被切成一段段，第三代的映射表可能长这样：

设备偏移 长度 在哪一代 那一代文件里的偏移
0 4 MiB 第 1 代（模板） 0
4 MiB 2 MiB 第 3 代（本代） 0
6 MiB 4 MiB 第 2 代 2 MiB
10 MiB …… 第 1 代 10 MiB

要读设备偏移 7 MiB 的数据：找到覆盖它的那一行（6 MiB 起、长 4 MiB），算出在那一行里的位置（7 − 6 = 1 MiB），于是去读第 2 代文件的 2 + 1 = 3 MiB 处。

几个要点：

  • 映射表完整覆盖整个设备，按地址升序，首尾相接，所以任何偏移都能一步找到对应的那一行。
  • 每一代的映射表都是完整的，不是只描述本代的块。新一代的映射表 = 上一代的映射表 + 本代改过的块覆盖上去。所以读的时候不用沿着代一层层往上翻，查本代这一张表就够了。
  • 从没被写过的地方，映射表里会标成“空”，读出来是全零，不占任何文件空间。

五、代际链

每一代都有一个唯一的 build ID。模板构建时，每一层（第 7 篇）是一代；之后每次暂停，又长出一代。

这条链有几个性质，后面会反复用到：

  • 只追加，不修改。新一代不会改动老一代的任何文件，只是在映射表里把一些区间指向自己。所以同一个模板拉起的几百台沙箱可以放心地共享模板那几代的文件。
  • 改得少，存得少。一代的数据文件大小正比于这一代改了多少。这是“只为用到的付费”在存储上的体现。
  • 判断“改了多少”是关键。磁盘的改动很好判断：写层里有的块就是改过的。内存的改动要靠一个“脏页判据”，判得准不准直接决定每一代存多大。第 17 篇讲上游的判据，第 19 篇讲它在 ARM 上怎么失灵，第 20 篇讲怎么修好。

六、快照放在哪

快照文件在宿主上分三层存放，别混在一起：

层 位置（我们的部署） 是什么 生命周期
持久化存储 本地目录 /tmp/templates，或 MinIO 的桶 每个 build ID 一个目录，放三件套、两张映射表、metadata.json 直到删除模板或快照
本地缓存 /orchestrator/build、/orchestrator/template 从持久化存储拉下来的副本，启动、恢复时实际读的是它 有过期时间；orchestrator 一重启就清空
沙箱运行态 /orchestrator/sandbox、/mnt/snapshot-cache 正在运行的沙箱的写层、暂停时的临时产物 沙箱销毁即清

持久化存储由一个叫 STORAGE_PROVIDER 的配置决定用哪种。上游支持 Google 和 AWS 的对象存储，以及本地目录；我们为了能在不连外网的环境里部署，加了一种 MinIO 后端，并把默认值改成了它。

不过这里有一个部署上的细节值得知道：我们的单节点部署脚本在 template-manager 的配置里把它写死成了本地目录，所以实际生效的是 /tmp/templates。在 openEuler 上 /tmp 是内存文件系统（tmpfs），宿主机一重启，所有模板就都没了，要重新构建。这不是 bug，而是当前部署的选择，第 23 篇把它列在“还没解决的问题”里。

七、三个操作，三种读写方式

有了快照的样子，三个操作就可以用一句话描述：

操作 对快照做什么
构建模板 从空白开始，一层一层地长出第 1 代、第 2 代……最后一代就是模板
启动沙箱 沿着模板的映射表读：snapfile 一次读完，内存和磁盘按需读
暂停 在当前这一代上再长出一代：只存改过的块，写一张新映射表
恢复 和启动一样读，只是读的是暂停留下的那一代

构建总览：为什么镜像不够，要的是一张快照

本篇目标：进入第二部分“构建模板”。本篇先回答一个看起来多余的问题：都有 Docker 镜像了，为什么还要“构建模板”？然后给出一次构建的输入和输出，把流水线的五个阶段过一遍，最后点出整个构建最核心的一个事实：构建本身就是在反复“启动—干活—暂停”。后面三篇再分别展开 base 阶段、指令与缓存、收尾阶段。

一、镜像只是一堆文件

用户写模板，最常见的起点是一个 Docker 镜像，比如 ubuntu:22.04，再加几行指令：

FROM ubuntu:22.04
RUN apt-get install -y python3 python3-pip
RUN pip install pandas
WORKDIR /home/user

在 Docker 里，镜像就是一叠文件层，容器启动时把它们叠起来当作根目录，然后直接运行一个进程。容器和宿主共用内核，所以“启动”只是创建一个进程，很快。

可 E2B 的沙箱是虚拟机。虚拟机要的不是“一叠文件”，而是：

  • 一块磁盘（块设备），上面有文件系统；
  • 一个内核，要从开机开始引导；
  • 一个 1 号进程（init），把系统服务一个个拉起来；
  • 沙箱里的管家 envd 已经在运行。

从一堆文件走到“envd 已经在运行”，要经过开机、内核初始化、systemd 启动几十个服务，通常要好几秒甚至更久。如果每次 Sandbox.create 都这样走一遍，“一百多毫秒可用”就无从谈起。

所以 E2B 的思路是：把这几秒提前做掉。 构建时真的开一台虚拟机，让它开机、装软件、跑启动命令，一直走到“一切就绪”，然后在那一刻把整台机器冻住、存成快照。以后每次启动，都从这一刻接着往下跑。

这就是“模板”：不是一堆文件，而是一台开到一半就冻住的机器。

二、输入和输出

一次构建：

内容
输入 基础镜像（或另一个已有的模板）；一串指令（RUN、COPY、ENV、WORKDIR、USER 等）；CPU 核数和内存大小；可选的启动命令（start）与就绪检查命令（ready）
输出 一个 build ID，以及它的快照三件套、映射表、metadata.json（第 4 篇）
副产品 中间每一层的快照（也是 build ID），可以被以后的构建复用

用户在 SDK 里调用 Template.build，请求先到 api。api 在数据库里登记“这个模板有一个新版本正在构建”，挑一个能构建的节点，把任务交给那里的 template-manager。template-manager 收下任务就立刻返回，构建在后台进行；SDK 这边则不断轮询构建的状态和日志，直到成功或失败。

前面说过，在我们的单节点部署里，template-manager 和 orchestrator 是同一个进程。所以构建用的虚拟机和用户的沙箱由同一个进程管理，共享同一套 Firecracker、网络槽位池、本地缓存，也共享同一个内存上限。

三、流水线的五个阶段

构建按固定顺序走五个阶段：

阶段 做什么 产出 详见
base 拉镜像、解包成 ext4 磁盘；开一台临时虚拟机装上 systemd 等必需组件；再用 systemd 正式开机，等 envd 就绪 第一层快照 第 6 篇
默认用户 创建名为 user 的默认用户并给它 sudo 权限 一层快照 第 7 篇
steps 每条指令一层：执行指令，然后暂停成新的一层 每条指令一层快照 第 7 篇
finalize 重启沙箱，跑配置脚本、执行用户的启动命令、轮询就绪检查，就绪那一刻拍下最终快照 最终快照（模板本身） 第 8 篇
optimize 从最终快照恢复两次，记下“一恢复就会访问哪些内存块”，写成预取表 不产生新层，只改元数据 第 8 篇

每个阶段在开始前都会算一个 hash：本阶段的 hash 由上一阶段的 hash 和本阶段的内容（比如这条指令的文本）共同决定。拿这个 hash 去“层缓存索引”里查，查到了说明以前构建过一模一样的东西，直接复用那一层，跳过整个阶段。第 7 篇细讲。

四、构建就是反复“启动—干活—暂停”

仔细看每个阶段在做什么，会发现它们几乎是同一个动作的重复：

拿到上一层的快照
 → 从它启动（恢复）一台虚拟机
 → 在里面干活（执行一条指令、跑一个脚本）
 → 暂停，存成新的一层快照

这里的“启动”和“暂停”，用的正是第三、四部分要讲的同一套代码：同一个 ResumeSandbox 把快照加载进 Firecracker，同一个 Pause 把内存和磁盘的改动导出成新的一代。区别只在于：

构建时 用户使用时
谁发起 template-manager 用户的 SDK 调用
沙箱能不能上网 base 阶段装包时可以 按用户配置
暂停后 立刻拿新一层接着构建下一条指令 沙箱离场，等用户来恢复
一次构建要转几圈 指令有几条就转几圈，外加 base、finalize 各一两圈 一圈

这也意味着：构建会受到启动和暂停的所有特性和问题的影响。 比如第 19 篇要讲的 ARM 上“读过就算脏”的问题，在构建的每一层暂停时同样存在；第 9 篇讲的构建内存故障，原因也和这些虚拟机共享同一个进程的内存上限有关。

还有一个细节：不是每一层都“从上一层恢复”。如果上一层是从缓存里直接拿来的（没有真的跑），下一层会用冷启动（从开机开始）而不是恢复，因为要让新的 CPU、内存规格生效。连续几条没命中缓存的指令则会共用一条“恢复—暂停”链，只有链的第一环付一次冷启动的代价。

五、层是怎么落地的

每一层暂停得到快照之后，要做三件事，顺序有讲究：

  1. 先放进本地缓存。下一条指令马上就要从这一层恢复，不能等上传完。
  2. 再异步上传到持久化存储，不阻塞下一层的构建。
  3. 最后写层缓存索引，而且要等这一层以及所有更早的层都上传完之后才写。

第 3 步的顺序很重要。索引一旦写下，别的构建就可能命中这一层、从它接着往下造；如果它依赖的前面某一层还没传完，那个构建就会去读一个不存在的文件。所以宁可晚一点登记，也不能先登记后上传。这和第 16 篇里暂停“等上传完成才返回”是同一个道理：元数据不能早于数据宣布就绪。

六、时限

构建的每一段都有超时：

环节 超时
base 阶段的装包脚本 5 分钟
base 阶段的第一层 10 分钟
每一条指令 1 小时
finalize 的配置脚本 5 分钟
等待就绪检查通过 10 分钟
optimize 的每次采集 5 分钟

optimize 是“尽力而为”的：采集失败只记一条警告，不让构建失败，模板照样可用，只是启动时少了预取。

一、从镜像到磁盘

1. 拉镜像

template-manager 先按用户给的镜像名（比如 ubuntu:22.04）去镜像仓库拉取。一个镜像往往同时有 x86 和 ARM 两种版本，拉的时候要指定平台，拉下来后还要再检查一遍它的架构字段对不对。两道检查都有必要：多架构镜像靠第一道挑出正确的版本；只有一种架构的镜像，第一道不起作用，只能靠第二道拦住。上游把平台写死成 amd64，这是第 9 篇要改的第一处。

2. 造一块空磁盘

接下来造一个 ext4 格式的磁盘文件。几个参数体现了沙箱的特点：

参数 含义 为什么
一开始按允许的最大尺寸造 默认上限约 24 GiB 先保证装得下，后面再收缩
每 4 KiB 一个 inode inode 是文件的“身份证”，数量在造盘时就定死了 解包 node_modules 这类海量小文件时不会先把 inode 用光
不给 root 预留空间 ext4 默认留 5% 给 root 应急 沙箱是一次性的，预留纯属浪费

3. 解包

镜像由好几层组成，后面的层可以覆盖、删除前面层里的文件。要得到最终的样子，得把各层按顺序叠起来。

E2B 的做法是：把磁盘文件挂载到一个临时目录；把每一层并行解包到各自的目录；用 Linux 的 overlayfs 把这些目录叠成一个只读视图（删除、覆盖的语义交给内核处理，比自己逐层重放可靠）；最后用 rsync 把叠好的视图整个拷进磁盘，保留权限、符号链接和硬链接。

4. 检查与收缩

拷完之后：检查文件系统 → 收缩到“刚好装下现有数据”的大小 → 再检查一次。先查后缩，是因为带着错误去缩会把问题放大；缩完再查，是因为收缩本身也可能留下小问题。

二、往磁盘里塞进了什么

用户的镜像里当然没有 E2B 的东西。在解包之前，E2B 会往镜像顶上追加两层自己的文件：

文件 用途
/usr/bin/envd 沙箱里的管家
/usr/local/bin/provision.sh 第一次开机时运行的装机脚本
/usr/bin/busybox、/usr/bin/init 一个“万能小工具箱”，第一次开机时当 1 号进程
/etc/inittab、/etc/init.d/rcS busybox 当 1 号进程时的“剧本”
/etc/systemd/system/envd.service 让 systemd 开机时拉起 envd
/etc/hostname、/etc/hosts、/etc/resolv.conf 主机名、DNS
两个 watchdog 覆盖配置 关掉 journald 和网络服务的“看门狗”
串口免登录配置 方便调试时从串口直接进系统

关掉看门狗这一条值得多说一句。systemd 的看门狗会定期检查服务是否还活着，太久没响应就重启它。可快照恢复会让虚拟机里的时钟出现跳变：从系统的角度看，好像某个服务“突然很久没响应了”，看门狗就会误判它卡死。所以要关掉。这是“一切皆快照”带来的一个副作用：系统软件默认假设时间是连续流逝的，快照打破了这个假设。

还有一处细节：envd 和 chrony（校时服务）被“启用”的方式，是直接在 systemd 的目录里放符号链接，效果等同于 systemctl enable。不用在镜像里真的运行 systemctl，因为此时还没有一个在运行的系统。

三、第一次开机：用 busybox 当临时的 1 号进程

现在磁盘有了，但里面多半没有 systemd。很多基础镜像是为容器设计的，容器不需要 init 系统。要装 systemd，就得运行 apt-get（或 dnf）；要运行包管理器，就得有一个在运行的系统。这是一个循环依赖。

E2B 的解法是开两次机。第一次开机，用磁盘里塞进去的 busybox 当 1 号进程。busybox 很小，一个二进制里包含了 sh、mount、sync 等上百个常用命令，自己就能当一个最简单的 init。它照着 /etc/inittab 这份剧本依次执行：

1. 挂载 /proc、/sys、/dev、/tmp、/run（容器里这些是运行时给的，裸机得自己挂）
2. 运行 provision.sh，输出加上 [external] 前缀
3. sync，把缓存刷到磁盘
4. 冻结根文件系统（fsfreeze），保证没有在途的写
5. 打印一行 "E2B_PROVISIONING_EXIT:<退出码>"
6. sleep infinity，等宿主来关机

这里面有两个巧妙的地方：

  • 日志靠前缀过滤。这台虚拟机里没有 envd，没有任何 RPC 通道。它的输出只能走串口，变成 Firecracker 进程的标准输出。宿主按 [external] 前缀把装机日志挑出来，转成用户在 SDK 里能看到的构建日志。
  • 结果靠一行文本。退出码也没有别的路可走，只能打印一行带固定前缀的文本，宿主扫描输出流认出它。如果读不到结果文件，就按失败处理，宁可误判失败也不误判成功。

宿主拿到退出码后主动关掉这台虚拟机。

这台临时虚拟机是整个构建里唯一允许上网的，因为装包要访问软件源。整个过程限时 5 分钟。

provision.sh 装了什么

软件包 谁需要它
systemd 第二次开机的 init 与服务管理
chrony、linuxptp 快照恢复后校时（从宿主提供的时钟设备同步）
openssh-server、sudo 用户在沙箱里的交互与提权
socat、curl、ca-certificates 用户命令和就绪检查常用

脚本开头还会把 /etc/resolv.conf 锁成不可修改，装完再解锁。因为装 systemd 的过程中，有的软件包会试图接管 DNS 配置，接管后沙箱的 DNS 就依赖一个在快照恢复后未必正常的服务。

四、第二次开机：systemd 正式登场

第一台虚拟机关掉之后，宿主检查一遍磁盘的完整性，再把磁盘的空闲空间扩到用户要求的大小（用户指定的磁盘大小指的是空闲空间，不是总大小）。

然后第二次开机，这次用 systemd 当 1 号进程，和以后所有的沙箱一样。systemd 拉起各种服务，其中包括 envd。宿主等 envd 能应答，把磁盘缓存刷下去，然后暂停，得到构建的第一层快照。

两台虚拟机用的是宿主上同一个磁盘文件，所以第一台装好的软件，第二台开机时自然就在。

五、为什么 base 最贵，也最值得缓存

base 阶段包含两次完整的冷启动和一次装包，通常是整个构建里最慢的一段，也是最容易失败的一段：镜像拉不下来、软件源连不上、包名在这个发行版里不存在……所以这一段会把内核日志也直接流给用户，方便排查。

反过来，它也是缓存收益最大的一段：只要基础镜像没变，第二次构建可以整段跳过。如果模板不是从镜像而是从另一个模板派生的，base 阶段根本不跑，直接拿那个模板的最后一层当起点。

六、在 ARM 上要改的地方

这一段在 x86 上写得很顺，搬到鲲鹏和 openEuler 上却处处碰壁：镜像平台写死 amd64；内嵌的 busybox 是 x86 二进制；provision.sh 只认 apt；有几个包在 openEuler 的软件源里装不上。这些都在第 9 篇统一讲。

本篇小结

概念 一句话解释
拉镜像 按平台挑版本，拉下来后再查一次架构
造磁盘 按最大尺寸造、每 4 KiB 一个 inode、不留 root 预留
解包 各层并行解包，用 overlayfs 叠好，rsync 进磁盘，查—缩—查
注入文件 envd、provision.sh、busybox、systemd 单元、关看门狗等
第一次开机 busybox 当 init，跑 provision.sh 装 systemd 等，结果靠一行文本回报，唯一能上网
第二次开机 systemd 开机、等 envd 就绪、暂停成第一层
缓存 base 最贵，基础镜像不变就整段跳过

指令、层与缓存：一条 RUN 是怎么执行的

本篇目标：base 阶段给了我们一台能开机、envd 已就绪的机器。接下来是用户自己的指令：RUN、COPY、ENV、WORKDIR、USER。本篇讲每条指令怎样变成“一层快照”；一条 RUN 从 template-manager 出发，经过哪些环节才在虚拟机里执行；指令之间传递了什么状态；以及为什么改了最后一行，前面的不用重做。

一、一条指令一层

steps 阶段把用户的指令逐条展开，每条指令就是一个小阶段，做的事情都一样：

从上一层的快照恢复一台虚拟机
 → 通过 envd 在里面执行这条指令
 → 暂停，存成新的一层

为什么要一条一层，而不是全部执行完再存一次？因为层是缓存的单位。如果十条指令只存一层，改了第十条就得把前九条全部重做；一条一层，就只需要从第九层接着做第十条。装 Python、装 pandas 这种动辄几分钟的指令，能省下大量时间。

每一层都是一个 build ID，都有自己的快照三件套。由于快照是增量的（第 4 篇），每一层只存这条指令改动的内存页和磁盘块。一条 RUN pip install pandas 那一层的磁盘增量，大致就是 pandas 装进去的那些文件。

二、六类指令

E2B 只支持 Dockerfile 的一个子集：

指令 做什么 会不会改变“当前状态”
RUN 在虚拟机里执行一条 shell 命令 不会
COPY / ADD 把用户上传的文件放进虚拟机 不会
ENV / ARG 设环境变量 改环境变量
WORKDIR 设工作目录 改工作目录
USER 切换后续指令的执行用户 改用户

没有 CMD、ENTRYPOINT、EXPOSE 这些。它们在 Docker 里描述“容器启动时干什么”，在 E2B 里由模板的启动命令和就绪检查承担（第 8 篇）。

指令之间传递什么

每条指令执行时都带着一份“当前状态”：以哪个用户、在哪个目录、带哪些环境变量。ENV、WORKDIR、USER 修改它，RUN、COPY 读取它但不修改。这份状态会写进每一层的元数据，随快照一起保存，所以下一层从快照恢复后仍然知道当前用户和目录；模板最终的这份状态，还会在启动沙箱时交给 envd，作为默认用户和默认目录。

这里有一个和 Docker 一致的语义：每条 RUN 是一个独立的 shell。你在一条 RUN 里 export FOO=1 或者 cd /tmp，下一条 RUN 看不到。副作用只留在文件系统里。要改环境变量和目录，必须用 ENV 和 WORKDIR。

ENV 还有一个小细节：变量的值会送进虚拟机里求值一次，所以 ENV PATH=$PATH:/opt/bin 这种引用已有变量的写法能正确展开。代价是每设一个变量就要在虚拟机里跑一次命令。

三、一条 RUN 的完整路径

以 RUN pip install pandas 为例：

  1. template-manager 从上一层快照恢复出一台构建用的虚拟机（就是第三部分要讲的 ResumeSandbox）；
  2. 它通过 orchestrator 内置的代理，连到这台虚拟机里 envd 的进程服务；
  3. envd 以当前用户、在当前目录、带着当前的环境变量，启动 bash -l -c "pip install pandas"；
  4. 命令的标准输出和标准错误以流的形式传回 template-manager，加上步骤编号，写进构建日志，SDK 那边轮询就能看到；
  5. 命令结束，envd 回报退出码。非零就判这一步失败，整个构建失败；
  6. 成功则把虚拟机里的磁盘缓存刷下去，然后暂停，得到新的一层。

注意第 2 步：template-manager 和这台虚拟机之间走的是数据面（第 2 篇），和用户在 SDK 里 sbx.commands.run(...) 走的是同一条路。构建没有什么“后门”，它就是一个特殊的 envd 客户端。

COPY 也类似：用户的文件先由 SDK 打包上传到存储，template-manager 取下来，通过 envd 的文件服务写进虚拟机。

四、层缓存：改了最后一行，前面不用重做

1. 层 hash

每个阶段在执行前都先算一个 hash：

本层 hash = SHA-256( 上一层 hash ; 指令类型 ; 指令参数 ; 上传文件的 hash )

base 阶段没有“上一层”，它的输入是镜像名、磁盘大小、provision 脚本的版本和一个缓存格式版本号。

由于每一层都把上一层的 hash 当作输入，整条链就是一条 hash 链：任何一环变了，它之后所有层的 hash 都会变。

2. 查缓存

算出 hash 后，去“层缓存索引”里查：以前有没有构建过 hash 一模一样的层？有，就直接拿那一层的 build ID 当本层的结果，跳过执行；没有，才真的恢复虚拟机去跑。

于是：

  • 改了第 3 条指令：第 1、2 条命中缓存，从第 3 条开始重做；
  • 改了 COPY 的文件内容：文件 hash 变了，这一条和之后的都重做；
  • 换了基础镜像：从 base 开始全部重做。

3. 缓存的“陷阱”

hash 只看指令的文本，不看指令执行的结果。RUN apt-get update && apt-get install -y python3 第一次构建时装的是当时最新的 python3，三个月后再构建，文本没变，缓存命中，用的还是三个月前那一层，不会去装新版本。这和 Docker 的层缓存行为一样。想强制重做，可以在构建时要求跳过缓存。

finalize 和 optimize 两个阶段从不查缓存，每次都重做，因为它们要在最终的状态上跑启动命令、采集预取表，结果和运行时机有关。

五、和 Docker 层的异同

Docker 的层 E2B 的层
存的是什么 文件系统的差分（一个 tar 包） 整台虚拟机的快照：内存 + 磁盘 + CPU 状态
能不能直接运行 不能，要叠起来再启动进程 能，最后一层就是一台随时可恢复的机器
缓存键 上一层 + 指令文本 + 文件内容 同左
每条 RUN 的环境 新 shell，副作用只留在文件里 同左
中间层占的空间 只有文件差分 文件差分 + 内存差分

最大的不同在第一行：E2B 的每一层都包含内存。这意味着每一层暂停时，都要判断“这条指令执行期间改了哪些内存页”。判得准，一层只多存几 MiB；判得不准，每一层都要多存上百 MiB。第 19 篇会看到，在 ARM 适配的早期版本上，后一种情况真的发生了。

六、默认用户

在用户的指令之前，还有一个小阶段：创建一个叫 user 的普通用户，把它加进有 sudo 权限的组，并把它设为后续指令的默认用户。用户在 SDK 里跑命令，默认就是以 user 身份执行的。

这一步在 Debian 系的镜像里用 adduser 和 sudo 组；可 openEuler 这类发行版没有 adduser 这个命令，sudo 权限组也叫 wheel 而不叫 sudo。第 9 篇会讲我们怎么改。

本篇小结

概念 一句话解释
一条指令一层 恢复 → 通过 envd 执行 → 暂停；层是缓存的单位
六类指令 RUN、COPY/ADD、ENV/ARG、WORKDIR、USER；没有 CMD、ENTRYPOINT
当前状态 用户、目录、环境变量；随快照保存，最后交给 envd 当默认值
独立 shell 每条 RUN 的 export、cd 不会带到下一条
一条 RUN 的路径 template-manager → orchestrator 代理 → envd → bash，输出流回构建日志
层 hash 链 本层 hash 包含上一层 hash，任何一环变化，之后全部重做
缓存只看文本 指令文本不变就命中，不管软件源有没有更新
和 Docker 的区别 E2B 的层包含内存，判脏的准确度直接影响每层大小

下一篇预告：《finalize 与 optimize：拍下最终那张快照》。模板的最后一张快照拍在什么时刻？为什么要重启一次、跑启动命令、等就绪再暂停？预取表又是什么，它怎样让启动更快？

finalize 与 optimize：拍下最终那张快照

本篇目标：所有指令执行完之后，还差最关键的一步：拍下模板的最终快照。本篇讲 finalize 阶段为什么要“重启一次、跑配置、启动用户服务、等就绪、再暂停”；为什么快照要拍在“就绪那一刻”；optimize 阶段怎样记录预取表；以及一个模板最终由哪些东西组成、什么时候才算真正可用。

一、finalize：最后一次开机

finalize 阶段总是重新开一台虚拟机，而不是从最后一条指令那一层恢复。原因是最终那一层的磁盘路径要指向最终 build ID 的产物，必须用新的配置重新拉起。

开机之后依次做四件事：

步骤 做什么 时限
1. 跑配置脚本 configure.sh：确保默认用户存在、复制家目录的默认文件、调整权限、开 swap 等 5 分钟
2. 启动用户服务 运行用户给的 start 命令（比如启动一个 Jupyter 服务），它会一直在后台跑 —
3. 等就绪 每 2 秒执行一次用户给的 ready 命令（比如 curl localhost:8888），直到成功 10 分钟
4. 拍快照 把虚拟机里的磁盘缓存刷到磁盘，然后暂停 —

几个细节：

  • 没有 start 命令也没有 ready 命令：跑完配置脚本就直接拍快照，模板冻住的那一刻就是“系统刚配好”。
  • 有 start 命令但没写 ready 命令：默认的“就绪检查”是 sleep 20，即固定等 20 秒。这不是探测，只是一个保守的等待：可能等不够（服务还没开始监听就被冻住了），也可能等太久（白白多花 20 秒构建时间）。好处是用户不用为每个模板写健康检查。
  • 就绪之后还要确认 start 命令真的在跑，没有提前崩掉，才去拍快照。
  • 刷盘这一步不能省。虚拟机里的程序写文件，数据可能还停留在内存的文件缓存里，没落到磁盘上。快照恢复后，系统会继续使用这块磁盘；没刷下去的那部分，在磁盘上就是缺的。虽然内存快照里也有这份缓存，但内存和磁盘必须一致，所以先刷再拍。

二、为什么快照要拍在“就绪那一刻”

这是整个 E2B 设计里最核心的一个决定。

快照记下的是虚拟机在那一刻的全部状态：内存里有哪些进程、每个进程执行到哪一行、打开了哪些文件、网络连接处于什么状态。以后每次从这张快照恢复，虚拟机都从同一刻接着往下跑。

如果快照拍在“开机前”，每次恢复都要从头开机，几秒钟；拍在“开机完成、envd 就绪”，每次恢复出来 envd 就已经在跑，可以立刻接受命令；拍在“用户的 Jupyter 已经启动、可以访问”，每次恢复出来 Jupyter 就是现成的，连它的启动时间也省了。

这就是为什么 E2B 能做到一百多毫秒可用：所有“准备”的时间都在构建时花掉了，而且只花一次。 之后成百上千次启动，都直接从“已准备好”开始。

这个设计也带来一些需要专门处理的副作用：

副作用 原因 怎么处理
所有沙箱的内存一开始一模一样 从同一张快照恢复 恢复后通过 envd 的 /init 给每台注入不同的身份、令牌、环境变量（第 13 篇）
虚拟机里的时钟停在构建那一刻 快照冻结了时间 恢复后校时（第 13 篇）
看门狗误判服务卡死 时钟跳变 构建时就关掉看门狗（第 6 篇）

三、optimize：记下“一恢复就会用到哪些内存”

模板拍好了。可从它恢复时，内存是懒加载的（第 12 篇）：虚拟机访问哪一页，才去取哪一页。刚恢复的那一小段时间里，envd、用户服务、内核都会密集地访问内存，引发一阵“缺页风暴”，每次缺页都要等 orchestrator 去取数据。

如果能提前知道这些页是哪些，就可以在虚拟机刚开始跑的同时，后台把它们先搬进来，等虚拟机真用到时已经在那了。

optimize 阶段就是去获取这份名单：

  1. 从刚拍好的最终快照恢复一台虚拟机；
  2. 等 envd 能应答；
  3. 读出这段时间里所有通过缺页进来的内存块，以及它们的先后顺序；
  4. 再恢复一次，重复一遍；
  5. 两次结果取交集：只保留两次都出现的块；
  6. 写进 metadata.json，成为这个模板的预取表。

取交集是为了滤掉偶然的访问（比如某个后台任务恰好在那一刻醒来），只留下“每次恢复都一定会用到”的部分。代价是可能漏掉一些只在一次运行里出现、但其实也很常用的块。

optimize 不产生新的一层，它只修改最终那一层的元数据。它也是“尽力而为”的：采集失败只记警告，模板照常可用，只是启动时没有预取可用。

四、模板最终长什么样

一个构建成功的模板，在存储里是这样一组东西：

内容 说明
一条代际链 base 层 → 默认用户层 → 每条指令一层 → finalize 层，每层一个 build ID，各有三件套和映射表
最终 build ID finalize 层，也就是这个模板版本对外的 ID
metadata.json 内核与 Firecracker 版本、默认用户与目录、环境变量、start 与 ready 命令、预取表
数据库记录 api 那边记着“模板 X 的当前版本是这个 build ID”

用户 Sandbox.create("my-python") 时，api 把模板名翻译成最终 build ID，交给 orchestrator 去恢复。

五、什么时候才算可用

构建的最后一步是等所有层都上传完成，然后才把构建标记为成功。

上一篇讲过，每一层暂停后是先放进本地缓存、再异步上传的，为的是不让上传拖慢下一层。可如果这时就告诉用户“构建好了”，用户马上 Sandbox.create，而沙箱被调度到另一个节点上，那个节点要从存储里取这个模板，可它还没传完。所以必须等全部上传完成才宣布可用。

这个“元数据不能早于数据宣布就绪”的原则，在第 16 篇的暂停里还会再见到一次。

六、构建在一个模板的一生里有多重要

把五个阶段串起来看，一次构建大概经历了：

  • 两次冷启动（base 阶段）+ 一次冷启动（finalize）；
  • 指令条数那么多次的“恢复—执行—暂停”；
  • 两次恢复（optimize）；
  • 若干次上传。

它比启动一台沙箱贵几个数量级，但对一个模板只做一次。之后这个模板可能被启动成千上万次，每次都直接享用构建时的成果。这是一笔典型的“预先投入，反复收益”的交易。

本篇小结

概念 一句话解释
finalize 重开一台虚拟机：配置 → 启动用户服务 → 等就绪 → 刷盘 → 拍快照
默认就绪检查 有 start 无 ready 时固定等 20 秒
拍在就绪那一刻 所有准备时间在构建时花掉，之后每次恢复都从“已就绪”开始

把构建搬到 ARM 上：我们改了什么

本篇目标：前面四篇讲的是上游 E2B 的构建流程，它在 x86 和 Ubuntu 上写得很顺。可我们要在鲲鹏（ARM）服务器、openEuler 系统上跑。本篇把构建路径上的修改分成三类讲：写死了架构的地方、发行版不同的地方、系统环境不同的地方。然后讲两个和构建有关的故障：一个是 Firecracker 版本目录引起的，一个是内存上限引起的，后者的症状和病因隔了三个服务。最后说明为什么模板构建的虚拟机不走第 15 篇的启动优化。

一、先看全貌

下面挑几处展开。

二、架构写死的地方

1. 镜像平台

第 6 篇讲过，拉镜像时要指定平台，拉下来再检查一遍架构字段。上游把这个平台写成了一个编译期常量 amd64，不是配置项。在 ARM 机器上，结果有两种：多架构镜像会拉到 x86 版本，单架构的 ARM 镜像则被第二道检查拦下来，报“镜像不是 amd64”。

改法是把常量改成 arm64。这意味着一个 orchestrator 二进制只能构建一种架构的模板。这本来就是合理的：ARM 机器上的 Firecracker 只能跑 ARM 的虚拟机。

2. busybox

base 阶段的第一次开机靠 busybox 当 1 号进程（第 6 篇）。上游把一个 x86 的 busybox 二进制直接编进 orchestrator 里，构建时写进磁盘。ARM 虚拟机的 CPU 根本不认识 x86 指令，内核一启动就找不到能执行的 init，构建在第一步就失败。

改法是同时内嵌 x86 和 arm64 两份 busybox，程序启动时按自己的架构挑一份。这里还有一个踩过的坑：最初用的是一个基于 musl 的 busybox，它体积小，但里面没有 bash，而 configure.sh 是 bash 脚本，跑不起来。最后换成了基于 glibc 的版本，同时把 configure.sh 改成只用最基本的 sh 语法，两头都不再依赖 bash。

三、发行版不同的地方

Ubuntu 和 openEuler 都是 Linux，但在构建会碰到的地方差得不少：

事情 Ubuntu / Debian openEuler / RHEL 系
查一个包装没装 dpkg-query rpm -q
装包 apt-get install dnf install
建用户 adduser --disabled-password（一个交互友好的脚本） useradd -m -s /bin/bash
有 sudo 权限的组 sudo wheel
识别标志 有 /etc/debian_version 没有

我们的改法都是先探测、再分支，而不是把 Ubuntu 的写法替换掉：

  • provision.sh：读 /etc/os-release 拿到发行版 ID，查包用 dpkg-query 还是 rpm -q、装包用 apt-get 还是 dnf，各走各的。遇到不认识的发行版直接报错。
  • 默认用户和 USER 指令：先在虚拟机里试一下 test -f /etc/debian_version，有就用 adduser，没有就用 useradd；再试一下 getent group wheel，有 wheel 组就加进 wheel，否则加进 sudo。
  • configure.sh：同样按 /etc/debian_version 分支。openEuler 那一支还要多处理一种情况：家目录已经存在时 useradd -m 会报错，所以先检查，存在就不让它建家目录，再手动把默认文件复制进去。

这样同一份代码既能构建 Ubuntu 模板，也能构建 openEuler 模板。

装包列表也精简了：上游装 12 个包，其中 fuse3、iptables、git、nfs-common 这几个，或者在 openEuler 上包名不同，或者对沙箱的基本功能不是必需的。我们保留了 systemd、ssh、sudo、chrony、linuxptp、socat、curl、证书这些必需品。用户真需要 git，可以在自己的 Dockerfile 里装。

四、系统环境不同的地方

1. envd 的 systemd 单元

上游给 envd 的 systemd 单元里写了一组资源控制指令：委托 cgroup、保证至少 50 MB 内存、开 CPU 记账、把 CPU 权重调到最高。目的是让 envd 在沙箱资源紧张时也能得到照顾。这组指令依赖 guest 内核和 systemd 的 cgroup 配置，在我们的 guest 环境里不适用。我们把这一组指令去掉了，envd 作为普通服务运行。

2. 宿主的 cgroup

orchestrator 启动时要初始化一棵 cgroup 树，用来给每台沙箱记账。上游要求宿主必须是 cgroup v2，否则直接报错退出。部分鲲鹏宿主跑的是 cgroup v1。我们的改法是检测到 v1 就跳过这棵树的初始化，orchestrator 照常启动。

这一处改动的影响不止于构建。ARM 移植时还把“把 Firecracker 进程放进它自己那个 cgroup”的那段代码注释掉了，于是所有 Firecracker 进程都继承了 orchestrator 所在的 cgroup。这件事在第 12 篇讲内存账、第 15 篇讲绑核时会再出现。

3. CPU 信息

orchestrator 会上报本机的 CPU 信息（家族、型号），供调度时参考。上游用的库在 ARM 上读不到这两个字段，返回空值，上游代码见到空值就报错。改法是在 ARM 上给出兜底值（家族 arm64、型号 0）。

五、故障一：Firecracker 的版本目录

宿主上的 Firecracker 按版本号放在 /fc-versions/<版本>/firecracker。模板构建时记下用的是哪个版本，以后启动这个模板的沙箱也用同一个版本。

我们在 ARM 上用的是自己编译的 Firecracker，它基于上游的 v1.12.1 版本，但部署时放在 v1.13.1 这个目录下，因为代码里查找版本时用的键是 v1.13.1。曾经有一次试图把一切改成名副其实的 v1.12.1，结果版本号的来源不止一处：环境变量里残留的旧值优先于代码里的常量，构建登记的版本指向了一个根本不存在的目录，报 stat /fc-versions/v1.13.1/firecracker: no such file or directory。实地测试又发现改名后运行时仍然按 v1.13.1 去找。最后的决定是不再和查找键较劲：目录就叫 v1.13.1，文档里说清楚“里面是基于 v1.12.1 自己编译的版本”。

这个故障的教训是：版本号这类“标签”往往有多个来源（常量、环境变量、配置文件、数据库），改一处之前要先把所有来源找全。

六、故障二：一次远离病因的内存故障

这是构建路径上最有代表性的一次故障。

症状：部署脚本卡在“等 api 健康”，最后报“部署超时”。api 一直返回 503。

表面上看，问题在 api。但 api 只有在发现至少一个可用的 orchestrator 节点时才报健康，而它一个节点都没发现。

再往下看，orchestrator（也就是 template-manager，单节点部署里它们是一个进程）一直在被 Nomad 反复重启，重启次数用完后任务被标记为失败。

再往下看，每次重启前，它都被内核的内存控制组强制杀掉了，原因是超过了 8 GiB 的内存上限。

真正的病因：用一个 200 MB 的基础镜像、跳过缓存做一次完整构建。进程自身的内存只有 125 MB 左右，可是：

  • 解包镜像各层时产生了大量文件缓存，这部分算在这个进程的内存账上；
  • 构建过程中往一个 tmpfs（内存文件系统）目录里写了文件，tmpfs 的页不能像普通文件缓存那样被回收，只能换出到交换分区，而交换分区已经没有余量了。

于是内核只能杀进程。

这条链上，从“构建内存超限”到“部署超时”隔了三个服务（template-manager → Nomad → api），终点的报错里没有任何一个字提到内存。

修法经历了一个来回：

  1. 先把上限从 8 GiB 提到 32 GiB，实测能通过一次 200 MB 基础镜像的完整重建；
  2. 后来在一台 1 TB 内存的机器上，觉得 32 GiB 太紧，提到 256 GiB，当作“跑飞了也不至于拖垮整机”的护栏；
  3. 再后来换到一台 128 GiB 内存的机器上，256 GiB 的申请让 Nomad 根本调度不了这个任务（资源不够），orchestrator 永远起不来，症状和第一次一模一样：api 503，部署卡住；
  4. 最终回到 32 GiB，并在配置旁写明两种失败模式：太小会被杀，太大会调度不上。

还有一个容易误解的地方：这个上限管的是 orchestrator 进程和构建，不包括虚拟机的内存。虚拟机内存由大页背衬，大页只记在单独的大页账上，不进这个上限（第 12 篇）。所以“同时跑几十台沙箱都没事”并不能说明这个上限够用，构建时解包镜像产生的文件缓存才是压垮它的那根稻草。

七、模板构建不走启动优化

第 15 篇会讲一个重要的启动优化：用一个小程序 fc-netns-exec 替换启动 Firecracker 时的 ip netns exec。这个优化只用于从快照恢复的沙箱，模板构建时开的虚拟机仍然走原来的 ip netns exec。

原因是两者用的磁盘路径机制不同：模板构建的虚拟机用的是一组固定路径，不带模板 ID 和 build ID；从快照恢复的沙箱则需要把快照里录死的路径重新指向自己的文件（第 11 篇）。优化代码判断：如果没有模板 ID 或 build ID，就退回原来的方式。构建一次只开几台虚拟机，不存在高并发争用，优化的收益本来就很小，没有必要冒风险。

启动就是恢复：一次 Sandbox.create 的全景

本篇目标：进入第三部分“启动沙箱”。本篇先把一次 Sandbox.create 从头到尾走一遍，建立全景：请求经过 api 到达 orchestrator；orchestrator 先过一道“准入闸门”；然后进入核心函数 ResumeSandbox，它分成“串行准备 → 三路并行 → 串行收尾”三段；最后 guest 里的 envd 醒过来。后面四篇分别把其中的 Firecracker、内存、磁盘与网络放大来看，第 14、15 篇讲时间和优化。

一、名字里的提示

orchestrator 里负责“启动一台沙箱”的那个函数，名字叫 ResumeSandbox：恢复沙箱，不是创建沙箱。

这个名字说出了 E2B 最核心的事实：它从不冷启动用户的沙箱。 模板构建时，系统已经开机、envd 已经就绪、用户的服务已经启动，那一刻被拍成了快照（第 8 篇）。Sandbox.create 做的是把这张快照加载进一个新的 Firecracker 进程，让虚拟机从那一刻接着跑。

而从用户暂停的快照恢复一台沙箱（Sandbox.connect，第 18 篇），走的也是同一个 ResumeSandbox。两者唯一的区别是用哪一张快照：模板的最终快照，还是暂停时留下的那一张。

冷启动 快照恢复
内核引导 要，几百毫秒到一秒 不要，内核状态在快照里
systemd 拉起几十个服务 要，几秒 不要
envd 初始化 要 不要，envd 进程在快照里本来就在跑
用户服务（如 Jupyter）启动 要 不要，构建时已经启动
宿主准备五样东西 要 要
加载快照 不要 要，几十毫秒

省掉的是 guest 内部的所有初始化；省不掉的是宿主侧的准备。后面会看到，启动的时间几乎全花在宿主侧。

二、请求链

SDK ── Sandbox.create("my-python") ──▶ api
api ── 认证、查模板最新 build ID、挑节点 ──▶ orchestrator 的 Create（gRPC）
orchestrator ── 准入 → ResumeSandbox ──▶ Firecracker + envd

api 做三件事：

  1. 验证 API 密钥，确认这个团队有权使用这个模板、没超过配额；
  2. 把模板名翻译成当前版本的 build ID；
  3. 选一个节点，调用那个节点上 orchestrator 的 Create 接口。

我们是单节点部署，第 3 步没有选择余地。

三、准入闸门

orchestrator 的 Create 接口在真正动手之前，先过两道检查：

第一道：节点上的沙箱总数有没有超上限。 超了直接拒绝。上游默认 200 台，我们放宽到 10000，因为我们的机器内存很大，真正的上限由内存和 CPU 决定，而不是这个数字。

第二道：同时“正在启动”的沙箱有没有超上限。 这是一个信号量：手里有 N 张票，每个启动拿一张，启动完还回去，票发完了后来的就得等。

为什么要限制“同时启动”的数量？因为启动是一个资源密集的瞬间：要创建进程、准备网络、加载快照、密集缺页。一百个沙箱同时启动，CPU、磁盘、内核锁都会被挤爆，每个都慢，甚至一起超时。限制同时启动的数量，让它们排队分批进行，总体反而更快、更稳。

上游这道闸门很紧：

参数 上游 我们
同时启动上限 3 代码默认 500，部署配置为 30，可用环境变量调整
从模板创建、拿不到票时 立即拒绝，让 api 换个节点重试 排队等待
从暂停快照恢复、拿不到票时 排队等，最多 15 秒 排队等，最多 300 秒
整个请求的超时 60 秒 300 秒

上游的设计适合多节点的大集群：一个节点忙，api 换一个就是了。我们是单节点，“换一个节点”无处可换，立即拒绝只会让用户看到失败。所以改成一律排队，并把超时放宽。这些参数怎样影响高并发下的表现，第 14、15 篇细讲。

四、ResumeSandbox 的三段结构

过了闸门，进入核心函数。它的骨架是三段：

第一段：串行准备

步骤 做什么
取模板句柄 不阻塞：缓存里没有就在后台开始拉取模板文件，先拿回一个“句柄”
发起几项后台准备 同时开始：领一个网络槽位、搭好根盘（NBD + 写层）、准备内存处理器（uffd）、开始预取
等网络槽位 槽位池预先建好，通常立刻就能领到
读模板元数据 版本、内核、Firecracker 版本等
创建 Firecracker 进程对象 生成启动脚本、检查二进制和内核文件存在。进程此时还没真正启动

第二段：三路并行

路 做什么 详见
拉起 Firecracker 执行启动脚本：进入私有的挂载和网络命名空间，启动 Firecracker 进程，等它的 API 套接字出现 第 11 篇
等 uffd 套接字 等内存处理器的通信套接字准备好 第 12 篇
接上根盘 把根盘的路径链接到 Firecracker 能找到的位置 第 13 篇

三路同时开始，全部完成才进入下一段。所以这一段的耗时等于最慢的那一路。

第三段：串行收尾

步骤 做什么
加载快照 通过 Firecracker 的 HTTP 接口加载 snapfile，告诉它内存由 uffd 提供
恢复运行 让 vCPU 开始执行
写 MMDS 把这台沙箱的身份信息写进 Firecracker 的元数据服务，guest 里可以读到
初始化 envd 调用 envd 的 /init：交给它访问令牌、环境变量、默认用户等

/init 成功返回，ResumeSandbox 就结束了。orchestrator 把沙箱登记进自己的表，告诉 api“创建成功”，api 再告诉 SDK。

五、guest 里发生了什么

从 guest 的角度看，这次“启动”是这样的：

  1. 时间停在构建那一刻，所有进程都停在原地；
  2. vCPU 恢复执行，进程们接着往下跑，好像什么都没发生；
  3. 一跑起来就开始访问内存，每次访问到还没取回的页都触发一次缺页，由宿主上的 uffd 处理器补上；
  4. envd 收到 /init，换上新的身份和环境变量；
  5. 时钟是错的（还停在构建时），需要校时；
  6. envd 对外应答，沙箱可用。

envd 没有重新启动，它只是“醒了过来”，接收了一份新的身份。这就是第 2 篇说的“envd 在构建时就已启动并冻进快照”的含义。第 13 篇会把这几件事细讲。

六、失败了怎么办

ResumeSandbox 里每准备好一样资源，就立刻登记一个对应的“清理函数”。任何一步失败，就按相反的顺序把已经登记的清理函数全部执行一遍：归还网络槽位、拆掉根盘、停掉 uffd、杀掉 Firecracker 进程。这样即使启动到一半失败，也不会在宿主上留下垃圾。

不过有一种情况例外：orchestrator 进程本身被强行杀掉时，清理函数来不及执行。网络槽位这类资源就会泄漏在宿主上。第 13 篇会讲这个问题，以及为什么只能通过“停服务、再清理”来回收。

省掉了什么 guest 内部的全部初始化；省不掉宿主侧的准备

拉起 Firecracker：启动脚本与加载快照

本篇目标：上一篇说启动分三段，中间那段最慢的一路是“拉起 Firecracker”。本篇放大看它：快照里录死了磁盘和内核的路径，每台沙箱却要用自己的文件，这个矛盾怎么解决；启动 Firecracker 的那条 shell 管线每一步在做什么；Firecracker 起来之后，orchestrator 通过哪几次 HTTP 调用把快照加载进去、让虚拟机跑起来。最后讲 ARM 上对内核启动参数和机器配置的两处修改。

一、一个矛盾：快照里录死了路径

Firecracker 打快照时，会把虚拟机配置的一部分也记进 snapfile，其中包括磁盘文件和内核文件的路径。加载快照时，它会按这些路径去打开文件。

问题是：模板构建时，磁盘在某个路径（比如 /fc-vm/rootfs.ext4）；以后从这个模板启动的几百台沙箱，每一台的磁盘在宿主上都是不同的设备或文件（各自的 NBD 设备，第 13 篇）。可它们加载的是同一张快照，快照里写的是同一个路径。

怎样让同一个路径，在每台沙箱眼里指向各自不同的文件？

二、解法：私有挂载命名空间加符号链接

答案是第 3 篇讲的挂载命名空间。每个 Firecracker 进程都运行在自己私有的挂载命名空间里，在这个命名空间里：

  1. 在快照记录的那个固定目录上盖一层空的内存文件系统（tmpfs），把宿主上原来的内容遮住；
  2. 在这层 tmpfs 里放一个符号链接，名字是快照记录的那个文件名，指向本沙箱自己的磁盘设备；
  3. 内核文件同理。

由于挂载命名空间是私有的，这层 tmpfs 和符号链接只有这个 Firecracker 进程看得见。几百个 Firecracker 各自在“同一个路径”上看到各自的文件，互不干扰。

这就像一栋楼里每户人家都有一个“101 号信箱”，但每户的“101 号信箱”是自己家门口那个。

三、启动脚本

orchestrator 为每个 Firecracker 生成一段启动脚本，执行方式大致是：

unshare -m -- bash -c "
  mount --make-rprivate / &&
  mount -t tmpfs tmpfs <沙箱目录> -o X-mount.mkdir &&
  ln -s <本沙箱的磁盘设备> <快照记录的磁盘路径> &&
  mkdir -p <内核目录> &&
  ln -s <宿主上的内核文件> <快照记录的内核路径> &&
  ip netns exec <网络命名空间> <firecracker> --api-sock <套接字路径>
"

逐段看：

片段 作用
unshare -m 创建一个新的私有挂载命名空间，后面的命令都在里面执行
mount --make-rprivate / 把整棵挂载树设为“私有”，保证里面的挂载不会传播回宿主
mount -t tmpfs ... 在沙箱目录上盖一层 tmpfs
ln -s ...（两次） 在固定路径放符号链接，指向本沙箱的磁盘和内核
ip netns exec <ns> 进入这台沙箱的网络命名空间
firecracker --api-sock <sock> 启动 Firecracker，它会在指定位置创建自己的 HTTP 接口套接字

最后一步 ip netns exec 让 Firecracker 运行在这台沙箱的网络命名空间里，于是它创建的 tap 网卡也在里面，虚拟机的网络就和宿主、和其他沙箱隔开了。

这条管线看起来很平常，但里面藏着启动最大的性能问题：mount --make-rprivate / 和 ip netns exec 都要遍历整棵挂载树、修改内核的全局数据结构，几百个沙箱同时做时要在内核的一把全局锁上排队。第 15 篇专门讲这个问题，以及我们怎样只换掉最后一环就省下一大截时间。

四、等 Firecracker 就绪

脚本启动后，orchestrator 要等 Firecracker 准备好接收命令。判断标准是：它的 API 套接字文件出现了。

上游的做法很朴素：每 10 毫秒检查一次文件在不在。平均要白等 5 毫秒，还有长尾。

等的同时，orchestrator 还在另一边盯着启动脚本这个进程：如果它提前退出（比如 Firecracker 二进制不存在、内核文件找不到），就立刻取消等待、报告真正的原因。这本来是上游的设计，可我们发现上游在等套接字的函数里用了一个和调用方无关的超时上下文，取消信号传不进去，结果 Firecracker 早已死掉，orchestrator 还在傻等，一直等到 300 秒超时，报的还是“超时”而不是真正的死因。第 15 篇讲这个修复。

五、加载快照的几次 HTTP 调用

Firecracker 就绪后，orchestrator 通过它的 HTTP 接口依次发出几个请求：

请求 内容 典型耗时
PUT /snapshot/load 加载 snapfile；内存后端设为 uffd，并给出 uffd 套接字的路径；先不要恢复运行 约 20～30 ms
PATCH /vm（state = Resumed） 让 vCPU 开始执行 不到 1 ms
PUT /mmds 写入这台沙箱的元数据：沙箱 ID、模板 ID、访问令牌的哈希等 不到 1 ms

加载快照是其中最重的一步。Firecracker 要读 snapfile，重建 KVM 虚拟机、vCPU、中断控制器、各个 virtio 设备，并恢复它们的状态。它还要连上 uffd 套接字，把虚拟机的内存区域交给 uffd 处理器，告诉它“这些内存的缺页由你负责”。注意，这时一页内存都没有读，内存是之后靠缺页一页页回来的（第 12 篇）。

加载时有一个参数“先不要恢复运行”：加载完，虚拟机处于暂停状态，由 orchestrator 再单独发一个“恢复”请求。分两步是为了在中间插入别的准备工作。

MMDS（MicroVM Metadata Service）是 Firecracker 内置的一个小型元数据服务，guest 里的程序可以通过一个固定的内部地址读到宿主写进去的内容，类似云主机的元数据接口。E2B 用它把“你是哪台沙箱”告诉 guest 里的 envd。

六、ARM 上的两处修改

1. 内核启动参数

每台虚拟机的内核在开机时会收到一串启动参数。虽然从快照恢复时内核不会重新开机，但构建时开机要用，而且这串参数会被记录下来。上游给的参数里有几项是 x86 专用的：

参数 含义

开关 上游 我们 原因

下一篇预告：《内存怎么回来：懒加载、预取与大页》。加载快照时一页内存都没读，那虚拟机的内存是怎么回来的？一页内存从快照文件到 guest 手里经过了什么？一台空闲沙箱在宿主上到底占多少内存？

内存怎么回来：懒加载、预取与大页

本篇目标：上一篇说加载快照时一页内存都没读。那虚拟机的 2 GiB 内存是怎么回到它手里的？本篇讲三件事：用 userfaultfd 懒加载，guest 用到哪页补哪页；用预取表在后台提前搬，缓解刚恢复时的缺页风暴；用大页背衬 guest 内存。最后用一组实测数字回答一个很实际的问题：一台空闲沙箱在宿主上到底占多少内存，并发能开多少台先被什么卡住。

一、为什么不一次读回来

一台 2 GiB 内存的沙箱，如果启动时先把 2 GiB 全部从快照文件读进内存，哪怕磁盘有每秒 2 GB 的速度，也要 1 秒。几百台同时启动，磁盘带宽直接被打满。

而实际上，一台刚恢复的沙箱用不到这么多。实测一台空闲的沙箱（2 GiB 规格），恢复后 5 分钟内只碰过约 157 MiB 的内存，不到 8%。剩下 92% 的内存，可能永远不会被访问。

所以 E2B 的做法是懒加载：先不读，guest 访问到哪一页，再去取哪一页。这就是第 3 篇讲的 userfaultfd 的用武之地。

二、补一页的路径

加载快照时，Firecracker 为 guest 内存映射了一段 2 GiB 的地址空间，但没有放进任何内容，然后把这段内存登记给 uffd，再通过一个 Unix 套接字把 uffd 的文件描述符和内存布局交给 orchestrator。从此，这段内存上发生的每一次缺页，都会通知 orchestrator 里的 uffd 处理器。

一次缺页的完整路径：

  1. guest 里某个程序访问了一个地址，这一页还没有内容；
  2. CPU 陷出，KVM 把这次访问报告给宿主内核，内核发现这段内存登记了 uffd，于是挂起这个 vCPU，向 orchestrator 发出一条缺页消息；
  3. orchestrator 的 uffd 处理器收到消息，算出这个地址对应 memfile 的哪个偏移；
  4. 查映射表（第 4 篇），找到这一块数据在哪一代的哪个文件里；
  5. 从本地缓存读出这一块。如果本地缓存还没有，就从持久化存储拉下来，放进缓存；
  6. 用 UFFDIO_COPY 把内容填进那一页；
  7. 内核唤醒 vCPU，它重做刚才那次访问，这次成功了。

一次缺页填多少？一整个 guest 页。E2B 的 guest 内存由 2 MiB 大页背衬，所以一次缺页就填 2 MiB。映射表里 memfile 的块大小也是 2 MiB，正好一次缺页对应一块（第 20 篇会看到，我们为了精确增量改动了这个对应关系）。

三、大页

guest 内存为什么用大页？

  • 运行时更快：虚拟机的地址翻译本来就比真机多一层（guest 页表 + 宿主的第二层页表），TLB 不命中的代价更高。大页让 TLB 覆盖范围扩大 512 倍。
  • 缺页次数更少：一个 400 MiB 的工作集，用 2 MiB 大页约 200 次缺页，用 4 KiB 小页要约 10 万次。每次缺页都是一次“内核 → orchestrator → 内核”的往返，次数少很多。

大页要提前在宿主上预留成一个大页池。我们的部署脚本在启动时向内核申请一大批 2 MiB 大页，挂在 /mnt/hugepages。有几点值得知道：

事实 含义
按需落地，不预留 Firecracker 映射了 2 GiB 的大页地址空间，但只有真正被缺页填进去的大页才从池里拿走
只增不减 guest 没有内存回收机制（balloon），碰过的页不会还回来，长期运行的沙箱会慢慢往规格上限靠
关闭即归还 沙箱销毁后，它占的大页全部回到池里
池子不会自己消失 停掉所有服务后，大页池仍然被内核预留着，要显式释放（第 15 篇）

四、预取：在缺页风暴之前先搬

懒加载有一个代价：刚恢复的那一小段时间里，envd、内核、用户服务都会密集地访问内存，几十上百次缺页接踵而来，每次都要等 orchestrator 去取。

第 8 篇讲过，构建模板的 optimize 阶段记下了一张预取表：“一恢复就会被访问的内存块，以及它们的先后顺序”。启动时，orchestrator 按这张表在后台提前把这些块搬进 guest 内存。

预取分两组工作者：

工作者 做什么 什么时候开始
取数据 按预取表的顺序，把块从存储读进本地缓存 立刻开始，甚至在 Firecracker 启动之前
填内存 把取好的块用 UFFDIO_COPY 填进 guest 内存 等 uffd 准备好之后

取数据和启动 Firecracker 是同时进行的。等 Firecracker 起来、uffd 就绪，很多块已经在本地缓存里等着了，直接填进去就行。

预取和真正的缺页走的是同一个填页函数。如果 guest 先访问了一页，缺页处理就把它填上；预取工作者后来再想填这一页，发现已经有了，就跳过。反过来也一样。两者不会冲突。

我们把两组工作者的并发数都翻了一倍：取数据从 16 个到 32 个，填内存从 8 个到 16 个。我们的机器核数多、本地磁盘快，更高的并发能更快地把预取表搬完。

五、成本被推迟了

懒加载让“启动”本身很快：加载快照只要几十毫秒，因为一页内存都没读。但搬内存的成本没有消失，只是推迟到了每一次缺页上。

鲲鹏 950 上的一个实测：一台沙箱在快照前把一份 192 MiB 的内存数据读一遍，用了 590.9 ms；暂停再恢复之后，第一次读同一份数据用了 702.6 ms，多出约 112 ms。这 112 ms 不算在“启动时间”里，而是由 guest 里第一个访问这些页的程序承担。

这是一个合理的交易：大部分内存永远不会被访问，没必要为它们付费；真正要用的那部分，用到时再付，而且预取已经帮忙付掉了最常用的那一部分。

六、一台空闲沙箱占多少内存

一个很实际的问题：一台什么都不做的沙箱，在宿主上到底占多少内存？我们用 2 vCPU、2048 MiB 规格的模板，分别启动 1、10、50 台空闲沙箱，测宿主上的变化，再做线性拟合：

部分 每台沙箱 是什么
大页 约 157 MiB guest 实际碰过的内存
普通内存 约 194 MiB 下面四项之和
　沙箱目录的文件页 62.4 MiB orchestrator 用 mmap 打开的这台沙箱的运行态文件
　其他文件缓存 104.8 MiB 大概率是根盘经 NBD 读写、读模板文件产生的缓存
　匿名内存 22.3 MiB orchestrator 为这台沙箱用的堆约 20 MiB，Firecracker 自身约 2.3 MiB
　其他 4.2 MiB 主要是内核对象
合计 约 350 MiB

两点值得记住：

memory_mb = 2048 是上限，不是占用。 空闲时只碰了 7.7%。规格调大，空闲占用几乎不变；真正决定空闲占用的是镜像内容，也就是快照那一刻 guest 里常驻了多少东西。

普通内存全部记在 orchestrator 的账上。 第 11 篇说过，ARM 移植时 Firecracker 进程没有被放进自己的 cgroup，而是留在 orchestrator 所在的 cgroup 里。guest 的大页走单独的大页账，不进这个 cgroup 的内存上限；但 Firecracker 和 orchestrator 为这台沙箱产生的文件缓存、匿名内存，全部算在 orchestrator 那个 32 GiB 的上限里（第 9 篇讲的那个上限）。

七、并发容量先被什么卡住

把上面的数字和两个上限放在一起算：

约束 能撑的空闲沙箱数
orchestrator 的 cgroup 开始回收旧缓存 约 89
cgroup 里的旧缓存全部挤完 约 167
大页池（约 391 GiB），每台都用满 2 GiB 195
大页池，每台只用空闲时的 157 MiB 2554

结论有点反直觉：先到上限的是 orchestrator 的 cgroup，不是大页池。 约 89 台空闲沙箱时，cgroup 用量就碰到了 32 GiB，内核开始回收构建等操作留下的旧文件缓存；超过约 167 台，就只能回收沙箱自己正在用的页，沙箱会变慢，严重时可能触发内存超限把 orchestrator 杀掉。

所以想稳定支撑 X 台空闲沙箱，orchestrator 的内存上限至少要 32 GiB（构建需要）再加上 X × 0.19 GiB。这个结论只对空闲沙箱成立；沙箱跑起重任务后，大页池按规格上限算的 195 台才是有保证的下限。

磁盘、网络与 envd：其余几样怎么就位

本篇目标：宿主为一台沙箱准备的五样东西里，Firecracker 和内存已经讲过。本篇讲剩下三样：根盘怎样由“模板只读层 + 写层”拼成一块盘，为什么我们要换一个自己编译的 NBD 模块；网络槽位是什么、为什么要提前建好放进池子、为什么 orchestrator 被强杀后会泄漏、怎么回收；最后是 envd 醒过来之后要做的四件事。

一、根盘：一块“拼”出来的盘

1. 两层

第 3 篇讲过写时复制。沙箱的根盘就是这样拼出来的：

层 内容 谁能写
模板层（只读） 模板最终那一代的 rootfs，通过映射表可以读到任意一块（可能在模板的任意一代文件里） 没人能写，几百台沙箱共享
写层 这台沙箱自己写过的块，一开始是空的；是一个按需增长的文件，用 mmap 访问 只有这台沙箱

读一块：先看写层里有没有，有就返回写层的；没有就按模板的映射表去读。写一块：只写进写层。

2. 用 NBD 呈现成一块盘

Firecracker 要的是一个“磁盘文件”或“块设备”的路径，它不懂什么映射表和写层。orchestrator 用 NBD 把这套逻辑包装成一块真正的块设备：

  1. 从宿主上空闲的 NBD 设备（/dev/nbd0、/dev/nbd1……）里领一个；
  2. orchestrator 自己当这个设备背后的服务端：内核把对这块盘的每一次读写请求转给 orchestrator，orchestrator 按上面的规则在写层和模板之间分派；
  3. 把这个设备的路径交给 Firecracker（通过第 11 篇讲的符号链接）。

于是 guest 里看到的就是一块普普通通的 /dev/vda，完全不知道背后是拼出来的。

这一步在 ResumeSandbox 的第一段就在后台开始了，和领网络槽位、准备 uffd 同时进行。等到三路并行段要用时，通常早已准备好，实测“准备根盘”平均只有 0.2 ms。

3. NBD 设备不够用

每台运行中的沙箱要占一个 NBD 设备。Linux 自带的 NBD 模块默认只创建很少几个设备，要同时跑几百台沙箱，设备数必须调大。

我们用的是一个自己编译的优化版 NBD 模块，加载时把设备数设为 512。部署上经历了三个阶段：

阶段 做法 问题
一 每次部署时，启动脚本里先卸载系统自带的 NBD 模块，再加载我们的版本 模块已加载时重复加载会报错；有设备在用时卸载会失败
二 启动脚本不再管模块，每次宿主重启后手动加载 容易忘
三 一次性固化：用我们的版本覆盖系统模块目录里的原版（原版备份），加开机自动加载和默认参数的配置 见下

固化之后还留了一个坑写在部署文档里：升级或重装内核时，新内核目录里放的又是发行版原版的 NBD 模块，开机照样自动加载、照样是 512 个设备，看起来一切正常，只有对比文件哈希才能发现被换回去了。还有一个硬性前提：自己编译的模块必须和正在运行的内核版本完全一致，否则根本加载不上。

二、网络槽位

1. 一个槽位里有什么

每台沙箱需要一套独立的网络。E2B 把这一套东西叫一个网络槽位（slot），编号从 1 开始。一个槽位包括：

东西 在哪 作用
网络命名空间 ns-<编号> 宿主 一个独立的网络视图，Firecracker 运行在里面
tap 网卡 命名空间里 Firecracker 用它和 guest 的网卡收发数据
一对 veth 一端在命名空间里，一端在宿主上 把命名空间接到宿主网络
若干 iptables 规则 宿主和命名空间里 地址转换、转发、端口重定向

一个有意思的设计：所有沙箱的 guest IP 都相同。因为它们从同一张快照恢复，guest 里的网络配置一模一样。区分它们靠的是外面那层：每个槽位的 veth 有不同的宿主侧地址，地址转换规则把流量正确地送进对应的命名空间。

2. 为什么要提前建好放进池子

建一个槽位要创建命名空间、创建网卡、配地址、加十几条 iptables 规则，几十毫秒是常事，而且要动内核的全局网络结构，并发时会互相等。如果每次启动都现建，这几十毫秒就直接加在启动时间上。

所以 orchestrator 启动后就在后台预先建好一批槽位放进池子；沙箱启动时直接领一个，用完了清理一下放回“复用池”，下次接着用。实测“等网络槽位”平均只有 0.7 ms。

池子的大小决定了高并发时会不会“领不到”：

池 上游 我们
新建槽位池 32 300
复用槽位池 100 1000

上游的大小适合一个节点同时只启动几台的情况。我们要求 100 路甚至更高的并发启动，池子太小就会出现“池空了，只能现建”的长尾。放大池子的代价是宿主上常驻更多的命名空间、网卡和 iptables 规则。我们还加了一行定期打印池子状态的日志，方便确认池子是否充足。

3. 被强杀时整池泄漏

槽位池平时由 orchestrator 管理。正常停止时，orchestrator 会把池子里所有槽位拆掉。可如果它被强行杀掉（比如被内存超限杀掉，或部署脚本直接 kill），来不及拆，宿主上就会留下成百上千个命名空间、网卡和 iptables 规则。下次启动时，新的 orchestrator 会避开这些已存在的编号，但留下的垃圾一直在。

最初我们想写一个“不停服务、只清垃圾”的清理命令。但很快发现这做不到：从进程外面看，池子里闲着的槽位和泄漏的槽位一模一样。两者都没有进程在命名空间里运行，都没有被打开的文件描述符引用（建好槽位后就关掉了），名字、地址、规则也完全相同。只有 orchestrator 进程内部知道哪些是它池子里的。而且即使精确地删掉了泄漏的那些，编号也还不回去，因为“哪些编号被外部占用”只在 orchestrator 启动时扫描一次。

所以最终的做法是承认这件事的本质是“停—清—启”：先优雅地停掉 orchestrator（让它自己把池子拆干净），再清理宿主上剩下的一切（此时剩下的必然是泄漏），然后重新启动。部署脚本的“停止服务”也改成先优雅停止 orchestrator，再做后面的事，避免强杀导致整池泄漏。

三、envd 醒过来

1. 四件事

Firecracker 恢复运行之后，guest 里的 envd 从构建那一刻接着往下跑。它要做四件事才能真正对外服务：

事情 为什么 怎么做
拿身份 快照里的 envd 还是构建时的那一个，不知道自己现在是哪台沙箱 从 MMDS 读取沙箱 ID 等信息（第 11 篇）
收配置 每台沙箱的访问令牌、环境变量、默认用户都不同 orchestrator 调用 envd 的 /init 接口，把这些交给它
对时 guest 的时钟停在构建那一刻，可能已经过去几天 chrony 从宿主提供的时钟设备（PTP）同步
对外就绪 之后 SDK 才能通过数据面访问它 外部轮询 envd 的健康检查，直到应答

2. /init 的超时

orchestrator 调 /init 是同步的，ResumeSandbox 要等它成功才返回。因为 envd 本来就在运行，这一步通常只要几毫秒。

上游给这一次请求设的超时是 50 毫秒，失败就重试，直到成功或整个请求超时。在高并发下，刚恢复的 guest 正在经历缺页风暴，envd 可能一时响应不过来，50 毫秒的超时会导致大量无意义的重试，反而更挤。我们把它放宽到 120 秒，等它慢慢应答。

3. MMDS 连接复用

envd 从 MMDS 读身份信息，用的是一个 HTTP 客户端。上游把这个客户端配置成“每次请求都新建连接、用完就关”。我们改成复用连接（保留最多 10 个空闲连接，空闲 90 秒才关闭）。这是 guest 侧唯一的一处修改，省的是每次请求建立 TCP 连接的那一点开销。

4. 为什么“envd 启动”不慢

常有人以为，Sandbox.create 在客户端看来比服务端日志慢了几百毫秒，是因为“envd 启动慢”。其实不是。envd 没有启动，它只是醒来。orchestrator 同步调的那次 /init 只有几毫秒。客户端多出来的时间是排队、路由、外部轮询健康检查、恢复后的缺页这几样的总和，第 14 篇会把它们拆开。

本篇小结

概念 一句话解释
根盘 模板只读层 + 沙箱写层，读先查写层，写只进写层
NBD orchestrator 当块设备的服务端，guest 看到一块普通的盘
NBD 模块 自己编译的优化版，512 个设备，一次性固化；内核升级会悄悄换回原版

一、三个口径，别混

口径 量的是什么 在哪测

三、报告分组不等于代码结构

第一版报告是按“概念”分组的：“沙箱恢复准备”“创建 Firecracker 进程”“Firecracker 恢复虚拟机”。看起来很整齐，可读起来总觉得数字对不上。原因是概念分组和代码的执行结构不是一回事：

  • “准备根盘”被分在“恢复准备”组，实际上它和“等 Firecracker 启动”“等 uffd”是在同一组并行任务里跑的；
  • “等 Firecracker 启动”被分在“创建 Firecracker 进程”组，可它和“创建进程对象”根本不在一段里，一个在串行准备、一个在并行段。

并行的阶段不能简单相加。要读懂数字，必须先按代码把真实的结构还原出来：

六、客户端多出来的约 300 ms

差值里的成分 在哪 量级

orchestrator 同步调用 envd /init 那一步，在 ResumeSandbox 的总耗时之内，而且只有几毫秒（envd 本来就在运行）。所以“envd 启动慢”的说法把好几样东西错算到了 envd 头上。

要把差值真正拆开，正确的做法是补点而不是做减法：给准入排队打点（已经做了）；在 envd 内部给收到 /init、对完时、第一次健康检查成功各打一个时间戳；再跑一遍并发为 1 的对照，和 100 并发逐阶段对比，就知道每个阶段被并发放大了多少倍。

七、一个埋点的坑：排队时间恒为 0

第一次加“准入排队”的计时后，报告里这一行的样本数是 0。

查下去发现，orchestrator 获取信号量有两条代码路径：从用户暂停的快照恢复时走一个专门的等待函数，普通的 Sandbox.create（从模板创建）则走另一个分支里内联的获取逻辑。我们只在前一个函数里打了点。而 100 并发压测用的正是 Sandbox.create，走的是没打点的那条，于是排队时间“恒为 0”。

两条路径都补上点之后，从模板创建时的排队时间才读得出来。

这个坑的教训很朴素：一个数字是 0 时，先确认它是“真的为 0”还是“根本没测到”。 样本数为 0 和数值为 0 是两回事，报告里要把样本数也打出来。

启动优化：把“拉起 Firecracker”压下来

本篇目标：上一篇的结论是，高并发下 82% 的启动时间卡在“拉起 Firecracker 并等它就绪”。本篇先找病因：启动脚本的最后一环 ip netns exec 远不止“进入网络命名空间”，它还偷偷做了五件 Firecracker 完全不需要、而且要抢内核全局锁的事。然后讲解法：一个约 70 行的小程序，只做真正需要的那一件事。接着讲顺带修掉的一个让失败空等 300 秒的 bug、两种试过又放弃的更激进的做法，以及并发参数和宿主侧的几项调整。

一、病因：ip netns exec 做了什么

第 11 篇的启动脚本最后一步是：

ip netns exec <网络命名空间> firecracker --api-sock <套接字>

直觉上这只是“进入那个网络命名空间，然后运行 firecracker”。可 ip 这个工具（属于 iproute2）的 netns exec 子命令，每次实际上做了六件事：

# 实际动作 代价 Firecracker 需要吗
1 打开命名空间文件，setns 进入网络命名空间 很便宜 需要，唯一需要的
2 再创建一个新的挂载命名空间 内核要复制整棵挂载树，持全局锁 不需要，脚本开头已经建过一个
3 把整棵挂载树递归设为 slave 又一次遍历整棵挂载树，持全局锁 不需要
4 卸载并重新挂载 /sys 重建 sysfs 的对象树，本身不便宜 不需要，Firecracker 不读 /sys 里的网络信息
5 把 /etc/netns/<ns>/ 下的文件绑定挂载到 /etc 为每个命名空间单独配 DNS 等 不需要，guest 用自己的 /etc
6 加载 ip 这个二进制本身 动态链接好几个库，每次都要解析 不需要

六件事里五件是白做的。更要命的是，第 2、3、4 件都要拿内核里一把全局的挂载命名空间锁。一台沙箱做一次，几毫秒，无所谓；100 台沙箱同时做，它们就得在这把锁上排成一队，一个一个来。

这正是“等待 Firecracker 启动”从单沙箱几十毫秒放大到 100 并发下 240 ms 的串行化来源之一；p99 远大于平均值的长尾形态，也是锁争用的典型特征。

二、解法：只保留第 1 件

我们用一个约 70 行的小程序 fc-netns-exec 替换 ip netns exec。它只做三步：

runtime.LockOSThread()                        // 把当前 goroutine 钉在一个系统线程上
fd := open("/run/netns/<ns>")                 // 打开网络命名空间
setns(fd, CLONE_NEWNET)                       // 进入它
execve(firecracker, args, env)                // 原地变成 firecracker 进程

没有第二个挂载命名空间，没有挂载树遍历，没有重挂 /sys，没有绑定 /etc。而且它是静态编译的，启动时不需要动态链接任何库。

第一行有讲究：setns 只改变调用它的那个系统线程所在的命名空间，可 Go 的运行时会把 goroutine 在不同线程之间搬来搬去。如果 setns 在线程 A 上执行，execve 却被调度到了线程 B 上，Firecracker 就会运行在错误的网络命名空间里。所以先把 goroutine 钉在一个线程上，保证这两步在同一个线程上发生。execve 会把整个进程收拢到这一个线程，Firecracker 从而完整继承目标命名空间。

启动管线的其余部分（unshare、mount、ln……）原封不动。和原来相比只有一个变量，效果好坏一目了然。

接入方式

两个设计细节：

  • 在脚本模板里生成，而不是对生成好的脚本做字符串替换。 如果做字符串替换（把 ip netns exec 替换成 fc-netns-exec），哪天上游改了模板的措辞，替换就会悄悄失效：不报错、不打日志，优化就这么静默消失了。在模板层面生成命令，不存在这个问题。
  • 只用于从快照恢复的沙箱。 模板构建的虚拟机仍然走 ip netns exec（第 9 篇讲过原因）。

开关

只有一个环境变量 E2B_FC_NETNS_EXEC_HELPER，同时充当开关和小程序的路径：

取值 行为
不设置 默认开启，用 /opt/e2b-infra/bin/fc-netns-exec
disabled 或 ip-netns-exec 或空 退回原来的 ip netns exec
其他路径 用那个路径下的小程序

改 Nomad 任务的环境变量、重新部署即可切换，不用重新编译。这方便做 A/B 对比：同样 100 并发，开和关各跑一次，比较“等待 Firecracker 启动”这一项。

默认开启有一个代价：代码不检查小程序文件在不在，直接拼进启动脚本。如果安装时漏了它，bash 报“命令找不到”，Firecracker 根本没起来，启动脚本以退出码 127 结束。这种失败必须快速、准确地报出来，否则排查起来很痛苦。这就引出了下一节的修复。

三、顺带修掉的 bug：死了还要等 300 秒

orchestrator 拉起启动脚本后，会同时做两件事：

  • 一边等 Firecracker 的 API 套接字出现；
  • 一边盯着启动脚本进程，如果它提前退出，就取消上面那个等待，并记下死因。

设计没问题，可上游在“等套接字”的函数里创建超时时，用的是一个全新的、和调用方无关的上下文，而不是调用方传进来的那个。于是调用方发出的取消信号根本传不进去。

后果：小程序缺失 → 启动脚本 127 退出 → orchestrator 发出取消 → 等套接字的函数收不到 → 一直等到超时（默认 300 秒）才返回，而且返回的错误是“超时”，而不是真正的“exit status 127”。

修法只有一行：创建超时时以调用方的上下文为基础。超时上限不变，但取消信号能传进来了；错误信息里也能带出真正的死因。

这一行修改在合并上游新版本时很危险：一旦这个文件有冲突，很容易顺手选了上游那一侧，bug 就悄悄回来了。而它的症状（沙箱起不来时卡 300 秒、报错指向超时）在正常压测里根本不显眼。所以我们在文档里专门写了一条：合版时务必确认这一行。

四、试过又放弃的两档

fc-netns-exec 只换掉了最后一环，启动脚本里还留着不少开销：

剩下的开销 说明
约 7 次 fork/exec bash、两次 mount、两次 ln、mkdir，每个都要加载程序、初始化 C 库
1 次挂载树遍历 脚本开头的 mount --make-rprivate /，同样持全局锁
bash 解析 启动 bash、解析脚本、为每个 && 分别 fork
10 ms 轮询套接字 平均白等 5 ms，还有长尾

我们试过两种更激进的做法：把整条启动管线重写成一个 Go 程序，以及重写成一个 C 程序，在一个进程里用系统调用直接完成所有挂载、链接和进入命名空间的动作，完全不经过 bash。

结果很有意思：子进程那一侧确实快了，从启动到 API 套接字出现，从 138 ms 降到了 29 ms。可父进程那一侧变慢了：为了让子进程拥有私有的挂载命名空间，创建子进程时要复制挂载命名空间，这一步在父进程里执行，被拖到了平均 143 ms。两段加起来，比只用 fc-netns-exec 还倒赔了约 31 ms。

原因在于：昂贵的“复制挂载命名空间”并没有消失，只是从子进程搬到了父进程，而且父进程是 orchestrator 本身，所有沙箱的启动都要经过它，搬过去反而更堵。于是这两档没有采纳，从主线代码里删除，实验记录归档保存。

这个经历说明了一件事：优化的收益要看端到端，不能只看被优化的那一段。 把成本从 A 处挪到 B 处，A 处的数字会很好看，但用户感受到的是 A + B。

六、宿主侧的几项调整

最后是几项和代码无关、但会直接影响启动成败的宿主配置。

大页池的申请与释放。 大页池要在宿主内存还没碎片化时尽早申请，所以部署脚本启动时就申请。可停止服务时，大页池不会自己消失：一台 1.1 TB 的机器上，停了服务后仍有约 218 GiB 被预留着，重启之前无法归还。我们加了一个单独的释放命令，按正确的顺序把池子清零（先清可超额部分，再清固定部分，避免清理过程中又冒出新的页），并且能识别 64K 页内核上 512 MiB 的大页。它不接进停止服务的流程，因为下次启动又要尽早申请，每次停服都释放反而得不偿失。后来为了和同机的其他沙箱系统共存，还把大页池的上限设为 64 GB。

NUMA 节点编号不连续导致调度器崩溃。 有些鲲鹏机器开启了一种内存热插拔模式，会出现只有内存、没有 CPU 的 NUMA 节点，节点编号也不连续（比如 0～3 之后直接是 10 和 19）。我们用的 Nomad 1.10 版本在采集 CPU 拓扑时会因此数组越界崩溃，systemd 反复重启它直到放弃，部署脚本则永远在等它的端口。上游在 1.11.2 修了这个问题，我们升级了 Nomad。

绑核与 NUMA 亲和。 想把沙箱限制在指定的 CPU 上（压测时要稳定数字，或者要和同机其他业务隔离），要先知道沙箱在哪个 cgroup 里。第 11 篇说过，ARM 移植时 Firecracker 进程没有被放进各自的 cgroup，所以从宿主侧能绑的对象只能是“orchestrator 加全部沙箱”这一整组。推荐的做法是给 Nomad 的任务 cgroup 设置允许使用的 CPU 和内存节点，一条命令立即生效。绑之前必须先算大页：大页是按 NUMA 节点分配的，绑到一个大页不够的节点上，沙箱会直接起不来。默认不绑，让沙箱用满整机。

暂停走一遍：存盘，然后离场

本篇目标：进入第四部分“暂停与恢复”。本篇先讲 E2B 原生的两个快照接口 Pause 和 Checkpoint 有什么区别；再讲一次快照前后沙箱的三个 ID 怎么变；然后按顺序走一遍暂停的六步，重点讲清一个事实：暂停一定会停掉沙箱，这不是偷懒，而是代码结构决定的。最后说明暂停为什么要等上传完成才返回，以及暂停在模板构建里扮演的角色。

一、两个接口

E2B 原生有两个和快照有关的接口，它们共用同一段“存盘”逻辑，区别在存完之后：

接口 做什么 SDK 里
Pause 存盘，停掉沙箱，产物上传进存储 sbx.pause()
Checkpoint 存盘，停掉沙箱，然后从刚存的快照再拉起一台 sbx.create_snapshot()

Pause 的语义是“沙箱到此为止，离场”。以后想用，再通过 Sandbox.connect() 恢复。

Checkpoint 的语义是“留一个存档，然后接着用”。看起来沙箱一直在，但底下其实是停掉旧的、从新快照启动一个新的。

注意名字的冲突：这个原生的 Checkpoint 接口，和我们新增的“快照回滚”里的 checkpoint 不是一回事。后者在同一个活着的 Firecracker 进程里原地存档，沙箱一刻都不停（见《E2B 沙箱快照回滚从零讲透》）。本书凡是说“原生 Checkpoint”，指的都是这个“存盘—停掉—重启”的接口。

二、三个 ID

一台沙箱有三个 ID，在原生 Checkpoint 前后的变化是：

ID 含义 Checkpoint 之后
沙箱 ID 用户看到的沙箱标识 不变
执行 ID 一次“执行”的标识，api、路由表、统计用 不变
生命周期 ID 一个 Firecracker 进程实例的标识 换新

用户看到的沙箱 ID 不变，可底下的 Firecracker 进程已经换了一个。为什么生命周期 ID 必须换新？因为旧沙箱被停掉时，它的清理协程会用自己的生命周期 ID 去删除 orchestrator 表里的条目。如果新沙箱沿用同一个 ID，旧的清理协程就会把新沙箱的条目也一起删掉。

这个细节说明了一件事：原生快照的每一次“存盘后继续”，都是一次销毁加一次重建。 新进程要重建 KVM 虚拟机、vCPU、设备、网络、uffd，然后靠缺页把工作集一页页换回来。这正是原生快照成本模型的根源（第 17 篇）。

三、暂停的六步

Pause 的主干按执行顺序是：

步 做什么 说明
① 停掉健康检查 接下来沙箱会停止响应，别让健康检查误报
② 暂停 vCPU 从此 guest 不再产生新的状态
③ 让 Firecracker 写出 snapfile 只写 CPU、中断控制器、设备状态，不含内存
④ 取“脏页集合” 问内存处理器：这一代哪些内存页改过
⑤ 导出内存增量 按脏页集合，从 Firecracker 进程里把这些页拷出来，写成紧凑文件
⑥ 导出磁盘增量 把写层里的块导出成紧凑文件。这一步会关掉沙箱

最后写元数据、上传。

注意第 ② 步之后一直没有恢复运行。对 Pause 来说，沙箱从此离场；对原生 Checkpoint 来说，“继续跑”是另起一台新沙箱实现的。

第 ④、⑤ 步怎么判断脏页、怎么拷贝，第 6 步怎么导出磁盘，下一篇细讲。这一篇先回答一个更根本的问题。

四、为什么暂停一定要停掉沙箱

第 ⑥ 步导出磁盘增量时，要把写层从根盘上“摘”下来，然后遍历其中写过的块。在代码里，导出磁盘增量的那个函数，参数之一就是“关掉沙箱”的回调。也就是说，导出磁盘这个动作本身就包含了停沙箱。

为什么必须这样？三个原因：

  1. 摘下写层之后，之后的写没有去处。 写层一旦被摘下，根盘就不再完整，guest 如果继续运行、继续写磁盘，这些写无处可去。
  2. 遍历写层时不能有并发写。 一边遍历一边有人写，导出的就是一个“一半新一半旧”的磁盘镜像，恢复后文件系统可能是坏的。
  3. NBD 设备要先释放，写层文件才能关闭。 写层文件被 NBD 服务端用 mmap 打开着，设备不断开，文件就关不掉。

对“沙箱离场”这个场景，停掉沙箱完全合理，反正它也要走了。但这也决定了原生快照不适合高频地存档读档：每存一次就要停一次、重建一次。这正是我们后来另做一套快照回滚的直接原因，那套方案的做法是把写层原地封存、换上一个新的空写层，不搬数据、不停沙箱。

五、等上传完成才返回

Pause 不是存到本地就返回，而是要等产物上传进存储之后才返回给调用方。所以用户在 SDK 里看到的 pause() 耗时，包含了停沙箱、导出、上传三部分，不只是冻结虚拟机那一下。

为什么要等？因为快照的元数据一旦被标记为“就绪”，就可能马上有人来恢复它，而恢复可能发生在别的节点上，要从存储里取。如果数据还没传完，那次恢复就会读到不存在的文件。这和第 5 篇构建时“全部层上传完才写缓存索引”是同一个原则：元数据不能早于数据宣布就绪。

六、暂停在构建里的角色

回头看第 7 篇：模板构建时，每一条指令执行完，都要“暂停成新的一层”。那里的“暂停”就是本篇的 Pause 流程（只是不经过 SDK）。所以：

  • 构建一个有 10 条指令的模板，要暂停十几次；
  • 暂停的每一个特性和问题，都会在构建的每一层重演一遍。第 19 篇讲的 ARM 上“读过就算脏”的问题，会让每一层都多存上百 MiB；第 20 篇的精确增量修好它之后，构建的每一层也跟着变小。

不过构建里有一个例外：冷启动的那几台构建虚拟机（base 阶段的第二次开机、finalize 的重新开机）不是从快照恢复的，它们的内存不经过 uffd 懒加载，而是由 Firecracker 直接管理。暂停它们时，判断脏页走的是另一条更简单的路，产出的映射表块大小仍是 2 MiB。第 20 篇讲精确增量时会再提到这一点。

增量怎么算出来：脏页、导出与映射表

本篇目标：上一篇列了暂停的六步，本篇放大其中最实质的三步：怎样判断哪些内存页改过（脏页判据），怎样把它们从 Firecracker 进程里搬出来，怎样导出磁盘增量。然后看成本：鲲鹏 950 上一次什么都没改的暂停也要约 250 ms，把这 250 ms 拆开看，会发现真正存内存状态的只有前 10 ms 左右，其余时间都在“拆机”。

一、内存：怎么知道哪些页改过

暂停时要导出的是“这一代改过的内存页”。没改过的页，在上一代（或模板）里本来就有，不用再存。问题是：orchestrator 怎么知道哪些页被 guest 写过？

上游在 x86 上的做法，巧妙地利用了第 3 篇讲的 uffd 写保护。回想一下，从快照恢复的沙箱，内存是靠缺页一页页填进来的，每次填页都经过 orchestrator 的 uffd 处理器。处理器在填页时会看这次缺页是读引起的还是写引起的：

缺页原因 填页时 之后
读 带上“写保护”标记填进去，这一页仍是只读的 如果 guest 后来写了它，会再触发一次写保护缺页，处理器解除保护
写 不带写保护，这一页直接可写 —

于是，一页内存只要被写过，它的写保护标记就一定被清掉了；只被读过的页，标记还在。Linux 在每个进程的 /proc/<pid>/pagemap 里为每一页记了若干状态位，其中第 63 位表示“这一页在内存里”，第 57 位表示“这一页被 uffd 写保护着”。所以：

脏页 ⟺ 在内存里（第 63 位 = 1）且 没有写保护（第 57 位 = 0）

Firecracker 提供了一个接口 GET /memory/dirty，就是按这条判据给出位图的：先找出在内存里的页，再对这些页查写保护位。

代价是：一页如果先被读、后被写，要多经历一次写保护缺页。收益是判据精确：只读不写的页不算脏，不会被导出。

记住这条判据。第 19 篇会看到，它在 ARM 上失灵了。

二、内存：怎么搬出来

拿到脏页集合后，要把这些页的内容存成文件。内容在哪？在 Firecracker 进程的地址空间里，guest 的内存就是 Firecracker 映射的一段内存。

E2B 不让 Firecracker 自己写文件，而是由 orchestrator 直接从 Firecracker 进程里读。Linux 有一个系统调用 process_vm_readv，可以从另一个进程的地址空间里读一段数据（需要权限）。orchestrator 把脏页对应的地址区间组织成一批“读取请求”，按系统允许的单次上限分批调用，读出来的数据依次写进一个本地文件。

这是一次真实的数据搬运：改了多少就拷多少，从一个进程的内存到另一个进程的文件。产物是紧凑的：只有脏页，首尾相接。

三、新一代的映射表

数据文件只是一串紧挨着的块，要靠映射表才知道每一块原来在哪（第 4 篇）。新一代的映射表这样生成：

新一代的映射表
  ├── 本代写过的块  →  指向本代的差分文件
  └── 没写过的块    →  沿用上一代映射表里的指向（可能指向更早的某一代）

相邻的、指向同一代且连续的区间会合并成一行，所以映射表通常不大。

四、磁盘：导出写层

磁盘的判断简单得多：写层里有的块，就是这一代写过的块。 写层只记录写进来的东西，读不会在写层里留下任何痕迹。所以磁盘增量天然是精确的，在 ARM 上也一样。

导出的步骤（上一篇说过，这一步会关掉沙箱）：

  1. 摘下写层：从根盘上拿下来，根盘就此作废；
  2. 停沙箱：另起一个协程去关掉沙箱，然后等 NBD 设备释放；
  3. 逐块导出：遍历写层里每个写过的块。全零的块只在映射表里记一个“空”标记，不写数据；非零的块依次追加进输出文件；
  4. 关闭写层文件。

和内存一样，产物是紧凑的，“文件里的偏移”和“磁盘上的偏移”不同，要靠映射表换算。

五、成本：什么都没改也要约 250 ms

有了这些机制，来看一次暂停到底花多少时间。鲲鹏 950 上，每一档用一台新沙箱，先改指定数量的内存和磁盘，再暂停，客户端测得的中位数：

改动量 暂停 恢复
0 MiB 251.9 ms 109.3 ms
256 MiB 429.9 ms 120.7 ms

按六个档位拟合，暂停大约是：

暂停耗时 ≈ 246 ms（固定开销） + 每 MiB 导出量 × 0.52 ms

改动量为 0 时也要约 250 ms。 这 250 ms 花在哪了？

六、拆开那 250 ms

在 920B 上，我们对一次改动量为 0 的暂停（总耗时 234.9 ms）做了逐段跟踪，从开始暂停算起：

时间点 发生的事
0～约 10 ms 暂停 vCPU 约 0.08 ms；写 snapfile 约 3.2 ms；取脏页位图 0.67 ms；约 9.6 ms 时内存差分文件写好
约 12 ms 开始导出磁盘，开始停沙箱
约 12～169 ms Firecracker 收到终止信号后退出，168.8 ms 时进程结束
169～232 ms 收尾：删 cgroup、停 uffd；刷盘、断开 NBD 设备；导出磁盘差分
232～235 ms 上传到本地存储并返回

真正保存内存状态的只有前约 10 ms，其余约 225 ms 都在销毁虚拟机环境、等它结束。 磁盘差分要等 NBD 设备释放后才能导出，暂停又要等上传完成才返回，所以这段等待全部计入暂停时间。

那 Firecracker 退出为什么要 150 多毫秒？我们对它的内核调用栈做了采样（采样本身会拖慢退出，时间点只能参考）：

时间点 内核在做什么
约 9～123 ms 主线程在运行，调用栈读不到
123 ms 释放挂载命名空间，等待 RCU 宽限期
137 ms 卸载挂载点
140 ms 关闭 KVM 虚拟机，等中断相关的清理工作完成
149 ms 销毁 KVM 虚拟机，等待 RCU 宽限期

（RCU 是 Linux 内核里一种同步机制，修改共享数据后要等一个“宽限期”，确认所有读者都已经离开，才能真正释放旧数据。销毁命名空间、销毁虚拟机都要等它。）

这里有约 114 ms 的一段未归因：进程在运行，但看不到在做什么。它是退出过程中最长的一段，要继续优化暂停，应该从这里查起。第 23 篇把它列在待解决的问题里。

改动量增大时呢？同样的跟踪在 256 MiB 档（总耗时 443 ms）上：

阶段 0 MiB 档 256 MiB 档 增长
开始停沙箱之前（含内存差分导出） 12.4 ms 88.8 ms 约 76 ms
开始停沙箱到 Firecracker 退出 约 156 ms 约 191 ms 约 35 ms
Firecracker 退出到磁盘差分导出完成 约 63 ms 约 160 ms 约 97 ms，其中写 64.5 MiB 磁盘差分约 71 ms

增长并不全是拷数据，进程退出本身也慢了约 35 ms。这是单次样本，只说明方向。

七、成本模型

把上面的观察合起来：

阶段 成本正比于
写 snapfile 常数，几毫秒
导出内存 脏页量（x86 上）；ARM 上见第 19 篇
导出磁盘 写过的块数，而且必须先停沙箱
销毁虚拟机 常数，但很大：一两百毫秒
上传 增量大小

一句话：原生暂停的主要代价来自销毁虚拟机，改动量只决定它上面那一层增量。 即使把脏页判据做到完美精确，“每次暂停都要拆掉整台虚拟机”这一项也不会变，因为它来自“沙箱离场”这个语义本身。

恢复：在新进程里读盘重建

本篇目标：暂停之后，用户调用 Sandbox.connect() 把沙箱拉回来。本篇讲：恢复和第三部分的“启动”是同一条路，只是用的快照不同；恢复时宿主上的一切都要重建；鲲鹏 950 上恢复在各种改动量下都是 100 ms 出头，时间花在哪；搬内存的成本被推迟到了恢复之后。接着总结原生快照擅长什么、不擅长什么。最后讲一个和恢复有关的 SDK 修复：恢复出来的沙箱少带了两个请求头。

一、恢复就是启动

用户对一台已暂停的沙箱调用 Sandbox.connect(sandbox_id)，请求经过 api 到达 orchestrator，走的是和 Sandbox.create 同一个 ResumeSandbox（第 10 篇）。区别只有两处：

启动（create） 恢复（connect）
用哪张快照 模板的最终快照 暂停时留下的那一代
映射表的链 模板的几层 模板的几层 + 每次暂停各一代，更长
节点选择 任意节点 优先原节点，那里有本地缓存
拿不到启动名额时（上游） 立即拒绝，换节点 排队等待

最后一行在上游有意义：恢复的快照文件已经缓存在原来那个节点上，换节点要重新从存储下载，代价高，所以宁可排队。我们是单节点部署，两者都改成了排队（第 10 篇）。

因为是同一条路，第三部分讲的所有内容（启动脚本、懒加载、预取、根盘、网络、envd 醒来）在恢复时全部原样发生。第 15 篇的启动优化，对恢复同样有效。

二、一切都要重建

恢复时，宿主上为这台沙箱准备的五样东西全部从零开始：

新建 Firecracker 进程
  ├── 建 KVM 虚拟机、vCPU、中断控制器、virtio 设备
  ├── 领一个网络槽位（可能和暂停前不是同一个）
  ├── 起一个新的 uffd 处理器，接管 guest 内存
  ├── 建 NBD 设备 + 根盘（模板只读层 + 暂停时导出的那一代 + 新的空写层）
  └── 加载 snapfile，恢复 vCPU 和设备状态
跑起来
  └── guest 访问一页还没有内容的内存 → 缺页 → uffd 处理器
       → 查映射表 → 读本地缓存（没有就从存储拉）→ 填进去

这就是第 16 篇说的“每一次都是销毁加重建”。暂停时拆掉的，恢复时一样一样再建起来。

三、实测：100 ms 出头，和改动量无关

鲲鹏 950 上，每一档一台新沙箱，客户端测得的恢复中位数：

改动量 恢复
0 MiB 109.3 ms
256 MiB 120.7 ms

几乎不随改动量变化。为什么？因为恢复不搬运任何数据：内存靠缺页按需回来，根盘按需从差分里读。改了 256 MiB 还是 0 MiB，恢复那一刻要做的事一样多。

在 920B 上对一次恢复（总耗时 92.6 ms）的时间拆分，从客户端发起调用开始计：

时间点 发生的事
0～35 ms 请求经 api 到节点；建 cgroup、网络槽位、NBD、uffd，启动 Firecracker 进程（约 27 ms 进程起来，28 ms API 就绪）
35～57 ms 加载 snapfile（约 21 ms）
57～58 ms 恢复 vCPU（约 1 ms）
58～93 ms 等 envd 就绪、api 返回
93～98 ms 第一条命令执行完

单台沙箱、没有并发时，启动 Firecracker 只要 28 ms 左右。对比第 14 篇 100 并发下的 240 ms，可见那里的时间几乎全是争用。

四、成本被推迟了

恢复很快，但内存的成本并没有消失，只是推迟到了恢复之后。

950 上的实测：一台沙箱在暂停前，第一次把一份 192 MiB 的内存数据读一遍，用了 590.9 ms；暂停、恢复之后，第一次读同一份数据用了 702.6 ms，多出约 112 ms。这 112 ms 不计入恢复耗时，而由 guest 里第一个访问这些页的程序承担。

所以评价恢复的快慢，不能只看 connect() 多久返回，还要看“恢复后第一次碰到工作集”要多久。第 20 篇讲精确增量时，我们就是用这个“恢复后第一次读一遍负载”的时间来衡量改动有没有让恢复变慢的。

五、原生快照擅长什么

把暂停和恢复合起来看，原生快照的设计对它的目标场景是合适的：

场景 为什么合适
跨节点迁移 产物自足、存进对象存储，任何节点都能加载
长期保存 同上，不依赖任何活着的资源
进程崩溃后恢复 恢复本来就是新建进程，原来那个死没死都无所谓
沙箱离场再回来 停掉沙箱本来就是这个场景的一部分
低频使用 一个沙箱暂停一两次，几百毫秒的固定开销摊得开

它不擅长的，是“高频、低延迟、沙箱不能中断”：每存一次档都要停一次、拆一次，每读一次档都要建一次、等缺页。这不是实现上的缺陷，而是成本模型和场景不匹配。这正是我们另做一套快照回滚的原因：回滚在同一个活着的进程里原地存档读档，存档、读档各约 20 ms 起。

两者的分工和互相影响，第五部分讲。

六、一个 SDK 修复：恢复后少了两个请求头

这是一个由快照回滚“暴露”出来的、原本就存在于恢复路径上的问题。

SDK 创建沙箱时，会为这台沙箱准备一组请求头，用于数据面上的路由。其中有两个是 E2b-Sandbox-Id 和 E2b-Sandbox-Port，proxy 靠它们把一类“按请求头寻址”的请求送到正确的沙箱和端口。

可 SDK 里 Sandbox.connect() 的代码路径只设置了访问令牌这一个请求头，漏掉了这两个路由头。于是通过 connect() 拿到的沙箱对象（包括所有暂停后恢复的沙箱），发出这类请求时，proxy 回答“缺少请求头”。

为什么一直没人发现？因为最常用的 envd 不受影响：访问 envd 的地址里本身就带着沙箱 ID（形如 49983-<沙箱ID>.<域名>），不需要靠请求头路由。直到快照回滚加进来，它的接口恰好是按请求头路由的，在恢复出来的沙箱上就完全用不了了。

修法是在 connect() 路径上补上这两个请求头，和 create() 保持一致。我们部署时把修好的 SDK 文件覆盖到 pip 安装的 e2b 包上。

这个例子说明：一条路径上长期存在的缺陷，可能因为“没人走那条路”而一直潜伏。 新功能走了一条不常走的路，它就浮出来了。第 22 篇还会看到几个类似的例子。

ARM 上的退化：读过就算脏

本篇目标：第 17 篇讲的脏页判据依赖 uffd 写保护。可我们的 ARM 服务器上，内核不支持这个功能。本篇讲 ARM 移植时为了绕过它做了什么改动，这个改动怎样让判据塌缩成“读过就算脏”，再叠加“每一代都是新进程”这个放大器，导致一台什么都没改的沙箱，每次暂停也要导出一百多 MiB。最后用三列对比数据说明：正确的答案其实一直就在旁边。

一、一处注释掉的代码

第 17 篇讲过，x86 上 uffd 处理器填页时，读缺页会带上“写保护”标记：

// 读缺页：带写保护填入，之后被写会再通知一次
if accessType != block.Write {
    copyMode |= UFFDIO_COPY_MODE_WP
}

我们 ARM 服务器上用的 6.6 内核，在 arm64 上不支持 uffd 写保护。带着这个标记去填页，内核直接报错，沙箱起不来。

ARM 移植时的做法是把这三行注释掉：

//if accessType != block.Write {
//    copyMode |= UFFDIO_COPY_MODE_WP
//}

沙箱能正常启动、正常运行了。可这三行注释掉之后，每一次填页都不带写保护，不管这次缺页是读引起的还是写引起的。

这个改动在当时是必要的，ARM 上没有更好的办法。它对运行没有任何影响，但对暂停有影响，而当时没有人注意到。

二、判据塌缩

回想判据：

脏页 ⟺ 在内存里 且 没有写保护

现在没有任何一页带写保护，判据的第二项永远为真，整个判据塌缩成了第一项：

脏页 ⟺ 在内存里

也就是说：凡是被换进过内存的页，都算脏。 被读过的页，因为读的时候要缺页把它换进来，所以也算脏。

三、两个放大叠在一起

“读过就算脏”单独看，好像也还好：多存一些只读的页而已。可它和原生快照的另一个特性叠在一起，就变成了一个很大的数。

放大一：每一代都是一个新进程。 第 16、18 篇讲过，暂停之后的恢复是新建一个 Firecracker 进程，新进程的 guest 内存一开始是空的。guest 一跑起来，它用到的所有页（工作集）都要重新经过缺页换进来。原生 Checkpoint 也一样：存完盘就停掉旧进程、从新快照拉起新进程。

放大二：换入即被判脏。 只要换进来，就在内存里；只要在内存里，就算脏。

两者一乘：每一代暂停导出的内存，下限约等于这一代 guest 碰过的全部页，和改了多少完全无关。

而 x86 上没有这个问题：同样是每代新进程、工作集重新换入，可换进来的是“读进来的干净页”，带着写保护，不算脏。所以 x86 的增量仍然只包含写过的页。

这是 ARM 移植带来的退化，不是 E2B 的设计问题。

四、实测

1. 连拍三次

在一台 ARM 服务器上（当时模板是 1 vCPU、1 GiB 内存），对同一台沙箱连续做三次原生 Checkpoint：

快照 场景 内存差分 磁盘差分
#1 沙箱刚起来 112 MiB 0
#2 中间什么都没做 112 MiB 0
#3 写了 200 MiB 随机数据 338 MiB 201 MiB

最能说明问题的是 #2：两次快照之间一条命令都没跑，如果是精确增量，这里应该接近 0。112 MiB 正是“从 #1 恢复之后到 #2 之间被换进来的页”，也就是这台沙箱（内核 + systemd + envd + 后台进程）的常驻工作集，约占 1 GiB 的 11%。

磁盘那一列是精确的：#1、#2 都是 0 字节。如果磁盘也有“读即脏”，沙箱启动必然读了一堆盘，不可能是 0。磁盘增量来自写层，写层只记写入，和 uffd 无关。

3 的内存差分 338 MiB ≈ 112（工作集）+ 200（写的数据，guest 的文件缓存本身就在内存里）+ 约 26（缓冲区、元数据、新换入的页）。

2. 三列对比

在鲲鹏 950 上，我们用一个探针脚本把三样东西并排量出来。每一步之间沙箱都经历一次暂停加恢复，也就是每一步都是一个新进程：

  • 左列：原生暂停用的判据，Firecracker 的 GET /memory/dirty；
  • 中列：Firecracker 的“写跟踪位图”（我们为快照回滚给 Firecracker 加的一个接口，它记录的是真正被写过的页）；
  • 右列：实际导出的内存差分大小。
步骤 原判据 写跟踪位图 实际导出
刚建好 118.0 MiB 4.6 MiB 118.0 MiB
只读 192 MiB，一字节没改 324.0 MiB 15.0 MiB 324.0 MiB
只改 12 MiB 148.0 MiB 19.7 MiB 148.0 MiB

从这三行能读出三件事：

  1. 左列等于右列，逐行相等。原生暂停就是按这个判据导出的，中间没有别的放大环节。要找原因，只需要看判据。
  2. 只读那一行，左列涨到 324 MiB。 读了 192 MiB、一个字节都没改，导出量却比上一步多了约 200 MiB。判据把“读”算成了“脏”。
  3. 中列是对的。 4.6、15.0、19.7，都是“真正写入量加上几 MiB 系统本底”（guest 内核自己的记账、日志、页表更新）。

920B 上三行的形状完全一样，只是本底大几十 MiB。所以这不是某一台机器的问题，是 ARM 适配版原生路径的问题。

五、预取也被算进去了

第 12 篇讲的预取，填页走的是和真实缺页同一个填页函数。x86 上预取填进去的页带写保护，不算脏；ARM 上不带，预取多少页就脏多少页。

也就是说，在 ARM 上调大预取，会直接放大每次暂停的体积。一个为了让启动更快的优化，在这里变成了暂停的负担。

六、还有一个测量上的陷阱

这个问题还影响了测量本身。我们原生快照的基准脚本，在每一档恢复之后，都会把负载完整读一遍，用来验证内容是否正确。可这一读，就让负载的全部页被换进内存、被判脏。结果修复前六个档位导出的内存差分恒在 440 MiB 左右，几乎不随档位变化。

“验证内容”这个动作本身，就在放大被测量的东西。这是测量里一个很隐蔽的陷阱：观察者改变了被观察的对象。

七、为什么不影响正确性

这个退化浪费空间和时间，但方向是安全的：

  • 一页被写过，写之前一定先被缺页换进来，所以它一定“在内存里”；
  • 所以“在内存里”是“被写过”的超集；
  • 按超集导出，只会多存一些没改过的页（内容和上一代一样，恢复时覆盖成相同的值），不会漏掉任何改过的页。

所以修复前的 ARM 版本，暂停恢复的结果始终是对的，只是每次多存了很多。这个“只会多、不会少”的性质很重要，下一篇会看到，它让“在内存里就算脏”这条退化的判据成了所有退路的落脚点。

八、正确的答案就在旁边

三列对比里最值得注意的是中列：Firecracker 一直在算一份正确的位图，只是原生暂停没有用它。

那么问题变成两个：

  1. 为什么原生路径不用那份位图？
  2. 用了它，就够了吗？

第一个问题的答案很简单：那份位图是我们为快照回滚加进 Firecracker 的，原生路径写在它之前。第二个问题的答案是“不够”，原因藏在 2 MiB 大页里。下一篇讲。

精确增量：判、存、填三层一起改

本篇目标：上一篇的结论是，正确的写跟踪位图就在 Firecracker 里。本篇先说明为什么“只换判据”不够：内存增量其实分三层，粒度被 2 MiB 大页锁成了一根链，只换最上面一层，导出量会被卡在约 130 MiB 的地板上。然后讲改之前先立的一条规矩“宁可多导，不可少导”；两条可选路线以及为什么选第二条；三层各自怎么改；改完之后恢复变慢了，又怎么收回来；什么时候退回旧判据。最后看修复前后的数字。

一、内存增量的三层

把原生暂停的内存路径按“谁决定粒度”切开，是三层：

层 做什么 粒度由谁决定 修复前
判 算出这一代哪些页要导出 判据给出的位图 按映射表的块大小（2 MiB）给出
存 把要导出的块拷进差分文件，映射表记下每块在哪 映射表的块大小，逐代继承 模板是 2 MiB，之后每代都是 2 MiB
填 恢复时 uffd 缺页，从映射表取内容填进去 guest 页的大小 大页 2 MiB；而且硬性要求“guest 页大小 = 映射表块大小”，否则拒绝启动

三层的粒度被一根链锁在一起：

guest 页 = 2 MiB（大页）
 → 填：一次缺页只能填一整页 2 MiB
 → 填的硬检查：guest 页大小必须等于映射表块大小
 → 存：映射表块大小 = 2 MiB，写在映射表里逐代继承
 → 判：位图再精细，最后也要归并到 2 MiB 块导出

所以这件事要分两半治：“判”决定读算不算脏；“存”和“填”决定最小能存多细。

二、只换判据的地板

最直接的想法：把“判”换成写跟踪位图，“存”和“填”不动。这能省多少？

我们写了一个探针，把 4 KiB 粒度的写跟踪位图按 2 MiB 归并（一个 2 MiB 块里只要有一个 4 KiB 页被写过，整块就要导出），算出“只换判据”时的导出量。920B 上：

场景 修复前导出 只换判据 4 KiB 真实写入
空转 162 MiB 134 MiB 4.1 MiB
只读 192 MiB 366 MiB 148 MiB 14.6 MiB
只改 12 MiB 184 MiB 156 MiB 20.5 MiB
写 192 MiB 382 MiB 358 MiB 219.8 MiB

看“空转”那行：真正写了 4.1 MiB，归并后却是 134 MiB，放大了三十多倍。为什么？因为这 4 MiB 不是连成一片的，而是散落在 2 GiB 的 guest 内存里：内核的页表更新、内存分配器、定时器、日志缓冲，各自落在不同的物理页上。4.1 MiB 约 1050 个 4 KiB 页，落进了约 67 个不同的 2 MiB 块，平均每块只有十几个页真被写过，剩下四百多个页是“陪绑”导出的。

这就是只换判据的地板：只要 guest 活着，每一代就有一百多 MiB 的“本底散写”，归并到 2 MiB 后约 130 MiB，和改动量无关。只换判据治好了“读算脏”，对读多写少的负载收益很大（只读那行从 366 降到 148），但对写多的负载只省个位数百分比，而且永远到不了真实写入量。

三、先立规矩：宁可多导，不可少导

在动手改之前，先想清楚改错了会怎样。

暂停导出的内存差分是相对上一代的。恢复时，没有被导出的页一律从上一代读。所以：

  • 多导一页：这一页的内容本来就能从上一代读到，重复存一份，只浪费空间和时间；
  • 少导一页：如果这一页其实被写过，恢复后它会变回上一代的旧内容。guest 内存由两个不同时刻拼成，页表、链表、引用计数前后对不上，轻则数据错乱，重则 guest 内核在恢复后几十毫秒内崩溃。更糟的是，暂停本身报成功，错误要到恢复时才暴露。

两个方向的代价完全不对称。所以任何判据的改动都必须满足：新判据给出的页集合，必须是真正被写过的页的超集。 旧的“在内存里就算脏”满足这一点（上一篇第七节），只是超得太多。换成写跟踪位图之后，必须逐项论证它覆盖了所有的写。

四、两条路线

要让导出量等于 4 KiB 粒度的真实写入，有两条路：

路线 A：关掉大页 路线 B：保留大页，4 KiB 存、2 MiB 拼
做法 模板关掉大页构建，guest 页、映射表块、缺页单位全是 4 KiB；只换“判” 换“判”；映射表块降到 4 KiB；缺页仍按 2 MiB，内容从多个 4 KiB 映射拼起来
改动量 约 40 行 + 模板参数 约 200 行，5 个包
导出量 真实写入 真实写入
缺页次数 乘以 512 不变
guest 运行时 失去大页的 TLB 收益 不变
影响面 所有用这个模板的沙箱，不只做快照的 只有原生快照的导出和恢复

选 B。 两条路线导出量相同，差别全在恢复和运行时。路线 A 让一个 400 MiB 工作集的缺页次数从约 200 次变成约 10 万次，每一次都是一次“内核 → orchestrator → 内核”的往返，恢复后首次触碰工作集的延迟会从几百毫秒升到秒级；还让所有沙箱在运行时失去大页。为了快照的体积让所有沙箱付运行时代价，不划算。

路线 B 的关键判断是：拼接能力其实已经存在。 按映射表读数据的那个通用函数本来就是一个循环：查一次映射，从对应那一代读“映射剩余长度和待读长度中较小的那个”，前进，再查，直到读满。它天然能跨越任意多代。修复前只有 uffd 用了一个“只取一个块”的捷径。所以要做的不是写一个拼接器，而是把 uffd 的路径换成“能拼的读法”，再把拼接的开销压下去。

五、三层各改了什么

1. 判：换成写跟踪位图

暂停取脏页时，不再调 GET /memory/dirty，而是：

  1. 让 Firecracker 把当前的写跟踪位图写进一个临时文件（这是我们给 Firecracker 加的接口）；
  2. 读取并解析这个文件，得到一个按 4 KiB 页的位集合；
  3. 以 4 KiB 为块大小返回。

这一步要成立有三个前提，都满足：

  • 这个接口要求虚拟机已暂停：暂停流程里取脏页时虚拟机确实已暂停；
  • 暂停流程先写了 snapfile，这次写不会清空位图（Firecracker 只在连内存一起导出时才清，原生暂停不让它导内存）；
  • 位图的起点就是这一代的起点：每一代都是新进程，从快照加载时位图为空，之前的写已经在上一代的差分里。（这一条在沙箱做过快照回滚之后不再成立，第 22 篇专门讲。）

位图覆盖了哪些写？它是两份位图的并集：KVM 记录的 guest 的每一次写（920B 上靠写保护陷出，950 上靠硬件 HDBSS），以及 Firecracker 自己写 guest 内存的地方（网卡收包缓冲、virtio 队列）。orchestrator 经 uffd 填进去的页不在位图里，也不该在：它们是“换入”，内容等于映射链里已有的内容。这恰恰是“换入即脏”的反面。

2. 存：映射表块大小降到 4 KiB，父代映射原样保留

生成新一代映射表时加一条规则：差分的块比上一代细、并且能整除上一代的块，就把新映射表的块大小改成差分的块大小。

上一代的映射一行都不用重写。 映射表里记的是字节区间，2 MiB 对齐的区间必然也是 4 KiB 对齐的；查找时只要求每段的起点落在块边界上，不要求每段长度等于块大小。所以一张 4 KiB 的映射表里，可以同时有 2 MiB 长的老映射和 4 KiB 长的新映射。

例如上一代把 [0, 2 MiB) 整块映射到第 1 代，本代只写了其中偏移 8 KiB 那一页，合并后：

[0,      8 KiB)  → 第 1 代，偏移 0
[8 KiB, 12 KiB)  → 本代，偏移 0        ← 本代唯一的一页
[12 KiB,  2 MiB) → 第 1 代，偏移 12 KiB

原来那条 2 MiB 的映射被切成三段，前后两段仍指向第 1 代，差分文件一个字节都不用动。

模板的映射表仍是 2 MiB；沙箱第一次原生暂停时切到 4 KiB，之后每一代继承 4 KiB。

3. 填：一次 2 MiB 缺页，三级取源

缺页单位仍然是 2 MiB 的 guest 页，可映射表现在是 4 KiB 的，一个 2 MiB 页可能由来自不同代的 512 个小块拼成。填页时按三级取源：

级 条件 做法 代价
一 映射表块大小就等于 guest 页 原来的路，直接取一块 和修复前一样
二 一条映射覆盖了整个 2 MiB 零拷贝：直接把那一代缓存文件里的那段切片交给 UFFDIO_COPY 和修复前一样
三 2 MiB 里混着不同代的块 从缓冲池取一块 2 MiB 缓冲，沿映射链逐段读满，填完把缓冲还回池里 最多 512 次查表 + 一次 2 MiB 拷贝

guest 物理页在 2 MiB 块里虽然混着，但整块都来自同一代的仍占多数，第二级能处理大部分缺页。缺页处理和预取共用这个入口。

原来那条“guest 页大小必须等于映射表块大小”的硬检查，也放宽成“guest 页大小必须是块大小的整数倍”。

六、恢复开销的来回

体积是“存”这一侧的收益；代价落在“填”这一侧，也就是恢复后懒加载的热路径上。我们用“恢复后第一次把负载整个读一遍的耗时”来衡量，它比恢复本身的耗时更接近用户真正等的时间。

第一版的“填”很直接：每次 2 MiB 缺页都新分配一块 2 MiB 缓冲，沿映射链读满再填。一个 400 MiB 的工作集约 200 次缺页，就是 400 MiB 的分配、清零、拷贝和之后的垃圾回收。920B 上六个档位的平均值：

版本 恢复后首次读负载（6 档平均）
修复前 243 ms
第一版 367 ms，每档多 100～200 ms
加上零拷贝快路径（第二级） 316 ms
再加上缓冲池（第三级） 241 ms，与修复前持平

后来缓冲池的取法又收紧了一次：最初每次取缓冲都会顺手构造一个新的池对象再丢掉，现在先查、只在第一次才构造。每次取缓冲从 207 ns、4 次内存分配降到 83 ns、1 次分配。在一次 2 MiB 拷贝面前这只是零头，但它体现同一条原则：懒加载路径上每一次缺页都是热路径，能不拷就不拷，要拷就不分配。

七、退路：什么时候退回旧判据

写跟踪位图只有在“这一代从启动起就开着跟踪，而且没有被清掉而未补回的部分”时才完整。任何一个条件不满足，就退回旧的“在内存里就算脏”，因为它不会漏掉写过的页。按顺序检查四道门：

# 条件 为什么不能用写跟踪位图
1 这台 orchestrator 没给虚拟机开脏页跟踪 位图里只剩 Firecracker 自己的写
2 为配合快照回滚而维护的“自启动以来脏页集”不可信 并回去也可能少导（第 22 篇）
3 Firecracker 没有导出位图的接口 拿不到位图
4 合并时页大小对不上 同 2

第 1 道门对应一个开关：脏页跟踪是否开启，默认跟着硬件走。950 有硬件记脏（HDBSS），默认开，原生暂停就是精确增量；920B 没有，默认关，原生暂停仍按旧判据。为什么 920B 默认不开？因为软件方式的跟踪要让每个干净页第一次被写时陷出一次，所有沙箱都要付这个运行期代价，不管它做不做快照。这一点第 21 篇再展开。

每次暂停都会在日志里说清：这次导出了多少页、依据是哪一种（写跟踪、写跟踪加累积、驻留）、为什么。修复前那种“导多导少完全看不见”的状态不会再有。

八、修复后的数字

920B 上开启跟踪、修复后，三列对比的右列（实际导出）等于中列（写跟踪位图），逐行相等：

场景 修复前导出 修复后导出
刚建好 154 MiB 5.5 MiB
只读 192 MiB 358 MiB 12.7 MiB
只改 12 MiB 176 MiB 20.3 MiB
写 192 MiB 370 MiB 209.5 MiB

修复后，导出量等于“这一档写入量 + 二三十 MiB 本底”，随写入量线性增长。导出量变小还带来一个直接收益：上传时间从约 200 ms 降到 50～150 ms。暂停和恢复的耗时本身变化不大，因为它们的主要成本本来就在拆机和建机上（第 17、18 篇）。

这次修复只是把 ARM 补回到 x86 本来就有的精确程度，并没有超越 x86 原生。

快照回滚动了哪些共用部件

本篇目标：进入第五部分。我们新增的快照回滚和 E2B 原有的暂停恢复是两套独立的机制，可它们管的是同一台沙箱、同一个 Firecracker、同一叠磁盘、同一份内存。本篇先用几句话交代两者的分工，然后列出回滚动过的共用部件，再逐项看：加了回滚之后，一台从不使用回滚的普通沙箱，在启动和暂停时多付了什么，我们又怎样让这些代价尽量为零。最后顺带讲为了和同机其他沙箱系统共存做的几处改名。

一、两种快照的分工

只讲结论，机制见《E2B 沙箱快照回滚从零讲透》：

暂停恢复（原生） 快照回滚（新增）
解决什么 沙箱离场后保存，以后在任意节点重建 活沙箱里高频、快速地回到之前的某个状态
存档后沙箱 停掉 继续跑
读档 新进程重建，靠缺页换回工作集 同一个进程原地写回改过的页
产物 自足、紧凑、可上传 只在本机、绑定这台沙箱的生命周期
典型耗时（950，0 MiB 档） 暂停约 250 ms，恢复约 110 ms 存档约 17 ms，读档约 22 ms

谁也替代不了谁：回滚的存档离不开这台活着的沙箱，沙箱一停就没了，所以长期保存、迁移只能靠原生；原生每次都拆机建机，几百毫秒，所以高频回退只能靠回滚。

二、共用了哪些部件

回滚要在一个活着的沙箱里原地存档读档，就不得不动几样原本只为原生路径服务的部件：

部件 原来 回滚加了什么
Firecracker 上游版本 三处扩展：快照时可导出脏页位图、随时导出当前写跟踪位图、原地回滚
虚拟机启动配置 不开脏页跟踪 按硬件决定是否开启脏页跟踪，从快照加载时也要开
磁盘写层 一台沙箱一个写层 存档时把当前写层封存成只读层、再开一个新写层，于是变成一叠
脏页位图 原生不用 回滚靠它判断“这次存档要存哪些页”，每次存档读档都会清零
proxy 只转发 拦截发往沙箱 49984 端口的回滚请求，由宿主处理

改动的原则是纯加法：不使用回滚的沙箱，行为应当和原来一模一样。下面逐项检查这条原则有没有做到。

三、一台普通沙箱启动时多做了什么

多做的事 发生在 代价
加载快照时按开关打开脏页跟踪 加载快照的那次 HTTP 请求里多一个参数 请求本身几乎无代价；运行期的代价见下一节
网络槽位多开一个 conntrack 句柄 槽位预先建池时，不在启动路径上 每个槽位一个套接字；关闭放在单独的协程里，因为关闭本身有点慢

前两项都尽量放在了启动的关键路径之外。conntrack 句柄在槽位建池时就打开，启动时直接拿来用；拆槽位时关闭句柄放进单独的协程，不让它拖慢拆除。

四、脏页跟踪的运行期代价

真正需要权衡的是第一项：脏页跟踪一旦打开，虚拟机的每一次写内存都可能被记录。 记录的方式取决于硬件：

机器 怎么记 运行期代价
鲲鹏 950 CPU 硬件 HDBSS 自动记录写过的页，guest 写内存不需要陷出 几乎没有
鲲鹏 920B 等无 HDBSS 的机器 KVM 把所有页设为写保护，每个干净页第一次被写时陷出一次，KVM 记下来再放行 所有开了跟踪的沙箱都要付，不管它用不用回滚

在 920B 上，如果默认打开跟踪，一台从不做存档的普通沙箱也会因为每个页第一次被写都要陷出一次而变慢。这对不用回滚的用户是纯损失。

所以开关的默认值跟着硬件走：

机器 不设开关时 结果
950（有 HDBSS） 探测到硬件能力，自动开 回滚是增量的；原生暂停是精确增量的（第 20 篇）；几乎无运行期代价
920B（无 HDBSS） 关 回滚每次全量，功能正确；原生暂停退回旧判据（多导但正确）；普通沙箱无额外代价
920B，显式打开 开，走 KVM 写保护 回滚和原生暂停都是增量的；所有沙箱付写保护代价

这是一个典型的取舍：有硬件支持时，精确增量几乎零副作用；没有硬件支持时，“精确增量”和“不让所有沙箱付写保护代价”只能二选一，默认选后者。 需要的人可以显式打开。开关只认标准的布尔写法，写成 yes、on 之类会被忽略并打一条警告，避免“以为开了其实没开”。

orchestrator 启动时会在日志和一个能力文件里写明：跟踪开没开、为什么开或不开（“探测到硬件能力”“没有硬件，软件跟踪代价太高”“显式设置为 true”），每次暂停的日志也会说明用了哪种判据。所以无论哪种组合，都能从日志里看出来，不会出现“悄悄退化”。

五、磁盘写层从一层变成一叠

回滚存档时，不搬任何磁盘数据，只是把当前写层“封存”成只读的，再开一个新的空写层。存档几次，就叠几层。读磁盘时要从最上面一层往下找，直到找到这一块，或者落到模板。

对从不存档的沙箱，写层始终只有一层，读写路径和原来完全相同。

对存过档的沙箱，层数会随存档次数增长，读路径会越来越长。回滚那边为此做了限制层数、折叠相邻层、回收不再被引用的层这几件事，保证读路径不会无限变长。这些是回滚自己的事，不展开。

但“一层变成一叠”对原生暂停有一个直接后果：第 17 篇讲的磁盘导出，原来只导出“当前写层”。当写层变成一叠之后，当前写层里只有最近一次存档之后的写，更早的写在下面那些封存层里。下一篇第一个故事就从这里开始。

六、脏页位图会被清零

另一个共用部件是 Firecracker 的写跟踪位图。第 20 篇的精确增量用它来判断“这一代 guest 写过哪些页”，前提是“位图的起点就是这一代的起点”。

可回滚在每次存档、每次读档时都会清零这份位图，因为回滚自己的下一次存档要“相对于这一刻”。对回滚来说这是正确的；对原生暂停来说，位图就丢了一截历史。这是下一篇的第二个故事。

三处被撞坏的地方和修法

本篇目标：快照回滚加进来以后，E2B 原有的暂停恢复被撞坏过三处：磁盘上，做过存档的沙箱一暂停，封存层里的数据就丢了；内存上，脏页位图被回滚清零，暂停少导了页；SDK 上，恢复出来的沙箱用不了回滚。本篇逐个讲：原因是什么，为什么没人发现，怎么修，怎么证明修好了。最后总结三条共同的教训，以及专门为“组合”设计的兼容矩阵测试。

一、磁盘：做过存档的沙箱一暂停，封存层就丢了

1. 原因

上一篇讲过，回滚每存一次档，就把当前写层封存成只读层、再开一个新写层。从第一次存档起，当前写层里只有最近一次存档之后的写，更早的写在下面那些封存层里。

E2B 原生暂停导出磁盘时，只导出当前写层（第 17 篇）。于是：

  • 做过存档的沙箱一暂停，最近一次存档之前写的所有数据都没被导出，恢复后这些块回到了模板的内容；
  • 做过读档的沙箱更严重：读档会换上一个新的空写层，暂停时几乎什么都导不出来。

这是三个问题里唯一一个真的丢数据的。

2. 为什么没人发现

本来有三道防线应该能抓住它，结果全部失效：

本应抓住它的 为什么没抓住
导出产物的自我校验 映射表是从导出的内容推出来的：导出了多少，映射表就描述多少。块数对得上，校验对得上，只是内容少了一截。没有独立的第二方来源可以对照
已有的回滚正确性测试 一个都不做原生暂停。它们测的是存档读档自己那条链；暂停是 E2B 原有的操作，两者的组合没人走过
修复后补写的第一版验证 写一个小文件 → 暂停恢复 → 读回比较，假通过

第三行是真正的教训。暂停恢复不会清空 guest 里的文件缓存（它就在内存快照里），刚写过的小文件从缓存里读回来，内容一定是对的，根本没碰到磁盘。guest 的页缓存能把磁盘层的错误完全盖住。

3. 怎么才看得见

验证方法要同时绕开两个“好心的”缓存：

  1. 在存档之前写一份足够大的随机数据（16 MiB），大到不可能全部留在缓存里；
  2. 存档；
  3. 在存档之后再写一份同样大小的随机数据；
  4. 暂停、恢复；
  5. 两份数据都用 O_DIRECT（绕开页缓存，直接读磁盘）读回，比对哈希。

抓缺陷的是第 1 步那一份：它落在被封存的层里，是唯一会丢的。第 3 步那一份是对照：它在当前写层里，修复前后都应该是对的，证明测试脚本本身在正常工作。没有对照组，“全部失败”可能只是脚本写错了。

4. 修法

暂停导出磁盘时，把整叠层交出来，按读的顺序压平（每一块取最上面那层里的版本）再导出。从没存过档的沙箱，写层只有一层，仍走原来的单层导出路径，逐字节不变。

用同一个构建在 920B 上验证：存档 → 暂停 → 恢复、读档 → 暂停 → 恢复，两种组合磁盘都完好，回滚自己的 59 项检查全过；同样的测试跑在修复前的版本上，恢复后的磁盘 3 次里 3 次都是坏的。

二、内存：脏页位图被清零，暂停少导了页

1. 原因

第 20 篇的精确增量用写跟踪位图判断“这一代 guest 写过哪些页”，它有一个前提：位图 = 这一代启动以来写过的所有页。对从不存档的沙箱，这成立。可 Firecracker 的位图在三个时刻会被清零或被绕过：

时刻 发生了什么
每次存档 写完差分之后清零位图，让下一次存档只相对于这一刻
每次读档 回滚完成后清零位图
读档写回内存时 Firecracker 经它自己对 guest 内存的映射写回页，KVM 不记这种写

于是一台做过存档的沙箱暂停时，只看位图，就只会导出“上一次存档或读档以来”写过的页。更早写过的页没导出，恢复时从上一代读回旧内容，guest 内存由两个时刻拼成。读档写回的那批页更隐蔽：它们确实改变了内存，却不在任何一份日志里。

2. 后果

正是第 20 篇说的最坏情形：暂停报成功，快照照常上传；恢复后 guest 内核在几十毫秒内崩溃。实测的形态是内核先报内存计数异常，接着一连串链表损坏，最后内核恐慌。运气“更好”一点、内核没立刻崩的话，就是一台能跑、但数据已经错乱的沙箱。

这个缺陷由一个专门的测试用例发现，并一直守着。

3. 修法：把即将被忘掉的位图收起来

每次位图要被清零时，被清掉的恰好是“即将被忘掉的页”，而这些位图此刻都在 orchestrator 手里。所以做法很直接：每台虚拟机维护一个“自启动以来脏页集”，在每个清零时刻之前，把相应的位图并进去；原生暂停时，把这个集合和写跟踪位图合并，再导出。

时机 并入什么
增量存档之后 这次存档写出的脏页位图（恰好就是被清掉的那些页）
全量存档之前 先导出一次当前的位图（见下）
存档超时 仍然尝试并入，超时的存档可能已经写完并清了位图
读档之前 当前的位图（上次存档以来写过、即将被回滚和清零的页）
读档准备好写回集合之后 写回集合（这些写不进任何日志）

全量存档为什么是例外？ 全量存档写出的位图是“每一页都是 1”，它描述的是“文件里有哪些页”，不是“guest 写过哪些页”。如果把它并进集合，这台沙箱以后每一次暂停都会导出整份内存。而沙箱的第一次存档总是全量的，等于每个用过回滚的沙箱都会中招。所以全量存档改为在拍之前、虚拟机已暂停时，先导出一次当前位图（导出不会清零），对第一次存档来说，这张图正好就是“启动以来写过的页”。这一步万一失败，就退而求其次并入全 1 的位图：多导，但不会少导。

4. 合不上就标“不可信”

位图来源多样，有时几何形状对不上（页大小不同、页数不同）。合并规则只接受一种安全的情况：新位图的页更粗，就展开成细页再并（一个粗页置位，它覆盖的细页全部置位，只会多记）。其余任何对不上的情况（新位图更细、不是整数倍、页数不同、文件缺失或格式错误），位照样并进来，但整个集合标记为“不可信”。暂停时发现集合不可信，就退回旧的“在内存里就算脏”（第 20 篇的第 2 道门）。

合并失败从不让存档或读档本身失败，只打一条警告：这次存档功能不受影响，受影响的只是这台沙箱下一次原生暂停的导出量。

5. 从不存档的沙箱不受影响

集合的初始状态是“空的、可信的”。从不存档的沙箱什么都不并，暂停时不做合并、不多分配内存，导出的页集合和没有这个机制时逐位相同。

暂停日志里现在会写明：导出多少页、依据是哪种（写跟踪、写跟踪加累积、驻留）、集合里有多少页、并过几次。修复前那个缺陷在日志里完全不可见，没有任何一行说“这次暂停只导出了上次的百分之一”。

三、SDK：恢复出来的沙箱用不了回滚

第 18 篇讲过：SDK 的 connect() 漏了两个路由请求头。envd 的地址里带着沙箱 ID，所以从来没受影响；回滚的接口是按请求头路由的，于是所有通过 connect() 拿到的沙箱（包括所有暂停后恢复的）都调不了回滚，proxy 报“缺少请求头”。

修法是在 connect() 里补上这两个请求头。这个缺陷严格说不是回滚“撞坏”的，而是一直潜伏在恢复路径上，回滚是第一个走到那里的功能。

四、兼容矩阵：专门测“组合”

三个问题都出在组合上：单独测回滚没问题，单独测暂停恢复也没问题，两者先后发生在同一台沙箱上才出事。所以我们专门写了一个兼容矩阵测试，把“回滚的操作”和“原生的操作”按各种顺序组合起来过一遍：

组 场景 格数
A 基线：没有存档的沙箱上暂停 → 恢复 1
B 存档之后做各种原生操作 8
C 读档之后做原生操作 3
D 连存三次档（多层封存）之后暂停 1
E 反过来：暂停恢复之后走完整的存档读档 1
F 销毁 1

每一格的判定有三种：

判定 含义
OK 能做，做完沙箱和数据都对
REFUSED 服务端明确拒绝，并且没留下半吊子状态。这是边界，不是缺陷
BROKEN 能调用但结果不对，或者本来能做的原生操作被弄坏了。唯一的真问题

几个设计要点：

  • 先测基线。第一组在没有任何存档的沙箱上跑一遍暂停恢复，确认原生能力本来是好的，后面才有资格说“是我们弄坏的”。
  • D 组专门测多层。磁盘问题的本质是“当前层之下还有 N 个封存层”，存一次档只有一层封存，测不透。
  • 数据一律 O_DIRECT 读回比哈希。
  • 预期的拒绝写成断言。比如“暂停恢复之后，回不到暂停之前的存档”：回滚的存档绑定在 Firecracker 进程上，暂停后进程换了，存档自然没了。这一格预期是 REFUSED，写成断言而不是注释：哪天行为变了（不管是变成支持，还是变成静默返回错误数据），测试会立刻报出来。

这个矩阵要回答的问题，不是“我们的新功能好不好用”，而是“我们有没有弄坏别人的功能”。

教训 在哪个问题里
两个各自正确的机制叠加时，要重新检查每一个前提。 精确增量假设“位图 = 这一代启动以来的写”，回滚假设“存档后可以清零位图”，各自都对，放在一起就错了 内存

贯穿全书的几个事实，正文会反复回到这里：

  • E2B 从不“冷启动”用户的沙箱。模板构建时已经把系统开到 envd 就绪那一刻并拍下快照，Sandbox.create 只是从这张快照恢复，envd 进程在快照里本来就在跑
  • 启动一台沙箱，宿主上要准备五样东西：Firecracker 进程、网络槽位、根磁盘（NBD + 写时复制）、内存懒加载（uffd）、guest 里的 envd。前三样在恢复时并行准备
  • 100 路并发下，ResumeSandbox 平均 294.7 ms，其中 82%（241.6 ms）卡在“拉起 Firecracker 并等它的 API 就绪”；加载快照本身只要 29 ms
  • 暂停一定会停掉沙箱。导出磁盘差分这个动作的参数之一就是“关掉沙箱”；恢复一定是新进程，沙箱 ID 不变，底下的 Firecracker 已经换了一个
  • 鲲鹏 950 上，暂停一个什么都没改的沙箱也要约 250 ms，其中真正存内存状态的只有前约 10 ms；恢复在各档改动量下都约 100～120 ms
  • ARM 适配基线上，内存增量的判据塌缩成“读过就算脏”：改 12 MiB，导出 148 MiB。修成精确增量要同时改三层（判、存、填），只换判据会被 2 MiB 大页卡住
  • 快照回滚和暂停恢复是两套独立的机制，但共用 Firecracker、写层、脏页位图。回滚加进来以后，暂停曾经静默丢过数据，后来修好了
  • 每个空闲沙箱在宿主上约占 350 MiB（大页 157 MiB + 普通内存 194 MiB），memory_mb 是上限而不是占用

第 2 篇｜一台沙箱由什么组成：从 SDK 到 Firecracker

要回答的问题：用户手里的 Sandbox 对象背后，宿主上有哪些进程、哪些文件？请求怎么一路走到虚拟机里？

第 3 篇｜必备底子：内存页、缺页、块设备与命名空间

第 4 篇｜快照是什么：三件套与映射表

要回答的问题：一张虚拟机快照里到底存了什么？“一代一代”的增量快照怎么拼起来？

  • 快照三件套：snapfile（vCPU 寄存器、中断控制器、设备状态，几十 KB）、memfile（内存）、rootfs（磁盘）
  • 为什么 E2B 的内存和磁盘不交给 Firecracker 存，而是自己管：要能增量、能按需取、能上传对象存储
  • 映射表（header）：把“设备上的第几块”翻译成“哪一代、哪个文件、哪个偏移”；增量只存改过的块，没改的指向上一代
  • 一代就是一个 build ID：模板的每一层、每次暂停，都长出新的一代；查一个块就是沿链条往上找
  • 存在哪：本地缓存、本地存储或对象存储（MinIO），以及“模板放在 tmpfs 上，宿主重启即丢”这个部署细节
  • 预告：构建是“长出第一批代”，启动是“沿链条读”，暂停是“再长一代”

第 5 篇｜构建总览：为什么镜像不够，要的是一张快照

要回答的问题：有了 Docker 镜像为什么还要“构建模板”？构建的输入、输出和主流程是什么？

要回答的问题：一个容器镜像怎样变成虚拟机能用的 ext4 磁盘？为什么第一次开机要用 busybox？

第 15 篇｜启动优化：把“拉起 Firecracker”压下来

要回答的问题：拉起一个 Firecracker 为什么在高并发下要 240 ms？我们改了什么，哪些试过又放弃了？

  • 病因：ip netns exec 远不止“进网络命名空间”，它还会再开一个挂载命名空间、遍历整棵挂载树、重挂 /sys；这些动作都抢同一把内核全局锁，100 路并发时互相排队
  • 解法：一个约 70 行的静态小程序 fc-netns-exec，只做 setns + execve 两件事；在脚本模板里生成而不是字符串替换；模板构建的虚机不走这条路
  • 默认开启的代价：小程序不在时 Firecracker 根本起不来，所以要有快速、准确的报错
  • 顺带修掉的 bug：等 socket 时用了与调用方无关的上下文，Firecracker 早已死掉还要空等 300 秒，报错还指向“超时”
  • 试过又放弃的两档：把整条启动管线重写成 Go / C，子进程侧从 138 ms 压到 29 ms，但父进程侧复制挂载命名空间反被拖到 143 ms，合计倒赔约 31 ms
  • 并发参数：同时启动上限 3 → 可配置（30 / 500）、排队超时 15 s → 300 s、网络槽位池 32 / 100 → 300 / 1000、预取并发翻倍、envd /init 超时放宽、uffd 等待 10 s → 120 s；怎样用“上限扫描”判断瓶颈是排队还是 CPU
  • guest 侧的一处小改：envd 取身份时复用连接，不再每次新建
  • 宿主侧：大页池的申请与释放、NUMA 节点编号不连续导致调度器崩溃、沙箱绑核与 NUMA 亲和

第 16 篇｜暂停走一遍：存盘，然后离场

第 17 篇｜增量怎么算出来：脏页、导出与映射表

要回答的问题：暂停时怎么知道哪些页、哪些块改过？数据怎么搬出来？暂停为什么改动量为 0 也要约 250 ms？

第 19 篇｜ARM 上的退化：读过就算脏

要回答的问题：为什么 ARM 上什么都没改，一次暂停也要导出一百多 MiB？

  • 后果链：写保护位恒为 0 → 判据塌缩成“驻留即脏” → 读进来的页全算脏
  • 叠加的放大：每一代都是新进程，guest 一跑就要把工作集重新缺页换入 → 每代增量的下限约等于工作集
  • 实测：连拍三次，中间什么都不做也是 112 MiB；950 上改 12 MiB 导出 148 MiB，只读 192 MiB 导出 324 MiB；预取会被直接算进增量
  • 为什么不影响正确性：驻留是写过的超集，只会多导，不会少导；磁盘侧走写层，仍然精确
  • 正确的位图其实就在旁边：Firecracker 的写跟踪位图同期只有 4.6 / 15 / 19.7 MiB

第 20 篇｜精确增量：判、存、填三层一起改

要回答的问题：把判据换成写跟踪位图就够了吗？为什么还要动存储和缺页？怎样做到导出精确而恢复不变慢？

  • 只换判据的地板：4 MiB 的散写落在 67 个不同的 2 MiB 块里，归并后仍是 134 MiB
  • 先立规矩：宁可多导，不可少导。少导一页，pause 报成功，resume 后 guest 内核崩溃
  • 两条路线：关大页（缺页次数 ×512，所有沙箱失去大页）vs 保留大页、4 KiB 存、2 MiB 拼。选后者
  • 三层的改法：判——换成写跟踪位图；存——映射表块大小降到 4 KiB，父代映射原样保留；填——一次 2 MiB 缺页，三级取源（整块同代零拷贝、跨代才拼、拼用缓冲池）
  • 恢复开销的来回：第一版每次缺页分配 2 MiB，恢复后首次触碰慢了约 120 ms；零拷贝快路径和缓冲池把它收回到修复前水平
  • 退路：跟踪没开、位图不可信、Firecracker 没有导出接口时，回到“驻留即脏”；每次暂停在日志里说清导了多少、凭什么导
  • 修复后（920B）：只读 192 MiB 的导出从 358 MiB 降到 12.7 MiB，只改 12 MiB 从 176 MiB 降到 20.3 MiB，导出量等于写跟踪位图，逐行相等

第五部分　和快照回滚共存：哪些地方被撞到，怎么修好

第 21 篇｜快照回滚动了哪些共用部件

要回答的问题：我们新增的快照回滚和暂停恢复是两套机制，为什么还会互相影响？加了回滚之后，普通的启动和暂停多付了什么？

  • 两种快照的分工一句话：回滚是活沙箱里的高频原地读档，暂停恢复是沙箱离场与重建；谁也替代不了谁（只讲结论，机制见回滚那本书）
  • 共用的部件：Firecracker（带回滚扩展）、虚机启动时的配置、写层、脏页位图、proxy、网络槽位
  • 启动时多了什么：加载快照时就打开脏页跟踪；关闭 SMT；每个网络槽位多开一个 conntrack 句柄；proxy 拦截一个专用端口
  • 脏页跟踪的运行期代价：没有硬件跟踪的机器上，每个干净页第一次被写都要陷出一次；所以默认值跟着硬件走（950 有 HDBSS 就开，920B 默认关）
  • 磁盘写层从“一层”变成“一叠”：读要穿过多层，所以回滚那边要折叠层、限制层数，普通读路径才不会越来越慢
  • 和同机其他沙箱系统共存：veth 改名、地址池错开、80 端口规则只匹配本地目的地址

第 22 篇｜三处被撞坏的地方和修法

要回答的问题：回滚加进来以后，暂停恢复具体出过哪些问题？为什么这些问题都是“静默”的？最后怎么修、怎么证明修好了？

  • 磁盘：做过 checkpoint 的沙箱一暂停，封存层就丢了
    • 原因：checkpoint 把写层封存、另开新写层；原生暂停只导出当前写层，更早的写全回到模板，做过 restore 的几乎什么都不剩
    • 为什么静默：映射表从导出内容推出来，自己跟自己对得上；已有测试不做暂停；第一版验证写小文件被 guest 页缓存盖住，假通过
    • 修法：暂停时把整叠层按读的顺序压平再导出；从没 checkpoint 过的沙箱走原来的单层导出，逐字节不变
    • 证据：在 checkpoint 前后各写一大份随机数据，暂停恢复后用 O_DIRECT 绕开页缓存读回比哈希；修复前 3/3 损坏，修复后全过
  • 内存：脏页位图被回滚清零，暂停少导了页
    • 原因：精确增量依赖“位图 = 这一代启动以来写过的页”；可 checkpoint 和 restore 都会清零位图，restore 写回内存还不进任何日志
    • 后果：pause 报成功，resume 后 guest 内核几十毫秒内崩溃
    • 修法：在每次清零之前，把即将被忘掉的位图并进一个每台虚机的“自启动以来脏页集”；暂停时并回再导出；全量 checkpoint 的“全 1”侧车不能并，改为拍之前先导一次活跃位图；对不上就标“不可信”、退回驻留判据
    • 从不 checkpoint 的沙箱完全不受影响
  • SDK：恢复出来的沙箱用不了回滚
    • connect() 只带访问令牌，没带沙箱路由头，proxy 无法按头路由；envd 不受影响（它的地址里带沙箱 ID），所以没人发现
  • 共同的教训：两个各自正确的机制叠加时，要重新检查每一个前提；测试要专门走“组合”，读回要绕开缓存
