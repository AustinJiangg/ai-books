｜从读一个文件说起：程序和操作系统是怎么打交道的

本篇目标：搞懂"程序读文件"这件日常小事背后到底发生了什么，理解用户态/内核态、系统调用、文件描述符这几个基础概念，并亲眼看到"数据被搬了好几次"这个事实——它正是 mmap 诞生的理由。

约定：本系列代码使用 C 语言 + Linux；涉及硬件细节时以 ARM64（aarch64） 为例，必要时对比 x86。

一、一个看似简单的问题

假设你有一个文件 hello.txt，内容是一行字：

Hello, mmap!

在终端里敲：

cat hello.txt

屏幕上就出现了 Hello, mmap!。

太简单了，对吧？但请你认真想一想：cat 这个程序，到底是怎么拿到硬盘上那几个字节的？

硬盘（或 SSD）是一块硬件，文件内容以电荷或磁信号的形式存在里面的某个位置。cat 只是一个普通程序，它怎么知道 hello.txt 存在硬盘的哪个位置？它怎么跟硬盘控制器"说话"？它又怎么把文字送到屏幕上？

答案是：cat 自己一样都不会做。它全靠"求"操作系统帮忙。

这句话就是整个系列的起点。

二、程序不能直接碰硬件

2.1 如果每个程序都能直接操作硬盘，会怎样？

设想一个没有"管理者"的世界：每个程序都可以直接对硬盘下命令。

  • 混乱：你的浏览器正在往硬盘第 1000 号位置写缓存，同时你的音乐播放器也往第 1000 号位置写配置。结果两边的数据互相覆盖，全坏了。
  • 不安全：一个随便下载的小游戏可以直接读走你硬盘上的密码文件、聊天记录，甚至把整块硬盘清零。
  • 太难写：硬盘有几十种型号，SATA、NVMe、U 盘、网络存储……每个程序都要自己学会跟所有硬件打交道？那写一个"打印文件内容"的程序可能需要几万行代码。

所以，现代计算机的做法是：在程序和硬件之间放一个"管理者"——操作系统内核（kernel）。

2.2 银行柜台的比喻

把计算机想象成一家银行：

银行 计算机
金库 硬件（硬盘、内存、网卡……）
柜员 操作系统内核
顾客 普通程序（cat、浏览器、游戏）
柜台窗口 系统调用

顾客不能自己走进金库拿钱。你只能走到柜台前，填一张单子："我要从我的账户取 500 元"。柜员核对你的身份，确认你确实有这个账户、确实有 500 元，然后柜员进金库取钱，从窗口递给你。

程序读文件也是一样：

  1. cat 走到"柜台"前说："请帮我打开 hello.txt。"
  2. 内核检查：这个文件存在吗？你有权限读吗？
  3. 检查通过，内核去和硬盘打交道，把数据取出来。
  4. 内核把数据从"窗口"递给 cat。

这个"柜台窗口"，在计算机里就叫系统调用（system call，简称 syscall）。

三、用户态与内核态：CPU 的两种身份

你可能会问：凭什么程序就"不能"直接碰硬件？程序也是在 CPU 上跑的指令，CPU 怎么知道该不该执行？

答案是：CPU 本身就有"身份等级"的概念。

3.1 ARM64 的异常级别

以 ARM64 处理器为例，CPU 在任意时刻都处在某个异常级别（Exception Level，EL）：

  EL0   ← 普通应用程序（cat、浏览器）     权限最低
  EL1   ← 操作系统内核（Linux）
  EL2   ← 虚拟机管理器（Hypervisor）
  EL3   ← 安全监控固件（Secure Monitor）   权限最高

普通程序运行在 EL0，这就是所谓的用户态（user mode）；Linux 内核运行在 EL1，这就是内核态（kernel mode）。

补充：x86 处理器用的是另一套叫法，叫"特权环"（ring），应用跑在 ring 3，内核跑在 ring 0。名字不同，思路一样。

在 EL0 下，有一大批"危险操作"是 CPU 直接拒绝执行的：比如修改内存翻译规则（第 3 篇会讲的页表）、直接访问硬件设备、关闭中断等等。如果用户程序硬要执行这些指令，CPU 会立刻产生一个"异常"，把控制权交给内核，内核通常会直接把这个程序杀掉。

门卫由硬件亲自把守：不是程序"自觉"不碰硬件，而是 CPU 在硬件层面就不允许它碰。

3.2 那怎么从 EL0 走到 EL1？

既然用户程序被关在 EL0，它怎么"请求"内核帮忙呢？

CPU 提供了一条专门的指令作为合法的"敲门"方式。在 ARM64 上，这条指令叫 svc（Supervisor Call，"呼叫管理者"）。

程序执行 svc 时，CPU 会：

  1. 自动把身份从 EL0 切换到 EL1；
  2. 跳转到内核预先设定好的固定入口地址（程序不能自己选跳到哪里，这保证了安全）；
  3. 内核接手，看看你要办什么业务，办完之后用 eret 指令切回 EL0，回到程序里继续执行。

这一来一回，就是一次系统调用。

四、系统调用：程序的"业务单"

4.1 业务编号与参数

内核提供的"业务"有好几百种：打开文件、读文件、写文件、创建进程、申请内存、发网络包……每种业务有一个编号，叫系统调用号。

在 ARM64 Linux 上，程序发起系统调用的规矩是：

  • 把系统调用号放进寄存器 x8；
  • 把参数依次放进寄存器 x0、x1、x2……（最多 6 个）；
  • 执行 svc #0；
  • 内核办完后，把返回值放在 x0 里。

几个和读写文件相关的调用号（ARM64）：

系统调用 编号 作用
openat 56 打开文件
close 57 关闭文件
read 63 读数据
write 64 写数据
mmap 222 内存映射（本系列主角）

你可能注意到了：这里没有 open，只有 openat。这是因为 ARM64 是比较新的架构，Linux 在设计它的系统调用表时去掉了一批"老式"接口，统一用功能更全的新版本代替。你在 C 代码里写 open()，C 库会帮你转换成 openat。

4.2 亲手"敲一次门"

为了让你感受到系统调用不是什么魔法，下面这段程序不用任何库函数来输出，直接用 svc 指令让内核往屏幕上写一句话（需要在 ARM64 Linux 上编译运行）：

// raw_write.c —— 不借助 printf，直接用 svc 发起 write 系统调用（仅限 ARM64）
int main(void) {
    const char msg[] = "Hello from svc!\n";

    register long x0 asm("x0") = 1;               // 参数1：文件描述符 1（标准输出）
    register long x1 asm("x1") = (long)msg;       // 参数2：数据的地址
    register long x2 asm("x2") = sizeof(msg) - 1; // 参数3：字节数
    register long x8 asm("x8") = 64;              // 系统调用号：write = 64

    asm volatile("svc #0"                         // 敲门！
                 : "+r"(x0)
                 : "r"(x1), "r"(x2), "r"(x8)
                 : "memory");

    return 0;
}

gcc raw_write.c -o raw_write && ./raw_write
# 输出：Hello from svc!

平时我们写的 printf、fwrite、write，最终都会落到类似这样的几条指令上。C 标准库（glibc）只是帮你把这些麻烦事包装好了。

4.3 文件描述符：柜台给你的"号码牌"

上面代码里有个神秘的数字 1，它是什么？

当你请内核打开一个文件时，内核不会把"文件本身"交给你（你也拿不住），而是给你一个小整数，叫文件描述符（file descriptor，简称 fd）。以后你想读这个文件，就拿着这个号码来："请帮我读 3 号文件。"

就像银行取号：你不需要知道金库里的保险柜在哪，只要拿着号码牌，柜员就知道你要办哪个业务。

每个程序一启动，就自带三个已经打开的 fd：

fd 名称 通常指向
0 标准输入 stdin 键盘
1 标准输出 stdout 屏幕（终端）
2 标准错误 stderr 屏幕（终端）

所以，你自己打开的第一个文件，拿到的 fd 通常是 3。

五、动手写一个迷你版 cat

有了这些知识，我们就能写出 cat 的核心逻辑了：

// mycat.c —— 一个最简版本的 cat
#include <fcntl.h>    // open
#include <unistd.h>   // read, write, close
#include <stdio.h>    // perror, fprintf

int main(int argc, char *argv[]) {
    if (argc != 2) {
        fprintf(stderr, "用法: %s 文件名\n", argv[0]);
        return 1;
    }

    // 第1步：请内核打开文件，拿到号码牌 fd
    int fd = open(argv[1], O_RDONLY);
    if (fd < 0) {
        perror("open");   // 打开失败（文件不存在、没权限……）
        return 1;
    }

    char buf[4096];       // 在自己的内存里准备一个"篮子"
    ssize_t n;

    // 第2步：反复请内核"往我的篮子里装数据"
    while ((n = read(fd, buf, sizeof(buf))) > 0) {
        // 第3步：请内核"把篮子里的东西送到屏幕"
        write(1, buf, n);
    }
    // read 返回 0 表示读到文件末尾；返回 -1 表示出错

    // 第4步：归还号码牌
    close(fd);
    return 0;
}

gcc mycat.c -o mycat
echo "Hello, mmap!" > hello.txt
./mycat hello.txt

请特别注意 read(fd, buf, sizeof(buf)) 这一行的语义：

"内核，请从 fd 号文件里读最多 4096 个字节，放进我提供的 buf 里。"

数据是被放进你提供的篮子里的。这个"放进"，就是一次拷贝。记住这个词，我们马上就要和它较真。

六、一次 read 背后，数据到底走了几步？

现在我们跟着那几个字节走一趟，看看从硬盘到屏幕，它们经历了什么。

6.1 读的过程

   ┌──────────┐
   │  硬盘     │  "Hello, mmap!" 存在某个扇区里
   └────┬─────┘
        │ ① 硬盘控制器通过 DMA 把数据搬进内存
        ▼
   ┌──────────────────────┐
   │ 内核的缓冲区           │  （这块区域叫 page cache，第 5 篇详讲）
   │ "Hello, mmap!"       │
   └────┬─────────────────┘
        │ ② CPU 把数据从内核缓冲区拷贝到用户的 buf
        ▼
   ┌──────────────────────┐
   │ 用户程序的 buf[4096]   │
   │ "Hello, mmap!"       │
   └──────────────────────┘

第①步：硬盘 → 内核内存。 内核查到 hello.txt 的内容存在硬盘哪个位置，然后给硬盘控制器下命令。这一步通常用 DMA（Direct Memory Access，直接内存访问） 完成：硬盘控制器自己把数据搬进内存，不需要 CPU 一个字节一个字节地搬，CPU 可以趁机去干别的事。

第②步：内核内存 → 用户 buf。 数据现在在内核的地盘里。但你的程序在 EL0，按规矩不能直接去内核的地盘翻东西。所以内核在 EL1 下，由 CPU 亲自把数据复制到你提供的 buf 中。

为什么内核不直接让程序去自己的地盘读？因为内核的地盘里堆着所有程序的数据和内核自己的机密。一旦开放，安全隔离就荡然无存。所以"拷贝一份给你"是最简单安全的做法。

6.2 写的过程

接着 write(1, buf, n) 又发生了一次反向的拷贝：

   用户的 buf  ──③ CPU 拷贝──▶  内核缓冲区  ──④──▶  终端/屏幕

6.3 数一数

对于 cat 这样一个"把文件内容原样输出"的程序：

  • 数据在内存里被 CPU 拷贝了 2 次（②和③）；
  • 程序和内核之间来回切换了好多次（每次 read、每次 write 都是一次 EL0 → EL1 → EL0）。

而 cat 本身对数据什么都没做，它只是个"二传手"。数据从内核绕到用户程序，再原封不动地绕回内核。

七、拷贝和切换的代价有多大？

文件只有 13 个字节时，这点开销当然无所谓。但如果是一个 10GB 的数据库文件、一个 4K 电影、一台每秒处理几万个请求的服务器呢？

开销主要来自两方面：

1. 系统调用本身的开销

每次 EL0 ↔ EL1 切换，CPU 都要保存和恢复一堆寄存器、做安全检查，为了防御某些 CPU 漏洞可能还要做额外的处理。单次可能只是几十到几百纳秒，但次数多了就很可观。

2. 数据拷贝的开销

CPU 拷贝数据要占用 CPU 时间，还要占用内存带宽。拷贝 1GB 数据，就意味着 CPU 要从内存读 1GB、再写 1GB。而且拷贝来的数据会挤进 CPU 缓存，把其他有用的数据挤出去。

小实验 1：感受系统调用次数的代价

dd 命令可以指定每次 read/write 的大小（bs 参数）。我们读同一个 10MB 文件，分别每次读 1 字节和每次读 1MB：

# 准备一个 10MB 的测试文件
dd if=/dev/zero of=test.bin bs=1M count=10

# 每次读 1 字节：需要大约 1000 万次 read + 1000 万次 write
time dd if=test.bin of=/dev/null bs=1

# 每次读 1MB：只需要 10 次 read + 10 次 write
time dd if=test.bin of=/dev/null bs=1M

你会看到两者耗时相差成百上千倍：前者要好几秒，后者只要几毫秒（具体数字因机器而异）。搬运的数据量完全一样，区别只在于"敲门"的次数。这说明系统调用不是免费的。

这个实验里，第二次运行时文件内容已经在内存的缓存里了，硬盘几乎没参与。所以剩下的时间几乎全是"系统调用 + 拷贝"的成本。

close(3) = 0 归还号码牌

和我们写的 mycat 一模一样！真正的 cat 只是缓冲区更大（128KB），并多做了些错误处理。

彩蛋：上面那行 aarch64-linux-gnu 说明我们在 ARM64 机器上。如果你去掉 -e 过滤，完整输出里会看到好几行以 mmap( 开头的系统调用。没错，cat 在启动阶段就悄悄用了 mmap：它用 mmap 把 C 库装进内存。我们的主角其实一直都在，只是你以前没注意到它。第 12 篇会专门讲这件事。

九、引子：能不能让文件"直接出现在内存里"？

回顾一下我们发现的问题：

  1. 用 read 读文件，数据要从内核拷贝一份到用户程序；
  2. 每读一块都要发起一次系统调用；
  3. 如果文件很大、又需要随机访问（比如数据库里跳着读第 100 万条、第 3 条、第 50 万条记录），你得反复调用 lseek 定位、再 read，非常繁琐，开销也大。

于是一个大胆的想法出现了：

能不能让内核做一次"安排"，之后文件的内容就像一个普通的大数组一样，直接出现在我程序的内存里？我想读第几个字节，就直接 p[i]；想改，就直接 p[i] = 'X'。不用再一次次敲门，也不用来回拷贝。

先剧透一眼它长什么样：

// 只是预览，第 6 篇会逐行详解
char *p = mmap(NULL, 文件大小, PROT_READ, MAP_PRIVATE, fd, 0);

putchar(p[0]);          // 直接读第 0 个字节，没有 read()
putchar(p[1000000]);    // 直接跳到第 100 万个字节，没有 lseek()

这就是 mmap（memory map，内存映射）。

但是，这怎么可能？

  • 程序在 EL0，内核的数据在 EL1 的地盘里，不是说不能直接看吗？
  • 一个 10GB 的文件，难道一调用 mmap 就把 10GB 全读进内存？要是内存只有 8GB 呢？
  • 你改了 p[i]，硬盘上的文件会跟着变吗？什么时候变？

要回答这些问题，我们必须先弄明白一件更根本的事：程序眼里的"内存"，到底是什么？ 指针里存的那个地址，真的是内存条上的某个位置吗？

本篇小结

概念 一句话解释
内核 管理所有硬件的"银行柜员"，程序必须通过它才能使用硬件
用户态 / 内核态 CPU 的两种身份。ARM64 上应用跑在 EL0，内核跑在 EL1，由硬件强制隔离
系统调用 程序请求内核办事的唯一正规渠道。ARM64 上用 svc 指令，调用号放在 x8
文件描述符 内核发给你的"号码牌"，一个小整数；0/1/2 是标准输入/输出/错误

开销来源 系统调用的切换开销 + 数据拷贝开销
mmap 的初心 让文件像数组一样直接出现在程序内存里，省掉拷贝和反复敲门

｜内存到底是什么：地址、字节和物理内存

本篇目标：弄清"内存"和"地址"到底是什么，理解指针的本质，建立对存储速度差距的直觉，并通过一个实验发现一件奇怪的事：程序看到的地址，并不是内存条上的真实位置。

一、内存是一排带编号的储物格

1.1 从比特到字节

计算机里最小的信息单位是比特（bit），它只能是 0 或 1，就像一个开关。

单个比特能表达的东西太少了，所以人们把 8 个比特打包成一组，叫一个字节（byte）。一个字节能表示 2⁸ = 256 种状态，刚好够放一个英文字母、一个 0～255 的数字。

一个字节：  0 1 0 0 1 0 0 0   = 72 = 字母 'H'

1.2 内存 = 一大排储物格

内存（RAM）可以想象成一条无限长的走廊，走廊一侧是一排储物格：

  • 每个格子里正好放 1 个字节；
  • 每个格子门上贴着一个编号，从 0 开始依次往上数；
  • 这个编号，就叫地址（address）。
地址:    0     1     2     3     4     5     6    ...
       ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┐
内容:   │ 'H' │ 'e' │ 'l' │ 'l' │ 'o' │  0  │  42 │ ...
       └─────┴─────┴─────┴─────┴─────┴─────┴─────┘

一台 16GB 内存的电脑，就有大约 160 亿个这样的格子。

CPU 访问内存时只会两个动作：

  • 读："把第 1000 号格子里的东西告诉我。"
  • 写："把 42 放进第 1000 号格子。"

所有复杂的程序，最终都是由海量的"读第几号格子、写第几号格子"组成的。

1.3 多字节的数据

一个 int 在 ARM64 上占 4 个字节，一个 long 或指针占 8 个字节。它们会占用连续的几个格子，而它的"地址"指的是第一个格子的编号。

int x = 0x12345678;   // 占 4 个格子

ARM64 Linux 采用小端序（little-endian），低位字节放在低地址：

地址:   1000  1001  1002  1003
内容:   0x78  0x56  0x34  0x12

（x86 也是小端序。这个细节和 mmap 关系不大，但你以后用 mmap 读二进制文件时会遇到它。）

二、指针就是地址

学 C 语言的新手常被"指针"吓到，其实它一点都不神秘：指针就是一个存放地址的变量。

// pointer.c
#include <stdio.h>

int main(void) {
    int x = 42;
    int *p = &x;      // &x：取 x 的地址；p 里存的就是这个地址

    printf("x 的值      = %d\n", x);
    printf("x 的地址    = %p\n", (void *)&x);
    printf("p 里存的值  = %p\n", (void *)p);
    printf("*p（顺着地址去拿）= %d\n", *p);
    printf("指针本身占 %zu 字节\n", sizeof(p));

    *p = 100;         // 顺着地址，往那个格子里写 100
    printf("现在 x = %d\n", x);
    return 0;
}

在 ARM64 Linux 上运行，你会看到类似：

x 的值      = 42
x 的地址    = 0xffffd2a3b6ac
p 里存的值  = 0xffffd2a3b6ac
*p（顺着地址去拿）= 42
指针本身占 8 字节
现在 x = 100
  • &x 是"x 住在几号格子"；
  • *p 是"到 p 记录的那个格子里去拿东西"；
  • 指针占 8 字节，因为 ARM64 是 64 位架构，地址用 64 位（8 字节）表示。

记住这个地址：0xffffd2a3b6ac。十六进制换算过来大约是 281 万亿。可你的电脑根本没有 281 万亿个字节的内存啊！这是怎么回事？先别急，第五节揭晓。

三、不同存储设备的速度差距

在讲内存原理之前，先建立一个重要的直觉：计算机里不同地方的数据，读取速度差距大得惊人。

3.1 存储层级

       速度越来越快、容量越来越小、价格越来越贵
                       ▲
            ┌──────────────────┐
            │   CPU 寄存器      │  几十个，每个 8 字节
            ├──────────────────┤
            │   L1 缓存         │  几十 KB
            ├──────────────────┤
            │   L2 / L3 缓存    │  几 MB 到几十 MB
            ├──────────────────┤
            │   内存（DRAM）     │  几 GB 到几 TB
            ├──────────────────┤
            │   SSD 固态硬盘     │  几百 GB 到几十 TB
            ├──────────────────┤
            │   机械硬盘 HDD     │  几 TB 到几十 TB
            └──────────────────┘

3.2 换算成人类能感受的时间

一次访问的大致耗时（数量级，不同硬件差别很大）：

存储 实际耗时 如果把 1 纳秒放大成 1 秒
L1 缓存 ~1 纳秒 1 秒（眨个眼）
L2 缓存 ~4 纳秒 4 秒
L3 缓存 ~10～40 纳秒 半分钟
内存 DRAM ~80～120 纳秒 一分半钟（泡杯咖啡）
NVMe SSD 随机读 ~20～100 微秒 6 小时～1 天多
机械硬盘随机读 ~5～10 毫秒 2～4 个月

读内存比读 SSD 快上千倍，比读机械硬盘快十万倍。

这个巨大的差距决定了操作系统几乎所有的设计：

  • 尽量把要用的数据留在内存里（这就是第 5 篇的 page cache）；
  • 尽量不让 CPU 干等磁盘（这和第 4 篇的缺页异常密切相关）；
  • mmap 能不能快，很大程度取决于数据是不是已经在内存里。

3.3 缓存行

CPU 从内存读数据时，不是一个字节一个字节地读，而是一次搬一整块，叫缓存行（cache line）。ARM64 处理器的缓存行通常是 64 字节。

所以连续访问相邻的数据很快（一次搬来，后面直接命中缓存），跳来跳去访问很慢。这叫局部性原理：程序访问过的数据，它附近的数据、它本身，很可能马上又要被访问。整个存储体系（包括后面要讲的页、预读）都建立在局部性之上。

四、物理内存：真实的储物格

4.1 物理地址

内存条上那些真实存在的储物格，它们的编号叫物理地址（physical address）。CPU 通过内存控制器，把物理地址送到内存条上，就能读写对应的格子。

4.2 物理地址空间里不只有内存

一个有趣的事实：物理地址并不全是内存条。

ARM64 系统里，一部分物理地址被分配给了各种硬件设备：网卡、串口、中断控制器、PCIe 设备等。CPU 往这些地址"写数据"，实际上是在给设备发命令。这叫 MMIO（Memory-Mapped I/O，内存映射 I/O）。

你看，"映射"这个词已经出现了：把设备"映射"到地址上，让 CPU 用读写内存的方式操作设备。mmap 的思想与此一脉相承：把文件映射到地址上，让程序用读写内存的方式操作文件。

比如在 QEMU 模拟的 ARM64 virt 机器上，物理地址布局大致是：

0x0000_0000 ～ 0x0800_0000   固件（Flash）
0x0800_0000 ～ ...           中断控制器 GIC
0x0900_0000                  串口 UART
...                          其他设备
0x4000_0000 ～               内存（RAM）从 1GB 处开始

小实验 1：看看你机器的物理地址布局

sudo cat /proc/iomem

在 ARM64 机器上你会看到类似（截取一部分）：

09000000-09000fff : pl011@9000000
40000000-13fffffff : System RAM
  40210000-41a0ffff : Kernel code
  ...

System RAM 就是真正的内存条区域，其他都是设备。（不加 sudo 的话，地址会全显示成 0，这是出于安全考虑。）

五、关键实验：地址真的是物理地址吗？

现在回到第二节留下的疑问。我们来做一个实验。

小实验 2：同一个地址，不同的值

// same_addr.c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int global = 0;   // 全局变量

int main(int argc, char *argv[]) {
    global = atoi(argv[1]);   // 用命令行参数给它赋值

    for (int i = 0; i < 5; i++) {
        printf("[进程 %d] global 的地址 = %p，值 = %d\n",
               getpid(), (void *)&global, global);
        sleep(1);
    }
    return 0;
}

编译后先单独运行两次：

gcc same_addr.c -o same_addr
./same_addr 1
./same_addr 2

你可能发现两次打印的地址不一样。这是因为 Linux 有一个安全机制叫 ASLR（地址空间布局随机化），每次运行都会把程序放到随机的位置，让攻击者猜不到地址。

我们用 setarch -R 临时关掉 ASLR，并让两个程序同时运行：

setarch -R ./same_addr 111 &
setarch -R ./same_addr 222 &
wait

输出类似：

[进程 5001] global 的地址 = 0xaaaaaaab0010，值 = 111
[进程 5002] global 的地址 = 0xaaaaaaab0010，值 = 222
[进程 5001] global 的地址 = 0xaaaaaaab0010，值 = 111
[进程 5002] global 的地址 = 0xaaaaaaab0010，值 = 222
...

两个同时运行的程序，变量在同一个地址 0xaaaaaaab0010，却存着不同的值！

如果这个地址是内存条上真实的格子编号，那这根本不可能：同一个格子在同一时刻只能放一个值。

唯一的解释是：

程序看到的地址是"假的"。两个进程的 0xaaaaaaab0010，实际上对应着内存条上两个不同的格子。

再加上第二节的疑问——地址 0xffffd2a3b6ac 大约是 281TB，远超实际内存——答案也就清楚了：程序里的地址，根本不是物理地址。

这些"假地址"叫虚拟地址（virtual address），而把虚拟地址变成真实物理地址的机制，就是下一篇的主角：虚拟内存。

六、为什么不让程序直接用物理地址？

在虚拟内存发明之前，早期计算机确实是让程序直接使用物理地址的。我们看看这会带来什么麻烦。

问题一：互相踩踏

程序 A 编译时假设自己的数据放在地址 0x1000，程序 B 也这么假设。两个同时运行，就会互相覆盖对方的数据。

物理内存   0x1000
          ┌─────────┐
程序A写 →  │  ???    │ ← 程序B也写
          └─────────┘

问题二：毫无隔离

任何程序都可以读写任何地址，包括别的程序的内存、操作系统内核的内存。一个有 bug 的程序写错一个指针，就可能把整个系统搞崩溃；一个恶意程序可以轻松偷走所有数据。

问题三：内存碎片

假设内存有 100MB，先后启动了几个程序又关掉了几个，空闲内存变成了这样：

|■■■■ 已用 ■■■■| 空闲 20MB |■■ 已用 ■■| 空闲 30MB |■■■ 已用 ■■■| 空闲 10MB |

总共空闲 60MB，但现在一个需要连续 40MB 的程序却无法运行，因为没有一块连续的 40MB 空间。

问题四：程序位置不固定

既然不知道程序会被加载到物理内存的哪个位置，程序里所有用到地址的地方（变量地址、函数地址）都得在加载时临时修改，这非常麻烦且低效。

问题五：内存不够用

如果一个程序需要的内存比物理内存还多，就根本跑不起来。

历史上的尝试

人们先后尝试过几种方案：

  • 基址 + 界限寄存器：给每个程序一个"起始位置"和"最大长度"，程序访问的地址自动加上起始位置，超出长度就报错。解决了互相踩踏和隔离问题，但碎片问题依旧，而且整个程序必须连续放在一起。
  • 分段：把程序分成代码段、数据段、栈段等几块，每块单独设置基址和界限。灵活了一些，但碎片问题仍然存在。

最终胜出的方案是分页（paging）：把内存切成固定大小的小块，用一张表记录"虚拟的第几块对应物理的第几块"。这张表叫页表。它一次性解决了上面全部五个问题——下一篇详细讲它是怎么做到的。

七、把思路串起来

回顾本篇的发现：

  1. 内存是一排带编号的储物格，编号叫地址；
  2. 指针就是存放地址的变量；
  3. 内存比磁盘快上千倍，所以"数据在不在内存里"决定了性能；
  4. 物理地址空间里既有内存，也有设备；
  5. 程序看到的地址不是物理地址，同一个地址在不同程序里对应不同的物理位置。

第 5 点是理解 mmap 的钥匙。回想上一篇的困惑："程序在 EL0，怎么能直接看到内核管理的文件数据？"答案其实已经呼之欲出了：

既然程序的地址都是"假的"，需要经过翻译才能找到真实的格子，那么只要内核把翻译规则改一改，让程序的某段虚拟地址翻译到"存着文件内容的那些物理格子"上，程序就能直接读到文件了。不需要拷贝，因为程序看到的就是那些格子本身。

这就是 mmap 的核心原理。接下来两篇，我们会把这套"翻译机制"彻底拆开。

本篇小结

概念 一句话解释
字节 8 个比特，内存里每个格子放 1 个字节
地址 格子的编号
指针 存放地址的变量，ARM64 上占 8 字节
存储层级 寄存器 > 缓存 > 内存 > SSD > HDD，越往下越慢越大
缓存行 CPU 一次从内存搬运的数据块，ARM64 上通常 64 字节
物理地址 内存条（和设备）上真实位置的编号
MMIO 设备占用物理地址，CPU 用读写内存的方式操作设备

｜虚拟内存：每个程序都活在自己的"楚门的世界"

本篇目标：理解虚拟地址如何被翻译成物理地址——页、页表、MMU、TLB 这四个核心概念；以 ARM64 为例拆解四级页表；最后第一次读懂进程的内存地图 /proc/self/maps，并在里面找到 mmap。

一、楚门的世界

电影《楚门的世界》里，主角楚门从出生起就生活在一个巨大的摄影棚里。他看到的街道、大海、天空全是布景，但他以为这就是整个世界。

每个进程都是一个楚门：

  • 它以为自己独占了一个巨大、连续、干净的内存空间，地址从 0 一直到几百 TB；
  • 它看不到别的进程，也看不到内核的内部；
  • 它访问的每一个地址，都会被悄悄"翻译"成某个真实的物理地址。

这套机制叫虚拟内存（virtual memory）。每个进程拥有的这片"假"地址范围，叫它的虚拟地址空间（virtual address space）。

  进程 A 的世界                     物理内存                     进程 B 的世界
 ┌──────────────┐                ┌──────────┐                ┌──────────────┐
 │ 0xaaaa...010 │ ──────┐        │ 格子 #7  │       ┌─────── │ 0xaaaa...010 │
 │              │       └──────▶ │  值=111  │       │        │              │
 │              │                ├──────────┤       │        │              │
 │              │                │ 格子 #42 │ ◀─────┘        │              │
 │              │                │  值=222  │                │              │
 └──────────────┘                └──────────┘                └──────────────┘

这就解释了上一篇的实验：两个进程的同一个虚拟地址，翻译到了不同的物理位置。

二、翻译的单位：页

2.1 为什么不能逐字节翻译？

最直接的想法是：给每个进程准备一张表，记录"虚拟地址 0 对应物理地址几、虚拟地址 1 对应物理地址几……"。

但这样一张表比内存本身还大——每个字节的映射都需要好几个字节来记录。行不通。

2.2 分页：以块为单位翻译

解决办法是批发：把虚拟地址空间和物理内存都切成固定大小的块，以块为单位做映射。

  • 虚拟地址空间里的一块，叫虚拟页（page），简称页；
  • 物理内存里的一块，叫物理页帧（page frame），简称页帧或物理页；
  • 一页的大小，最常见的是 4KB（4096 字节）。

ARM64 的特别之处：ARM64 硬件支持 4KB、16KB、64KB 三种页大小（ARM 称之为"翻译粒度 granule"），由内核编译时选定。大多数发行版用 4KB，但某些服务器发行版用过 64KB，Apple Silicon 上的 Linux 用 16KB。本系列默认 4KB，但写代码时永远不要把 4096 写死，要用 sysconf(_SC_PAGESIZE) 查询。

查看你的系统页大小：

getconf PAGESIZE
# 4096

2.3 地址的拆分

有了页，一个虚拟地址就可以拆成两部分：

     虚拟地址  =  [ 虚拟页号 ]  [ 页内偏移 ]

因为 4KB = 2¹²，页内偏移正好是地址的低 12 位。

举例：虚拟地址 0x12345678

0x12345678
  ├─────┤├─┤
  0x12345 0x678
  虚拟页号  页内偏移

翻译时只需要查出"虚拟页 0x12345 对应哪个物理页"，假设是物理页 0x8a0f1，那么物理地址就是：

物理页号 0x8a0f1 拼上偏移 0x678  →  物理地址 0x8a0f1678

页内偏移原样保留，只翻译页号。 映射表的条目一下子少了 4096 倍。

记录"虚拟页号 → 物理页号"的这张表，叫做页表（page table）。每个进程都有自己的一份页表，这就是每个进程拥有独立世界的原因。

三、多级页表：ARM64 的四级结构

3.1 一张大表还是太大

ARM64 Linux 下，用户程序通常可用 48 位虚拟地址，即 256TB 的空间。去掉 12 位页内偏移，还剩 36 位页号，也就是 2³⁶ ≈ 687 亿个虚拟页。

如果用一张平铺的页表，每个条目 8 字节，那么每个进程的页表就要 512GB。显然不可能。

可现实中一个进程通常只用了几十 MB 到几 GB，256TB 里绝大部分都是空的。为空白区域准备表项纯属浪费。

3.2 解决办法：像目录一样分级

想想图书馆怎么管理几百万本书：先分"楼层"，楼层里分"区"，区里分"书架"，书架上才是"书"。没人用的楼层，根本不用摆书架。

ARM64（4KB 页、48 位地址）把 36 位页号拆成 4 段，每段 9 位：

 63      48 47     39 38     30 29     21 20     12 11          0
┌─────────┬─────────┬─────────┬─────────┬─────────┬────────────┐
│ 全0或全1 │ L0 索引  │ L1 索引  │ L2 索引  │ L3 索引  │  页内偏移   │
│ (选择    │  9 位    │  9 位    │  9 位    │  9 位    │   12 位    │
│ TTBR0/1) │         │         │         │         │            │
└─────────┴─────────┴─────────┴─────────┴─────────┴────────────┘

为什么是 9 位？因为 2⁹ = 512，每张表 512 个条目 × 8 字节 = 4096 字节，正好一页。每一级的表本身就是一个物理页，设计得非常整齐。

Linux 内核给这四级起了通用的名字：

ARM64 叫法 Linux 通用叫法 每个条目管辖范围
L0 表 PGD（页全局目录） 512GB
L1 表 PUD（页上级目录） 1GB
L2 表 PMD（页中间目录） 2MB
L3 表 PTE（页表项） 4KB（一页）

3.3 一次完整的翻译（页表遍历）

  TTBR0_EL1 寄存器（存着 L0 表的物理地址）
        │
        ▼
  ┌──────────┐  用 L0 索引查
  │  L0 表    │─────────────┐
  └──────────┘             ▼
                     ┌──────────┐  用 L1 索引查
                     │  L1 表    │─────────────┐
                     └──────────┘             ▼
                                        ┌──────────┐  用 L2 索引查
                                        │  L2 表    │─────────────┐
                                        └──────────┘             ▼
                                                           ┌──────────┐  用 L3 索引查
                                                           │  L3 表    │──────┐
                                                           └──────────┘      ▼
                                                                    物理页号 + 页内偏移
                                                                         = 物理地址

每一级条目里存的是下一级表的物理地址，最后一级（L3）的条目里存的是目标物理页的地址。

稀疏的妙处：如果某个 512GB 范围完全没用，那么它在 L0 表里的条目就标记为"无效"，下面的 L1、L2、L3 表根本不用创建。一个普通进程的页表通常只占几十 KB 到几 MB。

3.4 页表项里还有什么？

一个 8 字节的页表项，除了物理页地址，还有一堆标志位。ARM64 上重要的几个：

标志 含义
有效位（bit 0） 这个条目是否有效。为 0 时，访问会触发异常（下一篇的主角：缺页异常）
AP（访问权限） 只读还是可写；用户态（EL0）能否访问
UXN / PXN 禁止用户态 / 内核态从这一页执行代码
AF（访问标志） 这一页是否被访问过（内核用它判断哪些页"热"、哪些页"冷"）
脏标记（DBM 相关） 这一页是否被写过

这些标志让页表不只是"翻译字典"，还是"门禁系统"：

  • 代码页设为"只读 + 可执行"，防止程序被篡改；
  • 数据页设为"可写 + 不可执行"，防止把数据当代码执行（防御很多攻击）；
  • 内核的页设为"EL0 不可访问"，用户程序就碰不到内核。

记住"有效位"和"只读"这两个标志，后面讲缺页、写时复制、mmap 时会反复用到。

3.5 大块映射：跳过最后几级

L1、L2 的条目除了指向下一级表，还可以直接指向一大块物理内存（ARM64 称为 block 描述符）：

  • L2 条目直接映射一块 2MB 的物理内存；
  • L1 条目直接映射一块 1GB 的物理内存。

这就是大页（huge page）的硬件基础。第 10 篇讲性能时会用到。

四、MMU：干翻译活的硬件

翻译工作如果由软件来做，每访问一次内存都要先跑几十条指令查表，程序会慢得无法忍受。所以 CPU 里专门有一个硬件部件负责翻译，叫 MMU（Memory Management Unit，内存管理单元）。

  • 程序发出的每一个地址都是虚拟地址；
  • MMU 自动查页表、算出物理地址，再去访问内存；
  • 整个过程对程序完全透明，程序根本不知道翻译发生过。

4.1 ARM64 的两个页表基址寄存器

ARM64 有个很优雅的设计：用两个寄存器分别管理地址空间的两半。

虚拟地址
0xFFFF_FFFF_FFFF_FFFF ┌─────────────────────┐
                      │                     │
                      │   内核空间           │  ← 由 TTBR1_EL1 指向的页表翻译
                      │                     │    （所有进程共享同一份）
0xFFFF_0000_0000_0000 ├─────────────────────┤
                      │                     │
                      │   不可用的"空洞"      │  ← 访问即出错
                      │                     │
0x0000_FFFF_FFFF_FFFF ├─────────────────────┤
                      │                     │
                      │   用户空间（256TB）   │  ← 由 TTBR0_EL1 指向的页表翻译
                      │                     │    （每个进程各一份）
0x0000_0000_0000_0000 └─────────────────────┘
  • 地址最高 16 位全是 0 → 用 TTBR0_EL1（用户页表）翻译；
  • 地址最高 16 位全是 1 → 用 TTBR1_EL1（内核页表）翻译。

进程切换时，内核只需要把 TTBR0_EL1 换成新进程的页表地址，CPU 瞬间就"进入"了另一个进程的世界。而内核那一半不用动。

上一篇实验里栈变量的地址 0xffffd2a3b6ac，看上去以 0xffff 开头，但它只有 48 位：0x0000_ffff_d2a3_b6ac，最高 16 位是 0，所以它在用户空间的顶部附近，不是内核地址。

五、TLB：翻译结果的小本本

5.1 翻译太慢了

仔细算一下：按 3.3 节的流程，翻译一个地址需要依次读 L0、L1、L2、L3 四张表，也就是额外的 4 次内存访问。本来只想读 1 次内存，结果要读 5 次，程序岂不是慢了 5 倍？

5.2 TLB 来救场

MMU 里有一个小而快的缓存，叫 TLB（Translation Lookaside Buffer，地址转换后备缓冲区），专门记录"最近翻译过的虚拟页 → 物理页"。

程序访问虚拟地址
       │
       ▼
   查 TLB ──── 命中（绝大多数情况）──▶ 直接得到物理地址，几乎零开销
       │
     未命中
       │
       ▼
  页表遍历（4 次内存访问）──▶ 结果存入 TLB ──▶ 得到物理地址

因为局部性原理，程序在一段时间内总是反复访问少数几个页，所以 TLB 命中率通常高达 99% 以上。

TLB 通常只有几十到几千个条目。假设有 1024 个条目，每条管 4KB，那 TLB 总共能"覆盖" 4MB 内存。如果程序在几 GB 的数据里随机跳着访问，TLB 就会频繁未命中——这正是大页能提升性能的原因（一条 2MB 大页条目顶 512 个普通条目）。

5.3 TLB 的一致性问题

TLB 是页表的缓存，那么当内核修改了页表（比如解除一个映射、修改权限）时，TLB 里的旧记录就过时了，必须作废。

  • ARM64 用 TLBI 指令作废 TLB 条目；
  • 在多核系统中，其他 CPU 核的 TLB 里可能也有旧记录，也要一起作废。ARM64 的 TLBI ... IS（Inner Shareable）变体可以由硬件广播给所有核。

这个操作叫 TLB shootdown（TLB 击落），代价不小。第 10 篇会讲到：munmap 有时候比你想象的慢，原因就在这里。

5.4 ASID：切换进程不用清空 TLB

进程切换后，旧进程的 TLB 记录对新进程无效。难道每次切换都清空 TLB？那太浪费了。

ARM64 给每个 TLB 条目打上一个标签，叫 ASID（Address Space ID，地址空间编号），表示"这条记录属于哪个进程"。切换进程时换一个 ASID 即可，旧进程的记录可以留着，等它切回来时还能用。

六、虚拟内存一次解决了所有问题

回顾上一篇列出的五个问题：

问题 虚拟内存的解法
互相踩踏 每个进程有独立页表，相同虚拟地址对应不同物理页
没有隔离 进程只能访问自己页表里有的页；内核页禁止 EL0 访问
内存碎片 虚拟上连续的页，物理上可以分散在任何地方
程序位置不固定 每个进程都可以使用相同的虚拟地址布局
内存不够用 页表项可以标记为"无效"，数据暂时放在磁盘上，用到时再调入（下一篇）

而且，虚拟内存还带来了一项全新的能力：

共享：两个进程的页表可以指向同一个物理页。比如 100 个进程都在用 C 库，内存里只需要放一份 C 库的代码，大家的页表都指向它。

这正是 mmap 的根基：让进程页表里的某些条目，指向存放着文件内容的物理页。

八、一个悬而未决的问题

上面的地图显示 C 库映射了约 1.6MB 的代码。那么问题来了：

程序启动那一刻，内核真的把这 1.6MB 全部从磁盘读进内存、并逐页填好页表了吗？

如果是这样，启动一个程序就要读很多数据；一个映射 10GB 文件的 mmap 调用就要读 10GB 才能返回。

事实并非如此。页表项里那个"有效位"，是一个精妙设计的起点：内核完全可以先把页表项留空，等程序真的访问某一页时，再临时去准备数据。

这个"临时准备"的过程，就是下一篇的主角：缺页异常。

｜缺页异常：操作系统的"按需供货"魔法

本篇目标：理解访问一个"不存在"的页时发生了什么——缺页异常（page fault）的完整流程；分清小缺页、大缺页和段错误；用实验证明"申请了内存 ≠ 占用了内存"。这是理解 mmap 为什么能"瞬间映射 10GB 文件"的关键。

一、先讲一个外卖店的故事

你开了一家外卖店，菜单上有 200 道菜。你有两种经营方式：

方式一：提前备齐。 每天开门前，把 200 道菜全部做好摆在柜台上。顾客点什么都能立刻拿走。但大部分菜根本没人点，最后全浪费了，而且每天开门前要忙好几个小时。

方式二：按单现做。 菜单照样挂着 200 道菜，但厨房里什么都不提前做。顾客点了哪道，才去做哪道。第一次点某道菜需要等一会儿，但不浪费，开门也很快。

现代操作系统管理内存，用的就是方式二。

  • "菜单上有 200 道菜" = 进程的地址空间里登记了一大片合法区域；
  • "厨房里什么都没做" = 页表项全都是无效的，没有分配物理内存；
  • "顾客点菜" = 程序第一次访问某个地址；
  • "现做" = 内核临时分配物理页、填好数据、改好页表。

这种策略叫按需分页（demand paging），而"顾客点菜"这一刻触发的事件，叫缺页异常（page fault）。

二、缺页异常是什么

回忆上一篇：每个页表项都有一个有效位。当程序访问一个虚拟地址时，MMU 去查页表，如果发现：

  • 对应的页表项无效（或者中间某一级表根本不存在）；或者
  • 页表项有效，但权限不符（比如往只读页里写）；

MMU 无法完成翻译，就会中断当前指令，产生一个异常，把控制权交给内核。这就是缺页异常。

"异常"这个词听起来像是出错了，但在这里它完全是正常业务流程的一部分。一个程序从启动到退出，通常会经历成千上万次缺页异常，绝大多数都是内核"故意安排"的。

三、ARM64 上的完整流程

我们以 ARM64 为例，慢镜头回放一次缺页异常。

 用户程序 (EL0)                硬件 (MMU/CPU)                     内核 (EL1)
 ─────────────                ──────────────                     ──────────
 执行 ldr x0, [x1]
 (读 x1 指向的地址)
        │
        └─────────────▶  查 TLB：未命中
                         查页表：L3 页表项无效！
                         │
                         ├─ 把出错的虚拟地址存入 FAR_EL1
                         ├─ 把出错原因存入 ESR_EL1
                         ├─ 把出错指令的地址存入 ELR_EL1
                         └─ 切换到 EL1，跳到异常向量表 ──────▶  ① 读 ESR：是"数据访问异常"
                                                               ② 读 FAR：出错地址是 X
                                                               ③ X 属于进程的合法区域吗？
                                                               ④ 合法：准备物理页，填数据
                                                               ⑤ 修改页表项，设为有效
                                                               ⑥ eret 返回
                         ◀────────────────────────────────────
                         回到 ELR_EL1 指向的那条指令
        ◀────────────────  重新执行 ldr x0, [x1]
 这次成功了！              （页表已有效，翻译成功）
 程序浑然不觉

几个关键点：

1. 硬件留下"案发现场"。 ARM64 用三个寄存器记录现场：

寄存器 记录的内容
FAR_EL1（Fault Address Register） 访问出错的虚拟地址
ESR_EL1（Exception Syndrome Register） 出错的原因：是读还是写？是哪一级页表缺失？还是权限错误？
ELR_EL1（Exception Link Register） 出错指令的地址，处理完后从这里继续

2. 指令会被重新执行。 这是缺页异常最妙的地方。处理完毕后，CPU 回到出错的那条指令重新执行，而不是跳过它。第二次执行时页表已经准备好了，指令顺利完成。程序完全感觉不到中间发生了什么，只是这条指令"执行得比平时慢了一点"。

3. 内核的判断依据。 第③步，内核怎么知道地址 X 是不是"合法区域"？内核为每个进程维护了一份"菜单"，记录哪些地址范围是合法的、权限是什么、背后关联着什么（文件？匿名内存？）。你在 /proc/self/maps 里看到的每一行，就是菜单上的一个条目。这个数据结构叫 VMA，第 11 篇会深入讲。

关键区分："菜单"（VMA）和"页表"是两回事。 菜单记录"你被允许用哪些地址"；页表记录"哪些地址现在真的有物理页"。菜单上有、页表里没有，就是"可以点但还没做的菜"——访问时触发缺页，内核现做。

四、缺页的几种情况

内核在第③④步会根据具体情况做不同处理。

情况一：首次访问匿名内存 → 分配一个清零的页

程序 malloc 了一大块内存，第一次往里写数据。这块地址在菜单上（合法），但页表里还没有。

内核的处理：从空闲物理页里拿一个，全部填 0，填入页表，返回。

为什么要填 0？因为这个物理页上一次可能被别的进程用过，里面可能有别人的密码、私信。不清零就会泄露数据。

情况二：访问文件映射，数据已在内存 → 直接挂上

程序访问了一段 mmap 映射的文件区域，而这部分文件内容恰好已经在内存的缓存里（第 5 篇的 page cache）。

内核的处理：找到那个缓存页，直接让页表项指向它。不用读磁盘，很快。

情况三：访问文件映射，数据不在内存 → 从磁盘读

和情况二一样，但文件内容不在内存里。

内核的处理：分配物理页，向磁盘发出读请求，让当前进程睡眠等待，CPU 去运行别的进程。磁盘读完后，唤醒进程，填好页表，返回。这可能需要几十微秒到几十毫秒。

情况四：写一个只读页 → 写时复制或报错

页表项有效但标为只读，程序却要写。内核检查菜单：

  • 如果菜单说这块区域本来就可写，只是页表故意设成只读，那这是写时复制（Copy-on-Write）的信号：复制一份私有副本给程序写（第 7 篇详讲）；
  • 如果菜单说这块区域本来就只读，那就是程序的错。

情况五：地址根本不在菜单上 → 段错误

程序访问了一个菜单上不存在的地址，比如空指针、野指针、数组越界越到了空白区域。

内核的处理：向进程发送 SIGSEGV 信号，默认动作是杀死进程。你看到的就是著名的：

Segmentation fault (core dumped)

段错误的本质，就是一次内核无法"兑现"的缺页异常。

五、小缺页与大缺页

内核把成功处理的缺页分成两类：

类型 英文 特点 典型耗时
小缺页 minor fault 不需要读磁盘：分配清零页、挂上已缓存的页 约 0.1～几微秒
大缺页 major fault 需要从磁盘读数据 SSD 约几十～几百微秒，机械硬盘几毫秒以上

两者的耗时可能相差上千倍。分析 mmap 性能时，第一件事就是看大缺页有多少。

六、实验：申请了内存 ≠ 占用了内存

6.1 实验程序

// lazy.c —— 观察按需分页
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/resource.h>

// 从 /proc/self/status 读取 VmRSS（实际占用的物理内存）
static long rss_kb(void) {
    FILE *f = fopen("/proc/self/status", "r");
    char line[256];
    long kb = -1;
    while (fgets(line, sizeof line, f)) {
        if (strncmp(line, "VmRSS:", 6) == 0) {
            sscanf(line + 6, "%ld", &kb);
            break;
        }
    }
    fclose(f);
    return kb;
}

static long minor_faults(void) {
    struct rusage ru;
    getrusage(RUSAGE_SELF, &ru);
    return ru.ru_minflt;
}

int main(void) {
    const size_t size = 1UL << 30;            // 1GB
    const long page = sysconf(_SC_PAGESIZE);

    printf("开始：        RSS = %6ld KB, 小缺页 = %ld\n", rss_kb(), minor_faults());

    char *p = malloc(size);
    if (!p) { perror("malloc"); return 1; }
    printf("malloc 1GB 后：RSS = %6ld KB, 小缺页 = %ld\n", rss_kb(), minor_faults());

    // 只写前 100MB，每页写一个字节
    for (size_t i = 0; i < 100UL * 1024 * 1024; i += page)
        p[i] = 1;
    printf("写 100MB 后： RSS = %6ld KB, 小缺页 = %ld\n", rss_kb(), minor_faults());

    // 把剩下的也写了
    for (size_t i = 0; i < size; i += page)
        p[i] = 1;
    printf("写满 1GB 后： RSS = %6ld KB, 小缺页 = %ld\n", rss_kb(), minor_faults());

    free(p);
    return 0;
}

gcc -O1 lazy.c -o lazy && ./lazy

6.2 典型输出（4KB 页）

开始：        RSS =   1408 KB, 小缺页 = 89
malloc 1GB 后：RSS =   1408 KB, 小缺页 = 91
写 100MB 后： RSS = 103944 KB, 小缺页 = 25691
写满 1GB 后： RSS = 1050132 KB, 小缺页 = 262236

如果你的系统开启了透明大页（第 10 篇），缺页次数可能会少得多，因为一次缺页可能直接分配 2MB。可以用 cat /sys/kernel/mm/transparent_hugepage/enabled 查看。

6.3 解读

  1. malloc(1GB) 之后，RSS 几乎没变。 申请 1GB 只是在"菜单"上登记了一段地址，没有分配任何物理内存。
  2. 写了 100MB 之后，RSS 涨了约 100MB，缺页增加了约 25600 次。 100MB ÷ 4KB = 25600，每页一次缺页，完美对应。
  3. 写满 1GB 后，缺页总数约 26 万次，对应 1GB ÷ 4KB = 262144 页。

这就是按需分页：内存是在第一次被触碰时才真正分配的。

6.4 用工具统计缺页

不改代码也可以统计任何程序的缺页次数：

/usr/bin/time -v ./lazy 2>&1 | grep -i fault
#   Major (requiring I/O) page faults: 0
#   Minor (reclaiming a frame) page faults: 262236

# 或者用 perf
perf stat -e page-faults,minor-faults,major-faults ./lazy

6.5 观察大缺页

大缺页需要从磁盘读数据。我们先清空系统的文件缓存（第 5 篇解释），然后运行一个"大"程序：

sync; echo 3 | sudo tee /proc/sys/vm/drop_caches
/usr/bin/time -v python3 -c "pass" 2>&1 | grep -i "page faults"
#   Major (requiring I/O) page faults: 87      ← 冷启动：要从磁盘读 Python 的代码
#   Minor (reclaiming a frame) page faults: 1012

/usr/bin/time -v python3 -c "pass" 2>&1 | grep -i "page faults"
#   Major (requiring I/O) page faults: 0       ← 再跑一次：都在内存里了
#   Minor (reclaiming a frame) page faults: 1018

第一次运行时，Python 解释器和它的库都不在内存里，访问代码时触发了大缺页；第二次运行，这些文件已被缓存，大缺页变成 0。（这个实验会清空整个系统的文件缓存，别在繁忙的生产服务器上做。）

七、实验：亲手制造一次段错误

// segv.c
#include <stdio.h>

int main(void) {
    int *p = (int *)0x1234;   // 一个肯定不在"菜单"上的地址
    printf("准备访问 %p ...\n", (void *)p);
    *p = 42;                  // 触发缺页 → 内核查菜单 → 不合法 → SIGSEGV
    printf("这句永远不会打印\n");

}

# Segmentation fault (core dumped)

内核日志里的 level 0 translation fault 说明：MMU 在第 0 级页表就发现条目无效了（这一大片区域根本没有页表）。esr 0x92000044 就是 ESR_EL1 寄存器的值，内核正是解码它得知"这是一次写操作导致的第 0 级翻译错误"。

八、按需分页带来的好处与代价

好处

  1. 启动快：程序启动时不需要把整个程序读进内存，用到哪部分读哪部分。
  2. 省内存：申请了没用的内存不占物理空间。很多程序会预留大块内存但只用一小部分。
  3. 可以"超额"：所有进程申请的内存总和可以超过物理内存。Linux 默认允许这种内存超售（overcommit）。
  4. 为 mmap 铺平道路：mmap 一个 10GB 的文件可以瞬间完成，因为它只是在"菜单"上登记，什么都不读。

代价

  1. 第一次访问变慢：每个页第一次被访问都要付出一次缺页的开销。对于"马上要全部用到"的内存，可以用 MAP_POPULATE 或 madvise 提前填充（第 10 篇）。
  2. 超售的风险：如果大家同时兑现承诺，物理内存不够了怎么办？内核会先尝试回收缓存、把不常用的页换出到磁盘（swap），实在不行就启动 OOM Killer（内存耗尽杀手），挑一个进程杀掉。
  3. 延迟不可预测：一次普通的内存读取，可能因为大缺页而卡住几毫秒。对延迟敏感的程序（比如交易系统、实时音视频）这是个大问题，可以用 mlock 把页面锁在内存里。

九、和 mmap 的关系

把本篇和前几篇连起来，mmap 的原理已经呼之欲出了：

调用 mmap(文件, 10GB)
   │
   └─▶ 内核只在"菜单"上登记：
       "地址 0xffff00000000 ~ 0xffff80000000 对应 文件 的 0~10GB 处"
       页表：一个都不填。 物理内存：一个字节都不分配。
       立即返回。

程序第一次读 p[5000]
   │
   └─▶ 缺页异常！
       内核查菜单：这个地址对应文件第 1 页（5000 / 4096 = 1）
       ├─ 文件第 1 页已在内存缓存中？ → 小缺页：直接挂上
       └─ 不在？ → 大缺页：从磁盘读进来，再挂上
       修改页表，重新执行指令，程序读到了数据

程序再读 p[5001]
   │
   └─▶ 同一页，页表已有效，TLB 命中，和读普通内存一样快

mmap 不读文件，缺页才读文件。 这就是 mmap 能"瞬间映射任意大文件"、并且"只为真正访问的部分付出代价"的秘密。

｜页缓存：文件在内存里的"分身"

本篇目标：认识 Linux 内核里最重要的缓存——页缓存（page cache）。理解读写文件时数据在哪里停留、脏页是什么、什么时候写回磁盘，并看清 read 与 mmap 在数据通路上的本质区别。

一、为什么需要页缓存

第 2 篇我们知道，读内存比读 SSD 快上千倍，比读机械硬盘快十万倍。同时，程序访问文件有很强的局部性：

  • 刚读过的文件，很可能马上又要读（比如你反复编译同一个项目，头文件被读了无数次）；
  • 读了文件的第 1 页，很可能接着读第 2、3 页。

于是内核做了一件很自然的事：把从磁盘读出来的文件内容留在内存里，下次再有人读，直接从内存拿。

这块用来缓存文件内容的内存，就叫页缓存（page cache）。名字里有"页"，因为它也以页（通常 4KB）为单位管理。

打个比方：图书馆的书都在地下书库（磁盘），取书要等管理员下去找。聪明的图书馆会在阅览室门口设一个"热门书架"（page cache），最近被借过的书先放在这里，下一个人要借直接拿。

二、页缓存长什么样

2.1 以文件为单位组织

页缓存不是一锅大杂烩，而是按文件组织的。内核为每个被打开过的文件维护一个"缓存目录"，记录：

这个文件的第 0 页、第 1 页、第 7 页……分别缓存在哪个物理页上。

 文件 /data/a.txt（12KB = 3 页）的缓存目录
 ┌──────────┬────────────────────┐
 │ 文件页号   │  物理页             │
 ├──────────┼────────────────────┤
 │    0     │  物理页 #1024        │
 │    1     │  （不在缓存中）       │
 │    2     │  物理页 #5577        │
 └──────────┴────────────────────┘

在 Linux 内核里，这个目录叫 address_space（名字有点误导，它其实是"某个文件在内存里的缓存"），每个文件的 inode 都有一个。第 11 篇会再见到它。

2.2 全局唯一

一个文件的某一页，在整个系统里只有一份缓存。无论多少个进程打开了这个文件，无论是用 read 读还是用 mmap 访问，用的都是同一份。这一点对理解 mmap 至关重要。

三、read 的完整过程

现在我们可以把第 1 篇的 read 讲得更精确了。程序调用 read(fd, buf, 4096) 读取文件的第 N 页：

          read(fd, buf, 4096)
                  │
                  ▼
   ┌──────── 查页缓存：第 N 页在吗？ ────────┐
   │ 在（缓存命中）                         │ 不在（缓存未命中）
   │                                       ▼
   │                         分配一个物理页，加入缓存目录
   │                         向磁盘发出读请求（DMA）
   │                         进程睡眠等待……磁盘完成，唤醒
   │                                       │
   ▼                                       ▼
   ┌───────────────────────────────────────────┐
   │   CPU 把页缓存里的数据 **拷贝** 到用户的 buf   │
   └───────────────────────────────────────────┘
                  │
                  ▼
              read 返回

注意两点：

  1. 即使缓存命中，拷贝依然发生：数据要从页缓存（内核地盘）复制到 buf（用户地盘）。
  2. 此刻同一份数据在内存里存了两份：一份在页缓存，一份在你的 buf。

3.1 预读：猜你下一步要读什么

磁盘有个特点：一次读 128KB 和一次读 4KB，耗时差别不大（主要成本在"找到位置"）。所以内核在发现你顺序读文件时，会主动多读一些后面的内容放进页缓存，这叫预读（readahead）。

  • 内核默认的预读窗口通常是 128KB，可以调整（/sys/block/<设备>/queue/read_ahead_kb）；
  • 如果你持续顺序读，预读窗口会逐渐扩大；
  • 如果你跳来跳去地读，内核发现预读没用，会减少或停止预读。

预读机制对 mmap 同样生效，第 10 篇会讲如何用 madvise 调整它。

四、write 的完整过程：脏页

写文件时，内核同样借助页缓存，而且更"偷懒"：

          write(fd, buf, 4096)
                  │
                  ▼
   确保文件第 N 页在页缓存中（必要时先从磁盘读进来）
                  │
                  ▼
   CPU 把 buf 里的数据 **拷贝** 到页缓存
                  │
                  ▼
   把这一页标记为 "脏"（dirty）
                  │
                  ▼
   write 立即返回！ ← 此时数据还没到磁盘

write 返回成功，并不代表数据已经写到磁盘上。 数据只是进了页缓存。这种策略叫写回缓存（write-back cache）。

被修改过、还没写回磁盘的页，叫脏页（dirty page）。干净页（clean page）表示内容和磁盘上一致。

4.1 为什么要这么偷懒？

  • 快：写内存是纳秒级，写磁盘是微秒到毫秒级。让程序等磁盘太浪费了。
  • 合并：如果程序对同一页连续写了 100 次，只需要最后写回磁盘一次。
  • 排序：内核可以把很多脏页攒起来，按磁盘上的位置排好顺序再写，效率更高。

4.2 脏页什么时候写回？

Linux 内核有专门的后台线程负责把脏页写回磁盘，触发时机主要有：

触发条件 相关参数（/proc/sys/vm/） 默认值
脏页存在时间太久 dirty_expire_centisecs 3000（即 30 秒）
后台线程定期醒来检查 dirty_writeback_centisecs 500（即 5 秒）
脏页占可用内存比例过高，后台开始写 dirty_background_ratio 10%
脏页比例太高，写进程被强制等待 dirty_ratio 20%

4.3 断电了怎么办？

既然数据可能在页缓存里停留几十秒，那么断电或系统崩溃时，这些脏页就丢了。

所以，对数据可靠性有要求的程序（数据库、版本控制系统等）在关键时刻会调用：

fsync(fd);       // 把这个文件的脏页（和元数据）全部写到磁盘，等写完才返回
fdatasync(fd);   // 类似，但尽量不写不必要的元数据（比如修改时间），更快

mmap 也有对应的 msync，第 9 篇详讲。

五、为什么 Linux 总是"吃光"内存？

5.1 常见的困惑

很多人第一次在 Linux 上运行 free，会被吓一跳：

free -h

               total        used        free      shared  buff/cache   available
Mem:            15Gi       3.1Gi       420Mi       210Mi        12Gi        12Gi
Swap:          2.0Gi          0B       2.0Gi

"16GB 内存只剩 420MB 空闲了！内存泄漏了吗？"

不是的。看 buff/cache 那一列：12GB 被用来做了缓存，其中绝大部分就是页缓存。

5.2 空闲内存就是浪费的内存

Linux 的哲学是：空着的内存一点用都没有。 既然现在没人要用这些内存，不如拿来缓存文件，说不定下次就能省一次磁盘读取。

而一旦有程序真的需要内存，内核会立刻回收页缓存：

  • 干净的缓存页：内容和磁盘一致，直接丢弃即可，瞬间完成；
  • 脏页：必须先写回磁盘，才能回收。

所以真正应该看的是 available 这一列：它估算了"如果有程序要内存，大约能拿出多少"，包括了可以回收的缓存。上面的例子里，available 有 12GB，系统非常健康。

5.3 回收哪些页？

内核用类似 LRU（最近最少使用） 的策略决定回收谁：最近很久没被访问的页优先被回收。具体做法是维护"活跃"和"不活跃"两个链表，并参考第 3 篇提到的页表访问标志（AF）来判断一个页最近是否被访问过。较新的内核还引入了更精细的多代 LRU（MGLRU）。

六、实验

实验 1：感受缓存的威力

# 生成一个 1GB 的文件
dd if=/dev/urandom of=big.bin bs=1M count=1024

# 清空页缓存（需要 root，生产环境慎用）
sync; echo 3 | sudo tee /proc/sys/vm/drop_caches

# 第一次读：从磁盘读
time cat big.bin > /dev/null

# 第二次读：从页缓存读
time cat big.bin > /dev/null

典型结果：第一次可能要几百毫秒到几秒（取决于磁盘），第二次只要一两百毫秒甚至更短。差距就是磁盘和内存的差距。

实验 2：看缓存涨落

sync; echo 3 | sudo tee /proc/sys/vm/drop_caches
free -m           # 记下 buff/cache
cat big.bin > /dev/null
free -m           # buff/cache 增加了约 1024MB

实验 3：查看某个文件有多少在缓存中

util-linux 自带一个小工具 fincore：

fincore big.bin
#   RES PAGES  SIZE FILE
#    1G 262144   1G big.bin        ← 整个文件都在缓存里

sync; echo 3 | sudo tee /proc/sys/vm/drop_caches
fincore big.bin
#   RES PAGES  SIZE FILE
#    0B     0   1G big.bin        ← 全被清掉了

（有趣的是，fincore 本身就是用 mmap + mincore 系统调用实现的：映射文件，再问内核"这些页哪些在内存里"。）

实验 4：观察脏页

grep -E "Dirty|Writeback" /proc/meminfo
# Dirty:               120 kB
# Writeback:             0 kB

dd if=/dev/zero of=dirty.bin bs=1M count=500     # 写 500MB，立即返回
grep -E "Dirty|Writeback" /proc/meminfo
# Dirty:            512104 kB                     ← 500MB 脏页，还没写到磁盘

sync                                               # 强制写回
grep -E "Dirty|Writeback" /proc/meminfo
# Dirty:               136 kB                     ← 写回完成

你会发现 dd 写 500MB 几乎瞬间完成，而后面的 sync 才是真正在等磁盘。（如果你的系统内存较小，dd 可能在写的过程中就因为 dirty_ratio 被迫等待了。）

七、绕过页缓存：直接 I/O

既然页缓存这么好，有没有人不想要它？

有。一些数据库（比如 MySQL 的 InnoDB、PostgreSQL 的部分配置）会用 O_DIRECT 标志打开文件，绕过页缓存，让数据在磁盘和用户缓冲区之间直接传输。原因是：

  • 数据库自己有一套更懂业务的缓存（buffer pool），内核再缓存一份就是双重缓存，浪费内存；
  • 数据库需要精确控制数据何时写入磁盘、以什么顺序写入。

记住这个思路，第 12 篇讲"为什么有的数据库不用 mmap"时还会遇到。

八、关键领悟：read 与 mmap 的本质区别

现在，所有的拼图都齐了。

8.1 read：从缓存复制一份给你

  ┌────────────── 内核地盘 ──────────────┐     ┌───── 用户地盘 ─────┐
  │                                      │     │                    │
  │   页缓存  [物理页 #1024: 文件第0页]   │ ─── 拷贝 ──▶ buf[4096]    │
  │                                      │     │  （物理页 #3000）   │
  └──────────────────────────────────────┘     └────────────────────┘

  同一份数据，内存里有 2 份

8.2 mmap：直接把缓存页挂进你的页表

  进程的页表                             页缓存
  ┌───────────────────────┐          ┌──────────────────────────┐
  │ 虚拟地址 0xffff12340000 │ ───────▶ │ 物理页 #1024：文件第 0 页   │
  └───────────────────────┘          └──────────────────────────┘

  程序访问 p[0]，MMU 直接翻译到物理页 #1024
  没有拷贝，内存里只有 1 份

这就是 mmap 的核心秘密：

mmap 不是把文件"复制"到你的内存里，而是把页缓存里的那些物理页，直接挂进你的页表。你看到的，就是页缓存本身。

现在可以回答第 1 篇留下的问题了：

问：程序在 EL0，内核的数据在内核地盘里，程序怎么能直接看到？ 答：页缓存页本身只是普通的物理页，所谓"内核地盘"是由页表权限决定的。内核在你的进程页表里添加一条映射，设置为 EL0 可访问，你就能看到它了。安全性没有破坏：内核只会映射你有权限访问的文件，并按你打开文件的方式设置读写权限。

问：mmap 10GB 文件，要先读 10GB 吗？ 答：不用。mmap 只登记"菜单"；你访问哪一页，就在缺页时把哪一页挂上（必要时从磁盘读进页缓存）。

问：我改了 p[i]，文件会变吗？ 答：如果是共享映射，你改的就是页缓存里的那一页，它变成了脏页，之后会被写回磁盘——就像 write 一样，只是省掉了拷贝。如果是私有映射，情况不同，第 7 篇详讲。

8.3 一个推论：一致性是天然的

因为一个文件页在系统里只有一份缓存，所以：

  • 进程 A 用 mmap（共享映射）修改了文件，进程 B 用 read 立刻就能读到新内容；
  • 进程 A 用 write 修改了文件，进程 B 的 mmap 映射里立刻就能看到新内容。

大家看的都是同一个物理页。（O_DIRECT 例外，因为它绕过了页缓存。）

｜mmap 登场：把文件变成一个数组

本篇目标：逐个参数讲清 mmap 和 munmap，写出第一个用 mmap 读文件和改文件的程序，用实验验证"mmap 什么都不读、缺页才读"，并盘点新手最容易踩的坑。

一、一句话定义

mmap 在进程的虚拟地址空间里开辟一段区域，并把这段区域和某个"后台对象"（通常是文件的一部分）关联起来。之后访问这段地址，就等于访问那个对象。

前五篇的知识在这里汇合：

  • "开辟一段区域" = 在进程的"菜单"（VMA）上登记一个新条目（第 3、4 篇）；
  • "关联到文件" = 这段地址发生缺页时，去文件的页缓存里找页（第 4、5 篇）；
  • "访问地址就是访问文件" = 页表直接指向页缓存的物理页，没有拷贝（第 5 篇）。

二、函数原型

#include <sys/mman.h>

void *mmap(void *addr, size_t length, int prot, int flags, int fd, off_t offset);
int   munmap(void *addr, size_t length);

mmap 的意思可以读成一句话：

"请在我的地址空间里，大约在 addr 附近，开一段 length 字节的区域，权限为 prot，映射方式为 flags，内容来自文件 fd 从 offset 开始的部分。"

下面逐个拆解。

2.1 addr：希望放在哪里

  • 绝大多数时候传 NULL，意思是"你（内核）帮我挑个地方"。内核会在 mmap 区域里找一块足够大的空白。
  • 如果传一个具体地址，内核只把它当作建议，可能采纳也可能不采纳。
  • 如果同时在 flags 里加了 MAP_FIXED，内核就必须放在这个地址。危险：如果那里原本已经有映射，会被悄无声息地覆盖。新代码建议用 MAP_FIXED_NOREPLACE（Linux 4.17+），遇到冲突会返回错误而不是覆盖。

2.2 length：映射多长

  • 要映射的字节数，必须大于 0。
  • 内核实际映射的长度会向上取整到页大小的整数倍。映射 100 字节，实际会占用一整页。

2.3 prot：权限（protection）

值 含义
PROT_READ 可读
PROT_WRITE 可写
PROT_EXEC 可执行（可以把这段内存里的内容当代码执行）
PROT_NONE 什么都不能干（访问即段错误），常用于"占位"或"警戒区"

可以用 | 组合，如 PROT_READ | PROT_WRITE。这些权限最终会被翻译成第 3 篇讲的页表项权限位。

2.4 flags：映射方式

flags 中必须且只能选一个下面的基本类型：

值 含义
MAP_SHARED 共享映射：你的修改会写进页缓存，其他映射同一文件的进程能看到，最终会写回文件
MAP_PRIVATE 私有映射：你的修改只有你自己能看到，不会写回文件（写时复制，第 7 篇详讲）

还可以加上各种附加标志，常用的有：

附加标志 含义
MAP_ANONYMOUS 不关联文件，只要一块内存（第 8 篇详讲）
MAP_FIXED / MAP_FIXED_NOREPLACE 必须使用 addr 指定的地址
MAP_POPULATE 映射时就把所有页预先准备好，避免后续缺页
MAP_NORESERVE 不为这段映射预留内存额度（与内存超售有关）
MAP_HUGETLB 使用大页（第 10 篇）
MAP_LOCKED 把页锁在内存里，不被换出

2.5 fd：哪个文件

用 open 打开的文件描述符。匿名映射时传 -1。

重要：mmap 成功之后，可以立即 close(fd)，映射依然有效。因为映射本身持有了对文件的引用，文件不会因为 fd 关闭而"消失"。

2.6 offset：从文件的哪里开始

从文件第 offset 个字节开始映射。它必须是页大小的整数倍，否则 mmap 直接失败，errno 为 EINVAL。

再次提醒：ARM64 Linux 的页大小可能是 4KB、16KB 或 64KB，永远用 sysconf(_SC_PAGESIZE) 获取页大小，不要写死 4096。一份在 4KB 系统上运行良好的代码，拿到 64KB 页的服务器上就可能因为 offset 不对齐而失败。

2.7 返回值

  • 成功：返回映射区域的起始地址（一个指针，通常是页对齐的）。
  • 失败：返回 MAP_FAILED（它的值是 (void *)-1），并设置 errno。

新手头号错误：用 NULL 判断 mmap 是否失败。mmap 失败不返回 NULL，必须和 MAP_FAILED 比较：

char *p = mmap(...);
if (p == MAP_FAILED) {     // ✅ 正确
    perror("mmap");
}
if (p == NULL) { ... }     // ❌ 错误：失败时 p 是 (void*)-1，不是 NULL

2.8 munmap：解除映射

munmap(addr, length);

把这段地址从"菜单"上删掉，清理对应的页表项（并作废 TLB）。之后再访问这段地址就是段错误。

  • 不调用 munmap，进程退出时内核也会自动清理所有映射；
  • 但对于长期运行的程序，用完不 munmap 就是地址空间泄漏；
  • munmap 不保证把修改写到磁盘上（第 9 篇详讲），它只是解除映射。修改过的页仍然留在页缓存里，稍后照常写回。

三、第一个程序：用 mmap 读文件

我们写一个程序，统计文件的字节数、行数，并打印第一行。

// mmap_count.c —— 用 mmap 统计文件行数
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/mman.h>
#include <sys/stat.h>

int main(int argc, char *argv[]) {
    if (argc != 2) {
        fprintf(stderr, "用法: %s 文件名\n", argv[0]);
        return 1;
    }

    // 1. 打开文件
    int fd = open(argv[1], O_RDONLY);
    if (fd < 0) { perror("open"); return 1; }

    // 2. 获取文件大小
    struct stat st;
    if (fstat(fd, &st) < 0) { perror("fstat"); return 1; }
    size_t size = st.st_size;
    if (size == 0) {                     // 空文件不能映射（length 必须 > 0）
        printf("空文件\n");
        close(fd);
        return 0;
    }

    // 3. 映射整个文件：只读、私有
    const char *p = mmap(NULL, size, PROT_READ, MAP_PRIVATE, fd, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }

    // 4. 映射建立后，fd 就可以关掉了
    close(fd);

    // 5. 像访问数组一样访问文件！
    size_t lines = 0;
    for (size_t i = 0; i < size; i++) {
        if (p[i] == '\n')
            lines++;
    }

    printf("文件大小: %zu 字节\n", size);
    printf("行数:     %zu\n", lines);

    // 打印第一行
    printf("第一行:   ");
    for (size_t i = 0; i < size && p[i] != '\n'; i++)
        putchar(p[i]);
    putchar('\n');

    // 6. 解除映射
    munmap((void *)p, size);
    return 0;
}

gcc -O2 mmap_count.c -o mmap_count
./mmap_count /etc/passwd
# 文件大小: 1876 字节
# 行数:     35
# 第一行:   root:x:0:0:root:/root:/bin/bash

看看第 5 步的循环：p[i] == '\n'。整个程序里没有一次 read 调用，文件就像一个普通的 char 数组。

3.1 与 read 版本对比

// read 版本的核心循环
char buf[65536];
ssize_t n;
while ((n = read(fd, buf, sizeof buf)) > 0) {
    for (ssize_t i = 0; i < n; i++)
        if (buf[i] == '\n') lines++;
}
对比项 read 版本 mmap 版本
需要自己管理缓冲区 是 否
数据拷贝 每次 read 拷贝一次 无
系统调用次数 文件大小 ÷ 缓冲区大小 mmap + munmap 各一次（但有缺页）
随机访问第 N 个字节 需要 lseek + read 直接 p[N]
处理跨缓冲区的数据（如一行被切成两半） 麻烦 不存在这个问题

最后一项其实是 mmap 在编程上最大的便利之一：解析文件格式时，数据结构可能横跨任意位置，read 版本需要处理"读了一半"的情况，mmap 版本则完全不用操心。

四、第二个程序：用 mmap 修改文件

把文件中所有小写字母改成大写，直接在原文件上修改：

// mmap_upper.c —— 用 mmap 把文件内容改成大写
#include <stdio.h>
#include <ctype.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/mman.h>
#include <sys/stat.h>

int main(int argc, char *argv[]) {
    if (argc != 2) {
        fprintf(stderr, "用法: %s 文件名\n", argv[0]);
        return 1;
    }

    // 要修改文件，必须以读写方式打开
    int fd = open(argv[1], O_RDWR);
    if (fd < 0) { perror("open"); return 1; }

    struct stat st;
    if (fstat(fd, &st) < 0) { perror("fstat"); return 1; }
    if (st.st_size == 0) { close(fd); return 0; }

    // 可读可写 + 共享映射：修改会进入页缓存，最终写回文件
    char *p = mmap(NULL, st.st_size, PROT_READ | PROT_WRITE,
                   MAP_SHARED, fd, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }
    close(fd);

    for (off_t i = 0; i < st.st_size; i++)
        p[i] = toupper((unsigned char)p[i]);   // 直接赋值就是在改文件

    munmap(p, st.st_size);
    return 0;
}

gcc mmap_upper.c -o mmap_upper
echo "hello, mmap world" > test.txt
./mmap_upper test.txt
cat test.txt
# HELLO, MMAP WORLD

关键的三个组合：

  1. open(..., O_RDWR)：文件必须以读写方式打开；
  2. PROT_READ | PROT_WRITE：映射区域可写；
  3. MAP_SHARED：修改要写回文件。

如果把 MAP_SHARED 换成 MAP_PRIVATE，程序照样能运行，p 里的内容也确实变成了大写，但 cat test.txt 会发现文件没变。原因留到下一篇讲。

注意：mmap 不能改变文件的大小。你只能在已有的范围内修改。想往文件末尾追加内容，需要先用 ftruncate 把文件变大，再映射（第 9 篇）。

五、mmap 背后发生了什么：一条时间线

我们把前几篇的知识串起来，看看 mmap_count 运行时，内核到底做了什么。

时刻 ①  mmap(NULL, size, PROT_READ, MAP_PRIVATE, fd, 0)
        内核：
        - 在 mmap 区域找一段足够大的空白虚拟地址
        - 在"菜单"上登记一个新条目（VMA）：
            "0xffff9a000000 起的 size 字节 → 文件 X 的 0 字节起，只读，私有"
        - 不读文件！不分配物理页！不填页表！
        - 返回 0xffff9a000000

时刻 ②  close(fd)
        菜单条目自己持有文件引用，映射不受影响

时刻 ③  第一次执行 p[0]
        MMU：页表项无效 → 缺页异常
        内核：
        - 查菜单：属于刚才那个映射，对应文件第 0 页
        - 查文件 X 的页缓存：第 0 页在吗？
            · 不在 → 分配物理页，从磁盘读（大缺页），顺便预读后面的若干页
            · 在   → 小缺页
        - 把这个页缓存页（以及附近已在缓存中的一些页）填入页表，标记只读
        - 重新执行 p[0]，成功

时刻 ④  p[1] ... p[4095]
        同一页，TLB 命中，和访问普通数组一样快

时刻 ⑤  p[4096]
        如果时刻③已经顺便映射了这一页，就直接命中；否则再来一次缺页

时刻 ⑥  munmap
        删除菜单条目，清除页表项，作废 TLB
        页缓存里的页仍然留着（其他人可能还要用）

5.1 "顺便映射附近的页"：fault-around

时刻③提到，缺页时内核会"顺便"把附近已经在页缓存里的页一起填入页表。这个机制叫 fault-around，默认一次最多处理 64KB（即 16 个 4KB 页），由调试文件系统里的参数 /sys/kernel/debug/fault_around_bytes 控制。它只对读操作引起的文件映射缺页生效，并且只"顺便"映射那些已经在页缓存里的页，不会为此额外读磁盘。

它的意义在于：顺序访问一个已缓存的文件时，不必每 4KB 就缺页一次，而是每 64KB 缺页一次，开销降到约 1/16。

实验：数一数缺页次数

在 mmap_count.c 的 munmap 前加上几行：

getrusage(RUSAGE_SELF, &ru);

你可能会观察到：

  • 100MB = 25600 个 4KB 页，但小缺页数远小于 25600（热缓存时约为 1600 左右再加上程序启动的开销），这就是 fault-around 的效果：25600 ÷ 16 = 1600；
  • 冷缓存时会出现一些大缺页，同时预读让后续的很多访问变成了小缺页。

（具体数字取决于内核版本、页大小、是否启用了大页，看量级即可。）

六、映射超出文件末尾会怎样？

这是一个容易让人困惑的地方。假设文件大小是 5000 字节，页大小 4096。

文件内容:  |<-------- 5000 字节 -------->|
页划分:    |<---- 第0页 4096 ---->|<---- 第1页 4096 ---->|<---- 第2页 ---->
                                  4096    5000          8192             12288

情况一：映射 5000 字节

char *p = mmap(NULL, 5000, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);

内核实际映射 2 页（8192 字节）。

  • p[0] ~ p[4999]：文件内容，正常读写；
  • p[5000] ~ p[8191]：可以访问，读出来是 0。写进去不会报错，但这些写入不会进入文件（文件大小还是 5000）。

情况二：映射 12288 字节（比文件大得多）

char *p = mmap(NULL, 12288, PROT_READ, MAP_SHARED, fd, 0);   // mmap 本身会成功！
  • p[0] ~ p[8191]：同上；
  • p[8192] 及以后：这一页完全在文件末尾之外，访问它会收到 SIGBUS 信号（总线错误），程序默认会崩溃。
Bus error (core dumped)

规律：文件末尾所在的那一页可以安全访问（多出的部分是 0）；完全超出文件末尾的页，访问即 SIGBUS。

SIGBUS 和 SIGSEGV 的区别：

  • SIGSEGV：这个地址根本不在"菜单"上；
  • SIGBUS：这个地址在菜单上，但背后的文件没有对应的数据，内核无法兑现。

第 9 篇还会看到 SIGBUS 的另一种常见成因：映射之后文件被别人截短了。

｜共享还是私有：MAP_SHARED、MAP_PRIVATE 与写时复制

本篇目标：彻底搞懂 MAP_SHARED 和 MAP_PRIVATE 的区别；理解操作系统中最巧妙的技巧之一——写时复制（Copy-on-Write，COW）；并用它解释为什么 fork 一个占用 10GB 内存的进程只需要几毫秒。

一、原件与复印件

想象办公室里有一份共享的合同原件，放在公共文件柜里（页缓存）。

共享方式（MAP_SHARED）：你直接在原件上修改。其他同事打开文件柜，看到的就是你改过的版本；到了晚上，行政人员会把原件归档（写回磁盘）。

私有方式（MAP_PRIVATE）：你也可以直接翻阅原件，但是一旦你想在某一页上涂改，行政人员会先把那一页复印一份交给你，你在复印件上随便画。原件不变，同事看不到你的涂改，晚上归档时也不会归档你的复印件。

这就是两种映射的全部区别。下面看它在内核里是怎么实现的。

二、MAP_SHARED：直接改原件

 进程 A 的页表                   页缓存                      进程 B 的页表
 ┌──────────────┐          ┌──────────────────┐          ┌──────────────┐
 │ 0xffffa000.. │ ───────▶ │ 物理页 #1024      │ ◀─────── │ 0xffff7000.. │
 │  (可读写)     │          │ 文件第 0 页        │          │  (可读写)     │
 └──────────────┘          └──────────────────┘          └──────────────┘
                                    │
                                    │ 脏页，稍后写回
                                    ▼
                               磁盘上的文件
  • 两个进程以 MAP_SHARED 映射同一个文件，它们的页表指向同一个物理页；
  • A 写入的数据，B 立刻就能读到（同一块物理内存，不需要任何"同步"）；
  • 用 read 读这个文件的进程也能读到（同一个页缓存页）；
  • 修改让页变脏，稍后由内核写回磁盘。

三、MAP_PRIVATE：写时才复印

3.1 读的时候和共享映射一样

MAP_PRIVATE 映射建立后，第一次读某一页时，内核做的事情和共享映射几乎一样：把页缓存里的那个物理页挂进页表。区别只有一个：

内核故意把页表项设为只读，哪怕你在 mmap 时要求了 PROT_WRITE。

 进程 A 的页表                         页缓存
 ┌──────────────────────┐         ┌──────────────────┐
 │ 0xffffa000..          │ ──────▶ │ 物理页 #1024      │
 │ 菜单上：可读写、私有     │         │ 文件第 0 页        │
 │ 页表项：**只读**         │         └──────────────────┘
 └──────────────────────┘

3.2 写的时候：触发复制

当进程第一次写这一页时：

 ① 进程执行写指令
 ② MMU 发现页表项只读 → 权限缺页异常（第 4 篇"情况四"）
 ③ 内核查菜单：这段区域"可写 + 私有"
    → 判断：这不是错误，而是写时复制的时机
 ④ 分配一个新的物理页 #3000
 ⑤ 把 #1024 的 4KB 内容完整复制到 #3000
 ⑥ 修改页表项：指向 #3000，并设为**可写**
 ⑦ 返回，重新执行写指令，这次写进了 #3000

 进程 A 的页表                         页缓存
 ┌──────────────────────┐         ┌──────────────────┐
 │ 0xffffa000..          │    ╳    │ 物理页 #1024      │ ← 原件，未被修改
 │ 页表项：可写            │         └──────────────────┘
 └──────────┬───────────┘
            │                     ┌──────────────────┐
            └───────────────────▶ │ 物理页 #3000      │ ← A 的私有复印件
                                  │ （已被 A 修改）     │
                                  └──────────────────┘

此后：

  • 进程 A 对这一页的所有读写都发生在 #3000 上，不再缺页；

  • 3000 不再属于任何文件，它变成了一个"匿名页"（第 8 篇）。内存紧张时，它不能被简单丢弃（磁盘上没有它的副本），只能换出到交换区（swap）；

  • 页缓存里的 #1024 原封不动，文件不会被修改。

3.3 为什么是"按页"复制？

COW 的粒度是一页。一个 1GB 的私有映射，如果你只改了其中 3 个字节，而这 3 个字节分布在 3 个不同的页上，那么只会复制 3 页（12KB），其他页仍然和页缓存共享。

这就是"写时复制"的精髓：能共享就共享，非复制不可时才复制，而且只复制被改的那一页。

四、实验一：共享与私有的直观对比

// share_vs_private.c
// 用法: ./a.out shared   或   ./a.out private
#include <stdio.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/mman.h>
#include <sys/wait.h>

int main(int argc, char *argv[]) {
    int shared = (argc > 1 && strcmp(argv[1], "shared") == 0);

    // 准备一个文件
    int fd = open("demo.txt", O_RDWR | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) { perror("open"); return 1; }
    write(fd, "original content\n", 17);

    char *p = mmap(NULL, 17, PROT_READ | PROT_WRITE,
                   shared ? MAP_SHARED : MAP_PRIVATE, fd, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }
    close(fd);

    pid_t pid = fork();            // 子进程继承这个映射
    if (pid == 0) {
        memcpy(p, "CHILD WROTE THIS", 16);
        printf("[子进程] 我看到: %.16s\n", p);
        return 0;
    }

    waitpid(pid, NULL, 0);         // 等子进程写完
    printf("[父进程] 我看到: %.16s\n", p);
    munmap(p, 17);
    return 0;
}

# [父进程] 我看到: CHILD WROTE THIS      ← 父进程看到了子进程的修改
cat demo.txt
# CHILD WROTE THIS                       ← 文件也被修改了

cat demo.txt

fork 之后，父子进程共享同一个映射：

  • MAP_SHARED 时，大家指向同一个页缓存页，子进程的修改就是对文件的修改；
  • MAP_PRIVATE 时，子进程写的时候触发 COW，修改只落在它自己的复印件上。

五、实验二：私有映射的一个"反直觉"细节

问题：MAP_PRIVATE 映射之后，别人通过 write 修改了文件，我能看到吗？

直觉可能是"私有映射是我自己的快照，看不到"。但答案是：取决于你有没有写过那一页。

  • 你没写过的页：页表仍然指向页缓存的原件，别人改了原件，你立刻能看到；
  • 你写过的页：已经换成了你的私有复印件，别人怎么改原件都与你无关。
// private_view.c —— 观察私有映射何时"脱离"文件
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/mman.h>

int main(void) {
    long page = sysconf(_SC_PAGESIZE);

    // 准备一个 2 页大的文件，全是 'a'
    int fd = open("view.bin", O_RDWR | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) { perror("open"); return 1; }
    for (long i = 0; i < 2 * page; i++) write(fd, "a", 1);

    char *p = mmap(NULL, 2 * page, PROT_READ | PROT_WRITE, MAP_PRIVATE, fd, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }

    printf("初始:              第0页=%c 第1页=%c\n", p[0], p[page]);

    p[0] = 'M';                         // 我写第 0 页 → 触发 COW
    printf("我写第0页后:        第0页=%c 第1页=%c\n", p[0], p[page]);

    pwrite(fd, "X", 1, 0);              // 别人（这里用 pwrite 模拟）改文件第 0 页
    pwrite(fd, "X", 1, page);           // 也改文件第 1 页
    printf("文件被别人改了之后:  第0页=%c 第1页=%c\n", p[0], p[page]);

    munmap(p, 2 * page);
    close(fd);
    return 0;
}

初始:              第0页=a 第1页=a
我写第0页后:        第0页=M 第1页=a
文件被别人改了之后:  第0页=M 第1页=X   ← 第1页没写过，看到了别人的修改

POSIX 标准没有规定这种情况下的行为，这是 Linux 的实际表现。所以：

MAP_PRIVATE 不是"快照"。它只保证"你的修改不影响别人"，不保证"别人的修改不影响你"。如果需要一个不受外界影响的稳定副本，要么确保文件不会被修改，要么自己完整拷贝一份。

六、COW 的最大用户：fork

6.1 fork 是什么

fork() 是 Unix 创建新进程的方式：它把当前进程完整复制一份，产生一个子进程。子进程拥有和父进程一模一样的内存内容。

Shell 里每执行一条命令，都会先 fork 自己，然后在子进程里 exec 那条命令。服务器程序也常用 fork 创建工作进程。Redis 做持久化快照时也会 fork。

6.2 傻瓜式实现会怎样

如果 fork 真的把父进程的所有内存逐字节复制一份：

  • 一个占用 10GB 内存的进程，fork 要复制 10GB，耗时数秒；
  • 内存立刻翻倍；
  • 而大多数情况下，子进程马上就会调用 exec 去运行另一个程序，刚复制的 10GB 立刻作废。

这太浪费了。

6.3 用 COW 实现 fork

Linux 的 fork 实际上这样做：

  1. 复制"菜单"和页表，而不是复制数据页本身；
  2. 把父子双方页表中所有可写的私有页都改为只读；
  3. 让每个物理页的"引用计数"加 1，表示现在有两个进程在用它。
 fork 之后：

 父进程页表                  物理内存                  子进程页表
 ┌──────────┐            ┌────────────┐            ┌──────────┐
 │ 页表项 只读 │ ─────────▶ │ 物理页 #500 │ ◀───────── │ 页表项 只读 │
 └──────────┘            │ 引用计数 = 2 │            └──────────┘
                         └────────────┘

之后，无论父进程还是子进程写某一页，都会触发 COW：复制这一页，写的那一方拿到复印件。另一方如果后来也去写，发现引用计数已经变回 1，就不用再复制，直接把页表项改回可写即可。

所以 fork 的成本主要是复制页表，与内存大小成正比但远小于复制数据本身（4KB 数据只对应 8 字节页表项），对于 10GB 内存的进程通常在几毫秒到几十毫秒之间。

6.4 实验三：fork 的速度与 COW 的代价

// fork_cow.c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>
#include <unistd.h>
#include <sys/resource.h>
#include <sys/wait.h>

static double now_ms(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec * 1e3 + ts.tv_nsec / 1e6;
}

int main(void) {
    size_t size = 2UL << 30;                       // 2GB
    long page = sysconf(_SC_PAGESIZE);
    char *mem = malloc(size);
    if (!mem) { perror("malloc"); return 1; }
    memset(mem, 1, size);                          // 先把 2GB 全部写一遍，确保真的占用内存

    double t0 = now_ms();
    pid_t pid = fork();
    if (pid == 0) {
        double t1 = now_ms();
        printf("[子] fork 耗时约 %.2f ms\n", t1 - t0);

        struct rusage ru;
        getrusage(RUSAGE_SELF, &ru);
        long before = ru.ru_minflt;

        for (size_t i = 0; i < size; i += page)    // 子进程把每一页都写一遍
            mem[i] = 2;

        getrusage(RUSAGE_SELF, &ru);
        printf("[子] 写遍 2GB 耗时 %.2f ms，触发缺页 %ld 次（每次都是一次 COW 复制）\n",
               now_ms() - t1, ru.ru_minflt - before);
        _exit(0);
    }
    waitpid(pid, NULL, 0);
    printf("[父] mem[0] 仍然是 %d\n", mem[0]);
    free(mem);
    return 0;
}

典型结果（具体数值因机器而异）：

[子] fork 耗时约 15.30 ms
[子] 写遍 2GB 耗时 820.45 ms，触发缺页 524288 次（每次都是一次 COW 复制）
[父] mem[0] 仍然是 1
  • fork 2GB 进程只用了十几毫秒；
  • 子进程写遍所有页时，才真正付出复制的代价：52 万次缺页、每次复制 4KB；
  • 父进程的数据完全不受影响。

如果系统启用了透明大页，memset 后的内存可能是 2MB 大页，缺页次数会少很多。

6.5 COW 的副作用

  • 写放大：只改 1 个字节，也要复制整整 4KB（大页下可能是 2MB）。
  • 内存突增：Redis 在 fork 后做持久化，如果此时有大量写请求，父进程会疯狂触发 COW，内存占用可能接近翻倍。这是 Redis 运维中的经典问题。
  • 延迟抖动：每次 COW 缺页都要分配内存、复制数据。

七、权限组合：什么能映射，什么不能

mmap 的权限受到文件打开方式的约束。内核的原则是：不能通过 mmap 获得比打开文件时更大的权限。

文件打开方式 映射方式 PROT_READ PROT_READ \| PROT_WRITE
O_RDONLY MAP_PRIVATE ✅ ✅（写的是私有复印件，不影响文件）
O_RDONLY MAP_SHARED ✅ ❌ EACCES（你没有写文件的权限）
O_RDWR MAP_PRIVATE ✅ ✅
O_RDWR MAP_SHARED ✅ ✅（修改写回文件）
O_WRONLY 任意 ❌ EACCES ❌ EACCES（映射至少需要可读）

注意第一行：只读打开的文件，可以私有地可写映射。这非常合理：你修改的只是自己的复印件，文件本身毫发无损。动态链接器加载共享库时就是这么做的（第 12 篇）。

另一个限制：如果文件所在的文件系统以只读方式挂载，MAP_SHARED + PROT_WRITE 同样会失败。

7.1 映射后修改权限：mprotect

int mprotect(void *addr, size_t len, int prot);

可以在映射之后修改某段区域的权限（同样以页为单位）。比如：

  • 把一段内存设为 PROT_NONE，做成"警戒区"，一旦越界访问就立刻段错误。线程栈底部的保护页就是这么实现的；
  • JIT 编译器（比如 JavaScript 引擎）先以可写方式生成机器码，再改为只读可执行；
  • 共享库加载后，把重定位完成的区域改为只读，防止被篡改（RELRO 技术）。

mprotect 同样不能突破文件打开方式的限制：对 O_RDONLY 打开的文件做的 MAP_SHARED 映射，无法通过 mprotect 改为可写。

八、如何选择

场景 选择 原因
修改文件并保存 MAP_SHARED 修改需要写回文件
多个进程通过文件共享数据 MAP_SHARED 大家看同一份物理页
只读访问文件 两者皆可，常用 MAP_PRIVATE 不写就不会复制，性能相同；私有映射更不容易误改文件
加载程序和库 MAP_PRIVATE 需要在内存中做少量修改（重定位），但不能改动磁盘上的文件
以文件为"模板"，各自修改 MAP_PRIVATE 例如从快照文件恢复虚拟机内存，见第 12 篇

本篇小结

概念 一句话解释
MAP_SHARED 页表直接指向页缓存，修改所有人可见并写回文件
MAP_PRIVATE 读时共享页缓存，写时复制一份私有页，修改不影响文件
写时复制（COW） 页表项故意设为只读，写时触发缺页，内核复制该页后再放行
COW 粒度 以页为单位，只复制被写的页

｜匿名映射：没有文件的 mmap

本篇目标：理解不关联任何文件的匿名映射；揭开 malloc 背后的 brk 与 mmap；学会用 mmap 在进程之间共享内存（父子进程、无关进程）；认识 /dev/shm、tmpfs 和 memfd_create。最后提醒一个 ARM64 上特别要注意的问题：共享内存的内存顺序。

一、只要内存，不要文件

到目前为止，mmap 都是"把文件映射进来"。但很多时候，程序只是想要一块内存，和任何文件都没关系。

mmap 也能做到，只要加上 MAP_ANONYMOUS 标志：

char *p = mmap(NULL, 1 << 20,                 // 1MB
               PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS,
               -1, 0);                        // 没有文件：fd 传 -1，offset 传 0

这叫匿名映射（anonymous mapping），"匿名"指的是它背后没有名字（没有文件）。

在第 3 篇的 /proc/self/maps 里，那些没有路径、inode 为 0 的 rw-p 行，就是匿名映射。[heap] 和 [stack] 本质上也是匿名内存。

1.1 匿名页从哪里来

对匿名映射来说，缺页时没有文件可读。内核的处理很简单：

  • 第一次写：分配一个新物理页，全部清零，挂进页表；
  • 第一次读（还没写过）：内核甚至不分配新页，而是把一个全系统共享的、内容全是 0 的特殊物理页——零页（zero page）——以只读方式挂上去。之后如果写，再触发 COW，换成真正的新页。

这意味着：申请一大块内存、只读不写，几乎不消耗物理内存。

为什么一定要清零？第 4 篇讲过：物理页可能刚被别的进程用过，不清零就会泄露数据。这也带来了一个保证：匿名映射的内存初始内容一定是 0。

1.2 匿名页的去处

匿名页没有"磁盘上的原件"，所以内存紧张时不能像干净的页缓存页那样直接丢弃。内核只能把它写到交换区（swap），等再访问时通过缺页读回来。没有配置 swap 的系统，匿名页就只能一直留在内存里，直到进程释放或被 OOM Killer 杀掉。

二、malloc 的秘密：brk 与 mmap

你每天都在用 malloc，它的内存从哪里来？

malloc 是 C 库（glibc）实现的函数，不是系统调用。glibc 向内核要内存有两条途径。

2.1 途径一：brk 扩展堆

进程的地址空间里有一块叫"堆"（heap）的区域，紧接在程序数据段之后。堆的末尾有一个边界，叫 program break。

 ┌──────────┬──────────────────────┬─ ─ ─ ─ ─ ─ ─ ─ ─ ─
 │ 程序数据段 │      堆（已分配）       │   （未分配的空地）
 └──────────┴──────────────────────┴─ ─ ─ ─ ─ ─ ─ ─ ─ ─
                                   ▲
                             program break
                       brk() 把它往右推，堆就变大

系统调用 brk / sbrk 可以移动这个边界。glibc 一次多要一些（比如 132KB），然后自己把这片区域切成小块分给多次 malloc。

缺点：堆是连续的，只能从末尾收缩。如果堆顶的一小块还在使用，下面释放了的大片内存也无法还给系统。

2.2 途径二：直接 mmap

对于大块内存，glibc 直接调用 mmap(MAP_PRIVATE | MAP_ANONYMOUS) 单独映射一块。free 时直接 munmap，立刻还给系统，没有碎片问题。

分界线叫 M_MMAP_THRESHOLD，默认是 128KB。glibc 还会动态调整这个阈值（最高到 32MB，64 位系统上），以减少反复映射/解除映射的开销。

此外，多线程程序中，glibc 会为不同线程创建多个"分配区"（arena），这些分配区的内存也是用 mmap 申请的。

2.3 实验：用 strace 观察

// malloc_demo.c
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    printf("--- 小块 ---\n");
    fflush(stdout);
    char *a = malloc(100);

    printf("--- 大块 ---\n");
    fflush(stdout);
    char *b = malloc(1 << 20);      // 1MB

    printf("--- 释放大块 ---\n");
    fflush(stdout);
    free(b);

    free(a);
    return 0;
}

gcc malloc_demo.c -o malloc_demo
strace -e trace=brk,mmap,munmap,write ./malloc_demo 2>&1 | tail -12

输出类似（省略了程序启动阶段的部分）：

write(1, "--- 小块 ---\n", 16)
brk(NULL)                               = 0xaaaae1d6e000
brk(0xaaaae1d8f000)                     = 0xaaaae1d8f000        ← 小块：推进 program break
write(1, "--- 大块 ---\n", 16)
mmap(NULL, 1052672, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) = 0xffff9c6ff000
                                                                ← 大块：直接匿名 mmap
write(1, "--- 释放大块 ---\n", 22)
munmap(0xffff9c6ff000, 1052672)         = 0                     ← free 大块：直接 munmap

几点观察：

  • malloc(100) 触发了 brk，推进了 132KB（0x21000 字节），后续小块分配直接从这里切，不再调用系统调用；
  • malloc(1MB) 直接 mmap 了 1052672 字节（1MB 加上一页，用于存放 glibc 的管理信息）；
  • free 大块时立刻 munmap。

2.4 线程栈

每创建一个线程，pthread_create 都会用匿名 mmap 为它分配一块栈（默认 8MB），并在栈的末端用 mprotect 设置一个 PROT_NONE 的保护页。线程栈溢出时撞到保护页，立刻段错误，而不是悄悄踩坏相邻的内存。

8MB 的线程栈并不会真的占用 8MB 物理内存，按需分页让它只占实际用到的那部分。

三、父子进程共享内存：MAP_SHARED | MAP_ANONYMOUS

匿名映射也可以是共享的。MAP_SHARED | MAP_ANONYMOUS 创建的内存，在 fork 之后父子进程看到的是同一块物理内存（不走 COW）。这是父子进程间通信最简单的方式。

// shared_counter.c —— 4 个子进程共同累加一个计数器
#include <stdio.h>
#include <stdatomic.h>
#include <unistd.h>
#include <sys/mman.h>
#include <sys/wait.h>

struct shared {
    long        plain;     // 普通变量
    atomic_long atomic;    // 原子变量
};

int main(void) {
    struct shared *s = mmap(NULL, sizeof *s, PROT_READ | PROT_WRITE,
                            MAP_SHARED | MAP_ANONYMOUS, -1, 0);
    if (s == MAP_FAILED) { perror("mmap"); return 1; }
    // 匿名映射的内容一定是 0，不用手动初始化

    const int N = 4, LOOPS = 1000000;
    for (int i = 0; i < N; i++) {
        if (fork() == 0) {
            for (int j = 0; j < LOOPS; j++) {
                s->plain++;                         // 非原子：读-改-写，会互相覆盖
                atomic_fetch_add(&s->atomic, 1);    // 原子：保证不丢失
            }
            _exit(0);
        }
    }
    for (int i = 0; i < N; i++) wait(NULL);

    printf("期望值:     %d\n", N * LOOPS);
    printf("普通变量:   %ld\n", s->plain);
    printf("原子变量:   %ld\n", atomic_load(&s->atomic));
    munmap(s, sizeof *s);
    return 0;
}

gcc -O1 shared_counter.c -o shared_counter && ./shared_counter
# 期望值:     4000000
# 普通变量:   1328547        ← 丢失了大量更新
# 原子变量:   4000000        ← 正确

这个实验同时说明了两件事：

  1. 四个进程确实在操作同一块内存（否则每个进程的修改父进程都看不到，结果会是 0）；
  2. 共享内存本身不提供任何同步。s->plain++ 实际上是"读出来、加一、写回去"三步，多个进程同时做就会互相覆盖。必须使用原子操作或锁。

如果把 MAP_SHARED 改成 MAP_PRIVATE，两个计数器都会是 0：每个子进程的修改都落在 COW 产生的私有复印件上，父进程看不到。

四、无关进程之间共享内存

父子进程可以通过继承共享映射。但如果是两个毫不相关的程序（比如一个生产者、一个消费者），它们怎么找到同一块内存呢？

答案是：给内存起个名字，让它看起来像一个文件，两边都去映射这个"文件"。

4.1 tmpfs：活在内存里的文件系统

Linux 有一种特殊的文件系统叫 tmpfs。它的文件完全存在于内存（页缓存）中，不对应任何磁盘。内存紧张时，它的页可以被换出到 swap。

系统通常在 /dev/shm 挂载了一个 tmpfs：

df -h /dev/shm
# Filesystem      Size  Used Avail Use% Mounted on
# tmpfs           7.8G     0  7.8G   0% /dev/shm

往 /dev/shm 里写文件，就是往内存里写数据，速度极快，但重启就没了。

内核内部，MAP_SHARED | MAP_ANONYMOUS 的共享匿名内存，其实也是借助同一套机制（shmem）实现的，只不过那个"文件"没有名字。

4.2 POSIX 共享内存：shm_open

shm_open 是一个标准接口，在 Linux 上它其实就是在 /dev/shm 里打开一个文件：

// shm_writer.c —— 生产者：创建共享内存并写入消息
#include <stdio.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/mman.h>

#define NAME "/demo_shm"
#define SIZE 4096

int main(void) {
    int fd = shm_open(NAME, O_CREAT | O_RDWR, 0600);   // 实际创建 /dev/shm/demo_shm
    if (fd < 0) { perror("shm_open"); return 1; }
    if (ftruncate(fd, SIZE) < 0) { perror("ftruncate"); return 1; }  // 设置大小

    char *p = mmap(NULL, SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }
    close(fd);

    snprintf(p, SIZE, "你好，我是进程 %d 写的消息", getpid());
    printf("已写入，按回车退出并删除共享内存\n");
    getchar();

    munmap(p, SIZE);
    shm_unlink(NAME);          // 删除名字（所有人解除映射后内存才真正释放）
    return 0;
}

// shm_reader.c —— 消费者：打开同名共享内存并读取
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/mman.h>

#define NAME "/demo_shm"
#define SIZE 4096

int main(void) {
    int fd = shm_open(NAME, O_RDONLY, 0);
    if (fd < 0) { perror("shm_open"); return 1; }

    char *p = mmap(NULL, SIZE, PROT_READ, MAP_SHARED, fd, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }
    close(fd);

    printf("读到: %s\n", p);
    munmap(p, SIZE);
    return 0;
}

gcc shm_writer.c -o shm_writer      # 老版本 glibc 需要加 -lrt
gcc shm_reader.c -o shm_reader

# 终端 1
./shm_writer
# 已写入，按回车退出并删除共享内存

# 终端 2
./shm_reader
# 读到: 你好，我是进程 7001 写的消息
ls -l /dev/shm/demo_shm
# -rw------- 1 you you 4096 Nov  2 10:00 /dev/shm/demo_shm

整个流程完全就是第 6 篇的"文件映射"：打开文件、设置大小、MAP_SHARED 映射。唯一的区别是这个文件住在内存里。两个进程的页表指向 tmpfs 里同一批物理页，读写都没有任何拷贝。

4.3 memfd_create：没有路径的内存文件

shm_open 需要一个全局可见的名字，可能和别人冲突，用完还得记得删除。Linux 3.17 引入了 memfd_create：

#define _GNU_SOURCE
#include <sys/mman.h>

int fd = memfd_create("my_buffer", MFD_CLOEXEC);   // 名字只用于调试显示
ftruncate(fd, size);
void *p = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);

它创建一个只能通过 fd 访问的内存文件，不在任何目录里出现。要和别的进程共享，可以：

  • 通过 fork 继承 fd；
  • 通过 Unix 域套接字把 fd "发送"给另一个进程（SCM_RIGHTS）。

memfd_create 还支持"封印"（sealing）：创建者可以宣布"这个文件从此不能再变大、不能再变小、不能再被写"，接收方就可以放心地映射，不必担心对方偷偷截断文件导致自己 SIGBUS（第 9 篇）。

它在虚拟化和图形系统中用得很多：例如虚拟机监控程序可以用 memfd 作为客户机内存，再把 fd 交给另一个进程（如 vhost-user 后端），让对方直接映射同一块客户机内存。

4.4 其他共享内存方式

还有一套更古老的 System V 共享内存（shmget / shmat），接口风格不同，但底层同样基于 shmem。新代码一般推荐 shm_open 或 memfd_create。

五、ARM64 特别提醒：共享内存与内存顺序

在 ARM64 上使用共享内存时，有一个比 x86 更容易踩的坑：内存顺序（memory ordering）。

考虑这样一段"生产者-消费者"代码：

// 生产者                          // 消费者
data = 42;                         while (ready == 0) ;   // 等待
ready = 1;                         printf("%d\n", data);  // 期望打印 42

在 x86 上，这段代码（编译器不乱来的前提下）通常"碰巧能用"，因为 x86 的内存模型比较强，写操作的顺序在其他核看来基本保持不变。

但 ARM64 是弱内存模型：CPU 为了性能，允许其他核看到的写入顺序与程序顺序不同。消费者可能看到 ready == 1，却读到旧的 data。

正确的做法是使用带有内存顺序语义的原子操作：

#include <stdatomic.h>

// 生产者
data = 42;
atomic_store_explicit(&ready, 1, memory_order_release);   // ARM64 上编译为 stlr 指令

// 消费者
while (atomic_load_explicit(&ready, memory_order_acquire) == 0)  // 编译为 ldar 指令
    ;
printf("%d\n", data);   // 保证读到 42

release 保证"在它之前的写入，不会被排到它之后"；acquire 保证"在它之后的读取，不会被排到它之前"。ARM64 有专门的 stlr（store-release）和 ldar（load-acquire）指令来高效实现这种语义。

结论：在共享内存里做进程间通信，永远使用原子操作、锁（比如 pthread_mutex 配合 PTHREAD_PROCESS_SHARED 属性）或其他同步原语，不要依赖"看起来能用"的普通读写。

六、匿名映射的其他用途

用途 做法

预留一大段地址空间 先用 PROT_NONE 映射一大块（不占物理内存），之后按需 mprotect 打开一部分。很多语言运行时（Go、Java）的堆都这么做

tmpfs / /dev/shm 存在内存中的文件系统
shm_open 在 /dev/shm 创建有名字的共享内存，供无关进程映射
memfd_create 创建没有路径、只能通过 fd 传递的内存文件，支持封印

｜数据什么时候真正落盘：一致性、同步与崩溃

本篇目标：弄清写进 mmap 区域的数据此刻在哪里、何时到达磁盘；掌握 msync 的正确用法；理解 munmap 和进程退出到底保证了什么；认识断电时的崩溃一致性问题；最后学会诊断和防范 mmap 特有的 SIGBUS。

一、你写下的数据，此刻在哪里？

假设你用 MAP_SHARED 映射了一个文件，然后执行：

p[100] = 'X';

这条指令执行完的瞬间，'X' 在哪里？

答案（结合第 5、6 篇）：在页缓存里的某个物理页上。它不在磁盘上。

 你的写入 ──▶ 页缓存中的物理页（变成脏页） ──?──▶ 磁盘
                                          这一步什么时候发生？

后半段旅程，和 write 写入的数据完全一样：由内核的后台回写线程在合适的时机写回磁盘（30 秒超时、脏页比例过高、内存回收等，见第 5 篇）。

1.1 内核怎么知道你写了？

这里有个有趣的问题：用 write 写文件时，内核亲自把数据拷进页缓存，当然知道哪一页脏了。但 mmap 的写入是程序直接用 CPU 指令写内存，内核根本不参与，它怎么知道哪些页被改过、需要写回？

Linux 用的是一个和写时复制很像的技巧：

  1. 对于共享的可写文件映射，页第一次被挂进页表时，内核故意把页表项设为只读；
  2. 程序第一次写这一页 → 权限缺页异常；
  3. 内核借此机会：通知文件系统"这一页要被写了"（文件系统可能需要在磁盘上预留空间），把页标记为脏，再把页表项改成可写；
  4. 后台线程把这一页写回磁盘后，会再次把页表项改回只读；
  5. 程序下次再写，又会触发一次缺页，页再次被标记为脏。
  干净 + 只读 ──写──▶ 缺页：标记脏 ──▶ 脏 + 可写 ──写回磁盘──▶ 干净 + 只读 ──写──▶ ...

这样，内核用很小的代价（每页每轮一次缺页）精确地追踪了所有 mmap 写入。这也意味着：往一个刚被写回的页上写数据，会有一次额外的缺页开销。

在 ARM64 上，较新的硬件（ARMv8.1 起）支持由硬件自动维护页表项中的"脏"状态（DBM 机制），内核可以利用它减少一部分这类缺页，但整体思路相同。

二、msync：把数据推到磁盘

2.1 函数原型

#include <sys/mman.h>

int msync(void *addr, size_t length, int flags);

msync 要求内核把指定范围内的脏页写回文件。addr 必须页对齐。flags 必须包含下面二者之一：

标志 含义
MS_SYNC 发起写回，并等待写入完成后才返回
MS_ASYNC 安排写回，立即返回

可选附加：

标志 含义
MS_INVALIDATE 让同一文件的其他映射失效，以便看到新数据（Linux 上由于页缓存是统一的，这个标志基本没有实际作用）

2.2 MS_SYNC 和 MS_ASYNC 的真相

  • MS_SYNC：真正有用的那个。在 Linux 上，它的效果大致相当于对这个文件范围调用 fdatasync：把数据写到磁盘并等待完成。函数返回 0 后，你可以相信数据已经持久化（前提是磁盘本身不撒谎）。
  • MS_ASYNC：在现代 Linux 上基本什么都不做。因为第 1.1 节的机制，内核早已知道哪些页是脏的，它们本来就会被后台线程写回。MS_ASYNC 不会让写回提前发生。

所以，需要持久化保证时，用 MS_SYNC。

2.3 用法示例

// 修改文件第 1000 字节附近的一条记录，并确保它落盘
long page = sysconf(_SC_PAGESIZE);

memcpy(p + 1000, record, sizeof record);

// msync 的地址要页对齐：从记录所在页的起点开始
char  *start = (char *)((uintptr_t)(p + 1000) & ~(uintptr_t)(page - 1));
size_t len   = (p + 1000 + sizeof record) - start;

if (msync(start, len, MS_SYNC) < 0) {
    perror("msync");          // 磁盘出错时会在这里报告！
}

最简单粗暴的做法是对整个映射区域调用 msync(p, size, MS_SYNC)，内核只会写真正脏了的页。

2.4 fsync 也可以

因为 mmap 写入的数据就在页缓存里，对同一个文件的 fd 调用 fsync(fd) 或 fdatasync(fd) 也能把它们写到磁盘。区别是：

  • fsync 作用于整个文件，还会写入元数据（文件大小、修改时间等）；
  • msync 只针对指定的地址范围。

如果你同时改变了文件大小（比如先 ftruncate 扩大文件再映射写入），最好在最后调用一次 fsync，确保文件大小这个元数据也已落盘。

三、常见误解：munmap 和退出会保存数据吗？

3.1 munmap

munmap 只是解除映射：删除"菜单"条目、清除页表项。被修改过的页依然作为脏页留在页缓存中，之后照常由后台线程写回。

  • 数据不会丢（只要系统不崩溃）：其他进程 read 这个文件马上就能看到你的修改；
  • 但也没有被保证落盘：munmap 不等待磁盘写入。

3.2 进程退出

进程退出（正常退出、被杀死、崩溃）时，内核会自动解除它的所有映射。效果和 munmap 一样：

  • MAP_SHARED 映射中的修改已经在页缓存里，不会因为进程退出而丢失，会被正常写回；
  • MAP_PRIVATE 映射中的修改（私有复印件）随进程一起消失，本来就不会写回文件。

这一点其实是 mmap 的一个优点：进程崩溃不会丢失已写入共享映射的数据。相比之下，用 fwrite 写到 C 库缓冲区、还没 fflush 的数据，进程崩溃时就丢了。

3.3 唯一会丢数据的情况

操作系统崩溃或断电。这时页缓存里还没写回的脏页全部丢失。

发生了什么 已写入 MAP_SHARED 的数据
调用 munmap 安全（在页缓存中，稍后写回）
进程正常退出 安全
进程崩溃 / 被 kill -9 安全
内核崩溃 / 断电，且之前没有 msync(MS_SYNC) 可能丢失
内核崩溃 / 断电，之前已经 msync(MS_SYNC) 成功 安全

四、崩溃一致性：比"丢数据"更麻烦的问题

4.1 你无法控制写回的时机和顺序

用 write 时，至少数据是在你调用 write 的那一刻才进入页缓存的。而用 mmap，数据从你写下的那一瞬间就在页缓存里了，内核随时可能把它写回磁盘——哪怕你只改了一半。

假设你要更新一个 8KB、横跨两页的数据结构：

  第 A 页: [旧数据前半部分]      第 B 页: [旧数据后半部分]
         ↓ 你开始修改
  第 A 页: [新数据前半部分]      第 B 页: [旧数据后半部分]   ← 此刻内核恰好写回了第 A 页
         ↓ 断电！
  磁盘上: 新的前半部分 + 旧的后半部分 = 一个损坏的数据结构

更糟的是，内核写回脏页的顺序也不受你控制。你先改了第 B 页再改第 A 页，磁盘上可能 A 先落地。

4.2 页本身也可能"撕裂"

即使是同一页，一个 4KB 的页写到磁盘时，底层设备也不一定保证原子性。断电时可能只写进去一部分（称为"撕裂写" torn write）。

4.3 应对思路

需要崩溃一致性的程序（数据库、文件系统、日志系统）通常采用以下方法之一：

  • 预写日志（WAL，Write-Ahead Log）：先把"我打算做什么修改"追加写到一个日志文件，并 fsync；然后再修改数据文件。崩溃后根据日志重放或回滚。
  • 写时复制数据结构：从不原地修改旧数据，而是把新版本写到新位置，最后用一次原子的"指针切换"（比如更新一个元数据页）让新版本生效。LMDB 就是这么做的（第 12 篇）。
  • 校验和：给每个数据块加上校验和，崩溃后能检测出哪些块损坏了。

所有这些方法都需要在关键步骤之间插入 msync(MS_SYNC) 或 fsync，作为"屏障"：确保前一步真正落盘之后，才开始下一步。

这是"数据库到底该不该用 mmap"之争的核心之一：mmap 让内核在任意时刻都可能写回任意脏页，程序很难控制写回顺序。第 12 篇会详细讨论。

五、错误去哪儿了？

用 write 时，如果出错（磁盘满了、I/O 错误），write 会返回 -1，你立刻就能知道。

用 mmap 写入数据，只是一条普通的内存写指令，不可能返回错误码。那么错误怎么报告呢？

  1. 写回时发生的 I/O 错误（比如磁盘坏道）：内核把错误记录在文件上，在你下一次调用 msync(MS_SYNC) 或 fsync 时返回 EIO。如果你从来不调用 msync/fsync，你可能永远不知道数据没写进去。
  2. 缺页时无法完成的情况：内核没法让一条内存访问指令"返回错误"，只能给进程发送一个信号——SIGBUS。

六、SIGBUS：mmap 的专属"地雷"

6.1 什么时候会收到 SIGBUS

原因 说明
访问超出文件末尾的整页 第 6 篇讲过：映射长度大于文件，访问完全在文件之外的页
映射后文件被截短 你映射了 1GB 文件，另一个进程把它截成了 1MB，你访问后面的部分
读取时发生 I/O 错误 缺页时需要从磁盘读，但磁盘返回错误
磁盘空间不足 你往一个"稀疏文件"的空洞里写数据，文件系统需要分配磁盘块，却发现磁盘满了
超出配额 类似磁盘满，用户的磁盘配额用完了

第二种最常见、也最危险：你的程序没有任何 bug，却因为别人修改了文件而崩溃。

6.2 实验：亲手制造 SIGBUS 并捕获它

// sigbus_demo.c —— 映射后文件被截短，访问触发 SIGBUS
#include <stdio.h>
#include <signal.h>
#include <setjmp.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/mman.h>

static sigjmp_buf jump_back;

static void on_sigbus(int sig, siginfo_t *info, void *ctx) {
    (void)sig; (void)ctx;
    // 信号处理函数里只做最少的事；这里为了演示打印出错地址
    char msg[96];
    int n = snprintf(msg, sizeof msg, "  收到 SIGBUS！出错地址: %p\n", info->si_addr);
    write(2, msg, n);
    siglongjmp(jump_back, 1);           // 跳回安全点，避免重新执行出错指令
}

int main(void) {
    long page = sysconf(_SC_PAGESIZE);

    // 创建一个 2 页大的文件
    int fd = open("bus.bin", O_RDWR | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) { perror("open"); return 1; }
    if (ftruncate(fd, 2 * page) < 0) { perror("ftruncate"); return 1; }

    char *p = mmap(NULL, 2 * page, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }

    // 注册 SIGBUS 处理函数
    struct sigaction sa = {0};
    sa.sa_sigaction = on_sigbus;
    sa.sa_flags = SA_SIGINFO;
    sigaction(SIGBUS, &sa, NULL);

    p[page] = 'A';
    printf("截断前：写第 2 页成功，p[page] = %c\n", p[page]);

    // 模拟"另一个进程"把文件截成 1 页
    ftruncate(fd, page);
    printf("文件已被截短为 1 页\n");

    printf("访问第 1 页：p[0] = %d（正常）\n", p[0]);

    if (sigsetjmp(jump_back, 1) == 0) {
        printf("访问第 2 页...\n");
        char c = p[page];               // 这一页已在文件之外 → SIGBUS
        printf("读到 %c（不会执行到这里）\n", c);
    } else {
        printf("从 SIGBUS 中恢复，程序继续运行\n");
    }

    munmap(p, 2 * page);
    close(fd);
    return 0;
}

gcc sigbus_demo.c -o sigbus_demo && ./sigbus_demo
# 截断前：写第 2 页成功，p[page] = A
# 文件已被截短为 1 页
# 访问第 1 页：p[0] = 0（正常）
# 访问第 2 页...
#   收到 SIGBUS！出错地址: 0xffffa1b21000
# 从 SIGBUS 中恢复，程序继续运行

注意：截断文件时，内核会把已经映射进页表的、超出新文件末尾的页从所有进程的页表中移除。所以即使第 2 页之前已经被访问过，截断后再访问也会触发缺页，然后发现"文件里已经没有这一页了"，于是发送 SIGBUS。

6.3 用 sigsetjmp/siglongjmp 捕获是好主意吗？

上面的做法可以让程序在 SIGBUS 后继续运行，但在真实项目中要非常谨慎：

  • 信号处理函数里能安全调用的函数非常有限；
  • 跳回之前，程序可能正处在某个数据结构修改的中途，状态不一致；
  • 多线程程序中处理更加复杂。

大多数程序的选择是：预防 SIGBUS，而不是处理 SIGBUS。

6.4 如何预防

风险 预防方法
访问超出文件末尾 映射前用 fstat 获取大小，绝不访问超出范围的部分
别人截断文件 只映射你能控制的文件；用文件锁（flock）协调；使用 memfd_create 的封印（F_SEAL_SHRINK）禁止截短
磁盘满导致写入失败 映射前用 fallocate / posix_fallocate 预先分配磁盘空间，而不是只用 ftruncate 创建稀疏文件
读取 I/O 错误 硬件问题，通常只能接受进程崩溃，或用 SIGBUS 处理函数记录日志后退出

ftruncate 和 fallocate 的区别：

ftruncate(fd, 1 << 30);          // 文件变成 1GB，但磁盘上没有分配空间（稀疏文件）
                                 // 读起来全是 0；写的时候才分配磁盘块，此时可能因磁盘满而 SIGBUS

posix_fallocate(fd, 0, 1 << 30); // 文件变成 1GB，并且磁盘块已经全部分配好
                                 // 如果空间不够，这个调用本身就会返回错误，而不是之后崩溃

七、混用 read/write 和 mmap

第 5 篇说过，Linux 上 read/write 和 mmap 共用同一个页缓存，所以它们之间是天然一致的：

  • 进程 A 通过 MAP_SHARED 写入，进程 B 立刻可以 read 到；
  • 进程 A 通过 write 写入，进程 B 的 MAP_SHARED（以及没写过对应页的 MAP_PRIVATE）映射立刻可以看到。

例外：

  • O_DIRECT：它绕过页缓存直接读写磁盘，可能和 mmap 看到的内容不一致。内核会尽力处理（在直接 I/O 前后刷新或作废页缓存），但同时对同一区域既做直接 I/O 又做 mmap 是自找麻烦。
  • 网络文件系统（如 NFS）：多台机器之间的一致性由 NFS 协议决定，比本地文件系统弱得多。

八、改变文件大小

mmap 不能改变文件大小。如果文件需要增长（比如日志不断追加），常见的做法有：

做法一：先扩大文件，再重新映射

// 文件从 old_size 增长到 new_size
posix_fallocate(fd, old_size, new_size - old_size);  // 或 ftruncate
munmap(p, old_size);
p = mmap(NULL, new_size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);

问题：重新映射后地址可能变了，所有指向旧映射的指针都会失效。

做法二：mremap（Linux 专有）

#define _GNU_SOURCE
#include <sys/mman.h>

ftruncate(fd, new_size);
p = mremap(p, old_size, new_size, MREMAP_MAYMOVE);

mremap 可以原地扩大映射；如果原地空间不够且指定了 MREMAP_MAYMOVE，内核会把映射搬到别处（只修改页表，不拷贝数据），但地址同样可能改变。

做法三：一次预留足够大的地址空间

// 预留 64GB 地址空间（不占物理内存，也不要求文件这么大）
char *base = mmap(NULL, 64UL << 30, PROT_NONE, MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE, -1, 0);

// 文件增长后，用 MAP_FIXED 把文件映射到这块预留区域的开头
ftruncate(fd, cur_size);
mmap(base, cur_size, PROT_READ | PROT_WRITE, MAP_SHARED | MAP_FIXED, fd, 0);

地址永远不变，指针永远有效。这是 LMDB 等数据库常用的思路：一开始就映射一个"最大大小"，文件在其中慢慢增长。

MAP_FIXED 在这里是安全的，因为我们覆盖的正是自己预留的区域。这也是 MAP_FIXED 少数正当的用法之一。

本篇目标：打破"mmap 零拷贝所以一定更快"的迷思。系统地分析 mmap 省掉了什么、又额外付出了什么；理解缺页开销、TLB 击落、预读；学会使用 madvise、MAP_POPULATE、大页和 mlock 调优；并亲手写一个基准测试。

一、一个流行的说法

在网上搜索 mmap，你经常会看到这样的说法：

"read 需要把数据从内核拷贝到用户空间，而 mmap 是零拷贝，所以 mmap 比 read 快。"

这句话只说对了一半。mmap 确实省掉了拷贝，但它也引入了 read 没有的开销。哪个更快，取决于场景。

我们先算清楚两边的账。

二、mmap 省掉了什么

2.1 数据拷贝

read 每读一字节都要从页缓存拷贝到用户缓冲区（第 5 篇）。现代 CPU 拷贝内存的速度大约是每秒十几到几十 GB，单核拷贝 1GB 数据需要几十毫秒，同时还会把 CPU 缓存"冲刷"一遍。mmap 没有这部分开销。

2.2 系统调用

read 每次调用都要切换到内核态再切回来（第 1 篇）。mmap 映射建立之后，访问数据完全不需要系统调用。

2.3 内存占用

read 时，数据在页缓存里有一份，在你的缓冲区里又有一份。如果 100 个进程都 read 同一个 1GB 文件到自己的缓冲区，就是 100GB + 1GB。而 100 个进程 mmap 同一个文件，只占用页缓存里的那 1GB。

2.4 编程便利

随机访问直接用下标，解析复杂格式不用操心缓冲区边界。这虽然不是"性能"，但常常间接带来性能：更简单的代码更容易优化。

三、mmap 额外付出了什么

3.1 缺页开销

read 的数据通路里没有缺页（读到的缓冲区通常早已在内存中）。mmap 的每个页第一次被访问时都要经历一次缺页异常：

  • 从用户态陷入内核（类似一次系统调用的开销）；
  • 查找 VMA、查找页缓存、加锁、修改页表；
  • 返回用户态，重新执行指令。

一次小缺页通常需要零点几到一两微秒。对 4KB 一页来说，这相当于每 4KB 数据付出一次"系统调用级"的开销。

对比：read 用 1MB 的缓冲区读一个已缓存的文件，每 1MB 才一次系统调用；而 mmap 即使有 fault-around（第 6 篇，每 64KB 一次缺页），每 1MB 也要 16 次缺页。所以顺序读一个大文件时，mmap 的缺页开销可能抵消甚至超过它省下的拷贝开销。

3.2 页表的建立与销毁

每映射一页，就要填一个页表项；munmap 时要逐一清除。映射 10GB 文件并全部访问，意味着要创建约 260 万个页表项（4KB 页），页表本身就要占约 20MB 内存。

3.3 TLB 压力与 TLB 击落

TLB 未命中：第 3 篇讲过，TLB 只能缓存有限的翻译结果。在一个巨大的映射区域里随机跳转访问，TLB 会频繁未命中，每次都要做一次四级页表遍历。

TLB 击落（shootdown）：当 munmap、mprotect 或内核回收页面时，需要作废所有 CPU 核上相关的 TLB 条目。

  • 在 x86 上，这需要给其他核发送处理器间中断（IPI），让它们各自作废，开销很大；
  • 在 ARM64 上，可以用带 IS（Inner Shareable）后缀的 TLBI 指令由硬件广播作废请求，再用 DSB ISH 等待完成，不需要打断其他核，这比 IPI 便宜得多。但当需要作废的范围很大、核数很多时，代价依然可观。ARMv8.4 引入的 TLB 范围作废指令（TLBI RVAE1IS 等）进一步降低了大范围作废的成本。

如果你的程序频繁地 mmap/munmap 小块区域（比如每处理一个请求就映射一次文件），这些开销会累积起来。

3.4 锁竞争

一个进程的所有映射由一个结构（mm_struct，第 11 篇）统一管理。历史上，缺页处理和 mmap/munmap 都要获取同一把锁（mmap_lock）。在多线程程序里，一个线程在做 mmap/munmap 时，其他线程的缺页处理可能被迫等待。

较新的内核（6.4 起）引入了按 VMA 加锁（per-VMA lock），大多数缺页不再需要全局锁，这个问题已大大缓解。

3.5 I/O 无法并行、无法异步

当数据不在页缓存中时，mmap 的访问会触发大缺页，线程同步阻塞直到这一页从磁盘读回。

  • 一个线程同一时刻只能等待一个缺页，无法同时发出多个读请求；
  • 程序也无法在等待时去做别的事情。

而用 pread 配合多线程、或者 Linux 的 io_uring，程序可以同时发出几十上百个读请求，充分利用 NVMe SSD 的并行能力。在"数据不在内存、随机读"的场景下，这个差距可能达到数倍到数十倍。

3.6 错误处理

第 9 篇讲过，mmap 的 I/O 错误以 SIGBUS 的形式出现，处理起来比检查 read 的返回值麻烦得多。这不直接影响速度，但影响工程上的取舍。

把上面两份账放在一起，可以得到一个粗略的判断：

五、调优手段

5.1 预读与 madvise

内核默认会根据访问模式猜测要不要预读（第 5 篇）。对于 mmap，你可以用 madvise 主动告诉内核你打算怎么访问：

int madvise(void *addr, size_t length, int advice);

常用的 advice：

建议 含义 适用场景
MADV_NORMAL 默认行为 —
MADV_SEQUENTIAL 我会顺序访问 内核加大预读，并更积极地回收已经读过的页
MADV_RANDOM 我会随机访问 内核关闭预读，避免读入用不到的数据
MADV_WILLNEED 我马上要用这段数据 内核异步开始把它读入页缓存，调用立即返回
MADV_DONTNEED 我暂时不用这段数据 立刻解除这段的页表映射；对私有匿名内存来说，物理页被释放，下次访问得到全 0 的新页
MADV_FREE 这段匿名内存可以回收（Linux 4.5+） 比 DONTNEED 更"懒"：内存紧张时才真正回收；如果回收前你又写了，就保留
MADV_HUGEPAGE / MADV_NOHUGEPAGE 希望 / 不希望使用透明大页 见 5.3 节
MADV_POPULATE_READ / MADV_POPULATE_WRITE 立即为这段区域完成缺页（Linux 5.14+） 提前付清缺页开销

示例：

char *p = mmap(NULL, size, PROT_READ, MAP_PRIVATE, fd, 0);

madvise(p, size, MADV_SEQUENTIAL);           // 顺序扫描整个文件
// 或者
madvise(p, size, MADV_RANDOM);               // 像数据库索引那样随机查找
// 或者
madvise(p + off, 64 << 20, MADV_WILLNEED);   // 提前把接下来要用的 64MB 读进来

madvise 只是"建议"，内核可以忽略。它也不会改变程序的正确性（MADV_DONTNEED、MADV_FREE 这类会丢弃数据的除外，要小心使用）。

5.2 MAP_POPULATE：映射时就付清缺页

char *p = mmap(NULL, size, PROT_READ, MAP_PRIVATE | MAP_POPULATE, fd, 0);

内核在 mmap 返回之前，就把整个区域的页全部读入并填好页表。好处是之后的访问不会再有缺页，延迟稳定；代价是 mmap 本身变慢了，而且如果你最终只用到一小部分，就白白浪费了时间和内存。

适合"马上就要全部用到"、或者"对后续访问延迟非常敏感"的场景。

5.3 大页

第 3 篇讲过，ARM64 页表的 L2、L1 条目可以直接映射一大块内存。把它用起来就是大页：

ARM64 粒度 普通页 常用大页 更大的页
4KB 粒度 4KB 2MB（L2 块） 1GB（L1 块）
16KB 粒度 16KB 32MB —
64KB 粒度 64KB 512MB —

此外，ARM64 页表项还有一个"连续位"（contiguous bit）：如果 16 个相邻的 4KB 页表项指向物理上连续、权限相同的内存，可以打上这个标记，TLB 就能用一个条目覆盖 64KB。较新的 Linux 内核（6.9 起）会利用它来支持"多尺寸透明大页"（mTHP）。

大页的好处：

  • TLB 覆盖面大幅增加：一个 2MB 条目顶 512 个 4KB 条目。对随机访问大块内存的程序（数据库、科学计算、虚拟机），TLB 未命中率会显著下降；
  • 页表更小，缺页更少：一次缺页处理 2MB 而不是 4KB。

坏处：

  • 内存浪费：只用了 1 字节，也要占 2MB；
  • 分配困难：需要 2MB 物理上连续的内存，系统运行久了内存碎片化，可能分配不到；
  • COW 代价：大页的写时复制要复制 2MB。

Linux 有两种使用大页的方式：

方式一：透明大页（THP，Transparent Huge Pages）

内核自动尝试用大页。查看和设置：

cat /sys/kernel/mm/transparent_hugepage/enabled
# always [madvise] never      ← 方括号是当前值
  • always：所有匿名内存都尝试用大页；
  • madvise：只对调用了 madvise(MADV_HUGEPAGE) 的区域使用；
  • never：关闭。

内核还有一个后台线程 khugepaged，会把零散的小页"合并"成大页。

THP 主要用于匿名内存。对于普通文件的 mmap，较新的内核和文件系统（如 XFS、ext4 支持"大 folio"之后）也能在页缓存中使用更大的页并以大页方式映射，但支持程度因内核版本和文件系统而异。

方式二：hugetlbfs（显式大页）

管理员预先保留一批大页，程序显式申请：

echo 512 | sudo tee /proc/sys/vm/nr_hugepages     # 预留 512 个 2MB 大页 = 1GB
grep Huge /proc/meminfo

void *p = mmap(NULL, 1 << 30, PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS | MAP_HUGETLB, -1, 0);

这种方式稳定可靠，不会因为碎片分配失败（因为是预留的），但需要提前规划，内存也被专门占用。数据库和虚拟机（例如给 Firecracker 的客户机内存使用大页）常用这种方式。

5.4 mlock：把页钉在内存里

mlock(p, size);       // 锁定这段区域：所有页立即调入内存，并且不会被换出或回收
munlock(p, size);
mlockall(MCL_CURRENT | MCL_FUTURE);   // 锁定进程的全部内存

适用于对延迟极度敏感的程序（实时音频、高频交易），或者存放密钥等不希望被换出到磁盘的敏感数据。受 RLIMIT_MEMLOCK 限制，普通用户能锁定的量通常很小。

5.5 减少映射/解除映射的次数

  • 长期复用同一个映射，而不是每次用都重新 mmap；
  • 一次映射大的范围，而不是很多次小映射；
  • 避免频繁 mprotect，它和 munmap 一样需要作废 TLB。

六、动手：写一个基准测试

下面的程序对比四种方式读取同一个文件（假设文件已在页缓存中）：

// bench.c —— 对比 read 与 mmap（请先让文件进入页缓存：cat 文件 > /dev/null）
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <inttypes.h>
#include <time.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/mman.h>
#include <sys/stat.h>

static double now(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + t.tv_nsec / 1e9;
}

static uint64_t sum(const uint8_t *p, size_t n) {
    uint64_t s = 0;
    for (size_t i = 0; i < n; i++) s += p[i];
    return s;
}

static uint8_t buf[1 << 20];          // 1MB 缓冲区

int main(int argc, char *argv[]) {
    if (argc != 2) { fprintf(stderr, "用法: %s 文件名\n", argv[0]); return 1; }
    int fd = open(argv[1], O_RDONLY);
    if (fd < 0) { perror("open"); return 1; }
    struct stat st;
    fstat(fd, &st);
    size_t size = st.st_size;
    long page = sysconf(_SC_PAGESIZE);
    size_t npages = size / page;
    const int OPS = 500000;           // 随机访问次数
    uint64_t s;
    double t;

    // 1. read 顺序读（1MB 缓冲区）
    t = now(); s = 0;
    off_t off = 0;
    ssize_t n;
    while ((n = pread(fd, buf, sizeof buf, off)) > 0) { s += sum(buf, n); off += n; }
    printf("read  顺序: %7.3f s  (校验和 %" PRIu64 ")\n", now() - t, s);

    // 2. mmap 顺序读（含映射、缺页、解除映射的全部开销）
    t = now();
    uint8_t *p = mmap(NULL, size, PROT_READ, MAP_PRIVATE, fd, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }
    s = sum(p, size);
    munmap(p, size);
    printf("mmap  顺序: %7.3f s  (校验和 %" PRIu64 ")\n", now() - t, s);

    // 3. pread 随机读：每次在随机页上读 64 字节
    srand(1); t = now(); s = 0;
    for (int i = 0; i < OPS; i++) {
        off_t o = (off_t)(rand() % npages) * page;
        pread(fd, buf, 64, o);
        s += sum(buf, 64);
    }
    printf("pread 随机: %7.3f s  (校验和 %" PRIu64 ")\n", now() - t, s);

    // 4. mmap 随机读：同样的访问序列
    p = mmap(NULL, size, PROT_READ, MAP_PRIVATE, fd, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }
    madvise(p, size, MADV_RANDOM);
    for (int round = 1; round <= 2; round++) {
        srand(1); t = now(); s = 0;
        for (int i = 0; i < OPS; i++) {
            size_t o = (size_t)(rand() % npages) * page;
            s += sum(p + o, 64);
        }
        printf("mmap  随机(第%d轮): %7.3f s  (校验和 %" PRIu64 ")\n", round, now() - t, s);
    }
    munmap(p, size);
    close(fd);
    return 0;
}

dd if=/dev/urandom of=bench.bin bs=1M count=2048    # 2GB 测试文件
cat bench.bin > /dev/null                            # 预热：确保在页缓存中
gcc -O2 bench.c -o bench
./bench bench.bin

你可能会观察到这样的规律（具体数值随机器、内核版本、页大小、是否启用大页而大幅变化，请以自己的测量为准）：

  1. 顺序读：read 和 mmap 的差距不大，有时 read 甚至更快。mmap 省掉了拷贝，但付出了几万次缺页；
  2. pread 随机读：每次访问都是一次系统调用加一次小拷贝；
  3. mmap 随机读第 1 轮：很多页是第一次被访问，需要缺页，开销与 pread 相近；
  4. mmap 随机读第 2 轮：大多数页已在页表中，访问就是纯粹的内存读，明显快于 pread——这正是 mmap 最擅长的场景。

可以进一步尝试：

  • 去掉 cat bench.bin > /dev/null 并先清空缓存，观察冷数据下的差异；
  • 在顺序读的 mmap 上加 MAP_POPULATE 或 madvise(MADV_SEQUENTIAL)；
  • 用 perf stat -e page-faults,dTLB-load-misses ./bench bench.bin 观察缺页和 TLB 未命中的次数（不同 CPU 支持的事件名可能不同，可用 perf list 查看）。

一、从进程到地址空间

Linux 内核用一个叫 task_struct 的结构描述每一个进程（或线程）。它里面有一个指针 mm，指向一个 mm_struct，这个结构描述了进程的整个用户地址空间。

 task_struct（进程/线程）
   │
   └── mm ──▶ mm_struct（地址空间）
                ├── pgd          ─▶ 这个进程的顶级页表（L0 表）的地址
                ├── mm_mt        ─▶ 所有 VMA 组成的树（maple tree）
                ├── mmap_lock    ─▶ 保护这个地址空间的读写锁
                ├── mmap_base    ─▶ mmap 区域的起点（从这里往下分配）
                ├── map_count    ─▶ VMA 的数量
                ├── total_vm     ─▶ 总共映射了多少页
                └── rss_stat     ─▶ 实际占用的物理页统计（文件页、匿名页、共享内存页）

同一个进程里的多个线程共享同一个 mm_struct，这就是为什么线程之间天然共享内存。fork 出来的子进程则得到一个新的 mm_struct，里面的 VMA 和页表是从父进程复制来的（第 7 篇的 COW）。

进程切换时，ARM64 内核会把新进程 mm->pgd 对应的物理地址写进 TTBR0_EL1 寄存器（同时带上它的 ASID），从此 CPU 就在新进程的"世界"里翻译地址（第 3 篇）。

二、VMA：地址空间的"菜单条目"

第 4 篇我们把 VMA 比作"菜单"。现在看看它的真面目：struct vm_area_struct，描述一段连续的、属性相同的虚拟地址区域。

 struct vm_area_struct
   ├── vm_start, vm_end   区域的起止虚拟地址 [vm_start, vm_end)
   ├── vm_mm              属于哪个 mm_struct
   ├── vm_flags           属性：VM_READ / VM_WRITE / VM_EXEC / VM_SHARED / VM_MAYWRITE ...
   ├── vm_page_prot       由 vm_flags 换算出的页表项权限位（ARM64 格式）
   ├── vm_file            如果是文件映射：指向哪个文件；匿名映射为 NULL
   ├── vm_pgoff           这段区域起点对应文件中的第几页
   ├── vm_ops             一组回调函数：发生缺页时调用谁、页面要被写时通知谁
   └── anon_vma           用于匿名页的反向映射（见第六节）

/proc/pid/maps 里的每一行，就是一个 VMA：

ffff8a400000-ffff8a5a0000 r-xp 00000000 fe:01 2071   /usr/lib/aarch64-linux-gnu/libc.so.6
│            │            │    │                      │
vm_start     vm_end       │    vm_pgoff × 页大小        vm_file
                          vm_flags（r-x，p = 没有 VM_SHARED）

2.1 VMA 的组织

一个进程可能有成百上千个 VMA。缺页时内核需要快速回答"这个地址落在哪个 VMA 里"，所以 VMA 被组织在一棵查找树中。从 6.1 版本开始，Linux 用一种叫 maple tree 的 B 树变体来存放 VMA（之前用的是红黑树加链表）。

2.2 VMA 的数量限制

每个进程的 VMA 数量有上限：

cat /proc/sys/vm/max_map_count
# 65530

如果一个程序创建了大量零散的映射（比如成千上万个小文件各自 mmap，或者频繁对不同小段 mprotect 导致 VMA 分裂），可能撞上这个上限，mmap 返回 ENOMEM——即使内存还很充裕。Elasticsearch 等大量使用 mmap 的软件会要求调大这个值。

2.3 VMA 的合并与分裂

  • 新映射和相邻的已有 VMA 属性完全相同（同一个文件且偏移连续、权限相同等）时，内核会合并成一个 VMA；
  • 对 VMA 中间一段做 munmap 或 mprotect，会把一个 VMA 分裂成两个或三个。

4.1 关于 folio

阅读较新的内核代码时，你会频繁看到 folio 这个词。它是内核对"一个或多个物理连续页组成的一块内存"的抽象。以前页缓存和匿名内存都以单个 4KB struct page 为单位管理，引入 folio 之后，内核可以更自然地以 16KB、64KB、2MB 等更大的单位管理内存，这也是文件 mmap 能使用大页的基础。初学时，把 folio 理解为"页"即可。

五、页缓存：address_space

第 5 篇说每个文件有一个"缓存目录"。在内核里，它是 struct address_space，每个文件的 inode 都有一个（inode->i_mapping）：

 struct address_space
   ├── i_pages      ─▶ 一棵 xarray 树：文件页号 → 缓存的 folio
   ├── i_mmap       ─▶ 一棵区间树：所有映射了这个文件的 VMA
   ├── a_ops        ─▶ 文件系统提供的操作：如何从磁盘读一页、如何把脏页写回
   └── nrpages      ─▶ 当前缓存了多少页
  • read() 和 mmap 缺页都通过 i_pages 查找页面，这就是两者共享同一份缓存的原因；
  • i_mmap 记录了"谁映射了我"，这是下一节反向映射的关键；
  • a_ops 让页缓存与具体文件系统解耦：ext4、XFS、NFS 各自实现如何读写。

六、反向映射：这一页被谁映射了？

6.1 为什么需要反向

页表是"正向"的：给一个虚拟地址，查出物理页。但内核有时需要回答相反的问题：

给我一个物理页，告诉我它被哪些进程的哪些虚拟地址映射了。

什么时候需要？

  • 内存回收：要把一个页从内存里踢出去，必须先把所有指向它的页表项都清除，否则进程会访问到一个已经被挪作他用的物理页；
  • 页面迁移：在 NUMA 系统里把页挪到离 CPU 更近的内存节点，或者为了拼出大页而整理碎片，都要更新所有映射；
  • 文件被截断：第 9 篇的 SIGBUS 实验里，截断文件后内核要把所有映射了被截掉部分的页表项清除。

6.2 怎么做

Linux 的反向映射（rmap）分两种情况：

  • 文件页：从页找到它所属文件的 address_space，再遍历 i_mmap 树里所有覆盖这个文件偏移的 VMA，在每个 VMA 对应的页表里找到并清除那个页表项；
  • 匿名页：每个匿名页记录一个 anon_vma 指针，anon_vma 把可能映射这个页的所有 VMA 串在一起（包括 fork 出来的父子进程的 VMA）。

反向映射的遍历本身有开销。一个被成千上万个进程映射的页（比如 libc 的代码页），回收它要清除成千上万个页表项。

七、内存回收与换出

当空闲内存不足时，内核的后台线程 kswapd 会被唤醒，开始回收页面（内存极度紧张时，正在申请内存的进程也会亲自参与回收，称为"直接回收"）。

回收的大致过程：

  1. 从 LRU 链表的"不活跃"一端挑选页面；
  2. 检查页表项的访问标志（ARM64 页表项中的 AF 位）：最近被访问过的页，给它"第二次机会"，移回活跃链表；
    • ARMv8.1 起支持硬件自动设置 AF 位；不支持时，内核会先清除 AF，下次访问时触发一次"访问标志错误"缺页来得知"它被访问了"；
  3. 通过反向映射，清除所有指向该页的页表项（并作废 TLB）；
  4. 根据页的类型处理：
    • 干净的文件页：磁盘上有一样的内容，直接丢弃；
    • 脏的文件页：先写回磁盘，再丢弃；
    • 匿名页：写入交换区（swap），页表项改为记录交换区位置；没有 swap 就无法回收；
  5. 物理页归还给空闲内存池。

之后进程再访问这些地址，会触发缺页：文件页从磁盘重新读回（大缺页），匿名页从 swap 读回（do_swap_page）。

如果回收也救不回来，内核会启动 OOM Killer，根据内存占用等因素选出一个进程杀掉（第 4 篇）。

对 mmap 来说这意味着：文件映射是"可回收"的内存。你 mmap 了一个 100GB 的文件并读遍了它，并不会导致内存耗尽——内核会在内存紧张时悄悄回收那些已经不常用的页，等你再访问时重新读入。代价是可能出现大量大缺页，性能下降。

八、实验：读懂 /proc/pid/smaps

/proc/pid/maps 只告诉你有哪些 VMA；/proc/pid/smaps 则给出每个 VMA 的详细内存统计。

8.1 实验程序

// smaps_demo.c —— 映射一个文件并读遍，再申请并写满一块匿名内存，然后暂停
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/mman.h>
#include <sys/stat.h>

int main(int argc, char *argv[]) {
    if (argc != 2) { fprintf(stderr, "用法: %s 文件名\n", argv[0]); return 1; }
    long page = sysconf(_SC_PAGESIZE);

    int fd = open(argv[1], O_RDONLY);
    if (fd < 0) { perror("open"); return 1; }
    struct stat st;
    fstat(fd, &st);
    char *f = mmap(NULL, st.st_size, PROT_READ, MAP_SHARED, fd, 0);
    if (f == MAP_FAILED) { perror("mmap"); return 1; }
    volatile char sink = 0;
    for (off_t i = 0; i < st.st_size; i += page) sink += f[i];   // 读遍文件映射

    size_t anon_size = 32 << 20;                                 // 32MB 匿名内存
    char *a = mmap(NULL, anon_size, PROT_READ | PROT_WRITE,
                   MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (a == MAP_FAILED) { perror("mmap"); return 1; }
    memset(a, 1, anon_size);                                     // 写满

    printf("PID %d，文件映射 %p，匿名映射 %p。按回车退出\n", getpid(), (void *)f, (void *)a);
    getchar();
    return 0;
}

字段 含义 本例解读
Size VMA 的大小（虚拟） 映射了 64MB
Rss 这段区域中实际在物理内存里的部分（Resident Set Size） 64MB 都已调入
Pss 按共享人数分摊后的占用（Proportional Set Size） 两个进程共享，每人分摊 32MB
Shared_Clean 和其他进程共享、且干净的页 页缓存页被两个进程共享
Private_Dirty 只有自己在用、且被修改过的页 0（只读映射）
Anonymous 匿名页的量 0（这是文件映射）
Swap 被换出到交换区的量 0

RSS 与 PSS 的区别是理解"一个进程到底占了多少内存"的关键：

  • 把所有进程的 RSS 加起来，共享的页会被重复计算，总和可能远大于实际物理内存；
  • 把所有进程的 PSS 加起来，正好等于这些进程实际占用的物理内存总量。

如果只运行一个实例，你会看到 Pss 等于 Rss，Shared_Clean 变为 0 而 Private_Clean 变为 64MB——"私有"在这里的意思只是"当前只有我一个进程映射了它"，和 MAP_PRIVATE 不是一回事。

一、你每天都在用的 mmap：程序和动态库的加载

还记得第 1 篇的彩蛋吗？strace cat 时出现了好几行 mmap。现在我们有足够的知识看懂它们了。

1.1 内核加载可执行文件

当你执行一个程序时，execve 系统调用里的内核代码（ELF 加载器）会读取可执行文件的头部，找到其中描述"哪些部分要加载到内存哪里"的程序头（PT_LOAD 段），然后对每一段做一次文件映射：

  • 代码段：PROT_READ | PROT_EXEC，私有映射；
  • 只读数据：PROT_READ；
  • 可读写数据：PROT_READ | PROT_WRITE，私有映射（写时复制，不会改动磁盘上的程序文件）；
  • 未初始化数据（.bss）：匿名映射，初始全为 0。

程序启动时一行代码都没有从磁盘读进来，都是执行到哪里、缺页到哪里（第 4 篇做 python3 冷启动实验时看到的大缺页，就是这么来的）。

1.2 动态链接器加载共享库

程序依赖的共享库（如 libc.so.6）由动态链接器 ld-linux-aarch64.so.1 在用户态加载。用 strace 观察：

strace -e trace=openat,mmap,mprotect,munmap,close cat /dev/null 2>&1 | grep -A 9 libc.so

在 ARM64 上输出类似这样（地址和大小因系统而异）：

mmap(NULL, 1826976, PROT_NONE, MAP_PRIVATE|MAP_ANONYMOUS|MAP_DENYWRITE, -1, 0) = 0xffffa1c40000
mmap(0xffffa1c50000, 1761440, PROT_READ|PROT_EXEC, MAP_PRIVATE|MAP_FIXED|MAP_DENYWRITE, 3, 0) = 0xffffa1c50000
munmap(0xffffa1c40000, 65536)           = 0
munmap(0xffffa1dfd000, 5280)            = 0
mprotect(0xffffa1dd9000, 77824, PROT_NONE) = 0
mmap(0xffffa1dec000, 20480, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_FIXED|MAP_DENYWRITE, 3, 0x18c000) = 0xffffa1dec000
mmap(0xffffa1df1000, 49632, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_FIXED|MAP_ANONYMOUS, -1, 0) = 0xffffa1df1000
close(3)                                = 0

逐行翻译：

调用 作用 对应知识
mmap(NULL, …, PROT_NONE, MAP_ANONYMOUS) 先预留一整段地址空间，什么权限都没有 第 8 篇：用 PROT_NONE 预留地址
mmap(…, PROT_READ\|PROT_EXEC, MAP_FIXED, fd=3, 0) 把库的代码映射到预留区域里（按对齐要求选定的位置） 第 6、7 篇：私有文件映射；MAP_FIXED 覆盖自己预留的区域

mmap(…, PROT_READ\|PROT_WRITE, MAP_FIXED, fd=3, 0x18c000) 从文件偏移 0x18c000 处映射可写数据段 私有可写映射，写时复制

之后，动态链接器还会进行重定位（修正库中引用的地址），写入的是私有可写页，触发 COW；完成后再用 mprotect 把一部分区域改回只读（称为 RELRO），防止被攻击者篡改。

1.3 为什么系统里 100 个进程只占一份 libc？

libc 的代码段是 MAP_PRIVATE 映射的，但代码段从来不被写，所以永远不会触发写时复制。所有进程的页表都指向页缓存里的同一批物理页。100 个进程运行，libc 代码在物理内存里只有一份。这就是第 11 篇中 smaps 里 Shared_Clean 和 Pss 的意义。

MAP_DENYWRITE 这个标志现在已被内核忽略。历史上它用于防止正在被执行的文件被写入。现在，如果你试图用 O_WRONLY 打开一个正在运行的程序文件，内核仍会返回 ETXTBSY（"文本文件忙"），这就是为什么升级软件时通常是"写新文件再改名替换"，而不是原地覆盖。

二、数据库：mmap 的拥护者与反对者

数据库是 mmap 最有争议的应用领域。

2.1 拥护者：LMDB

LMDB（Lightning Memory-Mapped Database）把整个数据库文件 mmap 进来，作为它的"缓存"：

  • 读：读取直接访问映射区域，返回的数据就是指向页缓存的指针，真正的零拷贝。读操作不需要加锁，也不需要系统调用；
  • 写：默认通过普通的 write/pwrite 写入（映射是只读的，防止程序的野指针意外破坏数据库）；也可以选择 MDB_WRITEMAP 让写入直接走映射；
  • 一致性：使用写时复制的 B+ 树，从不原地修改旧数据，新版本写到新的页上。提交时先 fdatasync 数据页，再写一个"元数据页"切换到新的树根。崩溃时，旧的元数据页依然指向一棵完整的旧树（第 9 篇讲的"写时复制数据结构"思路）；
  • 地址稳定：一开始就映射一个配置的最大大小（mapsize），文件在其中增长，所以返回给用户的指针一直有效（第 9 篇的"预留大块地址空间"）。

LMDB 代码量很小，读性能极高，被 OpenLDAP 等项目使用。

2.2 部分使用：SQLite、Lucene 等

  • SQLite 支持 PRAGMA mmap_size=N 开启 mmap 读取，在大多数构建中默认关闭。开启后读操作走映射，写操作通常仍用 write；
  • Apache Lucene（Elasticsearch 的底层）在 64 位系统上默认用 MMapDirectory 读取索引文件，大量依赖页缓存；
  • Kafka 用 mmap 访问它的索引文件；
  • Prometheus 的时序数据库也用 mmap 读取历史数据块。

它们的共同点是：主要用 mmap 读，写入则走更可控的路径。

2.3 反对者：为什么有的数据库放弃了 mmap

MongoDB 早期的存储引擎 MMAPv1 基于 mmap，后来被 WiredTiger 引擎取代，MMAPv1 在 4.2 版本中被移除。

2022 年，卡内基梅隆大学和慕尼黑工业大学的研究者在数据库会议 CIDR 上发表了一篇被广泛讨论的论文，标题大意是"你确定要在数据库管理系统里用 mmap 吗？"。论文总结的问题，恰好对应本系列的几个章节：

问题 说明 对应章节
事务安全 内核可能在任何时刻写回任何脏页，数据库无法阻止"未提交的修改"被写到磁盘 第 9 篇
I/O 阻塞 缺页是同步的，数据库无法控制何时发生 I/O，也无法异步、并发地发起 I/O 第 10 篇
错误处理 I/O 错误变成 SIGBUS，难以优雅处理；校验数据完整性也更困难 第 9 篇
性能扩展性 在高速 NVMe 上，页表维护、TLB 击落、内核单线程的页面淘汰会成为瓶颈 第 10、11 篇

论文的结论是：对于数据量超过内存、追求高性能的数据库，自己管理缓冲池（配合 O_DIRECT 或 io_uring）通常是更好的选择。

当然，LMDB 等项目的作者也有反驳：通过合适的设计（如只读映射加写时复制），许多问题是可以规避的；在数据能装入内存的场景下，mmap 的简洁与高性能难以替代。

这场争论没有标准答案，但它恰好是检验你是否理解本系列的绝佳材料： 如果你能看懂双方每一个论点背后的机制，你就真正理解了 mmap。

三、零拷贝与设备映射

3.1 mmap 是"零拷贝"吗？

假设一个 Web 服务器要把文件发送给客户端：

方式 数据拷贝次数（CPU 拷贝）
read 到缓冲区，再 write 到套接字 2 次：页缓存 → 用户缓冲区 → 套接字缓冲区
mmap 文件，再 write 映射区域到套接字 1 次：页缓存（通过映射）→ 套接字缓冲区
sendfile(sock, file_fd, ...) 0 次（在支持的网卡上，数据可直接从页缓存 DMA 到网卡）

所以 mmap 只是"少一次拷贝"，在"把文件发到网络"这件事上，sendfile 或 splice 才是更彻底的零拷贝。mmap 的零拷贝优势在于程序自己要读这些数据的场景。

3.2 映射设备内存

mmap 不只能映射文件，也能映射设备。驱动程序在自己的 mmap 回调里（第 11 篇），通常调用 remap_pfn_range() 把设备的物理地址直接填进进程的页表：

  • 帧缓冲（/dev/fb0）：映射后，写内存就是在屏幕上画像素；
  • GPU：显卡驱动通过 mmap 让程序直接访问显存或与 GPU 共享的内存；
  • 用户态驱动：DPDK、SPDK 等高性能网络/存储框架通过 VFIO 或 UIO，把网卡、NVMe 控制器的寄存器（PCIe BAR 空间）mmap 到用户空间，完全绕过内核直接操作硬件。

在 ARM64 上，映射设备时页表项会带上不同的内存属性（通过页表项的 AttrIndx 字段选择 MAIR_EL1 寄存器里预设的属性）：

  • 普通内存：可缓存（Normal, Cacheable）；
  • 设备寄存器：Device-nGnRE 等类型，不经过缓存，访问不能被合并或重排序，每次读写都真实到达设备；
  • 帧缓冲这类：常用 Normal Non-cacheable，允许写合并以提高效率。

这就是第 2 篇讲的 MMIO 在用户空间的延伸：通过 mmap，程序也能"用读写内存的方式操作设备"。

3.3 内核与用户共享的环形缓冲区

很多现代内核接口都用 mmap 建立内核与用户程序之间的共享内存，以避免反复的系统调用和拷贝：

  • io_uring：提交队列和完成队列是 mmap 出来的环形缓冲区，程序把请求写进去、从里面读结果；
  • perf：性能事件的采样数据通过 mmap 的环形缓冲区传给用户程序；
  • AF_XDP：高速网络数据包通过 mmap 的共享内存区域收发；
  • eBPF：某些类型的 BPF map 可以直接 mmap 到用户空间读写。

四、虚拟机：Firecracker 如何用 mmap 管理客户机内存

虚拟机是 mmap 最精彩的应用场景之一，它把本系列几乎所有的知识都用上了。我们以 Firecracker（一个基于 KVM 的轻量级虚拟机监控程序，常用于运行安全容器和无服务器函数）为例。

4.1 客户机的"物理内存"其实是主机进程的虚拟内存

启动一个 1GB 内存的 Firecracker 微虚拟机时，Firecracker 进程大致做了这样的事：

// 概念示意（Firecracker 本身用 Rust 编写）
void *guest_mem = mmap(NULL, 1UL << 30, PROT_READ | PROT_WRITE,
                       MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE, -1, 0);

struct kvm_userspace_memory_region region = {
    .slot            = 0,
    .guest_phys_addr = 0x80000000,          // 客户机看到的物理地址起点
    .memory_size     = 1UL << 30,
    .userspace_addr  = (uint64_t)guest_mem, // 对应主机进程中的虚拟地址
};
ioctl(vm_fd, KVM_SET_USER_MEMORY_REGION, &region);
  • 用一次匿名 mmap 申请 1GB 虚拟内存，MAP_NORESERVE 表示不预先占用内存额度；
  • 通过 KVM_SET_USER_MEMORY_REGION 告诉 KVM："客户机物理地址 0x8000_0000 开始的 1GB，对应我进程里这段虚拟地址。"在 ARM64 上，Firecracker 把客户机内存（DRAM）放在客户机物理地址 2GB 处，低于它的地址留给虚拟设备（MMIO）；
  • 客户机里的 Linux 以为自己有 1GB 物理内存，但它在主机上只是一个 mmap 区域。

这就是第 8 篇的匿名映射，加上第 4 篇的按需分页：客户机没碰过的内存，主机上不占任何物理页。 这让一台主机可以运行成千上万个微虚拟机。

4.2 ARM64 的两阶段地址翻译

客户机里的程序访问一个地址，要经过两次翻译：

 客户机程序的虚拟地址 (VA)
        │  第一阶段：客户机内核自己的页表（客户机的 TTBR0/TTBR1_EL1）
        ▼
 客户机"物理"地址（ARM 称为 IPA，中间物理地址）
        │  第二阶段：KVM 管理的 stage-2 页表（由 VTTBR_EL2 指向，在 EL2 生效）
        ▼
 主机物理地址 (PA)

第 1 篇提到的 EL2（虚拟机管理器级别）在这里登场了：stage-2 页表由主机的 KVM 维护，客户机完全看不到它。

当客户机第一次访问某个 IPA，而 stage-2 页表里还没有对应条目时，会触发一次 stage-2 缺页，CPU 陷入 EL2 交给 KVM 处理：

  1. KVM 根据内存区域登记，把 IPA 换算成 Firecracker 进程里的主机虚拟地址；
  2. KVM 像普通的内核代码那样"访问"这个主机虚拟地址，如果主机页表里也还没有，就触发主机侧的普通缺页（第 4 篇），分配一个清零的物理页；
  3. KVM 把这个物理页填进 stage-2 页表；
  4. 返回客户机，重新执行出错的指令。

缺页套缺页，但对客户机来说完全透明。

4.3 快照与恢复：MAP_PRIVATE 的妙用

Firecracker 支持把运行中的虚拟机保存成快照（包含内存文件和设备状态），之后从快照快速恢复。恢复时，客户机内存可以有两种"后端"：

后端一：文件映射

void *guest_mem = mmap(NULL, mem_size, PROT_READ | PROT_WRITE,
                       MAP_PRIVATE, snapshot_mem_fd, 0);

把快照内存文件私有映射为客户机内存。这一行代码同时用到了：

  • 按需分页（第 4 篇）：恢复时不读整个内存文件，客户机访问到哪一页，才从文件读哪一页，所以恢复几乎瞬间完成；
  • 页缓存（第 5 篇）：从同一个快照恢复的多个虚拟机，读到的是页缓存里的同一份物理页；
  • 写时复制（第 7 篇）：客户机写某一页时，才复制出一份私有页，快照文件本身永远不会被修改。

后端二：userfaultfd

Firecracker 也可以把客户机内存注册到 userfaultfd（见下一节），把缺页处理交给一个外部的"页面错误处理进程"。这个处理进程可以从任何地方取得页面内容：本地文件、远端存储、内存压缩池……这为更灵活的恢复策略（例如预取热点页面、跨主机懒加载）打开了大门。

4.4 其他用到 mmap 知识的地方

  • 气球设备（balloon）：主机想回收客户机暂时不用的内存时，客户机里的气球驱动"吃掉"一些页并把页号报告给 Firecracker，Firecracker 对这些页调用 madvise(MADV_DONTNEED)（第 10 篇），立即把物理页归还给主机；
  • 大页：Firecracker 可以配置用 2MB 大页（hugetlbfs）作为客户机内存，减少两阶段翻译下的 TLB 压力（第 10 篇）；
  • 增量快照：借助 KVM 的脏页跟踪，只保存自上次快照以来被写过的页（与第 9 篇讲的"内核如何追踪写入"思路相似）；
  • 与外部进程共享客户机内存：使用 vhost-user 等机制时，客户机内存改用 memfd_create 创建的共享映射，再把 fd 传给后端进程映射同一块内存（第 8 篇）。

五、userfaultfd：让用户程序接管缺页

5.1 是什么

正常情况下，缺页由内核处理：匿名页清零、文件页从页缓存取。userfaultfd 让一个用户程序说："这段内存的缺页，交给我来处理。"

工作流程：

 ① 程序创建 userfaultfd，得到一个文件描述符 uffd
 ② 用 UFFDIO_REGISTER 把一段内存区域注册到 uffd
 ③ 某个线程访问这段区域中的一个缺失页
      → 内核不再自己处理，而是让这个线程暂停，并往 uffd 上投递一条"缺页消息"
 ④ 处理线程从 uffd 读到消息：哪个地址缺页了
 ⑤ 处理线程准备好这一页的内容，用 UFFDIO_COPY 把它"放进"缺页地址
 ⑥ 内核填好页表，唤醒第③步暂停的线程，它重新执行指令，读到了处理线程提供的数据

用途：

  • 虚拟机热迁移（post-copy 方式）：先把虚拟机切换到目标主机运行，内存页在被访问时才从源主机拉取；
  • 虚拟机快照懒加载（如上一节的 Firecracker）；
  • 垃圾回收器、检查点/恢复工具（CRIU）等。

5.2 一个最小示例

// uffd_demo.c —— 用 userfaultfd 让用户线程处理缺页
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <pthread.h>
#include <sys/mman.h>
#include <sys/ioctl.h>
#include <sys/syscall.h>
#include <linux/userfaultfd.h>

#ifndef UFFD_USER_MODE_ONLY
#define UFFD_USER_MODE_ONLY 1       // Linux 5.11+：只处理用户态访问引发的缺页
#endif

static long page;
static int  uffd;

static void *fault_handler(void *arg) {
    (void)arg;
    // 准备一个"源页"，每次缺页时往里写不同内容
    char *src = mmap(NULL, page, PROT_READ | PROT_WRITE,
                     MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    int count = 0;
    for (;;) {
        struct uffd_msg msg;
        if (read(uffd, &msg, sizeof msg) != sizeof msg)   // 阻塞，直到有缺页消息
            continue;
        if (msg.event != UFFD_EVENT_PAGEFAULT)
            continue;

        unsigned long addr = msg.arg.pagefault.address & ~(page - 1);
        memset(src, 0, page);
        snprintf(src, page, "第 %d 次缺页由用户线程处理（页地址 %#lx）", ++count, addr);

        struct uffdio_copy copy = {
            .dst = addr, .src = (unsigned long)src, .len = page, .mode = 0,
        };
        if (ioctl(uffd, UFFDIO_COPY, &copy) < 0)          // 把内容放进缺页地址并唤醒
            perror("UFFDIO_COPY");
    }
    return NULL;
}

int main(void) {
    page = sysconf(_SC_PAGESIZE);

    uffd = syscall(SYS_userfaultfd, O_CLOEXEC | UFFD_USER_MODE_ONLY);
    if (uffd < 0) { perror("userfaultfd（可能需要 root 或较新的内核）"); return 1; }

    struct uffdio_api api = { .api = UFFD_API };
    if (ioctl(uffd, UFFDIO_API, &api) < 0) { perror("UFFDIO_API"); return 1; }

    size_t len = 4 * page;
    char *area = mmap(NULL, len, PROT_READ | PROT_WRITE,
                      MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (area == MAP_FAILED) { perror("mmap"); return 1; }

    struct uffdio_register reg = {
        .range = { .start = (unsigned long)area, .len = len },
        .mode  = UFFDIO_REGISTER_MODE_MISSING,            // 接管"页缺失"类缺页
    };
    if (ioctl(uffd, UFFDIO_REGISTER, &reg) < 0) { perror("UFFDIO_REGISTER"); return 1; }

    pthread_t t;
    pthread_create(&t, NULL, fault_handler, NULL);

    for (int i = 0; i < 4; i++)                           // 依次访问 4 页，每页触发一次缺页
        printf("第 %d 页的内容: %s\n", i, area + i * page);

    printf("再次访问第 0 页（不会再缺页）: %s\n", area);
    return 0;
}

一块"匿名内存"里的内容，完全由另一个线程按需"编造"出来。把第 snprintf 那一行换成"从快照文件读取对应页"或"从网络拉取对应页"，你就得到了 Firecracker 快照懒加载和虚拟机热迁移的核心思路。

出于安全考虑，许多发行版默认限制非特权用户使用 userfaultfd（/proc/sys/vm/unprivileged_userfaultfd 为 0）。UFFD_USER_MODE_ONLY 标志允许非特权用户只处理用户态访问引起的缺页；如果你的内核较老不支持，可以用 root 运行并去掉这个标志。

九、结语

回到第 1 篇开头那个看似简单的问题："程序是怎么读文件的？"

一路走来，我们发现 mmap 这一个系统调用背后，站着操作系统里最核心的一整套机制：

  • 用户态与内核态划定了安全边界；
  • 虚拟内存与页表让每个进程活在自己的世界里，也让"把文件放进地址空间"成为可能；
  • 缺页异常让一切都可以按需发生，于是映射 10GB 文件只需一瞬间；
  • 页缓存让文件内容在内存里只有一份，mmap 和 read 看到的是同一样东西；
  • 写时复制让共享与隔离兼得，fork 和程序加载因此变得廉价；
  • 而落盘、一致性、性能这些现实问题，则提醒我们：没有免费的午餐，每一种便利都有它的代价。

mmap 的思想可以浓缩成一句话：

不要搬运数据，去改变看待数据的方式。

不是把文件内容拷贝到程序里，而是调整页表，让程序"看到"文件本来所在的那块内存。理解了这一点，你再看到任何"映射"——内存映射 I/O、虚拟机的两阶段翻译、用户态驱动、零拷贝网络——都会觉得似曾相识。
