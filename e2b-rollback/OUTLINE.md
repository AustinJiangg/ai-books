# 大纲

**书名**：《E2B 沙箱快照回滚从零讲透》

**读者**：会一点编程、用过命令行的新手。不要求懂虚拟机、KVM、Firecracker、页表、文件系统，用到时从头讲。

**目的**：花几个小时读完，能把“给一台正在运行的沙箱存个档，过一会儿再原地读档”这件事从头到尾讲清楚：

- 为什么要做，原生的 pause / resume 为什么不够；
- 一次 checkpoint、一次 restore，宿主机上依次发生了什么；
- 怎么做到“只为改动付费”：脏页跟踪、内存差分树、磁盘分层；
- 怎么保证“回得去、回得对”，失败时怎么办；
- 到底多快，这些数字是怎么量出来的、能说明什么、不能说明什么；
- 测试怎么证明它是对的；
- 做过哪些优化，还剩哪些问题、往后怎么改。

概念讲透，只读不练，不安排动手实验。

**写法**：从现实问题出发，先讲“为什么需要”，再讲“是什么”，最后讲“这套实现怎么做、坑在哪”。多用生活类比（存档 / 读档、账本、图书馆分层书架）和图，公式只出现一处（回滚集），并配例子。每篇末尾有“本篇小结”表格。

**代码**：以讲清原理为主，不逐函数讲解源码，不给读代码的路线。正文只在必要时放几行示例，帮助理解：

- SDK 调用：`sandbox.checkpoint.create / restore / list / delete`；
- Firecracker 新增的接口长什么样；
- 计时、能力上报、错误 `reason` 这类能直接看到的输出。

**依据**：以 [AustinJiangg/e2b-infra](https://github.com/AustinJiangg/e2b-infra) 仓库里的现状为准，只讲这套快照回滚是怎么实现的，不讲官方 E2B 的新功能。

- **代码**：仓库根目录的 `0001-adapted-for-arm-architecture.patch`（orchestrator 侧的实现）、`firecracker.arm`（带扩展的 Firecracker）和 SDK 覆盖层 `e2b-deploy/dep/e2b-sdk-checkpoint/`。用来核对事实，正文不展开讲代码。
- **Firecracker 源码**：e2b-infra 里只有 `firecracker.arm` 二进制。Firecracker 一侧的事实以编出它的源码为准，正文给少量关键片段，只标源码目录内的路径和函数名，不加链接、不写仓库与分支名。改动清单见附录 A。
- **设计说明与测试数据**：仓库 `rollback/` 下的设计文档、测试脚本（`rollback/scripts/`）和鲲鹏 950 上的测试结果。正文按新手的顺序重新组织，不照搬。
- **只讲技术**：作者、团队、项目交付、内部仓库和分支名这些与实现无关的信息，书里一概不写。

本书自成一体。部署、网络、存储只讲到本书用得到的程度，详见同仓库的《E2B 部署从零讲透》《E2B 沙箱网络从零讲透》《E2B 沙箱存储从零讲透》。

**规模**：20 篇加 1 个附录（Firecracker 改动地图），每篇约 2700～5000 个汉字，合计约 7.9 万汉字，62 张图。

**名词**：正文统一用这几个说法，第 1 篇给出对照表。

| 本书说法 | 英文 / 接口名 | 一句话 |
|---|---|---|
| 存档 / 保存点 | checkpoint（`CreateCheckpoint`） | 把沙箱此刻的现场记下来 |
| 读档 / 回滚 | restore（`RestoreCheckpoint`） | 把**同一台活着的**沙箱原地变回那一刻 |
| 原生快照 | pause / resume（`Sandbox.Pause`、`ResumeSandbox`） | E2B 原有的“停下、存盘、离场、改天重建”的路径 |
| 冻结窗口 | `frozen`（pause 到 resume） | 业务真正感觉到的停顿 |
| 纪元 | epoch | 两次“脏页记录清零”之间的那段时间 |
| 回滚集 | revert set | 读档时必须写回的那批页 |
| 账本 | `Store` | orchestrator 内存里记着树、层、引用计数的那几张表 |

**全书的主线**：快照回滚要同时做到三件事，全书反复回到这三件事。

| 要做到 | 一句话答案 | 主要在哪几篇 |
|---|---|---|
| **回得对**：内存、CPU、设备、磁盘回到同一个时刻 | 宿主侧在同一个冻结窗口里一起存、一起换；拿不准就报错，绝不静默写错 | 第 2、6、7、11～13 篇 |
| **回得快**：代价只跟“改了多少”有关，跟“虚机多大”无关 | 只存改过的页（差分树）、磁盘封存只改名（分层）、在活着的进程里原地写回，什么宿主资源都不重建 | 第 3、8～11 篇 |
| **讲得清**：多快、对不对、坏了怎么办，都拿得出证据 | 三个钟分开量、按改动量分档；三层测试；每次调用回报 `memMode`，失败按 `reason` 分级 | 第 13、16、17、19 篇 |

**贯穿全书的几个事实**，正文会反复回到这里：

- 沙箱里不装任何代理。SDK 把请求发往沙箱的 49984 端口，宿主上的 orchestrator 代理在转发前把它截下来自己处理，沙箱里其实没人监听这个端口
- 对外只有四个 RPC（Create / Restore / List / Delete）加一个 `/health`
- Firecracker 只加了三处：快照请求多一个 `dirty_bitmap_path` 字段，新增 `PUT /snapshot/save-dirty-bitmap` 和 `PUT /snapshot/rollback` 两个端点。它不知道“树”是什么
- 读档在**同一个 Firecracker 进程**里原地完成：沙箱 ID、IP、端口映射、tap、NBD 设备、内存映射都不重建
- 账本只活在 orchestrator 进程内存里，启动时会把产物目录清空，从不读盘恢复。所以 checkpoint 只在沙箱“当前这一代”有效，orchestrator 重启、原生 pause / resume、迁移之后全部失效，把目录拷走也恢复不了
- 产物盘是 ext4，不支持 reflink。所以内存不能“每代克隆一份再改”，只能“每代只存差分、按页沿祖先找内容”
- 每个沙箱的第一个 checkpoint 默认是全量（2 GiB 内存约 0.5 秒），之后才是增量（几十毫秒）
- 脏页跟踪有三种后端：鲲鹏 950 上用硬件 HDBSS，其他机器用 KVM 写保护，没开就退回全量。功能都对，只是代价不同，而且会在启动日志和每次调用的 `memMode` 里说出来
- 设计目标是增量 checkpoint ≤ 200 ms、restore ≤ 100 ms，按客户端墙钟 p50 判定。在 950 的混合负载上，128 MiB 以内两项都达标，256 MiB 的 restore 开始超线
- 回滚管不到沙箱外面：外部数据库、已发出的请求、跨越回滚的 TCP 连接都不会跟着回去；单调时钟会倒退

## 第一部分　为什么要做：问题、基础与取舍

### 第 1 篇　让沙箱能回到上一步

- **一个场景**：一个 AI Agent 在沙箱里修 bug。它拉代码、装依赖、准备数据、起服务，花了好几分钟；然后升级一个组件、改配置、跑测试，测试失败，环境也被弄乱了。
  - 想要的是：在“准备完成”那一刻存个档，失败了就读档，换方案 B 再试。
  - 打个比方：游戏里的存档 / 读档。但存的是一整台正在运行的电脑，而且要快到可以一个任务里用十几次。
- **为什么“重来一遍”不行**，对比三种做法：
  - **重建沙箱**：慢，前面的准备全部重做；
  - **应用层撤销**：不知道一次操作改了哪些文件、起了哪些进程、内存里留下了什么；
  - **虚机级快照**：把整台机器的现场一起存下来。
- **用起来长什么样**：
  - 四个 SDK 调用；
  - 一段五行的示例：写 v1，存档，改成 v2，读档，读出来又是 v1。根盘文件和 `/dev/shm` 里的内存文件一起回来。
- **三条硬要求**，后面每篇都在回应：
  - **高频**：一个任务十几次，单次成本必须低；
  - **低延迟**：增量 checkpoint ≤ 200 ms、restore ≤ 100 ms；
  - **沙箱不能中断**：ID、IP、端口、外部持有的引用都要保留。
- **先给结论**：在鲲鹏 950 上，改动 64 MiB 时增量存档、读档的客户端耗时中位数是 41.4 ms、46.0 ms；首次全量约 0.5 秒。
- **全书地图**：一张图从上到下画五层（SDK → orchestrator 代理与 Checkpoint Service → 账本 → 分叉版 Firecracker → KVM / 硬件），旁边是宿主本地的产物盘。标出各篇讲哪一块。

### 第 2 篇　基础一：一台沙箱的“现场”由什么组成

- **从进程到虚拟机**：
  - 为什么 E2B 用虚拟机而不是容器做沙箱。对比三种隔离：进程、容器、microVM；
  - KVM 是什么：内核里让 CPU 直接跑客户机代码的模块；
  - Firecracker 是什么：一个只保留最少设备的“虚拟机外壳”进程。它砍掉了什么，这对快照意味着什么：要存的设备状态少，好做。
- **E2B 的沙箱模型**，只讲本书用得到的：
  - 模板与沙箱：用户沙箱其实是从模板快照“恢复”出来的；
  - 内存按需拉取：uffd 缺页时才从模板 memfile 取；
  - 磁盘分层：模板 rootfs 是只读底，每个沙箱一层自己的写层，经 NBD 设备交给虚机；
  - orchestrator 是宿主上管这些沙箱的进程。
- **一台沙箱的“现场”有七项**：
  - 内存
  - vCPU 寄存器
  - 中断控制器（ARM 上是 GIC）
  - virtio 设备的队列状态
  - 磁盘内容
  - 时钟
  - 外部世界：连接、数据库

  每一项回滚后怎么样，用一张表说清。前六项回得去，第七项回不去。
- **一致性：为什么必须是同一瞬间**。
  - guest 的 page cache 里有还没刷盘的数据，文件系统日志写了一半。
  - 如果内存是 T1 时刻、磁盘是 T2 时刻，恢复后 guest 内核可能直接报文件系统损坏。
  - 推论：存档必须先把虚机停住（pause），在一个“冻结窗口”里把内存和磁盘一起处理掉。
- **恢复的两种形态**：
  - **重建**：新起一个进程，加载快照文件。这是原生 resume 的做法；
  - **原地**：往活着的进程里写回。这是本书的做法。
- **一个判断快照是否正确的强判据**：回滚后，不只是数据对，沙箱还要能继续干活（命令能跑、文件能写、后台进程接着跑）。
- 配图：
  - `02-1` 宿主上一台沙箱的样子：Firecracker 进程、guest 内存、NBD 与写层、tap 与网络槽位、orchestrator；
  - `02-2` 七项状态与回滚边界：沙箱内的回得去，沙箱外的回不去；
  - `02-3` 一致性反例：内存 T1 + 磁盘 T2 = 损坏。

### 第 3 篇　基础二：页、脏页、稀疏文件与位图

为后面的“只为改动付费”打好四块地基。

- **页**：内存按 4 KiB 一页来管理。2 GiB 的 guest 内存是 524288 页。guest 物理地址（GPA）和页号是什么关系。
- **脏页**：被写过的页。为什么只想存脏页：大多数时候，两次存档之间只改了一小部分内存。
  - 怎么知道哪页被写过：先给一个直觉，“把页设成只读，第一次写就会被抓到”。细节留到第 8 篇。
- **位图**：用 1 个比特记一页脏不脏。2 GiB 内存的位图只有 64 KiB（8192 个 u64 字）。
  - 位图的并集、按字跳过全 0。
  - 这就是后面“与虚机规格线性相关的只有两次位图扫描，常数极小”的由来。
- **稀疏文件**：文件的逻辑大小等于整份内存，但只有写过的页占磁盘，没写过的区间读出来是 0。
  - `SEEK_DATA` / `SEEK_HOLE`；
  - 磁盘实占（`st_blocks`）与逻辑长度的区别。这个区别在第 17 篇读产物大小时要用。
- **写时复制与分层**：磁盘的“只读底 + 写层”。读的时候从上往下找，写的时候只写最上层。
- **reflink**：XFS、Btrfs 能让两个文件共享同一批磁盘块，写时才分裂；ext4 不行。
  - 为什么这一条决定了第 9 篇的整个设计：没有 reflink，“每代克隆一份完整内存再覆盖脏页”就退化成每次都真拷 2 GiB，而且完全静默。
- 配图：
  - `03-1` 页、位图与稀疏文件：同一份 2 GiB 内存的三种表示；
  - `03-2` 写层叠在只读底上：读往下找、写只落顶层；
  - `03-3` 有 reflink 与没有 reflink 时“克隆一份”的代价对比。

### 第 4 篇　为什么不直接用原生快照：目标、原则与取舍

- **E2B 原生快照怎么做**，只讲骨架，细节留到第 15 篇：
  - `Sandbox.Pause`：停虚机，导出内存差分和磁盘差分，Firecracker 进程退出，沙箱离场；
  - `ResumeSandbox`：新起进程，靠缺页把工作集慢慢换回来。
- **三条理由，原生不适合“高频小回退”**：
  1. **会中断沙箱**。导出磁盘增量的 `ExportDiff` 的参数之一就是“关掉沙箱”的回调；恢复也要新建进程。
  2. **成本模型不对**。代价看“虚机多大”，不看“回退了多少”。950 实测：改 0 MiB 时 pause 也要约 250 ms，resume 各档都在 110 ms 上下。
  3. **ARM 适配上增量已经退化**。uffd 的写保护在移植时被注释掉，判据变成“换入过就算脏”。这条后来在原生路径上修掉了（第 15 篇），但前两条与判据精不精确无关。
- **硬约束**：
  - aarch64（鲲鹏 920B / 950）；
  - 产物盘 ext4；
  - 不改动原生路径的行为（纯加法）；
  - 沙箱内不装代理；
  - orchestrator 与 Firecracker 版本必须成对。
- **四条设计原则**，全书都在实现它们：
  1. 成本只与改动量挂钩；
  2. 不重建任何宿主资源；
  3. 宁可报错，不可静默损坏；
  4. 能力随硬件自动降级，但要说出来。
- **明确不做什么**：
  - 宿主崩溃恢复
  - 跨节点迁移
  - 长期持久化
  - 进程已死后的恢复
  - 跨沙箱共享 checkpoint

  划界换来的简化：一整类问题不存在了。划界的代价：备份带不走，重启就失效。
- **三条被否决的路线**：
  - 在 guest 里跑 CRIU 式代理：恢复不了内核态，也解决不了磁盘；
  - 独立的 checkpointd 进程：要触达 orchestrator 私有的活体对象；
  - 全部塞进 Firecracker：磁盘根本不在 Firecracker 里，而且会开大 seccomp 的口子。

  最终形态是：**语义在 orchestrator，机械动作在 Firecracker**。
- **一句话的交易**：用“绑定沙箱生命周期”换掉产物自足和账本持久化，换来零拷贝封存、原地回滚，以及只随回退跨度增长的成本曲线。

  - `04-2` 四条原则落到哪些机制上；
  - `04-3` 三条备选路线与最终分工。

## 第二部分　怎么做：设计与实现

### 第 5 篇　总体架构：请求发往沙箱，却由宿主应答

- **难题**：打快照第一步是暂停虚机，而沙箱里的程序暂停不了自己。可是对用户来说，`sandbox.checkpoint.create()` 最好和 `sandbox.commands.run()` 一样，是沙箱对象上的一个方法。
- **拦截**：
  - SDK 把请求发到沙箱地址的 49984 端口；
  - orchestrator 的代理先解出（沙箱 ID, 端口），命中 49984 且路径是 checkpoint 的就不转发，交给 Checkpoint Service；
  - restore 进行中，发往这个沙箱的其他请求直接回答，不放进去。
- **为什么要再校验一次 token**：拦截点在代理自己的鉴权之下，绕过者必须自己补上。这是一个经典的安全教训。
- **分层与“语义只在一处”**：

  | 层 | 负责 | 不负责 |
  |---|---|---|
  | SDK | 发四个 RPC | 不知道请求没进沙箱 |
  | 代理 | 改道 | 不懂 checkpoint |
  | Service | 编排、串行、失败分级、计时 | 不碰 guest 内存 |
  | 账本 | 树、回滚集、层清单 | 不和 Firecracker 说话 |
  | Sandbox 对象 | 暂停、封层、换视图、清 conntrack | 不知道有树 |
  | Firecracker | 写快照、导出脏页图、原地回滚 | 不知道有树 |
  | KVM / CPU | 记脏页 | —— |

- **账本里有哪些表**：`bySandbox`、`bases`（当前基准与断链标志）、`rootfs`、`layerRefs`、`children`、`opLocks`……只在进程内存里。
- **Firecracker 只分叉了三处**，既有行为只有两处有意的变化（暂停前收尾挂起的设备访问；带内存文件的快照不 fsync）；版本必须成对，否则未改过的 Firecracker 返回 400 `Invalid request method and/or path`（中间有代理时可能是 404），被翻译成“这个 firecracker 不支持原地回滚”。
- **产物目录**：`/orchestrator/build/checkpoints/<沙箱>/ckpt_<时间>/`，里面有 `snapfile`、`mem_diff`、`mem_bitmap`、`rootfs.header`、`manifest.json`，以及 `layers/`。
  - 每个文件谁写、谁读、什么时候消失；
  - 原子提交：先写 `.tmp` 再 rename，不 fsync。`prepared` / `committed` 两个状态保证半写完的快照永远不会成为恢复目标。
- **`mem_mode` 字段为什么存在**：唯一理由是让“静默退化成全量”变得可见。
- 配图：
  - `05-1` 一次请求的路径：SDK → 49984 → 代理拦截 → Service，以及普通请求照常进沙箱；
  - `05-2` 分层与边界：谁知道“树”，谁只做机械动作；
  - `05-3` 产物目录树与各文件的生命周期。

### 第 6 篇　一次存档，逐步走：checkpoint

- **进入服务（窗口外）**：
  - 鉴权；
  - `WithoutCancel`：客户端放弃也不能让虚机停在暂停态；
  - 拒绝已撕裂的沙箱；
  - 取沙箱操作锁；
  - 锁内再确认沙箱还在、还是同一代；
  - 产物盘水位检查。
- **决定全量还是增量**：三个条件。
  - 没有父亲且开了全量根，就是全量；
  - 开了脏页跟踪、链没断、不是根，就是增量。
- **Prepare**：个数上限、字节上限、代际准入；建目录，写 `prepared` 的 manifest。此时条目对外不可见。
- **冻结窗口**，逐步：
  1. pause
  2. （仅全量）导出活跃脏页图
  3. 一次调用写出 vmstate、稀疏内存差分和位图侧车
  4. 封存写层：刷屏障、挂新空写层、换指针
  5. resume（无论前面成败，一定执行）
  6. 层文件移入 store，放在窗口外

  每步的代价与什么成正比：只有“写快照”这一步与本代脏页数相关，其余是常数。
- **为什么层文件挪到窗口外**：跨文件系统时挪动是一次拷贝，放在 resume 之后，冻结时长就不随改动量增长。
- **顺序约束一**：内存与磁盘在同一个窗口里（呼应第 2 篇）。
- **提交（窗口外）**：`AppendLayer` 写层 sidecar 和 header，`Commit` 把文件 rename 到位、发布进账本，基准 ← 本条目。
- **这里的失败不再干净**：写快照一旦成功，“纪元就前进了”，Firecracker 已清空脏页记录，差分文件成了那段脏页的唯一副本。所以之后的失败走三层降级：
  1. 正常提交；
  2. 隐藏提交（保住纪元）；
  3. 标记断链（此后拒绝恢复）。

  第 13 篇细讲。
- 配图：
  - `06-1` checkpoint 时间线：窗口外、冻结窗口、窗口外三段，每步标注代价是常数还是随改动量；
  - `06-2` 纪元前进前后：失败处理从“删干净”变成“三层降级”。

### 第 7 篇　一次读档，逐步走：restore

- **准备（窗口外）**：
  - 取条目：只给本代、非隐藏、已提交的；
  - 读各层 `.meta`，装配目标磁盘视图。为什么能挪到窗口外：读的都是不可变的东西，同沙箱操作又已被串行；
  - 产物盘水位检查：物化最多一份内存那么大；
  - 打开 restore 窗口，丢弃代理到这个沙箱的连接池。
- **冻结窗口**，逐步：
  1. pause，后台同时启动 conntrack 清理
  2. 导出活跃脏页图
  3. 物化：算回滚集，沿祖先链解析内容，写稀疏的 `revert_mem` 和 `revert_bitmap`
  4. `PUT /snapshot/rollback`：Firecracker 的九个阶段（第 11 篇）
  5. 整体换磁盘视图（挂载不动）
  6. 等 conntrack 清理结束
  7. resume
- **顺序约束二**：暂停之后才导出、才物化，否则物化文件会漏页。Firecracker 的覆盖校验是保险，顺序本身才是正确性的来源。
- **顺序约束三**：conntrack 必须在放流量回来之前清完。
- **收尾（窗口外）**：
  - 基准 ← 目标，树从这里长出新分支；
  - 磁盘账本 ← 目标 header；
  - 再等 guest 里的 envd 应答（上限 45 s），墙钟在这里校正。
  - **为什么先更新账本、再等 envd**：账本跟着状态走，不跟着 RPC 走。
- **冻结窗口里到底有什么**：一张对照表。与虚机规格有关的只有两次位图扫描，常数极小。所以 2 GiB 和 16 GiB 的沙箱回退同样多的页，冻结窗口几乎一样长。
- **三个钟**：
  - 客户端墙钟：调用方等了多久；
  - 冻结窗口：业务停了多久；
  - 宿主分阶段计时：停的时间花在哪。

  先看哪个钟异常，就知道往哪层找。
- **八条顺序约束汇总**：破坏后能立刻报错的只有一条，其余都是静默的。由此引出第 13 篇的不变量清单。
- 配图：
  - `07-1` restore 时间线：准备、冻结窗口（conntrack 并行）、收尾；
  - `07-2` 三个钟的嵌套关系；
  - `07-3` 八条顺序约束一览：哪条破坏后会报错，哪条会静默出错。

### 第 8 篇　怎么知道哪一页被写过：脏页跟踪与 HDBSS

- **脏页跟踪为什么既是性能问题又是正确性问题**：多记只是慢，漏记一页回滚就会漏写一页。
- **三种办法**：
  - **KVM 写保护 + 脏页日志**：把页设成只读，第一次写陷出到内核，记一笔；
  - **userfaultfd 写保护**：在用户态抓写；
  - **HDBSS**：ARMv9.5 的硬件能力，鲲鹏 950 实现了。CPU 直接把脏页的物理地址写进每个 vCPU 的缓冲区，不陷出。

  三者给上层的是同一种位图，语义一致，只差代价。
- **KVM 脏页日志的“破坏性读”**：读一次就清零。这正是“纪元”的由来，也是“写快照成功后失败不再干净”的根源。
- **HDBSS 怎么启用**：
  - 内核与 Firecracker 两侧各做一件事，六个前提；
  - 引导和加载两条路径都要武装；
  - 缓冲区大小（order），溢出时怎么办。
- **能力上报**：
  - 启动日志 `checkpoint capabilities` 一行，带理由；
  - Firecracker 自报 `hdbss` / `kvm-wp` / `off`；
  - `FC_HDBSS_REQUIRED` 让生产部署“宁可启动失败”；
  - 呼应原则四。
- **判据差异：读也算脏**。uffd 的“换入即脏”是怎么让增量塌缩成“整个工作集”的；本方案为什么不受影响。
- **精确的代价**：
  - 软件写保护每个首次写都要陷出一次；
  - HDBSS 几乎透明。
  - 什么时候不该开：从不 checkpoint 的沙箱。由此引出“按沙箱按需武装”这个候选方向（第 20 篇）。
- 配图：
  - `08-1` 三种脏页跟踪的路径对比：谁抓写、在哪记、要不要陷出；
  - `08-2` 纪元与破坏性读：每次快照或回滚都清零，位图恰好覆盖一段区间；
  - `08-3` 能力随硬件降级：hdbss → kvm-wp → off（全量），每级在哪里报出来。

### 第 9 篇　内存差分树：只存改过的页，还能回到任意一代

- **问题**：2 GiB 内存，20 个存档，每次改 40 MiB。三种存法对比：
  - 每代全量：40 GiB；
  - 每代自足：依赖 reflink；
  - 每代只存差分：约 2 GiB + 20 × 40 MiB。

  ext4 上只能选第三种。
- **一代产物**：稀疏差分 `mem_diff` 加位图侧车 `mem_bitmap`。
  - **核心不变量**：位图 `E_x` 恰好是从“父亲那一刻”到“x 那一刻”之间写过的页。它由两侧共同维持：Firecracker 写快照和回滚都清零，账本里新条目的父亲取当时的基准。
- **树，而不是链**：
  - ck1 → ck2 → ck3，回滚到 ck1，再存 ck4、ck5，就分叉了；
  - **创建时间的先后不等于依赖关系**；
  - “当前基准”与条目的 `ParentID` 是两份不同的记录。
- **回滚集**，全书唯一的公式：

  ```
  回滚集 = （基准 → 最近公共祖先 → 目标 两段路径上各代位图的并集） ∪ 活跃脏页
  ```

  - 用三段式的白话证明：不在回滚集里的页，当前内容 = 基准时刻 = 祖先时刻 = 目标时刻；
  - 两段路径缺一不可的反例；
  - 为什么必须并上活跃脏页的反例：页 42；
  - 这是“够用”的集合，不是“最小”的集合；
  - 一个完整的跨分支例子：ck5 → ck3。
- **内容解析**：要写回的某一页，它在目标时刻的内容在哪？沿目标的祖先链往上找，第一个位图里有它的那一代就是。全量根的位图全 1，所以一定能找到。
- **物化**：把回滚集和内容写成两个文件交给 Firecracker。短读就是错误，缺侧车就报错，绝不降级成“全量回滚”。
- **成本模型**：
  - 创建是 O(本代脏页)；
  - 恢复是 O(回滚集)，与链深无关；
  - 为什么即使目标很小，当前偏离多了恢复也慢。
- **全量根为什么是默认**：模板 memfile 不在本地，树根存一份全量，让回滚路径不跨网络。这是唯一保留的固定开销，有开关。
- **删除、隐藏与合并**（概念部分，空间部分见第 14 篇）：被后代依赖的节点转为隐藏；合并（compact）把隐藏节点并进孩子，不改变任何 restore 的结果；条目数有上界 ≤ 2V + 1。
- 配图：
  - `09-1` 三种存法的空间与时间对比；
  - `09-2` 回滚后分叉：ck1～ck5 的树，以及“当前基准”的移动；
  - `09-3` 回滚集图解：从 ck5 到 ck3，经最近公共祖先 ck1，哪些位图参与求并；
  - `09-4` 内容解析：沿祖先链找一页的来源。

### 第 10 篇　磁盘分层：封存只改个名字

- **运行中的读写落在哪**：
  - guest → virtio-block → NBD 设备 → orchestrator 里的 Overlay → 活写层或只读层；
  - 活写层与磁盘一样大，却是稀疏的；
  - 怎么知道哪些块写过。
- **存档：封存旧写层，接替新写层**：
  - 暂停后先刷屏障，再挂一个新的空写层，把旧写层追加进只读层栈，换指针；
  - **封存就是改名**：层文件就是 guest 自己写出来的那个文件，没有搬一个字节；
  - 不等 msync，把 O(改动量) 变成 O(1)，以及这样做为什么仍然安全：checkpoint 不承诺活过进程。
- **读档：换上目标视图，再给一个新的活写层**：
  - 不是把旧写层复制回来；
  - 视图在暂停前就装配好，暂停后整体换指针；
  - 为什么磁盘一换，内存和设备也必须一起换。
- **账本怎么记**：
  - `rootfs.header`：完整磁盘每个区间来自哪一层；
  - `.meta`：本层保存了哪些块；
  - 磁盘偏移与层文件偏移相同（恒等映射）。
- **删除与回收**：删记录不等于删层；层引用计数，最后一个引用它的视图放手才删。
- **层合并**：两层合一层，保留读取结果，减少文件数。当前什么时候允许合并。
- **长跑后的成本**：块归属索引、批量建目标索引；视图块数增长让 restore 变慢的问题（第 18 篇的案例）。
- **与原生 pause 的区别**：原生导出差分后不再使用原 Overlay，本方案一直在原 Overlay 底下换指针。
- 配图：
  - `10-1` 一次块读写的路径：guest 到层文件；
  - `10-2` 存档前后的层栈：旧写层改名成只读层，新空写层接上；
  - `10-3` 读档换视图：目标层栈 + 新写层，旧的哪些层还被引用；
  - `10-4` 引用计数与层合并。

### 第 11 篇　在活着的虚机里原地回滚：Firecracker 的三处扩展与九个阶段

- **为什么必须分叉 Firecracker**：上游已经有快照，但缺三样东西。最小化原则：分叉越小，跟上游越容易，出了问题越容易判断是不是自己引入的。
- **扩展一：`dirty_bitmap_path`**：差分文件不自说明，位图必须在同一次调用里落地，全量快照也写（全 1）。
- **扩展二：`PUT /snapshot/rollback`**：
  - `resume_vm: false`；
  - 回滚前的校验；
  - 错误分级：HTTP 状态码加结构化字段。
- **扩展三：`PUT /snapshot/save-dirty-bitmap`**：虚机暂停时导出“自上次清零以来”的脏页图。为什么非有不可：读档时要并上活跃脏页。
- **FCDB 位图格式**：逐字节布局、页索引空间、几何校验、尾字掩码。两侧实现的对称性。
- **九个阶段**，以“提交点”为界分成前后两半：
  1. 校验
  2. 静默在途 I/O
  3. 取活跃脏图与覆盖校验

  **提交点**：在此之前失败，虚机原样恢复；在此之后失败，就是“撕裂”。

  4. 内存写回
  5. vCPU
  6. 中断控制器 GIC
  7. 设备状态
  8. VMGenID
  9. 重置脏页基线

  每阶段做什么、为什么排在这里：
  - 内存先于设备；
  - VMGenID 后于内存；
  - 阶段 9 与账本“基准 ← 目标”是同一件事的两半。
- **`validate_topology`**：快照与运行对象的设备拓扑必须一致；balloon、vsock、vhost-user block 明确拒绝。
- **seccomp**：回滚路径需要额外放行的系统调用。
- **计时与回报**：`fc_validate`、`fc_memory`、`fc_vcpus`、`fc_gic`、`fc_devices`。
- 配图：
  - `11-1` 三处扩展在一次 checkpoint / restore 中各在哪一步被调用；
  - `11-2` 九个阶段与提交点：左边失败可恢复，右边失败即撕裂；
  - `11-3` FCDB 位图格式示意。

### 第 12 篇　回到过去之后：网络、设备与时间

“guest 回到了过去，外面的世界还在现在”带来的一组特有问题。

- **网络 RX 描述符缓存**：
  - 现象：回滚后网络收不到包；
  - 背景：virtio 队列是什么；
  - 根因：设备缓存了属于“未来”的描述符；
  - 修法，以及连带要放行的 seccomp 条目。
- **连接跟踪（conntrack）**：
  - 现象：跨越回滚的连接挂死；
  - 根因：宿主和沙箱命名空间里的 NAT 表项属于另一条时间线；
  - 两张表两种清法；
  - 怎么删：每批一次整表扫描，按代价模型选路；
  - 时机：pause 后启动、与回滚并行、resume 前等它结束；
  - 代理侧的连接池也要丢；
  - 对使用者的结论：跨越 restore 的 TCP 连接一律作废，要重连。
- **VMGenID**：告诉 guest“你被回滚过”的唯一一次通知。为什么要在内存之后。
- **时间**：
  - 单调时钟会倒退；
  - 墙钟在 restore 成功返回前由 envd 初始化校正；
  - 用户态缓存的随机数状态会回退，需要业务重新初始化。
- **队列页的脏标记**：Firecracker 写回走 VMM 映射，KVM 不记录。这批页要在阶段 9 之后重新标脏，否则下一代位图会漏掉它们。
- **在途调用会怎样**：
  - restore 期间别的命令、文件请求收到 409 `sandbox_restored`；
  - 已发出响应头的流只能表现为截断；
  - 4 沙箱 × 50 轮的测试证明：恢复返回后立即发命令没问题。
- **检查表**：还有哪些地方可能藏着同类问题，以及为什么要有逐设备的诊断日志。
- 配图：
  - `12-1` 两条时间线：guest 回到 T0，宿主 conntrack、对端、代理连接池还在 T1；
  - `12-2` conntrack 清理与回滚并行的时序；
  - `12-3` 回滚后各种“时间”的去向：墙钟、单调时钟、随机数。

### 第 13 篇　宁可报错，不可静默损坏：失败分级与不变量

- **总纲**：操作的是一台活虚机的内存。一次错误的回滚不会让它崩溃，只会让几页内容属于另一个时刻，然后很久以后才以莫名其妙的方式暴露。又没有“兜底重建”这条退路，所以失败必须分级、必须说出来。
- **提交点把失败切成两半**。
- **restore 的四档失败**：

  | 失败点 | 沙箱状态 | `reason` | 调用方该做什么 |
  |---|---|---|---|
  | 树解析不了 | 原样可用 | `chain_broken` | 先存一个新档 |
  | 提交点前其他失败 | 原样可用 | `internal` | 换目标或重试 |
  | 提交点后失败 | 撕裂，虚机保持暂停留作取证 | `torn` | 只能销毁重建 |
  | envd 45 s 不应答 | 已回到目标 | `guest_unresponsive` | 按业务决定 |

  - 45 s 为什么刻意低于 SDK 的超时：让失败由服务端报，而不是客户端超时；
  - 撕裂按“代”记，不按沙箱 ID。
- **checkpoint：纪元不能丢**，三层降级：正常提交 → 隐藏提交 → 标记断链。“宁可留垃圾，也不留坏链”。
- **隐藏条目、断链、账本污染（`rootfs_poisoned`）** 各是什么，怎么恢复正常。
- **完整错误表**：
  - `busy`、`disk_full`、`too_many_checkpoints`、`checkpoint_bytes_limit` 等；
  - 哪些可重试，哪些绝不能自动重试；
  - SDK 的异常类层次；
  - 四个 RPC 不自动重发，服务端也不取消。
- **不变量清单**：把前面各篇散落的约束收成一张表，并标明哪个单元测试或属性测试在守着它。
- 配图：
  - `13-1` restore 失败决策图：按失败发生在哪，走到四档之一；
  - `13-2` checkpoint 的三层降级；
  - `13-3` 错误 `reason` 速查：可重试 / 换个做法 / 销毁重建。

### 第 14 篇　并发、生命周期与空间：一个沙箱能存多少档

- **锁的层级**：
  - `Store.mu` 保护账本，持锁时不做 I/O；
  - `opLocks[沙箱]` 让同一沙箱的操作串行，排队超时回 `busy`。

  跨沙箱可以并发，同沙箱串行。为什么这样分。
- **暂停窗口本身就是静默机制**；Overlay 在 NBD dispatcher 底下换指针。
- **请求生命周期 ≠ 操作生命周期**：`WithoutCancel` 的又一处体现。
- **“这一代”是什么**：
  - 一个 Firecracker 进程就是一代；
  - 换代的情形：沙箱销毁、Firecracker 或 orchestrator 重启、宿主重启、迁移、原生 pause / resume；
  - 沙箱内普通进程退出不算换代。
- **一个思想实验：把产物目录完整拷走**，为什么还是恢复不了。四层依赖：
  1. 恢复机制要求活体；
  2. 磁盘产物不自足（相对模板的增量）；
  3. 账本不从磁盘加载；
  4. 缺运行时环境。

  其中内存那一半其实已经自足。这是取舍，不是缺陷。
- **删除与空间回收**，从用户视角讲：
  - `delete` 做了什么：可见条目消失，但被依赖的数据不一定马上释放；
  - “保留最新 N 个、删最旧的”在合并启用时会收敛；
  - 两种每沙箱上限：个数和字节，默认关闭；
  - 在字节上限下删哪个才能腾出空间：删最旧的，删最新的几乎没用。
- **容量规划**：
  - 一个沙箱的 checkpoint 大约占多少盘；
  - 节点产物盘怎么估；
  - 多租户节点的建议。
- 配图：
  - `14-1` 两级锁：全局账本锁与按沙箱的操作锁；
  - `14-2` 代际边界：哪些事件会让旧 checkpoint 全部失效；
  - `14-3` “拷走目录”思想实验的四层依赖；

## 第三部分　和原生快照一起用

### 第 15 篇　两种快照的分工：原生 pause 的精确增量与叠加使用

- **两种快照各解决什么**：
  - checkpoint / restore：活沙箱里的高频快速回退；
  - 原生 pause / resume：沙箱离场、长期保存、跨节点。

  根本差别：活体原地，还是自足重建。逐项对比机制与成本。
- **原生 pause 的内存增量为什么不精确**：
  - 判据在 ARM 上塌缩成“驻留即脏”；
  - 再叠加两个放大：每代都是新进程，换入即脏。

  “改 12 MiB，导出 148 MiB”的现象。x86 上为什么没有这个问题。
- **只换判据还不够**：header 按 2 MiB 归并造成“地板”，粒度为什么被钉死。
- **精确增量的三处修改**：
  1. **判**：换成 Firecracker 的写跟踪位图；
  2. **存**：header 块大小从 2 MiB 降到 4 KiB，父代映射原样保留；
  3. **填**：一次 2 MiB 缺页，三级取源。

  改判据之前先立的规矩：宁可多导，不可少导。
- **与 checkpoint 叠加：累积位图**。
  - 问题：Firecracker 的位图只记“上一次快照或回滚以来”，checkpoint 会清掉它。
  - 做法：每次清零前把位图收进一个每虚机的“开机以来写过的页”集合；对不上就标“不可信”，退回驻留判据。
  - 从不 checkpoint 的沙箱不受影响。
- **怎么叠加使用**：
  - 方向规则：先用 checkpoint 快速试错，选定满意的状态后，用原生快照固化或离场；
  - 原生 resume 之后旧 checkpoint 全部作废。
- **实测并列**：950 上原生 pause 由约 245 ms 固定开销主导，resume 约 110 ms 且之后还要付懒加载；checkpoint / restore 在同档位快 1.1～14.6 倍。说明这只是量级比较，两组条件不同。
- **兼容是单向的**：新 orchestrator 读得了旧快照，旧 orchestrator 读新快照会拒绝启动。
- 配图：
  - `15-1` 两种快照的分工与叠加：Agent 工作流底下发生了什么；
  - `15-2` 原生增量的三层（判、存、填），修复前后对比；
  - `15-3` 累积位图：checkpoint 清零前把位图收进“开机以来”集合；
  - `15-4` 950 同档位 checkpoint / restore 与 pause / resume 的耗时并列。

## 第四部分　多快：性能怎么量、量出了什么、怎么变快的

### 第 16 篇　性能怎么量：口径、档位与三种失真

- **“≤ 200 ms / ≤ 100 ms”本身不是口径**：没说谁的钟、哪一次、哪个统计量。本书钉在对自己最不利的一侧：
  - 增量 checkpoint：客户端墙钟 p50，p99 并列；
  - 原地 restore：同上；
  - 全量根单列，不参与判定。
- **统计入门**：中位数、p99、最大值；样本只有 10～30 个时，p99 就等于最大值，不能推断长尾。
- **为什么按改动量分档，不按内存大小分**：同一个 2 GiB 沙箱，改 1 MiB 和改 256 MiB 是两件事。
- **条件标签**：
  - 脏页后端
  - 产物文件系统
  - 内核
  - 二进制版本

  缺标签的数字不许引用；正确性可以远程验，性能必须在宿主上测。
- **负载构造的三种失真**：
  1. 分配成本混进档位；
  2. 写放大；
  3. 负载放错层。

  解法：预热加原地覆写。文件那份故意不用 `O_DIRECT`。混合档“内存 : 文件 = 3 : 1”从哪来。
- **一次迭代怎么设计**：从基点改规定量、存档、读档回基点、校验现场。
- **冻结窗口怎么测**，以及怎么把绑在一起的变量拆开。
- **怎么读一份报告**：先看条件标签，再看 `memMode`，再看分段。
- 配图：
  - `16-1` 三个钟与达标判定口径；
  - `16-2` 三种负载失真与“预热 + 原地覆写”；
  - `16-3` 一次分档迭代的步骤。

### 第 17 篇　性能实测：在鲲鹏 950 上到底多快

- **条件**：aarch64、ext4 产物盘、HDBSS 后端、2 GiB 沙箱。
- **十二档主表**：
  - 混合 0～512 MiB、纯内存 16、纯文件 16、只读触碰 192；
  - 读法：128 MiB 以内两项达标，256 MiB 的 restore p50 为 105.6 ms，开始超线，512 MiB 两项都超；
  - “实测边界是已测的档位，不是连续区间的保证”。
- **首次全量**：0.47 s、0.50 s，主要花在写 2 GiB 的快照上。
- **分段看时间花在哪**：
  - checkpoint 的增长主要在 `snapshot`；
  - restore 的增长在 `materialize` 和 `fc_memory`；
  - `assemble_view_pre` 约 0.2 ms，`wait_envd` 约 1.5 ms。
- **产物有多大**：
  - 文件写入经过 guest 页缓存，所以也出现在内存差分里；
  - 内存差分 ≈ 名义改动的 1.03～1.04 倍，加约 21 MiB 的基底。
- **同一个 checkpoint 串行读档 100 次**：p50 13.2 ms。为什么这么快：回滚集很小。
- **HDBSS 专项**：
  - 三级证据：能力、自报、数据面；
  - 默认 order 1；
  - 为什么不给“比软件快几倍”的结论：没有同机软件后端的对照。
- **并发**：
  - 16 个沙箱同时操作时，增量存档中位数约 100 ms，读档 60～75 ms；
  - 同一沙箱四个调用方争用时会怎样。
- **哪些不能下结论**：
  - 纯文件 16 MiB 比混合 16 MiB 慢，原因未归因；
  - 两次运行的漂移；
  - 页缓存是否全热没有证实。
- 配图：
  - `17-1` 混合负载各档 checkpoint / restore 的 p50 与参考线（折线 + 200 / 100 ms 横线）；
  - `17-2` 128 / 256 / 512 MiB 档的分段构成；
  - `17-3` 名义改动量与实际产物大小。

### 第 18 篇　从单沙箱到并发长跑：做过的优化

- **起点**：第一版在单沙箱、单次操作上已经达标。之后的问题来自“很多沙箱一起做”和“反复做很久”：共享锁、冻结窗口、存储、宿主网络、GC、历史增长。
- **按问题归类讲五组优化**，每组按“现象 → 根因 → 改法 → 怎么验证”：
  1. **减少跨沙箱互相等待**：
     - 文件 I/O 移出全局锁；
     - 每次 checkpoint 不再整份重写 `index.json`；
     - 锁外删文件；
     - 子节点计数代替扫描。
  2. **缩短冻结窗口**：
     - 减少 fsync；
     - 视图装配挪到 pause 前、层移动挪到 resume 后；
     - 位图按字跳零、批量解析；
     - 连续页用 `pread`。
  3. **并发网络清理**：
     - conntrack 与回滚并行；
     - netlink 连接复用；
     - 多沙箱合批；
     - 代理 full duplex 修复流式命令偶发截断。
  4. **历史增长后的成本**：
     - 块归属索引；
     - 位图装配；
     - 层文件从不回收 → 引用计数回收；
     - 隐藏 checkpoint 无上界积累 → 合并；
     - 视图块数增长让 restore 随时间变慢。
  5. **节点级长尾**：一个沙箱的 mmap 缺页拖长 Go GC 的停顿，落进别的沙箱的冻结窗口。改法是 `MADV_POPULATE`，并把映射故障转成 I/O 错误。
- **两个值得细讲的案例**：
  - “restore 读盘量指标在并发时虚高”：指标本身也会骗人；
  - “恢复开销：一个设计取舍的来龙去脉”：第一版为什么贵，两步收回。
- **量过之后决定不做的**：为什么有些看起来能优化的点不值得做。
- 配图：
  - `18-1` 五组优化各作用在 checkpoint / restore 时间线的哪一段；
  - `18-2` 案例：GC 长停顿怎么跨沙箱传染，`MADV_POPULATE` 怎么切断；
  - `18-3` 长跑中磁盘与隐藏条目的增长：修复前线性增长，修复后收敛。

## 第五部分　对不对、往后怎么走

### 第 19 篇　测试怎么做：怎样证明“回得对”

- **三层测试**：

  | 层 | 证什么 |
  |---|---|
  | 单元测试与属性测试（代码仓库里） | 部件与不变量 |
  | 整机验收（`rollback/scripts/acceptance/`，五个单文件脚本） | 整机正确性、耗时、并发、长跑 |
  | 补充测试与开发工具（`crtest/` 20 个用例、`dev/`） | 盲区、边界、故障注入 |

  一站式入口是 `rollback/scripts/950/run.sh smoke | func | perf | long | hdbss`。
- **属性测试**：随机生成大量操作序列，每一步拿实现与一个简单的参照模型比对；还故意注入变异，确认测试真的会失败。即“先自证会失败”。
- **正确性判据**：
  - 三重证据加一条最硬的：恢复后能继续干活；
  - `checkpoint_verify.py` 在一条直链上做 59 项检查：内存、文件、删除、权限位、进程（保存后启动的进程消失，保存后被杀的进程回来）。
- **树语义**：`correctness.py` 测线性、前滚、分叉跨 LCA、删除与合并、失败。
- **与原生生命周期的组合**：checkpoint 之后再原生 pause，磁盘与内存是否完好（T39）；有没有弄坏原生生命周期（T41）。
- **并发与长跑**：
  - 多沙箱随机操作，恢复后五字段逐项一致；
  - “资源走平”怎么判；
  - 为什么要长跑。
- **为什么测试要多问一句**：四个“静默”的真实故事：
  1. 增量静默退化成全量；
  2. checkpoint 之后原生 pause，封层丢了；
  3. 把读过的页当成脏页；
  4. 判据本身静默消失。

  三条纪律：
  - 每个结论带条件标签；
  - 验收脚本故意不抽公共模块，避免拷走一半后标签变成“未知”；
  - 测试先证明自己会失败。
- **950 上的结果**：
  - 10-15 smoke：59 项通过，10 次恢复全部一致；
  - 10-13 默认 func 回归：16 个用例通过，4 个跳过；
  - 恢复后立即请求：200 次恢复、400 条命令全成功。

  并且明确列出还没测的：小时级长跑、重启 / 注入 / 配额专项、跨树回滚的端到端用例。
- 配图：
  - `19-1` 三层测试金字塔与各自的入口；
  - `19-2` 59 项检查覆盖了现场的哪些部分；
  - `19-3` 测试矩阵：已证、待证、不做。
